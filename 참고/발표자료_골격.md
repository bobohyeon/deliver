## 01. 프로젝트 개요 (2~3장)

### 슬라이드 1 — 문제 정의
- 문서를 읽는 데 드는 시간 문제 (구체적 수치나 상황 1개)
- "이런 문서를 매번 사람이 다 읽어야 하는가"
- ❗ 추상적으로 쓰지 말 것. **누가 어떤 상황에서 겪는 불편인지** 한 문장으로

### 슬라이드 2 — 해결 방안 / 시스템 한 줄 정의
```
PDF Brief AI — 문서를 업로드하면 텍스트를 추출하고,
생성형 AI가 요약과 카테고리를 자동 생성하는 웹 서비스
```
- 지원 형식, 처리 흐름 아이콘 1줄
- **범용 설계** 언급: "문서 유형과 분석 기능을 추가할 수 있는 구조"

### 슬라이드 3 — 목표 및 범위
| 구분 | 내용 |
|---|---|
| 이번 범위 (Must) | 업로드 / 추출 / 요약 / 분류 / 조회 / 검색 / 다운로드 |
| 의도적 제외 | 인증(지시서상 선택), 알림, 다중 사용자 |
| 메인 확장 | 파인튜닝 모델 적용, 문서 유형 추가, 분석기 추가 |

> **"의도적 제외"를 명시하는 게 중요.** 안 만든 게 아니라 범위를 정한 것으로 읽힘.

## 02. 프로젝트 팀 구성 및 역할 (1~2장)

### 슬라이드 4 — 역할 분담
| 팀원 | 담당 (화면 + API + 로직 한 세트) | 주요 산출물 |
|---|---|---|
| A | 업로드 / 텍스트 추출 / OCR | ERD |
| B | LLM 요약 / 카테고리 분류 | 프롬프트 설계 |
| C | 조회 / 검색 / 결과 출력 / 다운로드 | 화면정의서 |
| 공통 | 공통 인프라, API 계약, DB 모델 | WBS |

**강조 포인트:** 프론트/백을 사람 기준으로 나누지 않고 **기능 단위(세로)로 나눴다.**
→ 이유를 한 줄로: "각자 사용자 흐름 하나를 끝까지 책임져서, 통합 시점의 책임 공백을 없애기 위해"

### 슬라이드 5 — 협업 방식
- Git 브랜치 전략 (`feature/기능명`, main은 항상 동작)
- PR 리뷰 후 머지
- 일일 체크인
- API 계약 사전 합의 → 통합 리스크 감소

## 03. 프로젝트 수행 절차 및 방법 (4~5장) ← **기술 역량 보여주는 구간**

### 슬라이드 6 — 전체 처리 흐름
- 지시서 플로우차트를 그대로 활용 (①~⑧)
- 각 단계에 담당자 표시

### 슬라이드 7 — 시스템 아키텍처
```
React (Vite)  ──axios──▶  FastAPI  ──▶  PostgreSQL
                             │
                             ├──▶ TextExtractor (PDF/DOCX/OCR)
                             └──▶ AIClient (OpenAI)
              전체 Docker Compose 구성
```
- Layered Architecture: `Router → Service → Repository/Client`
- **의존성이 한 방향**임을 화살표로 명확히

### 슬라이드 8 — 설계 포인드 ① 확장 가능한 구조 ⭐
> **이 슬라이드가 발표의 승부처.**

```
TextExtractor (Protocol)          Analyzer (Protocol)
├── PdfExtractor                  ├── SummaryAnalyzer
├── DocxExtractor                 └── CategoryAnalyzer
├── OcrExtractor                        ▲
└── FakeExtractor                 새 분석기는 여기에 추가만
```

말할 내용:
- "파일 형식이 늘어나도 **Extractor 구현체만 추가**하면 되고, 기존 코드는 수정하지 않습니다"
- "Document를 특정 문서 종류에 묶지 않고 `document_type` 필드로만 구분해서, 문서 유형 추가가 데이터 문제로 남습니다"
- "메인 프로젝트에서 이 자리에 파인튜닝 모델 기반 분석기를 추가할 계획입니다"

### 슬라이드 9 — 설계 포인트 ② Fake 구현체로 개발 병렬화
```
개발 중       → FakeClient   (API 비용 0, 즉시 응답, 오프라인 가능)
실서비스       → OpenAIClient
```
- **효과를 수치로**: "API 계정 발급 전에도 전체 흐름을 개발·테스트할 수 있었고, 개발 중 API 호출 비용을 N원으로 억제"
- 이건 실제로 겪은 일이므로 04에서 다시 언급하면 설득력 상승

### 슬라이드 10 — 프롬프트 및 출력 설계
- 요약/분류 프롬프트 구조 (시스템 프롬프트 + 문서 본문)
- **Structured Output** JSON 스키마 예시
- 토큰 절감: 프롬프트 캐싱 / 청킹 / 출력 필드 최소화
- 프롬프트 버전 관리 (`prompt_version`)

## 04. 프로젝트 수행 경과 (3~4장) — **릴레이 발표**

### 슬라이드 11 — 일정 및 진행 현황
- WBS 요약 (D1 인프라 → D3 통합 → D5 테스트 → D6 프리즈)
- 계획 대비 실제 (지연된 것도 솔직히 표기 + 원인)

### 슬라이드 12~14 — 담당별 트러블슈팅 (각 1장)

각자 아래 형식으로 **1장씩**. 문제 → 원인 → 해결 → 배운 점.

```
A: [문제] 스캔 PDF는 텍스트 레이어가 없어 추출 결과가 빈 문자열
   [원인] PDF 종류에 따라 추출 경로가 달라야 함
   [해결] 텍스트 레이어 유무를 판별해 OCR로 분기하는 하이브리드 구조
   [배움] 입력 데이터의 편차를 먼저 조사해야 한다

B: [문제] LLM 응답이 매번 다른 형식으로 와서 파싱 실패
   [원인] 자유 형식 출력에 의존
   [해결] Structured Output으로 스키마 강제 + 검증 실패 시 재시도 1회
   [배움] LLM 출력은 신뢰하지 말고 스키마로 강제한다

C: [문제] 분석 대기 중 사용자가 멈춘 줄 알고 중복 업로드
   [원인] 로딩 상태 피드백 부재
   [해결] 처리 단계별 상태 표시 + 버튼 비활성화
   [배움] 응답이 느린 기능은 UI가 상태를 말해줘야 한다
```

> ❗ **트러블슈팅 슬라이드가 04의 핵심.** "잘 만들었습니다"보다 "이런 문제를 이렇게 해결했습니다"가 훨씬 높게 평가됨.
> 개발하면서 문제 생길 때마다 **바로 메모**해둘 것. 나중에 기억나지 않음.

### 슬라이드 15 — 테스트 결과
- 단위 테스트 / 통합 테스트 시나리오 통과 현황 (표 + 건수)
- 처리 시간 실측 (문서 N페이지 → N초)
- 토큰 사용량 및 비용 실측 ← `Analysis` 테이블에서 추출

## 05. 자체 평가 의견 (2장)

### 슬라이드 16 — 성과와 한계

| 잘된 점 | 아쉬운 점 |
|---|---|
| Protocol 기반 설계로 확장 지점 확보 | HWP 구형 포맷 미지원 |
| Fake 구현체로 API 없이 병렬 개발 | 대용량 문서 처리 시간 |
| 세로 분할로 전원이 전체 흐름 경험 | 테스트 커버리지 부족 |

> **한계를 솔직히 쓰는 게 유리하다.** 단, "왜 그렇게 판단했는지"를 붙일 것.
> 예: "HWP 바이너리 파싱은 기간 대비 위험이 커서 HWPX만 지원하고 변환 안내로 처리했습니다"

### 슬라이드 17 — 메인 프로젝트 확장 계획 ⭐

```
[서브] OpenAI로 요약·분류 → 결과를 DB에 축적
                              │
[메인] 축적된 데이터 검수 → LoRA 파인튜닝 → Ollama 서빙
                              │
       동일 API, provider만 교체 → 비용/속도/품질 비교
```

말할 내용:
- "서브에서 저장한 분석 결과가 그대로 메인의 학습 데이터가 됩니다"
- "상용 API를 소형 자체 모델로 대체해 비용과 응답 속도를 개선하는 것이 메인 목표입니다"
- "이를 위해 `Analysis` 테이블에 provider·모델명·토큰 수를 미리 기록해두었습니다"

> 이 슬라이드가 있으면 **서브 발표가 메인 발표의 예고편**이 되고, 심사자에게 "설계 의도가 있는 팀"으로 인식됨.

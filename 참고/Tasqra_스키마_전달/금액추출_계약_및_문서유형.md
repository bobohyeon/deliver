# 1. 문서 유형 — 7종 → 9종

## 왜 바꾸나

현재 7종은 도메인을 정하기 전에 만든 것이라 **공공 SI 문서 흐름과 맞지 않는다.**

```
현재: CONTRACT · CONTRACT_CHANGE · MEETING_NOTES · REPORT · NOTICE · MANUAL · ETC
```

가장 큰 문제는 **`산출내역서` 가 없다**는 것이다. 금액 항목이 표로 정리된
문서이고 금액 기능의 주 입력인데, 지금은 `ETC` 로만 들어간다.

`NOTICE` 와 `MANUAL` 은 공공 SI 사업 문서 흐름에 거의 나오지 않는다. 대신
`입찰공고` · `제안서` · `대가지급청구서` 가 나온다.

## 제안 — 9종

| 코드 | 포함 문서 | 나오는 금액 |
|---|---|---|
| `RFP` | 제안요청서 · 입찰공고 · 사업계획서 | 사업 예산 · 추정가격 |
| `PROPOSAL` | 제안서 · 기술제안서 | 제안 가격 |
| **`COST_SHEET`** | **산출내역서 · 견적서 · 원가계산서** | **항목별 단가 · 수량 (핵심)** |
| `CONTRACT` | 계약서 · 과업지시서 · 착수신고서 | 계약 금액 |
| `CONTRACT_CHANGE` | 변경계약서 · 과업변경합의서 | 증감액 |
| `REPORT` | 착수 · 주간 · 월간 · 완료보고서 · 검사조서 | 집행액 · 진척률 |
| `MEETING_NOTES` | 회의록 | 간헐적 |
| **`BILLING`** | **대가지급청구서 · 세금계산서** | **청구액 · 부가세 (핵심)** |
| `ETC` | 그 외 | — |

**아홉 종류 전부가 금액과 관계가 있다.** 이게 도메인을 좁힌 효과다. 범용이었을
때는 `MANUAL` 처럼 금액이 없는 유형이 섞여 있었다.

## 금액 기능에서 중요한 세 종류

| | 유형 | 금액 기능에서의 역할 |
|---|---|---|
| 1 | `COST_SHEET` | **항목·수량·단가가 표로 있다.** 추출 정확도를 여기서 잰다 |
| 2 | `CONTRACT` · `CONTRACT_CHANGE` | **계약금액과 증감.** 프로젝트 집계의 기준선 |
| 3 | `BILLING` | **실제 청구액.** 집행률 계산에 쓴다 |

`COST_SHEET` 하나만 잘 되면 금액 기능의 데모가 성립한다. **평가셋도 여기에
집중하는 것이 맞다.**

## 유형을 늘리는 것의 대가

**분류 정확도 목표가 85%(`QUR-02`)인데, 유형이 늘면 떨어진다.** 9종은 적은
편이지만 `RFP` 와 `PROPOSAL` 은 문장이 비슷해서 섞일 수 있다.

세 가지로 완화한다.

| | 방법 |
|---|---|
| 1 | **업로드 시 사용자가 지정** (`document_type_source = MANUAL`). 자동 판별은 기본값일 때만 |
| 2 | **규칙 기반 1차 분류.** `공급자` + `공급받는 자` + `공급가액` 이 함께 나오면 `BILLING` |
| 3 | 애매한 것만 모델에 보낸다 |

2번은 재정님이 정리해 주신 문서 2절의 방식이다. **규칙으로 먼저 걸러면 모델
호출이 줄고 정확도가 올라간다.**

## DB 변경

`String + CHECK` 방식이라 **CHECK 제약만 바꾸면 된다.** `ALTER TYPE` 이 필요
없다. 이 방식을 택한 이유가 이런 상황이었다.

```python
op.drop_constraint("ck_documents_document_type", "documents", type_="check")
op.create_check_constraint(
    "ck_documents_document_type", "documents",
    "document_type IS NULL OR document_type IN ("
    "'RFP','PROPOSAL','COST_SHEET','CONTRACT','CONTRACT_CHANGE',"
    "'REPORT','MEETING_NOTES','BILLING','ETC')")
```

# 2. 금액 추출 JSON 계약

## 역할 경계

```
문서 텍스트  →  [ 세현님: 모델·프롬프트 ]  →  JSON  →  [ 보현님: 검증·계산·저장 ]
```

**세현님은 뽑기만 하고, 계산은 하지 않는다.** 합계도 더하지 않는다. 코드가
재계산해서 문서에 적힌 합계와 대조하는 것이 이 기능의 핵심(`AMT-03`)이기
때문이다. **모델이 미리 더해버리면 대조할 대상이 사라진다.**

## 응답 형식

```json
{
  "document_type": "COST_SHEET",
  "currency": "KRW",
  "stated_total": 97500000,
  "items": [
    {
      "item_name": "특급기술자",
      "category": "DIRECT_LABOR",
      "quantity": 3.0,
      "unit": "인월",
      "unit_price": 9500000,
      "amount": 28500000,
      "period_from": "2026-03-01",
      "period_to": "2026-05-31",
      "source_quote": "특급기술자 3인월 × 9,500,000원 = 28,500,000원",
      "confidence": 0.94,
      "reason": "산출내역서 인건비 표의 첫 행. 등급·인월·단가가 모두 명시됨"
    },
    {
      "item_name": "고급기술자",
      "category": "DIRECT_LABOR",
      "quantity": 6.0,
      "unit": "인월",
      "unit_price": 7200000,
      "amount": 43200000,
      "period_from": "2026-03-01",
      "period_to": "2026-08-31",
      "source_quote": "고급기술자 6인월 × 7,200,000원 = 43,200,000원",
      "confidence": 0.94,
      "reason": "같은 표의 두 번째 행"
    },
    {
      "item_name": "제경비",
      "category": "OVERHEAD",
      "quantity": null,
      "unit": null,
      "unit_price": null,
      "amount": 25800000,
      "period_from": null,
      "period_to": null,
      "source_quote": "제경비(직접인건비의 110%): 25,800,000원",
      "confidence": 0.88,
      "reason": "비율로 산정된 항목. 수량·단가가 없어 비워둠"
    },
    {
      "item_name": "부가세",
      "category": "VAT",
      "quantity": null,
      "unit": null,
      "unit_price": null,
      "amount": 9750000,
      "period_from": null,
      "period_to": null,
      "source_quote": "부가가치세: 9,750,000원",
      "confidence": 0.97,
      "reason": "합계 아래 별도 표기. 공급가액의 10%"
    }
  ],
  "notes": null
}
```

## 필드 설명

### 문서 단위

| 필드 | 필수 | 설명 |
|---|---|---|
| `document_type` | 예 | 9종 중 하나. 모르면 `"ETC"` |
| `currency` | 예 | ISO 코드. 표기 없으면 `"KRW"` |
| **`stated_total`** | **예** | **문서에 적힌 합계.** 없으면 `null` |
| `items` | 예 | 배열. 금액이 없으면 `[]` |
| `notes` | 아니오 | 판단이 어려웠던 점. 없으면 `null` |

**`stated_total` 이 이 계약에서 가장 중요한 필드다.** 항목 합계와 대조할
상대편이다. 이게 없으면 `AMT-03` 합계 대조가 성립하지 않는다.

문서에 합계가 여러 개면(공급가액 합계 · 부가세 포함 총액) **부가세를 포함하지
않은 합계**를 넣는다. 총액은 `items` 에 `category: "TOTAL"` 로 따로 넣지 말고
비워둔다.

### 항목 단위

| 필드 | 필수 | 형식 | 설명 |
|---|---|---|---|
| `item_name` | 예 | 문자열 | 문서에 적힌 항목명 그대로 |
| `category` | 아니오 | 아래 목록 | 원가 구분. 모르면 `null` |
| `quantity` | 아니오 | 숫자 | 소수 허용 (예: 1.5인월) |
| `unit` | 아니오 | 문자열 | `인월` · `식` · `개` · `m3` 등 |
| `unit_price` | 아니오 | 정수 | 단가 |
| **`amount`** | **예** | **정수** | 금액. 이것만은 반드시 |
| `period_from` | 아니오 | `YYYY-MM-DD` | 해당 기간 시작 |
| `period_to` | 아니오 | `YYYY-MM-DD` | 해당 기간 종료 |
| **`source_quote`** | **예** | 문자열 | **원문을 그대로 인용** |
| `confidence` | 예 | 0.0~1.0 | 확신도 |
| **`reason`** | **예** | 문자열 | **왜 이렇게 판단했는지** |

### `category` 값

공공 SI 원가 구조를 따른다.

| 값 | 뜻 |
|---|---|
| `DIRECT_LABOR` | 직접인건비 |
| `EXPENSE` | 직접경비 (여비·수용비 등) |
| `OVERHEAD` | 제경비 |
| `TECH_FEE` | 기술료 |
| `MATERIAL` | 재료비 · 물품비 |
| `SUBCONTRACT` | 외주비 |
| **`VAT`** | **부가가치세** |
| `OTHER` | 위에 없는 것 |

**`VAT` 를 반드시 구분해야 한다.** 부가세를 다른 항목과 똑같이 넣으면 코드가
합계를 낼 때 **이중으로 더해진다.** 이게 합계 대조가 틀리는 가장 흔한 원인이다.

## 지켜야 할 규칙

### 하지 말 것

| | 금지 | 이유 |
|---|---|---|
| 1 | **합계를 직접 계산하지 마라** | 코드가 재계산해서 대조한다. 그게 이 기능이다 |
| 2 | **문서에 없는 단가를 추정하지 마라** | `unit_price` 가 없으면 `null` |
| 3 | **부가세를 직접 계산하지 마라** | 적혀 있을 때만 항목으로 넣는다 |
| 4 | **`quantity × unit_price` 로 `amount` 를 만들지 마라** | 문서의 `amount` 를 그대로 읽는다 |
| 5 | **총액 행을 항목으로 넣지 마라** | `stated_total` 에 넣는다 |
| 6 | **숫자를 문자열로 주지 마라** | `"9,500,000"` 이 아니라 `9500000` |

**4번이 특히 중요하다.** 문서에 `3 × 9,500,000 = 28,000,000` 처럼 **문서 자체가
틀린 경우**가 있다. 그걸 그대로 읽어야 우리가 잡아낼 수 있다. 모델이 고쳐서
주면 오류가 숨는다.

### 값이 없을 때

**빈 문자열이나 `0` 을 쓰지 말고 `null` 을 쓴다.** `0` 은 "금액이 0원" 이라는
뜻이라 의미가 달라진다.

### 금액을 하나도 못 찾았을 때

```json
{
  "document_type": "MEETING_NOTES",
  "currency": "KRW",
  "stated_total": null,
  "items": [],
  "notes": "금액 관련 표나 숫자를 찾지 못했습니다"
}
```

**오류가 아니다.** 회의록에 금액이 없는 것은 정상이므로 빈 배열로 응답한다.

## 검증에 쓸 Pydantic 모델

보현님 쪽에서 이 모델로 받는다. **여기서 걸리면 `AI_INVALID_RESPONSE`(502) 로
응답하고 재시도한다.**

```python
from datetime import date
from decimal import Decimal
from typing import Literal
from pydantic import BaseModel, Field

DocumentType = Literal["RFP", "PROPOSAL", "COST_SHEET", "CONTRACT",
                       "CONTRACT_CHANGE", "REPORT", "MEETING_NOTES",
                       "BILLING", "ETC"]
Category = Literal["DIRECT_LABOR", "EXPENSE", "OVERHEAD", "TECH_FEE",
                   "MATERIAL", "SUBCONTRACT", "VAT", "OTHER"]


class AmountItemOut(BaseModel):
    item_name: str = Field(min_length=1, max_length=300)
    category: Category | None = None
    quantity: Decimal | None = Field(default=None, ge=0)
    unit: str | None = Field(default=None, max_length=20)
    unit_price: int | None = Field(default=None, ge=0)
    amount: int = Field(ge=0)
    period_from: date | None = None
    period_to: date | None = None
    source_quote: str = Field(min_length=1, max_length=1000)
    confidence: float = Field(ge=0.0, le=1.0)
    reason: str = Field(min_length=1, max_length=1000)


class AmountExtractionOut(BaseModel):
    document_type: DocumentType
    currency: str = Field(default="KRW", pattern=r"^[A-Z]{3}$")
    stated_total: int | None = Field(default=None, ge=0)
    items: list[AmountItemOut]
    notes: str | None = None
```

`amount` 를 `int` 로 둔 이유가 있다. **원 단위 정수라 소수가 필요 없고, 부동
소수점을 쓰면 합계에 오차가 생긴다.** `quantity` 만 `Decimal` 이다(1.5인월).

## 테스트 케이스 세 개

세현님 쪽에서 이 세 가지가 통과하면 인터페이스가 맞은 것이다.

### 1. 정상 — 합계가 맞는 산출내역서

```
직접인건비   특급기술자 3인월 × 9,500,000 = 28,500,000
            고급기술자 6인월 × 7,200,000 = 43,200,000
제경비       직접인건비의 110%            = 78,870,000
기술료                                    = 15,774,000
합계                                      = 166,344,000
부가세                                    =  16,634,400
```

기대: `items` 4개, `stated_total: 166344000`, `VAT` 항목 1개

**검증** — `VAT` 를 제외한 `amount` 합이 `stated_total` 과 같다.

### 2. 합계가 틀린 문서 — 이걸 잡는 게 기능이다

```
항목 A   1식 × 10,000,000 = 10,000,000
항목 B   1식 ×  5,000,000 =  5,000,000
합계                       = 14,000,000     ← 문서가 틀렸다
```

기대: `items` 2개, `stated_total: 14000000`

**모델이 15,000,000 으로 고쳐서 주면 안 된다.** 문서에 적힌 대로 14,000,000
을 주면 코드가 차액 1,000,000 을 잡아낸다. **이게 `AMT-03` 이다.**

### 3. 금액이 없는 문서

```
회의록 — 일정과 결정사항만 있고 금액 언급 없음
```

기대: `items: []`, `stated_total: null`, `notes` 에 사유

## DB 변경이 필요한 것

이 계약을 받으려면 `amount_items` 에 컬럼 두 개가 필요하다. **협의 사항이다.**

| 컬럼 | 형식 | 왜 |
|---|---|---|
| `unit_price` | `BigInteger` nullable | 재계산과 단가 선례 비교에 필요 |
| `category` | `String(20)` nullable + CHECK | **부가세를 구분하지 않으면 합계가 틀린다** |

현재 컬럼은 이렇다.

```
item_name  quantity  unit  amount  currency  period_from  period_to  source_quote
```

`stated_total` 은 항목이 아니라 문서 단위 값이라 `amount_items` 가 아니라
`analyses.result_json` 에 남기거나 `documents` 에 컬럼을 두어야 한다.
**`analyses.result_json` 에 두는 것을 제안한다.** 이미 JSONB 이고 분석 결과의
원본이 그대로 남는 곳이라 추가 컬럼이 필요 없다.

## 코드를 넣은 근거

**판단 기준 하나** — 프런트가 다르게 처리해야 하는가. 화면이 똑같이 "오류가
났습니다" 만 띄울 거라면 별도 코드를 두지 않았다.

### OCR 검수 8종

| 코드 | 프런트가 해야 하는 일 |
|---|---|
| `PAGE_NOT_FOUND` | 페이지 목록을 다시 불러온다 |
| `OCR_ELEMENT_NOT_FOUND` | 해당 박스를 화면에서 지운다 |
| **`OCR_ELEMENT_CONFLICT`** | **다시 불러온 뒤 사용자에게 재시도를 요청한다** |
| `OCR_ELEMENT_DELETED` | 복원 버튼을 안내한다 |
| `INVALID_BBOX` | 드래그한 영역을 되돌린다 |
| `RE_OCR_FAILED` | 그 박스만 재시도 버튼을 보여준다 |
| `REVIEW_NOT_COMPLETED` | 검수 화면으로 보낸다 |
| `REVIEW_ALREADY_COMPLETED` | 읽기 전용으로 바꾼다 |

**`OCR_ELEMENT_CONFLICT` 가 이 묶음에서 가장 중요하다.** `ocr_elements.version`
으로 낙관적 락을 걸기 때문에, 두 사람이 같은 박스를 고치면 나중 요청이 반드시
이 코드를 받는다. 이 코드가 없으면 사용자는 수정이 조용히 사라진 것처럼 느낀다.

### AI 제안 승인 2종

| 코드 | 언제 |
|---|---|
| `SUGGESTION_ALREADY_DECIDED` | 두 번 누름 · 다른 사람이 먼저 처리 |
| **`STALE_SUGGESTION`** | **`source_text_revision` < `documents.ocr_revision`** |

**`STALE_SUGGESTION` 은 검수와 분석을 잇는 코드다.** OCR 을 고치면
`documents.ocr_revision` 이 올라가는데, 그 전에 만든 제안은 낡은 텍스트에서
나온 것이다. 그걸 승인하면 고친 내용이 반영되지 않은 태스크가 생긴다.
숫자 비교 하나로 막을 수 있어서 반드시 넣었다.

세 테이블(`amount_items` · `decisions` · `schedule_items`)이 `suggestion_columns()`
로 같은 컬럼을 공유하므로 코드도 하나로 공유한다. 제안 종류마다 코드를 따로
두면 종류가 늘 때마다 코드가 늘어난다.

### 금액 4종

| 코드 | 언제 |
|---|---|
| `AMOUNT_ITEM_NOT_FOUND` | 항목 승인·수정 대상이 없다 |
| **`AMOUNT_NOT_ANALYZED`** | **금액 모델만 실패한 뒤 집계를 요청** |
| `CURRENCY_MISMATCH` | KRW · USD 가 섞여 합계 불가 |
| `NO_APPROVED_AMOUNTS` | 승인된 항목이 0건인데 집계 요청 |

**`AMOUNT_NOT_ANALYZED` 가 금액 모델을 따로 돌리기로 한 결정의 직접적인
결과다.** 모델이 둘로 나뉘면 **요약은 성공했는데 금액만 실패한 상태**가
생긴다. 지금까지는 없던 상태다. 이때 사용자가 금액 집계를 누르면 "분석
실패" 가 아니라 **"금액 분석만 아직 안 됐다"** 고 알려야 한다. 그래야
금액 분석만 다시 돌리면 된다는 걸 안다.

**합계 불일치는 에러코드로 두지 않았다.** `AMT-03` 은 불일치를 **표시하는
기능**이고 요청이 실패한 게 아니다. 200 으로 응답하고 본문에 차액을 담는다.

### 결정사항 · 일정 2종

조회·수정 대상이 없을 때다. 산출물 생성이 이 두 테이블을 읽으므로 필요하다.

### 산출물 5종

| 코드 | 언제 |
|---|---|
| `DELIVERABLE_NOT_FOUND` | 이력에서 다시 내려받기 실패 |
| `FORMAT_REQUIRED` | 형식 미선택 |
| `PERIOD_REQUIRED` | 기간 미선택 |
| **`DELIVERABLE_EMPTY`** | **기간 안에 담을 내용이 0건** |
| `DELIVERABLE_GENERATION_FAILED` | 파일 생성 중 실패 |

**`DELIVERABLE_EMPTY` 가 AI 호출 비용을 막는다.** 기간을 잘못 잡아 문서가
0건인 상태로 생성을 누르면, 검사 없이는 빈 보고서를 만들면서 AI 를
호출한다. 미리보기(`SFR-36`)가 있어도 건너뛰고 생성할 수 있으니 서버에서
한 번 더 막는다.

**`FORMAT_REQUIRED` · `PERIOD_REQUIRED` 는 조건부다.** 요청 스키마에서 두 값을
필수로 두면 Pydantic 이 422 `VALIDATION_ERROR` 로 먼저 막으므로 이 코드는
쓰이지 않는다. **미리보기 → 생성 2단계로 나눠서 형식을 나중에 정하는 흐름일
때만 필요하다.** 구현할 때 흐름이 1단계로 정해지면 두 코드는 지워도 된다.

### AI 모델 4종 — 금액 모델 분리를 감안한 부분

기존 `AI_PROVIDER_ERROR`(502) · `AI_TIMEOUT`(504) 은 그대로 두고 4종을 더한다.

| 코드 | 상태 | 프런트가 해야 하는 일 |
|---|---|---|
| **`AI_MODEL_NOT_LOADED`** | 503 | **잠시 후 자동 재시도.** 로컬 모델은 기동에 시간이 걸린다 |
| **`AI_MODEL_OUT_OF_MEMORY`** | 503 | **즉시 재시도하지 않는다.** 동시 요청을 줄여야 풀린다 |
| `AI_INVALID_RESPONSE` | 502 | 재시도해도 같을 수 있다고 안내 |
| `AI_ANALYZER_FAILED` | 502 | **실패한 분석만** 다시 돌리는 버튼 |

**넷을 나눈 이유가 각각 다르다.**

`AI_MODEL_NOT_LOADED` — 로컬 모델은 상용 API 와 달리 **띄우는 시간**이 있다.
컨테이너가 떴는데 모델이 아직 메모리에 안 올라간 구간이 존재한다. 이때
502 를 주면 화면이 "AI 오류" 라고 표시하는데, 실제로는 **기다리면 되는
상황**이다. 503 은 "지금은 안 되지만 곧 된다" 는 뜻이라 의미가 맞다.

`AI_MODEL_OUT_OF_MEMORY` — 회의에서 나온 **"모델을 여러 개 운영할 경우
메모리 사용량을 고려해 최적화한다"** 가 이 코드의 근거다. 모델 두 개를 같은
장비에 올리면 동시 요청이 겹칠 때 메모리가 먼저 터진다. `NOT_LOADED` 와
나눈 이유는 **재시도 전략이 반대**라서다. 앞은 기다리면 풀리고, 뒤는
동시 요청을 줄여야 풀린다. 같은 코드로 묶으면 화면이 계속 재시도해서
상황을 악화시킨다.

`AI_INVALID_RESPONSE` — 회의에서 **"초기에는 문자열(String) 형태로 결과를
전달받고, 이후 필요하면 JSON 필드로 나눈다"** 고 정했다. 문자열로 받아
파싱하는 구간에서는 **모델이 형식을 안 지키는 실패가 흔하다.** 이건 호출
실패(`AI_PROVIDER_ERROR`)가 아니라 **응답을 못 읽은 것**이라 원인이 다르다.
로그에서 구분되어야 프롬프트를 고칠지 파서를 고칠지 판단할 수 있다.

`AI_ANALYZER_FAILED` — 분석기 4개 중 일부만 실패한 경우다. `detail` 에
어느 분석기인지 담는다.

### 모델마다 코드를 만들지 않은 이유

금액 모델 전용으로 `AMOUNT_MODEL_ERROR` 같은 코드를 두지 않았다.

| | 모델별 코드 | **채택: 분석기 구분은 `detail` 로** |
|---|---|---|
| 모델이 3개로 늘면 | 코드도 늘어난다 | **안 늘어난다** |
| 어느 모델인지 | 코드로 안다 | `detail` + `analyses.analyzer_type` |
| 프런트 처리 | 같다 | 같다 |

**프런트가 하는 일이 같으면 코드를 나눌 이유가 없다.** 어느 모델이
실패했는지는 이미 `analyses` 테이블에 `analyzer_type` · `model_name` ·
`latency_ms` 를 저장하므로 그쪽에서 정확히 알 수 있다.

단 **`AMOUNT_NOT_ANALYZED` 는 예외로 두었다.** 그건 "모델이 실패했다" 가
아니라 **"금액 데이터가 아직 없다"** 는 다른 상태이고, 프런트가 금액 분석만
다시 돌리는 버튼을 보여줘야 하므로 구분이 필요하다.

## 넣지 않은 것

| 안 넣음 | 이유 |
|---|---|
| 일괄 처리 (`BATCH_*`) | 리비전 0004 에서 테이블을 뺐다. 최재정님 파트 |
| 태스크 (`TASK_*`) | `tasks` 테이블이 아직 없다 |
| `ACTION_ITEM_*` | 제안 4종 대칭 여부가 합의 대기 |
| `INVALID_TASK_STATUS` 류 | Pydantic `Literal` 이 422 로 막는다 |
| `AMOUNT_TOTAL_MISMATCH` | 합계 불일치는 실패가 아니라 표시 결과다 |
| `MODEL_NOT_FOUND` | `ANALYZER_NOT_FOUND` 가 이미 있다 |

**테이블이 없는데 에러코드만 있으면 그게 애매한 것이다.** 리비전 0004 가
만드는 8개 테이블에 대응하는 것만 넣었다.

## 적용 순서

`spec-compliance` 는 PR #4 로 이미 머지됐다. 이제 최신 main 위에 올리면 된다.

```
1. main 최신화                                          (완료 — 7bd50e0)
2. 리비전 20260811_0006 (down_revision 20260811_0005)   (완료)
3. 이 블록을 error_codes.py 에 추가
4. 리비전과 에러코드를 하나의 PR 로 올린다
```

3번을 2번과 같은 PR 에 넣는 이유는 **에러코드가 리비전 0006 의 테이블을
전제하기 때문이다.** 따로 올리면 참조할 테이블이 없는 코드가 먼저 들어간다.

PR #3 은 머지되지 않고 닫혔다. 닫힌 브랜치를 다시 쓰지 않고 **새 브랜치로
새 PR** 을 만든다.

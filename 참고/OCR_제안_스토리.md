# OCR / 텍스트 추출 전략 — 킥오프 제안 스크립트

> 대상: 팀원 2명 / 시점: D1(7/31) 킥오프 / 소요: **5분 발표 + 5분 토론**
> 목적: "OCR을 주 경로로 쓰지 말고 하이브리드로 가자"에 합의받기

---

## 결론 한 줄 (먼저 말할 것)

> **"OCR을 메인 경로로 쓰면 안 됩니다. 텍스트 레이어를 먼저 읽고, 없을 때만 OCR로 넘기는 2단 구조로 가야 합니다."**

---

## 스토리 흐름 (이 순서로 말하기)

### ① 지시서에서 근거를 먼저 짚기 (30초)

> "지시서 플로우차트 ③번을 다시 보면, **'이미지 텍스트 추출(OCR)'과 '텍스트 추출(PDF, DOCX 등)'이 두 줄로 나뉘어** 있습니다.
> 이건 한 가지 방법이 아니라 **경로가 두 개**라는 뜻입니다. 과제가 이미 하이브리드를 요구하고 있습니다."

→ 내 주장이 아니라 **지시서 해석**으로 시작하는 게 설득에 훨씬 강함.

### ② 핵심 사실 — PDF는 두 종류다 (1분)

> "PDF에는 두 종류가 있습니다.
> **① 텍스트 레이어가 있는 PDF** — 워드나 한글에서 '내보내기'로 만든 것. 글자 데이터가 파일 안에 그대로 있습니다.
> **② 스캔 PDF** — 종이를 스캔하거나 사진 찍은 것. 안에는 이미지만 있고 글자 데이터가 없습니다.
>
> ①번은 **OCR이 전혀 필요 없습니다.** PyMuPDF로 읽으면 정확도 100%, 처리 시간은 0.1초입니다.
> OCR을 쓰면 오히려 **정확도가 떨어집니다.** 있는 글자를 이미지로 바꿔서 다시 추측하는 거니까요."

→ 이게 팀원이 모를 가능성이 높은 핵심 사실. **여기서 설득이 끝남.**

### ③ OCR을 주 경로로 잡으면 뭐가 나쁜가 (1분)

| 항목 | OCR 주 경로 | 텍스트 레이어 추출 |
|---|---|---|
| 정확도 | 95~98% (오인식 존재) | **100%** |
| 처리 시간 | 페이지당 1~3초 | **0.1초 이하** |
| Docker 이미지 | +수백MB~GB | **+수MB** |
| 세팅 난이도 | 모델 다운로드, 의존성 충돌 | **pip 한 줄** |
| 좌표 정보 | 있음 | 있음 |

> "특히 **6일 프로젝트에서 Docker 이미지 세팅에 반나절 이상 쓰면 치명적**입니다.
> OCR 라이브러리는 의존성이 무거워서 3명 환경에서 각각 다른 문제가 터질 확률이 높습니다."

### ④ 제안 (1분)

```
파일 업로드
   │
   ├─ .docx  → python-docx
   ├─ .hwpx  → XML 파싱
   ├─ .pdf   → PyMuPDF로 텍스트 추출 시도
   │            │
   │            ├─ 글자가 나옴  → 그대로 사용        (대부분 여기)
   │            └─ 빈 결과      → OCR 폴백으로 전환
   └─ .png/.jpg → 바로 OCR
```

> "판별 로직은 간단합니다. **추출한 텍스트 길이가 임계값 미만이면 스캔 PDF로 판단**해서 OCR로 넘깁니다.
> 그리고 어느 경로로 처리했는지 `extract_method` 필드에 기록해서 화면과 발표 자료에 보여줍니다."

### ⑤ OCR 엔진은 가벼운 것으로 (30초)

> "OCR 엔진은 **EasyOCR 또는 Tesseract** 중 설치가 가벼운 쪽으로 하겠습니다.
> PaddleOCR이 성능은 더 좋다고 알려져 있지만, 의존성이 무거워서 6일 안에는 위험합니다.
> **PaddleOCR 도입과 엔진 정확도 비교는 메인 프로젝트 과제로 넘기겠습니다.**"

→ "안 한다"가 아니라 **"순서를 미룬다"** 로 말하는 게 중요.

## 예상 반론 3개와 대응

### 반론 1. "OCR이 과제 요구사항인데 안 쓰면 감점 아닌가?"

> "OCR을 **빼는 게 아니라 폴백 경로로 구현**합니다. 스캔 PDF와 이미지 파일은 실제로 OCR을 타고,
> 데모에서 스캔 문서를 넣어서 OCR 동작을 직접 보여줄 겁니다. 요구사항은 충족됩니다.
>
> 오히려 **'파일 종류를 판별해서 최적 경로로 분기한다'** 는 게 OCR만 쓰는 것보다 **설계 수준이 높습니다.**
> 발표에서 이 판단 근거를 설명하면 그게 기술 역량으로 평가됩니다."

**이게 가장 중요한 반박.** 감점이 아니라 **가점 요소**로 뒤집는 논리.

### 반론 2. "그냥 OCR 하나로 통일하는 게 코드가 단순하지 않나?"

> "`TextExtractor` 인터페이스를 두고 구현체를 나누면 오히려 단순합니다.
> 각 구현체는 자기 형식만 알면 되고, 서비스는 어떤 구현체인지 몰라도 됩니다.
> 그리고 파일 형식이 추가돼도 **기존 코드를 수정하지 않고 구현체만 추가**하면 됩니다."

### 반론 3. "판별 로직이 틀리면 어떡하나?"

> "틀려도 안전합니다. 텍스트 추출이 실패하면 OCR로 넘어가는 방향이라, **최악의 경우가 OCR을 타는 것**입니다.
> 반대 방향(OCR만 쓰기)은 잘 되는 문서도 정확도를 떨어뜨립니다."

## 30분 검증 방법 (합의 후 바로)

말로 끝내지 말고 숫자로 확인하고 넘어가:

```
1. 텍스트 PDF 1개, 스캔 PDF 1개 준비        (5분)
2. PyMuPDF로 둘 다 추출해서 글자 수 출력     (10분)
   → 텍스트 PDF: 수천 자 / 스캔 PDF: 0자 근처
3. 임계값 결정 (예: 페이지당 50자 미만 → OCR)  (5분)
4. 결과를 팀에 공유하고 확정                 (10분)
```

**30분이면 "추측"이 "측정"이 돼.** 이 숫자가 발표자료 슬라이드 8번에 그대로 들어감.

---

## 팀에 남길 결정 사항

- [ ] PDF 주 경로: **PyMuPDF 텍스트 추출**
- [ ] OCR 역할: **스캔 PDF / 이미지 폴백 전용**
- [ ] OCR 엔진: EasyOCR 또는 Tesseract (설치 검증 후 확정)
- [ ] 판별 임계값: 페이지당 글자 수 ___자 미만 → OCR
- [ ] `extract_method` 필드로 처리 경로 기록
- [ ] PaddleOCR 및 엔진 정확도 비교 → **메인 프로젝트로 이관**
- [ ] HWP: **HWPX만 지원**, 구형 바이너리 HWP는 안내 처리 (반나절 이상 쓰지 않기)

## 발표 시 톤

- **"제 생각엔"이 아니라 "지시서에 이렇게 나와 있고, 측정하면 이렇습니다"** 로
- OCR을 부정하는 게 아니라 **"OCR을 제대로 쓰는 위치에 두자"** 는 프레임
- 메인 프로젝트로 넘기는 항목을 명확히 말해서 **"기능을 줄인다"가 아니라 "순서를 정한다"** 로 들리게

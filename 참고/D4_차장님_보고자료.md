# PDF Brief AI — 프로젝트 진행 보고

보고: 김보현 | 8/4(화) | 팀 3인 (김보현·최재정·박세현)

---

## 1. 한 줄 요약

문서를 올리면 **텍스트/OCR로 내용을 추출하고, LLM이 요약·분류한 뒤, 검색·조회·다운로드**까지 되는 웹 서비스입니다. 코드 프리즈 8/5(수), 발표 8/7(금).

---

## 2. 처리 흐름

```
① 업로드 (PDF / DOCX / HWPX / 이미지)
      ↓
② 텍스트 레이어 추출 시도
      ↓  (글자 수가 임계값 미달 = 스캔 문서)
③ PaddleOCR v5로 이미지 OCR
      ↓
④ LLM 요약 (gpt-4o-mini)
⑤ LLM 카테고리 분류 + 분류 근거
      ↓
⑥ 목록 / 검색 / 상세 조회
⑦ 요약 보고서 .txt 다운로드
```

카테고리: `계약서 · 보고서 · 회의록 · 공지사항 · 메뉴얼 · 기타`

---

## 3. 기술 구성

| 영역 | 채택 | 선정 이유 |
|---|---|---|
| 백엔드 | FastAPI (Python) | LLM·OCR 생태계가 Python 중심 |
| DB | PostgreSQL 16 | JSONB로 분석 결과 저장, 본프로젝트까지 교체 없음 |
| OCR | **PaddleOCR v5** | 한국어 정확도. EasyOCR·Tesseract는 경량이지만 한국어 성능 미달로 기각 |
| LLM | OpenAI gpt-4o-mini | 비용 대비 한국어 요약 품질 |
| 프론트 | React 19 + Vite | |
| 실행 | Docker Compose | `db` / `api` / `frontend` 3개 서비스 |

## 4. 설계에서 신경 쓴 부분

### ① 문서 종류가 늘어도 코드가 안 바뀌게

`Document` 모델에 문서 종류를 **문자열 컬럼(`document_type`)** 으로 둡니다. 새 문서 유형이 생겨도 **테이블·모델 변경이 없습니다.**

### ② 분석기를 갈아끼울 수 있게 (Protocol 기반)

요약기·분류기가 공통 인터페이스를 구현합니다. 개발 중에는 API 비용이 들지 않는 **FakeClient**를 주입하고, 실제로는 OpenAI 클라이언트를 주입합니다. 설정값 한 줄(`USE_FAKE_AI`)로 전환됩니다.

→ **본프로젝트에서 자체 파인튜닝 모델로 교체할 때, 클라이언트 하나만 추가하면 됩니다.**

### ③ 계층 단방향 (Router → Service → Repository)

각 계층이 자기 아래만 호출합니다. 조회 로직이 라우터로 새어나가지 않게 해서, 테스트와 수정 범위를 좁혔습니다.

### ④ 분석 결과를 누적 저장 — 본프로젝트 연결점 ★

`analyses` 테이블에 분석마다 **행을 새로 쌓습니다.** 덮어쓰지 않고, `provider` / `model_name` / `tokens_in` / `tokens_out` / `latency_ms`를 함께 기록합니다.

이유 2가지:
- **모델 비교 실험** — 같은 문서를 여러 모델로 분석해 품질·비용·속도를 나란히 비교
- **본프로젝트 LoRA 학습 데이터** — (문서 원문, 요약) 쌍이 그대로 학습셋이 됩니다

`documents` 테이블에 `summary` 컬럼 하나를 두는 단순화를 **의도적으로 피했습니다.**

| 파트 | 담당 | 진행 |
|---|---|---|
| A. 업로드 · 텍스트 추출 | 최재정 | 완료 |
| B. LLM 요약 · 분류 | 박세현 | 완료 (실연동 확인 남음) |
| C. 목록 · 검색 · 상세 · 다운로드 (백엔드) | 김보현 | 완료 |
| C. 화면 (목록 · 상세) | 김보현 | 구현 완료, PR 리뷰 대기 |
| 화면 통합 (라우터 연결) | 박세현 | 협의 중 |
| 문서 수집 | 3인 | 진행 중 |
| 테스트 · 발표자료 | 3인 | 8/4~8/5 |

**업로드 → 추출 → 분석 → 목록 → 상세 → 다운로드 전 구간이 실제로 관통 확인되었습니다.**

## 7. 미니프로젝트에서 의도적으로 제외한 것

시간이 아니라 **판단으로 제외**한 항목입니다. 본프로젝트 과제로 기록해두었습니다.

| 항목 | 제외 이유 |
|---|---|
| 다크모드 | 발표장 PC 설정에 따라 화면이 달라지는 리스크 |
| Docker 이미지 최적화 (2.75GB) | 로컬 시연으로 확정 — 배포가 없어 크기가 무관 |
| `.pdf` 형식 다운로드, 문서 삭제 API | 요구 플로우에 없음 |
| 로그인 | 시간이 남으면 추가 (구조는 미리 잡아둠) |

## 8. 개발 과정에서 나온 이야깃거리 (발표 소재)

**① 다운로드 파일이 한 줄로 뭉치던 버그**
문자열을 이어붙일 때 구분자가 빠져 있었습니다. HTTP 응답은 200이라 검증을 통과했고, **파일을 실제로 열어보는 절차가 없어서 놓쳤습니다.** 이후 검증 항목을 "응답 코드"에서 "결과물 내용"으로 바꿨습니다.

**② 상세 조회만 500이 나던 버그**
스키마의 필드 별칭 설정 때문에, 같은 응답 객체를 만드는 두 경로 중 한쪽만 실패했습니다. 원인을 찾은 뒤 **성공하던 쪽과 같은 방식으로 통일**해서, 스키마가 바뀌어도 다시 깨지지 않게 했습니다.

**③ 목록 조회의 N+1 쿼리 (8/4 예정)**
현재 문서 1건마다 추가 조회가 2번 발생합니다(20건 = 41쿼리). **미리 고치지 않고 SQL 로그로 실측한 뒤 개선**해서, 수치로 개선 폭을 보여줄 예정입니다.

**④ 분량 제한 방식을 페이지 수 → 글자 수로 변경**
DOCX·HWPX는 흐름 기반 포맷이라 페이지 수가 정확하지 않습니다. 근사치 계산 대신 **글자 수(45,000자) 기준**으로 바꿨고, `latency_ms` 실측값으로 적정성을 검토할 예정입니다.

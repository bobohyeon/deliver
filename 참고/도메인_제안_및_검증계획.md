# 도메인 제안 및 검증 계획

> 작성: 김보현 (팀장) / 2026-07-31
> 대상: 최재정, 박세현
> 목적: `document_type` 과 `category` 값을 확정하기 위한 제안과, **말이 아니라 측정으로 검증하는 방법**

---

## 1. 제안 요약

> **도메인: 지자체 조례 · 공고문**
> 주제명: **지자체 조례·공고문 문서 분석 서비스** — 문서 유형과 분석 기능 확장을 전제로 설계

과제 지시서의 필수 기능(**요약 + 카테고리 분류**)은 그대로 구현하고,
문서 종류만 "지자체 조례·공고문"으로 특화한다.

---

## 2. 왜 이 도메인인가

### 2-1. 최종 목표와 이어진다

우리 팀이 궁극적으로 관심 있는 건 **"지자체 의회 법안 초안 작성 + 법률에 따른 금액 산정"** 이다.
그런데 그걸 하려면 그 전에 **기존 조례에서 기준금액과 근거조문을 정확히 읽어내는 능력**이 먼저 필요하다.
근거를 못 찾으면 새 금액을 산정할 방법이 없다.

```
미니프로젝트          본프로젝트              최종 목표
조례를 읽고 구조화  →  조례 간 비교·검색(RAG) →  법안 초안 + 금액 산정
(요약 · 분류 · 추출)    (근거 조문 탐색)          (기준으로 계산·생성)
```

**지금 만드는 게 장난감이 아니라 최종 목표의 1단계**가 된다.

### 2-2. 기술적으로도 유리하다

| 기준 | 평가 |
|---|---|
| 공개 데이터 | ◎ 자치법규정보시스템(ELIS), 국가법령정보센터, 지자체 홈페이지 |
| 개인정보 위험 | ◎ 없음 → Git 커밋 가능, 발표에 그대로 사용 가능 |
| **조항 단위 구조** | ◎ **제1조/제2조… 청킹 규칙이 명확** |
| 한국어 | ◎ 본프로젝트 LoRA 학습에 유리 |
| 분류축 | ◎ 분야(복지/재정/건설…)가 자연스럽게 존재 |

**"조항 단위"가 특히 중요하다.** 토큰 비용 절감을 위해 문서를 잘라서 처리해야 하는데,
조례는 문서 구조 자체가 조항으로 되어 있어 일반 보고서보다 파싱이 쉽다.

---

## 3. ⚠️ 지시서 정합성 — 요약·분류를 대체하지 않는다

지시서 문구:

> "생성형 AI(Chat GPT)/OLLama API 활용 **핵심 키워드 분류 및 요약** 기능개발"

즉 **필수 기능은 요약 + 분류 두 개**다.
"기준금액·적용대상·근거조문 추출"은 요약도 분류도 아닌 **제3의 기능(정보 추출)** 이므로,
**대체하면 안 되고 추가해야 한다.**

```
analyzers/
├── summary_analyzer.py     필수  조례/공고문 요약
├── category_analyzer.py    필수  분야 분류
└── criteria_analyzer.py    선택  기준금액·적용대상·근거조문 추출
                                  → D4 여유 시 착수, 아니면 본프로젝트
```

### 이게 오히려 발표 강점이 된다

`Analyzer` Protocol을 미리 설계해둔 이유가 정확히 이것이다.

> "지시서 요구사항인 요약·분류를 구현한 뒤, **같은 인터페이스에 도메인 특화 분석기를 하나 더 추가**해
> 확장성을 실제로 증명했습니다. 기존 코드는 한 줄도 수정하지 않았습니다."

**"확장 가능하게 설계했다"가 주장에서 증명으로 바뀌는 지점**이다.

### 우선순위 (지켜야 함)

```
D2~D3  summary + category 완성          ← 여기까지가 필수. 안전지대 확보
D4     여유 있으면 criteria_analyzer 착수
D5 이후 착수 금지 (미완성 리스크)
```

**요약·분류를 먼저 끝내고 어려운 걸 시도한다.** 반대로 하면 셋 다 미완성이 된다.

## 4. 확정 제안 값

### `document_type` — 업로드 시 지정하는 문자열 라벨

```
"ordinance"   조례 / 규칙
"notice"      공고문 / 고시
```

2개로 시작. 본프로젝트에서 값만 추가하면 확장된다 (코드 수정 없음).

### `category` — LLM이 분류, `Literal` 로 값 고정

```python
CATEGORIES = [
    "복지/보건",
    "재정/세제",
    "건설/도시",
    "환경/안전",
    "교육/문화",
    "산업/경제",
    "행정/제도",
]
```

**7개로 제한한 이유:** 후보가 10개 이상이면 LLM이 경계에서 흔들려 같은 문서가 매번 다르게 분류된다.
그러면 목록 화면의 카테고리 필터 기능이 신뢰를 잃는다.

**⚠️ 이 값은 §5-2 검증을 통과한 뒤 확정한다.** 지금은 초안이다.

# 5. 검증 계획 — 말이 아니라 측정으로

> 각 검증은 **합격 기준**을 미리 정하고, 통과하지 못하면 값이나 프롬프트를 고친다.
> 검증 결과는 그대로 **통합테스트시나리오 / 테스트결과서 산출물**이 된다.

---

## 5-1. 문서 수집 검증 (담당: 전원 / D2)

### 목표 구성 — 20건

| 유형 | 건수 | 목적 |
|---|---|---|
| 텍스트 레이어 PDF (조례) | 12 | 주 경로 (PyMuPDF) |
| **스캔 PDF / 이미지 공고문** | **5** | **PaddleOCR 시연** |
| 표가 많은 문서 (금액표 포함) | 3 | 구조 인식 한계 확인 |

### ⚠️ 스캔본 5건이 왜 필수인가

조례 PDF는 **대부분 텍스트 레이어가 있어서 OCR을 타지 않는다.** 스캔본이 없으면:

```
PaddleOCR을 도입했는데 데모에서 한 번도 실행되지 않음
→ "왜 OCR을 넣었나"에 답이 약해짐
→ 이미지 2.75GB의 정당성이 사라짐
```

오래된 고시, 첨부 서식류 중에 스캔해서 올린 문서가 있다. 그걸 찾아 5건 확보한다.

### 검증 방법 — 텍스트 레이어 유무 실측

```python
# ml/check_text_layer.py
import fitz, sys, os

for path in sys.argv[1:]:
    doc = fitz.open(path)
    total = sum(len(p.get_text().strip()) for p in doc)
    per_page = total / max(doc.page_count, 1)
    verdict = "TEXT_LAYER" if per_page >= 50 else "OCR 필요"
    print(f"{os.path.basename(path):40s} {doc.page_count:3d}p  "
          f"페이지당 {per_page:6.0f}자  → {verdict}")
    doc.close()
```

```powershell
docker compose exec api python /app/ml/check_text_layer.py /app/fixtures/*.pdf
```

### 합격 기준

- [ ] 총 20건 이상 확보
- [ ] `OCR 필요` 판정이 **5건 이상**
- [ ] `category` 7개 각각에 **최소 1건 이상** 존재
- [ ] 한 카테고리에 **50% 이상 몰리지 않음**
- [ ] 개인정보 포함 문서 **0건** (공개 자료만)
- [ ] `fixtures/README.md` 에 출처·라이선스 기록

**불합격 시:** 부족한 카테고리 문서를 추가 수집하거나, 카테고리 값을 조정(§5-2로 이동)

## 5-2. 카테고리 값 검증 (담당: 박세현 + 김보현 / D2 저녁)

**카테고리 값을 먼저 확정하고 코드를 짜면 안 된다.** 실제 문서로 검증한 뒤 확정한다.

### 절차

```
1. 수집한 20건을 3명이 각자 눈으로 분류 (LLM 없이)
2. 3명 결과 비교 → 사람끼리도 갈리는 문서를 찾는다
3. 사람끼리 갈리면 → 카테고리 정의가 모호한 것 → 값을 합치거나 기준을 명문화
4. 사람 3명이 일치한 것을 "정답(Golden)"으로 확정
5. LLM으로 분류 → 정답과 비교
```

### 합격 기준

| 지표 | 기준 |
|---|---|
| 사람 3명 간 일치율 | **70% 이상** (미달 시 카테고리 정의부터 수정) |
| LLM ↔ 정답 일치율 | **80% 이상** |
| 정의된 값 외 출력 | **0건** (`Literal` 강제가 동작하는지) |
| 최다 카테고리 비중 | **50% 이하** |

### 불합격 시 조치

```
사람 간 일치율 낮음   → 카테고리를 합친다 (예: 교육/문화 + 산업/경제 통합)
LLM 일치율 낮음      → 프롬프트에 각 카테고리 정의를 1줄씩 명시
정의 외 값 출력      → Literal 타입 + 검증 실패 시 재시도 1회 추가
한 곳에 몰림         → 그 카테고리를 2개로 분할
```

> **이 "정답 20건"이 본프로젝트의 평가셋이 된다.** LoRA 파인튜닝 모델의 성능을 측정할 때
> 같은 20건으로 비교하면 "상용 API 대비 몇 점"을 말할 수 있다. 지금 만들어두면 5주 뒤에 그대로 쓴다.

## 5-3. 추출 경로 분기 검증 (담당: 최재정 / D3)

텍스트 레이어 판별이 실제로 동작하는지 확인한다.

### 방법

```powershell
# 20건 업로드 후
docker compose exec db psql -U postgres -d pdfbrief -c "
SELECT e.extract_method, count(*), round(avg(e.char_count)) AS avg_chars
FROM extracted_texts e GROUP BY e.extract_method ORDER BY 2 DESC;"
```

### 합격 기준

| 지표 | 기준 |
|---|---|
| `TEXT_LAYER` 로 처리된 건수 | 12건 내외 |
| `OCR` 로 처리된 건수 | **5건 이상** |
| 추출 실패(`EXTRACTION_FAILED`) | **0건** |
| 텍스트 PDF가 OCR로 잘못 분기 | **0건** |
| 스캔본이 TEXT_LAYER로 잘못 분기 | **0건** |

### 불합격 시

`OCR_CHAR_THRESHOLD`(기본 50) 값을 조정한다.
`check_text_layer.py` 출력의 "페이지당 글자 수" 분포를 보고 **두 집단이 갈리는 지점**으로 설정한다.

## 5-4. 요약 품질 검증 (담당: 박세현 / D3~D4)

### 방법 — 정성 평가

3명이 각각 다른 5건씩(총 15건) 원문과 요약을 비교해 채점한다.

| 항목 | 배점 |
|---|---|
| 핵심 내용 포함 | 1~5 |
| 사실 정확성 (원문에 없는 내용 없음) | **0 또는 1** (있으면 즉시 0) |
| 분량 적정성 | 1~5 |

### 합격 기준

- [ ] 핵심 내용 평균 **3.5 이상**
- [ ] **사실 오류 0건** ← 하나라도 있으면 불합격
- [ ] 요약 길이가 원문의 20% 이하

### 불합격 시

```
사실 오류 발생  → 프롬프트에 "원문에 없는 내용을 추가하지 마시오" 제약 추가
                   + 원문 인용 근거를 함께 출력하도록 스키마 변경
분량 초과       → 프롬프트에 문장 수 상한 명시 (예: 3~5문장)
```

## 5-5. 환각 방지 검증 (담당: 박세현 / criteria_analyzer 착수 시)

**이 프로젝트에서 가장 중요한 검증이다.** 금액을 다루는 도메인이라
없는 숫자를 만들어내면 서비스 자체가 무의미해진다.

### 방법 — 함정 데이터로 시험

```
금액이 명시된 조항        5건
금액이 전혀 없는 조항     5건   ← 함정
금액이 "예산의 범위 내"처럼 모호하게만 적힌 조항  3건   ← 함정
```

### 합격 기준

| 케이스 | 기대 결과 | 기준 |
|---|---|---|
| 금액 있음 | 정확한 숫자 추출 | 5/5 정확 |
| **금액 없음** | **`null` 또는 "금액 없음"** | **5/5. 숫자를 만들어내면 0점** |
| 모호한 표현 | `null` + 원문 표현 그대로 기록 | 3/3 |

### 구현 방식

```python
class CriteriaResult(BaseModel):
    target: str | None = None          # 적용대상
    amount: int | None = None          # 기준금액 (없으면 None)
    amount_text: str | None = None     # 원문 표현 ("예산의 범위 내" 등)
    article_no: str | None = None      # 근거조문 ("제5조제2항")
    confidence: float
```

**`amount`는 반드시 `int | None`.** 빈 값을 0으로 채우면 "0원"으로 오해되므로 `None`을 유지한다.
프롬프트에도 "금액이 명시되지 않은 경우 amount를 null로 두고 amount_text에 원문 표현을 기록"을 명시한다.

## 5-6. 재현성 검증 (담당: 박세현 / D4)

같은 문서를 여러 번 분석했을 때 결과가 흔들리지 않는지 확인한다.

```powershell
# 같은 문서를 3회 analyze 호출 후
docker compose exec db psql -U postgres -d pdfbrief -c "
SELECT document_id, analyzer_type, result_json->>'category' AS category, count(*)
FROM analyses WHERE analyzer_type='category'
GROUP BY 1,2,3 ORDER BY 1;"
```

### 합격 기준

- [ ] 같은 문서의 `category` 가 **3회 모두 동일**
- [ ] 흔들리면 → `temperature=0` 설정 + 프롬프트에 카테고리 정의 명시

> `analyses` 테이블이 1:N 구조라 **재분석 결과가 덮어써지지 않고 누적**되므로 이 검증이 가능하다.
> 이 구조가 본프로젝트의 모델 비교에도 그대로 쓰인다.

## 6. 팀원별 성장 포인트

| 담당 | 이 도메인에서 다루게 되는 것 | 왜 성장에 좋은가 |
|---|---|---|
| **최재정** (A) | 스캔 품질이 낮은 공문서 OCR, 조항 단위 분리 | 실제 데이터의 편차를 다루는 경험. 판별 로직을 임계값으로 설계 |
| **박세현** (B) | 숫자+조건이 섞인 정보를 Structured Output으로 정확히 추출, 환각 방지 | 단순 요약보다 정밀한 프롬프트 설계·검증. Golden Dataset 평가 경험 |
| **김보현** (C) | 조문 번호·문서 유형별 정리 구조, 검색 | 본프로젝트 RAG 도입을 대비한 데이터 구조 설계 |

**박세현(B)의 난이도가 가장 높다.** 그래서 §3의 우선순위(요약·분류 먼저)를 반드시 지킨다.

| 4 | `criteria_analyzer` 를 무리해서 착수 → 요약·분류까지 미완성 | D4 이후 착수 금지 (§3) |
| 5 | 금액 환각 | §5-5 함정 데이터 검증 필수 |
| 6 | 문서 수집이 D2를 넘김 | 최소 10건으로 개발 시작하고 병행 수집 |

## 8. 일정 배치

| 시점 | 작업 | 담당 |
|---|---|---|
| D2 (8/1) | 문서 20건 수집 + 텍스트 레이어 실측 (§5-1) | 전원 |
| D2 저녁 | 카테고리 값 검증 및 확정 (§5-2) | 박세현 + 김보현 |
| D3 (8/2) | 추출 경로 분기 검증 (§5-3) | 최재정 |
| D3~D4 | 요약 품질 검증 (§5-4) | 박세현 |
| D4 (8/3) | 재현성 검증 (§5-6) / 여유 시 `criteria_analyzer` 착수 | 박세현 |
| D4 | 환각 방지 검증 (§5-5) — criteria 착수한 경우만 | 박세현 |
| D5 (8/4) | 검증 결과를 테스트결과서로 정리 | 전원 |

**§5 검증 결과가 그대로 `통합테스트시나리오(결과).xlsx` 와 `단위테스트결과서.xlsx` 가 된다.**
별도로 테스트 항목을 만들 필요가 없다.

## 9. 본프로젝트 확장 계획 (발표 05번에 사용)

```
[미니]  조례·공고문 요약 + 분야 분류
        (+ 여유 시 기준금액·근거조문 추출)
              │
              │  analyses 테이블에 provider / model_name / tokens 기록 누적
              ▼
[본]    ① 축적된 결과를 검수 → LoRA 파인튜닝 → Ollama 서빙
        ② criteria_analyzer 정식 도입
        ③ 조례 간 비교·검색 (RAG로 근거 조문 탐색)
              │
              ▼
[최종]  지자체 의회 법안 초안 작성 + 법률에 따른 금액 산정
```

**§5-2에서 만든 "정답 20건"이 본프로젝트의 모델 평가셋**이 된다.
같은 20건으로 상용 API와 파인튜닝 모델을 비교하면 "F1 0.72 → 0.85" 같은 수치를 말할 수 있다.

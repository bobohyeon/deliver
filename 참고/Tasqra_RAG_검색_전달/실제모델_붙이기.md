# 실제 임베딩 모델 붙이기 (튜닝 전 베이스 모델)

## 이 문서에 나오는 기능 ID

| ID | 작업명 |
|---|---|
| `RAG-02` | 임베딩 생성 · 저장 |
| `RAG-04` (=`SRH-001`) | 의미 검색 — **글자가 하나도 겹치지 않는 질의**로 관련 문서를 찾는다 |
| `RAG-08` (=`SRH-002-2`) | 근거 스니펫 연결 |

---

## 왜 하는가

지금은 가짜 임베더(`fake-hash-v1`)로 돌고 있다. 해시 벡터라 **의미가 없다.**
그래서 `RAG-04` 의 핵심 판정 기준을 아직 확인하지 못했다.

> **글자가 하나도 겹치지 않는 질의**로 관련 문서가 나온다

실제 모델을 붙이면 이것을 처음으로 확인할 수 있다. 그리고 검색 결과가 실제로
어떻게 나오는지 보면 "문서별로 묶어야 하나" 같은 화면 결정에도 근거가 생긴다.

**모델은 튜닝 전 `dragonkue/BGE-m3-ko` 를 쓴다.** 파인튜닝판은 우리 평가셋에서
전 지표가 10~15% 떨어졌으므로 채택 대상이 아니다.

## 준비 — 왜 호스트에 띄우나

| 방법 | 결과 |
|---|---|
| 컨테이너에 sentence-transformers | **기각.** api·worker 가 각각 약 2.3GB 를 올려 합계 4.6GB. 가용 4.8GB 로는 불가 |
| Ollama | **기각.** 설치돼 있지 않고, BGE-m3-ko GGUF 는 양자화·풀링이 미검증 |
| **호스트에 작은 서버** | 약 2.3GB 한 번. 컨테이너 이미지 그대로. **새 설치 0개** |

`C:\dev\embed-test\.venv` 에 sentence-transformers 가 이미 있고, HTTP 서버는
표준 라이브러리를 쓴다.

## 순서

### 0단계 — 메모리 확보

호스트에 약 2.3GB 가 필요하다. 검색 테스트에 워커는 필요 없으므로 잠깐 내린다
(paddleocr 모델이 올라가 있을 수 있다).

```powershell
cd C:\dev\Tesqra\Tasqra
docker compose stop worker
```

브라우저 탭도 줄이면 좋다.

### 1단계 — 임베딩 서버 띄우기

새 PowerShell 창을 하나 더 연다 (서버가 계속 떠 있어야 한다).

```powershell
cd C:\dev\embed-test
.venv\Scripts\activate
copy C:\dev\deliver\도구\embed_server.py .
python embed_server.py
```

모델을 올리는 데 시간이 걸린다. 준비되면 이렇게 나온다.

```
  듣는 곳   http://0.0.0.0:8900
  컨테이너  http://host.docker.internal:8900/v1
  모델      dragonkue/BGE-m3-ko
  차원      1024
  max_seq   1024
```

**Windows 방화벽이 물어보면 허용한다.** 컨테이너가 `host.docker.internal` 로
호스트에 닿아야 하므로 `0.0.0.0` 에 바인딩한다.

확인 (원래 창에서):

```powershell
curl.exe -s http://localhost:8900/health
```

### 2단계 — `docker-compose.yml` 에 3줄 추가

**팀 공유 파일이다.** 다만 기본값이 `true` 라 **팀원 동작은 그대로다** —
`USE_FAKE_AI` 와 완전히 같은 방식이다.

`api` 와 `worker` 의 `environment:` 양쪽에 넣는다. 청킹은 워커가 하고 검색은
api 가 하므로 둘 다 필요하다.

```yaml
      # 임베딩(RAG-02). 기본값 true 는 안전장치다 — 실제 모델은 약 2.3GB 를
      # 메모리에 올리므로, 켜져 있는 줄 모르면 개발 노트북이 스왑으로 밀린다.
      USE_FAKE_EMBEDDING: ${USE_FAKE_EMBEDDING:-true}
      EMBEDDING_BASE_URL: ${EMBEDDING_BASE_URL:-http://host.docker.internal:8900/v1}
      EMBEDDING_MODEL: ${EMBEDDING_MODEL:-dragonkue/BGE-m3-ko}
```

`worker` 에는 `extra_hosts` 가 없으므로 Linux 에서 `host.docker.internal` 이
닿지 않는다. Windows·Mac 의 Docker Desktop 은 기본 제공하므로 지금은 문제가
없지만, 팀에 Linux 사용자가 있으면 `api` 처럼 아래를 추가해야 한다.

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

### 3단계 — 루트 `.env` 로 켜기

`.env` 는 `.gitignore` 에 있으므로(153행) **커밋되지 않는다.** 개인 설정이다.

`C:\dev\Tesqra\Tasqra\.env` 를 만들고:

```
USE_FAKE_EMBEDDING=false
EMBEDDING_BASE_URL=http://host.docker.internal:8900/v1
EMBEDDING_MODEL=dragonkue/BGE-m3-ko
```

```powershell
docker compose up -d api
docker compose exec api python -c "from app.core.config import settings; print('가짜?', settings.USE_FAKE_EMBEDDING); print('주소', settings.EMBEDDING_BASE_URL); print('모델', settings.EMBEDDING_MODEL)"
```

`가짜? False` 가 나와야 한다. `True` 면 `.env` 가 읽히지 않은 것이다
(`docker compose restart` 는 환경변수를 다시 읽지 않는다 — `up -d` 를 써야 한다).

### 4단계 — 청킹 다시 돌리기

**이 단계를 빠뜨리면 검색 결과가 0건이 된다.**

검색은 `WHERE embedding_model = <현재 모델>` 로 걸린다. 지금 청크는
`fake-hash-v1` 로 만들어졌으므로 새 모델로는 걸리지 않는다. 서로 다른 벡터
공간을 섞지 않기 위해 일부러 넣은 조건이다.

```powershell
docker compose up -d worker
docker compose exec worker python -c "from app.worker import build_chunks_task as t; [print(f'prj={p} doc={d} -> 청크 {t.apply(args=[p,d]).get()}개') for p,d in [(1,1),(1,2),(2,3),(3,4)]]"
```

임베딩 서버 창에 요청 로그가 찍힌다. 청크 16개면 몇 초 안에 끝난다.

```powershell
docker compose exec db psql -U postgres -d tasqra -P pager=off -c "SELECT embedding_model, count(*) FROM document_chunks GROUP BY 1"
```

`dragonkue/BGE-m3-ko` 만 남아야 한다. `fake-hash-v1` 이 함께 있으면 청킹이
일부만 다시 돈 것이다 (재청킹은 문서의 옛 청크를 지우고 다시 만든다).

### 5단계 — `RAG-04` 판정 기준 확인

브라우저에서 **글자가 겹치지 않는 질의**를 넣는다.

| 질의 | 나와야 할 것 | 왜 어려운가 |
|---|---|---|
| 돈은 언제 받나요 | `4. 대금 지급` 조각 | "돈"·"받나요" 가 본문에 없다 |
| 여러 회사가 같이 들어갈 수 있나 | `7. 공동수급` 조각 | "공동수급체" 와 글자가 안 겹친다 |
| 늦게 끝내면 무슨 불이익이 있나 | `5. 지체상금` 조각 | "지체상금" 과 글자가 안 겹친다 |
| 사람 인건비를 어떻게 계산했나 | 산출내역서 `1. 직접인건비` | 다른 문서에서 와야 한다 |

**이게 통과하면 `RAG-04` 가 구조 완성에서 품질 검증까지 간다.**
안 되면 청킹 규칙이나 모델 선택을 다시 봐야 한다.

유사도도 함께 본다. 실제 모델이면 **0.2~0.9** 가 정상이다. 가짜 임베더에서
보였던 음수는 사라져야 한다.

### 6단계 — 정리

```powershell
# 임베딩 서버 창에서 Ctrl+C
docker compose stop worker      # 안 쓰면 메모리 회수
```

`.env` 를 그대로 두면 다음에 컨테이너를 띄울 때 임베딩 서버를 찾다가 실패한다.
서버를 안 띄울 거면 `USE_FAKE_EMBEDDING=true` 로 되돌리거나 `.env` 를 지운다.

## 실패할 때

| 증상 | 원인 |
|---|---|
| 검색 결과 0건 | 4단계(청킹 재실행)를 안 했다. `embedding_model` 을 확인한다 |
| `Connection refused` | 서버가 안 떠 있거나 `127.0.0.1` 에만 바인딩했다. `0.0.0.0` 확인 |
| `가짜? True` | `docker compose restart` 를 썼다. `up -d` 로 다시 |
| 아주 느리다 | 호스트 메모리가 부족해 스왑으로 밀렸다. `worker` 를 내리고 다시 |
| 차원 오류 | 모델이 1024차원이 아니다. `document_chunks` 에 `embedding_dim = 1024` CHECK 가 있다 |

## 아직 확인하지 못한 것

- **이 경로 전체를 실제로 돌려본 적이 없다.** `embed_server.py` 는 HTTP 규격만
  가짜 모델로 검사했다(15개 통과). 실제 sentence-transformers 로는 미검증이다
- 검색 지연이 얼마가 될지 모른다. 질의 임베딩이 CPU 에서 수백 ms 일 수 있어,
  전체 지연의 대부분이 DB(3~5ms)가 아니라 임베딩이 될 것이다

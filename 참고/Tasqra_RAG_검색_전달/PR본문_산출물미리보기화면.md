## 무엇

워크스페이스에 **「산출물」 탭**을 추가합니다. `GET /api/projects/{id}/deliverables/preview`
(먼저 머지된 `DLV-001-2`)를 화면에 붙인 것입니다.

유형 넷을 고르고 기간을 정하면 담길 내용이 몇 건인지 보여주고, 담을 것이 없으면
「만들기」가 비활성되고 그 이유가 문장으로 나옵니다.

| 새 파일 | 무엇 |
|---|---|
| `frontend/src/api/deliverable.js` | API 호출 |
| `frontend/src/features/deliverables/DeliverablesView.jsx` | 화면 |
| `frontend/src/features/deliverables/DeliverablesView.css` | 표현 |

`pages/WorkspacePage.jsx` 는 탭 등록만 바뀝니다.

## 왜

`DLV-001-2` 완료 판정이 *"**LLM 호출 전에 건수가 보이고** 대상이 없으면 생성이
방지된다"* 입니다. **"보인다" 는 화면을 말합니다.** API 응답에 값이 있는 것과
사람이 화면에서 보는 것은 다릅니다. 서버만 있을 때는 그 판정을 채우지 못했습니다.

## 판단 넷

### ① 판단을 화면에서 다시 하지 않습니다

`can_generate` 를 건수로 계산하지 않고 **서버 값을 그대로** 씁니다. 승인 대기는
건수에 있지만 생성 가능 판정에는 더하지 않는다 같은 규칙이 섞여 있어서, 화면에서
다시 구현하면 조용히 어긋납니다. 막힌 이유도 서버가 만든 문장을 그대로 보여줍니다.

같은 이유로 **"담길 내용 합계" 를 보여주지 않습니다.** 합계를 내려면 어느 넷을
더하는지 화면이 알아야 하고 그것이 곧 규칙 복제입니다(서버는 합계를 응답에 담지
않습니다 — `countable_total` 은 내부 판단용 프로퍼티입니다).

합계 대신 카드를 **「담길 내용」과 「담기지 않는 것」으로 묶었습니다.** 승인 대기가
4건인데 만들 수 없는 상황이 모순처럼 보이지 않게 하려는 것입니다.

### ② 기간 입력을 유형과 무관하게 늘 띄웁니다

어느 유형이 기간을 쓰는지는 서버가 압니다(주간 보고서만 필수). 화면이 그것을
알아야 한다면 그 규칙이 **DB CHECK · 서비스 · 화면 세 곳**에 생깁니다.

그래서 기간은 늘 보내고, 쓰지 않는 유형에서는 서버가 무시합니다. 응답의
`needs_period` 로 *"결정사항 대장은 기간을 쓰지 않습니다"* 안내만 띄웁니다.
기본값을 **이번 주(월~일)** 로 넣어 두므로 주간 보고서에서도 처음부터 값이 있어
`422 PERIOD_REQUIRED` 를 볼 일이 없습니다.

> 서버 주석이 이미 이 화면을 전제하고 있었습니다 — *"기간을 쓰지 않는 유형은
> 날짜가 와도 무시한다. 화면이 날짜를 남겨둔 채 유형만 바꿔도 결과가 유형의
> 뜻대로 나오게 하려는 것이다."*

시작일이 종료일보다 늦은 경우도 **서버가 판정**하게 두고(`422
INVALID_PROJECT_DATES`) 그 메시지를 띄웁니다. 화면에서 미리 막으면 또 두 곳입니다.

### ③ `completed_tasks` 를 0 으로 바꾸지 않습니다

`null` 은 **"0건" 이 아니라 "아직 셀 수 없다"** 입니다(`tasks` 테이블 미구현).
0 으로 두면 사용자가 *"이번 주에 완료한 일이 없다"* 로 잘못 읽습니다. 대시보드의
`open_tasks` 와 같은 규칙입니다.

`—` 로 표시하고 카드를 점선·저채도로 낮추고 **이유를 함께 적습니다.** 로딩 중의
`—` 와 헷갈리지 않게 하려는 것입니다.

어느 항목이 그런지는 **응답의 `uncountable` 로 판단**합니다. 화면에 필드 이름을
하드코딩하지 않았으므로, `tasks` 가 생겨 서버가 목록을 비우면 화면은 그대로
숫자를 표시합니다.

### ④ 「만들기」 버튼을 남겨 둔 이유

만들기(`DLV-002-1`)가 아직 없습니다. 그래도 버튼을 둡니다 — **없으면 "대상이
없으면 생성이 방지된다" 를 화면에서 확인할 수 없습니다.** 비활성 버튼이 곧 그
방지입니다.

대신 **버튼 아래에 준비 중임을 늘 적었습니다.** 눌러 보고 나서야 알게 되는 일이
없게 하려는 것입니다. 대시보드가 *"이동할 수 없는 것을 누를 수 있게 두면 고장으로
읽힌다"* 는 이유로 클릭 불가 카드를 `div` 로 둔 것과 같은 문제를 다르게 푼 것입니다.
여기서는 방지가 보여야 해서 버튼을 없앨 수 없었습니다.

## 유형마다 세는 대상이 다른 것을 화면에 적었습니다

| 유형 | 담기는 것 |
|---|---|
| 주간 보고서 | 기간 안의 문서·결정·일정·금액 |
| 결정사항 대장 | 결정 전부 (확정·미결·뒤집힘) |
| 다음 회의 안건 | 아직 정해지지 않은 결정만 |
| 프로젝트 현황 | 지금 상태 전부 |

**적지 않으면 결정사항 대장에서 날짜를 바꿔도 숫자가 안 변하는 것이 고장처럼
보입니다.** 유형 버튼마다 한 줄로 넣었습니다.

## 검증

`frontend/node_modules` 가 없어 `vite build`·`eslint` 를 돌리지 못했습니다. 대신
정적 검사를 돌렸습니다.

- **import 경로·괄호·JSX 태그·CSS 균형** — 기존 파일까지 **js/jsx 53개 · css 24개**
  전부 검사해 문제 0. 기존 파일을 함께 돌린 것은 검사기 자체가 맞는지 보려는 것입니다
- **화면이 읽는 `counts` 키 6개가 백엔드 스키마에 실재하는지** — 이름이 하나 틀리면
  에러 없이 `undefined` → `—` 로 조용히 어긋나는 종류라 따로 봤습니다
- **유형 4개 값이 서버 `DELIVERABLE_KINDS` 와 정확히 같은지**
- **`TABS` 와 `TabContent` 분기에 `deliverables` 가 둘 다 있는지** — `WorkspacePage`
  주석의 경고대로 한쪽만 고치면 새 탭에서 보드가 나오고 **에러가 나지 않습니다**
- **`?? 0` 이 없는지** — `null` 을 0 으로 만드는 실수를 막기 위한 검사입니다

총 14개 항목 통과. 다만 **브라우저에서 실제로 그려본 것은 아닙니다.**

## 이것으로도 `DLV-001-2` 는 아직 완료가 아닙니다

완료 판정("건수가 보이고 대상이 없으면 방지된다")은 이제 충족합니다. 그런데 기능
설명이 *"문서·**태스크**·결정·기한·금액·승인대기 건수를 확인한다"* 인데
**태스크를 못 셉니다** — `tasks` 테이블이 없습니다(`TSK-001-1`).

그래서 상태는 **부분 구현**으로 둡니다. 나열된 여섯 중 하나가 비어 있는 동안
구현됨으로 올리면, 나중에 태스크가 붙을 때 아무도 이 자리를 다시 보지 않습니다.

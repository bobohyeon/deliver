## 설계 결정 다섯

### ① 트라이그램(`pg_trgm` + `ILIKE`) — `tsvector` 가 아니다

**PostgreSQL 에 한국어 전문검색 설정이 없다.** `simple` 설정은 공백으로만 토큰을
나눈다.

```
질의 "계약금액"   본문 "계약금액은"   ->  simple tsvector 는 서로 다른 토큰
```

트라이그램은 글자 3개씩 겹쳐 보므로 조사·붙여쓰기에 걸리지 않는다. 완료 판정이
*"고유명사·숫자·문서번호처럼 **정확한 문자열**로 찾는다"* 이므로 형태소 분석이
아니라 부분 문자열 매칭이 목적에 맞다.

### ② 정확성과 순서를 나눴다

- **정확성은 `ILIKE` 가 보장한다.** 걸린 청크에는 검색어가 반드시 있다
- **순서는 `word_similarity()` 가 정한다.** 이건 정확성이 아니라 표시 순서이므로,
  나중에 바꿔도 **결과 집합은 같다**

`similarity()` 를 쓰지 않은 이유 — 그건 두 문자열 **전체**를 비교해서, 짧은 검색어
와 900자 청크를 비교하면 값이 늘 0 에 가깝다. `word_similarity` 는 본문 안의
**한 구간**과 비교하므로 짧은 질의에 맞다.

### ③ 엔드포인트를 새로 만들었다

`의미 검색(SRH-001)` 은 구현됨이고 프론트가 쓰고 있다. 요청 스키마에 `mode` 를
더하면 그 계약을 고쳐야 하고 회귀 위험이 생긴다. 나중에
`키워드·의미 결합(SRH-004)` 이 `/api/search/hybrid` 를 하나 더 두면 세 방식을
나란히 비교할 수 있다.

### ④ 응답 모양을 같게 두고 필드 셋만 더했다

| 필드 | 뜻 |
|---|---|
| `match_kind` | `"keyword"`. 의미 검색 응답에서는 `null` |
| `match_count` | 검색어가 그 청크에 몇 번 나오는가 |
| `match_offset` | `snippet` 안에서 검색어가 시작하는 위치. 프론트가 강조한다 |

스키마를 나누지 않은 이유는 **하이브리드가 두 결과를 한 순위로 합쳐야** 하기
때문이다. 모양이 다르면 합치는 코드를 또 써야 한다.

`similarity` 는 키워드에서 **코사인 유사도가 아니라 트라이그램 낱말 유사도**다.
어느 쪽인지는 `match_kind` 로 구분한다.

### ⑤ `embedding_model` 조건을 유지했다

키워드 검색에 임베딩은 상관없다. **그런데 빼면 안 된다.** 같은 문서를 두 모델로
청킹해 두면 같은 본문이 여러 행으로 있어서, 조건을 빼면 같은 텍스트가 결과에
중복으로 나온다. 의미 검색은 이 조건으로 중복을 우연히 피하고 있었다.

## 빼먹기 쉬운 곳 둘 — 실제로 막았다

**`ILIKE` 와일드카드.** `%` 는 "아무 글자나 몇 개든" 이므로 검색어에 그대로 들어가면
**조건이 사실상 사라져 프로젝트의 모든 청크가 걸린다.**

```
입력 "100%"   이스케이프 함    -> "%100\%%"    "100%" 를 글자 그대로 찾는다
              이스케이프 없음  -> "%100%%"     "100" 으로 시작하는 것 전부
```

SQL 주입과는 다른 문제다(바인드 파라미터로 넘기므로 주입은 안 된다). 막는 것은
**의미가 뒤바뀌는 것**이다. 역슬래시를 먼저 바꿔야 우리가 넣은 이스케이프를 다시
이스케이프하지 않는다.

**스니펫 offset.** 공백을 **누른 뒤에** 위치를 찾아야 한다. 원문에서 찾고 나서
누르면 글자 수가 줄면서 위치가 어긋난다. 앞에 `…` 를 붙이면 그만큼 offset 이
밀리는 것도 함께 반영해야 한다.

> ⚠ `match_offset` 을 `content_start` 에 더해 **원문 좌표로 쓸 수 없다.** 공백을
> 눌렀으므로 원문과 글자 수가 다르다. 원문 위 강조는 지금처럼 청크 단위
> (`content_start` ~ `content_end`)로 한다.

## 검증한 것

**Python 3.11 기준**이다(`backend/Dockerfile` 이 `python:3.11-slim`). 샌드박스의
기본 `python3` 는 3.9 라서 그것으로 검사하면 안 된다.

| 무엇 | 방법 | 결과 |
|---|---|---|
| 세 패치가 순서대로 붙는가 | `git apply --check` 연속 | 통과 |
| 문법 | 3.11 `py_compile` · 만진 파일 21개 | 통과 |
| `like_pattern` 와일드카드 차단 | `%` · `_` · `\` · `%` 단독 | 통과 |
| `_count_occurrences` | 대소문자 무시 · 없음 · 빈 검색어 | 통과 |
| `_keyword_snippet` offset | 짧은 본문 · 공백 누름 · 가운데 · 맨 앞 · 맨 끝 · 대소문자 · 못 찾음 | 통과 |
| **offset 무작위 대조** | **3000건** — 돌려준 offset 자리에 검색어가 정말 있는지 | **전부 통과** |

순수 함수는 소스에서 `ast` 로 떼어내 돌렸다. 손으로 옮기면 코드와 어긋나므로
**파일을 직접 읽어** 검사했다.

## 검증하지 못한 것 — DB 를 띄운 뒤 이것부터 본다

샌드박스에 `pytest`·`fastapi`·`sqlalchemy` 가 없고 외부 네트워크가 막혀 설치할 수
없다. **아래는 확인되지 않았다. 확인된 것처럼 말하지 않는다.**

| | 무엇을 확인할까 | 어떻게 |
|---|---|---|
| 1 | `backend/tests/test_search_keyword.py` 가 통과하는가 | `pytest backend/tests/test_search_keyword.py` |
| 2 | 마이그레이션이 도는가 | `alembic upgrade head` → `\d document_chunks` 에 `ix_chunk_text_trgm` |
| 3 | **`ILIKE` 가 그 인덱스를 타는가** | `EXPLAIN` 에 `Bitmap Index Scan on ix_chunk_text_trgm` 이 보여야 한다. `Seq Scan` 이면 검색어가 3글자 미만이거나 인덱스가 안 만들어진 것 |
| 4 | **`word_similarity` 의 한국어 분포** | 조사가 붙으면 1.0 이 안 된다. 순서가 쓸 만한지 실제 청크로 봐야 한다. **쓸 만하지 않으면 순서만 바꾸면 된다** — 결과 집합은 `ILIKE` 가 정하므로 안 변한다 |
| 5 | 의미 검색이 그대로 도는가 | `POST /api/search` 회귀 확인. 스키마에 필드가 셋 늘었으므로 프론트가 깨지지 않는지 |

> **3번과 4번은 성격이 다르다.** 3번은 **성능** 문제(느려질 뿐 결과는 맞다),
> 4번은 **표시 순서** 문제다. 둘 다 정확성을 깨뜨리지 않는다.

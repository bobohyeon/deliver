# PR 본문 — 프로젝트 금액 현황 API (복사해 붙이는 용도)

**제목**

```
feat: 프로젝트 금액 현황 API - 이미 있던 계산 로직을 DB·API 에 연결
```

**아래 선 밑을 전부 복사해서 PR 본문에 붙입니다.**

---

## 무엇

`GET /api/projects/{project_id}/amount-summary` 를 추가합니다. 경로는 팀 API
계약서 50행에 정해져 있던 것을 그대로 씁니다.

프로젝트의 **승인된** 금액 항목을 모아 원가구분별 합계·부가세 분리·수량×단가
검산 결과를 돌려줍니다.

## 왜 — **계산 로직은 이미 있었는데 아무도 부르지 않았습니다**

`services/amount_calculator.py` 는 테스트 22개로 검증돼 있었습니다. 그런데
**어느 라우터도 부르지 않았고 `import` 하는 파일조차 없었습니다.** 이름이
언급된 5곳은 전부 주석이었습니다.

그래서 기능명세서의 금액 계산·집계가 「미구현」으로 남아 있었습니다. 이 PR 은
새 계산을 만들지 않습니다 — **있던 것을 처음으로 쓰이게 합니다.**

## 계산기에 DB 행을 그대로 넘길 수 없었습니다 — 조용히 틀리는 것 셋

| | 스키마(`AmountItemOut`) | ORM(`AmountItem`) | 그대로 넘기면 |
|---|---|---|---|
| `category` | `AmountCategory` (Enum) | `str` | **`AttributeError`** (`.value` 호출) |
| `amount` | `int` 필수 | `Decimal \| None` | **`TypeError`** (`sum()` 이 `None`) |
| `unit_price` | `int \| None` | `Decimal \| None` | 검산 값이 어긋남 |
| `source_quote` | **필수** `min_length=1` | `NULL` 허용 | `ValidationError` |
| `confidence` | **필수** | `NULL` 허용 | `ValidationError` |

`AmountItemOut` 은 **LLM 응답 검증용** 스키마입니다. 추출기는 근거와 확신도를
반드시 내므로 그 둘을 필수로 둔 것이 맞습니다. 그런데 DB 는 둘을 `NULL` 로
허용합니다 — 사람이 손으로 넣은 항목에는 원문 근거가 없을 수 있어서입니다.

**억지로 맞추려면 없는 근거 문장을 지어내야 하는데, 그것은 "문서에 없는 값은
비운다"(`AMT-001-1` 완료 판정)를 정면으로 어깁니다.**

### 그래서 계산기의 요구를 실제로 쓰는 만큼으로 좁혔습니다

`services/amount_protocol.py` 에 `AmountLine`·`AmountDocument` `Protocol` 을 두고
계산기가 그 모양에만 의존하게 했습니다. `embedding/protocol.py` ·
`rerank/protocol.py` 와 같은 방식입니다.

**계산기 변경은 `import` 1줄 + 시그니처 8곳뿐이고 본문은 손대지 않았습니다.**
타입 힌트는 런타임에 검사되지 않으므로 **실행 동작이 전혀 바뀌지 않습니다** —
기존 테스트 22개가 그대로 통과합니다.

이제 그 모양을 만족하는 것이 둘입니다.

- `schemas/amount.py` 의 `AmountItemOut`·`AmountExtractionOut` — LLM 추출 경로
- `amount_summary_service.py` 의 내부 `dataclass` — DB 조회 경로

## 판단 다섯

### ① 승인된 항목만 셉니다 — `APPROVED` · `EDITED`

`PENDING`·`REJECTED` 는 빠집니다. *"승인 전에는 어디에도 반영되지 않고"*
(`AMT-001-2` 완료 판정)가 근거입니다.

`EDITED` 를 넣는 것은 **사람이 값을 고쳐 확정한 것**이라서입니다. 모델 주석에
그 뜻이 있습니다 — *"회사마다 산정식이 달라 우리 검산이 불일치로 나올 때의
탈출구가 이것이다."*

단가 선례 조회(`SRH-002-3`)가 쓰던 `APPROVED_DECISIONS` 상수를 그대로 씁니다.
두 곳이 갈리면 선례와 집계의 기준이 달라집니다.

### ② 금액이 `NULL` 인 항목을 0 으로 더하지 않습니다

문서에 금액이 안 적힌 항목이 있습니다(계약서: *"amount 가 null 인 항목을 그대로
둔다"*).

**0 으로 더하면 합계는 그대로지만 "모른다" 는 사실이 사라집니다.** 사용자는
합계를 전부라고 읽고 사업 규모를 작게 오해합니다. 그래서 합계에서 빼고
`excluded_no_amount` 로 건수를 알립니다.

대시보드에서 열린 태스크를 0 이 아니라 `null` 로 둔 것과 같은 판단입니다.
테스트로 **`NULL` 인 경우와 `0원` 인 경우가 구별되는지** 확인했습니다.

### ③ 검산 불일치를 고치지 않고 보고합니다

문서가 `3 × 100 = 400` 이라고 적어놨으면 **그대로 읽고 불일치로 보고합니다.**
합계도 문서에 적힌 400 을 씁니다. 코드가 고쳐버리면 오류가 숨습니다.

수량이나 단가가 없어 검산 자체가 불가능한 항목은 `unverifiable_line_count` 로
따로 셉니다 — 제경비·기술료처럼 비율로 산정된 항목이 여기 들어가고 **오류가
아닙니다.** 불일치와 섞으면 정상인 것이 문제로 보입니다.

### ④ 통화 검사를 항목 단위로 합니다

`aggregate_project` 도 통화 혼재를 잡지만 **문서 단위**로만 봅니다. DB 는 통화를
**항목마다** 들고 있어서 한 문서 안에서 섞이면 그 검사를 빠져나갑니다. 그래서
항목 전체로 먼저 확인하고 `409 CURRENCY_MISMATCH` 로 막습니다.

환율을 적용하지 않는 이유는 계산기 주석에 있습니다 — 어느 시점 환율이냐에 따라
결과가 달라져 *"같은 입력에 같은 결과"* 가 깨집니다.

### ⑤ VIEWER 를 막습니다 — 정책이 미결이라 한 곳에 모았습니다

`get_project_amount_access` 를 새로 만들어 **금액 열람 판정을 한 함수에** 뒀습니다.
역할별 허용 표에서 금액 항목 조회의 VIEWER 칸이 「미결」이고, 멤버 역할 변경
(`PRJ-004-3`)에도 *"금액 열람 권한은 함께 정책 확정 필요"* 가 붙어 있습니다.

**막는 쪽을 기본값으로 둔 이유는 방향이 비대칭이라서입니다.** 막았다가 푸는 것은
이 함수 한 줄입니다. 열었다가 막는 것은 **이미 본 뒤**라 되돌릴 수 없습니다.

기존 `get_project_editor_access` 를 그대로 쓰지 않은 것은 지금은 판정이 같아도
뜻이 다르기 때문입니다. 그것은 "고칠 수 있는가" 이고 이것은 "금액을 볼 수 있는가"
입니다. 같은 함수를 쓰면 나중에 금액을 열 때 편집 권한까지 함께 열립니다.

> ⚠️ **단가 선례 조회(`amount-precedents`)는 VIEWER 에게 열려 있습니다.** 정책이
> 정해지면 그것도 이 함수로 옮겨야 두 엔드포인트가 갈리지 않습니다. 지금 옮기지
> 않은 것은 이미 동작하는 기능의 권한을 바꾸는 일이라 팀 합의가 필요해서입니다.

## 이 API 가 하지 않는 것

**문서에 적힌 합계와의 대조(`check_total`)를 하지 않습니다.** 그 값이 DB 에
없습니다 — `amount_items` 는 항목만 담고 문서 합계를 저장하지 않습니다.

대조는 추출 시점(LLM 응답을 받은 순간)에만 가능하고, 계약서도 `amount_check` 를
분석 응답 안에 두고 있습니다. 여기서 "합계 일치" 를 억지로 만들면 **대조하지
않았는데 대조한 것처럼 보입니다.**

**금액 항목이 없어도 오류가 아닙니다.** 0원과 빈 집계를 돌려줍니다. 현황
조회이므로 빈 프로젝트에서 오류 화면이 뜨면 오히려 고장으로 읽힙니다.
`NO_APPROVED_AMOUNTS` 는 산출물 생성처럼 **막아야 하는** 자리에서 씁니다.

화면도 없습니다. 이 PR 은 DB→API 연결까지입니다.

## 검증

**테스트 24개 추가.** 계산 자체는 기존 22개가 덮고 있으므로 **DB 행을 계산기에
넘기는 경계**만 봅니다 — 조용히 틀리는 곳이 거기입니다.

| 무엇 | 개수 |
|---|---|
| 승인 상태 필터 | 3 |
| 금액 `NULL` 처리 (0 으로 만들지 않는가) | 3 |
| 문자열 `category` → Enum | 3 |
| `Decimal` → `int` (반올림, 잘라내지 않는가) | 2 |
| 부가세 분리 | 2 |
| 검산 (불일치·검산불가·위치) | 4 |
| 통화 (문서 사이 · 문서 안 · 빈 프로젝트) | 4 |
| 결과 순서 고정 (`AMT-002-2` 완료 판정) | 3 |

샌드박스에 `pydantic`·`sqlalchemy` 가 없어 `pytest` 를 돌리지 못했습니다. 대신
**패키지 `__init__` 을 우회해 순수 파일만 직접 로드하고 ORM·스키마 자리에만
스텁을 끼운 하니스로 실제 서비스 로직을 실행**했습니다. 계산기와 서비스는 진짜
코드입니다. **21개 항목 통과.**

`Depends(...)` 정의 순서도 검사했습니다 — 기본값이라 함수를 정의하는 순간
평가되므로 `get_amount_repository` 가 `get_amount_summary_service` 보다, 
`get_project_access` 가 `get_project_amount_access` 보다 위에 있어야 합니다.
아래에 두면 import 시점에 `NameError` 로 앱이 뜨지 않습니다.

계산기 변경이 시그니처뿐인지도 `git diff` 로 자동 확인했습니다.

## 기능명세서 상태

`amount-summary` 가 붙었으므로 **금액 계산·합계 검증(`AMT-002-1`)** 과
**프로젝트 금액 집계(`AMT-002-2`)** 가 처음으로 호출됩니다. 다만 완료로 올리기
전에 짚을 것이 있습니다 — **항목 추출(`AMT-001-1`)이 없어 `amount_items` 에 행이
생길 경로가 아직 없습니다.** 그래서 실제 데이터로 확인된 것은 아닙니다.

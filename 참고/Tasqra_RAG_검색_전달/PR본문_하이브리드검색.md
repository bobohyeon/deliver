## 왜 화면을 방식별로 나누지 않았나

검색창을 하나로 두고 결과를 합쳐서 보여줍니다. **사용자는 방식을 고르지 않습니다.**

`SearchView` 의 탭은 `role='tablist' aria-label='찾는 대상'` 으로, 가르는 축이
**무엇을 찾는가**(문서 내용 / 과거 단가 선례)입니다. 여기에 "키워드" 를 넣으면
**어떻게 찾는가**라는 다른 축이 한 컨트롤에 섞입니다. 사용자가 *"내가 지금 단가를
찾나 키워드를 찾나"* 를 판단해야 하는데, 그 질문은 성립하지 않습니다.

근거 셋:

- 화면정의서 `HOME-09` 배너가 제품 컨셉을 **"본문까지 통합 검색"** 이라고 씁니다
- `SRH-003` 의 구판 ID 가 `VIS-06 통합 검색(PostgreSQL FTS)` 입니다 — 원래 이름이 "통합" 입니다
- `SRH-004 키워드·의미 결합` 이 명세에 있는 이유가 이것입니다

## 왜 점수를 더하지 않고 순위로 합쳤나 (RRF)

두 점수의 **스케일이 다릅니다.** 실측으로 확인했습니다.

| | `0.8` 의 뜻 |
|---|---|
| 의미 검색 (코사인 유사도) | 벡터 방향이 비슷함 |
| 키워드 검색 (트라이그램 낱말 유사도) | 조사가 붙음 (정확일치 `1.0` · 조사붙음 `0.8` · 불일치 `0`) |

같은 `0.8` 이 다른 뜻이라 더하거나 크기를 비교하면 근거 없는 숫자가 나옵니다.
RRF 는 점수를 버리고 **순위만** 씁니다 — `Σ 1/(k + 순위)`. 정규화 상수를 데이터마다
다시 정할 필요도 없습니다.

**두 방식이 동의하는 결과가 자연히 위로 옵니다.**

```
한쪽에서 1등        : 1/61        = 0.0164
양쪽에서 3등·5등    : 1/63 + 1/65 = 0.0313   <- 이게 위
```

`k = 60` 은 RRF 를 제안한 논문(Cormack 외, 2009)이 쓴 값이고 이후 사실상 기본값입니다.
우리 데이터로 재기 전에는 통용값을 씁니다.

## 응답 스키마 — 필드를 더했고 기존 계약은 그대로입니다

`SearchResultItem` 에 더한 필드는 모두 기본값이 `null` 이라 **`POST /api/search` 의
기존 응답은 달라지지 않습니다.**

| 필드 | 뜻 |
|---|---|
| `match_kind` | `"vector"` · `"keyword"` · `"both"`. 의미 검색에서는 `null` |
| `match_count` | 검색어가 그 조각에 몇 번 나오나 |
| `match_offset` | `snippet` 안에서 검색어가 시작하는 위치 (강조용) |
| `fused_score` | RRF 점수. 순서의 근거 |
| `vector_rank` · `keyword_rank` | 각 방식에서 몇 등이었나 |

**`similarity` 의 뜻이 `match_kind` 에 따라 다릅니다.** `vector`·`both` 는 코사인
유사도이고 `keyword` 는 트라이그램 낱말 유사도입니다. 그래서 화면이 코사인일 때만
"유사도 N%" 로 보여주고, 키워드로만 걸린 결과는 대신 "N회 일치" 를 보여줍니다.

`fused_score` 는 **유사도가 아닙니다.** 크기 자체에 뜻이 없고 서로 비교할 때만
뜻이 있습니다(약 0.016 부터). 백분율로 표시하면 안 됩니다.

## 고친 버그 둘 — 하이브리드로 바뀌면서 드러난 것

**① `최고 N%` 가 틀린 값이 됩니다.**

기존 코드가 *"서버가 거리 오름차순으로 주므로 첫 조각이 가장 가깝다"* 를 전제했는데,
RRF 순서에서는 첫 조각이 "합친 순위 1위" 일 뿐 코사인 최고가 아닙니다. 코사인이 있는
조각들의 최대값으로 바꾸고, 전부 키워드로만 걸리면 표시를 숨깁니다.

**② 이모지·확장 한자가 있으면 강조가 어긋납니다.**

서버(파이썬)는 글자를 **코드포인트**로 세고 브라우저(JS)는 **UTF-16 코드유닛**으로
셉니다. `🙂` 나 확장 한자 `𠀋` 같은 BMP 밖 문자는 파이썬 1글자 = JS 2글자입니다.
그런 문자가 검색어 앞에 있으면 offset 이 밀리고, **서로게이트 반쪽이 잘려 깨진 글자가
표시됩니다.** 재현했습니다.

```
py_offset=79  js_slice="\ude42 계약"   <- 깨진 문자
```

조달 문서에 이모지는 드물지만 확장 한자는 인명·지명에 나올 수 있고 OCR 오인식도
있습니다. 프론트가 **서버 offset 을 먼저 믿되 그 자리에 검색어가 있는지 확인하고,
어긋나면 직접 찾도록** 했습니다(`usableOffset`). 스키마 주석에도 단위 차이를 남겼습니다.

## 재순위(SRH-002-1)와의 관계

리랭커는 받은 후보 안에서 순서만 바꾸므로 **후보에 없는 정답은 올릴 수 없습니다.**
그래서 후보를 만드는 단계가 리랭커의 상한을 정합니다.

이 PR 로 **후보가 벡터 단독에서 벡터+키워드 합집합으로 바뀝니다.** 평가셋 진단에서
정답 청크의 숫자값이 다른 청크에도 그대로 있는 질의가 26~27% 였고, 그 구간이 벡터가
가장 약한 자리입니다. 키워드가 그것을 후보에 넣어주므로 **상한이 올라갑니다.**

후보 폭은 `SEARCH_HYBRID_CANDIDATES`(기본 30)이고 요청의 `candidates` 로 덮을 수
있습니다. 리랭커를 `top-10` · `top-20` · `top-50` 중 무엇으로 받을지 실험할 때
이 값을 씁니다.

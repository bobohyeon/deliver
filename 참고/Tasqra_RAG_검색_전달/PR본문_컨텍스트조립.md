## 무엇

검색이 찾아온 청크들을 **토큰 예산 안에서** LLM 프롬프트의 근거로 조립합니다.

**DB·HTTP·LLM 을 아무것도 모르는 순수 로직입니다.** 그래서 모델 없이 전부
테스트됩니다. 새 파일 `app/services/context_assembly.py` 와 테스트, 설정 두 개,
그리고 `chunking.py` 에 공개 이름 하나가 늘었습니다.

**DB 변경이 없습니다.** 마이그레이션을 추가하지 않았습니다.

## 이름이 오해를 부를 수 있어 먼저 적습니다

`RAG-002-1 프롬프트 컨텍스트 조립` 은 **프롬프트 문구를 쓰는 일이 아닙니다.**
무엇을 시킬지는 분석기 쪽이 정하고, 여기는 **근거 자료를 예산 안에 담는 것**까지입니다.
그래서 선행 기능이 `RAG-001-2`(임베딩 생성·벡터 인덱스 저장)이고 검색 사슬 안에 있습니다.

```
[프롬프트 문구]        분석기 쪽
"다음 근거를 보고 답하라"

[근거 자료 조립]       이 PR
[근거 1] 입찰공고.pdf · 조각 5번
준공 검사 완료 후 30일 이내에 지급한다. ...
```

## 왜 그냥 이어 붙이면 안 되는가 — 겹침이 예산을 먹습니다

청킹이 검색 정확도를 위해 **앞 청크의 끝부분을 다음 청크 앞에 겹쳐 넣습니다**
(`chunking.py` 의 `_apply_overlap` · `CHUNK_OVERLAP_TOKENS` 기본 48).

```
청크 n     ... 준공 검사 완료 후 30일 이내에 지급한다.
청크 n+1   준공 검사 완료 후 30일 이내에 지급한다. 선금은 ...
           └──────── 겹침 ────────┘
```

인접한 두 청크를 나란히 담으면 **같은 문장이 두 번 들어갑니다.** 예산이 4,000
토큰인데 겹침으로 수백 토큰을 버리면 근거 한두 조각이 덜 들어갑니다.

**좌표로 겹침 길이를 계산하지 않았습니다.** `_apply_overlap` 주석이 명시합니다 —
*"겹친 부분은 앞 청크의 본문이므로 ... 그래서 `char_count` 와 구간 길이는 다르다."*
`content_start` 가 겹침을 포함하지 않아 `char_count - (content_end - content_start)`
로는 어림값만 나옵니다. **문장 단위로 이미 담은 것을 건너뛰는 쪽**이 정확하고,
인접하지 않은 청크의 정형 문구(청렴계약·담합금지)까지 함께 걸러집니다.

## 설계 결정 넷

| | 규칙 | 왜 |
|---|---|---|
| 1 | **문장 단위 중복 제거** | 겹침과 정형 문구를 함께 걸러냅니다 |
| 2 | **청크는 통째로 담고, 안 들어가면 건너뜁니다** | 반만 담으면 LLM 이 인용한 문장을 사용자가 원문에서 찾지 못합니다. 멈추지 않고 다음 것을 봅니다 — 뒤에 더 작은 청크가 들어갈 수 있습니다 |
| 3 | **첫 근거만 예외로 자릅니다** | 첫 청크가 예산보다 크면 아무것도 못 담게 됩니다. `truncated` 로 알립니다 |
| 4 | **예산에 근거 머리말까지 포함해 셉니다** | 빼고 세면 근거가 많을 때 실제 프롬프트가 예산을 넘습니다 |

**검색이 정한 순서를 그대로 지킵니다.** 문서·조각 번호로 다시 정렬하지 않습니다 —
관련도 높은 것이 앞에 와야 LLM 이 그것을 더 크게 봅니다.

## 청킹과 같은 자를 씁니다

`CharRatioTokenCounter`(`CHARS_PER_TOKEN = 1.89`, 실측)와 문장 경계 규칙을
`chunking.py` 에서 가져다 씁니다. **토큰을 세는 자가 청킹과 달라지면 예산이
어긋납니다.**

문장 경계 규칙은 `_SENTENCE_BREAK` 가 private 이어서 `SENTENCE_BREAK` 라는 공개
이름을 `chunking.py` 에 두 줄 더했습니다. 규칙을 두 곳에 적으면 갈라질 수 있고,
갈라지면 **같은 문장이 다르게 쪼개져 중복 판정이 조용히 실패합니다.**

## 잡은 버그 둘

**① 잘린 스니펫을 근거로 쓰려던 것.**
`SearchResultItem.snippet` 은 220자(키워드는 160자)로 잘린 값입니다. 근거로 쓰면
문장이 중간에서 끊깁니다. 리포지토리가 이미 전문을 들고 오므로
(`search_by_vector` 가 `(DocumentChunk, filename, ...)` 를 돌려주고
`DocumentChunk.text` 가 전문입니다) 거기서 받는 `ContextChunk` 를 따로 두었습니다.
ORM 을 직접 받지 않는 것은 이 모듈이 SQLAlchemy 를 모르게 두려는 것입니다.

**② 한 청크 안의 중복이 걸러지지 않던 것.**
`seen` 집합을 청크 단위로만 갱신해서, 같은 문장이 한 청크에 세 번 있으면 세 번 다
담겼습니다. 표의 같은 행이 반복되는 문서에서 실제로 예산을 먹습니다. 지역 집합을
두어 고쳤습니다.

그 수정이 테스트 2개를 깨뜨렸는데, 원인이 **테스트 자료** 였습니다 — 긴 본문을
*"같은 문장 × 60"* 으로 만들어서 중복 제거가 1문장으로 줄여 버렸습니다. 서로 다른
문장을 만드는 `long_text()` 헬퍼로 고쳤습니다. **코드가 맞고 테스트가 비현실적이었습니다.**

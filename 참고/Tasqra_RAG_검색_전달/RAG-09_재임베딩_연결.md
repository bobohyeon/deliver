# 검수 확정 후 다시 임베딩하기(RAG-09) 연결 · 토큰 추정값 실측 반영

2026-08-18.

## 이 문서에 나오는 ID

| ID | 작업명 |
|---|---|
| `RAG-01` | 문서를 조각으로 자르기(청킹) |
| `RAG-02` | 조각을 벡터로 만들기(임베딩) |
| `RAG-04` | 뜻이 비슷한 내용 찾기(의미 검색) |

## 1. 무엇이 빠져 있었나

`build_chunks_task.delay()` 를 부르는 곳이 `worker.py` 두 곳뿐이었다 — 문서 추출
완료 직후와 자기 재시도. **검수 확정에는 아무것도 걸려 있지 않았다.**

`chunking_service.rebuild_for_document` 의 docstring 에는 이미 이렇게 적혀 있다.

> `RAG-09(검수 확정 시 재임베딩)도 이 메서드를 부른다.`

부르는 쪽만 없었다. 그래서 **검수로 본문을 고쳐도 검색은 고치기 전 내용을 계속
돌려주는 상태**였다.

## 2. 어디에 걸었나 — 트랜잭션 커밋 뒤

`core/transaction.py` 의 `transactional` 은 `with` 블록이 끝날 때 `db.commit()`
한다. 그래서 `service.complete_ocr_review(...)` 가 **리턴한 시점에는 이미 커밋이
끝나 있다.** 라우터에서 부르면 워커가 낡은 본문을 읽는 일이 없다.

트랜잭션 **안에서** 큐에 넣으면 안 된다. 워커가 커밋 전에 DB 를 읽어 고치기 전
본문으로 청킹할 수 있다. Spring 의
`@TransactionalEventListener(phase = AFTER_COMMIT)` 이 필요한 자리이고, 여기서는
`with` 블록 밖이 그 자리다.

같은 패턴이 이미 있었다 — `document_router.py` 의 재시도 라우터가
`service.prepare_retry(...)` 뒤에 `extract_document_task.delay(...)` 를 부른다.

## 3. 실패를 삼킨다 — 재시도와 반대로

재시도는 큐 등록이 실패하면 503 을 던져도 된다. 사용자가 다시 누르면 된다.

**검수 확정은 다르다.** 검수는 이미 커밋됐다. 여기서 503 을 주면 사용자는 "검수
완료가 실패했다"고 읽고 다시 누르는데, 실제로는 이미 완료되어 있다. 사용자에게
거짓을 말하는 셈이다. 그래서 로그만 남기고 성공을 돌려준다.

놓친 문서는 나중에 찾을 수 있다. `ChunkRepository.stale_document_ids()` 가 청크의
`text_version` 이 `extracted_texts.text_version` 보다 작은 문서를 준다.
`ix_chunk_stale (document_id, text_version)` 인덱스가 이 조회용이다.

## 4. 재정님 파일을 4줄로 줄인 방법

검수 완료에 걸 수 있는 자리는 `document_router.py` 아니면 `document_service.py`
이고 **둘 다 문서(`DOC`) 영역**이다. 피할 수 없다.

그래서 try/except 와 로그와 판단 근거를 전부 **우리 파일**(`worker.py`)의
`enqueue_build_chunks()` 안에 넣고, 라우터는 한 줄만 부르게 했다.

| 파일 | 영역 | 변경 |
|---|---|---|
| `api/routes/document_router.py` | 문서 | **import 1줄 + 호출 1줄 + 주석 3줄** |
| `worker.py` | 우리 | `enqueue_build_chunks()` 추가, 기존 호출도 이걸 쓰게 정리 |
| `repositories/chunk_repository.py` | 우리 | `is_current_for_document()` 추가 |
| `services/chunking_service.py` | 우리 | 최신이면 건너뛰기, 본문이 비면 청크 삭제 |
| `services/chunking.py` | 우리 | `CHARS_PER_TOKEN` 1.2 -> 1.89 |
| `core/config.py` | 우리 | `CHUNK_MAX_TOKENS` 주석에 결합 관계 명시 |

부수 효과로 `worker.py` 의 중복이 없어졌다. 추출 완료 쪽도 같은 함수를 쓴다.

## 5. 헛일 방지 — 최신이면 건너뛴다

검수 확정은 **본문이 하나도 바뀌지 않아도** 일어난다. 요소를 제외했다 되돌린
경우가 그렇다. 그때마다 수백 청크를 다시 임베딩하면 낭비다 — 문서 임베딩이 건당
244~519ms 였다.

`is_current_for_document()` 는 `(text_version, embedding_model)` 쌍을 중복 없이
뽑아 그것이 정확히 찾는 쌍 하나인지 본다. 세 경우가 한 번에 걸러진다.

| 결과 | 뜻 | 판정 |
|---|---|---|
| 쌍이 없다 | 청크가 아예 없다 | 만든다 |
| 쌍이 여러 개 | 이전 재청킹이 중간에 끊겨 섞였다 | 다시 만든다 |
| 쌍이 하나인데 다르다 | 낡았거나 다른 모델이다 | 다시 만든다 |
| 쌍이 하나이고 같다 | 최신이다 | **건너뛴다** |

모델 이름을 임베딩 **결과**가 아니라 클라이언트에게 미리 묻는 것이 핵심이다.
`result.model` 은 임베딩을 실제로 돌린 뒤에야 알 수 있어서 "돌릴지 말지" 판단에는
쓸 수 없다. `EmbeddingClientProtocol` 에 `model_name` 이 있는 이유가 이것이다.

## 6. RAG-09 때문에 새로 닿게 된 경로 하나

`rebuild_for_document` 는 본문이 비면 청크를 **지우지 않고** 0 을 돌려줬다.
지금까지는 문제가 아니었다 — 추출 직후에 본문이 비는 문서는 청크도 없었다.

RAG-09 를 붙이면 달라진다. 검수에서 요소를 **전부 제외**하면 본문이 비고, 청크는
남는다. 그러면 **지워진 내용이 검색에 계속 나온다.** 바로 아래 "청크가 만들어지지
않았다" 분기는 이미 지우고 있어서 두 경로가 불일치였다. 맞췄다.

## 7. 글자/토큰 비를 실측값으로 바꿨다 (1.2 -> 1.89)

`chunking.py` 의 주석에 이렇게 적혀 있었다.

> `!! 이 값은 실측하지 않았다. embed-test 에서 실제 토크나이저로 재서 고쳐야 한다.`

실측했다. 조달 문서 867건 본문의 글자/토큰 비 중앙값이 **1.89** 다.

1.2 는 토큰을 **과대추정**해서 청크가 필요보다 짧게 끊겼다.

| | 최대 글자 | 실제 토큰 | 상한(1024) 사용률 |
|---|---|---|---|
| 1.2 | 480 x 1.2 = **576자** | 약 305 | 30% |
| 1.89 | 480 x 1.89 = **907자** | 약 480 | 47% |

### 안전한지 확인한 근거

처음에 "모델 최대가 384 토큰이라 907자면 잘린다"고 판단했는데 **틀렸다.**

- 모델(`dragonkue/BGE-m3-ko`) **기본값**이 384 인 것은 맞다.
- 그러나 우리는 그것을 덮어써서 **1024** 로 쓴다 — `도구/embed_server.py` 의
  `DEFAULT_MAX_SEQ = 1024`. 인자 없이 실행하면 이 값이다.
- 정확도 측정도 1024 로 했다. `config.py` 의 `CHUNK_MAX_TOKENS` 주석에 그 근거가
  이미 적혀 있었다.
- 907자를 최악의 비율(숫자만 나열된 산출내역서, 비 0.9 가정)로 되돌려도 1,008
  토큰이라 1024 안이다.

### 앞으로 이 값을 만질 때

`CHARS_PER_TOKEN x CHUNK_MAX_TOKENS` 가 청크의 최대 **글자** 수이고, 그것을 실제
토크나이저로 재서 임베딩 모델의 `max_seq_length` 를 넘으면 **모델이 뒤를 조용히
잘라낸다. 에러가 나지 않는다.** 두 값을 따로 바꾸면 안 되고, `embed_server.py` 의
`max_seq` 까지 셋을 함께 봐야 한다. 이 내용을 두 파일 주석에 적어 뒀다.

## 8. 검사

| 도구 | 무엇을 | 결과 |
|---|---|---|
| `python3 -m py_compile` | 문법 | 4파일 통과 |
| `도구/check_python_defaults.py` | 최상위 기본값·정의 순서 | 85파일 통과 |
| `도구/check_chunking.py` | 청킹 규칙·좌표·토큰 상한 | 문서 3건 x 비율 2가지 통과 |

`check_chunking.py` 는 새로 만들었다. `chunking.py` 가 `re` 와 `structure.py` 만
쓰므로 SQLAlchemy 없이 단독으로 돈다는 점을 이용한다.

### 검사기를 만들다 잡은 것

처음 쓴 불변식이 **"좌표로 자른 원문이 청크 텍스트의 부분문자열인가"** 였는데
5개 조각 중 4개가 실패했다. 코드가 아니라 **검사가 틀렸다.**

청크 텍스트는 `제목 + 겹침 + 본문` 이고, 겹침은 좌표 구간 **앞**(이전 청크)에서
빌려온 것이라 구간 안에 없다. 그래서 제목과 본문 사이가 벌어져 부분문자열이 되지
않는다. 설계대로다 — 겹침을 제목 뒤에 두는 것은 BGE-M3 가 CLS 풀링이라 앞쪽
토큰이 주제 신호가 되기 때문이다.

올바른 불변식으로 바꿔 확인했다.

- 청크의 끝은 좌표 구간의 끝과 같다 (겹침은 앞에만 붙는다) — **5/5**
- 좌표 구간 길이는 청크 길이를 넘지 않는다 — **5/5**
- 겹침으로 늘어난 글자 수가 조각마다 일정 (53자) — 확인

즉 **좌표는 정확하다.** 검색 결과에서 조각을 눌렀을 때 원문에 강조되는 구간은 그
조각 자신의 구간이고, 빌려온 겹침은 강조에서 빠진다. 그게 맞는 동작이다.

## 9. 아직 확인하지 못한 것

- **도커에서 실제로 돌려보지 않았다.** 검수 확정 -> 청크가 새로 만들어지는지,
  건너뛰기가 실제로 걸리는지, 본문을 비웠을 때 청크가 지워지는지. 확인용
  `도구/verify_rag09.sql` 을 만들어 뒀다.
- 실측 1.89 는 **중앙값**이고 분포(특히 표가 많은 산출내역서)는 이 환경에서 다시
  재지 못했다. `g2b_qa.jsonl` 이 로컬에만 있다. 최악값 0.9 가정은 여유를 크게 둔
  것이지 측정한 값이 아니다.
- 청크가 길어지면 검색 품질이 어떻게 변하는지 재측정하지 않았다. 문맥이 늘어 좋아질
  것으로 보지만, 한 조각에 여러 주제가 섞이면 나빠질 수도 있다. `RAG-04` 질의
  3개로는 판단할 수 없다.

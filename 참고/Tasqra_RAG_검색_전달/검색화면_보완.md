# 검색 화면 보완 — 결과 유지 · 원문 위치 강조

2026-08-18. 검색 화면(`VIS-07`)을 실제로 써 보고 나온 문제 세 가지를 고쳤다.

## 이 문서에 나오는 ID

| ID | 작업명 |
|---|---|
| `RAG-04` | 뜻이 비슷한 내용 찾기(의미 검색) |
| `RAG-07` | 프롬프트에 넣을 근거 조각 모으기 |
| `RAG-08` | 답변에 출처 문서와 원문 인용 붙이기 |
| `VIS-07` | 검색 화면 |

## 고친 것 세 가지

### 1. 한 문서의 조각이 카드로 흩어져 나온다

상위 20개가 긴 문서 하나의 조각으로 채워질 수 있었다. 45,000자 문서면 조각이
50개가 넘으니 목록을 독점한다. 문서별로 묶어서 문서당 2개만 펼치고 나머지는
접었다. 머리글에 `문서 2개 · 조각 10건` 처럼 둘을 나눠 적는다 — 조각 수만
보여주면 "문서 10개"로 오해한다.

**묶는 일을 서버가 아니라 화면이 한 이유.** 서버가 문서당 상한을 걸면 순위의
의미가 바뀌고, 그 상한값에 근거가 없다. 그리고 API 는 조각을 줘야 한다 —
근거 조각 모으기(`RAG-07`)는 같은 문서에서 여러 조각을 골라야 하고, 원문
인용(`RAG-08`)도 조각 단위여야 의미가 있다.

### 2. 문서를 열었다가 뒤로 오면 검색 결과가 사라진다

검색 조건이 컴포넌트 상태(`useState`)에만 있어서 화면을 떠나면 없어졌다.
조건을 **URL 쿼리**(`?q=...&scope=all`)로 옮기고 결과는 **react-query 캐시**에
두었다.

- URL 에 있으니 뒤로가기·새로고침·주소 공유가 다 된다.
- 캐시에 있으니 돌아올 때 **다시 검색하지 않는다.** 이게 중요한 이유는 질의
  한 번에 300ms 가 드는데 그 대부분이 질의 임베딩이기 때문이다(DB 는 3~5ms).
- `staleTime` 을 10분으로 두었다. 프로젝트 기본값은 30초인데(`main.jsx`),
  문서를 읽고 돌아오는 데 30초는 쉽게 넘긴다.

입력창만 로컬 상태로 남겼다. 글자를 칠 때마다 URL 이 바뀌면 뒤로가기 이력이
한 글자마다 쌓인다. 확정(제출)할 때만 URL 에 쓴다.

기각한 방법: `sessionStorage` — 주소 공유와 새로고침이 안 되고, URL 과 화면이
따로 놀아 어긋난다.

### 3. 다른 카드를 눌러도 문서의 맨 앞이 나온다

유사도 39%인 조각을 눌렀는데 문서 첫 부분이 열렸다. 어느 조각을 눌렀는지
화면에 남지 않았다.

검색 응답에 이미 `content_start` · `content_end` 가 있다. `extracted_texts.
content` 안의 구간이다. 그리고 문서 상세 응답의 `extracted_text` 가 바로 그
`extracted.content` 를 그대로 담는다(`document_router.py`) — **같은 문자열이라
좌표를 그대로 쓸 수 있다.** 서버는 고치지 않았다.

- 검색 화면: 조각을 누르면
  `/projects/{p}/documents/{d}?tab=content&from=&to=` 로 이동한다.
- 문서 내용 탭: 그 구간을 `<mark class="range">` 로 감싸고
  `scrollIntoView` 로 그 자리로 스크롤한다.

좌표가 `null` 인 조각(긴 줄을 강제로 쪼갠 경우)은 파라미터 없이 문서만 연다.

## 남의 영역을 건드린 부분

`frontend/src/features/document-detail/DocumentContentTab.jsx` 는 문서(`DOC`)
영역이다. 재정님께 알려야 한다.

다행히 이 파일에 **키워드 검색·하이라이트·스크롤이 이미 구현돼 있었다**
(`splitText` · `<mark>` · `marksRef` · `scrollIntoView`). 그래서 새로 만든
것은 구간 강조 하나뿐이고, 기존 코드는 손대지 않았다.

- `splitText` 는 그대로 두었다. 검사에서 기존 동작이 안 바뀐 것을 확인했다.
- 파라미터가 없으면 기존과 **완전히 같게** 동작한다.
- 직접 입력한 검색어가 있으면 키워드 검색을 우선한다. 구간 강조는 "어디서
  왔는지"이고 검색어는 "지금 찾는 것"이라 더 새로운 의도다.
- 강조 색을 다르게 했다. 키워드는 노랑(`#ffdf68`), 구간은 파랑
  (`#dbe4ff` + `#355ad9` 테두리). 같은 색이면 둘을 구별할 수 없다.
- `강조 해제` 버튼을 넣었다. URL 을 `{tab:'content'}` 로만 바꾼다 — 통째로
  비우면 다른 탭으로 튄다.

## 알려진 한계

**원문이 수정되면 좌표가 어긋날 수 있다.** 검수로 텍스트를 고치면 청킹 당시의
좌표가 실제와 달라진다.

- 길이를 벗어난 경우는 걸러낸다(`0 <= from < to <= 길이`). 아니면 강조하지
  않는다 — 엉뚱한 곳을 강조하는 것보다 낫다.
- **길이 안에서 내용만 바뀐 경우는 지금 걸러내지 못한다.** 다만 이건 곧 고칠
  수 있다. `document_chunks.text_version` 컬럼이 **이미 있고** 청킹이 채운다
  (`chunking_service.py` 가 `text_version=extracted.text_version` 로 저장하고,
  `models/chunk.py` 에 `ix_chunk_stale (document_id, text_version)` 인덱스까지
  있다). 없는 것은 **응답 스키마의 필드 하나**뿐이다.

  그래서 `SearchResultItem` 에 `text_version` 을 더하고(마이그레이션 불필요),
  프론트에서 문서 상세의 `text_version` 과 다르면 강조를 건너뛰면 된다.
  두 줄짜리 작업이다. 이 문서를 쓸 때 "대조할 수가 없다"고 적었던 것은 내가
  컬럼 존재를 확인하지 않고 쓴 것이다 — 확인 후 정정했다.

## 검사

`npm` 레지스트리가 이 환경에서 403 이라 `vite build` 를 돌릴 수 없다. 그래서
두 단계로 확인했다.

| 도구 | 무엇을 | 결과 |
|---|---|---|
| `도구/check_jsx.py` | import 해석 · 괄호 · JSX 태그 · CSS 클래스 | js/jsx 46 · css 22 통과 |
| `도구/check_search_pure.mjs` | 순수 함수 4개의 동작 | 39건 통과 |

`check_search_pure.mjs` 는 함수 로직을 복사해 두지 않고 **소스 파일에서 함수
선언을 잘라내 실행한다.** 복사본을 검사하면 원본이 바뀌어도 계속 통과한다.

검사한 것 중 실제로 버그를 잡은 항목:

- `parseRange('', '20', 100)` → `null`. `Number('')` 이 `0` 이라 빈 문자열을
  그냥 두면 `from=0` 으로 통과해 문서 맨 앞을 강조해 버린다.
- `splitRange` 가 원문을 잃지 않는지. 세 조각을 다시 이어 붙여 원문과 같은지
  네 가지 경계(맨 앞·맨 끝·전체·가운데)에서 확인했다.
- `groupByDocument` 가 조각을 잃지 않는지, 묶음 안에서 유사도 내림차순이
  유지되는지, 조각이 목록에서 흩어져 있어도 한 묶음으로 모이는지.

렌더링은 검사하지 못한다(react 를 불러올 수 없음). 브라우저에서 눈으로
확인해야 한다.

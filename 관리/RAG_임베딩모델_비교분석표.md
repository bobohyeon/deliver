## 1. 결론 — 무엇을 정했나

| 항목 | 정한 것 | 근거 |
|---|---|---|
| **컬럼 차원** | **`vector(1024)`** | 실측 최고가 1024 이고, 후보 4종 중 셋이 1024 를 지원한다 |
| **기본 모델** | **`nlpai-lab/KURE-v1`** (1024) | 뜻으로만 찾는 질의 34개 중 27개. 5개 모델 중 1위 |
| 대안 | `BAAI/bge-m3` (1024) | 차원이 같아 **재임베딩 없이 바꿔 끼울 수 있다** |
| 탈락 | `e5-small-ko-v2` (384) · `e5-base` (768) | 384 는 14개, 768 은 13개. 1024 의 절반이다 |
| API 모델 | **지금은 안 쓴다. 배제도 안 한다** | 셋 다 다국어이고 한국어 성능을 재지 않았다 |
| 모델 확정 | **보류** | KURE 와 bge 는 R@5 1문항 차이. 표본 34개에서 노이즈 범위 |

### 그래서 왜 이 결론인가 — 근거 넷

| | 확인한 것 | 무엇을 뜻하나 |
|---|---|---|
| 1 | **1024 차원이 384·768 을 크게 앞섰다** | 1024 는 23~27개 · 768 은 13개 · 384 는 14개. 컬럼 차원을 1024 로 두는 1차 근거다 |
| 2 | **차원이 높으면 좋다는 것은 성립하지 않는다** | 384 를 768 로 두 배 올렸는데 점수가 내려갔다 (14 → 13). top10 까지 보면 24 → 18 로 6문항 차이다 |
| 3 | **한국어 특화가 효과 있다** | 차원을 1024 로 고정하고 계열만 바꾸니 한국어 특화 27 대 다국어 원본 23. R@3 에서는 22 대 16 |
| 4 | **그래서 다국어 API 로 갈 근거가 약해졌다** | Voyage · OpenAI · Gemini 셋 다 다국어다. 다국어가 한국어 특화를 이기지 못한 사례를 직접 만들었다 |

### 주의 — 이 표를 잘못 읽는 방법

| 잘못된 읽기 | 왜 틀렸나 | 맞는 읽기 |
|---|---|---|
| API 모델은 쓸 필요 없다 | 우리는 API 를 **재지 않았다.** `e5-large` 한 개로 다국어 전체를 판단할 수 없다 | 재보지 않고 배제하는 것도 근거 없는 판단이다. 2라운드로 남긴다 |
| KURE-v1 이 최고 모델이다 | `bge-m3` 와 **1문항** 차이다. R@1 에서는 `e5-large` 가 1위다 | top5 화면이라 R@5 기준이 맞다. 1건만 보여주면 판단이 달라진다 |
| 384 는 나쁜 차원이다 | 384 모델이 **글자겹침 질의에서는 38/39 로 1위**였다 | 차원이 아니라 용도가 다르다. 뜻으로 찾는 데 약하다 |
| 비용 때문에 로컬을 골랐다 | API 비용은 **100문서당 $0.06~0.15** 다. 무시할 수준이다 | 쟁점은 비용이 아니라 **문서가 외부로 나가는 것**이다 |

## 3. 실측 — 실행 비용 (CPU)

**GPU 없이 쟀다.** 청크 127개를 임베딩한 시간이다.

| 모델 | 차원 | 적재 초 | 임베딩 초 | 100청크당 초 | 메모리 MB | 뜻으로만 R@5 | 1문항당 비용 |
|---|---|---|---|---|---|---|---|
| **KURE-v1** | 1024 | 6.4 | 50.3 | 39.58 | 1,534 | **27** | **1.47** |
| bge-m3 | 1024 | 7.4 | 51.7 | 40.70 | 1,552 | 26 | 1.57 |
| e5-large | 1024 | 35.4 | 48.9 | 38.51 | 1,456 | 23 | 1.67 |
| e5-small-ko-v2 | 384 | 6.6 | 4.7 | **3.67** | **421** | 14 | **0.26** |
| e5-base | 768 | 30.6 | 13.9 | 10.97 | 636 | 13 | 0.84 |

> `1문항당 비용` = 100청크당 초 ÷ 맞춘 개수. 낮을수록 같은 성능을 싸게 얻는다.

| 관찰 | 내용 |
|---|---|
| **1024 세 모델은 속도가 거의 같다** | 38.5 · 39.6 · 40.7 초. **성능만 보고 골라도 된다** |
| **384 는 11배 빠르다** | 3.67 초 대 39.58 초. 메모리도 421MB 대 1,534MB. 성능이 절반이라 못 쓰지만 문서가 수만 건이면 다시 볼 값이다 |
| **768 이 좋은 중간값이었다** | 10.97초 · 636MB. 1024 의 3.5배 빠르고 메모리 절반 이하. **성능이 따라왔다면 좋은 타협점이었을 텐데 아니었다** |
| **우리 규모에서는 속도가 쟁점이 아니다** | 문서 5건이 127청크에 50초다. 문서 100건이면 약 17분이고 업로드 시 한 번만 한다 |

## 4. 차원 분석 — 흔히 보는 차원 표가 우리 실측과 맞지 않았다

차원 효과와 계열 효과를 분리하려고 `e5` 원본 계열의 768 과 1024 를 넣었다.

| 차원 | 모델 | 계열 | 한국어 | 뜻으로만 R@5 | 뜻으로만 R@10 |
|---|---|---|---|---|---|
| 384 | e5-small-ko-v2 | e5 | 한국어 튜닝 | 14 | 24 |
| **768** | **e5-base** | e5 | 다국어 원본 | **13** | **18** |
| 1024 | e5-large | e5 | 다국어 원본 | 23 | 25 |
| 1024 | bge-m3 | bge | 다국어 | 26 | 28 |
| 1024 | **KURE-v1** | bge 기반 | **한국어 특화** | **27** | **29** |

**384 를 768 로 두 배 올렸는데 R@5 가 14 에서 13 으로 내려갔다.
R@10 은 24 에서 18 로 6문항 내려갔다.**

### 왜 이런 일이 생기나 — 세 요인이 섞여 있다

| 요인 | 효과 크기 | 근거 | 숫자 |
|---|---|---|---|
| **모델 크기 · 계열** | **가장 크다** | 같은 e5 원본 계열 안에서 768 → 1024 | 13 → 23 (**10문항**) |
| **한국어 튜닝** | **차원 2배보다 크다** | 384 한국어 튜닝판이 768 다국어 원본을 이겼다 | 14 > 13 |
| 차원 자체 | 작다 | 같은 1024 안에서 갈린다 | 23 · 26 · 27 |

> **차원은 상한만 정하고 실제 성능은 계열과 학습이 정한다.**
> 흔히 보는 차원 표(384 경량 / 768 표준 / 1024 고성능 / 3072 최대)는
> **같은 계열 안에서만 성립한다.**

### 그래서 컬럼 차원을 1024 로 두는 근거가 둘이다

| 근거 | 내용 |
|---|---|
| **실측 최고** | 1024 세 모델이 23 · 26 · 27 이고 768 은 13, 384 는 14 다 |
| **후보 호환성** | 후보 4종 중 셋이 1024 를 지원한다 — 로컬 한국어 모델 · Voyage(기본값) · OpenAI large(임의 지정). **Gemini 만 1024 가 없다** |

### 기각한 차원과 이유

| 차원 | 기각 이유 |
|---|---|
| 384 | 뜻으로만 찾는 질의에서 14/34. 1024 의 절반이다 |
| **768** | **13/34 로 384 보다도 낮았다.** 게다가 Voyage 와 로컬 한국어 모델을 쓸 수 없게 된다 |
| 1536 · 3072 | 저장 용량이 1.5~3배로 늘고 **이 차원을 내는 로컬 모델이 없다.** API 에 묶인다 |

## 5. API 모델 사양 — 공개 문서 기준이고 우리가 재지 않았다

> **주의** — 아래 표에 **검색 성능 열이 없는 것은 재지 않았기 때문이다.**
> 우리 문서·우리 질의로 재야 2절과 같은 축에서 비교할 수 있다.

| 모델 | 제공자 | 지원 차원 | 최대 입력 토큰 | 1M 토큰 단가 | 한국어 | 우리 관점 비고 |

| **voyage-3.5** | Voyage AI (MongoDB) | 256 · 512 · **1024(기본)** · 2048 | **32,000** | $0.06 | 다국어 | **1024 가 기본이라 컬럼을 안 바꾸고 비교할 수 있다** |
| voyage-3.5-lite | Voyage AI (MongoDB) | 256 · 512 · 1024(기본) · 2048 | 32,000 | $0.02 | 다국어 | 같은 차원에 더 싸다 |
| text-embedding-3-large | OpenAI | 256~3072 **임의 지정** (기본 3072) | 8,192 | $0.13 | 다국어 | 1024 로 줄여서 쓸 수 있다 |

| 구분 | 모델 | 지원 차원 | 최대 입력 | 비용 | **한국어 실측** |

| **로컬 · 실측** | **KURE-v1** | 1024 고정 | 미실측 | 0원 · CPU 40초/100청크 | **27 / 34** |
| 로컬 · 실측 | bge-m3 | 1024 고정 | 미실측 | 0원 · CPU 41초/100청크 | 26 / 34 |

### 비용이 실제로 얼마인가 — 우리 규모로 환산

| 기준 | 토큰 추정 | voyage-3.5 | text-embedding-3-large |
|---|---|---|---|
| 문서 5건 (이번 시험 코퍼스) | 약 5만 | $0.003 | $0.007 |
| 문서 100건 | 약 100만 | $0.06 | $0.13 |
| 문서 1,000건 | 약 1,000만 | $0.60 | $1.30 |

> 토큰 추정은 청크 127개 · 평균 400자 기준의 **어림**이다.
> 한국어는 토크나이저에 따라 글자당 0.7~1.5 토큰으로 갈린다.

**비용은 쟁점이 아니다. 문서 1,000건을 다 임베딩해도 1달러 안이다.**

### 그러면 진짜 쟁점은 무엇인가

| 쟁점 | 내용 |
|---|---|
| **문서가 외부로 나간다** | 임베딩은 **문서 전량**을 보낸다. 요약은 사용자가 요청한 1건만 보내지만 임베딩은 업로드된 모든 문서가 대상이다. **입찰·계약 문서다** |
| **검색할 때마다 외부 호출** | 질의도 임베딩해야 한다. 네트워크 지연과 장애가 검색 기능에 그대로 온다. 로컬은 그런 의존이 없다 |
| **한국어 성능을 모른다** | 우리 실측에서 다국어 원본이 한국어 특화에 4문항 뒤졌다. API 모델도 다국어다 |
| **Gemini 멀티모달은 쓰면 안 된다** | PDF 를 직접 넣으면 **사람이 고친 OCR 텍스트가 반영되지 않는다.** OCR 검수가 우리 차별점인데 그것을 무력화한다 |

## 6. 판단 기준 — 무엇을 보고 골랐나

**성능만 본 것이 아니다.** 아래 9개 축으로 보고 정했다.

| 기준 | 왜 보는가 | 로컬 KURE-v1 | API 모델 | 우리 판단 |
|---|---|---|---|---|
| **한국어 검색 성능** | 문서가 전부 한국어다 | **실측 27/34 로 1위** | 재지 않았다 | 실측이 있는 쪽을 택한다 |
| **문서가 외부로 나가나** | 입찰·계약 문서다 | 안 나간다 | **문서 전량이 나간다** | **이것이 API 의 핵심 쟁점이다** |
| 비용 | 예산 제약 | 0원 (CPU 시간만) | 100문서당 $0.06~0.15 | **비용은 쟁점이 아니다** |
| 검색 시 외부 의존 | 검색이 멈추면 기능이 죽는다 | 없다 | 질의마다 외부 호출 | 로컬이 유리하다 |
| 최대 입력 길이 | 청크가 한도를 넘으면 조용히 잘린다 | **미실측 — 확인 필요** | 8,192 ~ 32,000 (문서 기준) | 우리 청크는 450자라 아직 문제 없어 보이지만 재지 않았다 |
| 차원 유연성 | 컬럼을 바꾸면 재임베딩이다 | 모델마다 고정 | 임의 지정 가능 (OpenAI) | 1024 로 맞추면 양쪽 다 가능하다 |
| 교체 비용 | 판단이 틀렸을 때 | 차원 같으면 재임베딩 없음 | 같음 | **1024 를 택한 이유다** |
| GPU 필요 여부 | 우리 개발기에 GPU 가 없다 | CPU 로 돌아간다 (실측) | 필요 없다 | 둘 다 문제 없다 |
| 라이선스 | 과제 제출물이다 | **미확인 — 확인 필요** | 상용 API 약관 | 로컬 모델 라이선스를 확인해야 한다 |

### 기각한 선택지와 이유

| 기각한 것 | 왜 기각했나 |
|---|---|
| 384 차원 모델을 쓴다 | 속도가 11배 빠르지만 뜻으로 찾는 성능이 절반이다. 우리 목적이 의미 검색이다 |
| 768 로 컬럼을 줄인다 | 저장이 줄지만 실측이 384 보다도 낮았다. Voyage 와 로컬 한국어 모델도 못 쓴다 |
| 3072 으로 크게 잡는다 | 저장이 3배로 늘고 이 차원을 내는 로컬 모델이 없다 |
| **API 모델을 즉시 배제한다** | 우리가 잰 다국어 모델은 `e5-large` 하나다. API 모델들은 그보다 크고 최신이라 **배제할 근거가 없다** |
| 지금 API 모델을 도입한다 | 문서 전량이 외부로 나간다. 그 결정을 **성능 근거 없이** 할 수 없다 |
| 결과를 문서 단위로 묶는다 | 근거 스니펫에 원문을 인용해야 하는데 문서로 묶으면 사라진다. **결과 단위는 청크** |
| 임베딩을 비동기로 만든다 | 작업 큐가 아직 없고 업로드·분석이 이미 동기다. 일관성을 택했다 |

## 7. 측정 이력 — 네 번 재면서 무엇을 바꿨나

**평가셋을 고친 회차가 있다. 회차 간 수치를 그대로 비교하면 안 된다.**

| 회차 | 무엇을 바꿨나 | 왜 | 결과 |
|---|---|---|---|
| 1차 | 모델 3개 · 질의 40개 | 첫 측정 | 1024 두 모델이 384 를 앞섰다. 한 모델만 맞춘 문항이 3개 있었다 |
| 2차 | 질의 40 → 73 · `overlap` 라벨 추가 | 글자만 겹쳐서 맞춘 것을 걸러내야 했다 | `no_overlap` 에서 격차가 커졌다. **이 지표를 기준으로 삼기로 했다** |
| 3차 | 평가셋 5문항 삭제 · 4문항 정답 확장 | 측정 불가 문항(정답 청크 60개 이상)과 모호 문항을 뺐다 | 수치가 소폭 변했다. **1차 수치는 지우지 않고 병기했다** |
| **4차** | **모델 3 → 5** (`e5-base` 768 · `e5-large` 1024 추가) | **차원 효과와 계열 효과를 분리해야 했다** | **차원 단조성이 깨졌다. 한국어 특화 효과가 확인됐다** |

### 평가셋을 어떻게 만들었나

| 단계 | 내용 |
|---|---|
| 1. 문서에서 역으로 뽑았다 | 도메인 지식이 없어도 되는 방법이다. 청크를 읽고 그 청크가 답이 되는 질문을 만들었다 |
| 2. **일부러 다른 말로 물었다** | "입찰보증금" 을 **"돈을 걸지 않고 참여할 수 있나"** 로 바꿨다. 키워드 검색으로는 못 찾게 만든 것이다 |
| 3. 글자 겹침을 라벨로 표시했다 | 질의 단어가 정답 청크에 그대로 있으면 `overlap` 으로 찍었다. 39개가 겹치고 34개가 안 겹친다 |
| 4. **라벨 검사 도구를 만들었다** | `도구/embed-test/check_queries.py` 가 라벨이 안 맞는 행을 잡아준다. 손으로 찍은 라벨을 믿을 수 없어서다 |

### 이 측정의 한계 — 발표 때 먼저 말할 것

| 한계 | 내용 |
|---|---|
| **표본이 작다** | 뜻으로만 찾는 질의가 34개다. **1~2문항 차이는 노이즈로 봐야 한다.** KURE 와 bge 를 못 가르는 이유다 |
| **청킹이 본구현이 아니다** | 시험용 청킹(450자·문단 우선)으로 쟀다. 본구현 청킹이 나오면 다시 재야 한다 |
| 문서가 5건이다 | 청크 127개다. 실제 운영에서는 문서가 늘어 후보가 많아지므로 난도가 올라간다 |
| **정답을 내가 정했다** | 질의를 만든 사람이 정답도 찍었다. 다른 사람이 보면 다르게 찍을 문항이 있다 |
| 최대 입력 길이를 안 쟀다 | 청크가 모델 한도를 넘으면 **조용히 잘린다.** 450자라 아직 문제 없어 보이지만 확인하지 않았다 |

## 8. 남은 확인 — 아직 모르는 것

**이 표에 있는 것을 모른 채로 결론을 확정하지 않았다.**

| 항목 | 왜 필요한가 | 지금 상태 |
|---|---|---|
| **로컬 모델 라이선스** | 과제 제출물에 쓸 수 있는지 | 미확인. KURE-v1 · bge-m3 둘 다 봐야 한다 |
| 모델 최대 입력 길이 실측 | 청크가 조용히 잘리는지 | 미확인. `max_seq_length` 를 찍어보면 된다 |
| **DB 이미지 pgvector 교체** | 리비전 `0011` 이 돌아가려면 | `docker-compose.yml` 이 `postgres:16-alpine` 이다. **팀 합의 필요** |
| `requirements.txt` 에 pgvector | SQLAlchemy `Vector` 타입 | 없다. 추가 필요 |
| KURE-v1 대 bge-m3 | 기본 모델 확정 | R@5 1문항 차이. 평가셋을 키워야 갈린다 |
| API 모델 실측 (2라운드) | 다국어 API 가 한국어 특화를 이기는지 | 안 했다. **데이터 유출 허용 여부가 선행 판단이다** |

### 확인한 것 — 코드로 본 값이다

| 확인 대상 | 결과 |
|---|---|
| DB 이미지에 pgvector 가 있나 | **없다.** `docker-compose.yml` 이 `postgres:16-alpine` 이다 |
| 마이그레이션에 `CREATE EXTENSION vector` 가 있나 | **없다.** 리비전 `0001`~`0009` 전체를 봤다 |
| `requirements.txt` 에 pgvector 가 있나 | **없다** |
| 작업 큐(celery·redis)가 있나 | **없다.** 코드에 매치 0건이다. 그래서 임베딩도 동기로 간다 |

| CHECK 제약 명명 선례가 있나 | 있다. `0009` 가 `ck_extracted_text_char_count` 를 썼다. `ck_{테이블단수}_{컬럼}` 형태를 따른다 |

## 1. 결론 — 무엇을 정했나

| 항목 | 정한 것 | 근거 |
|---|---|---|
| **컬럼 차원** | **`vector(1024)`** | 상위 4위가 모두 1024. 768 은 27·22, 384 는 19 |
| **기본 모델** | **`dragonkue/BGE-m3-ko`** (1024) | 뜻으로만 찾는 질의 **64개 중 41개.** 9개 모델 중 1위 |
| 대안 | `nlpai-lab/KURE-v1` · `Snowflake/snowflake-arctic-embed-l-v2.0` | 둘 다 37개. **1위와 통계적으로 구별되지 않는다.** 차원이 같아 재임베딩 없이 교체 가능 |
| 탈락 | `bge-m3`(35) · `nomic`(768·27) · `Qwen3`(27) · `e5` 3종(22·19·18) | |
| API 모델 | **지금은 안 쓴다. 배제도 안 한다** | 여전히 재지 않았다. **다만 배제 근거가 이번에 더 약해졌다** (5절) |
| **라이선스** | **후보 9종 전부 확인 — 걸러지는 것 없음** | apache-2.0 넷 · mit 다섯. 상업 이용 가능 |
| **모델 확정** | **확정** (8월 12일 판의 "보류" 해제) | 질의를 73 → 133 으로 키워 판별했다 |
| 주의 | **채택 모델은 Ollama 공식 라이브러리에 없다** | GGUF + `Modelfile` 로 등록해야 한다 (6절) |

### 그래서 왜 이 결론인가 — 근거 넷

| | 확인한 것 | 무엇을 뜻하나 |
|---|---|---|
| 1 | **상위 4위가 모두 1024 차원이다** | 41 · 37 · 37 · 35 가 1024 다. 768 은 27·22, 384 는 19. **컬럼 차원을 1024 로 두는 1차 근거** |
| 2 | **차원이 높으면 좋다는 것은 성립하지 않는다** | 1024인 `e5-large` 가 **9종 중 최하위(18)** 다. 384(19)보다도 낮다 |
| 3 | **한국어 튜닝이 효과를 낸 사례는 하나다** | `BGE-m3-ko`(41)가 원본 `bge-m3`(35)를 6문항 앞섰다. **그런데 `KURE-v1`(37)은 원본과 구별되지 않는다**(p=0.77) |
| 4 | **다국어라서 불리하다는 것도 성립하지 않는다** | 다국어 `arctic`(37)이 한국어 특화 `KURE-v1`(37)과 **동점**이다 |

3번과 4번을 합치면 결론은 하나다.

> **범주(한국어 특화 · 다국어 · 차원)로 고르면 안 된다. 개별 모델을 재야 한다.**
> 이름에 `ko` 가 붙었다고 나은 것이 아니고(384 한국어판이 8위),
> 다국어라고 못한 것도 아니다(`arctic` 이 2위).

### 주의 — 이 표를 잘못 읽는 방법

| 잘못된 읽기 | 왜 틀렸나 | 맞는 읽기 |
|---|---|---|
| `BGE-m3-ko` 가 확실히 최고다 | 2위와 **4문항** 차이고, 안겹침만 보면 **통계적으로 유의하지 않다**(p=0.22) | 8개 지표 전부에서 1위이고 전체 질의로는 유의하다(p=0.039). **한 지표만 튄 것이 아니라는 것이 근거다** |
| 한국어 특화 모델을 쓰면 된다 | `KURE-v1`(37)과 다국어 원본 `bge-m3`(35)가 구별되지 않는다 | 범주가 아니라 **개별 모델**을 재야 한다 |
| API 모델은 쓸 필요 없다 | 우리는 API 를 **재지 않았다.** 게다가 다국어 `arctic` 이 한국어 특화와 동점이 나왔다 | **API 를 배제할 근거가 8월 12일 판보다 약해졌다** (5절) |
| 384 는 나쁜 차원이다 | 384 모델이 **글자겹침 질의에서 64/69 로 9종 중 1위**였다 | 차원이 아니라 용도가 다르다. 뜻으로 찾는 데 약하다 |
| 속도로 모델을 가릴 수 있다 | 같은 모델을 세 번 재서 **47.5 · 56.1 · 77.7초**가 나왔다 | 속도 순위를 매기지 않는다. 확실한 것은 `Qwen3` 가 2~2.5배 느리다는 것뿐 |
| 로컬은 공짜다 | 호출 비용은 0원이지만 **배포 무게**가 생긴다. 그리고 **채택 모델은 Ollama 공식이 아니라 등록 작업이 붙는다** | 6절 |

### 이 결론으로 할 수 있는 것

| 할 일 | 내용 | 선행 조건 |
|---|---|---|
| **리비전 `0011`** | `CREATE EXTENSION vector` · `document_chunks.embedding vector(1024)` · **`embedding_model` + CHECK `embedding_dim = 1024`** (교체 가능성 — `API_계약_RAG_검색_초안.md` 7-1절) | **DB 이미지를 pgvector 포함본으로 교체** (팀 합의) |

| **채택 모델 Ollama 등록** | GGUF 내려받기 → `ollama create` | 없다. 바로 착수 가능 |

### 개수 차이가 우연인지 검정했다

개수만 보면 "같은 질의에서 누가 맞히고 누가 틀렸는지" 를 알 수 없다.
`results_detail.csv` 의 질의별 적중을 맞대어 **엇갈린 질의만** 세었다(McNemar).

| 대비 | A만 맞힘 | B만 맞힘 | 엇갈림 | 양측 p | 판정 |
|---|---|---|---|---|---|
| BGE-m3-ko 대 KURE-v1 · 안겹침 64 | 5 | 1 | 6 | **0.22** | 유의하지 않다 |
| BGE-m3-ko 대 KURE-v1 · 전체 133 | 8 | 1 | 9 | **0.039** | **유의하다** |
| KURE-v1 대 bge-m3 · 안겹침 64 | 7 | 5 | 12 | **0.77** | **구별 불가** |

**측정 전에 판정선을 정해 두었다.** 안겹침 64문항에서 6문항 이상이면 실제 차이,
4~5문항은 참고, 3문항 이하는 판별 불가.

**`BGE-m3-ko` 는 4문항 앞섰다 — 판정선을 넘지 못했다.**
안겹침 64문항 중 **6개만 엇갈렸고 58개는 `KURE-v1` 과 똑같이 움직였다.**
그런데도 1위로 적는 근거는 8개 지표 전부에서 1위이고 전체 질의로는 유의하기
때문이다.

**`KURE-v1` 과 `bge-m3` 는 구별되지 않는다.** 37 대 35 로 벌어져 보이지만
엇갈린 12문항이 7 대 5 로 거의 반반이다. 8월 12일 판에서 "1문항 차라 판별 불가"
라고 서술한 것이 이번에 **검정으로 확인됐다.**

### 이 표에서 읽을 것

| 관찰 | 내용 |
|---|---|
| **1위는 BGE-m3-ko** | 안겹침 41/64. 2·3위 37, 4위 35 |
| **2·3·4위는 서로 구별되지 않는다** | 대안이 형식적인 대안이 아니라 **실제로 바꿔 써도 되는 후보**라는 뜻이다 |

## 4. 차원 분석 — 흔히 보는 차원 표가 우리 실측과 맞지 않았다

차원 효과와 계열 효과를 분리하려고 `e5` 원본 계열의 768 과 1024 를 넣었다.

| 차원 | 모델 | 계열 | 한국어 | 안겹침 R@5 | 안겹침 R@10 |
|---|---|---|---|---|---|
| 384 | e5-small-ko-v2 | e5 | 한국어 튜닝 | 19 | 28 |
| **768** | **e5-base** | e5 | 다국어 원본 | **22** | **29** |
| **1024** | **e5-large** | e5 | 다국어 원본 | **18** | **21** |
| 768 | nomic-v2-moe | nomic | 다국어 | 27 | 33 |
| 1024 | bge-m3 | bge | 다국어 | 35 | 44 |
| 1024 | arctic-l-v2.0 | arctic | 다국어 | 37 | 43 |
| 1024 | KURE-v1 | bge 기반 | 한국어 특화 | 37 | 47 |
| 1024 | **BGE-m3-ko** | bge 기반 | 한국어 튜닝 | **41** | **48** |

**같은 `e5` 계열 안에서 768(22) → 1024(18) 로 내려갔다.**
`e5-large` 는 1024차원인데 384차원 모델(19)보다도 낮고 **9종 중 최하위**다.

### `e5-large` 이상 현상 — 재현되지만 원인은 모른다

545청크에서도 그랬고 649청크에서도 그렇다. 상세 결과에 단서는 있다.
질의가 달라도 같은 청크 묶음이 반복해서 1위로 올라온다.

```
e5-large / 안겹침 / top5 = 374,300,273,144,186
e5-large / 안겹침 / top5 = 374,300,186,144,408
e5-large / 안겹침 / top5 = 300,374,273,186,144
```

**이것은 관찰이고 원인이 아니다.** 세운 가설 둘을 모두 기각했다.

| 가설 | 결과 |
|---|---|
| 청크가 512토큰을 넘어 조용히 잘렸다 | **기각.** 512토큰 초과 청크가 0개다 |
| 특정 청크가 허브처럼 모든 질의를 흡수한다 | **기각.** 다른 모델에서는 같은 현상이 안 나타난다 |

### 세 요인이 섞여 있다

| 요인 | 효과 크기 | 근거 | 숫자 |
|---|---|---|---|
| **모델과 학습** | **가장 크다** | 같은 1024 안에서 갈린다 | 18 · 35 · 37 · 37 · 41 (**23문항**) |
| 차원 자체 | 있으나 단조롭지 않다 | 상위 4위가 1024지만 최하위도 1024다 | 768 은 27·22, 384 는 19 |
| 한국어 튜닝 | **모델에 따라 다르다** | `BGE-m3-ko` 는 원본 +6, `KURE-v1` 은 구별 불가 | 41 · 37 대 35 |

> **차원은 상한만 정하고 실제 성능은 모델과 학습이 정한다.**
> 흔히 보는 차원 표(384 경량 / 768 표준 / 1024 고성능 / 3072 최대)는
> **같은 계열 안에서도 성립하지 않았다.**

### 그래도 컬럼 차원을 1024 로 두는 근거가 둘이다

| 근거 | 내용 |
|---|---|
| **실측 상위 독점** | 상위 4위(41·37·37·35)가 모두 1024다. 768 은 27·22, 384 는 19 |
| **후보 호환성** | 1024 후보가 **다섯**이다(`BGE-m3-ko`·`KURE-v1`·`arctic`·`bge-m3`·`Qwen3`). API 후보 넷도 1024 를 낼 수 있다. **바꿔 끼울 여지가 가장 넓은 차원이다** |

### 기각한 차원과 이유

| 차원 | 기각 이유 |
|---|---|
| 384 | 안겹침 19/64. 1위의 절반 이하다 |
| 768 | 27·22 로 1024 상위권에 못 미친다. `nomic`(27)이 그중 최고인데 5위다 |
| 1536 · 3072 | 저장 용량이 1.5~3배로 늘고 **이 차원을 내는 로컬 모델이 없다.** API 에 묶인다 |

## 6. 라이선스와 배포 무게

성능이 같아도 이 두 가지로 판단이 갈릴 수 있다.

### 라이선스 — 후보 9종 전부 확인했다

허브 모델 카드의 `license` 필드를 직접 읽었다. AI 요약이나 블로그가 아니다.

| 모델 | 라이선스 | 상업적 사용 |
|---|---|---|
| **`dragonkue/BGE-m3-ko`** (채택) | **apache-2.0** | **가능** |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | apache-2.0 | 가능 |
| `nomic-ai/nomic-embed-text-v2-moe` | apache-2.0 | 가능 |
| `Qwen/Qwen3-Embedding-0.6B` | apache-2.0 | 가능 |
| `nlpai-lab/KURE-v1` | **mit** | 가능 |
| `BAAI/bge-m3` | **mit** | 가능 |
| `intfloat/multilingual-e5` (base·large) | mit | 가능 |
| `dragonkue/multilingual-e5-small-ko-v2` | mit | 가능 |

**라이선스로 걸러지는 후보는 없다.** 이 기준은 결과적으로 판별력이 없었다.
다만 확인하지 않고 넘어갔다면 채택 모델이 비상업 라이선스일 위험을 안고
제출했을 것이므로 확인 자체는 필요한 절차였다.

| | MIT | Apache-2.0 |
|---|---|---|
| 상업 이용·수정·재배포 | 가능 | 가능 |
| 의무 | 저작권 표시 | 저작권 표시 + **변경 사실 고지** + `NOTICE` 보존 |

원본 `bge-m3` 가 MIT 인데 파생본 `BGE-m3-ko` 가 apache-2.0 인 것은 문제없다.
**MIT 는 재라이선싱을 막지 않는다.** 원본 MIT 고지만 유지하면 된다.

> 같은 연구실(고려대 NLP&AI)의 `KULLM3` 는 **CC-BY-NC**(비상업)라서 확인이
> 필요했다. `KURE` 는 다르게 MIT 다. **이름이 비슷하다고 같은 라이선스라고
> 볼 수 없다.**

### 채택 모델의 배포 경로에 작업이 하나 붙는다

**`BGE-m3-ko` 는 Ollama 공식 라이브러리에 없다.** 허깅페이스 전용 모델이라
**GGUF 파일을 내려받아 `Modelfile` 로 직접 등록**해야 한다.

| 후보 | 배포 작업 |
|---|---|
| `bge-m3` · `arctic-l-v2.0` · `nomic-v2-moe` · `Qwen3` | `ollama pull` 한 줄 |
| **`BGE-m3-ko`** (채택) | GGUF 내려받기 → `ollama create` → 태그 관리 |
| `KURE-v1` | `ollama pull daynice/kure-v1` (비공식 저장소) |

**채택을 뒤집는 사유는 아니다.** 한 번 등록해 두면 이후는 같다. 다만
**임베딩 생성·저장(RAG-02) 에 "모델 등록" 작업이 하나 늘어난다.**

**공식 경로가 꼭 필요하면 `arctic-embed-l-v2.0` 이 `ollama pull` 한 줄로 끝난다.**
안겹침 37문항으로 채택 모델과 4문항 차이고 통계적으로 구별되지 않는다.

**GGUF 는 양자화본이라 우리가 잰 fp32 점수와 다를 수 있다. 그건 안 쟀다.**

### 왜 허깅페이스 얘기가 나오나 — 코드로 확인한 사실

| 확인한 것 | 결과 |
|---|---|
| **우리 시험 도구가 무엇을 쓰나** | `sentence-transformers`. `SentenceTransformer("dragonkue/BGE-m3-ko")` 의 **그 문자열이 허깅페이스 저장소 경로**다. 모델 9개 전부 허깅페이스에서 받았다 |
| **Tasqra 본코드에 허깅페이스가 있나** | **없다.** `transformers` · `sentence-transformers` · `torch` 가 `requirements.txt` 에 하나도 없다. AI 의존은 `openai` **한 줄뿐**이다 |
| **로컬 LLM 은 허깅페이스를 쓰나** | **아니다.** `app/ai/local_client.py` 는 **Ollama** 의 OpenAI 호환 엔드포인트를 부른다 |

### 로컬을 택하면 새로 들어오는 것

| 항목 | 무엇이 | 왜 부담인가 |
|---|---|---|
| **패키지** | `sentence-transformers` → `torch` · `transformers` · `tokenizers` 등 | `torch` 는 파이썬 패키지 중 가장 무거운 축이다. 컨테이너 이미지가 커지고 빌드가 느려진다 |
| **모델 파일** | `BGE-m3-ko` 는 XLM-R large 계열 (**568M 파라미터 · 가중치 2,166MB**) | 이미지에 넣으면 이미지가 커지고, 런타임에 받으면 **허깅페이스가 죽으면 앱이 못 뜬다** |
| 메모리 | **실측 최고 2,203MB** | 컨테이너 메모리 상한을 올려야 한다 |
| 기동 시간 | **실측 적재 7.4초** (캐시가 이미 있는 상태) | 캐시가 없으면 내려받는 시간이 더 붙는다 |
| **모델 등록** | Ollama 공식이 아니라 GGUF 등록이 필요하다 | 위에 적었다 |

**Ollama 로 올리면 `torch` 를 넣지 않아도 된다.** 이미 Ollama 를 쓰고 있으므로
그 경로가 배포 무게를 가장 줄인다. **다만 채택 모델은 GGUF 등록이 선행된다.**

### 이 부담을 줄이는 방법

| 방법 | 내용 | 대가 |
|---|---|---|
| **Ollama 에 GGUF 로 등록한다** | `torch` 를 안 넣고 HTTP 로 부른다. **지금 로컬 LLM 구조와 같은 모양** | 등록 작업 · **양자화로 점수가 달라질 수 있다** |
| 모델을 이미지에 미리 넣는다 | 빌드 때 내려받아 굽는다 | 이미지가 커진다. 모델을 바꾸면 다시 빌드 |
| 볼륨에 캐시를 마운트한다 | `HF_HOME` 을 볼륨으로 둔다 | 볼륨을 팀원마다 채워야 한다 |
| 임베딩만 별 컨테이너로 뺀다 | 본 API 는 가볍게 둔다 | 컨테이너가 하나 늘고 그것도 관리 대상 |
| ONNX 로 바꿔 `torch` 를 뺀다 | `onnxruntime` 만 둔다 | 변환 작업이 붙고 정확도를 다시 확인해야 한다 |

**판단하지 않는다.** 배포는 이 시험의 범위가 아니고 팀 결정이다.
다만 **로컬이 0원이라는 말이 배포 무게까지 0이라는 뜻은 아니다.**

## 7. 판단 기준 — 무엇을 보고 골랐나

**성능만 본 것이 아니다.** 아래 축으로 보고 정했다.

| 기준 | 왜 보는가 | 로컬 `BGE-m3-ko` | API 모델 | 우리 판단 |
|---|---|---|---|---|
| **한국어 검색 성능** | 문서가 전부 한국어다 | **실측 41/64 로 1위** | 재지 않았다 | 실측이 있는 쪽을 택한다 |
| **문서가 외부로 나가나** | 입찰·계약 문서다 | 안 나간다 | **문서 전량이 나간다** | **이것이 API 의 핵심 쟁점이다** |
| 호출 비용 | 예산 제약 | 0원 (CPU 시간만) | Voyage 는 **첫 2억 토큰 무료** = 문서 약 1.3만 건 | **비용은 쟁점이 아니다** |
| **배포 무게** | 컨테이너 이미지와 기동 시간 | `torch` 가 들어오거나 **Ollama 에 GGUF 등록**이 필요하다 | `requirements` 에 줄 하나 없이 HTTP 호출 | **API 가 유리하다** |
| 검색 시 외부 의존 | 검색이 멈추면 기능이 죽는다 | 없다 | 질의마다 외부 호출 | 로컬이 유리하다 |
| **최대 입력 길이** | 청크가 한도를 넘으면 조용히 잘린다 | **8,192 실측.** 우리 청크 최대 306토큰(정답 청크) | 8,192 ~ 32,000 | **잘림 없음 확인** |

| **교체 비용** | 판단이 틀렸을 때 | **1024 후보 다섯을 바꿔 끼울 수 있다.** `embedding_model` 컬럼과 접두어 설정 분리로 준비했다 | 같음 | **1024 를 택한 이유다** |
| GPU 필요 여부 | 우리 개발기에 GPU 가 없다 | CPU 로 돌아간다 (실측) | 필요 없다 | 둘 다 문제 없다 |
| **라이선스** | 과제 제출물이다 | **apache-2.0 — 확인 완료** | 상용 API 약관. 데이터 학습 이용 조항을 봐야 한다 | **로컬은 문제 없다** |
| **Ollama 경로** | 지금 로컬 LLM 을 Ollama 로 쓴다 | **공식 없음. GGUF 등록 필요** | 해당 없음 | 작업이 하나 늘어난다 |

### 기각한 선택지와 이유

| 기각한 것 | 왜 기각했나 |
|---|---|
| 384 차원 모델을 쓴다 | 9~11배 빠르지만 뜻으로 찾는 성능이 절반 이하다(19 대 41). 우리 목적이 의미 검색이다 |

| 임베딩을 비동기로 만든다 | 작업 큐가 아직 없고 업로드·분석이 이미 동기다. 일관성을 택했다 |

## 8. 측정 이력 — 다섯 번 재면서 무엇을 바꿨나

**평가셋을 고친 회차가 있다. 회차 간 수치를 그대로 비교하면 안 된다.**

| 회차 | 청크 | 질의 | 모델 | 무엇을 바꿨나 | 결과 |
|---|---|---|---|---|---|
| 1차 | 127 | 40 | 3 | 첫 측정 | 1024 두 모델이 384 를 앞섰다 |
| 2차 | 127 | 73 | 3 | `overlap` 라벨 추가 | 글자만 겹쳐서 맞춘 것을 걸러냈다. **이 지표를 기준으로 삼았다** |
| 3차 | 127 | 73 | 3 | 5문항 삭제 · 4문항 정답 확장 | 수치가 소폭 변했다 |
| 4차 | 127 | 73 | 5 | `e5-base`·`e5-large` 추가 | 차원 단조성이 깨졌다 |
| **5차** | **649** | **133** | **9** | **문서 10건 · 고시 질의 60개 추가 · 후보 4종 추가 · 정밀도 통일** | **기본 모델이 바뀌었다. 이전 결론 둘을 철회했다** |

### 5차에서 철회한 것

| | 8월 12일 판 | **8월 13일 판** |
|---|---|---|
| **기본 모델** | `KURE-v1` | **`BGE-m3-ko`** (당시 후보에 없었다) |
| **384 대 768** | 384 한국어판(14) > 768 원본(13). "한국어 튜닝이 차원 2배보다 크다" | **뒤집혔다.** 384(19) **<** 768(22). **그 서술을 철회한다** |
| **한국어 특화 효과** | "확인됐다" (KURE 27 > e5-large 23) | **범주로는 성립 안 한다.** 다국어 `arctic`(37) = `KURE-v1`(37) |
| `e5-large` | 23/34 (중위) | **18/64 (최하위)** |
| KURE 대 bge-m3 | 1문항 차 · 서술로만 "판별 불가" | **검정으로 확인** (p=0.77) |
| 최대 입력 길이 | 미실측 | **실측.** 512토큰 초과 청크 0개 |

**작은 표본의 결론을 그대로 들고 가면 안 된다는 사례로 남긴다.**

### 5차에서 늘린 것 — 청크만이 아니다

**질의를 73 → 133 (안겹침 34 → 64)로 늘린 것이 핵심이다.**
청크만 늘리면 방해물만 늘고 순위는 안 바뀐다. 4차에서 청크를 4.3배 늘렸을 때
`KURE` 와 `bge-m3` 의 격차가 1문항 그대로였던 것이 그 증거다.

한번은 계약현황 CSV 20건을 넣어 청크를 **3,655개**까지 늘려 봤다. 결과는 이랬다.

| | 545청크 | 3,655청크 |
|---|---|---|
| 청크 | 545 | 3,655 (6.7배) |
| 채점 질의 | 73 | **73 (그대로)** |
| 정답 청크 | 35 | **35 (그대로)** |

**새로 들어온 3,110청크에 정답이 하나도 없었다.** 순수한 방해물이고 측정 시간만
5개 모델에 122분으로 늘었다. **그래서 되돌리고 질의를 늘리는 쪽으로 갔다.**

### 평가셋을 어떻게 만들었나

| 단계 | 내용 |
|---|---|
| 1. 문서에서 역으로 뽑았다 | 청크를 읽고 그 청크가 답이 되는 질문을 만들었다 |
| 2. **일부러 다른 말로 물었다** | "제안서 평가위원 수" 를 **"심사할 사람을 몇 명 모아야 하나"** 로 바꿨다 |
| 3. 글자 겹침을 라벨로 표시했다 | 69개가 겹치고 64개가 안 겹친다 |
| 4. **라벨 검사 도구를 만들었다** | `check_queries.py` 가 라벨이 안 맞는 행을 잡아준다 |
| 5. **부분 문자열까지 검사했다** | `보안` 은 청크에 `보안약점` 이 있어 걸렸고 `정하` 는 `지정하여야` 안에 있어 걸렸다. 도구로 전수 검사해 9건을 고쳤다 |
| 6. **조 번호를 쓰지 않았다** | "제18조의 배점한도는?" 이라고 물으면 `제18조` 글자가 그 청크에만 있어 **글자 일치로** 맞힌다 |

## 9. 남은 확인 — 아직 모르는 것

**이 표에 있는 것을 모른 채로 결론을 확정하지 않았다.**

| 항목 | 왜 필요한가 | 지금 상태 |
|---|---|---|
| **DB 이미지 pgvector 교체** | 리비전 `0011` 이 돌아가려면 | `docker-compose.yml` 이 `postgres:16-alpine` 이다. **팀 합의 필요** |

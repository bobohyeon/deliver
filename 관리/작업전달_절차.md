# 작업 전달 절차 — 왜 느렸는지와 어떻게 빨라지는지

2026-08-20. *"뭘 해줘 라고 하면 결과물 나오기까지 너무 오래 걸린다"* 를 실측해서 찾은
원인과 고친 절차. **이 문서는 짧게 유지한다.**

## 원인 — 낡은 기준으로 패치를 떠서 거부됐고, 그 우회가 결과물을 키웠다

```
샌드박스 Tasqra 클론  626c211
원격 main            90ff05f
                     -> 59커밋 뒤처짐 · 94파일 7,638줄 변경
```

이 상태에서 패치를 만들면 **거부되는 것이 정상이다.** 그래서 이전 세션들은
`참고/Tasqra_*_전달/파일-NN-이름/` 에 **바뀐 파일 전체를 복사**해 넣는 우회를 썼다.

| | 결과 |
|---|---|
| 전체 파일 복사 | 파일마다 수백 줄을 다시 써야 한다. **이게 대기 시간의 대부분이다** |
| 사용자 쪽 | 손으로 덮어써야 하고, 그 사이 팀이 고친 부분을 **조용히 지운다** |

**낡은 기준이 원인이었고, 기준을 맞추면 우회가 필요 없다.**

## 고친 절차 — 실측으로 확인했다

### 1. 작업 시작 전 (반드시)

```bash
cd /projects/sandbox/Tasqra
git fetch origin
git checkout -B <작업브랜치> origin/main
git rev-parse --short HEAD        # 이 값을 전달 문서에 적는다
```

> **이 세 줄을 건너뛰면 그 뒤 작업 전체가 버려진다.** 59커밋 뒤처진 채로
> 만든 코드는 이미 남이 고친 파일을 되돌린다.

### 2. 코드를 고치고 커밋한다 (샌드박스 클론 안에서만)

```bash
git add <파일들>
git commit -m "feat: ..."
```

팀 레포에 **푸시하지 않는다.** 커밋은 패치를 뜨기 위한 것이다.

### 3. 패치를 뜬다

```bash
git format-patch -1 -o /projects/sandbox/deliver/참고/<전달폴더>/
```

여러 커밋이면 `-1` 대신 `origin/main..HEAD` 를 쓴다.

### 4. 사용자가 받는 명령 (전달 문서에 이대로 적는다)

```powershell
cd C:\dev\Tesqra\Tasqra
git branch --show-current          # 위치 확인. PowerShell 은 cd 실패해도 계속 간다

git fetch origin
git checkout -b <작업브랜치> origin/main
git am --3way C:\dev\deliver\참고\<전달폴더>\0001-....patch
git push -u origin <작업브랜치>
```

`git am` 은 커밋 메시지까지 함께 들어간다. 실패하면 `git am --abort` 로 원상복구된다.
**덮어쓰기가 아니므로 남의 작업을 지우지 않는다.**

### 5. 전체 파일 복사는 언제만 하는가

**기본은 하지 않는다.** 다음 두 경우만 예외다.

- 새로 만드는 파일이 많아 패치보다 파일이 읽기 쉬울 때
- 사용자가 코드를 눈으로 검토하겠다고 할 때

## 검증 기록

`origin/main`(`90ff05f`) 기준으로 한 줄 고쳐 `format-patch` 로 떴다.

```
패치 26줄  ->  깨끗한 클론에서 git am --3way 성공
```

같은 변경을 전체 파일 복사로 전달하면 그 파일 전체 줄 수를 다시 써야 한다.
**26줄 대 수백 줄이 대기 시간의 차이다.**

## 세션을 더 빠르게 하는 요청 방법

| 요청 | 효과 |
|---|---|
| 파일 경로를 지정한다 | 탐색(grep·read)이 사라진다. 가장 크다 |
| "검증 생략" / "픽스처로 검증까지" | 검증 수준을 고른다. 문서 수정이면 생략해도 된다 |
| "커밋 메시지 한 줄" | 긴 메시지를 쓰지 않는다 |
| 한 메시지에 한 가지만 | 답이 짧아진다 |
| 이미 만든 도구를 돌려 결과만 준다 | 다시 계산하지 않는다 (`id_queries.py` 등) |

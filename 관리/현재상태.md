### 다시 겪지 않게 적어 두는 것 다섯

**① `RENDERERS` 에 한 줄 더하면 된다는 추천은 틀렸다.** 실제로 걸린 것이 셋이었다 —

**② 본문 미리보기(`GET /deliverables/preview/content`)는 `XLSX` 를 못 준다.**

**`TEXT_PREVIEW_FORMATS = ("MD", "HTML")`** 를 `SUPPORTED_DELIVERABLE_FORMATS` 와

브라우저에 `.xlsx` 뷰어가 없어서 화면은 `HTML` 로 대신 보여준다(내용이 같다).

`<h2>{절 제목}</h2>` 와 `<table>` 을 **속성 없이** 찾으므로, 꾸밀 때 절 번호는

## ⚠ 갚아야 할 빚 — **태스크 제안 테이블을 만들 때 반드시 할 일**

> **이 절은 지우지 않는다.** 아래 마이그레이션을 하기 전까지 남겨 둔다.

`tasks.source_suggestion_id` 를 **금액 항목 id(`amount_items.id`)로 쓰기 시작했다**
(금액 불일치 태스크 제안, `AMT-004-3`). 원래 그 컬럼은 「제안 테이블의 id」 자리인데
제안 테이블이 아직 없어서 빌려 쓴 것이다.

**왜 빌려도 안전했나.** 그 컬럼은 그때까지 **전부 NULL 이었다** — `POST /tasks` 가
값을 넘기지 않아 아무도 쓰지 않았다(확인함). 그래서 우리가 넣는 값은 **한 종류뿐**이고,
나중에 갈라놓을 때 어느 행이 무엇인지 100% 확실하다. 추측할 것이 없다.

**애매해지는 시점은 두 종류가 섞인 뒤다.** 그래서 LLM 제안 테이블
(`task_suggestions`, `ANL-002-1` 이 채운다)을 만드는 **그 리비전 안에서 함께** 갈라야
한다. 그 뒤에 갈라려 하면 어느 id 가 어느 테이블 것인지 알 수 없다.

### 그 리비전에서 할 네 가지

```
① task_suggestions 테이블 생성                              ← 어차피 필요한 것
② tasks 에 source_amount_item_id 추가 (FK → amount_items.id, ON DELETE SET NULL)
③ UPDATE tasks
     SET source_amount_item_id = source_suggestion_id,
         source_suggestion_id  = NULL
   WHERE source_suggestion_id IS NOT NULL                  ← 값이 한 종류라 안전
④ source_suggestion_id 에 FK → task_suggestions.id 추가
```

②③④ 는 ① 에 얹는 덤이다. 따로 리비전을 만들지 않는다.

**한 컬럼이 두 테이블을 가리키면 FK 를 걸 수 없다**는 것이 갈라야 하는 이유다. FK 가
없으면 제안이 지워져도 태스크가 없는 id 를 가리킨 채 남는다 — 에러가 나지 않고 추적만
끊긴다.

### 함께 남겨 둔 곳

같은 내용을 코드에도 적어 둔다. 한 곳만 보고 놓치지 않게 하려는 것이다.

| 어디 | 무엇 |
|---|---|
| `backend/app/models/task.py` | `source_suggestion_id` 컬럼 주석 |
| 금액 불일치 → 태스크 엔드포인트 | 왜 이 컬럼을 빌려 쓰는지 |
| 이 절 | 마이그레이션 네 단계 |

### 덤으로 확인한 것

`TaskService.create(..., *, origin="MANUAL", source_suggestion_id=None)` 이 **이미
있다**(재정님). 활동 로그(`task_activity_logs`)에도 두 값을 남긴다. `TaskResponse` 에
`source_suggestion_id` 도 이미 노출된다. 그래서 금액 불일치 제안은 **엔드포인트 하나만**
만들면 되고 서비스·모델·스키마를 고치지 않는다.

`origin` 은 `'AI_APPROVED'` 를 쓴다. 엄밀히는 AI 가 아니라 계산에서 나온 제안이지만
그 값의 뜻은 「사람이 타이핑한 것이 아니라 시스템 제안을 승인한 것」이라 성질이 같다.
`'CALCULATED'` 를 새로 넣으려면 `ck_task_origin` CHECK 을 바꿔야 해서 리비전이 생긴다.

### 미리보기를 글자로만 보여주려던 것을 뒤집었다 — `iframe sandbox` (패치 `51`)

패치 `50` 에서 **미리보기를 `MD` 글자(`<pre>`)로만** 보여줬다. 근거로 "HTML 을 심으려면
`dangerouslySetInnerHTML` 이 필요하고 위험하다" 를 댔다.

**사용자가 «그러면 미리보기 하는 의미가 없잖아» 라고 했고, 맞는 지적이었다.**
그리고 «엑셀도 PDF 도 미리보기가 있어야 하는데» 라는 말이 결정적이었다 — 글자로
보여주는 방식은 그 형식들로 **확장되지 않는다.**

**내가 피해야 할 것을 잘못 골랐다.** 피해야 하는 것은 `dangerouslySetInnerHTML` 이고,
안전하게 HTML 을 그리는 표준 방법이 따로 있다 — **`<iframe sandbox>`** 다.

```jsx
<iframe sandbox='' srcDoc={body} title='...'/>
```

`sandbox` 를 **빈 값**으로 두면 스크립트·폼·팝업·부모 접근이 **전부 막힌다.** 그래서
혹시 `deliverable_html.render_html` 의 `escape` 에 구멍이 생겨도(나중에 절을 더하는
사람이 빠뜨리면) **실행 자체가 불가능하다.** `dangerouslySetInnerHTML` 은 그 한 겹만
믿는 것이고 `iframe sandbox` 는 두 겹이다.

`render_html` 이 `<!doctype>` 부터 `<style>` 까지 담은 **완전한 문서**를 만들기
때문에 `srcDoc` 에 그대로 넣으면 된다.

| 정한 것 | 왜 |
|---|---|
| 보기 방식 둘 — 「그대로 보기」(HTML) · 「글자로 보기」(MD) | HTML 은 결과를, MD 는 «어떤 표가 어떻게 적히는지» 를 보여준다. 산출물을 다른 문서에 붙여 쓸 사람에게는 뒤쪽이 필요하다 |
| 미리보기도 **만들기와 같은 형식 검사** | 없는 형식 `422`, `XLSX`·`PDF` 는 `501`. **미리보기만 되고 만들기는 안 되는 형식을 두지 않는다** — 미리 본 뒤 만들기에서 처음 막히면 헛수고다 |
| 높이를 정해 두고 안에서 스크롤 + 「크게 보기」 | `srcDoc` 은 스크립트 없이 높이를 스스로 맞출 수 없다. **높이를 재려고 sandbox 를 열지 않는다** |
| `sandbox` 에 허용 항목을 하나도 넣지 않는다 | 하나라도 더하면 그만큼 열린다. 필요해질 때까지 비워 둔다 |

**나중에 형식이 늘어날 때** (사용자 질문이었다)

| 형식 | 어떻게 |
|---|---|
| `PDF` | **같은 iframe** 에 blob URL 을 넣으면 브라우저가 그려 준다. 화면 구조를 안 바꾼다 |
| `XLSX` | 브라우저가 못 그린다. 그런데 **HTML 렌더로 대신할 수 있다** — 두 형식이 같은 `build_document` 에서 나오므로 **담긴 내용이 같다.** 「그대로 보기」에 HTML 을 띄우고 「이 내용이 XLSX 로 나갑니다」를 적으면 된다 |

즉 지금 구조가 그 둘까지 간다. 서비스도 `RENDERERS` 에서 형식별 생성기를 고르는
구조라 **`preview_content` 는 고칠 것이 없다.**

### 재분석하면 금액이 두 배가 된다 — 찾아서 고쳤다 (패치 `45`)

`amount_repository` 의 두 조회(`list_precedents` · `list_project_items`)가 **어느
분석에서 나온 항목인지 보지 않았다.** 조건이 프로젝트·승인상태뿐이었다.

문서를 다시 분석하면 `analyses` 에 새 행이 쌓이고(`DOC-006-2`) 금액 항목도 새로
생기는데 **옛 항목은 지워지지 않는다.** 그래서 같은 문서의 금액이 **분석 횟수만큼
더해진다.** 선례 조회에서는 같은 항목이 여러 번 나와 중앙값을 끌어당긴다.

`models/amount.py` 의 `analysis_id` 주석이 이미 이렇게 적어 뒀다 —

> 어느 분석 실행에서 나온 항목인지. 재분석하면 analyses 에 새 행이 쌓이므로
> (DOC-006-2) 이 값으로 "최신 분석의 금액" 과 과거 것을 구별한다.

**의도는 적혀 있었고 쿼리에 없었다.** 청킹·집계·`check_total` 과 같은 모양이다.

고친 방법: 문서마다 «승인된 항목이 있는 가장 최신 분석» 만 남기는 서브쿼리를
만들어 두 조회가 **같은 것을 쓰게** 했다. 한쪽만 고치면 선례에는 두 번 나오는데
집계는 한 번 세는, 설명할 수 없는 상태가 된다.

| 정한 것 | 왜 |
|---|---|
| `MAX(analysis_id)` 로 최신을 고른다 | `analyses.id` 가 자동증가라 나중 것이 항상 크다. `created_at` 은 같은 초에 두 번 분석하면 순서가 흔들린다 |
| 서브쿼리에서 **승인 상태를 먼저 거른다** | 분석 #2 가 아직 미승인이고 #1 이 승인돼 있을 때, 최신(#2)만 보면 승인 필터를 거쳐 **0건이 되어 금액이 사라진다** |
| `unit_price IS NOT NULL` 은 서브쿼리에 넣지 않는다 | 그것은 «쓸 수 있는 값인가» 조건이고 «어느 분석이 최신인가» 와 무관하다 |

**지금은 재현되지 않는다.** 항목 추출(`AMT-001-1`)이 미구현이라 한 문서에 분석이
하나뿐이다. 그래서 사용자가 확인한 `75,250,000` 은 이 패치 전후로 같다.
**추출이 붙는 순간 터진다.**

### `check_total()` 을 살렸다 — 리비전 `0022` (패치 `46`)

아래 절에 적어 둔 «로직은 있고 담을 곳이 없다» 를 해결했다. `documents` 에
**`stated_total_amount`**(`Numeric(18,2)`, nullable)를 더했다.

| 정한 것 | 왜 |
|---|---|
| `documents` 에 둔다 | 문서 하나에 합계는 하나다. `amount_items` 에 두면 항목마다 복제되고 한 항목만 고쳐지면 어느 것이 맞는지 알 수 없다 |
| **nullable** | 합계가 적혀 있지 않은 문서가 정상적으로 있다(공고문·계약서 본문). 0 을 넣으면 «0원인 문서» 와 «안 적힌 문서» 가 구별되지 않고 대조가 늘 불일치로 나온다 |
| `Numeric(18,2)` | `amount_items.amount` 와 같은 형. 다르면 계산기에 넘길 때 변환 규칙이 둘이 되어 반올림이 어긋난다 |
| CHECK `>= 0 OR NULL` | 음수 합계는 문서에 적힐 수 없다. 0 은 허용한다 — NULL 과 뜻이 다르다 |
| `stated_totals()` 를 **별도 조회**로 | `list_project_items` 튜플에 끼우면 금액 항목 목록 화면도 쓰지 않는 값을 들고 다니고, 자리 수가 늘어 부르는 곳마다 고쳐야 한다 |
| **맞은 문서도 응답에 담는다** | 불일치만 주면 «대조했고 맞았다» 와 «대조를 안 했다» 가 구별되지 않는다. 앞은 정확도의 증명이고 뒤는 정보가 없는 상태다 |
| 대조 못 한 문서는 **건수만** | 표에 빈 줄로 넣으면 정상 문서가 오류처럼 보인다. `TotalCheck.comparable` 이 그 구별을 위해 있다 |

응답에 `total_checks`(문서별 대조)와 `documents_without_stated_total` 이 붙는다.
`difference = item_total - stated_total` 이고 **`verify_line` 과 같은 방향**이다
(계산값 − 문서값). 두 곳이 반대면 화면이 어느 쪽인지 외워야 한다.

화면에 **부가세를 빼고 비교한다는 사실을 적어 뒀다.** 문서의 합계가 부가세를 포함한
값이면 이 대조는 늘 불일치로 나오는데, 이유를 모르면 계산이 틀렸다고 읽는다.

`setup_logging()` 이 `main.py` 에만 있는데 워커는
`celery -A app.worker.celery_app worker` 로 떠서 `app.main` 을 절대 불러오지 않는다.
`worker.py` 의 import 는 `logging`·`celery`·`app.core.config`·`app.db.session` 넷뿐이었다.
**포맷터 자체가 안 붙어 있었다** — 값만 넘겼으면 아무것도 안 보였을 것이다.

| 무엇 | 어디 |
|---|---|
| 워커 프로세스에서 `setup_logging()` 호출 + `worker_hijack_root_logger=False` | `worker.py` |
| `request_id` 를 태스크 인자로 받아 contextvar 에 심기 | `worker.py` 두 태스크 |
| 값 전달 | `upload_router.py`(내가) · `document_router.py:122`(내 줄) |
| **`document_router.py:33` 재시도 경로** | **재정님** — 안 고쳐도 안 깨진다 |

**정한 것 넷.**

1. **`request_id` 는 기본값 `"-"` 인 키워드 인자다.** 필수로 만들면 배포 순간
   **큐에 남아 있던 메시지**가 인자 2개로 들어와 전부 `TypeError` 로 죽는다.
   그 시점에 올라온 문서가 조용히 처리되지 않고 사용자는 업로드가 됐다고 본다
2. **`setup_logging()` 을 멱등으로 만들었다.** `main.py` 8행이 라우터를 import 하는
   사슬로 `app.worker` 가 끌려오는데 거기서도 부른다. 막지 않으면 루트 로거에
   핸들러가 둘 붙어 **모든 API 로그가 두 줄로** 나온다. 에러가 아니라서 못 알아챈다.
   `handler.set_name()` 으로 표시하고 같은 이름이 있으면 그대로 돌아온다
3. **꺼내는 방법을 둘 다 뒀다.** `get_request_id`(의존성, `request.state` 에서 읽어
   확실하다)와 `current_request_id`(contextvar, 서명을 못 고칠 때). `document_router` 는
   재정님이 만지는 중이라 서명을 건드리지 않는 쪽을 썼다
4. **`bind_request_id` 가 받은 값을 다시 검사한다.** 큐 메시지도 외부 값이 닿을 수
   있는 경로이고 줄바꿈이 섞이면 로그를 위조할 수 있다(미들웨어가 헤더를 검사하는
   것과 같은 이유)

확인 방법 — 문서를 올린 뒤 `docker compose logs worker` 에 `[request_id=...]` 가
업로드 응답의 `x-request-id` 와 같은 값으로 찍히는지 본다. `-` 로 나오면 전달이
끊긴 것이고, 대괄호 자체가 없으면 `setup_logging()` 이 안 걸린 것이다.

## 세현님 리랭커·어댑터 (브랜치 `feat/embedding-adapters`, 8/21)

**아직 머지 안 됐고 PR 도 없다.** `app/rerank/` 와 `adapters/` 가 main 에 없으므로
**머지 전에는 리랭커를 하이브리드에 붙일 수 없다.**

최종 측정(문서 단위 `hit rate@k`):

| `N` | `k=1` | `k=3` | `k=5` | `k=10` | 상한 |
|---|---|---|---|---|---|
| 없음 | 66.4% | 88.8% | 93.0% | 97.2% | — |
| 10 | 70.1% | 93.0% | 96.3% | 97.2% | 97.2% |
| **20** | 69.6% | 93.5% | **97.2%** | **98.1%** | **99.5%** |
| 30 | 69.6% | 93.0% | 96.7% | 98.1% | 99.5% |

**정정 — 리랭커는 정확도를 올린다.** 한 번 "리랭커를 켜면 97.2% → 96.3% 로
내려간다" 고 잘못 말했다. 그것은 `없음`의 `k=10` 과 `N=10`의 `k=5` 를 비교한 것이다.
**같은 `k` 로 보면 +3.3~4.2%p 로 늘 이득이다.** 함정 ①(비교축을 안 맞추고 숫자를
해석하는 것)을 그대로 밟았다.

`N=30` 은 `k=5` 가 오히려 내려가 포화다 → **`N=20` 이 무릎.** 설정 기본값은
`RERANK_CANDIDATE_POOL=10` 이고 근거는 지연(527ms vs 901ms)이다. 짚어둘 것은
**`N=10` 이면 상한이 97.2% 라 `k=10` 이 그 위로 못 간다**는 점이다.

**상한 = 정답이 후보 `N` 안에 있는 비율.** 리랭커는 후보 안에서만 재정렬하므로
상한을 넘지 못한다. 그래서 **하이브리드가 같은 `N` 에서 상한을 올릴 수 있다** —
의미 검색이 놓친 것을 키워드가 후보에 넣으니까. 다만 **가설이고 측정해야 안다.**
후보 희석(키워드가 틀린 것으로 자리를 채움)과 지연 증가가 반대쪽 위험이다.

> ⚠️ **하이브리드가 의미 검색보다 나은지 자체를 아직 안 재봤다.** 그 위에 리랭커를
> 얹으면 측정 안 된 것이 둘 쌓여 나중에 원인을 못 가린다. 순서는 **머지 → 같은
> 스크립트로 하이브리드 재측정 → 결합 결정** 이다.

기타: GPU 없으면 리랭킹을 켜지 말 것(후보 10건에 CPU 8.5초 / GPU 0.5초).
범용 리랭커를 어댑터 없이 쓰면 **나빠진다**(`k=1` 66.4% → 37.9%).
이미지가 **11.1GB** 가 된다(`torch` 가 CUDA 런타임을 끌고 옴) — 세현님이 판단으로
받아들였고 근거를 `requirements.txt` 에 남겼다.

## API 를 화면 없이 확인하는 방법

`docker compose up -d` 후 **`http://localhost:8000/docs`** (FastAPI 자동 문서 =

## 마이그레이션은 `docker compose up -d` 로 안 돌아간다 (2026-08-25 확인)

리비전 `0022` 를 올릴 때 실제로 겪었다. **`up -d` 는 이미 돌고 있는 컨테이너를
건드리지 않는다.**

```yaml
command: sh -c "alembic upgrade head && uvicorn app.main:app --reload"
```

`alembic upgrade head` 는 **컨테이너가 시작될 때 한 번**만 실행된다. 코드가 바인드
마운트(`./backend/app:/app/app`, `./backend/migrations:/app/migrations`)라서 파일을
고쳐도 이미지가 바뀌지 않고, 그래서 `up -d` 는 재생성할 이유가 없다고 판단해
`Container tasqra-api  Running` 만 찍고 넘어간다.

로그에 `WatchFiles detected changes ... Reloading` 이 보이는 것은 uvicorn `--reload`
가 **컨테이너 안의 앱 프로세스만** 다시 띄운 것이다. `command` 를 다시 실행하는 게
아니라 alembic 은 건너뛴다.

| 하려는 것 | 명령 |
|---|---|
| **마이그레이션 적용** | **`docker compose restart api`** |
| 환경변수 변경 반영 | `docker compose up -d` (restart 는 env 를 다시 안 읽는다) |
| 컨테이너를 새로 만들기 | `docker compose up -d --force-recreate api` |

**팀에 안내할 때도 `restart api` 라고 써야 한다.** `up -d` 로 안내하면 팀원은 파일은
받았는데 컬럼이 없는 상태가 되고, 원인이 안 보인다.

확인은 두 줄로 한다.

```powershell
docker compose exec -T db psql -U postgres -d tasqra -c "SELECT version_num FROM alembic_version;"
docker compose exec -T db psql -U postgres -d tasqra -c "SELECT column_name, data_type, is_nullable FROM information_schema.columns WHERE table_name='documents' AND column_name='stated_total_amount';"
```

## PowerShell — `Invoke-WebRequest` 에는 `-UseBasicParsing` 을 붙인다

안 붙이면 **「보안 경고: 스크립트 실행 위험」** 이 뜨고 멈춘다. PowerShell 5.1 이
응답을 Internet Explorer 엔진으로 HTML 파싱하려 해서다. 우리 응답은 JSON 이라
파싱이 필요 없고, 붙이면 경고도 사라지고 더 빠르다. `RawContentStream` 은 그대로
쓸 수 있어 한글 처리에 영향이 없다.

`Invoke-RestMethod` 는 이 경고가 없지만 **한글이 깨진다** — FastAPI 가
`content-type` 에 `charset` 을 안 붙여서 PowerShell 이 ISO-8859-1 로 읽는다.
그래서 한글이 섞인 응답은 아래 방식으로 읽는다.

```powershell
$r = Invoke-WebRequest -Uri "$base/..." -Headers $headers -UseBasicParsing
$s = [Text.Encoding]::UTF8.GetString($r.RawContentStream.ToArray()) | ConvertFrom-Json
```

## 반드시 기억할 함정 셋

1. **지표 정의를 확인하지 않고 숫자를 해석하지 않는다.** 같은 자료로 3.4배가 난다 —
   `accuracy@k`(첫 정답 순위가 k 이하면 1) 대 표준 `recall@k`. 우리 도구는 앞의 것이다.
2. **`similarity` 의 뜻이 `match_kind` 에 따라 다르다.** `vector`·`both` 는 코사인,
   `keyword` 는 트라이그램(조사가 붙으면 1 미만). 무조건 "유사도 N%" 로 쓰면 안 된다.
3. **검색이 0건이면 청크의 `embedding_model` 을 먼저 본다.** 지금 쓰는 모델과 다르면
   조용히 0건이다. 에러가 아니다.

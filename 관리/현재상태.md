### 산출물 화면 — 붙였다 (패치 `40`, 아직 안 올림)

백엔드가 다 됐는데 화면이 없어서 `docs` 나 PowerShell 로만 쓸 수 있었다. 그 상태로는
완료 판정의 "목록에서 다운로드" · "갱신 필요가 표시된다" 를 확인할 수 없다.

| 화면에 생긴 것 | 근거 |
|---|---|
| 만들기 버튼이 실제로 만든다 | 산출물 만들기(`DLV-002-1`) |
| 만든 산출물 목록 — 제목·형식·크기·만든 시각 | 이력 조회(`DLV-003-3`) |
| 내려받기 · 삭제(확인창) | 이력 조회(`DLV-003-3`) |
| `갱신 필요` 배지 + **무엇이 몇 건 늘었는지 문장** | 갱신 필요 판정(`DLV-003-4`) |

**정한 것 넷.**

1. **`XLSX`·`PDF` 는 보이되 고를 수 없게 했다.** 숨기면 DB·명세에 있는 형식이
   화면에서 사라져 "없는 것" 으로 읽힌다. 그냥 두면 눌러서 `501` 을 받고 나서야
   아는데 그건 사용자에게 **고장으로 읽힌다.** 서버의 `501` 은 그대로 남는다
2. **다운로드 경로를 화면이 조립하지 않는다.** 목록이 준 `download_url` 을 그대로
   쓴다. 조립하면 서버가 경로를 바꿀 때 화면이 조용히 `404` 를 받는다
3. **오류 문구를 화면이 다시 만들지 않는다.** `422 DELIVERABLE_EMPTY` 든 `501` 이든
   서버 `message` 가 이미 한국어다. `code` 별로 문장을 새로 쓰면 서버와 어긋난다
4. **`갱신 필요` 배지만으로 끝내지 않는다.** 배지만 보면 다시 만들어도 무엇이
   달라지는지 모른다. `stale_changes` 를 "문서 2건이 늘었습니다" 로 편다.
   라벨은 `CONTENT_COUNTS` 에서 파생해 **한 곳에서만** 관리한다

`utils/download.js` 를 새로 뺐다. `parseFilename`·`triggerBrowserDownload` 가
`api/document.js` 안에만 있었는데, 복사하면 한쪽만 고쳐서 **한글 파일명이 한 화면에서만
깨진다.** 에러가 없어 알아채기 어렵다.

`도구/check_jsx.py --all` 통과(js/jsx 55 · css 27). `node_modules` 가 없어
`vite build` 는 못 돌린다 — **화면 확인은 사용자 PC 에서 해야 한다.**

### 새로 확인한 함정 — 임베딩 모델 이름이 경로마다 다르다

검색은 `WHERE embedding_model = 지금 쓰는 모델` 로 걸린다. 그런데 —

| 서빙 경로 | `document_chunks.embedding_model` 에 남는 값 |
|---|---|
| `local-http` (호스트 `embed_server.py`) | `dragonkue/BGE-m3-ko` |
| `local-model` (컨테이너 직접 로드) | `dragonkue/BGE-m3-ko+embedding-hn-v1` |

**한 경로로 색인한 뒤 다른 경로로 검색하면 조용히 0건이다.** 에러가 없다.
경로를 바꾸면 그 모델로 만든 청크를 지우고 다시 색인해야 한다.

그리고 `도구/docker-compose.override.yml` 이 **8/24 에 무력해져 있었다** —
`EMBEDDING_PROVIDER` 를 지정하지 않아 기본값 `local-model` 이 이겨서, 서버를 띄워
둬도 컨테이너가 모델을 직접 올렸다. 지금은 `EMBEDDING_PROVIDER: "local-http"` 를
넣어 고쳤다.

### 패치 `41` 로 세 곳을 고쳤다 (2026-08-25)

**먼저 정정.** 워커 로그에 `request_id` 가 `-` 로 찍히는 게 아니라 **아예 없었다.**
`setup_logging()` 이 `main.py` 에만 있는데 워커는
`celery -A app.worker.celery_app worker` 로 떠서 `app.main` 을 절대 불러오지 않는다.
`worker.py` 의 import 는 `logging`·`celery`·`app.core.config`·`app.db.session` 넷뿐이었다.
**포맷터 자체가 안 붙어 있었다** — 값만 넘겼으면 아무것도 안 보였을 것이다.

| 무엇 | 어디 |
|---|---|
| 워커 프로세스에서 `setup_logging()` 호출 + `worker_hijack_root_logger=False` | `worker.py` |
| `request_id` 를 태스크 인자로 받아 contextvar 에 심기 | `worker.py` 두 태스크 |
| 값 전달 | `upload_router.py`(내가) · `document_router.py:122`(내 줄) |
| **`document_router.py:33` 재시도 경로** | **재정님** — 안 고쳐도 안 깨진다 |

**정한 것 넷.**

1. **`request_id` 는 기본값 `"-"` 인 키워드 인자다.** 필수로 만들면 배포 순간
   **큐에 남아 있던 메시지**가 인자 2개로 들어와 전부 `TypeError` 로 죽는다.
   그 시점에 올라온 문서가 조용히 처리되지 않고 사용자는 업로드가 됐다고 본다
2. **`setup_logging()` 을 멱등으로 만들었다.** `main.py` 8행이 라우터를 import 하는
   사슬로 `app.worker` 가 끌려오는데 거기서도 부른다. 막지 않으면 루트 로거에
   핸들러가 둘 붙어 **모든 API 로그가 두 줄로** 나온다. 에러가 아니라서 못 알아챈다.
   `handler.set_name()` 으로 표시하고 같은 이름이 있으면 그대로 돌아온다
3. **꺼내는 방법을 둘 다 뒀다.** `get_request_id`(의존성, `request.state` 에서 읽어
   확실하다)와 `current_request_id`(contextvar, 서명을 못 고칠 때). `document_router` 는
   재정님이 만지는 중이라 서명을 건드리지 않는 쪽을 썼다
4. **`bind_request_id` 가 받은 값을 다시 검사한다.** 큐 메시지도 외부 값이 닿을 수
   있는 경로이고 줄바꿈이 섞이면 로그를 위조할 수 있다(미들웨어가 헤더를 검사하는
   것과 같은 이유)

확인 방법 — 문서를 올린 뒤 `docker compose logs worker` 에 `[request_id=...]` 가
업로드 응답의 `x-request-id` 와 같은 값으로 찍히는지 본다. `-` 로 나오면 전달이
끊긴 것이고, 대괄호 자체가 없으면 `setup_logging()` 이 안 걸린 것이다.

## 세현님 리랭커·어댑터 (브랜치 `feat/embedding-adapters`, 8/21)

**아직 머지 안 됐고 PR 도 없다.** `app/rerank/` 와 `adapters/` 가 main 에 없으므로
**머지 전에는 리랭커를 하이브리드에 붙일 수 없다.**

최종 측정(문서 단위 `hit rate@k`):

| `N` | `k=1` | `k=3` | `k=5` | `k=10` | 상한 |
|---|---|---|---|---|---|
| 없음 | 66.4% | 88.8% | 93.0% | 97.2% | — |
| 10 | 70.1% | 93.0% | 96.3% | 97.2% | 97.2% |
| **20** | 69.6% | 93.5% | **97.2%** | **98.1%** | **99.5%** |
| 30 | 69.6% | 93.0% | 96.7% | 98.1% | 99.5% |

**정정 — 리랭커는 정확도를 올린다.** 한 번 "리랭커를 켜면 97.2% → 96.3% 로
내려간다" 고 잘못 말했다. 그것은 `없음`의 `k=10` 과 `N=10`의 `k=5` 를 비교한 것이다.
**같은 `k` 로 보면 +3.3~4.2%p 로 늘 이득이다.** 함정 ①(비교축을 안 맞추고 숫자를
해석하는 것)을 그대로 밟았다.

`N=30` 은 `k=5` 가 오히려 내려가 포화다 → **`N=20` 이 무릎.** 설정 기본값은
`RERANK_CANDIDATE_POOL=10` 이고 근거는 지연(527ms vs 901ms)이다. 짚어둘 것은
**`N=10` 이면 상한이 97.2% 라 `k=10` 이 그 위로 못 간다**는 점이다.

**상한 = 정답이 후보 `N` 안에 있는 비율.** 리랭커는 후보 안에서만 재정렬하므로
상한을 넘지 못한다. 그래서 **하이브리드가 같은 `N` 에서 상한을 올릴 수 있다** —
의미 검색이 놓친 것을 키워드가 후보에 넣으니까. 다만 **가설이고 측정해야 안다.**
후보 희석(키워드가 틀린 것으로 자리를 채움)과 지연 증가가 반대쪽 위험이다.

> ⚠️ **하이브리드가 의미 검색보다 나은지 자체를 아직 안 재봤다.** 그 위에 리랭커를
> 얹으면 측정 안 된 것이 둘 쌓여 나중에 원인을 못 가린다. 순서는 **머지 → 같은
> 스크립트로 하이브리드 재측정 → 결합 결정** 이다.

기타: GPU 없으면 리랭킹을 켜지 말 것(후보 10건에 CPU 8.5초 / GPU 0.5초).
범용 리랭커를 어댑터 없이 쓰면 **나빠진다**(`k=1` 66.4% → 37.9%).
이미지가 **11.1GB** 가 된다(`torch` 가 CUDA 런타임을 끌고 옴) — 세현님이 판단으로
받아들였고 근거를 `requirements.txt` 에 남겼다.

## API 를 화면 없이 확인하는 방법

`docker compose up -d` 후 **`http://localhost:8000/docs`** (FastAPI 자동 문서 =
Spring 의 Swagger UI). `Try it out` 으로 실제 응답을 본다. 화면이 없는 API 를
사용자가 확인할 수 있는 유일한 경로다.

## 반드시 기억할 함정 셋

1. **지표 정의를 확인하지 않고 숫자를 해석하지 않는다.** 같은 자료로 3.4배가 난다 —
   `accuracy@k`(첫 정답 순위가 k 이하면 1) 대 표준 `recall@k`. 우리 도구는 앞의 것이다.
2. **`similarity` 의 뜻이 `match_kind` 에 따라 다르다.** `vector`·`both` 는 코사인,
   `keyword` 는 트라이그램(조사가 붙으면 1 미만). 무조건 "유사도 N%" 로 쓰면 안 된다.
3. **검색이 0건이면 청크의 `embedding_model` 을 먼저 본다.** 지금 쓰는 모델과 다르면
   조용히 0건이다. 에러가 아니다.

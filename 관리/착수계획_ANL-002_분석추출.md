> 조사 방식: Tasqra `main`(HEAD `584486a`) 코드를 직접 읽어 확인한 것만 적는다.
> 문서끼리 비교하지 않고 코드가 근거다. 확인 못 한 것은 "확인 못 함"으로 남긴다.

## 한 줄 요지

**저장 스키마와 하류 소비는 이미 다 있고, 그 사이를 잇는 "추출기 + 영속화
다리"만 없다.** 결정사항 추출(`ANL-002-2`)·일정 추출(`ANL-002-3`)은 새 테이블
없이 지금 착수할 수 있고, 이걸 채우면 결정사항 대장(`DLV-003-1`)과 주간
보고서(`DLV-002-1`)의 막힌 부분이 바로 풀린다. 액션 아이템 추출(`ANL-002-1`)만
**저장할 테이블 자체가 없어** 마이그레이션이 선행이고, 그것이 태스크 제안
승인(`TSK-002-1`)의 상류다.

## 1. 조사로 확인한 현재 상태

### 1-1. 분석기 프레임워크 (있음, 그러나 추출기 미등록)

- 계약: `backend/app/analyzers/protocol.py` — `Analyzer.analyze(text) -> AnalyzeResult`.
  `AnalyzeResult.result` 는 `dict[str, Any]` 로 열려 있어 분석기가 늘어도 API 계약이
  안 바뀐다(Spring 의 interface + 열린 응답 DTO).
- 구현체는 **요약·분류 둘뿐**이다 — `summary_analyzer.py`, `category_analyzer.py`.
- 조립: `dependencies.py:get_analyzer_registry()` 가 `{"summary", "category"}` 만
  등록한다. `AnalyzerType`(`enums.py`)에는 `EXTRACT="extract"`, `AMOUNT="amount"` 가
  선언돼 있으나 **레지스트리에 없다.** 그래서 `analyzer_types=["extract"]` 로 부르면
  `analysis_service.py` 가 `ErrorCode.ANALYZER_NOT_FOUND`(400)를 던진다.

### 1-2. 저장 스키마 (이미 있음 — 마이그레이션 불필요)

리비전 `20260811_0007_analysis_artifacts.py` 가 `decisions`·`schedule_items`
테이블을 만들었고, ORM 매핑도 이미 붙어 `models/__init__.py` 에 등록돼 있다
(`Decision`, `ScheduleItem`). AI 제안 공통 6컬럼을 갖는다 —
`confidence · reason · decision(PENDING/APPROVED/EDITED/REJECTED) · decided_by ·
decided_at · source_text_revision`.

- `decisions`: `title · content · status(DECIDED/PENDING/REVERSED) · superseded_by ·
  decided_on` + 공통 6컬럼. **`status` 와 `decision` 은 다른 축이다** — `status` 는
  결정 자체의 상태, `decision` 은 AI 제안 승인 여부. 둘 다 `PENDING` 값을 가져
  헷갈리기 쉽다(`models/decision.py` 머리말이 명시).
- `schedule_items`: `title · kind(MILESTONE/DEADLINE/MEETING/PERIOD) · starts_on ·
  ends_on` + 공통 6컬럼. `kind` 마다 의미 있는 날짜 컬럼이 다르고, 둘 다 nullable
  이다(문서에 없으면 NULL, LLM 이 지어내지 않는다).

### 1-3. 하류 소비 (이미 있음 — 행이 생기기만 기다린다)

- 산출물: `deliverable_repository.py` 가 `list_decisions()`·`list_schedule_items()`·
  `count_decisions()`·`count_schedule_items()` 로 두 테이블을 직접 읽는다.
  `deliverable_service.py` 는 이걸 주간 보고서·결정사항 대장의 재료로 조립한다
  (line 492·507·510, 616~617). 승인 대기 집계 `count_pending_suggestions()` 는
  금액·결정·일정의 `decision='PENDING'` 을 합산한다.
- 즉 **결정사항 대장(`DLV-003-1`)·주간 보고서(`DLV-002-1`)의 소비 코드는 완성돼
  있고, `decisions`/`schedule_items` 에 행이 0건이라 표가 비어 있을 뿐이다.**

### 1-4. 진짜 공백 — 무엇이 없나

1. **추출기 미구현**: `extract` 분석기 클래스가 없다.
2. **영속화 다리 없음**: 어디에서도 `Decision(...)` / `ScheduleItem(...)` 행을
   INSERT 하지 않는다(코드 전역 grep 0건). `analysis_service` 는 `analyses` 행만
   만들고 자식 테이블은 채우지 않는다.
3. **저장소 없음**: `decision_repository` / `schedule_repository` 가 없다.
4. **액션 아이템은 저장할 곳 자체가 없다**: `action_items` 테이블도 `task_suggestions`
   테이블도 없다. 태스크 승인 승인 전 제안이 머물 자리가 없다. `tasks.origin` 은
   `MANUAL/AI_APPROVED` 뿐이고, `tasks.source_suggestion_id` 는 지금 금액
   항목 id 를 임시로 빌려 쓰는 중이다(`models/task.py` 주석). 최신 리비전은 `0022`.

> 참고: 금액 항목 추출(`AMT-001-1`)도 같은 상태다 — LLM 응답 검증 스키마
> (`schemas/amount.py`)·정규화(`amount_normalizer.py`)·계산기(`amount_calculator.py`)는
> 있으나 `amount_items` 행을 INSERT 하는 경로가 없다. 추출과 영속화의 공백이
> ANL-002 와 동형이다. 이 계획의 "추출기+다리" 설계는 금액에도 그대로 재사용된다.

## 2. 세 모양 정합성 검증 — 추출기 출력 = 저장 스키마 = 소비

착수 전 "추출기가 낼 JSON → 테이블 컬럼 → 산출물이 읽는 값" 이 한 줄로
맞물리는지 확인했다. **맞물린다.** 아래가 그 대응이다.

### 결정사항 (`ANL-002-2`)

| 추출기 출력(JSON) | `decisions` 컬럼 | 소비(산출물) |
|---|---|---|
| `title` | `title` (NOT NULL) | 대장 표의 "결정 내용" |
| `content` | `content` | 상세 |
| `decided_on`(원문에 있으면) | `decided_on` (nullable) | 대장 "결정일", 기간 필터 기준 |
| `status`(결론 났으면 DECIDED, 아니면 PENDING) | `status` | 대장 "상태", 회의 안건(PENDING) |
| `reason` | `reason` (NOT NULL) | 근거 |
| `confidence` | `confidence` | — |
| (고정) | `decision='PENDING'` | 승인 대기 집계 |

### 일정·기한 (`ANL-002-3`)

| 추출기 출력(JSON) | `schedule_items` 컬럼 | 소비 |
|---|---|---|
| `title` | `title` (NOT NULL) | 보고서 "일정·기한" 행 |
| `kind` (4값 중 하나) | `kind` (NOT NULL, CHECK) | `due_on` 계산 분기 |
| `starts_on`/`ends_on`(원문에 있으면) | `starts_on`/`ends_on` (nullable) | 다가오는 기한, 기간 필터 |
| `reason`/`confidence` | 동일 | — |
| (고정) | `decision='PENDING'` | 승인 대기 집계 |

**정합성 확인된 제약(추출기가 반드시 지켜야 함):**

- `reason` 은 NOT NULL → 추출기가 항목마다 근거 문장을 반드시 낸다(스키마 강제).
- 날짜·`content` 등은 nullable → **원문에 없으면 NULL.** LLM 이 만들어 채우면
  안 된다(명세서 완료 판정 "문서에 없는 값은 만들지 않는다"와 일치).
- `status`/`decision` 두 축을 섞지 말 것. 추출기는 `status` 를 정하고, `decision` 은
  항상 `PENDING` 으로 시작한다(승인 전 반영 금지 원칙).
- `schedule_items.kind` 는 CHECK 제약이라 4값 밖이면 INSERT 가 깨진다 →
  분류 분석기의 `FALLBACK_CATEGORY` 와 같은 방어(허용값 밖이면 기본값)가 필요.
- `source_text_revision` 은 `documents.ocr_revision` 을 넣는다 → 문서 재수정 시
  `STALE_SUGGESTION` 판정이 성립한다(소비·승인 코드가 이미 이 컬럼을 본다).

### 액션 아이템 (`ANL-002-1`) — 여기서 어긋난다

추출기 출력은 정의할 수 있으나 **저장 스키마가 없다.** 대응표를 그릴 대상 테이블이
없다. 그래서 이것만 마이그레이션이 선행이며, 이 계획에서 별도 단계로 뗀다.

## 3. 착수 계획

### Phase 1 — 결정사항·일정 추출 (마이그레이션 불필요, 하류 즉시 해소)

목표: `extract` 분석기가 `decisions`·`schedule_items` 에 `PENDING` 제안 행을
채운다. 완료되면 결정사항 대장(`DLV-003-1`)·주간 보고서(`DLV-002-1`)가 실제
자료로 채워진다.

제안 파일 매니페스트(모두 코드 상단 3단 주석 유지):

1. `backend/app/schemas/extract.py` — LLM 응답 검증 스키마. `schemas/amount.py`
   (`AmountExtractionOut`)와 동형. `ExtractionOut{ decisions: [...], schedule_items: [...] }`,
   각 항목에 `reason`/`confidence` 필수, 날짜·content 는 Optional, `kind` 는 enum.
2. `backend/app/analyzers/prompts.py` — `build_extract_prompt()` + `EXTRACT_SYSTEM_PROMPT`
   추가(기존 파일에 함수만 더함, `PROMPT_VERSION` 규칙 준수).
3. `backend/app/analyzers/extract_analyzer.py` — `Analyzer` 구현. `summary_analyzer`
   패턴 그대로(timeout·JSON 방어 파싱). `result` 에는 검증된 추출 결과를 그대로 담아
   `analyses[].result` 로도 노출.
4. `backend/app/repositories/decision_repository.py`,
   `backend/app/repositories/schedule_repository.py` — `create()` 중심(`analysis_repository`
   패턴).
5. **영속화 다리** — `analysis_service.analyze_document()` 를 확장. AI 호출 후
   같은 트랜잭션 안에서 `analyzer_type == "extract"` 이면 검증 결과를 두 저장소로
   INSERT. 설계 대안 두 가지:
   - (A) `analysis_service` 안에 타입별 "sink" 디스패치. 트랜잭션 하나로 묶기 쉬움.
   - (B) 금액이 택한 "전용 서비스/어댑터" 경로처럼 `extract` 전용 서비스로 분리.
   → **권고 (A)**: 산출물 소비가 `analysis_id` FK 로 제안을 묶으므로, `analyses`
   행 생성과 자식 행 생성을 한 트랜잭션에 두는 편이 단순하고, `amount` 도 같은
   sink 로 흡수해 두 추출이 갈리지 않게 한다.
6. `dependencies.py:get_analyzer_registry()` 에 `"extract": ExtractAnalyzer(ai_client)`
   등록 + 두 저장소 주입.

검증(사용자 PC 필요 항목 명시): `git apply --check` → `py_compile` 1회 →
`USE_FAKE_AI=true` 로 `POST /documents/{id}/analyze` 에 `extract` 넣어 행 생성 확인
→ 결정사항 대장 미리보기 건수가 0에서 증가하는지. **실모델 정확도 측정은
샌드박스 밖(재정님·세현님)** 몫이다.

### Phase 2 — 액션 아이템 추출 (마이그레이션 선행, 태스크 제안의 상류)

1. 리비전 `0023` — `action_items`(또는 `task_suggestions`) 테이블. `decisions`/
   `schedule_items` 와 같은 AI 제안 6컬럼 + `title · description · due_on · assignee` 후보.
   동시에 `tasks.source_suggestion_id` 의 임시 차용을 정리(`models/task.py` 주석의
   ①②③ 절차: `source_amount_item_id` 분리 후 FK).
2. `extract_analyzer` 출력에 `action_items` 추가, 다리에서 새 테이블로 INSERT.
3. 그 뒤 태스크 제안 승인(`TSK-002-1`)이 이 테이블을 `PENDING → AI_APPROVED`
   로 승격하는 경로를 얻는다(현재 부분 구현의 막힌 지점).

Phase 2 는 팀 공유 스키마 변경(마이그레이션 + 다른 팀원 컨테이너 영향)이라
**단독 진행 금지, 팀 합의 후.**

## 4. 담당 재배정 — 제안(팀 결정 사항)

`ANL-002` 는 명세서상 박세현님 담당이고, 재배정은 팀이 정한다. 아래는 제안일
뿐이다.

- **상류(추출기 본체 = LLM 프롬프트·모델 선택·정확도)는 박세현님 유지**가 맞다.
  모델 비교(`ANL-004-2`)와 직결되고, 추출 품질이 곧 그 측정 대상이다.
- **영속화 다리·저장소·레지스트리 배선(§3 Phase 1 의 4·5·6)은 하류 소비를 아는
  김보현이 맡는 것**을 제안한다. 세 모양 정합성(결정·일정 → 산출물)이 여기서
  깨지면 내 하류가 막히므로, 계약을 쥔 쪽이 다리를 놓는 편이 왕복이 적다.
- 경계: 박세현님이 `schemas/extract.py`(추출기 출력 계약)를 확정하면, 김보현이
  그 계약을 받아 다리·저장·소비를 잇는다. **계약 스키마 하나로 두 사람의 작업이
  분리된다**(Spring 의 interface 를 두고 provider/consumer 를 나누는 것과 같다).

## 5. 리스크·주의

- **한 트랜잭션 안의 부분 실패**: `extract` 추출은 성공했으나 자식 INSERT 가 CHECK
  제약(`kind`, 기간 순서)으로 깨지면 `analyses` 행까지 롤백된다. 추출기 단계에서
  허용값·기간 순서를 먼저 방어할 것.
- **재분석 중복**: `analyses` 는 재분석 시 새 행을 쌓는다(덮어쓰지 않음). 자식
  제안도 그대로 쌓이면 대장·보고서에 중복이 뜬다. 재분석 시 이전 `PENDING` 제안
  처리 정책(무시/치환)을 착수 전 정할 것. (승인된 것은 건드리면 안 된다.)
- **`status` vs `decision` 혼동**: §2 의 두 축을 코드·프롬프트·리뷰에서 반복 확인.
- 측정 반복 금지: 정확도 수치는 재정님·세현님이 낸다. 여기서 같은 측정을 다시
  돌리지 않는다.

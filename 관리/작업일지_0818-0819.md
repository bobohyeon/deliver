### 이날 잡은 가장 중요한 것 — 곱해지는 값

`CHARS_PER_TOKEN` 을 실측값(1.2 → **1.89**)으로 고쳤는데, 그 값이 **세 값과 곱해진다.**

| 곱해지는 값 | 실제 의미 | 결과 |
|---|---|---|
| `MAX_TOKENS` (480) | 청크 최대 글자 | 576 → 907자. 여유 충분 |
| `MIN_TOKENS` (48) | **흡수 기준 글자** | 58 → 91자 **→ 짧은 절이 삼켜짐 → 회귀** |
| `OVERLAP_TOKENS` (48) | 겹침 글자 | 58 → 91자. 그대로 둠(미결) |

`돈은 언제 받나요` 의 정답이 **1위(53%)에서 2위(47%)로 밀렸다.** `MIN_TOKENS` 를
48 → **30** 으로 같이 내려 조각 경계를 원래대로 되살렸다.

**문법·정의순서·청킹 규칙 검사가 전부 통과한 상태였다.** 실제 모델로 실제 질의를
넣어 순위를 봐야 나왔다. 그래서 `check_chunking.py` 에 옛 설정과의 경계 대조를
불변식으로 넣어 두었다.

### 유니코드 정규화

NFD(자모 분리)로 들어오면 제목 판정이 **전부 실패**한다.

| 입력 | `detect_heading` | 길이 |
|---|---|---|
| `제 3 장 계약 및 대금` (NFC) | `True` | 13 |
| 같은 문장 (NFD) | **`False`** | 24 |

정규식이 `제` 를 못 찾는다. 제목을 놓치면 청크가 제목에서 끊기지 않고 접두어도
안 붙는다(BGE-M3 는 CLS 풀링이라 앞쪽 토큰이 주제 신호).

**좌표는 정규화하지 않는다.** `content_start`·`content_end` 는 DB 원본 기준이고,
정규화한 길이로 매기면 원문 강조가 어긋난다(NFD 면 길이가 두 배). 텍스트만
정규화하고 좌표는 원본으로 두었다.

기존 문서 4건은 `is_nfc = t` 로 확인 → **재청킹·재측정 불필요**.

### 반복 노이즈 제거 — 만들다 본문을 지웠다

`structure.py` 기본값으로 만들었더니 이렇게 됐다.

    지운 것: '- # -'  '조달청 전자입찰 특별유의서에 따른다'
            '본문 # 입니다. 사업 기간은 십이 개월이다.'   <- 본문
            '제 # 장 개요'                              <- 제목
    결과: 청크 0개 (문서 전체가 사라졌다)

원인 두 개 — `normalize_repeated_text` 가 숫자를 `#` 로 바꿔 `본문 1` 과 `본문 2` 가
같아지고, 좌표가 없어 상·하단 대역으로 걸러낼 수 없다.

기본값을 세 군데 보수적으로 바꿨다.

| 설정 | `structure.py` | `mark_repeated_as_noise` |
|---|---|---|
| 숫자 치환 | 켬 | **끔** |
| 반복 비율 | 0.5 | **0.9** |
| 줄 길이 제한 | 없음 | **80자** |

그리고 **제목(`HEADING`)은 후보에서 제외**한다. 조달공고는 서식이 같아서
`제 1 장 총칙` 이 거의 모든 문서에 나오는데, 제목은 노이즈가 아니라 구조다.

노이즈 제거는 **자동으로 켜지지 않는다.** `mark_repeated_as_noise()` 를 직접
불러야 하고, 그 전에 `repeated_noise_report()` 로 목록을 봐야 한다.

## 환경 제약

**샌드박스(내 개발 환경)**

- `sqlalchemy`·`pydantic`·`numpy`·`openpyxl`·`pandas` 없음 → ORM 파일은 `py_compile` 만
- PyPI · npm · huggingface **전부 403** → 설치 불가
- `node` 는 `NODE_OPTIONS` 를 비워야 실행됨 (`env -u NODE_OPTIONS node ...`)
- `/tmp` 가 bash 호출 간 초기화됨
- `xlsx` 는 `zipfile` + OOXML 직접 작성으로 만든다 (`도구/_build_feature_spec*.py`)

**로컬(사용자 PC)**

- 메모리 16GB, 가용 4.8GB. 임베딩 모델 2.3GB
- `robocopy` 는 크기·시각 같으면 건너뜀 → **반드시 `/E /IS`**
- `docker compose restart` 는 환경변수를 다시 읽지 않음 → `up -d`
- **워커는 코드를 다시 읽지 않음** (celery 에 `--reload` 없음) → `restart worker` 필요.
  api 는 `uvicorn --reload` 라 자동
- DB 사용자는 **`postgres`** (`tasqra` 는 DB 이름)
- PowerShell 은 `<` 리다이렉션 불가, `Get-Content |` 는 한글을 ASCII 로 깨뜨림
  → SQL 은 `docker compose cp` 로 넣고 `psql -f` 로 실행
- 프론트 **새 파일** 추가 시 Vite HMR 놓침 → `restart frontend`
- 로컬 `gh` 는 **인증 안 됨** → PR 은 웹에서 만든다

## 8/19 추가 — `amount_items` 모델과 리비전 0015

### 왜 마이그레이션이 필요했나

ORM 모델을 만들려고 보니 **테이블에 없는 컬럼 두 개를 코드가 이미 쓰고 있었다.**

| 컬럼 | 쓰는 곳 |
|---|---|
| `unit_price` | `amount_calculator.py:107,110`(수량×단가 검산) · `amount_normalizer.py:138` · `schemas/amount.py:46` |
| `category` | `schemas/amount.py:37` (`AmountCategory` 8종 enum 은 이미 있었음) |

저장할 컬럼이 없으면 검산을 한 번 하고 버린다. 그러면 금액 계산·합계 검증
(`AMT-002-1`), 원가구분별 집계(`AMT-002-2`·`AMT-003-2`), 재계산·이력
(`AMT-004-*`) 이 다 막힌다.

### 넣은 것 · 안 넣은 것

넣음 — 둘 다 nullable

| 컬럼 | 타입 | nullable 이유 |
|---|---|---|
| `unit_price` | `Numeric(18,2)` | 제경비·기술료처럼 비율 산정 항목은 단가가 원래 없다 |
| `category` | `String(20)` + CHECK | 판별 못 하면 비운다. `OTHER` 를 넣으면 "판별 못 했다" 와 "기타로 판별했다" 를 구별할 수 없다 |

**안 넣음 — 비율(`rate`·`rate_base`).** LLM 추출 계약(`schemas/amount.py`)에 비율
필드가 없어서 채울 게 없다. 리비전 0007 의 원칙과 같다 — *"안 쓰는 컬럼을 미리
붙이지 않는다."* 추출 스키마에 비율을 넣기로 하면 그때 별도 리비전으로.

### 계산식을 사용자가 편집하게 할까 (멘토님 지적)

결론: **필요 없다. 우리가 계산식을 적용하지 않기 때문이다.**

`amount_calculator.py` 의 공개 함수가 하는 일은 이것뿐이다.

| 함수 | 하는 일 | 회사마다 다른가 |
|---|---|---|
| `verify_line` | 수량 × 단가 = 금액 검산 | 아니오 — 곱셈 |
| `check_total` | 항목 합계 = 문서의 합계 대조 | 아니오 — 덧셈 |
| `sum_vat` | 부가세 분리 | 아니오 |
| `aggregate_by_category` | 원가구분별 집계 | 아니오 |

`제경비 = 직접인건비 × 비율` 같은 산정식이 아예 없다. 회사마다 다른 건 비율인데,
그 비율을 적용한 **결과가 이미 문서에 금액으로 적혀 있어서** 우리는 그 값을 읽는다.

검산이 불일치로 나와도 금액을 고치지 않는다(`amount_calculator.py` 원칙 3).
사용자가 판단해 값을 수정하고 `decision = EDITED` 로 남는다 — 식을 편집하는
대신 결과를 고치고 사실을 기록한다. 탈출구가 이미 설계돼 있었다.

임의 수식 편집기를 하지 않는 이유 세 개 — 결정론성이 깨져 `AMT-002-1` 완료
판정("동일 입력에 동일 계산 결과")을 못 만족 / 사용자가 쓴 식이 맞는지 검증
불가 / `eval` 은 임의 코드 실행 경로.

### 추계로 확장할 수 있나

**막지 않는다. 오히려 지금 컬럼이 추계의 재료다.**

- **계산 로직** — `amount_calculator.py` 가 순수 함수라 `estimate_*` 를 옆에 더하면
  된다. 기존 함수를 고칠 필요가 없다.
- **LLM 어댑터** — 새로 만들 필요 없다. `app/ai/` 에 `AIClientProtocol` +
  구현 3개(fake·local·openai)가 이미 있다. 게다가 추계 자체는 곱셈·덧셈이라
  LLM 이 필요 없다. 판단이 필요한 곳("우리 항목 ≈ 과거 항목")은 임베딩 검색으로
  이미 된다.
- **저장** — `amount_items` 에는 못 넣는다. not-null 컬럼이 전부 문서 출처를
  전제한다(`document_id`·`analysis_id`·`source_text_revision`·`reason`). 억지로
  넣으면 구분 컬럼 + 기존 모든 쿼리에 필터가 필요하고, 한 곳만 빠뜨려도 추계값이
  "문서에 적힌 금액" 으로 집계된다. 더 근본적으로 두 값의 신뢰 수준이 다르다.
  → `amount_estimates` 같은 별도 테이블(프로젝트 단위)이 맞다. **그때 이번 모델을
  고칠 필요는 없다.** 이 내용을 모델 파일 상단 주석에 남겼다.
- **재료** — 추계의 입력은 과거 사업의 단가이고, 그게 `amount_items.unit_price` 다.
  지금 안 넣으면 나중에 "과거 데이터가 없다" 가 된다. 데이터는 소급해 만들 수 없다.

가는 순서: `unit_price`·`category`(지금) → 금액 추출(`AMT-001-1`) → 선례 검색
(`SRH-002-3`) → 추계. 3번까지 오면 "선례 N건의 단가 중앙값 + 근거 문서" 수준의
최소 추계가 된다.

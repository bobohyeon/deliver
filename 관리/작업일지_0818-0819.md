### 이날 잡은 가장 중요한 것 — 곱해지는 값

`CHARS_PER_TOKEN` 을 실측값(1.2 → **1.89**)으로 고쳤는데, 그 값이 **세 값과 곱해진다.**

| 곱해지는 값 | 실제 의미 | 결과 |
|---|---|---|
| `MAX_TOKENS` (480) | 청크 최대 글자 | 576 → 907자. 여유 충분 |
| `MIN_TOKENS` (48) | **흡수 기준 글자** | 58 → 91자 **→ 짧은 절이 삼켜짐 → 회귀** |
| `OVERLAP_TOKENS` (48) | 겹침 글자 | 58 → 91자. 그대로 둠(미결) |

`돈은 언제 받나요` 의 정답이 **1위(53%)에서 2위(47%)로 밀렸다.** `MIN_TOKENS` 를
48 → **30** 으로 같이 내려 조각 경계를 원래대로 되살렸다.

**문법·정의순서·청킹 규칙 검사가 전부 통과한 상태였다.** 실제 모델로 실제 질의를
넣어 순위를 봐야 나왔다. 그래서 `check_chunking.py` 에 옛 설정과의 경계 대조를
불변식으로 넣어 두었다.

### 유니코드 정규화

NFD(자모 분리)로 들어오면 제목 판정이 **전부 실패**한다.

| 입력 | `detect_heading` | 길이 |
|---|---|---|
| `제 3 장 계약 및 대금` (NFC) | `True` | 13 |
| 같은 문장 (NFD) | **`False`** | 24 |

정규식이 `제` 를 못 찾는다. 제목을 놓치면 청크가 제목에서 끊기지 않고 접두어도
안 붙는다(BGE-M3 는 CLS 풀링이라 앞쪽 토큰이 주제 신호).

**좌표는 정규화하지 않는다.** `content_start`·`content_end` 는 DB 원본 기준이고,
정규화한 길이로 매기면 원문 강조가 어긋난다(NFD 면 길이가 두 배). 텍스트만
정규화하고 좌표는 원본으로 두었다.

기존 문서 4건은 `is_nfc = t` 로 확인 → **재청킹·재측정 불필요**.

### 반복 노이즈 제거 — 만들다 본문을 지웠다

`structure.py` 기본값으로 만들었더니 이렇게 됐다.

    지운 것: '- # -'  '조달청 전자입찰 특별유의서에 따른다'
            '본문 # 입니다. 사업 기간은 십이 개월이다.'   <- 본문
            '제 # 장 개요'                              <- 제목
    결과: 청크 0개 (문서 전체가 사라졌다)

원인 두 개 — `normalize_repeated_text` 가 숫자를 `#` 로 바꿔 `본문 1` 과 `본문 2` 가
같아지고, 좌표가 없어 상·하단 대역으로 걸러낼 수 없다.

기본값을 세 군데 보수적으로 바꿨다.

| 설정 | `structure.py` | `mark_repeated_as_noise` |
|---|---|---|
| 숫자 치환 | 켬 | **끔** |
| 반복 비율 | 0.5 | **0.9** |
| 줄 길이 제한 | 없음 | **80자** |

그리고 **제목(`HEADING`)은 후보에서 제외**한다. 조달공고는 서식이 같아서
`제 1 장 총칙` 이 거의 모든 문서에 나오는데, 제목은 노이즈가 아니라 구조다.

노이즈 제거는 **자동으로 켜지지 않는다.** `mark_repeated_as_noise()` 를 직접
불러야 하고, 그 전에 `repeated_noise_report()` 로 목록을 봐야 한다.

**로컬(사용자 PC)**

- **레포 경로 — 두 레포가 다른 상위 폴더에 있다**

  | 레포 | 경로 | 브랜치 |
  |---|---|---|
  | 개인 (`bobohyeon/deliver`) | `C:\dev\deliver` | `docs/design-artifacts-0805` |
  | 팀 (`ParkSehyeon1009/Tasqra`) | `C:\dev\Tesqra\Tasqra` | — |

  `C:\dev\Tesqra\deliver` **가 아니다.** deliver 는 Tesqra 폴더 밖에 있다.
  실제로 그렇게 잘못 안내해서 `cd` 가 실패했다. 그리고 **PowerShell 은 `cd` 가
  실패해도 뒤 명령을 계속 실행한다** — 그때 `git pull` 이 엉뚱한 레포(Tasqra)에서
  돌았다. 여러 줄 명령을 만들 때는 이동 뒤에 `git branch --show-current` 를 넣어
  위치를 확인하게 한다.
- **`git switch -c <새브랜치> origin/main` 은 upstream 을 `origin/main` 으로 잡는다.**
  그래서 그냥 `git push` 를 치면 안 된다. 푸시할 때 `git push -u origin <새브랜치>`
  로 upstream 을 바로잡는다.
- 메모리 16GB, 가용 4.8GB. 임베딩 모델 2.3GB
- `robocopy` 는 크기·시각 같으면 건너뜀 → **반드시 `/E /IS`**
- `docker compose restart` 는 환경변수를 다시 읽지 않음 → `up -d`
- **워커는 코드를 다시 읽지 않음** (celery 에 `--reload` 없음) → `restart worker` 필요.
  api 는 `uvicorn --reload` 라 자동
- DB 사용자는 **`postgres`** (`tasqra` 는 DB 이름)
- PowerShell 은 `<` 리다이렉션 불가, `Get-Content |` 는 한글을 ASCII 로 깨뜨림
  → SQL 은 `docker compose cp` 로 넣고 `psql -f` 로 실행
- 프론트 **새 파일** 추가 시 Vite HMR 놓침 → `restart frontend`
- 로컬 `gh` 는 **인증 안 됨** → PR 은 웹에서 만든다

## 전처리를 나중에 뺄 수 있나 — 네 범주로 갈린다

리팩토링할 때 "이게 왜 있었나" 를 다시 추적하지 않도록 남긴다.

| 범주 | 예 | 언제 뺄 수 있나 |
|---|---|---|
| **환경 때문** | `CharRatioTokenCounter` · 가짜 임베더 · `check_jsx.py` · `check_python_defaults.py` · `embed_server.py` · `docker-compose.override.yml` | 실제 토크나이저 · 정식 서빙 · CI 가 생기면 |
| **다른 사람 작업이 아직 없어서** | `units_from_elements` 의 대체 판정 (`has_structure` 가 False 일 때 우리가 `is_strong_heading` 으로 채우는 부분) | **모든 문서가 `element_type` 을 갖게 된 뒤** |
| **위치가 차선** | 유니코드 정규화를 청킹 입구에서 하는 것 | 재정님과 합의해 추출 시점으로 옮기면 |
| **도메인·모델 때문** | `HEADER_FOOTER` 버리기 · 제목 접두어 · 겹침 · 표 헤더 반복 · `가.`·`나.`·`다.` 제외 · `WHERE embedding_model` | **빼면 안 된다** |

### 가장 크게 단순해지는 것 — 실제 토크나이저

8/18 회귀의 근본 원인이 `CharRatioTokenCounter` 였다. `CHARS_PER_TOKEN` 이 세 값과
곱해져서, 하나만 고치니 검색 정답이 1위에서 2위로 밀렸다.

실제 토크나이저를 쓰면 **그 곱셈이 전부 사라진다.** `MIN_TOKENS = 30` 이 진짜
30 토큰을 뜻하게 되고 `CHARS_PER_TOKEN` 자체가 없어진다. 그 회귀 종류가
구조적으로 불가능해진다.

갈아끼울 준비는 되어 있다 — `TokenCounter` 가 `Protocol`(= Java interface)이고
`chunk_units(counter=...)` 로 주입받으므로 청킹 로직은 고치지 않는다.

`tokenizers` 는 Rust 기반이라 torch 없이 약 3MB 다(임베딩 모델 2.3GB 와 다르다).
컨테이너에 넣는 것이 현실적이다. **다만 PyPI 가 개발 환경에서 막혀 있어 내가
검증하지 못했다.**

### 주석처리가 아니라 삭제 + 근거 기록

주석 처리한 코드는 왜 껐는지 잊힌다. 반년 뒤에 "켜도 되나" 를 아무도 모르고
그대로 남는다. 그리고 더 위험한 것은, **필요 없어 보이는 전처리가 조용한 실패를
막고 있다**는 점이다.

| 빼면 | 어떻게 실패하나 |
|---|---|
| 유니코드 정규화 | NFD 문서에서 제목을 전부 놓침. **에러 안 남** |
| `WHERE embedding_model` | 다른 벡터 공간 거리를 계산. **에러 안 나고 숫자만 무의미** |
| 겹침 | 문장이 경계에서 잘려 양쪽 문맥 부족. 품질만 조금씩 떨어짐 |

셋 다 테스트가 통과하고 화면도 정상이다. 그래서 뺄 때 순서는 —
①왜 넣었는지 확인 ②빼기 전 품질 측정(`check_rag04_quality.py`) ③빼고 다시 측정
④안 떨어지면 삭제하고 근거는 작업일지에.

## 파이프라인에서 전처리가 두 곳에 나뉘어 있다

```
업로드 → 추출(재정님) → [검수(재정님)] → 청킹(우리) → 임베딩(우리) → 검색(우리)
```

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 추출 | 재정님 | 줄마다 `element_type` 판정(`HEADING`·`HEADER_FOOTER`·`TABLE_ROW`) · `is_paragraph_start` · `table_id` · 좌표 |
| 청킹 | 우리 | 유니코드 정규화 · **그 `element_type` 을 보고** 조각 나누기 · `HEADER_FOOTER` 버리기 · 제목 접두어 · 겹침 |

**우리 청킹이 재정님 판정에 의존한다.** 재정님이 `HEADER_FOOTER` 를 안 채우면 우리
`DROP_TYPES` 가 아무것도 못 버린다(8/18 까지 그 상태였다).

`chunking_service._build_units()` 가 갈림길이다 — `ocr_elements` 가 있으면
`units_from_elements()`, 없으면 `units_from_plain_text()`.

## 재추출은 현재 코드로 막혀 있다

"전체 재추출 후에 대체 판정을 지운다" 고 적었는데, 실현 가능성을 확인하니
**경로가 없다.**

```python
# extraction_service.py:83
if document.status == DocumentStatus.EXTRACTED.value:
    return document                     # 이미 추출된 문서는 즉시 반환

# prepare_retry
if document.status != DocumentStatus.FAILED.value:
    raise BusinessError(ErrorCode.DOCUMENT_RETRY_NOT_ALLOWED)   # 409
```

억지로 `status` 를 바꿔도 터진다. `_attach_review_pages` 가
`document.review_pages.append(page)` 만 하고 기존 페이지를 비우지 않아서, 리비전
0006 의 `uq_doc_page (document_id, page_number)` 유니크 제약에 걸린다.

| 방법 | 되나 | 대가 |
|---|---|---|
| 문서 삭제 후 재업로드 | **됨** | `cascade` 로 하위 데이터 정리 · 검수 내용도 사라짐 |
| `status` 를 FAILED 로 바꾸고 retry | **안 됨** | `uq_doc_page` 유니크 제약 위반 |
| 검수 화면에서 사람이 `element_type` 지정 | 됨 | 수백 줄은 비현실적 |
| 재추출 기능 신설 | — | **명세서에 없음.** `DOC-006-2` 는 분석이지 추출이 아니다 |

`[TEST]` 문서는 삭제 후 재업로드로 하면 된다(시드라 잃을 것이 없다).

**운영 문서에는 문제가 남는다** — 검수를 마친 문서를 재추출하면 사람이 고친
텍스트가 날아간다. 재추출 기능을 만들 때 "검수 내용을 어떻게 할 것인가" 가 결정
사항이고, 그것 때문에 명세서에 없는 것으로 보인다. 재정님과 얘기할 안건이다.

### 1번 — 리비전 0015

`unit_price`(`Numeric(18,2)`) · `category`(`String(20)`) 추가. 둘 다 nullable.
코드가 이미 쓰는데 테이블에 없던 컬럼이었다 — `amount_calculator.verify_line()` 이
수량×단가를 검산하고 `schemas/amount.py` 가 받는다.

`alembic current` = `20260819_0015 (head)`. 컬럼·제약·부분인덱스가 모델 선언과
정확히 일치해서, 나중에 `alembic revision --autogenerate` 를 돌려도 엉뚱한 차이가
나지 않는다.

**CHECK 제약 4개가 실제로 거부하는 것을 확인했다** — 음수 단가 · 목록 밖 원가구분 ·
목록 밖 상태 · 기간 역순. 선언만 해 두고 동작하지 않으면 없는 것과 같다.

### 2번 — 시드

| 항목 | 현재 사업(prj1) | 과거 사업(prj2) |
|---|---|---|
| 특급기술자 | 3인월 × 9,500,000 | 3인월 × **8,800,000** |
| 고급기술자 | 6인월 × 7,200,000 | 5인월 × **6,900,000** |

| 제경비·기술료·부가세 | 수량·단가 NULL | 수량·단가 NULL |

`decision` 은 과거 사업 `APPROVED`, 현재 사업 `PENDING` 이다. 그래야 승인 필터를

**일부러 심은 것 둘**
- 과거 사업 중급기술자: 6 × 5,400,000 = 32,400,000 인데 문서에는 32,000,000.
  `verify_line` 이 400,000 차이를 잡는다. **문서 합계는 32,000,000 기준으로
  맞춰 뒀으므로** `check_total` 은 통과한다 — 두 검사를 따로 확인할 수 있다.
- 남의 프로젝트에 단가 **99,000,000** 을 `APPROVED` 로. 격리가 깨지면 즉시 보인다.
  `PENDING` 으로 두면 승인 필터에 걸려서 격리 때문에 빠진 것인지 구별할 수 없다.

### 3번 — `SRH-002-3` 최소 버전


조회 조건 넷: 내 멤버십 − 현재 프로젝트 / `decision IN (APPROVED, EDITED)` /
`unit_price IS NOT NULL` / 항목명 완전·부분일치(완전일치 우선 정렬).

**검색 API 를 고치지 않았다.** 의미 검색은 청크 **문장**을 주고 이 기능은 **단가
숫자**를 줘야 한다(완료 판정: "단가가 출처와 함께 표시된다"). 서로 대체하지 않는다.

**`GET` + 프로젝트 경로다.** `SRH-001` 을 `POST` 로 하고 경로에 프로젝트를 안 넣은
근거(질의가 문장 · 범위가 배열 · 검색어가 로그에 남지 않아야 함 · 범위가 멤버십
전체일 수 있음)가 여기엔 해당하지 않는다. 항목명은 짧고, 조회이며, **현재
프로젝트가 반드시 필요하다**(제외 기준).

`median` 을 직접 구현한 이유는 `float` 변환을 피하려는 것이다. 조달 금액은 억
단위라 오차가 눈에 보인다. **평균이 아니라 중앙값**인 이유는 선례가 적을 때 한
건의 이상치가 평균을 끌고 가기 때문이다.

`get_project_access` 를 쓴다(editor 가 아니라). 금액 열람 권한 제한(`AMT-003-1`)의
VIEWER 정책이 미결이라, 지금 잠그면 정해질 때 되돌려야 한다.

### 계산식을 사용자가 편집하게 할까 — 안 한다

멘토님 지적("회사마다 비용산정 계산식이 다르다")에 대한 결론이다. **우리가 계산식을
적용하지 않기 때문에 해당하지 않는다.** `amount_calculator` 가 하는 일은 수량×단가
검산 · 합계 대조 · 부가세 분리 · 원가구분별 집계뿐이고 전부 곱셈·덧셈이다.
회사마다 다른 건 비율인데 그 결과가 이미 문서에 금액으로 적혀 있다.

검산이 불일치로 나와도 금액을 고치지 않는다. 사용자가 값을 수정하면
`decision = EDITED` 로 남는다 — 식을 편집하는 대신 결과를 고치고 사실을 기록한다.

임의 수식 편집기를 안 하는 이유 — 결정론성이 깨져 `AMT-002-1` 완료 판정을 못
만족 / 사용자가 쓴 식의 정확성을 검증 불가 / `eval` 은 임의 코드 실행 경로.

## 8/19 — 프로젝트 핵심 현황(대시보드) 되는 지표만 완료

`DSH-001` 의 완료 판정은 **"최신 데이터가 지표·목록에 반영되고 각 항목에서 관련
화면으로 이동할 수 있다"** 다(기능명세서 v5 xlsx). 요구하는 지표는 여섯인데 넷은
지금 셀 수 있고 둘은 아니다.

| 지표 | 되나 | 근거 |
|---|---|---|
| 문서 수 | **됨** | `documents` |
| 처리 중 문서 | **됨** | `documents.status` |
| 문서 유형 분포 | **됨** | `documents.document_type` · `ix_doc_type (project_id, document_type)` 이 이 조회 순서 |
| 최근 문서 | **됨** | `ix_doc_list (project_id, created_at)` |
| 승인 대기 | **금액만** | `amount_items` 모델이 오늘 생겼다. `decisions`·`schedule_items` 는 테이블만 있고 모델이 없다 |
| 열린 태스크 | **안 됨** | `decisions` 는 리비전 0007 로 테이블이 있으나 ORM 모델이 없다 |

→ 위 "알려진 문제" 의 **ORM 모델 4개 없음** 항목이 일부 풀렸다. `amount_items` 가
생겨서 금액 승인 대기를 셀 수 있다. `decisions`·`schedule_items`·`deliverables`
는 그대로다.

### 만들다 발견한 것 — 대시보드 숫자가 이미 틀려 있었다

기존 `DashboardView` 는 문서 목록을 받아 **화면에서** 셌다.

```js
const processing = documents.filter(d => [...].includes(d.status))   // .length 를 카드에 씀
```

그런데 그 `documents` 는 `GET /documents` 의 **첫 페이지**다.

| 지점 | 사실 |
|---|---|
| `document_router.py:18` | `size: int = Query(20, ge=1, le=100)` |
| `api/project.js` `listProjectDocuments` | 파라미터를 안 넘긴다 → `page=1, size=20` |
| `useWorkspaceData` | `documents: documentsQuery.data?.items ?? []` |

**문서가 21건 이상인 프로젝트에서 카드 숫자가 조용히 틀린다.** 에러도 안 나고
화면도 정상으로 보인다. 지금은 `[TEST]` 문서가 4건이라 드러나지 않았다.

페이지를 전부 받아 세는 방법은 문서가 늘수록 요청이 늘어 답이 아니다. **세는 일은
DB 가 한다.** 그래서 이 작업의 요점이 "카드를 추가하는 것" 이 아니라 **"세는 위치를
화면에서 서버로 옮기는 것"** 이 됐다.

### 확정한 결정과 근거

| 결정 | 근거 |
|---|---|
| **열린 태스크는 `0` 이 아니라 `null`** | `0` 을 주면 "태스크가 0건" 과 "아직 셀 수 없다" 를 화면에서 구별할 수 없다. 사용자가 **"할 일이 없다" 고 잘못 읽는다.** 금액 선례에서 `summary` 를 `None` 으로 둔 것과 같은 판단 |
| 필드 이름을 `pending_amount_items` 로 | `pending_suggestions` 처럼 뭉뚱그리면 `decisions`·`schedule_items` 가 연결됐을 때 "이미 다 세고 있었다" 고 착각한다. **세는 대상을 이름에 박는다** |
| `total` = 상태별 **합** | 아는 상태만 더하면 `enums.py` 에 상태가 추가되고 이 파일이 안 고쳐질 때 총계가 조용히 작아진다. 합으로 두면 모르는 상태가 와도 총계는 맞고 묶음에만 안 잡힌다 |
| 유형 분포에서 **NULL 을 안 버린다** | `document_type` 은 nullable 이고 미분류 문서가 실제로 있다. 버리면 분포 합이 문서 수보다 작아져 **사용자가 숫자를 믿지 못한다.** "미분류" 는 유형이 아니라 유형이 없는 상태라서 `ETC`(사람이 고른 기타)와 구별해 맨 끝에 둔다 |
| 지표를 **한 응답**으로 | 카드마다 엔드포인트를 두면 열 때 요청이 다섯 번 나가고 그 사이 문서가 늘면 카드끼리 어긋난다("문서 12건" 인데 "유형 분포 합 11") |
| `dashboard_repository.py` 를 새로 만듦 | ①집계가 한 테이블에 안 머문다(`documents` + `amount_items`, 나중에 `decisions`). "이 숫자가 어디서 왔나" 를 한 파일에서 확인하는 편이 낫다 ②`document_repository.py` 는 재정님 영역이라 집계만 더하려고 건드리면 얻는 것 없이 충돌 지점이 생긴다 |
| 조회 다섯 번을 합치지 않음 | 지표마다 한 번이라 **항상** 다섯 번이다(결과 수에 비례하지 않아 N+1 아님). 합치면 지표를 더할 때마다 쿼리를 다시 손봐야 하고 어느 숫자가 틀렸는지 가려내기 어렵다. 세 조회 모두 이미 맞는 인덱스가 있다 |
| 서비스가 세션을 안 받음 | 읽기만 해서 commit 할 것이 없고 조회는 전부 리포지토리를 거친다. 안 쓸 의존성을 받아 두면 읽는 사람이 "여기서 직접 쿼리도 하나" 를 확인해야 한다 |
| `get_project_access` (VIEWER 허용) | 현황은 멤버가 문서 목록에서 이미 볼 수 있는 정보를 세어 보여주는 것이라 더 넓은 권한을 요구할 근거가 없다. 금액 열람 정책(`AMT-003-1`)이 정해져 VIEWER 에게 금액을 감춰야 하면 **엔드포인트를 잠그는 게 아니라 `pending_amount_items` 만 가린다** — 나머지 지표는 VIEWER 가 봐도 된다 |
| 최근 문서 정렬에 `id` 보조 | `created_at` 이 `server_default=func.now()` 라 같은 트랜잭션의 여러 건이 동일해진다. 그러면 새로고침할 때 목록 순서가 흔들린다 |

## 8/19 — UI 시안 v2 (피드백 5건 반영)

`산출물/UI시안_Tasqra_v1.html` 을 고쳤다. 파일명은 그대로 두고 안쪽을 v2 로 올렸다.

| 받은 지적 | 무엇을 고쳤나 |
|---|---|
| 사이드바가 프로젝트별로 가야 한다 | 프로젝트 > 대시보드·문서·검색·금액·보드·설정 으로 중첩. **실제 앱 라우팅(`/projects/:projectId/:tab`)과 같은 모양**이라 코드와도 맞는다. 한 번에 한 프로젝트만 펼친다 |
| 새 프로젝트 생성 버튼 | 「프로젝트」 구역 제목 오른쪽에 `＋`. 접혀도 남는다 |
| 접으면 글씨가 잘린다 · 토글이 사이드바 안에 있어야 한다 | 아래 별도 항목 |
| 금액 승인 대기 섹션이 너무 넓다 | 본문 폭을 다 먹던 카드 하나를 **두 칸(1.4 : 1)** 으로 나눔 |
| OCR 검수가 더 강조돼야 한다 | OCR 을 **주 강조(채움)** 로 올리고 금액을 두 번째로 내림 |

### 글씨 잘림의 원인 두 개

1. `.rail__tag`(`DOCUMENT · TO · ACTION`)가 접힘에서 숨는 규칙에 빠져 있었다.
   v1 은 `body.mini .rail__name, .rail__label, .rail__section, …` 처럼 선택자를
   나열했는데, 그러면 **하나 빠뜨렸을 때 그것만 잘려 보인다.**
2. `.rail` 에 `overflow: hidden` 이 없어 접는 동안 글씨가 삐져나왔다.

고친 방식 — 글씨에 전부 `.rail__text` 를 달고 `body.mini .rail__text { display:none }`
**한 규칙**으로 숨긴다. 접혀도 남아야 하는 것(`＋` 버튼, 아바타 이니셜)은
`.rail__keep` 을 단다. 폭이 고정된 것만 해당한다. 이제 새 글씨를 넣을 때 둘 중
하나를 반드시 달아야 하고, 안 달면 검사가 잡는다.

접기 버튼은 헤더에서 **사이드바 안(로고 오른쪽)** 으로 옮겼다. 헤더에 있으면
사이드바와 따로 움직이는 것처럼 보인다.

### OCR 을 주 강조로 올린 근거

취향이 아니라 순서가 있다. **검수를 마쳐야 본문이 확정된다.** 그전에는
`text_version` 이 오르지 않아 청킹·검색·금액 추출이 모두 이전 본문 기준으로
돌아간다. 즉 다른 일이 전부 이것에 막힌다. 금액 승인은 그다음이다.

채움 강조는 **하나만** 쓴다(문서에서 쓰는 규칙과 같다). 그래서 OCR 은 어두운
채움, 금액은 흰 카드에 왼쪽 띠만 둬서 두 번째 순위임이 보이게 했다. 그리고 OCR
카드에는 건수만이 아니라 **실제 문서 목록과 검수 버튼**을 넣었다 — 숫자만 있으면
결국 목록으로 한 번 더 가야 한다.

### 새 도구 — `도구/check_mockup.py`

목업이 깨진 채로 공유되면 팀원이 디자인이 아니라 버그를 보고 판단한다. v1 의
글씨 잘림이 정확히 그럴 뻔한 경우였다. 8건을 본다 — 태그 균형 · class 정의 ·
**접힘에서 잘릴 글씨** · `.rail` 의 `overflow:hidden` · 접기 버튼 위치 ·
테마 변수 대칭 · 정의 없는 `var()` · 채움 강조가 하나인지.

### 검사기가 거짓 통과한 것 — 내 주석이 내 검사를 무력화했다

일곱 가지를 일부러 깨뜨려 확인했는데 하나가 안 잡혔다.

`.rail` 블록 안에 이런 주석을 달아 뒀다.

```css
/* overflow:hidden 이 있어야 접는 동안 글씨가 삐져나오지 않는다. */
overflow: hidden;
```

선언을 지워도 **주석에 있는 `overflow:hidden` 글자가 정규식에 걸려** 통과했다.
같은 함정이 class 정의 검사에도 있었다 — 주석에 "`.rail__text` 를 붙여라" 라고
쓰면 실제 규칙이 없어도 정의된 것으로 세어진다.

고친 방법: `<style>` 을 읽을 때 `/* … */` 를 먼저 지운다. **검사기는 주석이 아니라
코드만 봐야 한다.** 지금은 일곱 가지 전부 잡히고 원본은 8건 통과한다.

깨뜨리는 스크립트에 `assert` 를 넣는 것도 이번에 배운 것이다. 처음에는 패턴이 안
맞아 아무것도 안 깨뜨렸는데, 출력만 보면 "검사기가 못 잡았다" 와 구별되지 않았다.
**깨뜨리기가 실패하면 시끄럽게 실패해야 한다.**

### 출력 형식도 하나 고쳤다

통과할 때도 설명을 붙여서 `통과 … → .rail__text 를 붙여라` 처럼 나왔다. 경고인지
아닌지 헷갈린다. 설명은 실패할 때만 보여준다.


## 8/19 — UI 시안 v3 · "금액을 왜 따로 뺐나" 에 대한 정정

v2 에서 OCR 검수와 금액 승인 대기를 **두 카드로 나눠** 두었는데, "금액만 따로
빼는 게 어떤 의미가 있나" 라는 물음을 받고 다시 보니 **내 근거가 약했다.**

### 둘은 성격이 같다 — 스키마에 그렇게 박혀 있다

OCR 검수와 금액 승인 대기는 둘 다 **사람이 확인해야 넘어가는 대기 큐**다. 이건
해석이 아니라 스키마가 말한다 — `SuggestionDecision`
(`PENDING`·`APPROVED`·`EDITED`·`REJECTED`)을 **`amount_items` · `decisions` ·
`schedule_items` 셋이 공유한다**(`models/enums.py`). 승인 대기는 한 종류가 아니라
여러 종류를 가진 한 가족이다.

기능명세서도 같다. `DSH-002` 가 **"승인 대기 및 활동 타임라인"** 이고 설명이
"**승인 대기 제안**, 이번 주 활동, 제안 종류별 채택률…" 이다. 승인 대기를 하나의
개념으로 묶어 놓았다.

→ 따로 뺄 이유가 없다. **한 영역에 종류별 줄**로 둔다.

### 검토한 세 안

| 안 | 문제 |
|---|---|
| 금액을 빼고 OCR + 액션 태스크를 위로 | **액션 태스크는 올릴 내용이 없다** — `decisions` ORM 모델이 없어 지금도 앞으로도 항상 빈 상태다. 가장 좋은 자리에 영구히 빈 카드를 두는 셈. 그리고 금액을 빼면 **유일하게 새로 동작하는 기능이 화면에서 사라진다**(시드에 `PENDING` 6건이 있다). `AMT-001-2` 완료 판정이 "승인 전에는 어디에도 반영되지 않는다" 이므로 **승인 진입점이 반드시 필요**하고 대시보드가 그 자리다 |
| 셋 다 동일 크기 카드 | 동일 크기는 "무엇이 급한지" 를 화면이 말하지 않는다는 뜻이다. 대시보드가 할 일을 안 하게 된다. 게다가 하나는 항상 비어 있어 빈 카드가 나머지와 같은 무게를 갖는다 |
| **한 영역에 종류별 줄** (채택) | 아래 |

### 채택안

| `DSH-002` 와 방향이 같다 | 그 기능이 이 자리를 활동 이력으로 확장한다 |

### 오른쪽 보조 열을 없앴다

참고 시안 3장 모두 오른쪽 열이 있었지만, 거기엔 일정·팀 활동·거래 내역 같은
**실제 내용**이 있었다. 우리는 아직 없다. 억지로 두면 빈 카드가 생긴다.
지금은 `문서 유형 분포` + `처리 상태` 를 2단으로 나란히 두고, 활동 이력
(`DSH-002`)이 생기면 그때 다시 넣는다.

### 사이드바 기본은 펼침

접힘을 기본으로 두면 처음 들어온 사람이 아이콘만 보고 무엇인지 모른다. 사용자가
접으면 그 선택은 `localStorage` 에 기억한다.

### 검사기가 이름에 의존하고 있었다

`check_mockup.py` 가 채움 강조를 `class="urgent"` 로 세고 있었다. 카드를 개편하면서
`urgent` 클래스가 사라졌는데, 그러면 **0개를 세고도 통과할 뻔했다.** 강조가 아예
없는 것도 잘못인데 검사가 못 잡는 상태였다.

`is-filled` 표식으로 바꿨다. 클래스 이름을 바꿔도 검사가 살아 있고, 0개와 2개를
모두 잡는다. 일부러 0개·2개로 만들어 확인했다.

**교훈** — 검사기가 특정 이름을 하드코딩하면 리팩토링할 때 조용히 무력해진다.
의도를 나타내는 표식(`is-filled`)을 두고 그것을 세는 편이 낫다. `enums.py` 를
직접 불러 쓰기로 한 것과 같은 이유다.

사이드바 기본이 펼침인지도 검사에 넣었다(9건). `<body>` 에 `mini` 가 있으면 실패한다.

### 사이드바 끊김

캡처를 재정님께 이미 보냈고 본인이 수정하기로 했다고 확인받았다. 새 레일은
`position: fixed` 라 그 문제가 구조적으로 생기지 않으므로, 시안 쪽에서는 더 볼
것이 없다. 앱 적용 시점에 재정님 수정과 겹치는지만 확인한다.


### 8/19 — 시안 v4: 가운데를 2단으로 (버튼 거리 문제)

"검수하기 버튼이 너무 멀다" 는 지적을 받았다. 실제 문제였다.

v3 의 `확인이 필요한 일` 은 본문 폭을 다 쓰는 한 영역이었고 줄이 4칸
(종류 · 건수 · 설명 · 버튼)이었다. 폭이 900px 을 넘으니 **이름과 버튼이 양 끝에
떨어져** 눈이 오래 이동한다. 숫자를 읽고 → 이름을 읽고 → 화면 끝까지 가서 누른다.

고친 방식 두 개를 함께 적용했다.

| | |
|---|---|
| 가운데를 **2단**으로 | 왼쪽 `확인이 필요한 일` · 오른쪽 `액션 태스크`. 칸이 좁아져 버튼이 이름 옆에 온다 |
| 줄을 4칸 → **3칸** | 종류를 이름 앞 인라인 칩으로 합쳤다. `건수 · 이름+설명 · 버튼` |

`태스크` 줄은 오른쪽 카드로 옮겼으니 목록에서 뺐다. `결정·일정` 은 흐린 줄로 남는다.

### 액션 태스크는 "예시" 로 표시했다

이 기능은 데이터가 없다(`decisions` ORM 모델 없음). 그래서 카드 세 장을 넣되
**`예시` 배지와 "아직 연결되지 않았습니다"** 를 붙였고, 머리말에도 적었다.

두 가지를 피하려는 것이다 — 빈 상태로 두면 팀원이 **레이아웃을 판단할 수 없고**,
표시 없이 샘플을 넣으면 **만들어진 기능으로 오해한다.** 목업의 목적이 "여기에
무엇이 올 것인가" 를 보이는 것이므로 예시를 두고 사실을 밝히는 편이 맞다.

지표 타일의 `열린 태스크 —` 와는 다르게 다룬 것에 주의. 그건 **숫자**라서 예시를
넣으면 거짓이 된다(`0` 도 `3` 도 사실이 아니다). 카드의 배치는 숫자가 아니라
**자리**라서 예시가 성립한다.

### 죽은 CSS 정리

구조를 바꾸면서 `.empty` 규칙이 아무 데서도 안 쓰이게 됐다(옛 액션 태스크 빈 상태
전용이었다). 지웠다. `.tile.is-danger` 는 남겼다 — 처리 실패가 1건이라도 생기면
붙는 상태 변형이고, 지우면 "실패는 빨갛게" 라는 의도가 조용히 사라진다. 왜 남기는지
주석을 달았다.

정리 뒤 안 쓰는 클래스는 `mini`(JS 가 붙인다) · `is-danger`(실패 발생 시) 둘뿐이다.

### 물어볼 것 갱신 (8개)

`확인이 필요한 일` 을 한 영역에 모은 판단 자체를 물어보는 항목을 넣었다 — 나눠
두는 편이 나은지. 그리고 액션 태스크가 예시라는 사실을 머리말에 명시했다.

### 무엇을 고쳤나

전에는 sticky + 고정 높이였다.

```
.workspace-shell   display:grid · grid-template-columns:280px minmax(0,1fr) · align-items:start
.project-sidebar   position:sticky · top:84px · height:calc(100vh - 84px)
```

`position: fixed` 로 바꿨다. 헤더 아래부터 화면 끝까지 **항상** 차지하므로 그
종류의 빈틈이 구조적으로 생기지 않는다. 목록이 길어지면
`.project-sidebar__list` 안에서만 스크롤한다(그 규칙은 이미 있었다).

`fixed` 는 그리드 흐름에서 빠지므로 두 가지를 함께 고쳐야 했다.

1. `.workspace-shell` 을 `block` 으로 — `grid` 로 두면 `.workspace-content` 가
   첫 열(280px)로 들어가 **본문이 찌그러진다**
2. `.workspace-content` 에 `margin-left: 280px` — 본문이 사이드바 아래로 깔리지
   않게

`workspace.css` **파일 끝에 추가만** 했다. 기존 규칙은 건드리지 않았다 — 그 파일
1행이 압축돼 있어 고치면 충돌 지점이 커진다.

### 브레이크포인트에 틈이 있었다

처음에 `@media (min-width: 901px)` 로 썼는데, 위쪽 블록이 `max-width: 900px` 라서
**900px 과 901px 사이에 틈이 생긴다.** 브라우저 확대나 배율이 있는 화면에서는
뷰포트 폭이 `900.5px` 처럼 소수가 될 수 있고, 그 폭에서는 두 블록 다 적용되지
않아 사이드바가 옛 배치로 돌아간다(= 끊김이 다시 보일 수 있다).

`@media not all and (max-width: 900px)` 로 바꿨다. 정확한 여집합이라 틈이 없다.

**무조건 적용되게 두면 안 된다** — 위 `max-width:900px` 블록보다 뒤에 있으므로,
조건 없이 두면 좁은 화면에서 그 블록을 덮어써 **모바일 가로 스크롤 배치가 깨진다.**

### 원인을 여전히 단정하지 않는다

`sticky` 가 왜 무력해졌는지는 화면을 보지 못해 확정하지 못했다. `fixed` 로 바꾼
것은 **원인을 맞혀서가 아니라 그 종류의 빈틈이 생길 수 없는 구조로 바꾼 것**이다.
넣은 뒤 긴 페이지에서 눈으로 확인해야 한다.

### 발견한 별개 문제 (손대지 않음)

헤더 높이가 `responsive.css` 에서 **800px 이하일 때 72px** 이 되는데
(`@media(max-width:800px)` 25행), `workspace.css` 의 사이드바 블록은 **900px 기준**
으로 72px 을 가정한다. **801~900px 구간에서 12px 이 어긋난다.** 이번 변경과 무관한
기존 문제라 그대로 뒀다. 셸을 정리할 때(시안 적용) 함께 맞춘다.

### 값을 그대로 적은 이유

`280px` · `84px` 를 변수로 뽑지 않았다. 이 파일이 이미 그렇게 쓰고 있어서
일관성을 택했다. 변수화는 `tokens.css` 정리(시안 확정 후)에서 함께 한다.

### 검증

`check_jsx.py` js/jsx 48 · css 22 통과. 깨끗한 `a0db7f0` 사본에 패치를 적용해
파일 1개가 나오고 그 사본에서도 검사가 통과하는 것을 확인했다.

**눈으로 볼 것** — 문서가 여러 개인 프로젝트에서 대시보드를 열고 **끝까지
스크롤해서** 사이드바 흰 배경과 오른쪽 테두리가 끊기지 않는지. 그리고 창을

### 탭으로 나눈 이유

중앙값·최저·최고를 **서버가 준다**(`amount_precedent_service.median`). 금액이 문자열

### 기존 `formatNumber` 가 금액에 안 맞았다

`formatNumber` 는 `value.toLocaleString('ko-KR')` 인데 **문자열에 부르면 그 문자열이
그대로 돌아와 쉼표가 붙지 않는다.** `Number` 로 바꾸면 쉼표는 붙지만 정밀도가 깨진다.
그래서 `formatMoney` 를 더했다 — 숫자로 바꾸지 않고 문자열의 정수부에 직접 구분을
넣는다. 소수부가 `.00` 이면 뗀다.

`node` 로 11건 시험했다 — `9500000.00` → `9,500,000` · `0.00` → `0` ·
`1234.50` → `1,234.5` · `null`·`''`·`undefined` → `-` · 음수 · 조 단위 · 숫자가
아닌 값은 그대로.

### 8/19 — 수량이 `3.0000` 으로 나와 3000 으로 읽혔다

단가 선례 화면을 확인하다가 "승인됨 배지 위에 수량 3000은 뭘 말하는 거야?" 라는
물음을 받았다. **3000 이 아니라 3인월이었다.**

`amount_items.quantity` 가 `Numeric(18, 4)` 라서 서버가 `"3.0000"` 을 보내는데
화면에 그대로 뿌렸다. 소수점 뒤 0 네 개가 붙어 **3000 처럼 읽힌다.** 조달 금액
화면에서 수량을 1000배로 오독하게 만드는 버그다.

전달: `참고/Tasqra_RAG_검색_전달/12-precedent-quantity-fix.patch` (파일 3개).

| | 전 | 후 |
|---|---|---|
| 수량 | `수량 3.0000` | `수량 3인월` |
| 총액 | 표시 안 함 | `총액 26,400,000` |

`formatMoney` 를 수량에도 쓴다. 그 함수가 이미 **뜻 없는 소수점 뒤 0 을 떼기**
때문에 `3.0000` → `3`, `2.5000` → `2.5`, `0.2500` → `0.25` 가 된다. 주석을 "금액
문자열" 에서 "Numeric 문자열(금액·수량)" 로 고쳤다.

**총액을 함께 내기로 한 이유** — 응답의 `amount` 필드를 안 보여 주고 있었다.
`source_quote` 안에는 있지만 구조화된 값으로는 없었다. 단가가 적정한지 판단할 때
"3인월 규모의 사업이었다" 가 필요하다. 규모가 다르면 단가도 다르게 볼 수 있다.

실제 함수로 뽑은 표시 문구

```
특급기술자   8,800,000/인월     수량 3인월 · 총액 26,400,000   직접인건비
고급기술자   6,900,000/인월     수량 5인월 · 총액 34,500,000   직접인건비
중급기술자   5,400,000/인월     수량 6인월 · 총액 32,000,000   직접인건비
제경비      11,000,000/단위 없음  (수량·총액 없음)              원가구분 미판별
```

### 미리보기를 만들다 내가 두 번 틀렸다

표시 문구를 미리 보려고 파이썬으로 `formatMoney` 를 **다시 구현**했는데 자리수
묶기가 틀려서 `,880,0000` 이 나왔다. 실제 코드가 아니라 미리보기 스크립트의 버그다.

**같은 로직을 두 번 구현하면 어느 쪽이 틀렸는지 알 수 없다.** 실제 함수를 소스에서
잘라내 `node` 로 돌리는 방식으로 바꿨다(`check_search_pure.mjs` · `check_dashboard.py`
와 같은 방식). 처음부터 그렇게 했어야 했다.

### 패치를 합칠 때 겪은 것 — 10번을 이미 적용한 상태였다

11번에 10번(사이드바 고정)을 합쳐 넣고 10번을 지웠는데, **보현이 이미 10번을 적용해
둔 상태**였다(커밋은 안 한 채). 같은 60줄을 두 번 넣으려다
`patch does not apply` 로 거부됐다.

| | |
|---|---|
| 내 잘못 | 패치를 합칠 때 "이전 패치를 이미 적용했으면 어떻게 하나" 를 안내에 안 적었다 |
| 확인 방법 | `git diff --stat` 이 `+59 · 삭제 0` 이고, 그 블록에만 있는 ASCII 표식(`not all and` · `margin-left: 280px` · `z-index: 25`)이 원본에 0곳인 것을 대조했다 |
| 해결 | `git checkout -- frontend/src/styles/workspace.css` 로 버리고 11번 적용 (같은 내용이 11번에 있다) |

**이 일이 `git apply` 를 쓰는 이유를 보여줬다.** robocopy 로 덮었으면 사이드바
블록이 두 번 들어간 파일이 조용히 만들어졌을 것이다.

그리고 **한글로 확인하라고 안내한 것도 잘못이었다.**
`git diff | Select-String "사이드바 고정"` 이 아무것도 못 찾았는데, 이미 작업일지에
적어 둔 함정이다 — *"PowerShell 의 `Get-Content |` 는 한글을 ASCII 로 깨뜨린다."*
파이프를 타는 한글은 못 믿는다. **확인용 검색은 ASCII 패턴으로만** 주고, 파일을
직접 읽는 `Select-String -Path` 를 쓴다.

### 증분 패치를 만드는 순서

11번을 아직 커밋하지 않은 상태에서 12번을 만들면 같은 문제가 되풀이된다. 그래서
**11번을 먼저 커밋하고 그 위에서 12번을 뜬다.** 샌드박스에서도 로컬 커밋을 하나
만들어(`푸시하지 않는다`) 그 위의 차이만 패치로 냈다. `a0db7f0` 사본에 11번을
적용·커밋한 뒤 12번을 올려 통과하는 것까지 확인했다.


### 8/19 — 단가에 "무엇 하나의 값인지" 를 붙였다

`8,800,000` 만 있으면 **사업 전체 금액으로 읽힌다.** 수량을 `3.0000` 으로 뿌린 것에
이어 두 번째 오독이었다. 두 번 연속 물음을 받았다는 것이 **화면이 설명을 못 하고
있다는 신호**였다.

전달: `참고/Tasqra_RAG_검색_전달/13-precedent-unit-label.patch` (파일 2개).

```
8,800,000 원  (1인월 단가)
3인월 기준 26,400,000
직접인건비        [승인됨]
```

용어 설명은 **패널 위에 한 번만** 둔다. 줄마다 붙이면 선례 20건에서 스무 번
반복돼 오히려 안 읽힌다. 결과에 인월 항목이 있을 때만 띄운다 — 식·건·개 단위만
나온 결과에는 필요 없는 설명이다.

### "3인 기준" 으로 쓰지 않았다

제안받은 문구는 `3인 기준 26,400,000` 이었는데 그대로 쓰지 않았다.

**`3인월` 은 3명x1개월 일 수도 1명x3개월 일 수도 있다.** 사람 수와 기간을 곱한
총량만 세는 단위라서, 문서에 `3인월` 이라고만 적혀 있으면 **몇 명인지 알 수 없다.**
`3인 기준` 은 우리가 모르는 것을 단정하는 것이고, 조달 문서에서 "3명이 투입된
사업" 으로 읽히면 규모를 잘못 판단한다.

단위를 그대로 둬 `3인월 기준` 으로 썼다. 대신 **단가 쪽에 뜻을 붙였다** —
`(1인월 단가)`. 제안의 `(1인/한달)` 이 정확히 그 자리였다.

### 단위를 하드코딩하지 않았다

`amount_items.unit` 은 `String(30)` 이다. 인월만 오는 것이 아니라 식·건·개·㎡·월도
온다. `(1인/한달)` 로 박아 두면 **식 항목에서 거짓이 된다.**

데이터의 단위를 그대로 넣어 자동 대응하게 했다. 실제 함수로 뽑아 확인한 결과

```
특급기술자            8,800,000 원  (1인월 단가)   3인월 기준 26,400,000
소프트웨어 라이선스     450,000 원  (1식 단가)     12식 기준 5,400,000
임차료              1,200,000 원  (1월 단가)     2.5월 기준 총액 없음
제경비             11,000,000 원                (수량 없음)
```

### 수량x단가 검산은 화면에서 하지 않는다

`amount` 와 `quantity x unit_price` 가 어긋나는 경우가 있다. 시드에 일부러 심어
뒀다 — 과거 사업 중급기술자가 `6 x 5,400,000 = 32,400,000` 인데 문서에는
`32,000,000` 이다.

그 불일치를 화면에 보여주면 유용하겠지만 **하지 않았다.** 보여주려면 곱셈이
필요하고, 금액이 문자열로 오는 것을 `float` 로 바꿔 계산하면 **거짓 불일치가 난다.**
"화면에서 계산하지 않는다" 를 스스로 정해 놓고 여기서 깨면 일관성이 없다.

서버의 `amount_calculator.verify_line()` 이 이미 그 검산을 한다. **응답에 결과를
담는 것이 맞고, 그건 `AMT-002-1`(금액 계산·합계 검증)이다.** 그때 화면에 표시한다.

### 오독이 두 번 나온 것에서 배운 것

`3.0000` → 3000, `8,800,000` → 사업 전체 금액. 둘 다 **값은 맞고 표시가 부족한**
경우였다. 조달 금액 화면에서는 숫자 하나가 1000배로 읽히거나 규모가 잘못 읽히면
판단이 뒤집힌다.

앞으로 금액·수량을 화면에 낼 때 확인할 것 —
① 소수점 뒤 뜻 없는 0 이 붙어 있지 않은가 ② 그 숫자가 **무엇 하나의 값인지**
적혀 있는가 ③ 단위를 코드에 박지 않고 데이터에서 가져오는가.

## 이 코드에서 확인한 것 — 90% 목표에 바로 걸리는 다섯 가지

### 1. "정확도 90%" 가 어느 지표인지 먼저 정해야 한다 (가장 급함)

**같은 자료로 3.4배 차이가 이미 나 있다.** 우리 문서에 기록된 사실이다
(`도구/embed-test/ir_eval.py` 머리 주석).

| 지표 | 값 | 정의 |
|---|---|---|
| 우리 `R@5` | **0.927** | 첫 정답의 순위가 5 이하면 1. = `Success@5` · `HitRate@5` = `accuracy@5` |
| 표준 `recall@5` | **0.2724** | 상위 5 ∩ 정답 / 정답 전체 |

**즉 지표를 안 정하면 "이미 92.7% 로 목표 초과" 와 "27.2% 로 한참 멀다" 가 같은
데이터에서 동시에 성립한다.** 네 사람이 각자 재고 숫자를 비교하는 주말인데,
이것을 안 맞추면 비교 자체가 성립하지 않는다.

`ir_eval.py` 주석에 이미 적혀 있다 — *"팀원과 숫자를 나란히 놓기 전에 반드시
도구를 맞춘다."*

세 번째 숫자도 돌아다닌다 — 작업일지의 `recall@5 = 0.6596`(세현님 측정). 위 둘과
정의가 같은지 **확인하지 못했다.** 회의에서 지표를 정할 때 이 숫자가 무엇인지도
같이 확인해야 한다.

→ **제안: `accuracy@1` 을 주 지표로, `recall@5` 를 보조로.** 이유는 우리 화면이
"정답 조각을 1위로 올리는가" 를 보이기 때문이다(검색 결과 첫 줄). 그리고
`ir_eval.py` 가 `accuracy@1` 을 `run_eval.py` 의 `R@1` 과 검산하도록 만들어져 있어
두 도구를 맞출 수 있다.

### 2. 평가셋이 73건이다 — 작업일지·기능명세서의 "133건" 은 틀렸다

실측했다. `도구/embed-test/queries.csv`

| | |
|---|---|
| 질의 | **73건** (`overlap` 39 · `no_overlap` 34) |
| 정답 짝 | 93개 · 질의당 평균 **1.27개** (1개 55 · 2개 16 · 3개 2) |
| 이력 | 78건으로 만들고(`d9256ec`) 측정 불가 5문항을 지워 73건(`165c93d`). **133건이었던 적이 없다** |

작업일지 244행과 기능명세서 `RAG-002-2` 비고가 둘 다 133건이라 적고 있다. **고쳐야
한다.** 팀원과 조건을 맞출 때 질의 수가 어긋나면 숫자를 비교할 수 없다.

정답 평균이 1.27개라는 것도 중요하다. `ir_eval.py` 주석의 3.4배 차이는 "정답 평균

작을 것**이다 — 다만 그것도 재봐야 안다.

### 3. 질의 73건이면 1문항이 1.37%p 다 — 90% 판정이 한 문항으로 갈린다

| 질의 수 | 1문항의 무게 |
|---|---|
| 47건 (세현님) | 2.13%p |
| **73건 (우리)** | **1.37%p** |
| 133건 | 0.75%p |
| 200건 | 0.50%p |

73건에서 90% 는 정답 65.7건이다. **한 문항 차이로 "90.4% 달성" 과 "89.0% 미달" 이

이것이 이미 문제를 일으킨 적이 있다 — 세현님의 학습 데이터 552→671쌍 증가 효과가
**측정되지 않았다.** 평가 질의가 47의 배수여서 1문항이 2.13%p 인데 관측된 변화가

→ **90% 를 목표로 삼으려면 평가셋을 먼저 키워야 한다.** 주말 작업의 첫 항목이
"데이터셋 보완" 인 것은 방향이 맞다.

### 4. 파인튜닝으로 안 풀리는 부분이 있다 — 후보 생성

작업일지에 기록해 둔 것 — *"리랭커는 recall 을 못 올린다. 후보에 없으면 못 살린다.
`recall@5 = 0.6596` 의 34% 는 후보 생성 문제 → `SRH-003` 키워드 검색이 필요."*

임베딩을 아무리 잘 튜닝해도 **벡터 검색이 후보에 못 넣은 조각은 리랭커도 LLM 도
살릴 수 없다.** 의미 검색은 고유명사·숫자·문서번호에 약하다(그래서 `SRH-003` 을
분리했다). 조달 문서는 공고번호·법조항·금액이 핵심이라 이 약점이 그대로 드러난다.

→ 주말 테스트에서 **틀린 질의를 "임베딩이 못 잡은 것" 과 "애초에 후보에 없던 것"
으로 나눠 세면** 파인튜닝으로 풀릴 몫과 키워드 검색이 필요한 몫이 갈린다.
`no_overlap` 34건이 그 구분에 쓸 재료다.

### 5. 네 사람이 각자 재면 세 가지가 어긋난다

## 청킹 설정이 정확도에 직접 걸린다 (잊지 말 것)

임베딩 모델만 바꾸는 것이 아니라 **청킹 값도 정확도를 움직인다.** 8/18 에 겪었다.

`MIN_TOKENS`(흡수 기준)가 58자 → 91자로 넓어졌고, 짧은 절이 삼켜져 **검색 정답이
1위에서 2위로 밀렸다.** `MIN_TOKENS` 를 48 → 30 으로 같이 내려 되살렸다.

미결로 남은 것 — `OVERLAP_TOKENS` 가 58 → 91자로 늘어 1·2위 간격이 6.0%p →

## 회의 목적 정정 — 측정이 아니라 재현성이다

앞에서 "정확도 90% 를 어떻게 재나" 로 정리했는데 목적이 다르다.

> **같은 테스트 데이터를 각자 로컬에서 돌려 결과를 공유하고, 무엇이 달랐나를
> 찾는다.** 팀 레포에 코드를 올리지 않는다. 세현님이 거의 일주일 데이터를
> 돌렸는데 정확도가 오르지 않는 이유를 못 찾아서, 처음부터 같은 데이터로 다시
> 시작하는 것이다.

즉 **차이를 만드는 변수를 찾는 실험**이다. 그러면 중요한 것이 바뀐다 — 점수가
아니라 **조건을 빠짐없이 같은 형식으로 남기는 것**이 실험의 성패를 가른다.

### 우리 문서에 이미 답이 절반 적혀 있다

#### 1. `0.927` 대 `0.2724` 는 **우리 대 세현님** 이었다

`관리/RAG_평가데이터셋_선별기준.md` 6절에 그대로 있다.

```
KoViDoRe (정답 평균 2.7개)
  우리 R@5        0.927
  세현님 recall@5 0.2724      <- 실력 차이가 아니라 정의 차이
```

그리고 같은 절에 **"팀원과 숫자를 나란히 놓기 전에 반드시 도구와 정의를 맞춘다"**
고 적어 두었다. 6절 제목이 *"질의당 정답 개수 — 지표 정의가 갈린다"* 이고 첫 줄이
*"이것이 가장 조용히 사고를 낸다"* 다.

**내일 하려는 일이 정확히 그 경고가 가리키는 상황이다.** 이미 한 번 겪은 차이를
다시 겪을 수 있다.

#### 2. "세 모델이 모두 틀렸는데 원인이 모델이 아니라 평가셋이었다" 는 선례

커밋 `165c93d` (8/11). 그 메시지를 그대로 옮긴다.

> 세 모델이 모두 틀린 13문항을 진단한 결과, 원인이 모델이 아니라 평가셋에
> 있었다. 청크 13·24·2 가 실제 정답인데 오답으로 채점되고 있었다.
> 원인은 같은 종류 정보가 여러 문서에 흩어져 있는 것이다.
>   예산·금액 → 60개 이상 청크

조치는 **삭제 5문항 · 정답 확장 4문항** (78 → 73). 지운 것들의 이유가 구체적이다.

| 지운 문항 | 이유 |
|---|---|
| 이 일에 잡힌 예산이 얼마인가 | 예산 청크가 60개 이상 — **측정 불가** |
| 하나만 내면 되나 | "하나" 가 무엇인지 문장에 없다 |
| 무엇을 해야 하는지 적힌 서류를… | "받나" 가 다운로드인지 작성기준인지 모호 |
| 밖으로 새지 않게 다짐을… | 코퍼스에 서약서·협약이 여럿 |

그리고 커밋 메시지에 **"점수를 올리려는 조치가 아니다. 측정할 수 없는 문항을 빼고
잘못 채점된 문항을 바로잡은 것이다"** 라고 못 박아 뒀다.

**세현님이 일주일 정확도가 안 오른다면 같은 진단을 먼저 해 볼 값이 있다.** 모델을
바꾸기 전에 "이 문항이 애초에 채점 가능한가" 를 보는 것이다.

#### 3. `check_queries.py` 가 그 진단을 자동으로 한다

`도구/embed-test/check_queries.py`. **`numpy`·`torch` 가 필요 없어 모델을 내려받기
전에 돌릴 수 있다.** 잡는 것 셋 —

| 잡는 것 | 왜 |
|---|---|
| `run_eval.py` 가 **조용히 건너뛸 행** | 없는 청크 번호 · 정답 없음 · `note` 에 "예시" 가 든 행. *"질의 40개를 넣었는데 32개만 채점돼도 알아채기 어렵다. 실제로 그 사고가 났다"* |
| `no_overlap` **어휘 누출** | 질의 단어가 정답 청크 본문에 있으면 잡는다. *"이건 사람 눈으로는 반드시 새어나간다"* — 실제로 `91ef087` 에서 "점수를" 을 잡았다 |
| 정답이 **한 문서에 몰리는지** | 몰리면 모델 비교가 그 문서 특성만 재게 된다 |

### 학습 데이터와 평가 데이터를 구분해야 한다

"같은 테스트 데이터 10만건" 이 무엇의 10만건인지 확인이 필요하다.

| | 규모 | 쓰임 |
|---|---|---|
| 학습 쌍 (파인튜닝용) | 세현님 552 → 671쌍 이었다. 10만건이면 이쪽일 것이다 | 모델을 고친다 |
| 평가 질의 (측정용) | 우리 **73건** · 세현님 **47건** | 점수를 낸다 |

**학습 데이터를 통일해도 평가셋이 다르면 숫자를 비교할 수 없다.** 그리고 "무엇이
달랐나" 를 찾으려면 나머지를 붙잡고 하나만 바꿔야 한다. 그래서 **먼저 고정할 것은
평가셋과 지표**다. 그 둘을 고정하면 남은 차이(하이퍼파라미터·`max_seq`·청킹·전처리)
가 원인 후보로 좁혀진다.

### 각 실행에 함께 남길 조건 — 이것이 없으면 차이를 못 가린다

네 사람이 결과를 모아 비교할 때 조건이 안 적혀 있으면 원인을 추적할 수 없다.
`ir_eval.py` 결과에 아래를 함께 찍는 것을 먼저 하는 게 좋겠다.

| 항목 | 왜 |
|---|---|
| 모델 이름·경로 | 파인튜닝본인지 base 인지. LoRA 어댑터는 `ir_eval.py` 가 못 받는다(병합본 필요) |
| `--max-seq` | *"학습 전/후는 반드시 같은 `--max-seq` 로 돌린다"* |
| 지표 이름 | `accuracy@k` 인가 `recall@k` 인가 — 위 1번 |
| 평가셋 파일명·질의 수·정답 짝 수 | 73건인지 47건인지. 1문항의 무게가 1.37%p 대 2.13%p |

### 1. 학습 데이터에 질의 필드가 없다 — 가장 강한 단서

`si_train.jsonl` 의 키가 `source·text·doc·type` 뿐이다. **질의가 없다.**
`anchor`·`positive`·`negative`·`query` 어느 것도 없다.

그리고 `corpus.jsonl` 과 **거의 같다** — `heading` 만 빠지고 행이 27개 적다
(1,505 → 1,478). 크기도 1,820KB 대 1,813KB 다.

**즉 학습 데이터가 사실상 코퍼스 그 자체다.** 임베딩을 지도학습으로 파인튜닝하려면
최소 (질의, 정답) 쌍이 필요한데 그것이 없다. 쌍이 없으면 대조학습이 성립하지
않는다. 비지도 방식(TSDAE·SimCSE 등)이었다면 개선폭이 작은 것이 정상이고,
라이브러리가 조용히 건너뛴 경우일 수도 있다.

**"일주일 동안 정확도가 오르지 않은" 이유의 가장 강한 후보다.**

### 2. `si_eval.jsonl` 의 `summary` 가 질의 역할일 것 — 단위가 점수를 가른다

평가셋에만 `summary` 가 있다(학습셋에는 없다). 이것이 질의라면 **문서 단위인지
청크 단위인지**가 점수를 완전히 갈라놓는다.

| `summary` 가 | 결과 |
|---|---|
| **문서 단위** | 한 summary 에 청크가 여러 개 → **정답이 모호** → 점수가 낮게 나온다 |
| 청크 단위 | 요약이 본문 어휘를 그대로 써서 점수가 높게 나온다 |

**전자면 우리가 이미 겪은 문제와 같은 종류다** — `165c93d` 에서 "예산 청크가 60개
이상이라 측정 불가" 로 5문항을 지운 그 상황이다. 모델이 아니라 평가셋 구조 문제다.

확인 방법은 싸다 — `서로 다른 summary 수` 와 `서로 다른 doc 수` 를 비교하면 된다.

### 3. 텍스트가 전처리 전이다

`si_train/corpus.jsonl` 첫 줄에서 —

```
"질병관리청 국립보건연구원 공고 제\n2026\n–403호\n입 찰 공 고 서"
"...입찰자가 계약을 체결하지 않거나, 계약을 / 체결하고 불이행하는 경우..."
```

| 흔적 | 문제 |
|---|---|
| `제\n2026\n–403호` | **공고번호가 줄바꿈으로 쪼개졌다.** 조달 문서에서 공고번호는 핵심 식별자다 |
| `계약을 / 체결하고` | 줄바꿈이 `/` 로 치환된 흔적 |
| `–` 가 en dash (U+2013) | 하이픈이 아니다. `제2026–  403호` 에 공백 두 개 |

우리가 청킹 전처리에서 다룬 것이 정확히 이 종류다 — **유니코드 정규화(NFC)**.
NFD 로 들어오면 `detect_heading` 이 전부 실패했다. 그리고 공고번호가 쪼개지면
**의미 검색과 키워드 검색 둘 다 해로워진다.**

### 4. 평가셋 호환은 안 된다 (예상대로)

`source` 형식이 `문서명#c0` · `#c1` 이다. 우리 `queries.csv` 의
`gold_chunk_ids` 는 **정수 청크 번호**다. 청킹 기준도 다르다. 즉 **우리 73건
평가셋을 세현님 코퍼스에 그대로 쓸 수 없고 그 반대도 안 된다.**

### 5. 청크 길이는 우리와 비슷한 규모로 보인다

평균 줄 1,238~1,606B 에서 JSON 구조 오버헤드를 빼면 대략 **350~470자**다
(한글 UTF-8 3바이트 가정). 우리 기준선은 평균 305자이고 "512토큰 초과 0개" 를
조건으로 관리했다. 세현님 쪽도 초과가 없는지 확인이 필요하다 — 초과하면 뒤가
잘려 나가는데 조용히 일어난다.

### 6. 두 폴더 모두 corpus 대비 27행이 적다

`1505 → 1478` · `1366 → 1339`. **차이가 똑같이 27이다.** 우연으로 보기 어렵다.
빈 텍스트나 너무 짧은 청크를 거른 규칙이 있을 것이다. 무엇을 걸렀는지 확인하면
그 규칙이 정답 청크를 지우지 않았는지 볼 수 있다.

### 확인용 스크립트를 보냈다

전수 키 확인 · `summary` 단위 판정 · 길이 분포 · 전처리 흔적 개수를 한 번에 낸다.

## 8/19 — 정정: 앞 진단의 1번 결론이 틀렸다 (질의 필드는 있다)

도구로 전수 확인한 결과 **앞 절 "1. 학습 데이터에 질의 필드가 없다" 는 오진이다.**

| | `si_train.jsonl` | `worksheet/si_eval.jsonl` |
|---|---|---|
| 행 | 1,478 | 1,339 |
| `summary` 있는 행 | **400 (27.1%)** | **214 (16.0%)** |
| `heading` 있는 행 | 1,401 (94.8%) | 1,304 (97.4%) |
| 서로 다른 `summary` | 400 (전부 다르다) | 214 (전부 다르다) |
| 서로 다른 `doc` | 56 | 30 |
| doc 당 `summary` | 7.14 | 7.13 |

### 왜 틀렸나 — 첫 줄만 본 키 목록을 믿었다

처음 받은 키 목록이 `source|text|doc|type` 이었다. 그것은 **첫 줄 기준**이었고
그 첫 줄에 하필 `summary`·`heading` 이 없었다. 전수로 세면 `summary` 는 400행,
`heading` 은 1,401행에 있다.

`diag_dataset.py` 머리말에 *"첫 줄만 보면 놓친다"* 라고 적어 둔 그 함정에
내가 그대로 빠졌다. **도구가 만든 사람의 오진을 잡았다.** 도구를 만든 값을
이 한 건으로 회수했다.

### 정정된 진단 — 문제는 "없다" 가 아니라 "27% 뿐이다"

- 학습에 쓸 수 있는 (질의, 정답) 쌍은 **400개**다. 1,478개가 아니다.
- 평가에 쓸 수 있는 질의는 **214개**다.
- `summary` 는 **청크 단위**다(doc 당 7.14개, 전부 서로 다름).
  → 앞 절 2번의 "문서 단위여서 정답이 모호하다" 우려는 **해소됐다.**
  → `165c93d` 와 같은 종류의 문제가 아니다.
- 512토큰 초과 **0행**. 잘림 문제도 없다. p99 가 905자(어림 479토큰)로 상한에
  거의 붙어 있어 우연이 아니라 의도된 설계로 보인다.

즉 세현님 평가셋은 구조가 **꽤 건전하다.** 남은 결함은 규모와 전처리다.

### 전처리 흔적은 실재하지만 앞서 본 것보다 국부적이다

| 흔적 | `si_train` | `si_eval` |
|---|---|---|
| 연속 공백 2칸 이상 | 465 (31.5%) | 532 (39.7%) |
| `' / '` 치환 | 358 (24.2%) | 419 (31.3%) |
| 숫자 사이 줄바꿈 | 65 (4.4%) | 74 (5.5%) |
| `'제'` 뒤 줄바꿈 | 60 (4.1%) | 55 (4.1%) |
| en dash·em dash | 13 (0.9%) | 27 (2.0%) |
| NFC 정규화 | **문제 없음** | **문제 없음** |

첫 진단에서 "공고번호가 쪼개졌다" 를 본 것은 맞지만 **전체의 4~5%다.**
샘플 한 줄이 하필 그 4%였다. 다만 공고번호·금액이 있는 청크는 질의가 몰리는
자리라 4% 라도 영향이 작다고 단정할 수 없다.

연속 공백 31~40% 는 표를 텍스트로 옮긴 흔적이다. 우리도 같은 문제를 겪었다.

### 27행 차이 — 길이 기준이 아니다

두 폴더 모두 정확히 27행이 적은 것이 확인됐고, **길이 기준이 아니다.**

```
si_train  걸러진 61~898자 (중앙 385) / 남은 17~913자 (중앙 334)
si_eval   걸러진 56~861자 (중앙 350) / 남은 23~914자 (중앙 358)
```

걸러진 것의 중앙값이 남은 것보다 오히려 **길다.** 짧은 것을 걸러낸 규칙이 아니다.

걸러진 본문을 보면 성격이 뚜렷하다 — 청렴계약 조항(금품·향응, 담합),
겸업 제한, 공동수급표준협정서(`○○○회사(대표자 :   )` 같은 빈 서식),
수의계약 배제 사유. **문서마다 글자까지 똑같이 반복되는 정형 문구다.**

그래서 **중복 제거 가설**이 가장 그럴듯하다. 이것을 판정하는 기능을
`diag_dataset.py --compare` 에 넣었다 — 걸러진 본문이 남은 쪽에 그대로
있으면 중복 제거이고, 없으면 내용이 실제로 빠진 것이다. 전자면 해롭지 않다.

두 폴더가 **똑같이 27** 인 것은 아직 설명되지 않았다. 문서 집합이 다른데
같은 수가 빠지는 것은 우연으로 보기 어렵다. 재확인이 필요하다.

### 도구를 고쳤다

이번 결과에서 정작 중요한 것(커버리지 27%)을 도구가 경고하지 않았다.
필드가 있는지만 보고 몇 행에 채워졌는지를 보지 않았다. 고쳤다.

- 질의 커버리지가 90% 미만이면 **쓸 수 있는 쌍의 개수**를 경고한다
- 쌍이 1,000개 미만이면 파인튜닝에 적은 편이라고 알린다
- `--compare` 에 중복 제거 판정과 문서 편중 판정을 넣었다
- 길이 컷 판정의 부등호를 엄격하게 바꿨다(경계가 같으면 깨끗한 컷이 아니다)

## 1. 작업 규칙 — 레포마다 권한이 다르다

| 레포 | 성격 | 커밋·푸시 |
|---|---|---|
| `bobohyeon/deliver` | **개인 레포** · 산출물 문서 | 변경 내용을 보여주고 **승인받은 뒤 에이전트가 직접** 해도 된다 |
| `ParkSehyeon1009/Tasqra` | **팀 레포** · 코드 | **에이전트는 절대 직접 하지 않는다** |

**팀 레포 절차는 항상 이 순서다.**

```
1  사용자가 먼저 레포 상태를 확인한다
2  에이전트가 변경 파일과 실행할 명령어를 정리해서 알려준다
3  사용자가 직접 커밋·푸시한다
```

**팀 공유 파일**(`docker-compose.yml` 등)을 고칠 때는 다른 팀원의 컨테이너나
마이그레이션이 깨지는지 먼저 알린다.

### 그 외 지켜온 규칙

| | 규칙 |
|---|---|
| 1 | 코드 파일 상단에 **3단 주석** — (1) 이 파일의 책임 (2) 다른 파일과의 관계 (3) Spring 비교 |
| 2 | 산출물 문서는 **흑백 무채색.** 강조는 검정 채움 하나. 색·과한 장식 없음 |
| 3 | **기능 ID 만 쓰지 않는다.** `RAG-01` 대신 `문서를 조각으로 자르기(RAG-01)` |
| 4 | 추측으로 단정하지 않는다. **코드·산출물로 확인한 뒤 말하고, 확인 불가면 그렇다고 명시한다** |
| 5 | 사용자는 **자바·Spring 배경.** 파이썬 개념은 Spring 대응물과 비교해 설명한다 |

## 4. 확정된 것

### 임베딩 모델

| | |
|---|---|
| 컬럼 | **`vector(1024)`** |
| 기본 모델 | **`dragonkue/BGE-m3-ko`** (apache-2.0) |
| 대안 | `nlpai-lab/KURE-v1`(mit) · `Snowflake/snowflake-arctic-embed-l-v2.0`(apache-2.0) |
| 탈락 | `e5` 3종 · `nomic`(768) · `Qwen3-Embedding-0.6B` |
| 근거 | 글자 안 겹치는 질의 **64개 중 41개** · 8개 지표 전부 1위 |
| 한계 | 2위(37)와 **4문항** 차. 안겹침만 보면 유의하지 않다(p=0.22). 전체 133문항으로는 유의(p=0.039) |

**대안 둘은 1위와 통계적으로 구별되지 않는다.** 형식적 대안이 아니라 실제로
바꿔 써도 되는 후보다. 차원이 같아 DB 를 안 건드리고 교체 가능하다.

if content_changed or chunk_structure_changed:

`document_chunks.text_version` 비교만으로 **단락 경계 변경까지 감지된다.**
내가 우려했던 설계 구멍이 정면으로 막혔다.

#### 왜 `project_id` 를 역정규화하는가

```sql
SET LOCAL hnsw.iterative_scan = strict_order;
SELECT * FROM document_chunks
WHERE project_id = :project_id
ORDER BY embedding <=> :query LIMIT :k;
```

**즉 `project_id` 는 `iterative_scan` 의 전제다. 택일이 아니다.**

`임` 은 판단이 갈려 **실측으로 정하기로 남겨뒀다.**

### B 가 왜 먼저인가

**컨테이너를 재생성해서 마이그레이션을 돌린 뒤에 컬럼을 추가하면 또 한 번
재생성해야 한다.** 지금은 커밋 전이라 자유롭게 고칠 수 있다.

### B 의 내용 — 원본 위치 하이라이트

재정님이 리비전 `0010` 으로 `ocr_elements` 에 `content_start` · `content_end` 를
넣었다. `extracted_texts.content` 문자열 안의 위치다.
**청크도 같은 좌표를 가지면 이게 된다.**

```
청크 (content_start, content_end)
   ∩ ocr_elements (content_start, content_end)
   -> 그 청크를 만든 element 들
   -> element 의 x · y · width · height (정규화 좌표)
   -> 원본 페이지 이미지에 검색 근거를 네모로 표시
```

**출처 표시가 "3쪽" 에서 "3쪽 이 위치" 로 올라간다.** 정수 컬럼 두 개 값이다.

**나중에 넣으면 `ALTER` 는 쉽지만 기존 행의 값을 채울 수 없다.** 오프셋을 알려면
재청킹을 해야 한다. `nullable` 로 두면 청킹 규칙이 안 정해져도 무해하다.

### B 의 결론 — 넣는다. 코드에서 확인한 근거 네 개

**추측이 아니라 `origin/main` 코드를 읽고 확인했다.**

| | 확인한 것 | 어디서 |
|---|---|---|
| 1 | `ocr_elements.content_start`·`content_end` 는 `extracted_texts.content` 의 오프셋이고 **nullable** 이다 | `models/document.py:127-128` |
| 2 | **오프셋이 살아 있게 유지된다.** 사람이 OCR 글자를 고치면 본문을 그 자리에서 갈아끼우고 **뒤따르는 element 들의 오프셋을 `delta` 만큼 밀어준다** | `services/document_service.py:_replace_ocr_content` (132-162) |
| 3 | `ocr_elements` 에 `x`·`y`·`width`·`height` 정규화 좌표가 있다 -> 교집합으로 **네모를 그릴 수 있다** | `models/document.py:116-119` |
| 4 | `extracted_texts.text_version` 이 **본문이 실제로 바뀔 때만** 증가한다 -> 청크 stale 판정이 성립한다 | `document_service.py:182, 234` |

**2번이 결정적이다.** 오프셋이 최초 적재 때만 계산되는 값이면 편집 한 번에
전부 틀어져서 하이라이트가 거짓말을 한다. 그런데 실제로는 편집마다 유지된다.
**좌표계가 살아 있으므로 청크가 같은 좌표를 갖는 것이 의미가 있다.**

### B 를 쓸 때 반드시 지킬 것 세 가지 — 확인된 함정

| | 함정 | 대응 |
|---|---|---|
| 1 | **오프셋이 `NULL` 인 element 가 존재한다.** 같은 문자열이 여러 번 나와 위치를 특정 못 하면 `0010` 백필이 `NULL` 을 넣는다. 신규 적재(`extraction_service.py:138-142`)도 `find()` 실패 시 `NULL` | 교집합 조회에 `content_start IS NOT NULL` 을 넣는다. **하이라이트는 "되면 그린다" 이고 보장 기능이 아니다.** 안 되면 페이지 번호까지만 출처로 쓴다 |
| 2 | `is_in_content = false` 인 element 는 본문에 없다. `_replace_ocr_content` 가 이때 기대값을 `""` 로 본다 | 교집합에 `is_in_content = true` 를 넣는다. 7절 2번(제외 element 는 검색에서 뺀다)과 방향이 같다 |
| 3 | **`_replace_ocr_content` 는 `ocr_elements` 만 밀어준다. 청크 오프셋은 안 밀어준다** | 그래서 편집 뒤 청크 오프셋은 낡는다. 다만 `text_version` 이 올라가므로 **낡은 것을 알 수 있다.** 재청킹으로 해결하고, **오프셋을 부분 보정하려 들지 않는다** (7절 5번과 같은 안건) |

### B 의 주된 근거가 기능명세서에서 약해졌다 — 정직하게 남긴다

**컬럼을 넣자고 한 핵심 근거가 "원본 위치 하이라이트" 였는데, 기능명세서가
그것을 범위 밖으로 명시했다.**

| ID | 비고 |
|---|---|
| `TSK-003-1` | **원문 위치 하이라이트는 범위 밖** |
| `AMT-003-3`·`SRH-002-2` | *"출처 문서·원문 근거"* 까지다. **인용이고 위치가 아니다** |

`SRH-002-2`(근거 스니펫 연결, P1)는 청크의 `text` 컬럼만으로 된다. **오프셋이
필요 없다.**

> **내가 구 판(v2) 7절을 기준으로 판단했고, 그 시점 문서가 낡은 것이었다.
> 새 명세서를 먼저 확인해야 했다.**

**그래도 컬럼은 그대로 둔다.** 이유는 셋이다.

| | 이유 |
|---|---|
| 1 | **비용이 실질적으로 0** 이다. nullable 정수 2개이고 청크가 0행이다 |
| 2 | 재정님이 `0010` 으로 **같은 좌표계를 `ocr_elements` 에 이미 투자**했고, `_replace_ocr_contents` 가 그것에 의존해 동작한다 |
| 3 | `REV-003-2` 비고가 *"`RAG-001` 청킹 입력 순서와 직결"* 이라 좌표계가 죽은 설계가 아니다 |

**단, 하이라이트를 산출물에서 성과로 내세우지 않는다.** 넘긴 이유를 적을 때는
"해석 불가"가 아니라 **"범위 밖 + 우리 미결 질문과 무관"** 으로 적는다.

빼려면 리비전 하나로 `drop_column` 2줄이면 된다. **지금이 가장 싸다는 점만
기억한다.**

**3번을 청크까지 밀어주도록 고치지 않는 이유** — 청크는 여러 element 를 묶은
것이라 경계가 편집으로 깨질 수 있다. 오프셋만 밀면 텍스트와 어긋난다.
**재청킹이 정답이고, 그 트리거는 7절 5번에서 정해야 한다.**

## 7. 재정님과 협의할 안건 — **여섯 개 중 다섯 개가 해결됐다**

**청킹 규칙과 테이블 스키마는 분리된다.** 규칙이 바뀌면 행만 다시 만들면 되고
스키마 변경이 아니다.

| | 안건 | 결과 (2026-08-14 오후) |
|---|---|---|
| 1 | 청크 경계를 무엇으로 끊나 | **해결.** `element_type` 5종 + `is_paragraph_start` 가 들어왔다 (4-A절). 단락에서 끊고 토큰 수로 상한 |
| 2 | `is_excluded` · `is_in_content` 인 element 를 넣나 | **해결.** `REV-004-3`(분석 제외·복원) 이 `구현됨` 이고 확정 텍스트에서 빠진다 |
| 3 | 청크가 `content_start` · `content_end` 를 갖나 | **해결 — 넣었다** (리비전 `0011`). 단 근거가 약해졌다 (6절 B 끝부분) |
| 4 | 표를 어떻게 다루나 | **해결.** `TABLE_ROW`/`TABLE_HEADER` + `table_id`·`table_row` 로 행 단위가 유지된다. 머리행 복제는 우리 청킹에서 한다 |
| 5 | 텍스트가 갱신되면 재청킹은 **누가 트리거하나** | **부분 해결.** `RAG-001-3` 선행이 `REV-004-1`(검수 완료)로 명시됐다. **동기냐 비동기냐는 여전히 미정** |
| 6 | 청크 최대 토큰 | **해결 — 제약이 사라졌다.** 채택·대안 3종(`BGE-m3-ko`·`KURE-v1`·`arctic`)이 **전부 8,192 실측**. 512 상한 모델(`e5`·`nomic`)은 탈락 |

### 5번이 유일하게 남았다 — 그런데 상황이 바뀌었다

인수인계 작성 시점에 *"작업 큐가 없다(celery·redis 0건)"* 고 썼는데,
**`document-async-processing` 브랜치가 Celery·Redis 를 넣고 있다**
(`docker-compose.yml` +39줄, `backend/app/worker.py` 신규).

`SYS-002-2`(비동기 작업 큐)가 P0 이고 그 브랜치가 곧 머지될 것으로 보인다.
**그러면 `RAG-001-3` 재인덱싱을 비동기로 짜는 것이 자연스러워진다.**
큐가 들어온 뒤에 결정하는 것이 맞다.

### 새 안건 네 개 — **전부 답을 받았다 (2026-08-14 오후)**

| | 물음 | 재정님 답 |

## 9-B. 지표 정의가 세현님과 다르다 — 숫자를 나란히 놓기 전에 맞춰야 한다

**우리 `run_eval.py` 의 `R@k` 는 표준 `recall@k` 가 아니다.**

세현님은 `sentence-transformers` 의 `InformationRetrievalEvaluator` 를 쓴다고
확인해 주셨다. 그 도구의 기본 출력이 `map@100`·`mrr@10`·`ndcg@10`·
`recall@1`·`recall@5` 이고 스크린샷과 정확히 일치한다.

| 우리 | `InformationRetrievalEvaluator` | 정의 |
|---|---|---|
| **`R@k`** | **`accuracy@k`** | 상위 k 안에 정답이 하나라도 있으면 1 |
| — | `recall@k` | `\|상위k ∩ 정답\| / \|정답 전체\|` |
| `MRR` | `mrr@10` | 첫 정답의 1/순위 |

**정답이 하나면 두 정의가 같다. 여러 개면 크게 갈린다.**

실제로 3.4배 차이가 났다 (정답 평균 2.7개짜리 자료에서).

```
우리 R@5         0.927
세현님 recall@5  0.2724      <- 실력 차이가 아니라 정의 차이
```

> **`R@k` 를 `recall@k` 라고 부르지 않는다. 비교할 때는 `accuracy@k` 와 맞춘다.**

**대응** — `도구/embed-test/ir_eval.py` 를 만들어 두었다.
`InformationRetrievalEvaluator` 를 직접 호출해 5개 지표 + `accuracy@k` 를 같이
찍는다. `accuracy@1` 이 우리 `R@1` 과 맞는지가 **검산**이 된다.

### 세현님 파인튜닝 결과 — 전 지표가 떨어졌다

3만 쌍 기준.

| 지표 | 학습 전 | 학습 후 | 변화 |
|---|---|---|---|
| map@100 | 0.2524 | 0.2338 | −7.4% |
| mrr@10 | 0.4810 | 0.4428 | −7.9% |
| ndcg@10 | 0.3220 | 0.3011 | −6.5% |
| **recall@1** | 0.1419 | 0.1240 | **−12.6%** |
| recall@5 | 0.2724 | 0.2638 | −3.2% |

**전 지표가 6~13% 균일하게 떨어졌다.** 데이터 부족이면 보통 지표별로 개선·악화가
섞인다. **균일한 하락은 학습 설정 문제 신호**이고, `recall@1` 이 가장 크게 무너진
것은 최상위 정밀도가 깨졌을 때 나오는 모양이다.

세현님은 10만 -> 26만 쌍으로 늘려 다시 돌리는 중이다. **원인이 데이터 양이
아니면 똑같이 떨어진다.**

| | 가설 | 상태 |
|---|---|---|
| — | 접두어 불일치 | **기각.** `bge-m3` 계열은 접두어가 없고 양쪽이 같다 |
| 1 | 평가셋이 학습 도메인과 다르다 | 미확인. 다르면 하락은 실패가 아니라 분포 이동이다 |
| 2 | 학습률·에폭 과다 | 미확인. `recall@1` 붕괴와 가장 잘 맞는다 |
| **3** | **`MultipleNegativesRankingLoss` 의 거짓 음성** | 미확인. **좁은 도메인 26만 쌍이면 배치 안에 비슷한 문단이 섞인다.** 정답을 맞혔는데 벌점을 받는다. **쌍을 늘리면 더 심해진다** |
| 4 | 이미 튜닝된 모델을 또 튜닝 | 베이스가 `BGE-m3-ko` 면 2차 튜닝이다 |

**제안한 진단 두 개 (추가 학습 없이 된다)**

```
A  평가셋을 도메인으로 쪼개 재기
   학습 도메인 쪽 오름 + 다른 쪽 내림  ->  정상적인 특화
   둘 다 내림                        ->  학습 설정 문제 (가설 2·3)

B  에폭별 체크포인트를 각각 재기
   1에폭부터 계속 내려감  ->  학습률이 높다
   올랐다가 내려감        ->  과적합. 조기 종료로 해결
```

### 10-1. 공지는 머지 뒤다 — 순서를 틀렸던 기록

처음에 **"공지 먼저, PR 나중"** 이라고 안내했는데 **틀렸다.**

**`main` 에 머지되기 전에는 팀원이 `git pull` 해도 아무것도 받지 않는다.**
변경이 `feat/rag-document-chunks` 에만 있기 때문이다. 그 상태에서
`docker compose down -v` 를 돌리면 **로컬 개발 데이터만 날리고 얻는 것이 없다.**

```
1  PR 올린다        팀원 영향 없음. 각자 main 에 있어서 pull 해도 변화 없다
2  리뷰 · 머지
3  머지 직후 공지    이때부터 pull 이 실제로 변경을 가져온다
```

미리 알릴 것이 있다면 **"pull 하라"가 아니라 "곧 머지된다"는 예고**다.
성격이 다르므로 메시지를 둘로 나눈다.

**예고에 넣을 것** — 리뷰하려고 브랜치를 직접 체크아웃하는 경우에도
`down -v` 가 필요하다는 점. 리뷰어는 로컬에서 돌려볼 수 있다.

> **일반화 — 팀 공유 파일(`docker-compose.yml` 등)의 변경 공지는 "머지 시점"에
> 맞춘다.** 브랜치에만 있는 변경을 두고 실행 명령을 안내하면 팀원이 헛일을 하거나
> 데이터를 잃는다.
| 2 | 재정님과 7절 안건 협의 (특히 5번 재청킹 트리거) | 병행 가능 | 착수 |

## 11. 이번 시험에서 틀렸던 것 — 반복 방지

**새 세션에서 같은 실수를 하지 않기 위해 남긴다.**

### 철회한 서술 네 개 — 모두 표본이 작을 때 1~4문항 차이로 쓴 결론

| 철회 | 이유 |
|---|---|
| "768 이 384 보다 낮다" | 뒤집혔다. 384(19) < 768(22) |
| "한국어 특화가 효과 있다" | 다국어 `arctic`(37) = `KURE-v1`(37) |
| "재순위로 384 를 쓸 수 있다" | 근거였던 R@10 도약이 사라졌다 |
| "API 를 볼 필요가 줄었다" | 근거가 9종 중 **최하위 모델 하나**였다 |

> **범주 안의 격차가 범주 간 격차보다 크다.** `arctic` 37 대 `e5-large` 18 —
> 둘 다 "다국어" 다. **범주로 고르지 말고 개별 모델을 재야 한다.**

### 방법론에서 틀렸던 것

| | 무엇 | 교훈 |
|---|---|---|
| 1 | `e5-large` 폭락을 **토큰 잘림으로 단정** | 재보니 잘린 청크가 0개였다 |
| 2 | `Qwen3` 70배 느림을 **모델 특성으로 단정** | `bfloat16` 이었다. fp32 로 맞추니 2~2.5배 |
| 3 | 패딩 가설 — **산술이 맞아떨어졌는데 전제가 틀렸다** | 패딩 모양을 찍어보니 `(8, 398)` 이었다 |
| 4 | 메모리 "2차에서 정상 측정됐다" | **가중치보다 작은 값**을 찍고 있었다 |
| 5 | 문서를 늘려 판별하려 함 | 청크 6.7배 늘려도 정답·질의가 그대로면 순위가 안 바뀐다. **질의를 늘려야 갈린다** |

> 그럴듯한 근거를 먼저 만들고 확인을 나중에 하는 실수를 세 번 했다.

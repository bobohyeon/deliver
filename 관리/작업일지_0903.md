# 2026-09-03 작업일지 — 프로젝트 문서 기반 질의응답(CHAT-001)

## 1. 이번 기록의 범위

프로젝트 문서 기반 질의응답(CHAT-001)의 첫 실제 Ollama 확인에서 나온 검색·응답 오류와 수정 결정을 기록한다. 이 기록은 사용자 PC의 단일 테스트 문서로 확인한 기능 점검이며, 모델 품질 벤치마크나 전체 정확도 측정이 아니다.

## 2. 확인된 사실

1. 테스트 산출내역서의 기존 청크는 기본 임베딩 모델로 만들어져 현재 어댑터 검색 공간과 달랐다. 현재 모델 조합으로 재색인한 뒤 문서 1건에서 청크 4개가 생성됐고, CHAT 검색이 질문과 맞는 산출내역서 원문 행을 근거로 표시했다.
2. 검색 근거는 맞았지만, `특급기술자 1인당 인건비는 얼마야?` 질문에서 원문 행 `특급기술자 / 3인월 / 9,500,000 / 28,500,000`의 단가가 아니라 총액 `28,500,000원`을 답했다.
3. 범용 프롬프트에 표의 열 대응, 단가와 총액 구분, 수량×단가 관계를 추가한 `chat-v2`도 같은 오답을 막지 못했다. 따라서 프롬프트 문구 추가만으로 해결됐다고 판정하지 않는다.
4. 별도 질문에서는 근거 원문에 없는 숫자 `755`가 답변에 나타난 사례가 있었다. 정확한 재현 조건과 반복 횟수는 아직 기록하지 않았으므로 오류 사례로만 남기고 발생률로 해석하지 않는다.

## 3. 결정

범용 CHAT 프롬프트에 `3 / 인 / 월` 같은 문서별 표기법을 계속 추가하지 않는다. 금액 질문이 아닌 일반 질문까지 프롬프트가 길어지고, 이번 실제 확인에서 프롬프트 강화만으로는 오답이 막히지 않았기 때문이다.

단가·1인당·개당·단위당 질문만 다음 구조화 검증 경로로 분리한다.

1. 기존 검색으로 실제 근거 청크를 먼저 확정한다.
2. 같은 프로젝트와 같은 근거 문서의 **승인된 최신 금액 항목**만 조회한다.
3. 질문에 포함된 항목명이 하나로 확정되고 `quantity`, `unit`, `unit_price`, `amount`가 모두 있을 때만 답한다.
4. 항목명·수량과 단위·단가·총액이 실제 근거 청크의 같은 원문 행 또는 `source_quote`에도 함께 있는지 대조한다. 숫자는 부분 문자열이 아니라 토큰 경계로 비교해 단가 `500,000`을 총액 `9,500,000`의 일부로 오인하지 않는다.
5. 서버가 `수량 × 단가`를 계산해 문서 총액과 일치하는지 검산한다. 불일치하면 문서 값을 고치지 않고 계산값과 차이를 알린다.
6. 후보가 없거나 여러 개이거나 원문과 대조되지 않으면 일반 LLM으로 되돌리지 않고 단가를 확정할 수 없다고 답한다.
7. `단가 말고 총액`, `단가와 총액` 같은 부정·복합 질문은 단가 전용 경로가 가로채지 않는다. 수량·단가가 없는 비율 항목 때문에 `요율`도 이 경로에서 제외한다.

`3 / 인 / 월`, `3인월`처럼 구분자만 다른 표기는 프롬프트 지시가 아니라 서버의 비교용 정규화에서 같은 `3인월`로 취급한다.

## 4. 구현 상태

Tasqra 팀 레포의 로컬 작업 브랜치에서 다음을 수정했다. 팀 레포에는 커밋·푸시하지 않았다.

- `backend/app/services/chat_service.py`
  - 일반 CHAT 프롬프트를 짧은 범용 규칙으로 되돌림
  - 단가 질문의 승인 금액 항목·근거 청크 교차검증 및 수량×단가 검산 추가
  - 일반 LLM 프롬프트 버전을 `chat-v3`로 변경
- `backend/app/dependencies.py`
  - 같은 요청의 `AmountRepository`를 `ChatService`에 주입
- `backend/tests/test_chat_service.py`
  - 기존 단가 질문 시험을 구조화 검증 경로에 맞게 갱신
  - `3 / 인 / 월` 표기가 프롬프트 추가 없이 대조되는 조건 포함

## 5. 현재 검증 수준과 남은 확인

- 세 변경 파일의 Python 문법 검사는 통과했다.
- 샌드박스에는 프로젝트 의존성 `pydantic`이 없어 pytest 수집 단계에서 중단됐다. 코드 실패로 통과했다고 기록하지 않는다.
- 사용자 PC의 Docker API 컨테이너에서 CHAT 단위시험과 실제 Ollama 질문을 다시 확인해야 한다.
- 실제 DB 금액 항목이 `PENDING`이면 답변에 사용하지 않는다. 먼저 사용자가 승인한 `APPROVED` 또는 수정 승인한 `EDITED` 항목이어야 한다.
- 이번 변경은 단가 역할을 안전하게 고르는 1차 범위다. 사용자가 새 수량을 제시한 `2인월 금액` 계산은 질문의 수량·단위를 명확히 해석하는 별도 단계로 둔다.


## 6. 전달 패치 생성기 정정

첫 배포한 `make_chat_unit_price_patch.py`는 관련성 게이트가 있는 CHAT 파일의 `Sequence` import와 `_search_is_relevant()`를 앵커로 가정했다. 사용자 PC에는 관련성 게이트를 제외한 CHAT 파일이 있어 첫 import 앵커가 0개로 판정됐고, 패치 파일이 생성되지 않았다. 뒤따른 `git apply`의 파일 없음 메시지는 이 실패의 연쇄 오류이며 Tasqra 소스에는 변경이 적용되지 않았다.

생성기를 다음 두 상태를 모두 지원하도록 고쳤다.

- 관련성 게이트 있음: `Sequence`, `_search_is_relevant()` 존재
- 관련성 게이트 없음: 기본 import와 `_calculate_evidence_budget()`만 존재

사용자가 적용한 기존 CHAT 전달 패치 중 관련성 게이트를 제외한 `01·02·03·04·06·07`을 깨끗한 코드에 다시 적용해 사용자 상태를 재구성한 뒤, 수정 생성기로 패치를 만들고 `git apply --check`가 통과하는 것까지 확인했다.


## 7. 사용자 PC 재검증 결과

수정된 생성기로 패치를 적용한 뒤 사용자 PC의 Docker Python 3.11 일회용 시험 경로와 실제 Ollama 화면에서 재검증했다. 사용자가 실제 화면의 정상 출력을 확인했다.

- 질문: `특급기술자 1인당 인건비는 얼마야?`
- 답변: 문서 단위를 `인월`로 명시하고 **1인월당 단가 9,500,000원**을 반환
- 검산 표시: **수량 3인월 × 단가 9,500,000원 = 총액 28,500,000원**
- 근거 표시: `[TEST] 산출내역서.pdf`의 해당 산출내역 행

이 결과로 기존 오류였던 총액 `28,500,000원`을 1인당 단가로 답하는 문제는 재현되지 않았다. 단가 질문의 구조화 금액 항목·원문 근거 교차검증 경로가 실제 사용자 환경에서 동작한 것으로 판정한다. 다만 단일 문서·단일 질문의 기능 확인 결과이며 전체 금액 질의 정확도로 확대하지 않는다.


## 8. 복수 기술자 단가 질문 보류 원인과 확장

사용자 화면에서 단일 항목 질문은 정상 처리됐지만 다음 두 질문은 `단가를 하나로 확정하지 못했습니다`로 보류됐다.

- `기술자들별로 1인당 인건비 말해줘`
- `특급기술자, 고급기술자, 중급기술자 1인당 인건비는?`

원인은 임베딩 모델이나 생성 LLM이 아니다. 검색은 산출내역서 근거 청크를 찾았고, 단가 질문은 LLM 호출 전에 서버의 구조화 검증 경로로 분기된다. 당시 코드는 승인 금액 후보가 정확히 1개일 때만 답하도록 되어 있어 집합 질문은 후보 0개, 명시형 복수 질문은 후보 3개로 보류됐다. 답변 근거가 비어 있던 것도 이 서버 보류 응답의 결과다.

복수 지원 범위는 다음으로 정했다.

1. 쉼표·접속사로 여러 기술자 이름을 명시하면 요청한 이름과 승인 항목 후보가 모두 일치할 때만 목록으로 답한다. 하나라도 없으면 부분 답변하지 않고 전체 보류한다.
2. `기술자별`, `기술자들별`, `각 기술자`, `모든 기술자` 질문은 같은 근거 문서의 승인 항목 중 항목명에 `기술자`가 포함된 행을 모두 대상으로 한다.
3. 후보는 한 문서에서만 나와야 한다. 서로 다른 문서의 단가를 한 목록으로 섞지 않는다.
4. 각 행은 기존 단일 질문과 같이 수량·단위·단가·총액을 검산하고, `source_quote`가 있으면 실제 근거 청크에 그 인용이 포함돼야 한다. 과거 수동 입력처럼 인용이 없으면 네 값이 같은 한 원문 행에 함께 있을 때만 인정한다.
5. 중복 항목명이나 한 행의 검증 실패가 있으면 전체를 보류한다.
6. 이 경로는 LLM을 호출하지 않으며 일반 CHAT 프롬프트도 늘리지 않는다.

Tasqra 로컬 코드와 단위시험을 갱신했고 Python 문법 및 `git diff --check`를 통과했다. 샌드박스에는 프로젝트 의존성이 없어 pytest 실행은 사용자 PC의 앞선 일회용 Docker Python 3.11 경로로 확인한다. 사용자 PC의 관련성 게이트 없는 CHAT 상태에 기존 단가 패치까지 적용한 상태를 재구성한 후, 후속 패치 `패치/chat-multi-unit-price.patch`의 `git apply --check` 통과를 확인했다.


## 9. 복수 기술자 단가 사용자 PC 재검증

후속 패치 적용 뒤 실제 Ollama 화면에서 `기술자들별로 1인당 인건비 말해줘` 질문을 재검증했고 정상 목록이 반환됐다.

- 특급기술자: 1인월당 9,500,000원 — 3인월 × 9,500,000원 = 28,500,000원
- 고급기술자: 1인월당 7,200,000원 — 6인월 × 7,200,000원 = 43,200,000원
- 중급기술자: 1인월당 5,800,000원 — 4인월 × 5,800,000원 = 23,200,000원
- 근거: `[TEST] 산출내역서.pdf`의 해당 산출내역 청크

이 결과로 집합형 복수 질문이 단일 후보 제한에 걸리던 문제는 사용자 환경에서 해결된 것으로 판정한다. 이 경로도 LLM 생성 결과가 아니라 승인된 금액 항목과 원문 행을 서버가 대조해 만든 답변이다. 단일 테스트 문서에서의 기능 확인이며 전체 문서 정확도로 확대하지 않는다.


## 10. 명시적 인월 수량 계산 확장

복수 기술자 단가 목록의 사용자 PC 성공 확인 뒤, 승인 단가를 이용한 명시적 인월 수량 계산을 다음 단계로 구현했다.

### 처리 규칙

1. `인건비`, `금액`, `비용`, `계산`, `얼마` 중 하나가 있는 **금액 의도 질문**에서만 `2인월`, `1.5인월`, `2 / 인 / 월` 수량을 읽는다. `투입 기간이 2인월이야?` 같은 사실 확인 질문은 계산 경로가 가로채지 않고 일반 문서 질의 경로로 보낸다.
2. `특급기술자 2인월 인건비는?`처럼 수량이 하나로 명시되면 기존 구조화 단가 검증을 모두 거친 뒤 `2인월 × 검증 단가`를 계산한다. 특급기술자 단가 9,500,000원 기준 예상 답은 19,000,000원이다.
3. `기술자들별로 2인월 인건비`도 같은 문서에서 검증된 각 기술자 단가에 동일한 2인월을 적용한다.
4. `특급 2인월, 고급 3인월`처럼 한 질문에 서로 다른 수량이 있으면 항목별 대응을 추측하지 않고 나누어 질문해 달라고 답한다.
5. `2명 인건비`, `2인 인건비`처럼 기간이 없으면 계산하지 않고 `2인월`처럼 투입 기간을 포함해 달라고 요청한다.
6. 승인 행의 실제 단위가 정확히 `인월`일 때만 인월 계산을 허용한다. `인일`, `개월`, `명` 단가를 인월 단가처럼 곱하지 않는다.
7. 원문 행의 기존 `수량 × 단가 = 총액` 검산이 불일치하면 새 수량 계산에도 그 단가를 사용하지 않는다.
8. 금액 계산은 `Decimal`과 원 단위 반올림을 사용하며 LLM을 호출하지 않는다. 일반 CHAT 프롬프트도 늘리지 않는다.

### 검증 상태

- 단일 2인월 계산, 복수 기술자 2인월 계산, 기간 없는 2명 질문 보류, 서로 다른 수량 보류, 비금액 인월 질문의 일반 경로 유지, 인일 단가 거부 시험을 추가했다.
- Tasqra 로컬 변경의 Python 문법 검사와 `git diff --check`가 통과했다.
- 사용자 PC의 현재 상태(기존 단가 검증 + 복수 기술자 패치 적용)를 재구성한 뒤 후속 패치 `패치/chat-person-month-calculation.patch`의 `git apply --check`가 통과했다.
- 실제 pytest와 Ollama 화면 확인은 사용자 PC에서 수행한다.


## 11. 인월 수량 계산 사용자 PC 재검증

후속 패치 적용 뒤 실제 Ollama 화면에서 단일·복수 인월 계산과 기간 없는 인원 질문을 확인했다.

| 질문 | 실제 결과 | 판정 |
|---|---|---|
| `특급기술자 2인월 인건비는?` | 2인월 × 9,500,000원 = **19,000,000원** | 정상 |
| `기술자들별로 2인월 인건비를 계산해줘` | 특급 **19,000,000원**, 고급 **14,400,000원**, 중급 **11,600,000원** | 정상 |
| `특급기술자 2명 인건비는?` | 인원 수만으로 계산할 수 없으며 투입 기간을 포함해 `2인월`처럼 질문하라고 안내 | 정상 보류 |

각 계산 답변에는 `[TEST] 산출내역서.pdf`의 산출내역 원문 근거가 표시됐다. 기간 없는 `2명` 질문에는 계산에 쓸 수 있는 근거가 없으므로 근거를 붙이지 않았다. 이는 오류가 아니라 숫자를 추측하지 않는 의도된 결과다.

이 확인으로 다음 경로가 사용자 환경에서 동작한 것으로 판정한다.

1. 승인된 최신 금액 항목과 원문 행에서 1인월 단가를 검증한다.
2. 질문에 명시된 하나의 인월 수량을 검증 단가와 `Decimal`로 곱한다.
3. 같은 수량의 복수 기술자 질문은 기술자별로 계산한다.
4. 기간 없는 인원 수는 계산하지 않고 필요한 단위를 되묻는다.

### 현재 남은 표현 범위

아래는 이번 실패가 아니라 아직 지원하지 않기로 둔 표현이다.

- 한 질문에서 항목마다 수량이 다른 경우: `특급 2인월, 고급 3인월`
- 인원과 기간을 따로 말한 경우: `특급기술자 2명이 3개월 일하면?`
- 다른 표기: `2 M/M`, `2 PM`, `두 인월`
- 승인 행 단위가 `인일`, `명`, `개월`인 경우의 단위 변환

다음 우선순위는 **항목별로 서로 다른 인월 수량을 한 질문에서 안전하게 연결하는 것**이 적절하다. 이름과 수량이 한 쌍으로 명시돼 모호성이 가장 작고, 현재처럼 나누어 질문하게 하는 불편을 줄일 수 있다. 그다음에 `인원 × 개월 = 인월` 변환을 검토하되 전일 투입 가정이 필요한지는 먼저 표시하거나 확인해야 한다.


## 12. 항목별 서로 다른 인월 수량 계산 확장

사용자가 실제 화면에서 `특급기술자 2인월, 고급기술자 3인월, 중급기술자 1.5인월 인건비는?` 질문이 아직 보류되는 것을 확인했다. 기존 구현은 질문 안의 인월 수량이 둘 이상이면 항목과 수량의 대응을 해석하지 않고 분리 질문을 요청하도록 제한했기 때문이다. 임베딩·LLM 실패가 아니라 서버의 보수적 파싱 범위다.

다음 조건을 모두 만족할 때만 항목별 계산하도록 확장했다.

1. 모든 수량 표현이 완전한 항목명 바로 뒤의 `...기술자 N인월` 형태다.
2. 발견한 전체 인월 표현 수와 항목명·수량 쌍 수가 같다.
3. 같은 항목명이 중복되지 않고 질문에도 정확히 한 번만 나온다.
4. 요청 항목명 집합과 같은 근거 문서의 승인 금액 후보 집합이 정확히 같다.
5. 기존 단일·복수 단가 경로처럼 인월 단위, 원문 행, 수량×단가=총액 검산을 모두 통과한다.

목표 질문의 계산값은 다음과 같다.

- 특급기술자: 2인월 × 9,500,000원 = **19,000,000원**
- 고급기술자: 3인월 × 7,200,000원 = **21,600,000원**
- 중급기술자: 1.5인월 × 5,800,000원 = **8,700,000원**

`특급기술자 2인월과 3인월`처럼 수량 하나가 항목명과 연결되지 않거나, 같은 기술자 이름을 중복해서 적으면 전체를 보류한다. LLM과 범용 프롬프트는 사용하지 않는다.

Tasqra 로컬 코드와 회귀시험을 갱신했고 Python 문법 및 `git diff --check`를 통과했다. 사용자 PC의 누적 상태(단가 검증 → 복수 기술자 → 공통 인월 계산)를 재구성한 뒤 후속 패치 `패치/chat-item-person-months.patch`의 `git apply --check`가 통과했다. 실제 pytest와 화면 검증은 사용자 PC에서 수행한다.


## 13. 항목별 서로 다른 인월 계산 사용자 PC 재검증

후속 패치 적용 뒤 실제 Ollama 화면에서 다음 질문을 재검증했다.

- 질문: `특급기술자 2인월, 고급기술자 3인월, 중급기술자 1.5인월 인건비는?`
- 특급기술자: 2인월 × 9,500,000원 = **19,000,000원**
- 고급기술자: 3인월 × 7,200,000원 = **21,600,000원**
- 중급기술자: 1.5인월 × 5,800,000원 = **8,700,000원**
- 근거: `[TEST] 산출내역서.pdf`의 해당 산출내역 원문

세 항목 모두 질문에 지정한 서로 다른 인월 수량과 승인 단가가 정확히 연결됐고, 계산 결과와 원문 근거가 함께 표시됐다. 사용자가 실제 화면의 정상 출력을 확인했으므로 항목명·수량 1:1 연결과 결정론적 계산 경로가 사용자 환경에서 동작한 것으로 판정한다.

이 결과는 단일 테스트 문서와 위 질문에 대한 기능 확인이다. 다른 문서 형식이나 표현을 포함한 전체 금액 질의 정확도로 확대하지 않는다. 다음 검토 범위는 `특급기술자 2명이 3개월 일하면?`처럼 인원과 기간을 따로 제시한 표현이며, `2명 × 3개월 = 6인월` 계산 전에 전일 투입 가정을 명시하거나 사용자에게 확인하는 규칙이 필요하다.


## 14. 인원과 기간을 분리한 인건비 계산 확장

다음 표현을 승인된 1인월 단가로 계산하는 후속 패치를 만들었다.

- 질문 예시: `특급기술자 2명이 3개월 일하면 인건비는?`
- 계산식: **1인월 단가 × 2명 × 3개월**
- 특급기술자 1인월 단가가 9,500,000원이면 결과: **57,000,000원**
- 총투입량: **6인월**

`6인월`은 비용 계산식을 생략하거나 다른 단가로 바꾸는 값이 아니라 `2명 × 3개월`의 총투입량을 나타내는 보조 단위다. 답변에는 `1인월 단가 × 인원 × 개월` 계산식을 먼저 표시하고 총투입량을 함께 적는다.

### 처리 조건

1. `인건비`, `금액`, `비용`, `계산`, `얼마` 중 하나가 있는 금액 의도 질문에서만 처리한다.
2. 완전한 기술자 항목명 하나와 양의 정수 인원 하나, 양의 개월 수 하나가 `기술자 N명이 M개월` 순서로 연결될 때만 계산한다.
3. 답변에 **전일 투입 기준**을 명시한다. 투입률이나 파트타임 조건을 임의로 만들지 않는다.
4. 질문의 기술자명과 승인 후보가 정확히 같고, 같은 검색 근거 문서의 최신 `APPROVED` 또는 `EDITED` 항목이어야 한다.
5. 승인 행 단위가 정확히 `인월`이고, 원문 행 대조와 기존 `수량 × 단가 = 총액` 검산이 일치해야 한다.
6. 복수 인원·복수 기간, 소수 인원, 0 이하 값, 항목과 인원·기간 연결 실패는 계산하지 않고 표현을 다시 요청한다.
7. 기존 `2인월` 파싱과 항목별 서로 다른 인월 계산보다 뒤에서 처리하므로 앞선 지원 범위를 바꾸지 않는다.
8. LLM이나 범용 프롬프트에 계산을 맡기지 않고 서버가 `Decimal`로 계산한다.

후속 패치는 `패치/chat-people-months-calculation.patch`다. Tasqra 로컬 코드의 Python 문법 검사, 목표·거부 표현 파서 확인, `6 × 9,500,000 = 57,000,000` 계산 확인을 통과했다. 현재 구현 상태에 대한 패치 역방향 적용 검사도 통과해 직전 누적 패치 상태용 후속 패치임을 확인했다. 실제 Docker 시험과 Ollama 화면 확인은 사용자 PC에서 수행한다.


## 15. 인원 × 기간 인건비 계산 사용자 PC 재검증

후속 패치 적용 뒤 실제 화면에서 다음 질문을 재검증했다.

- 질문: `특급기술자 2명이 3개월 일하면 인건비는?`
- 답변 전제: **전일 투입 기준**
- 계산식: **특급기술자 1인월 단가 9,500,000원 × 2명 × 3개월 = 57,000,000원**
- 총투입량 표시: **6인월**
- 근거: `[TEST] 산출내역서.pdf`의 특급기술자 원문 행

사용자 화면에서 1인월 단가·인원·개월을 모두 드러낸 계산식과 총투입량이 정확히 표시됐고, 같은 산출내역서 원문 근거도 함께 반환됐다. 따라서 단일 기술자의 명확한 `인원 × 개월` 표현을 승인된 1인월 단가로 계산하는 경로가 사용자 환경에서 동작한 것으로 판정한다.

이 결과는 단일 테스트 문서와 전일 투입을 가정한 위 질문에 대한 기능 확인이다. 투입률·파트타임 조건이 명시된 질문이나 여러 기술자의 인원·기간을 한 번에 연결하는 표현까지 검증된 것으로 확대하지 않는다.


## 16. 투입률·파트타임 조건 안전 차단

인원과 기간을 분리한 계산이 정상 동작한 뒤, 질문에 투입률이 명시돼도 기존 파서가 이를 무시하고 전일 투입 금액을 반환할 수 있는 위험을 먼저 차단했다.

- 위험 질문: `특급기술자 2명이 3개월 동안 50% 투입되면 인건비는?`
- 잘못된 처리: `50%`를 무시하고 9,500,000원 × 2명 × 3개월 = 57,000,000원 반환
- 이번 처리: 계산하지 않고 투입률 조건을 반영한 총 인월을 직접 알려 달라고 요청
- 사용자가 직접 환산해 `특급기술자 3인월 인건비`처럼 질문하면 기존 승인 단가·원문 검증 경로로 계산

안전 차단은 금액 의도 질문에서 명시 인월·인원×개월 파싱보다 먼저 실행한다. 숫자 `%` 또는 `퍼센트`, `투입률`, `파트타임`, `반일` 중 하나가 있으면 보류한다. 반대로 조건이 없는 `특급기술자 2명이 3개월 일하면 인건비는?`와 기존 `2인월` 질문은 그대로 처리한다.

후속 패치는 `패치/chat-workload-condition-guard.patch`다. Tasqra 로컬 코드의 Python 문법 검사와 목표·비대상 표현 검사를 통과했고, 현재 적용 상태에서 패치 역방향 검사도 통과했다. 실제 사용자 PC 적용과 화면 확인은 아직 수행하지 않았다.


## 17. 명확한 숫자 투입률 계산 확장

투입률 조건을 전부 막던 16절의 안전 차단을 다음처럼 세분화했다. 숫자로 명확하게 계산할 수 있는 투입률은 살리고, 애매하거나 잘못된 표현만 계속 보류한다.

- 질문 예시: `특급기술자 2명이 3개월 동안 50% 투입되면 인건비는?`
- 계산식: **1인월 단가 9,500,000원 × 2명 × 3개월 × 투입률 50% = 28,500,000원**
- 인원·기간 기준 총투입량: **6인월**
- 투입률 적용 유효 총투입량: **3인월**

숫자 `%` 또는 `퍼센트` 표현이 투입·투입률·근무·파트타임·반일 문맥과 가까이 하나만 있고, 값이 `0 초과 100 이하`일 때만 계산한다. 단일 기술자의 인원과 개월도 하나로 연결돼야 하며, 기존 승인 단가·검색 원문·`인월` 단위·문서 원행 총액 검산을 모두 통과해야 한다.

다음은 계산하지 않고 명확한 투입률이나 표현을 다시 요청한다.

- 숫자 없는 `파트타임`, `반일`, `투입률`
- `0%`, `101%`처럼 허용 범위를 벗어난 값
- 한 질문의 복수 투입률
- 할인율처럼 투입 문맥과 연결되지 않은 `%`
- 숫자 투입률은 있지만 기술자·인원·개월 연결이 불완전한 표현

투입률이 없는 기존 질문은 전일 투입 기준 계산을 그대로 유지한다. 첨부 화면에서 이미 확인한 `특급기술자 2명이 3개월 일하면 인건비는?`의 57,000,000원·총투입량 6인월·원문 근거 결과가 회귀 기준이다.

후속 패치는 `패치/chat-workload-rate-calculation.patch`다. Python 문법과 diff 검사를 통과했고, 실제 파서 메서드로 명확한 비율·거부 표현을 확인했다. `2명 × 3개월 × 50% = 유효 3인월`, `9,500,000원 × 3인월 = 28,500,000원` 계산 및 기존 전일 투입 57,000,000원 회귀 계산도 확인했다. 현재 적용 상태에서 패치 역방향 검사까지 통과했으며 사용자 PC 화면 검증은 아직 수행하지 않았다.


## 18. 숫자 투입률 계산 및 회귀 사용자 PC 최종 확인

사용자가 숫자 투입률 계산과 애매한 표현의 안전 보류 확인을 모두 마쳤다고 보고했다. 안내한 확인 범위는 다음과 같다.

- 명확한 `50%`, `50퍼센트` 투입률: 1인월 단가 × 인원 × 개월 × 투입률 계산
- 숫자 없는 `파트타임`, 허용 범위를 벗어난 `0%`, 한 질문의 복수 투입률: 계산하지 않고 명확한 투입률을 요청
- 투입률 없는 기존 인원 × 기간 질문: 전일 투입 계산을 그대로 유지

첨부 화면에서는 마지막 회귀 항목을 직접 확인했다.

- 질문: `특급기술자 2명이 3개월 일하면 인건비는?`
- 답변: **1인월 단가 9,500,000원 × 2명 × 3개월 = 57,000,000원**
- 총투입량: **6인월**
- 근거: `[TEST] 산출내역서.pdf`의 특급기술자 원문 행

따라서 숫자 투입률 지원을 추가한 뒤에도 비율 없는 기존 전일 투입 계산과 원문 근거 반환은 유지된 것으로 판정한다. 이번 확인은 단일 테스트 문서의 기능 검증이며 전체 문서 형식이나 모든 자연어 표현의 정확도로 확대하지 않는다.

## 19. 프로젝트 현황 개요 구조화 패치

프로젝트 현황 산출물의 개요가 한 문단으로 이어져 내용을 빠르게 구분하기 어려운 문제를 개선했다. 주간 보고서의 기간 변동 요약은 기존 2~4문장 형식을 유지하고, 프로젝트 현황만 근거가 있는 `자료:`, `진행:`, `결정:`, `일정:`, `금액:` 표제 중 2~4개의 짧은 줄로 요약하도록 구분했다. 자료가 적으면 1줄을 허용하고 전체 250자 제한은 유지한다.

LLM에는 Markdown 글머리표를 만들게 하지 않고 순수 텍스트 줄을 `\n`으로 구분하게 한다. 출력 형식별 렌더러가 다음처럼 표시를 맡는다.

- Markdown: 여러 줄 개요를 목록으로 변환
- HTML/PDF: 여러 줄 개요를 동일한 무채색 메모 영역의 목록으로 표시
- XLSX: 각 줄에 불릿을 붙이고 논리적 줄바꿈과 자동 줄바꿈을 함께 계산해 행 높이에 반영
- 한 줄 개요와 주간 보고서 개요: 기존 문단 표시 유지

Tasqra 로컬에서 다음 5개 파일을 수정했다.

- `backend/app/analyzers/prompts.py`: 개요 프롬프트를 `overview-v3`로 올리고 산출물 종류별 형식 규칙 추가
- `backend/app/services/deliverable_service.py`: 개요 생성 요청에 산출물 종류 전달
- `backend/app/services/deliverable_markdown.py`: 여러 줄 개요 목록 렌더링
- `backend/app/services/deliverable_html.py`: HTML/PDF 목록 렌더링과 무채색 스타일
- `backend/app/services/deliverable_xlsx.py`: 불릿 표시와 여러 줄 행 높이 계산

Python 문법 검사와 `git diff --check`를 통과했다. 후속 패치 `패치/project-status-overview.patch`는 위 5개 파일만 포함하며 현재 구현 상태에서 `git apply --reverse --check`가 통과했다. 실제 모델이 생성한 2~4개 항목과 Markdown·HTML·PDF·XLSX 화면은 사용자 PC에서 확인해야 하므로 아직 최종 화면 검증 완료로 기록하지 않는다.

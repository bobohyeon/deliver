# 타팀 발표 정리 (1조 · 3조)

미니 프로젝트 발표를 듣고 적은 메모를 정리한 것이다. 우리 프로젝트에 없던 것과
심사 피드백을 중심으로 본프로젝트 준비에 쓸 수 있게 묶었다.

---

## 1. 피드백 종합 — 두 팀에 공통으로 나온 것

두 팀 모두에게 지적된 항목이 심사 기준으로 보인다.

| 지적 | 1조 | 3조 |
|---|---|---|
| 목소리 크게 | O | O |
| 말 속도 조절 | | O |
| 한 페이지에 다 담지 말고 나누기 | | O |
| 듣는 사람이 이해하게 — 더 단순하게 | | O |
| 산출물을 일일이 설명하지 않기 | O | |
| 주장에 기준·수치가 없음 | O | |
| 미구현을 강조하지 않기 | O | |

### 특히 중요한 두 가지

**미구현을 어떻게 말하는가**

> "무조건 솔직한 게 좋은 것은 아니다. 미구현이 아니라 **향후 개발사항 / 개선사항**으로
> 분류해서 말하라."

1조는 솔직한 태도 자체는 좋게 평가받았지만("학습한 느낌이 든다") 발표 구성으로는
지적을 받았다. "구현률 50%" 를 밝힌 것도 여기 걸렸다.

우리는 `ISS-046` 을 결함으로 기록하고 `2+2N` 을 "본프로젝트 이관" 으로 배치했다.
이미 이 방식이었으므로 유지한다.

**주장에 기준을 붙이는가**

1조는 전처리를 설명했으나 페이지 수와 처리 시간 기준이 없다는 지적을 받았다.
분류가 안 된 것도 "프롬프트 문제인가 싶었다" 로 끝나 근거가 약했고, 심사자가 준
답은 **"프롬프트에 분류 기준을 먼저 적었어야 했다"** 였다.

3조는 반대로 걸렸다. 통합테스트 시나리오가 우리보다 촘촘했는데 발표에서 줄줄이
읽어 지적을 받았다. **문서는 촘촘하게, 발표는 대표 사례 하나만.**

### 긍정 평가

- 1조 — 솔직하고 학습한 느낌이 든다
- 3조 — 이것저것 시도하는 것은 좋다

## 2. 우리에게 없던 것 — 확인해서 걸러낸 결과

처음 메모만 보고 "없다" 고 판단했다가 코드로 확인하니 **우리도 있는 것이 여럿**이었다.
아래는 코드와 산출물로 확인한 결과다.

### 우리도 있는 것 (착각이었던 항목)

| 항목 | 확인 근거 |
|---|---|
| **하이브리드 파이프라인** — 텍스트 레이어는 살리고 이미지 영역만 OCR | `ExtractMethod.HYBRID` 값이 있다. `pdf_extractor._extract_page()` 가 PyMuPDF 블록을 순회하며 `type==0`(텍스트)은 그대로, `type==1`(이미지)은 그 영역만 OCR 한다 |
| **정답 데이터 기반 정확도 판정** | `IT-06-2` 기대결과가 `ground_truth_accuracy 값이 산출됨` 이다. 정답 없이 측정할 때는 `avg_confidence` 를 쓰고 화면에 그 사실을 안내한다 |
| **AI 타임아웃 처리** | `AI_TIMEOUT_SECONDS` 설정 + `asyncio.timeout` → `AI_TIMEOUT`(504). `summary_analyzer` · `category_analyzer` 양쪽에 있다 |
| 로컬 경량 모델의 언어 쏠림 | 우리는 OpenAI API 를 썼으므로 겪지 않는 문제다. 없는 기능이 아니라 **다른 선택**이다 |

**하이브리드는 오히려 우리가 한 걸음 더 갔다.** 이미지 OCR 결과의 픽셀 좌표를 PDF
페이지 좌표로 되돌려(`inverse_scale`) 텍스트 블록과 같은 기준으로 정렬한다
(`elements.sort(key=lambda e: (e.y, e.x))`). 그래서 이미지 안 글자가 본문 흐름의
제자리에 들어간다. 아무 요소도 없는 페이지는 전체를 OCR 하는 폴백도 있다.

3조와의 진짜 차이는 처리가 아니라 **보여주기**다. 3조는 페이지별 텍스트 / 이미지
영역을 화면에서 육안으로 확인할 수 있게 만들었고, 우리는 `extract_method` 값으로만
기록한다.

### 여전히 우리에게 없는 것

| 항목 | 팀 | 우리 상태 |
|---|---|---|
| **CER / WER** 지표 | 3조 | `ground_truth_accuracy` 라는 자체 지표를 쓴다. 업계 표준 지표가 아니라 다른 결과와 비교가 안 된다 |
| **OCR 결과를 테이블에 저장** | 3조 | `/api/ocr-compare` 는 즉석 응답만 하고 저장하지 않는다. 그래서 엔진별 정확도 추이를 볼 수 없다 |
| **LLM 재시도 · 폴백** | 3조 | 타임아웃은 있으나 재시도나 대체 모델 전환은 없다 (`retry` · `fallback` 코드 없음) |
| **3종 병렬 OCR 후 자동 채택** | 3조 | 비교 화면만 제공하고 선택은 사람이 한다 |
| **텍스트 / 이미지 영역 시각화** | 3조 | 내부에서는 나누지만 화면에 보여주지 않는다 |
| 유저용 / 개발자용 화면 분리 | 3조 | OCR 비교가 사용자 화면에 섞여 있다 |
| 전처리 선택 + 비포 / 애프터 비교 | 3조 | `PRESET_*` 은 있으나 사용자 선택 UI 가 없다 |
| 프롬프트 3갈래 (교정 · 요약 · 번역) | 3조 | 요약 · 분류 2갈래 |
| 오탈자 수정 · 번역 기능 | 3조 | 없음 |
| PDF 다운로드 | 3조 | txt 만. 의도적으로 제외했다 |
| 모델별 서버 포트 분리 후 통합 처리 | 1조 | 단일 프로세스 |
| 사용자 피드백 수집 (품질 개선 루프) | 1조 향후 | 없음 |
| 벡터DB · RAG · 파인튜닝 | 1조 향후 | PostgreSQL 선정 이유로만 언급 |
| Neon (관리형 PostgreSQL) · 클라우드 배포 | 3조 / 1조 | 로컬 도커만 |
| Notion + Canva 로 회의록 · WBS | 3조 | xlsx · md + git |
| 테스트 대상 파일명을 세세하게 기록 | 3조 | 유형으로만 기록 |

**전처리 비포 / 애프터는 지금 자산으로 바로 만들 수 있다.** `PRESET_*` 과
`preprocess_for_layout` 이 이미 있으니 화면만 붙이면 된다.

### 1조가 발견한 것 — 자체 모델을 쓸 때의 예고편

> Gemma 1B 는 **입력이 길어질수록 가중치가 주 언어(영어)로 쏠린다.**
> 그래서 영어로 나온 결과를 다시 한국어로 번역했다.

1조은 카테고리 분류가 잘 안 된 원인도 결국 가벼운 Gemma 모델 탓으로 결론 내렸고,
앞으로 두 가지 모델을 쓸 계획이라고 했다.

우리는 상용 API 를 써서 겪지 않았지만, **본프로젝트에서 자체 모델을 쓴다면 그대로
만날 문제다.** 다만 재번역은 지연이 두 배가 되고 정보가 손실되므로, 근본 대책은
모델 크기를 올리거나 출력 언어를 강제하는 쪽이다.

## 3. 우리가 더 나았던 것

본프로젝트에서 버리지 말아야 할 것들이다.

- **DB 저장과 검색** — 1조는 DB 저장이 없고 문서 검색도 미구현이었다
- **조회 흐름 완결** — 목록 · 상세 · 검색 · 다운로드 · 삭제가 다 붙어 있다
- **에러코드 11종 체계와 request_id 로깅** — 두 팀 모두 언급이 없었다
- **읽기 순서 보정** — 이미지 안 글자를 본문 흐름의 제자리에 넣는다
- **정량 측정과 과제 이관 기록** — `2+2N`, 문서 9건에 쿼리 20개처럼 수치로 남기고
  안 고친 이유까지 적었다. 1조가 지적받은 "기준 없음" 의 반대 사례다
- **페이크 구현체로 병렬 작업** — API 계약을 먼저 고정해 세 명이 동시에 움직였다
- **테스트 산출물** — 단위 66행 · 통합 44항목

## 4. 본프로젝트 우선순위

효과 대비 비용 순서다.

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | **OCR 결과를 테이블에 저장** | 지금은 즉석 비교만 한다. 저장해야 엔진별 정확도 추이를 볼 수 있고, 아래 2번의 전제가 된다 |
| 2 | **CER / WER 로 지표 전환** | `ground_truth_accuracy` 는 우리끼리만 통한다. 표준 지표로 바꾸면 외부와 비교할 수 있다 |
| 3 | **LLM 재시도 · 폴백** | 타임아웃은 이미 있다. 재시도와 대체 모델 전환만 추가하면 된다 |
| 4 | **N+1 해소** — 표시용 값 비정규화 | 방향과 목표치(쿼리 20 → 2)가 이미 정해져 있다 |
| 5 | **전처리 선택 + 비포 / 애프터 화면** | `PRESET_*` 자산이 있어 화면만 붙이면 된다 |
| 6 | **텍스트 / 이미지 영역 시각화** | 내부에서 이미 나누고 있다. 좌표를 화면에 그리기만 하면 된다 |
| 7 | **3종 병렬 후 자동 채택** | 1번이 끝나면 자연스럽게 이어진다 |
| 8 | **유저 / 개발자 화면 분리** | OCR 비교를 개발자 영역으로 옮기면 사용자 화면이 단순해진다 |
| 9 | **벡터DB + RAG** | PostgreSQL 을 고른 이유를 실제로 살리는 일 |

6번은 **이미 가진 데이터를 안 보여주고 있을 뿐**이라 비용 대비 인상이 가장 크다.

## 5. 우리팀이 받은 질문과 답

우리 팀은 **피드백은 받지 않았고 질문만 받았으며 세 개 모두 답변했다.** 아래는 그
답변을 정리한 것이다. 세 질문 모두 "발표에서 설명이 부족했던 지점" 을 가리키므로
다음 발표에서 그대로 보완한다.

### Q1. 추출기 · 분석기가 무엇을 의미하는가

발표에서 용어를 정의하지 않고 쓴 것이 원인이다. 다음에는 한 문장으로 먼저 정의한다.

> 추출기는 **파일에서 글자를 꺼내는 부품**, 분석기는 **꺼낸 글자를 AI 에 보내
> 결과를 만드는 부품**입니다. 둘 다 규격이 같아서 갈아 끼울 수 있습니다.

**추출기 (`TextExtractor`)**

- 규격은 하나다. `extract(file_path) -> ExtractResult`
- `ExtractResult` 는 `content` · `page_count` · `char_count` · `extract_method`
- 파일 종류마다 방법이 달라서 종류별로 만들었다. PDF 는 PyMuPDF, DOCX 는
  python-docx, 이미지는 OCR
- `ExtractorRegistry` 가 확장자 → 추출기 매핑을 들고 있다. 새 형식을 지원하려면
  추출기 하나 만들고 `register()` 한 줄이면 된다

**분석기 (`Analyzer`)**

- 규격은 하나다. `async analyze(text) -> AnalyzeResult`
- `AnalyzeResult` 는 `result`(dict) · `provider` · `model_name` ·
  `prompt_version` · `tokens_in` · `tokens_out` · `latency_ms`
- 요약기와 분류기 두 개가 있고, 요청의 `analyzer_types` 로 무엇을 돌릴지 고른다
- `result` 를 dict 로 열어둔 이유는 분석기마다 결과 모양이 달라서다. 분석기를
  추가해도 API 응답 규격이 바뀌지 않는다

**Spring 비교** — `TextExtractor` · `Analyzer` 는 Java interface 이고,
`ExtractorRegistry` 는 `Map<String, TextExtractor>` 를 주입받아 확장자별로 고르는
전략 패턴이다.

**효과** — OCR 엔진 3종을 붙일 때 라우터와 서비스를 고치지 않았다. 이 말을 함께
하면 "그래서 왜 그렇게 했나" 가 해결된다.

### Q2. 데이터 구조 다시 설명

세 테이블이고, 나눈 기준은 **값의 수명**이다.

| 테이블 | 담는 것 | 문서 1건당 | 언제 바뀌나 |
|---|---|---|---|
| `documents` | 파일 자체 — 파일명 · 저장 경로 · 형식 · 크기 · 상태 · 업로드 시각 | 1행 | 업로드 때 정해지고 안 바뀐다 |
| `extracted_texts` | 뽑아낸 글자 — 본문 · 페이지 수 · 글자 수 · 추출 방법 | 1행 (1:1) | 추출을 다시 하면 바뀐다 |
| `analyses` | AI 결과 — 분석기 종류 · 결과 JSON · 모델명 · 토큰 · 응답 시간 | N행 (1:N) | 분석할 때마다 새로 쌓인다 |

**왜 합치지 않았나**

한 테이블에 넣으면 재분석할 때 이전 결과가 덮인다. `documents.summary` 컬럼을 두지
않은 이유가 그것이다. 모델을 비교해야 하는데 이전 결과가 사라지면 비교할 대상이
없어진다.

**`analyses` 를 1:N 으로 둬서 얻은 것**

- 요약과 분류가 각각 한 행이 된다. `analyzer_type` 으로 구분하므로 분석기를 늘려도
  테이블을 바꾸지 않는다
- `result_json` 이 JSONB 라서 분석기마다 결과 구조가 달라도 된다
- `model_name` · `prompt_version` · `tokens_in` · `tokens_out` · `latency_ms` 를
  함께 기록한다. 본프로젝트에서 자체 모델과 상용 API 를 비교할 원본 데이터다
- `cascade="all, delete-orphan"` 이라 문서를 지우면 자식이 함께 정리된다

**대가**

목록을 불러올 때 쿼리가 `2+2N` 이 된다. 문서 9건에 20개였다. 표시용 값만
`documents` 에 함께 저장하면 2개로 줄어든다. 본프로젝트 과제로 넘겼다.

### Q3. 3조는 데이터 구조가 더 나뉘어 있었는데 왜 더 나눴을까

3조는 **OCR 모델 결과 테이블**과 **대화 내용 결과 테이블**을 따로 뒀다. 스키마를
직접 본 것이 아니라 발표 메모 기준의 추정이지만, 이유는 기능에서 설명된다.

**OCR 결과 테이블이 필요했던 이유** — 3조는 3종을 병렬로 돌려 그중 좋은 것을 골랐다.
그러려면 엔진별 결과를 각각 저장해야 한다. 우리는 비교를 화면에서만 보여주고
저장하지 않으므로 그 테이블이 없다.

**대화 내용 결과 테이블이 필요했던 이유** — 교정 · 요약 · 번역 세 갈래를 돌리니
종류별 결과를 쌓아야 한다. 우리는 `analyses` 한 테이블에 `analyzer_type` 으로
구분해 담았다.

**즉 같은 문제를 다르게 푼 것이다.**

| | 3조 | 우리 |
|---|---|---|
| 방식 | 종류별로 테이블을 나눔 | 한 테이블 + 구분 컬럼 + JSONB |
| 장점 | 컬럼이 명확하고 DB 가 타입을 보장한다 | 테이블 수가 적고 스키마 변경 없이 확장된다 |
| 단점 | 테이블과 조인이 늘어난다 | 타입 보장이 애플리케이션 책임이 된다 |

**어느 쪽이 맞나 — 저장할 결과의 모양이 얼마나 다른가로 갈린다.**

- OCR 결과는 엔진이 달라도 컬럼이 거의 같다 (텍스트 · 글자 수 · 소요 시간 · 신뢰도).
  → **테이블 하나 + `engine` 구분 컬럼**이 낫다
- LLM 결과는 분석기마다 모양이 크게 다르다 (요약은 문장, 분류는 라벨 + 근거,
  번역은 원문 + 역문). → **JSONB** 가 낫다

그래서 본프로젝트 방향은 이렇다. **OCR 결과는 테이블로 승격하고**(지금은 저장하지
않아 추이를 볼 수 없다), **LLM 결과는 현재 구조를 유지한다.**

## 6. 확인한 것

발표 뒤에 확인해 답을 얻은 항목이다.

| 질문 | 답 |
|---|---|
| 1조 시연 영상에 OCR 모델 선택 기능이 있었는가 | 없었다 |
| 3조가 PDF 안에 OCR 별 원문 결과를 넣은 이유 | 넣으면 좋겠다고 생각해서 넣었으나 지저분해서 추후 수정 예정 |
| 3조에서 페이지별 텍스트 / 이미지 영역을 사용자가 수정할 수 있는가 | 수정하지 못한다 |
| 3조의 ground truth 검증 방식 | **미확인.** 궁금해서 적어둔 것이며 아직 답을 못 들었다 |

### 참고 — 1조의 `re.findall` → `re.finditer`

1조는 이 변경으로 PaddleOCR 처리 시간이 급감했다고 했다. 이유로 C++ 기반 작업,
결과 객체 구조, 정규식 부하 감소를 들었는데 **결과 객체 구조 설명이 생략됐다.**

`findall` 은 매칭 전부를 리스트로 만들고 `finditer` 는 필요할 때 하나씩 꺼낸다.
OCR 결과가 크면 객체 생성과 메모리 비용에서 차이가 난다 — 이것이 빠진 설명으로
추정되나 확인은 하지 못했다.

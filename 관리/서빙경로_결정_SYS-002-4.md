# 임베딩 모델 서빙 경로 결정 — `SYS-002-4`

2026-08-24. 담당 김보현. 명세서에서 **유일한 `미결` P1** 이던 항목이다.

기능명세서의 완료 판정은 이렇다.

> 개발·배포 양쪽에서 같은 모델·차원으로 임베딩되고, 모델 이름이
> `document_chunks.embedding_model` 과 일치한다.

## 결정

**`local-model` — 컨테이너 안에서 모델을 직접 로드하는 경로를 표준으로 한다.**

`local-http`(호스트에 별도 서버)는 **컨테이너 메모리를 아껴야 할 때만 쓰는 예외**로
남긴다. 지우지는 않는다.

## 왜 바뀌었나 — 8/20 결정이 뒤집혔다

`관리/현재상태.md` 본문에는 이렇게 적혀 있었다.

> 컨테이너에 sentence-transformers 를 넣지 않기로 결정 — api·worker 각 2.3GB 로
> 가용 메모리를 넘는다

그 판단은 **세현님 어댑터 머지(PR #49)로 전제가 사라졌다.** 코드로 확인한 사실이다.

| 확인한 것 | 근거 |
|---|---|
| `torch`·`sentence-transformers`·`peft` 가 이미 설치된다 | `backend/requirements.txt` 58~60행 |
| 이미지가 11.1GB 다 | 같은 파일 39행 주석 (세현님이 근거를 남겼다) |
| 파인튜닝 어댑터가 저장소에 있다 | `backend/adapters/embedding-hn-v1` · `reranker-v1` |
| 기본값이 이미 직접 로드다 | `app/core/config.py` `EMBEDDING_PROVIDER="local-model"` |
| 직접 로드는 fp16 약 1.2GB 다 | 같은 파일 주석. 2.3GB 는 fp32 기준이었다 |

**컨테이너에 모델을 넣지 않기로 한 결정을 지키려 해도 이미 라이브러리는 들어와
있다.** 서버를 따로 띄워도 이미지 크기는 그대로다. 아끼는 것은 실행 시 메모리뿐이다.

## 결정을 가른 조건 — 시연 방식

사용자 확인(2026-08-24): **발표에서 직접 시연하지 않고 녹화본을 쓴다. 녹화는 GPU 가
있는 PC(세현님)에서 한다.**

이 조건이 결정을 뒤집었다.

| | `local-model` | `local-http` |
|---|---|---|
| 준비 단계 | `docker compose up -d` 하나 | 호스트 서버 + override 파일 **두 개를 짝으로** |
| 실행 시 메모리 | api·worker 각 약 1.2GB | 컨테이너 0, 호스트가 부담 |
| 어댑터 | 저장소에서 바로 읽는다 | 서버 쪽에도 같은 어댑터를 맞춰야 한다 |
| 끊기는 자리 | 없음 | 서버만 죽으면 조용히 연결 거부 |

녹화하는 PC 에 GPU 와 메모리가 있으므로 **단계가 적은 쪽이 낫다.** 서버와 override 는
한 쌍이라 하나만 남기면 실패하는데, 녹화 도중에 그걸 겪으면 다시 찍어야 한다.

## 사용자 PC(GPU 없음)에서는 어떻게 되나

**임베딩은 CPU 에서도 돌아간다.** GPU 가 반드시 필요한 것은 리랭커뿐이고 그것은
기본값이 꺼짐이다(`RERANK_ENABLED=false`).

> ⚠️ CPU 에서 임베딩이 **얼마나 느린지는 재보지 않았다.** 느리다고 단정하지 않는다.
> 청킹처럼 문서 전체를 한 번에 임베딩하는 경로에서 문제가 되면 그때 측정한다.

## 완료 판정의 뒷부분 — 이름 일치가 진짜 함정이다

판정문이 "모델 이름이 `document_chunks.embedding_model` 과 일치한다" 로 끝나는
이유를 실제로 확인했다. **두 경로가 다른 이름을 남긴다.**

| 경로 | 기록되는 이름 | 근거 |
|---|---|---|
| `local-model` | `dragonkue/BGE-m3-ko+embedding-hn-v1` | `app/embedding/local_model_client.py` `model_name` — 어댑터 이름을 붙인다 |
| `local-http` | `dragonkue/BGE-m3-ko` | `app/embedding/local_client.py` `model_name` — 설정값 그대로 |

검색은 `WHERE embedding_model = 지금 쓰는 모델` 로 걸린다. 그래서 —

**한 경로로 색인한 뒤 다른 경로로 검색하면 에러 없이 0건이다.**

경로를 바꾸면 그 모델로 만든 청크를 지우고 다시 색인해야 한다. 검색이 0건일 때
가장 먼저 볼 것:

```sql
SELECT embedding_model, count(*) FROM document_chunks GROUP BY 1;
```

## 함께 고친 것 — override 파일이 무력해져 있었다

`도구/docker-compose.override.yml` 은 실제 임베딩을 붙일 때 쓰는 파일인데
**`EMBEDDING_PROVIDER` 를 지정하지 않았다.** 기본값 `local-model` 이 이기므로,
호스트에 서버를 띄워 두고 이 파일을 넣어도 **컨테이너가 모델을 직접 올렸다.**
에러가 나지 않아 알아채기 어렵고 메모리만 조용히 먹는다.

`EMBEDDING_PROVIDER: "local-http"` 를 넣어 고쳤다(2026-08-24).

## 남은 위험

- **모델을 바꾸면 전체 재색인이 필요하다.** 어댑터를 교체하는 것도 이름이 바뀌므로
  같다. 바꾸기 전에 청크 수를 확인한다
- api 와 worker 가 **각각** 모델을 올린다. 8GB 카드에서 리랭커까지 켜면 모자란다
  (임베딩 fp16 1.2GB × 2 + 리랭커 fp32 2.3GB). 호스트에서 Ollama 가 GPU 를 잡고
  있으면 시스템 메모리로 밀려 **에러 없이 크게 느려진다**
- `USE_FAKE_EMBEDDING` 기본값은 `true` 로 둔다. 이 결정은 "실제로 쓸 때 어느 경로냐"
  이고, 기본을 가짜로 두는 안전장치와 충돌하지 않는다

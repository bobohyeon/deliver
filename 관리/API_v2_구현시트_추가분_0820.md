## 2. 공통 응답 `SearchResponse` — 시트 칸에 안 들어가서 따로 적는다

`#36`~`#38` 이 **같은 응답 스키마**를 쓴다. 엔드포인트를 셋으로 나눴지만 계약은
갈리지 않았다 — 어느 방식으로 걸렸는지는 `match_kind` 로만 드러난다.

```
{ query, searched_project_ids[], embedding_model, took_ms, total, results[] }
```

`results[]` 의 각 항목 —

| 필드 | 뜻 |
|---|---|
| `chunk_id` · `document_id` · `document_filename` · `project_id` · `project_name` | 출처 |
| `seq` | 문서 내 조각 순서. **0부터** (화면은 +1 해서 보여준다) |
| `page_number` | 없을 수 있다 |
| `similarity` | **⚠ 뜻이 `match_kind` 에 따라 다르다** — 아래 |
| `snippet` | 원문 인용. 의미 검색은 앞 220자, 키워드는 매치 주변 160자 |
| `char_count` | 청크 전체 길이. `snippet` 이 잘렸는지 판단용 |
| `content_start` · `content_end` | 원문 강조용 구간. 모르면 `null` |
| `match_kind` | `"vector"` · `"keyword"` · `"both"`. 의미 검색은 `null` |
| `match_count` | 검색어가 그 조각에 몇 번 나오나 |
| `match_offset` | `snippet` 안에서 검색어가 시작하는 위치 |
| `fused_score` · `vector_rank` · `keyword_rank` | 하이브리드만 |

**프런트가 반드시 알아야 하는 것 셋**

1. **`similarity` 를 무조건 "유사도 N%" 로 쓰면 안 된다.** `vector`·`both`·`null` 은
   코사인 유사도지만 **`keyword` 는 트라이그램 낱말 유사도**다(실측: 정확일치 `1.0` ·
   조사붙음 `0.8` · 불일치 `0`). 뜻이 다른 값을 같은 이름으로 부르면 안 된다.
2. **`fused_score` 는 유사도가 아니다.** 크기 자체에 뜻이 없고 서로 비교할 때만
   뜻이 있다(약 0.016 부터). 백분율로 표시하면 안 된다.
3. **`match_offset` 은 파이썬 코드포인트 기준이다.** JavaScript 는 UTF-16
   코드유닛으로 세므로 BMP 밖 문자(이모지 · 확장 한자 `𠀋`)가 앞에 있으면 어긋나
   **서로게이트 반쪽이 잘린다**(재현했다). 쓰기 전에 그 자리에 검색어가 있는지
   확인하고, 어긋나면 스니펫에서 직접 찾는다.

`embedding_model` 이 **`fake-hash-v1`** 이면 개발용 가짜 임베딩이라 의미 검색 순서에
뜻이 없다.

## 4. ⚠ 기능 ID 표기가 시트와 다르다 — 결정이 필요하다

**시트는 옛 2단 ID(`SYS-02`·`VIS-01`·`REV-05`)를 쓰고 있다.** 기능명세서가 8/19 에
v5 로 통합되면서 **3단(`SRH-001`·`DSH-001`·`REV-004-1`)으로 바뀌었다.**

위 CSV 는 **v5 로 적었다.** 근거 — 기능명세서가 현재 진실이고, 팀 레포 코드의 주석도
8/20 에 63곳을 v5 로 갱신했다(PR #38). 시트만 옛 ID 로 남으면 세 곳의 표기가
갈린다.

**다만 시트 전체를 바꾸는 것은 팀과 정해야 한다.** 세 갈래가 있다.

| | 방법 | 평가 |
|---|---|---|
| **A** | 추가분만 v5 로 쓰고, 기존 35행은 나중에 한 번에 | **지금 이 문서가 이 방식이다.** 섞이지만 되돌리기 쉽다 |
| B | 추가분도 옛 ID 로 맞춘다 | 시트 안은 일관되지만 명세서·코드와 갈린다 |
| C | 시트 전체를 v5 로 바꾼다 | 가장 깔끔하다. 35행을 대조해야 하고 **`RAG`·`VIS` 외에는 1:1 매핑이 없다**(기능명세서 부록 B) |

옛 ID 를 각 행 비고에 병기해 두면 어느 쪽으로 가도 찾을 수 있다. 대응은 아래와 같다.

| 이 문서의 v5 ID | 시트의 옛 ID | 작업명 |
|---|---|---|
| `SRH-001` | `RAG-04` | 의미 검색 |
| `SRH-003` | `VIS-06` | 키워드 검색(통합 검색) |
| `SRH-004` | `RAG-05` | 키워드·의미 결합 |
| `SRH-002-3` | `RAG-12` | 유사 사업 단가 선례 |
| `RAG-002-2` | `RAG-10` | 검색 품질 측정 |
| `DSH-001` | `VIS-01`·`VIS-02` | 프로젝트 핵심 현황 |
| `REV-004-1` | `REV-05` | OCR 텍스트 수정 |
| `DOC-001-2` | `DOC-06`·`DOC-07` | 비동기 처리·재시도 |

> **`REV-004-1` 과 `DOC-001-2` 는 재정님 파트다.** 코드에서 계약(요청·응답·오류)은
> 정확히 읽었지만, **기능 ID 대응은 내가 추정한 것**이다. 부록 B 가 `REV`·`DOC`
> 접두어는 1:1 매핑이 없다고 명시하므로 **재정님 확인이 필요하다.** 확인 전에는
> 그 두 칸을 비워 두는 것도 방법이다.

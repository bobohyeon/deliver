## 1. 결론

| | |
|---|---|
| **정한 것** | `pgvector` 컬럼을 **`vector(1024)`** 로 한다 |
| **쓸 모델** | **`dragonkue/BGE-m3-ko`** (한국어 튜닝 · 1024차원 · apache-2.0) |
| **대안** | `nlpai-lab/KURE-v1`(mit) · `snowflake-arctic-embed-l-v2.0`(apache-2.0). **차원이 같아 DB 를 안 건드리고 바꿔 끼울 수 있다** |
| **안 쓰는 것** | `e5` 3종 · `nomic`(768) · `Qwen3-Embedding-0.6B` |
| **한 줄 근거** | 뜻으로만 찾아야 하는 질문 **64개 중 41개**를 top5 에 넣었다. 2위는 37개, 최하위는 18개 |
| **이 결정으로** | 리비전 `0011`(pgvector · `document_chunks`)을 만들 수 있다 |
| **확인된 것** | **차원이 높으면 좋다는 것은 성립하지 않는다.** 1024인 `e5-large` 가 9종 중 최하위다 |
| **주의** | 채택 모델은 **Ollama 공식 라이브러리에 없다.** GGUF 로 등록해야 한다 (6절) |

**차원을 몰라서 마이그레이션을 미뤄뒀던 것이 이 시험의 목적이었다.**
`RAG-03` 비고에 "차원은 임베딩 모델 확정 후" 라고 적어둔 그것이다.

## 2. 용어 — 이 문서를 읽는 데 필요한 만큼만

| 용어 | 쉬운 말 | 이 시험에서 |
|---|---|---|
| **임베딩** | 글을 숫자 목록으로 바꾸는 것. **뜻이 비슷하면 숫자도 비슷해진다** | 문서 조각 649개와 질문 133개를 숫자로 바꿨다 |
| **벡터** | 그 숫자 목록 | `[0.12, -0.83, 0.31, …]` |
| **차원** | 숫자가 **몇 개**인가 | 1024개짜리 다섯, 768개 둘, 384개 하나 |
| **청크** | 문서를 잘라놓은 **조각** | 문서 10건 → 649조각 (평균 305자) |
| **유사도** | 두 숫자 목록이 얼마나 닮았나 (0~1) | 0.79 면 꽤 닮은 것 |
| **`top5`** | 질문과 가장 닮은 조각 **5개** | 649개를 줄 세운 뒤 앞 5개 |
| **`R@5`** | **top5 안에 정답이 있었나.** 있으면 1점 | 64문항 중 41문항 → 0.641 |
| **`R@1`** | **1등이 정답이었나.** 더 엄격한 자 | R@5 보다 항상 낮거나 같다 |
| **`R@10`** | top10 안에 있었나. 더 느슨한 자 | |
| **`MRR`** | 정답이 **몇 등이었나**를 점수로. 1등 1점 · 2등 0.5점 · 5등 0.2점 | 순위가 위일수록 높다 |
| **`gold`** | **사람이 미리 정해둔 정답 조각 번호** | 내가 조각을 읽고 지정했다 |
| **`overlap`** | 질문에 정답 조각의 **단어가 그대로 들어 있다** | 지금 쓰는 키워드 검색으로도 찾힌다 |
| **`no_overlap`** | 질문에 그 단어가 **하나도 없다** | **뜻으로만 찾아야 한다. 이게 핵심** |
| **`pgvector`** | PostgreSQL 이 벡터를 저장·검색하게 해주는 확장 | 여기 컬럼 차원을 정하는 것이 이번 목적 |

### 자바·Spring 로 바꿔 말하면

| 이번 개념 | Spring 쪽 대응 |
|---|---|
| 임베딩 | `hashCode()` 인데 **"비슷한 객체는 비슷한 값"** 이 나오는 해시 |
| 벡터 검색 | `map.get(key)` 가 아니라 **"키가 가장 비슷한 것"** 을 찾는 조회 |
| 차원 | 테이블 컬럼 타입. `vector(1024)` 는 `NUMERIC(10,2)` 처럼 **스키마에 박힌다** |
| 차원 변경 | 컬럼 타입 변경 + **전체 데이터 재생성**. 그래서 미리 정한다 |
| `R@5` | 통합테스트의 `assertTrue(result.contains(expected))` |
| `MRR` | 위 assert 를 통과했는지가 아니라 **몇 번째로 나왔는지**까지 보는 것 |
| 모델 교체 | 구현체 갈아 끼우기. **접두어를 코드에 박으면 안 되는 이유가 이것이다** |

## 3. 누가 무엇을 정했나 — **모델은 정답을 모른다**

"모델이 스스로 top 을 지정했다" 는 아니다. **역할이 셋으로 나뉜다.**

```
사람(나)이 한 일                        모델이 한 일
──────────────────────────────────────────────────────────────
1  문서 10건을 649조각으로 자른다
2  조각을 읽고 그 조각이 답이 되는
   질문을 만든다
3  정답 번호를 적는다   gold = 630
                                        4  조각 649개를 각각 숫자로 바꾼다
                                        5  질문도 숫자로 바꾼다
                                        6  질문과 닮은 순서로 649개를
                                           줄 세운다
                                           -> 그 앞 5개가 top5

채점 코드가 한 일
──────────────────────────────────────
7  top5 안에 630 이 있나?  있으면 "맞춤"
```

**모델이 하는 일은 6번, 줄 세우기뿐이다.** 정답이 무엇인지 모른다.
정답은 **내가 조각을 읽고 정했고**, 맞았는지 대조하는 것은 채점 코드다.

| 오해 | 실제 |
|---|---|
| 모델이 정답을 골랐다 | 모델은 **649개를 닮은 순서로 줄 세웠을 뿐**이다 |
| 모델이 top 을 지정했다 | top5 는 그 줄의 **앞 5칸**을 잘라낸 것이다 |
| 모델이 채점했다 | 채점은 `run_eval.py` 가 `gold` 와 대조해서 한다 |

Spring 으로 보면 **모델은 `Comparator` 이고, `gold` 는 테스트의 `expected` 값**이다.
`Comparator` 는 무엇이 정답인지 모른 채 정렬만 한다.

## 4. 후보 9종 — 각자 답하는 질문이 있다

| 모델 | 차원 | **이 모델이 답하는 질문** |
|---|---|---|
| `BAAI/bge-m3` | 1024 | **기준선.** 한국어 튜닝이 이걸 못 이기면 튜닝할 이유가 없다 |
| `nlpai-lab/KURE-v1` | 1024 | 한국어 특화(고려대)가 효과 있나. bge-m3 기반이라 조건이 같다 |
| **`dragonkue/BGE-m3-ko`** | 1024 | **다른 한국어 튜닝은 다른가.** 같은 bge-m3 기반, 다른 제작자 |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | 1024 | **다국어 최신 모델이 한국어 튜닝을 이기나** |
| `nomic-ai/nomic-embed-text-v2-moe` | 768 | 768차원 · MoE 구조로 충분한가 |
| `Qwen/Qwen3-Embedding-0.6B` | 1024 | **디코더 계열이 인코더보다 나은가** |
| `intfloat/multilingual-e5-base` | 768 | 같은 계열 안에서 차원만 다르면 어떻게 되나 |
| `intfloat/multilingual-e5-large` | 1024 | 위와 같은 축의 상단 |
| `dragonkue/multilingual-e5-small-ko-v2` | 384 | **작은 모델로 충분한가.** CPU 로 감당되는가 |

```
축 1  한국어 튜닝 효과   ->  bge-m3 대 KURE-v1 · BGE-m3-ko
축 2  다국어 최신 대 한국어 튜닝  ->  arctic 대 KURE-v1 · BGE-m3-ko
축 3  같은 계열의 차원   ->  e5 384 · 768 · 1024
축 4  구조 (인코더 대 디코더)  ->  bge 계열 대 Qwen3
```

`e5` 셋을 넣은 이유는 **차원 효과와 계열 효과를 분리**하기 위해서다.
같은 학습 조건 안에서 차원만 다른 비교가 여기서만 가능하다.

## 6. 그래서 왜 `BGE-m3-ko` 인가

| | 근거 | 수치 |
|---|---|---|
| 1 | **모든 지표에서 1위다** | R@1·R@3·R@5·R@10·MRR × 겹침·안겹침·전체 **8칸 전부** |
| 2 | 2위와 4문항 차 | 안겹침 41 대 37 |
| 3 | 순위를 더 위로 올린다 | 안겹침 `MRR` 0.503 대 0.457 |
| 4 | 공개 벤치마크도 뒷받침한다 | MTEB-ko-retrieval **2위** (1위는 KURE-v1) |
| 5 | 라이선스가 깨끗하다 | **apache-2.0** — 상업 이용 가능 |
| 6 | 되돌리기가 싸다 | 대안 둘과 **차원이 같아 DB 를 안 건드리고 교체 가능** |

### 근거의 한계를 먼저 적는다

**미리 정해둔 판정선을 넘지 못했다.** 측정 전에 이렇게 정했다 —
안겹침 64문항에서 6문항 이상 차이면 실제 차이, 3문항 이하면 판별 불가.

**BGE-m3-ko 는 KURE-v1 을 4문항 앞섰다. "참고" 구간이다.**

같은 질의에 대한 적중을 맞대어 검정한 결과다.

| 대비 | 엇갈린 문항 | 양측 p | 판정 |
|---|---|---|---|
| BGE-m3-ko 대 KURE-v1 · 안겹침 64 | 6 (5 대 1) | **0.22** | 유의하지 않다 |
| BGE-m3-ko 대 KURE-v1 · 전체 133 | 9 (8 대 1) | **0.039** | **유의하다** |
| KURE-v1 대 bge-m3 · 안겹침 64 | 12 (7 대 5) | **0.77** | **구별 불가** |

**안겹침 64문항 중 6개만 엇갈렸고 58개는 KURE 와 똑같이 움직였다.**
그런데도 1위로 적는 근거는 **8칸 전부에서 1위이고 전체 질의로는 유의하기
때문**이다. 한 지표만 튄 것이 아니다.

**2·3·4위(KURE-v1 · arctic · bge-m3)는 서로 구별되지 않는다.**
그래서 대안 둘은 형식적인 대안이 아니라 **실제로 바꿔 써도 되는 후보**다.

### 384차원을 안 쓰는 이유가 결론보다 중요하다

```
e5-small-ko-v2   단어 겹침 문항   64 / 69   ->  9종 중 1위
                 뜻으로만 문항    19 / 64   ->  9종 중 8위
```

**작은 모델은 글자가 겹칠 때만 잘한다.** 그건 지금 쓰는 키워드 검색이
이미 하는 일이다. 뜻으로 건너뛰는 능력이 약하다.

**만약 `단어 겹침` 만 재고 모델을 골랐다면 384차원을 뽑았을 것이다.
그리고 뜻으로 묻는 질문의 70%를 놓쳤을 것이다.**

거꾸로 이것이 **하이브리드 검색(RAG-05)** 의 근거다. 낱말 일치는 낱말 일치가
잘하는 일을 하고, 벡터는 벡터가 잘하는 일을 한다. 둘을 합쳐야 두 유형을
모두 잡는다.

### 차원이 높으면 좋다는 것은 성립하지 않는다

흔히 보는 차원 표(384 경량 · 768 표준 · 1024 고성능)는 **같은 계열 안에서도
성립하지 않았다.** 같은 `e5` 계열 셋을 재서 확인했다.

| 차원 | 모델 | 계열 | 뜻으로만 (64문항) |
|---|---|---|---|
| 384 | `e5-small-ko-v2` | e5 · **한국어 튜닝** | 19 |
| **768** | `e5-base` | e5 · 다국어 원본 | **22** |
| **1024** | **`e5-large`** | e5 · 다국어 원본 | **18 (9종 중 최하위)** |

**차원을 768 에서 1024 로 올렸는데 점수가 내려갔다.**
`e5-large` 는 1024차원인데 384차원 모델보다도 낮다.

상세 결과에 단서는 있다. 질의가 달라도 같은 조각 묶음이 반복해서 1위로 올라온다.

```
e5-large / 뜻으로만 / top5 = 374,300,273,144,186
e5-large / 뜻으로만 / top5 = 374,300,186,144,408
e5-large / 뜻으로만 / top5 = 300,374,273,186,144
```

**이것은 관찰이고 원인이 아니다.** 토큰 잘림 가설과 특정 조각 편향 가설은 둘 다
확인 과정에서 기각됐다. 잘린 조각은 애초에 없었다(9절).

**그래도 `vector(1024)` 는 유지한다.** 상위 4위가 모두 1024이고 768(27·22)과
384(19)는 그보다 낮다. `e5-large` 는 계열 안의 이상값이다.

### "한국어 특화면 낫다" 도 그대로는 성립하지 않는다

차원을 1024 로 고정하고 계열만 바꿔 비교했다.

| 모델 | 성격 | 뜻으로만 R@5 |
|---|---|---|
| **`BGE-m3-ko`** | bge-m3 **한국어 튜닝** | **41** |
| `KURE-v1` | bge-m3 **한국어 특화** | 37 |
| `arctic-l-v2.0` | **다국어** 최신 | 37 |
| `bge-m3` | **다국어** 원본 | 35 |
| `e5-large` | 다국어 원본 | 18 |

**같은 원본에서 갈라진 한국어 튜닝 둘이 41 과 37 로 다르다.**
그리고 **다국어 `arctic` 이 한국어 특화 `KURE-v1` 과 동점(37)** 이다.
`KURE-v1`(37)과 다국어 원본 `bge-m3`(35)는 **구별되지 않는다**(p=0.77).

| 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|
| `BGE-m3-ko` 의 한국어 튜닝은 원본을 **6문항** 앞섰다 | "한국어 특화 모델이면 다국어보다 낫다" |
| 튜닝이 효과를 낸 사례가 **있다** | 그 효과가 **한국어 특화라는 범주에서 온다** |

**결론 — 범주로 고르지 말고 개별 모델을 재야 한다.**
이름에 `ko` 가 붙었다고 나은 것이 아니고(384 한국어판이 8위다),
다국어라고 못한 것도 아니다(`arctic` 이 2위다).

### 컬럼 차원은 1024 로 확정

`pgvector` 는 차원이 **정확히** 맞아야 한다. 그래서 컬럼 차원이 쓸 수 있는
모델을 가른다.

| 차원 | 후보 | 판단 |
|---|---|---|
| **1024** | `BGE-m3-ko` · `KURE-v1` · `arctic` · `bge-m3` · `Qwen3` | **다섯을 서로 바꿔 끼울 수 있다** |
| 768 | `nomic-v2-moe` · `e5-base` | `vector(1024)` 에 그대로 못 넣는다 |
| 384 | `e5-small-ko-v2` | 같음 |

**상위 4위가 전부 1024 안에 있다.** 768 로 정하면 그 넷을 다 잃는다.

### 라이선스 — 후보 9종 전부 확인, 걸러지는 것 없음

허브 모델 카드의 `license` 필드를 직접 읽었다. AI 요약이나 블로그가 아니다.

| 라이선스 | 모델 |
|---|---|
| **apache-2.0** | `BGE-m3-ko`(채택) · `arctic-l-v2.0` · `nomic-v2-moe` · `Qwen3` |
| **mit** | `KURE-v1` · `bge-m3` · `e5` 3종 |

원본 `bge-m3` 가 MIT 인데 파생본 `BGE-m3-ko` 가 apache-2.0 인 것은 문제없다.
MIT 는 재라이선싱을 막지 않는다. **상업 이용에 지장 없다.**

같은 연구실의 `KULLM3` 가 **CC-BY-NC**(비상업)라 확인이 필요했는데,
`KURE` 는 MIT 다. **이름이 비슷하다고 같은 라이선스라고 볼 수 없다.**

### 채택 모델의 배포 경로에 작업이 하나 붙는다

**`BGE-m3-ko` 는 Ollama 공식 라이브러리에 없다.** 허깅페이스 전용 모델이라
**GGUF 파일을 내려받아 `Modelfile` 로 직접 등록**해야 한다.

| 후보 | 배포 작업 |
|---|---|
| `bge-m3` · `arctic-l-v2.0` · `nomic-v2-moe` · `Qwen3` | `ollama pull` 한 줄 |
| **`BGE-m3-ko`** (채택) | GGUF 내려받기 → `ollama create` → 태그 관리 |
| `KURE-v1` | `ollama pull daynice/kure-v1` (비공식 저장소) |

**채택을 뒤집는 사유는 아니다.** 한 번 등록해 두면 이후는 같다. 다만
**임베딩 생성·저장(RAG-02) 에 "모델 등록" 작업이 하나 늘어난다.**
그것을 모르고 일정을 잡으면 막힌다.

**공식 경로가 꼭 필요하면 `arctic-embed-l-v2.0` 이 `ollama pull` 한 줄로 끝난다.**
안겹침 37문항으로 채택 모델과 4문항 차이고 통계적으로 구별되지 않는다.

**GGUF 는 양자화본이라 우리가 잰 점수와 다를 수 있다. 그건 안 쟀다.**

## 7. 실제로 어떻게 판단했나 — 예시 둘

### 맞춘 예 — 이게 `RAG-04` 다

**내가 읽은 구절** (630번 조각, 행정안전부고시 별표 2)

```
사업규모별 제안서 평가위원 수 (제30조제2항 관련)
  사업예산액   1억원 미만 / 1억원이상~50억원 미만 / 50억원 이상
  위원수       7명 이상   /  8명 이상            /  9명 이상
```

**내가 만든 질문**

```
"심사할 사람을 몇 명 모아야 하나"

  제안서 평가위원 -> 심사할 사람     위원수 -> 몇 명
  630번 조각의 단어를 하나도 쓰지 않았다   (no_overlap)
```

**내가 적은 정답** — `gold = 630`

**모델이 줄 세운 결과** (649개 중 앞 5개)

| 모델 | top5 | 정답 위치 | |
|---|---|---|---|
| **BGE-m3-ko** | `630, 591, 585, 595, 24` | **1등** | 맞춤 |
| bge-m3 | `630, 591, 595, 585, 24` | **1등** | 맞춤 |
| KURE-v1 | `591, 630, 595, 585, 24` | **2등** | 맞춤 |
| e5-small-ko-v2 (384) | `585, 13, 431, 48, 43` | **10등 안에도 없음** | **놓침** |

**"평가위원" 이라는 말을 몰라도 "심사할 사람" 으로 물어서 찾았다.**
`RAG-04` 완료 판정 기준이 "글자가 하나도 겹치지 않는 질의로 관련 문서가
나온다" 이므로, **이 문항 하나가 그 증거다.** 발표에서 보여줄 사례로 쓸 수 있다.

**그리고 384차원이 이 문항을 놓친 것이 6절 표의 실체다.**

### 틀린 예 — 숫자에는 약하다

**질문** `"사업금액 578600000원"` — `gold = 7`
(단어가 그대로 겹치는 쉬운 문항이다)

| 모델 | top5 | 정답 위치 |
|---|---|---|
| BGE-m3-ko | `520, 527, 530, 498, 516` | **10등 안에도 없음** |
| KURE-v1 | `527, 520, 530, 526, 497` | **10등 안에도 없음** |
| bge-m3 | `527, 520, 525, 498, 526` | **10등 안에도 없음** |

**앞에 온 것들이 전부 다른 문서의 금액 조각이었다.**
숫자를 물었는데 다른 숫자로 끌려간다. **조각을 5배로 늘리자 더 나빠졌다** —
127조각일 때는 384차원 모델이 4등으로 잡았는데 지금은 아무도 못 잡는다.

이것이 **하이브리드 검색(RAG-05)** 이 필요한 근거다. 기능명세서 완료 판정이 이미
"고유명사·코드번호 검색에서 벡터 단독보다 정확하다" 로 적혀 있었고,
**이번 시험이 그 근거를 수치로 채웠다.** 키워드 쪽은 **통합 검색(VIS-06,
PostgreSQL FTS)** 과 결합하라고 비고에 지정되어 있다.

## 8. 이 시험으로 알게 된 것 여섯 개

| | 알게 된 것 | 어디에 쓰나 |
|---|---|---|
| 1 | **`vector(1024)`** 로 간다 | 리비전 `0011` 착수 근거 |
| 2 | `top-k` 는 **5 이상**이어야 한다. 1등만 보면 절반도 못 맞춘다 (R@1 25 대 R@5 41) | `RAG-04` 구현 기본값 |
| 3 | **숫자·코드번호는 벡터가 약하다** | `RAG-05` 하이브리드 근거 |
| 4 | **같은 모델이 겹침 1위 · 안겹침 8위를 동시에 한다** | `RAG-05` 를 P0 로 볼 근거 |
| 5 | 문서 격리는 **벡터가 아니라 `project_id` 조건**이 한다 | `PRJ-08` · `RAG-04` |
| 6 | **모델 교체를 위해 컬럼과 설정을 미리 준비해야 한다** | `document_chunks.embedding_model` · 접두어 설정 분리 |

6번이 이번에 새로 추가됐다. 후보 다섯이 모두 1024차원이므로 **컬럼을 안 건드리고
벡터만 다시 만들면 모델을 바꿀 수 있다.** 그것을 가능하게 하는 조건은
`관리/API_계약_RAG_검색_초안.md` 7-1절에 규정했다.

## 9. 믿을 수 있는 수치인가

### 8월 11일 판에서 뒤집힌 것

**표본을 키우자 결론 두 개가 바뀌었다.** 작은 표본의 결론을 그대로 들고 가면
안 된다는 사례로 남긴다.

| | 8월 11일 판 (127조각 · 73질의) | **8월 13일 판 (649조각 · 133질의)** |
|---|---|---|
| **기본 모델** | `KURE-v1` | **`BGE-m3-ko`** (당시엔 후보에 없었다) |
| **384 대 768** | 384 한국어판(14)이 768 원본(13)을 **이겼다** | **뒤집혔다.** 384(19) < 768(22) |
| **한국어 특화 효과** | "확인됐다" — KURE(27) > e5-large(23) | **범주로는 성립 안 한다.** 다국어 arctic(37) = KURE(37) |
| `e5-large` | 23 / 34 (중위) | **18 / 64 (최하위)** |
| KURE 대 bge-m3 | 1문항 차 · "판별 불가" 로 서술 | **검정으로 확인** (p=0.77) |

**"한국어 튜닝이 차원 2배보다 크다" 는 8월 11일 판의 서술은 철회한다.**
근거였던 `384 한국어판 > 768 원본` 이 표본을 키우니 반대로 나왔다.

### 회차 기록

| 회차 | 조각 | 질의 | 모델 | 무엇을 바꿨나 |
|---|---|---|---|---|
| 1~3차 | 127 | 78 → 73 | 3 | 정답을 좁게 잡은 것 수정 · 라벨 위반 수정 |
| 4차 | 127 | 73 | 5 | `e5-base`·`e5-large` 추가 — 차원과 계열 분리 |
| **5차** | **649** | **133** | **9** | **문서 10건 · 고시 질의 60개 추가 · 후보 4종 추가** |

5차에서 늘린 것은 조각뿐이 아니다. **질의를 73 → 133 (안겹침 34 → 64)로 늘린
것이 핵심이다.** 조각만 늘리면 방해물만 늘고 순위는 안 바뀐다. 4차에서 조각을
4.3배 늘렸을 때 KURE 와 bge-m3 의 격차가 1문항 그대로였던 것이 그 증거다.

### 재현성이 확인됐다

같은 코퍼스·질의로 두 번 돌렸더니 품질 수치가 **완전히 같았다.**

| 모델 | 8모델 실행 | 3모델 실행 |
|---|---|---|
| `KURE-v1` 안겹침 R@5 | 0.578 | **0.578** |
| `BGE-m3-ko` 안겹침 R@5 | 0.641 | **0.641** |

**품질은 결정적이다.** 모델 간 격차를 실행 잡음으로 의심할 필요가 없다.
**반대로 비용은 흔들렸다** — `KURE-v1` 을 세 번 재서 47.5 · 56.1 · 77.7초가 나왔다.

### 같은 조건이란 세 가지다 — 하나를 놓쳤다

| | 조건 | 이번 시험 |
|---|---|---|
| 1 | **접두어** — 모델이 선언한 값을 그대로 쓴다 | 맞췄다 |
| 2 | **최대 입력 길이** — 잘림이 없는지 토큰으로 확인 | 맞췄다. **512토큰 초과 조각 0개** |
| 3 | **정밀도(dtype)** | **놓쳤다.** `Qwen3` 만 `bfloat16` 이었다 |

3번 때문에 `Qwen3` 를 처음에 "70배 느려 측정 불가" 로 적었다. `float32` 로
맞추자 **26배 빨라졌고** 실제 격차는 2~2.5배였다. 파라미터 수가 596M 대 568M 로
거의 같으니 애초에 70배가 날 이유가 없었다.

**`Qwen3` 는 최종적으로 품질에서 떨어졌다**(안겹침 27 대 41). 결론은 같지만
**근거가 바뀌었다.** 처음 근거로 제출했다면 검토에서 반박당했을 것이다.

### 이 수치를 쓸 때 주의할 것

| | 주의 |
|---|---|
| 1 | **본구현 검색 품질 예측치로 쓰면 안 된다.** 조각을 자르는 방식이 다르다 (이번은 글자 수, `RAG-01` 은 토큰 수 · `element_type`) |
| 2 | **속도 순위를 매기지 않는다.** 같은 모델이 실행마다 47.5~77.7초로 흩어졌다 |
| 3 | **양자화본으로 배포할 예정인데 fp32 로 쟀다.** 그 차이를 안 쟀다 |
| 4 | 문서 하나(조달청 질의응답)가 코퍼스의 **46%** 다 |
| 5 | **필터 없이 전량 검색했다.** 실사용은 `project_id` 로 좁혀져 더 쉬워진다 |

## 10. 한 문장

> **글자가 하나도 겹치지 않는 질문 64개 중 `BGE-m3-ko` 가 41개를 top5 에 넣었고
> 최하위 모델은 18개였다. 그래서 `pgvector` 를 `vector(1024)` 로 정하고
> `BGE-m3-ko` 를 기본 모델로 둔다. 모델은 나중에 바꿀 수 있지만 차원은 못 바꾼다.**

## 1. 결론

| | |
|---|---|
| **정한 것** | `pgvector` 컬럼을 **`vector(1024)`** 로 한다 |
| **쓸 모델** | `nlpai-lab/KURE-v1` (고려대 · 한국어 검색 특화 · 1024차원) |
| **대안** | `BAAI/bge-m3` (차원이 같아 **DB 를 안 건드리고 바꿔 끼울 수 있다**) |
| **안 쓰는 것** | `multilingual-e5-small-ko-v2` (384차원) |
| **한 줄 근거** | 뜻으로만 찾아야 하는 질문 34개에서 **1024차원이 27개, 384차원이 14개** 맞췄다 |
| **이 결정으로** | 리비전 `0010`(pgvector · `document_chunks`)을 만들 수 있다 |

**차원을 몰라서 마이그레이션을 미뤄뒀던 것이 이 시험의 목적이었다.**
`RAG-03` 비고에 "차원은 임베딩 모델 확정 후" 라고 적어둔 그것이다.

## 2. 용어 — 이 문서를 읽는 데 필요한 만큼만

| 용어 | 쉬운 말 | 이 시험에서 |
|---|---|---|
| **임베딩** | 글을 숫자 목록으로 바꾸는 것. **뜻이 비슷하면 숫자도 비슷해진다** | 문서 조각 127개와 질문 73개를 숫자로 바꿨다 |
| **벡터** | 그 숫자 목록 | `[0.12, -0.83, 0.31, …]` |
| **차원** | 숫자가 **몇 개**인가 | 1024개짜리 모델 둘, 384개짜리 하나 |
| **청크** | 문서를 잘라놓은 **조각** | 문서 5건 → 127조각 |
| **유사도** | 두 숫자 목록이 얼마나 닮았나 (0~1) | 0.79 면 꽤 닮은 것 |
| **`top5`** | 질문과 가장 닮은 조각 **5개** | 127개를 줄 세운 뒤 앞 5개 |
| **`R@5`** | **top5 안에 정답이 있었나.** 있으면 1점 | 34문항 중 27문항 → 0.794 |
| **`R@1`** | **1등이 정답이었나.** 더 엄격한 자 | R@5 보다 항상 낮거나 같다 |
| **`R@10`** | top10 안에 있었나. 더 느슨한 자 | |
| **`MRR`** | 정답이 **몇 등이었나**를 점수로. 1등 1점 · 2등 0.5점 · 5등 0.2점 | 순위가 위일수록 높다 |
| **`gold`** | **사람이 미리 정해둔 정답 조각 번호** | 내가 조각을 읽고 지정했다 |
| **`overlap`** | 질문에 정답 조각의 **단어가 그대로 들어 있다** | 지금 쓰는 키워드 검색으로도 찾힌다 |
| **`no_overlap`** | 질문에 그 단어가 **하나도 없다** | **뜻으로만 찾아야 한다. 이게 핵심** |
| **`pgvector`** | PostgreSQL 이 벡터를 저장·검색하게 해주는 확장 | 여기 컬럼 차원을 정하는 것이 이번 목적 |

### 자바·Spring 로 바꿔 말하면

| 이번 개념 | Spring 쪽 대응 |
|---|---|
| 임베딩 | `hashCode()` 인데 **"비슷한 객체는 비슷한 값"** 이 나오는 해시 |
| 벡터 검색 | `map.get(key)` 가 아니라 **"키가 가장 비슷한 것"** 을 찾는 조회 |
| 차원 | 테이블 컬럼 타입. `vector(1024)` 는 `NUMERIC(10,2)` 처럼 **스키마에 박힌다** |
| 차원 변경 | 컬럼 타입 변경 + **전체 데이터 재생성**. 그래서 미리 정한다 |
| `R@5` | 통합테스트의 `assertTrue(result.contains(expected))` |
| `MRR` | 위 assert 를 통과했는지가 아니라 **몇 번째로 나왔는지**까지 보는 것 |

## 3. 누가 무엇을 정했나 — **모델은 정답을 모른다**

"모델이 스스로 top 을 지정했다" 는 아니다. **역할이 셋으로 나뉜다.**

```
사람(나)이 한 일                        모델이 한 일
──────────────────────────────────────────────────────────────
1  문서 5건을 127조각으로 자른다
2  조각을 읽고 그 조각이 답이 되는
   질문을 만든다
3  정답 번호를 적는다   gold = 24
                                        4  조각 127개를 각각 숫자로 바꾼다
                                        5  질문도 숫자로 바꾼다
                                        6  질문과 닮은 순서로 127개를
                                           줄 세운다
                                           -> 그 앞 5개가 top5

채점 코드가 한 일
──────────────────────────────────────
7  top5 안에 24 가 있나?  있으면 "맞춤"
```

**모델이 하는 일은 6번, 줄 세우기뿐이다.** 정답이 무엇인지 모른다.
정답은 **내가 조각을 읽고 정했고**, 맞았는지 대조하는 것은 채점 코드다.

| 오해 | 실제 |
|---|---|
| 모델이 정답을 골랐다 | 모델은 **127개를 닮은 순서로 줄 세웠을 뿐**이다 |
| 모델이 top 을 지정했다 | top5 는 그 줄의 **앞 5칸**을 잘라낸 것이다 |
| 모델이 채점했다 | 채점은 `run_eval.py` 가 `gold` 와 대조해서 한다 |

Spring 으로 보면 **모델은 `Comparator` 이고, `gold` 는 테스트의 `expected` 값**이다.
`Comparator` 는 무엇이 정답인지 모른 채 정렬만 한다.

## 4. 왜 모델을 3개로 추렸나 — 각 모델이 질문 하나에 답한다

후보가 일곱 개 이상 있었는데 셋으로 줄였다. **CPU 만 쓸 수 있어서
많이 돌리면 시간이 과하게 든다.** 그래서 알고 싶은 것을 두 축으로 좁혔다.

| | 모델 | 차원 | **이 모델이 답하는 질문** |
|---|---|---|---|
| 1 | `BAAI/bge-m3` | 1024 | **기준선.** 한국어 특화가 이걸 못 이기면 특화할 이유가 없다 |
| 2 | `nlpai-lab/KURE-v1` | 1024 | **한국어 특화가 효과 있나.** bge-m3 기반이라 조건이 같다 |
| 3 | `multilingual-e5-small-ko-v2` | 384 | **작은 모델로 충분한가.** CPU 로 감당되는가 |

```
축 1  한국어 특화 효과   ->  1번 대 2번
축 2  모델 크기          ->  1·2번 대 3번
```

3번을 "자원 절약용" 이 아니라 **진짜 후보**로 넣었다.
모델 카드가 "2배 큰 `e5-base` 보다 한국어 벤치마크에서 낫다" 고 밝히고 있어서
CPU 환경이면 이길 수도 있다고 보고 대등하게 시험했다.

### 지금 넣지 않은 후보

| 모델 | 언제 넣나 |
|---|---|
| `BGE-m3-ko` · `KoE5` (둘 다 1024) | **넣지 않는다.** 6절 이유 참조 |
| `KURE-v1-gguf` (1024 · CPU 최적화) | CPU 색인이 실제로 느려서 문제가 됐을 때 |
| CLOVA Studio 임베딩 | 유료. 로컬로 좁힌 뒤 마지막에 |

## 5. 결과 — 문항 수로 읽는다

시험 규모: **문서 5건 · 조각 127개 · 질문 73개** (뜻으로만 34 · 단어 겹침 39)

| 모델 | 차원 | **뜻으로만 (34문항)** | 단어 겹침 (39문항) | 속도 (100조각당) | 메모리 |
|---|---|---|---|---|---|
| **KURE-v1** | 1024 | **top5 에 27개 (79.4%)** | 33개 (84.6%) | 46초 | 1,544MB |
| bge-m3 | 1024 | top5 에 26개 (76.5%) | 32개 (82.1%) | 43초 | 1,552MB |
| e5-small | 384 | **top5 에 14개 (41.2%)** | **38개 (97.4%)** | **4초** | **426MB** |
| (가짜 모델) | 64 | **0개 (0%)** | 15개 | — | — |

**맨 아래 줄이 바닥선이다.** 글자 겹침만 보는 가짜 모델을 먼저 돌려
`뜻으로만` 문항에서 **0개**가 나오는 것을 확인했다.
실제 모델이 그 0 을 얼마나 넘는지가 임베딩을 쓸 근거다.

| 무엇을 봤나 | 값 |
|---|---|
| 바닥 (글자만 보는 가짜 모델) | 0 / 34 |
| **1024차원 실제 모델** | **27 / 34** |
| 384차원 실제 모델 | 14 / 34 |

## 6. 그래서 왜 KURE-v1 인가

| | 근거 | 수치 |
|---|---|---|
| 1 | **차원이 두 배 낫다** | 1024 가 27개, 384 가 14개. **13문항 차이** |
| 2 | 두 1024 모델 중 KURE 가 앞선다 | top3 로 좁히면 **22개 대 19개** |
| 3 | 순위를 더 위로 올린다 | `MRR` 0.533 대 0.499 |
| 4 | 되돌리기가 싸다 | bge-m3 와 **차원이 같아 DB 를 안 건드리고 교체 가능** |

### 다만 "확정" 이 아니라 "기본값" 이다

| 보류 이유 | 내용 |
|---|---|
| 차이가 작다 | top5 기준으로는 **27개 대 26개, 문항 하나 차이** |
| 뒤집힌 구간이 있다 | 단어 겹침 문항에서는 bge-m3 가 앞선다 |
| 무작위성 증거 | **한 모델만 맞춘 문항 3개를 세 모델이 각각 하나씩** 맞췄다 |
| 그래서 | 같은 차원 모델을 더 넣어도 같은 잡음만 본다. **평가셋을 키운 뒤 다시 본다** |

**차원은 확정, 모델은 기본값.** 이 구분이 중요하다.
차원을 잘못 정하면 전체를 다시 임베딩해야 하고(CPU 로 반나절),
모델은 나중에 바꿔도 공짜다.

### 384차원을 안 쓰는 이유가 결론보다 중요하다

```
e5-small  단어 겹침 문항   38 / 39   ->  세 모델 중 1위
          뜻으로만 문항    14 / 34   ->  세 모델 중 최하위
```

**작은 모델은 글자가 겹칠 때만 잘한다.** 그건 지금 쓰는 키워드 검색이
이미 하는 일이다. 뜻으로 건너뛰는 능력이 약하다.

**만약 `단어 겹침` 만 재고 모델을 골랐다면 e5-small 을 뽑았을 것이다.
그리고 실제 사용자 질문에서 절반을 놓쳤을 것이다.**

## 7. 실제로 어떻게 판단했나 — 예시 둘

### 맞춘 예 — 이게 `RAG-04` 다

**내가 읽은 구절** (24번 조각, 중앙보훈병원 입찰공고문)

```
8. 낙찰자 결정방법
  가. 평가방법 : 별첨 "제안요청서" 참조
   - 분야별 배정 : 기술능력배점 90점, 입찰가격배점 10점
```

**내가 만든 질문**

```
"실력과 싼값 중 무엇을 더 보나"

  기술능력 -> 실력      입찰가격 -> 싼값
  24번 조각의 단어를 하나도 쓰지 않았다   (no_overlap)
```

**내가 적은 정답** — `gold = 4, 24`
(기초과학연구원 공고에는 80% / 20%, 중앙보훈병원 공고에는 90점 / 10점.
같은 종류 정보가 두 문서에 있어 **둘 다 정답으로 뒀다**)

**모델이 줄 세운 결과** (127개 중 앞 5개)

| 모델 | top5 | 정답 위치 | |
|---|---|---|---|
| bge-m3 | `24, 26, 57, 55, 21` | **1등** | 맞춤 |
| KURE-v1 | `26, 24, 8, 21, 55` | **2등** | 맞춤 |
| e5-small | `24, 26, 59, 36, 42` | **1등** | 맞춤 |

**"기술능력배점" 이라는 말을 몰라도 "실력" 으로 물어서 찾았다.**
`RAG-04` 완료 판정 기준이 "글자가 하나도 겹치지 않는 질의로 관련 문서가
나온다" 이므로, **이 문항 하나가 그 증거다.** 발표에서 보여줄 사례로 쓸 수 있다.

### 틀린 예 — 숫자에는 약하다

**질문** `"사업금액 578600000원"` — `gold = 7`
(단어가 그대로 겹치는 쉬운 문항이다)

| 모델 | top5 | 정답 위치 |
|---|---|---|
| bge-m3 | `123, 119, 113, 106, 127` | **10등 안에도 없음** |
| KURE-v1 | `123, 118, 119, 113, 122` | **10등 안에도 없음** |
| e5-small | `5, 6, 107, 7, 126` | 4등 |

**앞에 온 것들이 전부 다른 문서의 예산금액 조각이었다.**
숫자를 물었는데 다른 숫자로 끌려간다.

이것이 `RAG-05`(하이브리드 검색 · 키워드 + 벡터 · P2)가 필요한 근거다.
기능명세서 완료 판정이 이미 "고유명사·코드번호 검색에서 벡터 단독보다
정확하다" 로 적혀 있었고, **이번 시험이 그 근거를 수치로 채웠다.**
키워드 쪽은 `VIS-06`(PostgreSQL FTS)과 결합하라고 비고에 지정되어 있다.

## 8. 이 시험으로 알게 된 것 다섯 개

| | 알게 된 것 | 어디에 쓰나 |
|---|---|---|
| 1 | **`vector(1024)`** 로 간다 | 리비전 `0010` 착수 근거 |
| 2 | `top-k` 는 **5 이상**이어야 한다. 1등만 보면 3분의 1만 맞는다 | `RAG-04` 구현 기본값 |
| 3 | **숫자·코드번호는 벡터가 약하다** | `RAG-05` 하이브리드 근거 |
| 4 | **큰 조각은 단어가 겹쳐도 못 찾는다** (438자에 필드 20여 개) | `RAG-01` 이 `element_type` 으로 묶는 이유 |
| 5 | 문서 격리는 **벡터가 아니라 `project_id` 조건**이 한다 | `PRJ-08` · `RAG-04` |

## 9. 믿을 수 있는 수치인가 — 세 번 재고 한 번 예측했다

| 회차 | 문항 | 무엇을 고쳤나 | KURE 결과 |
|---|---|---|---|
| 1차 | 78 | — | 24 / 39 |
| 2차 | 73 | 측정 불가 5문항 삭제 · 정답 4문항 확장 | 27 / 34 |
| 3차 | 73 | 질문에 정답 단어가 하나 새어 있던 것 수정 | **27 / 34** |

**1차에서 세 모델이 똑같이 틀린 13문항을 파보니 모델 잘못이 아니었다.**
내가 정답을 좁게 잡아 **맞은 것을 틀렸다고 채점하고 있었다.**
그것을 고친 것이 2차다.

그리고 **2차 결과를 내기 전에 예측값을 먼저 적어두고 대조했다.**

| 모델 | 예측 | 실측 |
|---|---|---|
| KURE-v1 | 0.794 | **0.794** |
| bge-m3 | 0.765 | **0.765** |
| e5-small | 0.412 | **0.412** |

소수 셋째 자리까지 맞았다. 채점이 흔들리지 않는다는 뜻이다.

### 이 수치를 쓸 때 주의할 것

| | 주의 |
|---|---|
| 1 | **본구현 검색 품질 예측치로 쓰면 안 된다.** 조각을 자르는 방식이 다르다 (이번은 글자 수, `RAG-01` 은 토큰 수 · `element_type`) |
| 2 | 두 1024 모델의 **속도 차이는 비교하지 않는다.** 같은 조건에서 10초 흔들렸다 (CPU 측정 노이즈) |
| 3 | 문항 73개, 정답으로 쓴 조각 35개 / 127개. **표본이 작다** |

## 10. 한 문장

> **글자가 하나도 겹치지 않는 질문 34개 중 1024차원 모델이 27개를 top5 에
> 넣었고 384차원은 14개였다. 그래서 `pgvector` 를 `vector(1024)` 로 정하고
> `KURE-v1` 을 기본 모델로 둔다. 모델은 나중에 바꿀 수 있지만 차원은 못 바꾼다.**

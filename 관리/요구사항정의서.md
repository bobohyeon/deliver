## 1. 개요

### 1.1 배경

앞선 미니 프로젝트에서 **문서를 넣으면 텍스트를 뽑아 요약·분류하는 도구**를
만들었다. 동작은 했지만 산출물이 문서 한 건 단위에서 끝났다.

그 프로젝트를 진행하면서 팀은 이슈 46건, 결정사항 29건, 주간 보고, WBS 를
**손으로** 만들었다. 도구가 문서를 읽고 있었는데도 그랬다.

**Tasqra 는 그 손작업을 도구가 하게 만드는 것이다.**

### 1.2 제품 정의

> **문서를 올리면 프로젝트 문서가 나오는 도구.**

입력은 계약서·회의록·보고서 같은 실무 문서이고, 출력은 **주간 보고서·프로젝트
현황·결정사항 로그(대장)·회의 안건**이다. 태스크 보드는 그 사이의 중간 산물이다.

### 1.3 검토했으나 채택하지 않은 정의

| 대안 | 왜 채택하지 않았나 |
|---|---|
| 문서 요약 도구 | 미니 프로젝트와 같다. 확장이 아니다 |
| **태스크 보드까지** | **"그 태스크 모음집으로 뭘 하나" 에 답이 없다.** 이 질문이 범위를 산출물까지 밀어낸 결정적 이유다 |
| 비용추계 도구 | 없는 금액을 만들어야 한다. 단가 근거를 댈 수 없다 (7.2절) |

### 1.4 문서 범위

이 문서는 Tasqra 전체의 요구사항을 다룬다. 미니 프로젝트에서 이미 구현된 부분도
**현재 요구사항으로 다시 기술**한다. 이미 됐다는 이유로 빼면 인수인계 시점에
근거가 사라진다.

## 2. 이해관계자와 사용자

### 2.1 이해관계자

| 구분 | 관심사 | 이 문서에서 확인할 곳 |
|---|---|---|
| 개발팀 3인 | 20일 안에 만들 수 있는가 | 8절 제약사항 |
| 심사위원 | 주장에 기준과 수치가 있는가 | 6·7절 검증 방법 |
| 가상 사용자 (SI · 공공사업 수행팀) | 손으로 만드는 문서를 줄여주는가 | 3.10절 산출물 |

**심사위원 항목이 요구사항에 들어간 이유가 있다.** 미니 프로젝트 심사에서
**"주장에 기준·수치가 없다"** 는 지적을 받았다. 그래서 이 문서의 모든 요구사항에
검증 방법 열을 붙였다. 검증 방법을 못 쓰는 요구사항은 요구사항으로 두지 않았다.

### 2.2 사용자 역할

프로젝트 단위로 3종을 둔다. 상세 권한표는 기능명세서 4절에 있다.

| 역할 | 할 수 있는 것 |
|---|---|
| `OWNER` | 전부. 멤버 초대 · 권한 변경 · 프로젝트 삭제 · 금액 추출·검토 |
| `EDITOR` | 문서 업로드 · OCR 검수 · 분석 결과 검토 · 금액 추출·검토 · 산출물 생성 |
| `VIEWER` | 일반 조회만. 금액 탭과 금액 직접 경로에는 접근할 수 없음 |

### 2.3 요구사항 출처

| 표기 | 출처 |
|---|---|
| `목업` | 박세현 화면 목업 |
| `기획안` | 박세현 `기획안_v0.1` · `착수기획서_v1.0` |
| `확장안` | 최재정 `기능 확장 아이디어` (일반 · 검수 · 일괄 3모드) |
| `OCR-DB` | 최재정 `OCR-DB 설계안` |
| `미니` | 미니 프로젝트 구현 코드 및 그 결함 기록 |
| `심사` | 미니 프로젝트 심사 피드백 |
| `팀합의` | 본프로젝트 논의 중 결정 |

## 3. 기능 요구사항 (SFR)

### 3.1 계정과 접근 통제

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-01` | 사용자는 계정을 만들고 로그인해 자신을 식별할 수 있어야 한다. 비밀번호는 복원 불가능한 형태로만 저장된다 | 필수 | 기획안 | DB 에서 평문 부재 확인 · 오인증 401 |
| `SFR-02` | **모든 보호 자원은 인증 없이 접근할 수 없어야 한다** | 필수 | 미니 | 보호 엔드포인트 전수 목록에 토큰 없이 호출해 전부 401 |

**`SFR-02` 를 따로 뺀 이유** — 라우터마다 검사하면 반드시 하나를 빠뜨린다.
공통 의존성 한 곳에서 강제하고, 그 적용 여부를 **목록으로 전수 확인**하는 것을
요구사항으로 못박는다.

### 3.2 프로젝트

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-03` | 사용자는 프로젝트를 만들고 진행 상태를 관리하며 필요 시 보관·삭제할 수 있어야 한다 | 필수 | 목업 | 생성자 자동 `OWNER` 등록 확인 |
| `SFR-04` | `OWNER` 는 멤버를 초대하고 역할을 부여할 수 있어야 하며, 역할별 허용 동작이 문서로 존재해야 한다 | 필수 | 기획안 | 권한표 각 행을 테스트로 확인 |
| `SFR-05` | **모든 데이터 접근은 프로젝트 경계를 넘을 수 없어야 한다** | 필수 | 팀합의 | 타 프로젝트 식별자를 직접 넣어 404 확인 |

**`SFR-05` 가 이 시스템의 유일한 격리 경계다.** 인증만 통과하면 남의 문서가
보이는 상태가 가장 위험하다. 서비스 계층이 아니라 **데이터 접근 계층에서** 막는
것을 요구사항으로 둔다. 서비스 계층은 호출 경로가 여러 개라 빠지는 곳이 생긴다.

### 3.3 문서 입력과 처리

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-06` | 사용자는 PDF · DOCX · HWPX · JPG · PNG 를 업로드할 수 있고, 허용 범위를 벗어난 파일은 이유를 알 수 있는 형태로 거부되어야 한다 | 필수 | 미니 | 형식 위반 415 · 크기 초과 413 · 사유 메시지 확인 |
| `SFR-07` | 시스템은 파일 형식에 맞는 방법으로 텍스트를 추출해야 하며, 스캔 문서와 이미지에서도 텍스트를 얻어야 한다 | 필수 | 미니 | 스캔 PDF · 이미지에서 텍스트 산출 확인 |
| `SFR-08` | **업로드 요청은 추출 완료를 기다리지 않아야 한다.** 처리 경과는 사용자에게 단계별로 보여야 한다 | 필수 | 미니 | 24페이지 스캔 PDF 업로드가 즉시 응답 · 진행 단계 표시 |
| `SFR-09` | 사용자는 문서 목록과 상세를 보고, 원본을 내려받고, 삭제할 수 있어야 한다. 삭제 시 하위 데이터가 남지 않아야 한다 | 필수 | 목업 | 삭제 후 하위 테이블 잔존 행 0 |
| `SFR-10` | 사용자는 문서를 다시 분석할 수 있어야 하며, 이전 결과가 지워지지 않아야 한다 | 중요 | 미니 | 재분석 후 이전 행 존재 확인 |
| `SFR-11` | 사용자는 업로드 시 문서 유형을 지정할 수 있어야 하고, 지정하지 않으면 시스템이 판별해야 한다 | 중요 | 팀합의 | 7종 지정 · 미지정 시 자동 판별 동작 |
| `SFR-12` | **업로드한 파일은 서버 재기동 후에도 유지되어야 한다** | 중요 | 미니 | 컨테이너 재기동 후 원본 다운로드 성공 |

**`SFR-08` 이 본프로젝트 최우선 요구사항이다.** 미니 프로젝트는 업로드 요청
스레드에서 OCR 을 직접 돌렸다. 사용자가 여러 명이 되는 순간 처리 자원이
고갈된다. 기능이 아니라 **구조를 바꿔야 하는 요구사항**이라 먼저 둔다.

**`SFR-11` 의 목적이 바뀌었다.** 문서 유형은 목록 필터·프롬프트 힌트·산출물
분류에 쓰고, 계약서 계열에서는 액션아이템 분석 실행 범위를 정하는 데도 쓴다.
요약·분류·결정·일정은 기본 분석으로 실행하고, 금액은 사용자가 명시적으로 추출·
재추출한다. `features` 수행 과업 분석도 명시 요청형이다.

### 3.4 OCR 검수

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-13` | 사용자는 문서 페이지 이미지 위에서 OCR 인식 영역과 신뢰도를 눈으로 확인할 수 있어야 한다 | 중요 | 확장안 · OCR-DB | **화면 확대·축소를 바꿔도 영역이 글자 위에 유지되는지** 확인 |
| `SFR-14` | 사용자는 잘못 인식된 텍스트를 고칠 수 있어야 하며, 원래 인식값이 보존되어야 한다. 같은 대상을 두 사람이 동시에 고치면 한쪽이 거부되어야 한다 | 중요 | 확장안 | 수정 후 원본값 잔존 · 동시 수정 시 나중 요청 409 |
| `SFR-15` | **검수 결과는 이후 분석에 반영되어야 한다.** 검수 후 기존 분석 결과는 낡았음이 표시되어야 한다 | 중요 | 팀합의 | 검수 확정 후 분석이 수정본 기준으로 실행 · 낡은 분석 표시 확인 |
| `SFR-16` | 사용자는 인식 영역의 위치·구조·읽는 순서를 편집할 수 있어야 한다 | 선택 | 확장안 | 사용자 지정이 자동 결과로 덮이지 않는지 확인 |

**검수가 왜 중요 등급인가 — 금액 때문이다.** 문장은 오탈자가 있어도 요약이 대충
맞지만, **숫자는 `1` 을 `7` 로 읽으면 집계 전체가 틀린다.** 금액 요구사항
(`SFR-24`~`SFR-26`) 의 정확도가 이 영역에 걸려 있다.

**`SFR-15` 가 가장 놓치기 쉬운 요구사항이다.** 검수를 해놓고 분석이 낡은 텍스트를
쓰면 검수가 무의미해진다. 전파 사슬을 요구사항으로 명시한다.

결정사항과 일정이 산출물(`SFR-34`)의 재료가 된다. 액션아이템은 **문서 분석 결과**로
남기며, AI가 새 태스크를 제안하는 기능과 같은 것으로 보지 않는다.

코드 내부의 `features` 분석은 소프트웨어 기능 목록이나 액션아이템이 아니라 문서에
적힌 **수행 과업·사업 범위**를 `name`·`summary`와 원문 위치로 뽑는 별도 분석이다.
기본 분석 흐름의 액션아이템은 `action_task` 분석이 담당한다.

**`SFR-19` 에 근거를 요구사항으로 넣은 이유** — 분류가 틀렸을 때 사용자가 왜
틀렸는지 알아야 고칠 수 있고, 그 수정 비율이 정확도 측정치(`QUR-02`)가 된다.

옛 텍스트를 갖고 있으면 검색이 낡은 것을 찾아온다. `SFR-15`(검수 전파)의
사슬이 여기까지 이어져야 한다.

**`SFR-43` 은 원칙을 요구사항으로 못박은 것이다.** AI 는 문서에서 뽑고, 계산은
코드가 한다. 문서에 `3 × 9,500,000 = 28,000,000` 처럼 **틀린 계산이 적혀
있어도 그대로 읽어야** 우리가 잡아낼 수 있다. 모델이 고쳐서 주면 오류가 숨는다.

**`SFR-46` 이 모델 학습의 전제다.** 학습 전후를 같은 자로 재지 않으면
"좋아졌다" 를 증명할 수 없다.

이미지의 크기가 다르면 영역이 어긋난다. 비율로 저장하면 배율과 무관해진다.

흐름을 통과시킬 수 있어야 한다.

### 4.4 성능 요구사항 (PER)

| ID | 요구사항 | 목표 | 중요도 | 측정 방법 |
|---|---|---|---|---|
| `PER-01` | 10페이지 스캔 문서 처리 완료 | ≤ 60초 | 중요 | 동일 파일 3회 평균 |
| `PER-02` | 업로드 응답 시간 | 파일 크기와 무관하게 즉시 | 필수 | 24페이지 스캔 문서로 확인 |
| `PER-03` | **목록 조회 질의 수** | **문서 수와 무관하게 일정** | 필수 | 문서 5건·50건에서 질의 로그 개수 비교 |
| `PER-04` | 주간 보고서 생성 | ≤ 15초 | 중요 | LLM 0회 + DB 조회·렌더링 시간 |
| `PER-05` | 동시 사용 | 4~5인 정상 동작 | 중요 | 동시 업로드 5건 |

50건에서 같은 수가 나오면 통과다.

**`PER-06` 은 비용 요구사항이다.** 최신 산출물 네 종류는 저장된 DB 자료를
재사용해 구조화하며 원문이나 요약을 AI에 다시 보내지 않는다. 생성 경로의 AI 호출
목표와 현재 확인값은 모두 0회다.

### 4.6 품질 요구사항 (QUR)

| ID | 요구사항 | 목표 | 중요도 | 측정 방법 |
|---|---|---|---|---|
| `QUR-01` | 결정사항·일정·금액 분석 결과 검토율 | 측정 가능해야 한다 | 중요 | 종류별 PENDING·승인·수정·거절 상태 집계 |
| `QUR-02` | 문서 유형 판별 정확도 | ≥ 85% | 중요 | **사람이 판별을 고친 비율** |
| `QUR-03` | 날짜 추출 정확도 | 측정 가능해야 한다 | 중요 | Golden Dataset 원문 대조 |
| `QUR-04` | 금액 항목 추출 정확도 | 측정 가능해야 한다 | 중요 | Golden Dataset 원문 대조 |
| `QUR-05` | **금액 집계 정확도** | **100%** | 중요 | 단위테스트 |
| `QUR-06` | **모든 오류 응답이 서버 기록에 남아야 한다** | 누락 0 | 필수 | 각 오류 상태를 유발하고 기록 확인 |

**`QUR-02` 의 측정 방식을 바꿨다.** 별도 정답 데이터를 만드는 대신 **사람이 AI
판별을 고친 비율**을 쓴다. 정답셋을 만드는 비용이 없고, 실사용 데이터라서 발표에서
더 설득력이 있다.

**`QUR-04` 와 `QUR-05` 를 나눈 것이 중요하다.** 추출은 원문이 정답이라 측정할 수
있고, 집계는 코드가 하니 100% 여야 한다. **"AI 가 금액을 얼마나 잘 맞추나" 는
정답이 없어서 하나의 지표로 쓸 수 없다.** 그래서 두 줄로 갈랐다.

**`QUR-06` 은 미니 프로젝트에서 실제로 빠져 있던 결함이다.** 사용자에게는 오류가
보이는데 서버 기록에는 아무것도 없어서, 무슨 일이 있었는지 추적할 수 없었다.

## 6. 범위에서 제외한 것

| 안 함 | 이유 |
|---|---|
| 실시간 공동 편집 | 문서 편집 도구를 대체하려는 게 아니다 |
| 본격적인 일정 관리 도구 | 범위 밖 |
| **사람이 원가를 입력하는 비용 관리** | 제품 컨셉과 반대다. **우리는 문서에서 뽑는다** |
| **금액 추계 · 예측** | 없는 값을 만드는 일이다. 근거를 댈 수 없다 |
| **AI 태스크 제안과 검토** | 액션아이템·금액은 문서 분석 결과로만 다룬다. 새 태스크 제안, 승인·수정·거절·일괄 승인, 금액 불일치 확인 태스크 제안은 현재 제품 범위에서 제외한다 (`SFR-28`·`SFR-29`) |
| **인수인계 문서 자동 생성** | 프로젝트 현황과 기존 산출물에 내용이 겹치고 전용 데이터가 부족하다. 유지 산출물 네 종류는 그대로 둔다 |
| 모바일 전용 앱 | 반응형 화면으로 대응 |
| **법률 문서 자동 생성** | 환각 위험 · 책임 문제 · 검증 부담 |
| 지식을 모델에 학습시키기 | `COR-05`. 단가는 바뀌는 값이라 `SFR-42` 로 찾아온다 |
| **원문 위치 하이라이트** | 분석 규격을 바꿔야 해서 3인이 서로 기다린다 (`COR-03`) |

**세 번째 항목의 경계를 분명히 한다.** 사람이 원가를 입력하는 관리 기능은 안 하고,
**문서에서 뽑은 금액의 집계와 검증은 한다.** 차이는 "숫자를 누가 넣는가" 다.

## 7. 검토했으나 채택하지 않은 방안

**요구사항정의서에 이 절을 두는 이유** — 폐기한 방안과 그 이유가 남아 있지 않으면
같은 논의를 다시 한다. 미니 프로젝트에서 실제로 반복했다.

### 7.1 문서 유형과 무관하게 모든 분석을 항상 실행하는 안 — **수정됨**

| 구분 | 현재 실행 범위 | 이유 |
|---|---|---|
| 기본 분석 | 요약·분류·결정사항·일정 | 일반 문서 분석 흐름에서 공통으로 필요하다 |
| 문서 유형 조건 | 계약서·계약 변경 문서의 액션아이템 | 실행 의무가 명확한 문서군으로 제한한다 |
| 명시 요청 | 금액 추출·재추출, `features` 수행 과업 분석 | 비용과 사용자 의도를 고려해 필요할 때 실행한다 |

초기에는 분석기를 모두 동시에 실행하려 했지만 최신 코드는 위 범위를 사용한다.
문서 유형은 액션아이템의 실행 범위에 쓰되, 금액은 유형에 따라 자동 생략하지 않고
사용자가 문서 상세에서 명시적으로 실행한다.

### 7.2 비용추계 기능 — **판단이 바뀌었다**

| | |
|---|---|
| 원래 구상 | 단가와 수량으로 **없는 금액을 산출**한다 |
| 폐기 사유 | 단가 마스터를 만들어야 하고, **"그 단가 근거가 뭐냐" 에 답할 수 없다** |
| 1차 결론 | 집계로 좁혔다. 문서에 적힌 금액만 모은다 |
| **바뀐 이유** | **RAG 로 과거 문서에서 단가를 찾아오면 출처를 댈 수 있다** (`SFR-42`) |
| 현재 | **보류 해제.** 환각이 아니라 선례 기반 추정이 된다 |

**도메인을 공공 SI·용역으로 좁힌 것이 결정적이었다.** 나라장터에 과거 문서가
공개돼 있고, SW기술자 평균임금처럼 **공표된 단가**가 있다. 그러면 "이 단가
근거가 뭐냐" 에 답할 수 있다.

단, 계산은 여전히 코드가 한다(`SFR-43`). AI 는 문서에서 뽑고 값을 찾아올 뿐이다.

### 7.3 근거를 원문 위치로 표시하는 안

| | 채택안 | 폐기안 |
|---|---|---|
| 방식 | 판단 근거를 **문장으로** 서술 | 몇 페이지 어느 위치인지 좌표로 표시 |
| 규격 변경 | 없음 | 분석 규격을 바꿔야 한다 |
| 3인 병행 | 가능 | **서로 기다린다** (`COR-03`) |
| 대가 | 원문 대조 검증이 어렵다 | — |

**대가를 그냥 감수하지 않고 대체 수단을 뒀다.** 검증이 필요한 금액에는
합계 대조(`SFR-25`)를 넣어 다른 방식으로 확인한다.

### 7.4 분석을 하나로 합치는 안

| | 채택안 (종류별 분석기) | 폐기안 (하나로 합침) |
|---|---|---|
| 출력 규격 | 요약·분류·결정·일정·액션아이템·금액별로 검증 | 한 응답 규격에 모두 결합 |
| 실행 범위 | 기본·문서 유형 조건·명시 요청으로 구분 | 매번 전체 실행 |
| 실패 범위 | 하나가 실패해도 나머지 결과를 보존 | 응답 하나가 실패하면 전부 실패 |
| 금액 정확도 | 전용 프롬프트와 엄격 JSON 검증 사용 | 다른 분석 지시와 섞여 주의가 분산됨 |

종류별 분석기 구조는 유지한다. 다만 **항상 전부 실행한다는 초기 결정은 폐기**했고,
최신 실행 범위는 7.1절을 따른다. 분석기별 결과·프롬프트 판·오류를 독립적으로
남기는 것이 `SFR-22`·`SFR-23`의 근거다.

### 7.5 RAG 를 범위에서 빼려던 안 — **판단이 바뀌었다**

| | 처음 판단 | 현재 |
|---|---|---|
| RAG | 범위 밖 | **정식 범위** (`SFR-38`~`SFR-42`) |
| 근거 | "기간 필터가 그 자리를 이미 채우고 있다" | **산출물 생성에는 여전히 필요 없다. 금액 근거에 필요하다** |

처음 근거가 틀린 것은 아니다. **산출물 생성에는 RAG 가 필요하지 않다.** 프로젝트
와 기간으로 범위가 좁혀지고, 저장된 요약을 모으면 된다(`PER-06`).

**바뀐 것은 금액이다.** 단가 선례를 찾아오는 데 의미 검색이 필요하고, 그게
비용추계를 환각에서 벗어나게 한다. **RAG 를 쓰는 자리가 산출물이 아니라
금액이었다는 것이 뒤늦게 분명해졌다.**

**챗봇(`SFR-41`)은 선택으로 남긴다.** 의미 검색과 단가 선례 검색이 먼저다.
그 둘은 금액 근거에 직접 쓰이고, 챗봇은 그 위에 얹는 화면이다.

## 9. 미결 사항

최신 코드와 확정 결정을 대조한 뒤에도 요구사항 수준에서 근거가 부족한 것만 남겼다.

| | 안건 | 관련 요구사항 | 현재 확인 | 필요한 사람 |
|---|---|---|---|---|
| 1 | `VIEWER`에게 금액 원시 분석 응답과 단가 선례 API까지 차단할 것인가 | `SFR-48` · `SER-04` | 금액 탭·주요 API는 차단됐지만 두 우회 노출 경로가 남아 부분 충족 | 전원 |
| 2 | 추출한 문서 기재 합계를 문서 합계 컬럼에 자동 반영할 것인가 | `SFR-25` | `stated_total`은 분석 JSON에만 저장돼 전 구간 자동 대조가 확인되지 않음 | 보현 · 세현 |
| 3 | 금액 값 수정·감소도 산출물 갱신 필요로 판정할 것인가 | `SFR-37` · `SFR-44` | 현재는 원천 건수 증가 중심이며 자동 재생성은 범위 밖 | 전원 |
| 4 | Golden Dataset의 금액·액션아이템 정답 수와 담당 | `TER-03` | 검색 평가셋과 별개로 확정 근거 부족 | 전원 |

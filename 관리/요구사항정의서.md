## 1. 개요

### 1.1 배경

앞선 미니 프로젝트에서 **문서를 넣으면 텍스트를 뽑아 요약·분류하는 도구**를
만들었다. 동작은 했지만 산출물이 문서 한 건 단위에서 끝났다.

그 프로젝트를 진행하면서 팀은 이슈 46건, 결정사항 29건, 주간 보고, WBS 를
**손으로** 만들었다. 도구가 문서를 읽고 있었는데도 그랬다.

**Tasqra 는 그 손작업을 도구가 하게 만드는 것이다.**

### 1.2 제품 정의

> **문서를 올리면 프로젝트 문서가 나오는 도구.**

입력은 계약서·회의록·보고서 같은 실무 문서이고, 출력은 **주간 보고서·결정사항
대장·회의 안건**이다. 태스크 보드는 그 사이의 중간 산물이다.

### 1.3 검토했으나 채택하지 않은 정의

| 대안 | 왜 채택하지 않았나 |
|---|---|
| 문서 요약 도구 | 미니 프로젝트와 같다. 확장이 아니다 |
| **태스크 보드까지** | **"그 태스크 모음집으로 뭘 하나" 에 답이 없다.** 이 질문이 범위를 산출물까지 밀어낸 결정적 이유다 |
| 비용추계 도구 | 없는 금액을 만들어야 한다. 단가 근거를 댈 수 없다 (7.2절) |

### 1.4 문서 범위

이 문서는 Tasqra 전체의 요구사항을 다룬다. 미니 프로젝트에서 이미 구현된 부분도
**현재 요구사항으로 다시 기술**한다. 이미 됐다는 이유로 빼면 인수인계 시점에
근거가 사라진다.

## 2. 이해관계자와 사용자

### 2.1 이해관계자

| 구분 | 관심사 | 이 문서에서 확인할 곳 |
|---|---|---|
| 개발팀 3인 | 20일 안에 만들 수 있는가 | 8절 제약사항 |
| 심사위원 | 주장에 기준과 수치가 있는가 | 6·7절 검증 방법 |
| 가상 사용자 (SI · 공공사업 수행팀) | 손으로 만드는 문서를 줄여주는가 | 3.10절 산출물 |

**심사위원 항목이 요구사항에 들어간 이유가 있다.** 미니 프로젝트 심사에서
**"주장에 기준·수치가 없다"** 는 지적을 받았다. 그래서 이 문서의 모든 요구사항에
검증 방법 열을 붙였다. 검증 방법을 못 쓰는 요구사항은 요구사항으로 두지 않았다.

### 2.2 사용자 역할

프로젝트 단위로 3종을 둔다. 상세 권한표는 기능명세서 4절에 있다.

| 역할 | 할 수 있는 것 |
|---|---|
| `OWNER` | 전부. 멤버 초대 · 권한 변경 · 프로젝트 삭제 |
| `EDITOR` | 문서 업로드 · OCR 검수 · 제안 승인 · 산출물 생성 |
| `VIEWER` | 조회만 |

### 2.3 요구사항 출처

|---|---|

## 3. 기능 요구사항 (SFR)

### 3.1 계정과 접근 통제

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-01` | 사용자는 계정을 만들고 로그인해 자신을 식별할 수 있어야 한다. 비밀번호는 복원 불가능한 형태로만 저장된다 | 필수 | 기획안 | DB 에서 평문 부재 확인 · 오인증 401 |
| `SFR-02` | **모든 보호 자원은 인증 없이 접근할 수 없어야 한다** | 필수 | 미니 | 보호 엔드포인트 전수 목록에 토큰 없이 호출해 전부 401 |

**`SFR-02` 를 따로 뺀 이유** — 라우터마다 검사하면 반드시 하나를 빠뜨린다.
공통 의존성 한 곳에서 강제하고, 그 적용 여부를 **목록으로 전수 확인**하는 것을
요구사항으로 못박는다.

### 3.2 프로젝트

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-03` | 사용자는 프로젝트를 만들고 진행 상태를 관리하며 필요 시 보관·삭제할 수 있어야 한다 | 필수 | 목업 | 생성자 자동 `OWNER` 등록 확인 |
| `SFR-04` | `OWNER` 는 멤버를 초대하고 역할을 부여할 수 있어야 하며, 역할별 허용 동작이 문서로 존재해야 한다 | 필수 | 기획안 | 권한표 각 행을 테스트로 확인 |
| `SFR-05` | **모든 데이터 접근은 프로젝트 경계를 넘을 수 없어야 한다** | 필수 | 팀합의 | 타 프로젝트 식별자를 직접 넣어 404 확인 |

**`SFR-05` 가 이 시스템의 유일한 격리 경계다.** 인증만 통과하면 남의 문서가
보이는 상태가 가장 위험하다. 서비스 계층이 아니라 **데이터 접근 계층에서** 막는
것을 요구사항으로 둔다. 서비스 계층은 호출 경로가 여러 개라 빠지는 곳이 생긴다.

### 3.3 문서 입력과 처리

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-06` | 사용자는 PDF · DOCX · HWPX · JPG · PNG 를 업로드할 수 있고, 허용 범위를 벗어난 파일은 이유를 알 수 있는 형태로 거부되어야 한다 | 필수 | 미니 | 형식 위반 415 · 크기 초과 413 · 사유 메시지 확인 |
| `SFR-07` | 시스템은 파일 형식에 맞는 방법으로 텍스트를 추출해야 하며, 스캔 문서와 이미지에서도 텍스트를 얻어야 한다 | 필수 | 미니 | 스캔 PDF · 이미지에서 텍스트 산출 확인 |
| `SFR-08` | **업로드 요청은 추출 완료를 기다리지 않아야 한다.** 처리 경과는 사용자에게 단계별로 보여야 한다 | 필수 | 미니 | 24페이지 스캔 PDF 업로드가 즉시 응답 · 진행 단계 표시 |
| `SFR-09` | 사용자는 문서 목록과 상세를 보고, 원본을 내려받고, 삭제할 수 있어야 한다. 삭제 시 하위 데이터가 남지 않아야 한다 | 필수 | 목업 | 삭제 후 하위 테이블 잔존 행 0 |
| `SFR-10` | 사용자는 문서를 다시 분석할 수 있어야 하며, 이전 결과가 지워지지 않아야 한다 | 중요 | 미니 | 재분석 후 이전 행 존재 확인 |
| `SFR-11` | 사용자는 업로드 시 문서 유형을 지정할 수 있어야 하고, 지정하지 않으면 시스템이 판별해야 한다 | 중요 | 팀합의 | 7종 지정 · 미지정 시 자동 판별 동작 |
| `SFR-12` | **업로드한 파일은 서버 재기동 후에도 유지되어야 한다** | 중요 | 미니 | 컨테이너 재기동 후 원본 다운로드 성공 |

**`SFR-08` 이 본프로젝트 최우선 요구사항이다.** 미니 프로젝트는 업로드 요청
스레드에서 OCR 을 직접 돌렸다. 사용자가 여러 명이 되는 순간 처리 자원이
고갈된다. 기능이 아니라 **구조를 바꿔야 하는 요구사항**이라 먼저 둔다.

**`SFR-11` 의 목적이 축소됐다.** 원래는 문서 유형으로 분석기를 골라 쓰려던
기능이었다. 그 계획을 폐기했으므로(7.1절) 지금 목적은 **목록 필터 · 프롬프트
힌트 · 산출물 분류** 셋이다. **유형을 몰라도 분석은 전부 돌아간다.**

### 3.4 OCR 검수

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-13` | 사용자는 문서 페이지 이미지 위에서 OCR 인식 영역과 신뢰도를 눈으로 확인할 수 있어야 한다 | 중요 | 확장안 · OCR-DB | **화면 확대·축소를 바꿔도 영역이 글자 위에 유지되는지** 확인 |
| `SFR-14` | 사용자는 잘못 인식된 텍스트를 고칠 수 있어야 하며, 원래 인식값이 보존되어야 한다. 같은 대상을 두 사람이 동시에 고치면 한쪽이 거부되어야 한다 | 중요 | 확장안 | 수정 후 원본값 잔존 · 동시 수정 시 나중 요청 409 |
| `SFR-15` | **검수 결과는 이후 분석에 반영되어야 한다.** 검수 후 기존 분석 결과는 낡았음이 표시되어야 한다 | 중요 | 팀합의 | 검수 확정 후 분석이 수정본 기준으로 실행 · 낡은 분석 표시 확인 |
| `SFR-16` | 사용자는 인식 영역의 위치·구조·읽는 순서를 편집할 수 있어야 한다 | 선택 | 확장안 | 사용자 지정이 자동 결과로 덮이지 않는지 확인 |

**검수가 왜 중요 등급인가 — 금액 때문이다.** 문장은 오탈자가 있어도 요약이 대충
맞지만, **숫자는 `1` 을 `7` 로 읽으면 집계 전체가 틀린다.** 금액 요구사항
(`SFR-24`~`SFR-26`) 의 정확도가 이 영역에 걸려 있다.

**`SFR-15` 가 가장 놓치기 쉬운 요구사항이다.** 검수를 해놓고 분석이 낡은 텍스트를
쓰면 검수가 무의미해진다. 전파 사슬을 요구사항으로 명시한다.

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |

**`SFR-20` 이 "태스크 모음집으로 뭘 하나" 에 답하는 출발점이다.** 여기서 뽑은
결정사항과 날짜가 산출물(`SFR-34`)의 재료가 된다. 요약만으로는 주간 보고서가
안 나온다.

**`SFR-19` 에 근거를 요구사항으로 넣은 이유** — 분류가 틀렸을 때 사용자가 왜
틀렸는지 알아야 고칠 수 있고, 그 수정 비율이 정확도 측정치(`QUR-02`)가 된다.

### 3.7 금액

**원칙 — 있는 금액을 모은다. 없는 금액을 만들지 않는다.**

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-24` | 시스템은 문서에 적힌 금액 항목을 구조화해 뽑아야 하고, **문서에 없는 값은 채우지 않아야 한다.** 각 항목에 판단 근거와 출처 문서가 붙어야 한다 | 중요 | 팀합의 | Golden Dataset 원문 대조 · 빈 값 유지 확인 |
| `SFR-25` | **시스템은 항목 합계와 문서에 적힌 합계를 대조해 불일치를 알려야 한다** | 중요 | 팀합의 | 불일치 문서 투입 시 차액 표시 |
| `SFR-26` | 시스템은 여러 문서의 금액을 프로젝트 단위로 합쳐 현재 상태를 보여줘야 하고, 같은 입력에는 항상 같은 결과를 내야 한다 | 중요 | 팀합의 | 단위테스트로 동일 입력 동일 출력 확인 |

**`SFR-25` 가 이 시스템에서 검증 가능한 유일한 기능이다.** 요약·결정·일정은 AI 가
뽑은 게 맞는지 확인할 방법이 없다. **금액은 재계산해서 대조된다.** 그래서 심사
지적("기준과 수치가 없다")에 직접 답하는 요구사항이다.

**`SFR-26` 은 문서 하나로는 알 수 없는 것을 알려준다.** 계약서의 계약금액,
변경합의서의 증액, 주간보고의 집행액을 모아야 잔액이 나온다. **"문서는 프로젝트
맥락 안에 있다" 는 제품 주장을 증명하는 건 금액이다.**

### 3.8 태스크

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-27` | 사용자는 태스크를 직접 만들고 상태·담당자·기한을 관리할 수 있어야 한다 | 중요 | 목업 | 3열 보드에서 상태 변경 동작 |
| `SFR-28` | **AI 가 뽑은 항목은 사람이 승인해야 태스크가 되어야 한다.** 거부한 항목은 다시 올라오지 않아야 한다 | 중요 | 팀합의 | 승인 전 보드 미표시 · 거부 후 재출현 없음 |
| `SFR-29` | 태스크에는 출처 문서와 판단 근거가 함께 보여야 하고, AI 생성 여부가 구분되어야 한다 | 중요 | 팀합의 | 출처 링크 이동 · 배지 표시 |
| `SFR-30` | 시스템은 누가 무엇을 했는지 기록해야 한다 | 선택 | 팀합의 | 활동 기록 조회 |

**`SFR-28` 이 이 제품의 안전장치다.** AI 가 뽑은 걸 바로 등록하면 틀린 태스크가
보드를 채우고, 사용자는 도구를 신뢰하지 않게 된다. **승인 단계는 기능 축소가
아니라 요구사항이다.**

**`SFR-30` 은 선택이지만 산출물의 재료다.** 없으면 주간 보고서의 "이번 주 활동"
항목이 비게 된다.

### 3.9 가시성

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-31` | **승인 대기 중인 제안이 있으면 사용자가 알 수 있어야 한다** | 중요 | 팀합의 | 대기 건수와 출처 문서명 표시 |
| `SFR-32` | 사용자는 프로젝트 현황을 한 화면에서 볼 수 있어야 한다 | 선택 | 목업 | 지표 카드 표시 |
| `SFR-33` | 사용자는 프로젝트 안에서 문서 본문을 검색할 수 있어야 한다 | 선택 | 기획안 | 프로젝트 경계 안에서만 결과 반환 |

**`SFR-31` 만 중요 등급인 이유** — 승인이 안 되면 산출물이 비어서 나온다.
대시보드 지표는 없어도 데모가 성립하지만, 이건 흐름을 막는다.

### 3.10 산출물

**이 영역이 제품의 출력물이다. 문서를 넣으면 문서가 나온다.**

| ID | 요구사항 | 중요도 | 출처 | 검증 방법 |
|---|---|---|---|---|
| `SFR-34` | 시스템은 축적된 데이터로 **주간 보고서 · 결정사항 대장 · 회의 안건**을 만들어야 한다 | 중요 | 팀합의 · 심사 | 우리 팀 문서를 넣어 손으로 만든 것과 나란히 비교 |
| `SFR-35` | 사용자는 산출물의 대상 기간과 파일 형식을 정할 수 있어야 하고, **형식에 기본값을 두지 않는다** | 중요 | 팀합의 | 형식 미선택 시 생성 불가 |
| `SFR-36` | **생성 전에 무엇이 담길지 미리 보여야 한다** | 중요 | 팀합의 | AI 호출 없이 건수 표시 확인 |
| `SFR-37` | 만든 산출물은 이력으로 남아 다시 내려받을 수 있어야 하고, 이후 문서가 추가되면 갱신이 필요함이 표시되어야 한다 | 중요 | 팀합의 | 생성 후 문서 추가 시 갱신 안내 표시 |

**`SFR-34` 의 검증 방법이 이 문서에서 가장 중요하다.** 미니 프로젝트에서 팀이
손으로 만든 결정사항 대장 29건과 주간 보고가 남아 있다. **같은 입력을 넣어
자동 생성물과 나란히 놓을 수 있다.** 비교 대상이 있으니 기준이 저절로 생긴다.

**`SFR-36` 이 세 가지를 동시에 해결한다.**

| | |
|---|---|
| 빈 산출물 방지 | 기간을 잘못 잡아 "문서 0건" 인 보고서를 만드는 걸 막는다 |
| 비용 절약 | AI 호출 전에 무엇이 잡히는지 보인다. 미리보기는 조회라서 공짜다 |
| 승인 유도 | "승인 대기 5건" 을 보여줘 순서를 화면이 알려준다 |

**`SFR-35` 에서 기본값을 없앤 것은 의도적이다.** 기본값이 있으면 사용자가 형식을
안 보고 만들고, 열어본 뒤 다시 만든다. 한 번 고르게 하는 게 싸다.

### 4.1 시스템 구성 요구사항 (SYR)

| `DAR-03` | 분석 결과는 덮어쓰지 않고 누적되어야 한다 | 필수 | 재분석 후 이전 행 존재 |

| `DAR-07` | 좌표는 이미지 크기와 무관한 형태로 저장되어야 한다 | 중요 | 다른 배율로 렌더링해도 위치 유지 |

**`DAR-01` 이 미니 프로젝트에서 실제로 문제였다.** 코드가 테이블을 만드는 방식은
처음엔 편하지만 컬럼을 하나 바꿀 때마다 데이터를 버려야 한다. 팀이 3명이 되면
각자 로컬 DB 가 달라진다.

**`DAR-07` 이 `SFR-13` 이 깨지는 원인을 막는다.** 화면이 보는 이미지와 인식 기준
이미지의 크기가 다르면 영역이 어긋난다. 비율로 저장하면 배율과 무관해진다.

### 4.3 인터페이스 요구사항 (SIR)

| ID | 요구사항 | 중요도 | 검증 방법 |
|---|---|---|---|
| `SIR-01` | **모든 오류 응답은 같은 형태여야 하고, 식별 가능한 코드를 포함해야 한다** | 필수 | 전 오류 응답 형태 일치 확인 |
| `SIR-02` | 오류 코드는 한 곳에서 정의되고 중복되지 않아야 한다 | 필수 | 정의 목록 중복 검사 |
| `SIR-03` | 화면과 서버가 주고받는 규약이 문서로 존재해야 한다 | 필수 | 계약서와 실제 응답 대조 |
| `SIR-04` | AI 제공자는 교체 가능해야 하며, **키 없이도 전체 흐름이 동작해야 한다** | 필수 | 키 미설정 상태로 업로드부터 산출물까지 통과 |

**`SIR-04` 가 20일 일정을 지키는 장치다.** 개발과 테스트에서 실제 AI 를 부르면
비용과 시간이 들고, 응답이 매번 달라 테스트를 쓸 수 없다. 대체 구현으로 전체
흐름을 통과시킬 수 있어야 한다.

### 4.4 성능 요구사항 (PER)

| ID | 요구사항 | 목표 | 중요도 | 측정 방법 |
|---|---|---|---|---|
| `PER-01` | 10페이지 스캔 문서 처리 완료 | ≤ 60초 | 중요 | 동일 파일 3회 평균 |
| `PER-02` | 업로드 응답 시간 | 파일 크기와 무관하게 즉시 | 필수 | 24페이지 스캔 문서로 확인 |
| `PER-03` | **목록 조회 질의 수** | **문서 수와 무관하게 일정** | 필수 | 문서 5건·50건에서 질의 로그 개수 비교 |
| `PER-04` | 주간 보고서 생성 | ≤ 15초 | 중요 | AI 1회 + 조회 |
| `PER-05` | 동시 사용 | 4~5인 정상 동작 | 중요 | 동시 업로드 5건 |
| `PER-06` | 산출물 생성 시 AI 호출 수 | 보고서 1건당 1회 | 중요 | 호출 로그 개수 |

**`PER-03` 의 측정 방법이 목표 자체보다 중요하다.** "빠르다" 는 측정할 수 없고
장비에 따라 달라진다. **질의 개수는 장비와 무관하고 정수로 나온다.** 문서 5건과
50건에서 같은 수가 나오면 통과다.

**`PER-06` 은 비용 요구사항이다.** 보고서를 만들 때 원문을 다시 보내면 문서
10건에 약 28,000 토큰이 들지만, 이미 저장된 요약만 보내면 약 1,500 토큰이다.
**저장된 결과를 재사용하는 것을 요구사항으로 못박는다.**

### 4.5 보안 요구사항 (SER)

| ID | 요구사항 | 중요도 | 검증 방법 |
|---|---|---|---|
| `SER-01` | **프로젝트 경계를 넘는 데이터 접근이 불가능해야 한다** | 필수 | 타 프로젝트 식별자 주입 시도 (`SFR-05`) |
| `SER-02` | 비밀번호는 복원 불가능한 형태로만 저장되고 응답에 포함되지 않아야 한다 | 필수 | DB 확인 · 응답 본문 검사 |
| `SER-03` | 외부 서비스 키는 서버에만 있어야 한다 | 필수 | 화면 번들 문자열 검사 |
| `SER-04` | 역할별 허용 동작이 서버에서 강제되어야 한다 | 필수 | `VIEWER` 토큰으로 쓰기 시도 시 403 |

**`SER-04` 에서 "서버에서" 가 핵심이다.** 화면에서 버튼을 숨기는 것은 보안이
아니다. 요청을 직접 보내면 통과한다.

### 4.6 품질 요구사항 (QUR)

| ID | 요구사항 | 목표 | 중요도 | 측정 방법 |
|---|---|---|---|---|
| `QUR-01` | 제안 채택률 | ≥ 70% | 중요 | 거부 기록 기반 실사용 집계 |
| `QUR-02` | 문서 유형 판별 정확도 | ≥ 85% | 중요 | **사람이 판별을 고친 비율** |
| `QUR-03` | 날짜 추출 정확도 | 측정 가능해야 한다 | 중요 | Golden Dataset 원문 대조 |
| `QUR-04` | 금액 항목 추출 정확도 | 측정 가능해야 한다 | 중요 | Golden Dataset 원문 대조 |
| `QUR-05` | **금액 집계 정확도** | **100%** | 중요 | 단위테스트 |
| `QUR-06` | **모든 오류 응답이 서버 기록에 남아야 한다** | 누락 0 | 필수 | 각 오류 상태를 유발하고 기록 확인 |

**`QUR-02` 의 측정 방식을 바꿨다.** 별도 정답 데이터를 만드는 대신 **사람이 AI
판별을 고친 비율**을 쓴다. 정답셋을 만드는 비용이 없고, 실사용 데이터라서 발표에서
더 설득력이 있다.

**`QUR-04` 와 `QUR-05` 를 나눈 것이 중요하다.** 추출은 원문이 정답이라 측정할 수
있고, 집계는 코드가 하니 100% 여야 한다. **"AI 가 금액을 얼마나 잘 맞추나" 는
정답이 없어서 하나의 지표로 쓸 수 없다.** 그래서 두 줄로 갈랐다.

**`QUR-06` 은 미니 프로젝트에서 실제로 빠져 있던 결함이다.** 사용자에게는 오류가
보이는데 서버 기록에는 아무것도 없어서, 무슨 일이 있었는지 추적할 수 없었다.

### 4.7 테스트 요구사항 (TER)

| ID | 요구사항 | 중요도 | 검증 방법 |
|---|---|---|---|
| `TER-01` | 모든 필수·중요 요구사항에 검증 방법이 있어야 한다 | 필수 | 이 문서의 검증 방법 열 빈칸 0 |
| `TER-02` | **외부 AI 호출 없이 전체 흐름을 테스트할 수 있어야 한다** | 필수 | 키 미설정 상태로 전 구간 통과 (`SIR-04`) |
| `TER-03` | 정확도 측정용 정답 데이터가 존재해야 한다 | 중요 | Golden Dataset 문서 수와 정답 항목 수 |
| `TER-04` | 통합 테스트 시나리오가 요구사항 ID 를 인용해야 한다 | 중요 | 시나리오와 이 문서의 ID 대조 |

**`TER-01` 이 심사 지적에 대한 직접적인 답이다.** 검증 방법을 못 쓰는 요구사항은
요구사항으로 두지 않았다. 그래서 이 문서에 빈칸이 없다.

기다리지 않아야 한다. 그래서 근거 표시 방식을 바꿨고(7.1절), 분석기를 나란히
두는 구조를 택했다.

## 6. 범위에서 제외한 것

| 안 함 | 이유 |
|---|---|
| 실시간 공동 편집 | 문서 편집 도구를 대체하려는 게 아니다 |
| 본격적인 일정 관리 도구 | 범위 밖 |
| **사람이 원가를 입력하는 비용 관리** | 제품 컨셉과 반대다. **우리는 문서에서 뽑는다** |
| **금액 추계 · 예측** | 없는 값을 만드는 일이다. 근거를 댈 수 없다 |
| 모바일 전용 앱 | 반응형 화면으로 대응 |
| **법률 문서 자동 생성** | 환각 위험 · 책임 문제 · 검증 부담 |
| AI 학습 | `COR-05` |
| **원문 위치 하이라이트** | 분석 규격을 바꿔야 해서 3인이 서로 기다린다 (`COR-03`) |

**세 번째 항목의 경계를 분명히 한다.** 사람이 원가를 입력하는 관리 기능은 안 하고,
**문서에서 뽑은 금액의 집계와 검증은 한다.** 차이는 "숫자를 누가 넣는가" 다.

## 7. 검토했으나 채택하지 않은 방안

**요구사항정의서에 이 절을 두는 이유** — 폐기한 방안과 그 이유가 남아 있지 않으면
같은 논의를 다시 한다. 미니 프로젝트에서 실제로 반복했다.

### 7.1 문서 유형으로 분석 방식을 고르는 안

| | 채택안 | 폐기안 |
|---|---|---|
| 방식 | 문서 유형과 무관하게 항상 전부 분석 | 유형별로 쓸 분석기를 규칙표로 선택 |
| 병렬성 | 한 번에 동시 실행 | **분류를 먼저 돌려야 해서 2단계로 쪼개진다** |
| 누락 | 없음 | **회의록·보고서에도 금액이 나오는데 놓친다** |
| 순환 문제 | 없음 | 분류는 분석 결과인데 선택은 분석 전에 필요하다 |

**병렬 처리가 안 된다는 지적이 폐기의 결정적 근거였다.** 규칙표 방식은 분류
결과를 기다려야 하므로 동시 실행이 불가능해진다.

### 7.2 비용추계 기능

| | |
|---|---|
| 원래 구상 | 단가와 수량으로 **없는 금액을 산출**한다 |
| 문제 | 단가 마스터를 만들어야 하고, **"그 단가 근거가 뭐냐" 에 답할 수 없다** |
| 대체 | 집계로 좁혔다. 문서에 적힌 금액만 모은다 |
| 결과 | **프로젝트 최대 위험이 통째로 사라졌다.** 모든 숫자에 출처 문서가 있다 |

### 7.3 근거를 원문 위치로 표시하는 안

| | 채택안 | 폐기안 |
|---|---|---|
| 방식 | 판단 근거를 **문장으로** 서술 | 몇 페이지 어느 위치인지 좌표로 표시 |
| 규격 변경 | 없음 | 분석 규격을 바꿔야 한다 |
| 3인 병행 | 가능 | **서로 기다린다** (`COR-03`) |
| 대가 | 원문 대조 검증이 어렵다 | — |

**대가를 그냥 감수하지 않고 대체 수단을 뒀다.** 검증이 필요한 금액에는
합계 대조(`SFR-25`)를 넣어 다른 방식으로 확인한다.

### 7.4 분석을 하나로 합치는 안

| | 채택안 (넷으로 나눔) | 폐기안 (하나로 합침) |
|---|---|---|
| 입력 토큰 | 약 11,200 | **약 2,850** |
| 기존 코드 | **수정 0줄** | 흡수하며 회귀 위험 |
| 실패 범위 | 하나 실패해도 나머지 살아남는다 | 전부 실패 |
| 금액 정확도 | **프롬프트를 집중할 수 있다** | 주의가 분산된다 |

**토큰 4배를 감수했다.** 개발 중에는 대체 구현을 쓰므로(`SIR-04`) 실제 비용은
측정·데모 때만 발생한다. 그리고 **금액은 정확도가 중요해서 프롬프트를 섞지 않는
편이 낫다.**

단, 이건 되돌릴 수 있는 결정이다. **넷으로 시작해서 측정한 뒤 재검토한다.**

## 9. 미결 사항

**착수 전에 팀 합의가 필요한 것만 남겼다.** 기능명세서 17절의 25건 중 요구사항
수준에서 답해야 하는 것을 골랐다. 나머지는 구현 세부라서 기능명세서에 둔다.

| | 안건 | 관련 요구사항 | 내 의견 | 필요한 사람 |
|---|---|---|---|---|
| 1 | **산출물 영역을 중요 등급으로 두는 데 동의하는가** | `SFR-34`~`37` | **동의 필요.** 이게 없으면 "태스크 모음으로 뭘 하나" 에 답이 없다 | 전원 |
| 2 | 검수 구조 편집을 선택 등급으로 두는 데 동의하는가 | `SFR-16` | 동의 요청 | 재정 |
| 3 | 조회 권한자에게 금액을 보일 것인가 | `SFR-26` · `SER-04` | 미결 | 전원 |
| 4 | 항목 추출과 금액 중 무엇을 먼저 만드는가 | `SFR-20` · `SFR-24` | **항목 추출로 승인 골격을 만들고 금액을 두 번째로 얹는다** | 보현 |
| 5 | 활동 기록의 항목 목록 | `SFR-30` | 팀 합의 필요. 주간 보고서 재료다 | 전원 |
| 6 | 배포 환경 (클라우드 · 사내) | `SYR-01`·`SYR-05` | 인식 처리에 전용 장비가 필요한지와 직결 | 전원 |
| 7 | AI 제공자 (상용 API · 로컬 모델) | `SIR-04` | **상용 API 유지 권장.** 소형 로컬 모델에서 언어 쏠림 사례를 봤다 | 세현 |
| 8 | Golden Dataset 문서 수와 담당 | `TER-03` | 미정 | 전원 |
| 9 | 담당 재편 확정 | 전체 | **진행 중.** 확정 전에는 WBS 담당을 갱신할 수 없다 | 전원 |

**9번이 다른 것을 막고 있다.** 담당이 확정되지 않으면 WBS 를 확정할 수 없고,
WBS 가 없으면 20일 안에 들어가는지 확인할 수 없다.

## 0. 지표 읽는 법

| 지표 | 뜻 | 자바·Spring 로 바꿔 말하면 |
|---|---|---|
| **R@1** | 1등으로 올린 것이 정답인 비율 | `assertEquals(expected, list.get(0))` |
| **R@3** | 상위 3개 안에 정답이 있는 비율 | `assertTrue(list.subList(0,3).contains(expected))` |
| **R@5** | 상위 5개 안에 정답이 있는 비율 | 같은 방식 · **화면에 5개를 보여주므로 이것이 실사용 지표다** |
| **R@10** | 상위 10개 안 | 더 넉넉하게 본 값 |
| **MRR** | 정답이 몇 등에 올라왔는지의 역수 평균 | 1등이면 1.0 · 2등이면 0.5 · 5등이면 0.2 |

| 질의 구분 | 뜻 | 왜 나눴나 |
|---|---|---|
| **겹침 (overlap)** | 질문에 정답 조각의 낱말이 **그대로 들어 있다** | 지금 쓰는 낱말 검색으로도 찾힌다 |
| **안겹침 (no_overlap)** | 질문에 그 낱말이 **하나도 없다** | **뜻으로만 찾아야 한다. 임베딩을 쓰는 이유가 이것이다** |

**판단 기준은 "안겹침 R@5" 다.** 겹침 질의는 임베딩 없이도 되는 일이라 모델을
고르는 근거가 못 된다. 실제로 두 지표에서 순위가 뒤집힌다(2절·3절).

**비율보다 문항 수를 먼저 적었다.** `0.641` 보다 `41 / 64` 가 크기를 가늠하기 쉽고,
"몇 문항 차이" 로 판정선을 정했기 때문이다.

## 5. 실행 비용

### 5-1. 믿을 수 있는 값 — `check_model_cost.py` 3종

모델 하나를 독립 프로세스에서 순차로 쟀다. 다른 프로세스를 함께 돌리지 않았다.

| 모델 | dtype | 상한 | 적재(초) | 전체(초) | **100청크당(초)** | 적재직후(MB) | **최고(MB)** |
|---|---|---|---|---|---|---|---|
| `nlpai-lab/KURE-v1` | float32 | 8192 | 6.9 | 308.3 | **47.51** | 810 | **2,203** |
| `dragonkue/BGE-m3-ko` | float32 | 8192 | 7.4 | 371.2 | **57.19** | 809 | **2,203** |
| `Qwen/Qwen3-Embedding-0.6B` | float32 | 1024 | 8.0 | 763.9 | **117.70** | 3,951 | **4,801** |

**메모리는 "최고" 열을 쓴다.** `적재직후` 는 safetensors 가 파일을 메모리에
매핑(mmap)만 해둔 상태라 아직 읽지 않은 몫이 빠져 있다. 가중치가 2,166MB 인
모델이 809MB 로 보이는 이유가 이것이다.

### 5-2. 참고 값 — `run_eval.py` (신뢰도 낮음)

| 모델 | 적재(초) | 전체(초) | 100청크당(초) | 메모리(MB) |
|---|---|---|---|---|
| `BAAI/bge-m3` | 21.8 | 395.1 | 60.88 | 1,986 |
| `nlpai-lab/KURE-v1` | 6.6 | 364.2 | 56.11 | 1,534 |
| `dragonkue/multilingual-e5-small-ko-v2` | 6.6 | 35.1 | **5.41** | 430 |
| `intfloat/multilingual-e5-base` | 7.3 | 116.3 | 17.92 | 671 |
| `intfloat/multilingual-e5-large` | 6.8 | 374.9 | 57.77 | 1,481 |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | 7.9 | 372.6 | 57.41 | 1,473 |
| `nomic-ai/nomic-embed-text-v2-moe` | 13.5 | 167.7 | 25.84 | 2,091 |
| `dragonkue/BGE-m3-ko` | 6.7 | 372.3 | 57.36 | **-359** |

**이 표의 메모리 열은 틀렸다.** 두 가지 증거가 있다.

| 증거 | 내용 |
|---|---|
| 1 | `BGE-m3-ko` 에 **-359MB** 를 찍었다. 음수는 있을 수 없다 |
| 2 | 같은 모델을 **1,494MB** 로도 찍었는데(3모델 실행) **가중치만 2,166MB** 다. 모델이 자기 가중치보다 적게 쓸 수는 없다 |

원인은 **현재 사용량을 모델 전후로 재서 빼는 방식**이다. 앞 모델이 해제된 몫까지
상계되어 실제보다 작아지고, 때로는 음수가 된다.

**시간 열도 흔들린다.** `KURE-v1` 을 세 번 재서 **47.51 · 56.11 · 77.67초**가
나왔다. 같은 모델·같은 코퍼스다. 반면 `BGE-m3-ko` 는 **57.19 · 57.27 · 57.36** 으로
붙어 있다. 왜 한쪽만 흔들리는지 모른다.

> **그래서 이 표로 속도 순위를 매기지 않는다.** 확실한 것은 `Qwen3` 가 다른
> 1024 후보보다 **약 2~2.5배 느리다**는 것뿐이다. 이 격차는 편차를 넘는다.

`e5-small-ko-v2`(384)가 **5.41초**로 압도적으로 빠른 것은 차원과 층수가 작아서이며,
이건 편차로 설명되지 않는 실제 차이다.

### 채택 모델의 배포 경로에 작업이 하나 더 붙는다

**`dragonkue/BGE-m3-ko` 는 Ollama 공식 라이브러리에 없다.** 허깅페이스 전용
모델이다. Ollama 로 올리려면 **GGUF 파일을 내려받아 `Modelfile` 로 직접 등록**해야
한다.

| 후보 | Ollama 경로 | 배포 작업 |
|---|---|---|
| `bge-m3` · `arctic-l-v2.0` · `nomic-v2-moe` | **공식** | `ollama pull` 한 줄 |
| **`BGE-m3-ko`** (채택) | **GGUF + Modelfile** | 파일 내려받기 → `ollama create` → 태그 관리 |
| `KURE-v1` | 비공식 저장소 | `ollama pull daynice/kure-v1` |

**이것이 채택을 뒤집는 사유는 아니다.** 품질이 41 대 37 로 앞서고 한 번 등록해
두면 이후는 같다. 다만 **`RAG-02 임베딩 생성·저장` 에 "모델 등록" 작업이 하나
늘어난다.** 그 작업을 모르고 배포 일정을 잡으면 막힌다.

**대안이 여기서 값을 한다.** 공식 경로가 필요하면 `arctic-embed-l-v2.0`(안겹침 37 ·
BGE-m3-ko 와 4문항 차 · 통계적으로 구별 안 됨)이 `ollama pull` 한 줄로 끝난다.
차원이 같으므로 DB 를 안 건드리고 바꿔 끼울 수 있다.

**GGUF 변환본의 품질은 재지 않았다.** GGUF 는 양자화본이므로 우리가 잰 fp32
점수와 다를 수 있다. 10절에 미확인으로 올렸다.

### 접두어에서 걸린 함정

`nomic` 이 선언한 값은 이렇다.

```
"query":    "search_query: "
"document": ""                  <- 비어 있다
"passage":  "search_document: " <- 실제 문서 접두어는 여기
```

`document` 키를 그대로 믿으면 **nomic 문서에 접두어가 안 붙는다.**
`arctic` 은 정반대로 `"document": ""` 가 **진짜로 안 붙이는 것이 맞다**(`passage`
키가 없다). 같은 빈 문자열인데 뜻이 다르다. 규칙은 이렇게 정했다.

> `passage` 가 있고 비어 있지 않으면 그것을 쓴다. 없으면 `document` 를 쓴다.
> 그것도 비어 있으면 접두어 없음.

## 7. 통계 검정 — 개수 차이가 우연인지 본다

같은 질의에 대한 적중을 맞대어 **엇갈린 질의만** 세었다(McNemar).
개수 차이만 보면 "누가 맞히고 누가 틀렸는지" 를 알 수 없다.

| 대비 | A만 맞힘 | B만 맞힘 | 엇갈림 | 양측 p | 판정 |
|---|---|---|---|---|---|
| BGE-m3-ko 대 KURE-v1 · 안겹침 64 | 5 | 1 | 6 | **0.22** | 유의하지 않다 |
| BGE-m3-ko 대 KURE-v1 · 전체 133 | 8 | 1 | 9 | **0.039** | **유의하다** |
| KURE-v1 대 bge-m3 · 안겹침 64 | 7 | 5 | 12 | **0.77** | **구별 불가** |

**측정 전에 판정선을 정해 두었다.** 결과를 보고 기준을 옮기지 않기 위해서다.

| 격차 (안겹침 64문항) | 판정 |
|---|---|
| 6문항 이상 | 실제 차이로 본다 |
| 4~5문항 | 참고. 다른 기준과 함께 판단 |
| 3문항 이하 | 판별 불가 |

**BGE-m3-ko 는 KURE-v1 을 4문항 앞선다 — 판정선을 넘지 못했다.**
안겹침 64문항 중 **6개만 엇갈렸고 58개는 똑같이 움직였다.** 그런데도 1위로 적는
근거는 **8개 지표 전부에서 1위이고 전체 질의로는 유의하기 때문**이다(p=0.039).

**KURE-v1 과 bge-m3 는 구별되지 않는다(p=0.77).** 37 대 35 로 벌어져 보이지만
엇갈린 12문항이 7 대 5 로 거의 반반이다. 개수 차이는 우연이었다.

## 8. 이 표에서 나온 발견 셋

### 8-1. 차원이 높으면 좋다는 것은 성립하지 않는다

| 차원 | 모델 | 안겹침 R@5 |
|---|---|---|
| 1024 | `BGE-m3-ko` | **41** |
| 1024 | **`e5-large`** | **18 (최하위)** |
| 768 | `nomic` | 27 |
| 384 | `e5-small-ko-v2` | 19 |

**1024인 `e5-large` 가 384인 `e5-small-ko-v2` 보다 낮다.**
545청크에서도 그랬고 649청크에서도 그렇다. **재현되지만 원인은 모른다.**

상세 결과에 단서는 있다. 질의가 달라도 같은 청크 묶음이 반복해서 1위로 올라온다.

```
e5-large / 안겹침 / 상위5 = 374,300,273,144,186
e5-large / 안겹침 / 상위5 = 374,300,186,144,408
e5-large / 안겹침 / 상위5 = 300,374,273,186,144
```

**이것은 관찰이고 원인이 아니다.** 토큰 잘림 가설과 허브 청크 가설은 둘 다
기각했다. 잘린 청크는 애초에 없었다(9절).

**그래도 `vector(1024)` 결정은 유지된다.** 상위 4위가 모두 1024이고,
768(27·22)과 384(19)는 그보다 낮다. `e5-large` 는 계열 안의 이상값이다.

### 8-2. 같은 모델이 1위와 8위를 동시에 한다

| `dragonkue/multilingual-e5-small-ko-v2` (384차원) | 순위 |
|---|---|
| 겹침 R@5 — **64 / 69** | **1위** |
| 안겹침 R@5 — **19 / 64** | **8위** |

질의 낱말이 조각에 그대로 있으면 작은 모델도 맞힌다. 반대로 큰 모델도 낱말이
안 겹치면 절반을 놓친다.

**그래서 벡터 검색 하나로는 부족하다.** 낱말 일치(BM25 등)와 벡터 검색을 함께
쓰고 점수를 합치는 편이 두 유형을 모두 잡는다. 의미 검색(RAG-04)과
하이브리드 검색(RAG-05)을 나눠 둔 근거가 이 표다.

### 8-3. 정밀도를 맞추지 않으면 성능 비교가 아니라 설정 비교가 된다

`Qwen3` 를 처음 잴 때 `bfloat16` 으로 올라왔고, 나머지는 `float32` 였다.

| | bfloat16 | float32 | 배수 |
|---|---|---|---|
| 100청크당 | 약 3,000초 | **117.7초** | **약 26배** |

**모델을 바꾸지도, 청크를 줄이지도 않았다.** 정밀도만 맞췄다.
파라미터 수는 596M 대 568M 로 거의 같으므로 처음의 70배 차이는 모델 특성이
아니었다.

모델을 나란히 재려면 세 가지를 맞춰야 한다. **이번에 둘은 맞췄고 하나를 놓쳤다.**

| | 조건 | 이번 시험 |
|---|---|---|
| 1 | **접두어** | 맞췄다 (6절) |
| 2 | **최대 입력 길이** | 맞췄다 (9절) |
| 3 | **정밀도(dtype)** | **놓쳤다** |

### 청크와 토큰

| 항목 | 값 |
|---|---|
| 전체 청크 | 649개 |
| 총 글자 | 210,078자 |
| 평균 | 305자 |
| 가장 긴 청크 | 697자 |
| **512토큰 초과 청크** (XLM-R 계열) | **0개** |

**잘린 청크는 없다.** 상한이 512인 `e5` 3종과 `nomic` 도 잘림이 발생하지 않았다.

토크나이저가 다르면 토큰 수가 다르다. 같은 청크가 XLM-R 로는 512 이하인데
Qwen3 로는 620토큰까지 나온다. **"몇 토큰인가" 는 모델마다 다른 값이다.**

### 평가셋

| 항목 | 값 |
|---|---|
| 질의 | 133개 |
| 겹침 | 69개 |
| **안겹침** | **64개** |
| 정답으로 쓴 청크 | 62개 |

안겹침 질의는 **정답 조각의 낱말을 부분 문자열까지 피해서** 썼다. 도구로 전수
검사해 걸린 것을 고쳤다. 예를 들어 `보안` 은 조각에 `보안약점` 이 있어 걸렸고,
`정하` 는 `지정하여야` 안에 들어 있어 걸렸다.

고시 조문 기반 질의 60개는 **조 번호를 쓰지 않았다.** "제18조의 배점한도는?" 이라고
물으면 `제18조` 라는 글자가 그 조각에만 있어 **임베딩 실력이 아니라 글자 일치로**
맞히기 때문이다.

| 항목 | 값 |
|---|---|
| 장치 | CPU 전용 (GPU 없음) |
| 라이브러리 | sentence-transformers |
| 정밀도 | float32 (`Qwen3` 는 `bfloat16` → `float32` 강제) |

### 재현성

같은 코퍼스·질의로 두 번 돌렸더니 품질 수치가 **완전히 같았다.**

## 10. 이 표에 없는 것

| 없는 것 | 왜 |
|---|---|
| API 모델 (Voyage·OpenAI·Gemini) | 팀에서 쓰지 않기로 정했다. 하네스는 남겨 뒀다 |
| 양자화본 성능 | **fp32 로 재고 양자화본으로 배포할 예정이다.** 그 차이를 안 쟀다 |
| **채택 모델의 GGUF 변환본 성능** | `BGE-m3-ko` 는 Ollama 공식이 아니라 GGUF 로 등록해야 한다(6절). **GGUF 는 양자화본이므로 우리가 잰 fp32 점수와 다를 수 있다** |
| Ollama 경로 속도 | 위와 같은 이유. 후보 전부에 해당한다 |
| 나머지 6종의 믿을 수 있는 비용 | `check_model_cost.py` 로 3종만 쟀다 |
| 속도의 여러 번 측정 중앙값 | 한 번씩만 쟀다. `KURE-v1` 이 47.5~77.7초로 흩어졌다 |
| `Qwen3` 의 깨끗한 메모리 | 지금 값은 fp32 변환으로 두 벌이 겹친 상태다 |
| 재순위(reranker) 조합 | 384차원 + 교차 인코더가 1024를 대체할 수 있는지 안 봤다 |
| 프로젝트 단위 필터를 걸었을 때 | 필터 없이 전량 검색으로 쟀다. 실사용은 프로젝트로 좁혀진다 |

**여기 있는 것을 모른 채로 이 표를 "완결" 이라고 부르지 않는다.**
기본 모델을 정하는 데 필요한 것은 채워져 있고, 배포 성능을 약속하는 데 필요한
것은 비어 있다.

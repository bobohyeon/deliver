# 팀 공유용 메시지 초안

메신저에 그대로 붙여 넣을 수 있게 쓴 것이다. **표를 쓰지 않았다** — 카카오톡 ·
Slack 에서 마크다운 표가 깨지기 때문이다.

구성은 **① 두 분 것 위에 무엇을 얹는지 → ② 바뀌어야 하는 부분** 순서다.
일정 논쟁은 앞세우지 않는다. 20일이라는 전제만 짧게 밝히고 기능으로 넘어간다.

세 덩어리다. 팀 채널에 ①을 올리고 ②③은 각자에게 따로 보낸다.

## ① 팀 채널 — 전체 공유

```
[본프로젝트 설계 정리 · 확인 부탁드립니다]

세현님 목업·기획안, 재정님 3모드 확장안·OCR DB 설계안 위에 제 금액 파트를
얹어서 문서로 정리했습니다. 두 분 설계는 그대로 살렸고, 분석기가 2개 이상이 될 때
안 맞는 지점만 조정했습니다.

■ 전제 — 구현은 20일로 잡았습니다

테스트 기간을 반드시 남겨야 해서 이렇게 끊었습니다.

  설계·합의      8/10 ~ 8/14    5일
  구현           8/17 ~ 9/5     20일   (코드 프리즈 9/4 금)
  테스트·산출물   9/7  ~ 9/11    5일
  리허설·예비     9/12 ~ 9/13    2일

구현 20일은 영업일 15일이고 3인이면 45 인일입니다.
P0+P1 이 78개라 다 못 합니다.

근데 덜어내는 방식보다 묶는 방식으로 가면 꽤 들어갑니다.
액션아이템과 금액이 같은 골격(제안 카드 → 승인 → 태스크 → 역추적)을 쓰기 때문에,
골격을 한 번 만들면 두 번째 분석기는 훨씬 쌉니다.
그래서 기능을 빼는 논의보다 "무엇을 같이 만들면 싸지나" 를 정하는 게
남는 게 많다고 봅니다.

테스트·산출물 5일에는 문서를 새로 쓰지 않습니다.
기능명세서에 P0·P1 전부 완료 판정 기준을 붙여놨는데, 그게 그대로
통합테스트 기대결과가 됩니다. 5일은 실행과 판정에만 씁니다.


■ 두 분 것 위에 제가 얹는 것

새로 만드는 화면은 하나(단가 기준)뿐입니다. 나머지는 두 분이 만든 것 위에 얹습니다.


[세현님 목업 위에]

1) 문서 유형별 분석기 라우팅
   무엇: 문서 유형에 따라 어떤 분석기를 돌릴지 정하는 표를 만듭니다.
         계약서면 금액까지, 회의록이면 액션아이템까지.
   이걸로: 세현님이 대시보드에 그려놓은 "문서 유형 분포" 가 실제로 쓰입니다.
         계약서 9건에서 뽑는 게 지금은 없는데, 거기에 금액이 붙습니다.
         그리고 회의록에 금액 분석기를 안 돌려서 API 비용과 시간을 아낍니다.
         설정 화면에 이 표를 그대로 보여주면 "분석기가 갈아 끼울 수 있는
         부품" 이라는 말을 화면으로 증명할 수 있습니다.

2) 문서 상세 우측 패널에 "금액 항목" 섹션
   무엇: 액션아이템 카드와 똑같은 형식으로 금액 항목 카드를 붙입니다.
         제안 카드, 승인/수정/거부 버튼, 확신도, 출처 링크 전부 그대로 씁니다.
   이걸로: 계약서를 열면 항목명·수량·단가·금액이 카드로 뜹니다.
         승인하면 확정되고, 승인 전에는 어디에도 반영되지 않습니다.
         UI 패턴을 새로 만들지 않으니 프론트 작업이 거의 없습니다.

3) 합계 대조
   무엇: 뽑아낸 항목들을 Python 으로 더해서 문서에 적힌 합계와 맞춰봅니다.
   이걸로: 이게 금액 기능이 다른 분석기보다 센 지점입니다.
         액션아이템은 AI 가 뽑은 게 맞는지 알 방법이 없는데,
         금액은 재계산해서 대조할 수 있습니다.
         예를 들어 항목 합계 72,000,000 인데 문서 기재가 79,200,000 이면
         차액 7,200,000 을 표시하고 "부가세 누락 가능" 을 띄웁니다.

4) 태스크 자동 제안
   무엇: 합계가 안 맞거나 단가가 미확정이면 태스크 제안을 만듭니다.
         (자동 등록은 안 합니다. 승인해야 등록됩니다)
   이걸로: 세현님 보드가 항상 채워집니다.
         검증만 하는 기능이면 문서가 깨끗할 때 태스크가 안 생겨서
         시연할 때 보드가 빕니다. 그런데 문서에 단가가 안 적혀 있는 경우는
         거의 항상 있어서, 태스크·승인 UI·역추적이 전부 동작하는 화면을
         만들 수 있습니다.

5) 프로젝트 금액 현황
   무엇: 프로젝트 카드와 대시보드에 "미확정 금액" 지표를 넣습니다.
   이걸로: 프로젝트를 열기 전에 신뢰할 수 있는 금액인지 알 수 있습니다.
         승인 대기와는 성격이 다릅니다. 승인 대기는 사람이 판단하면 끝인데,
         미확정 금액은 단가 같은 문서 밖의 값을 채워야 끝납니다.


[재정님 파이프라인 위에]

6) 검수된 텍스트를 금액 계산의 입력으로
   무엇: 검수 완료된 텍스트로 금액을 뽑고, 어느 revision 을 썼는지 기록합니다.
   이걸로: 재정님 검수 모드의 효과를 수치로 보여줄 수 있습니다.
         검수 전 금액 오류 몇 건 → 검수 후 몇 건, 이렇게요.
         검수 모드가 "있으면 좋은 기능" 이 아니라 "없으면 틀리는 기능" 이 됩니다.

7) revision 사슬을 금액까지 연장
   무엇: 재정님이 두신 analyses.source_text_revision 을 금액까지 잇습니다.
         ocr_elements 수정 → ocr_revision++ → extracted_texts
         → analyses → amount_items → cost_estimates
   이걸로: OCR 을 고치면 이미 계산된 금액이 자동으로 "오래됨" 표시가 됩니다.
         12,000,000 을 72,000,000 으로 고쳤는데 화면에 옛 금액이 남으면
         안 되니까요. 문장은 오탈자 한둘 있어도 요약이 대충 맞는데
         금액은 한 글자가 전부를 바꿉니다.

8) OCR 박스 좌표로 금액 역추적
   무엇: 금액 항목에 ocr_element_id 를 붙입니다.
   이걸로: 금액 숫자를 누르면 원본 이미지의 그 박스가 하이라이트됩니다.
         재정님이 저장하는 좌표를 그대로 씁니다. 제가 새로 만들 게 없습니다.

9) 단가 기준 데이터
   무엇: 단가표를 만들고 항목마다 출처와 기준일을 붙입니다.
   이걸로: 문서에 단가가 안 적힌 항목도 계산할 수 있습니다.
         AI 가 단가를 추측하면 그게 환각이라, 문서에 없으면 비워두고
         사람에게 묻습니다. 그게 이 기능의 안전장치입니다.


정리하면, 제 파트의 원칙은 하나입니다.
"LLM 은 문서에 있는 것만 뽑고, 계산은 Python 이 한다."
문서에 없는 숫자를 AI 가 만들어내지 않게 하는 게 핵심입니다.


■ 바뀌어야 하는 부분 — 6개

1) 분석기 규격에 위치 정보를 넣어야 합니다   [가장 중요]

   코드를 보니 지금 분석기는 텍스트 문자열 하나만 받습니다.

     async def analyze(self, text: str) -> AnalyzeResult

   근데 세현님 목업 액션아이템 카드에 이렇게 있습니다.

     근거 · 3페이지 "다음 주 금요일까지 김민수 책임이…"

   "3페이지" 를 알 방법이 지금 규격에는 없습니다.
   텍스트를 한 문자열로 합쳐서 넘기기 때문입니다.
   ExtractResult 에 page_count 는 있는데 content 는 페이지 구분이 없습니다.

   즉 역추적이 액션아이템·금액 양쪽 다 지금 규격으로는 불가능합니다.
   컨셉 원칙 3번(모든 결과는 원문으로 역추적된다)이 여기 걸려 있습니다.

   → analyze() 에 optional 인자로 위치 정보를 넘기는 방식을 제안합니다.

     async def analyze(self, text, context=None) -> AnalyzeResult

     context 에 (페이지번호, 시작offset, 끝offset) 목록을 담습니다.
     기존 요약·분류 분석기는 안 고쳐도 됩니다. optional 이라 무시하면 됩니다.

   이 위치 정보는 재정님이 텍스트 조립할 때 자연히 나옵니다.
   reading_order 로 이어 붙일 때 각 조각의 offset 을 기록하면 됩니다.

   인터페이스 변경이라 구현 첫 주에 규격만 먼저 확정하면 좋겠습니다.
   페이크 값으로 프론트를 붙이면 세 사람이 병렬로 갈 수 있습니다.
   미니 프로젝트에서 페이크 구현체로 병렬 작업한 것과 같은 방식입니다.

2) 파이프라인 단계에서 분석기 이름을 빼야 합니다   [세현님·프론트]

   목업이 "④ 액션 아이템 추출" 로 되어 있는데 이게 특정 분석기 이름입니다.
   금액 분석기 들어오면 6단계, 그다음엔 7단계가 됩니다.
   그때마다 화면·상태 enum·백엔드를 각자 고쳐야 합니다.
   → "분석 2/3" 처럼 분석기 개수 기반으로 바꾸면 됩니다.
   라우팅이 들어오면 문서마다 분석기 수가 달라져서 (회의록 3개, 계약서 4개)
   고정 단계로는 표현이 안 됩니다.

3) 문서 분류 결과를 라우팅 기준으로 올려야 합니다   [세현님·DB]

   라우팅을 설계하다 막혔습니다.
   분류 결과는 분석을 돌려야 나오는데, 라우팅은 분석 전에 정해야 해서 순환입니다.
   → 분류만 라우팅 대상에서 빼고 무조건 먼저 실행하고,
     그 결과를 documents.document_type 에 확정값으로 넣는 방식을 제안합니다.
   미니 프로젝트에서 항상 general 이던 그 컬럼이 여기서 실제로 쓰입니다.
   분류가 틀리면 라우팅도 틀리니까 사람이 고칠 수 있게 해야 합니다.

4) revision 사슬을 금액까지 연장   [재정님 설계의 연장]
   위 7번 내용입니다.

5) tasks 의 출처가 3갈래가 됩니다   [세현님·DB]

   지금 source_analysis_id 하나인데, 금액 항목과 OCR 박스도 출처가 됩니다.
   → nullable FK 3개 + CHECK 제약을 제안합니다.
     source_type + source_id 방식은 FK 를 못 걸어서 안 쓰는 게 좋다고 봅니다.

6) AI 채택률을 분석기별로 나눠야 합니다   [세현님·대시보드]

   목업에 "AI 제안 채택률 72%" 가 하나로 있는데 분석기가 늘면 의미가 섞입니다.
   액션아이템은 놓쳐도 사람이 기억하지만 금액은 놓치면 돈이 틀립니다.
   같은 지표로 묶기 어렵습니다.
   그리고 거부를 기록해둬야 채택률 계산이 됩니다.


■ 용어 하나 맞추고 갔으면 합니다 — 분석기

미니 프로젝트 발표에서 "분석기가 무슨 뜻이냐" 를 질문받았는데,
우리끼리도 정의가 조금씩 다른 것 같아서 코드 기준으로 적어둡니다.

분석기는 Analyzer Protocol 을 구현한 클래스입니다.
규격은 메서드 하나뿐입니다.

  async def analyze(self, text: str) -> AnalyzeResult

  입력: 추출된 텍스트 문자열 하나
  출력: result(dict) + 모델명·토큰·지연시간

지금 2개 있습니다. SummaryAnalyzer, CategoryAnalyzer.
dependencies.get_analyzer_registry() 가 {"summary": ..., "category": ...} 로
들고 있고, 요청의 analyzer_types 로 골라서 asyncio.gather 로 동시 실행합니다.
결과는 analyses 테이블에 한 행씩 쌓이고 analyzer_type 으로 구분합니다.

중요한 건 분석기가 아는 게 거의 없다는 점입니다.
파일도 모르고 (PDF 인지 HWPX 인지 모름), 문서도 모르고 (document_id, project_id
모름), DB 도 모릅니다 (저장은 서비스가 함).
텍스트 문자열 하나 받아서 dict 하나 돌려주는 부품입니다.
그래서 갈아 끼울 수 있습니다.

금액 분석기를 만든다는 건 AmountAnalyzer 클래스 하나 만들고
registry 에 "amount": AmountAnalyzer(ai_client) 한 줄 추가하는 겁니다.
라우터·서비스는 안 고칩니다.

이 정의 때문에 위 1번이 문제가 됩니다.
분석기가 텍스트만 받으니까 페이지를 모르는 겁니다.


■ 먼저 정할 것 4개

1. 분석기 규격에 위치 정보 추가 (바뀔 것 1번)
   역추적이 여기 걸려 있고 인터페이스 변경이라 제일 먼저 정해야 합니다.

2. 파이프라인 단계 일반화 (바뀔 것 2번)
   목업·프론트·enum·백엔드 4곳이 걸립니다.

3. 분류 결과를 라우팅 기준으로 쓸지 (바뀔 것 3번)
   documents 컬럼 의미가 바뀌어서 마이그레이션에 영향 있습니다.

4. 단가 기준 데이터 범위
   제 파트 최대 위험입니다. 공공 단가 체계를 20일에 다루는 건 불가능해서,
   팀이 만든 소규모 단가표로 고정하고 화면에 "데모 범위" 라고 밝히는 방향을
   생각하고 있습니다. 이걸 안 정하면 발표에서 "그 숫자 근거가 뭐냐" 로
   무너집니다.

내일(8/11) DB 모델링 하기로 되어 있으니 1번 3번만이라도 답 주시면 좋겠습니다.

문서에 제 의견을 다 적어놨는데 어디까지나 제안입니다.
아니라고 생각하시는 부분 말씀해 주시면 고치겠습니다.
```

```
새로 안 만들었습니다.

금액 항목이 액션아이템하고 구조가 같아서요 —

기획안에 빠져 있는 것 같습니다. 그 자리가 제 금액 파트라고 보고 있습니다.
문서 유형 분포에 계약서가 9건인데 계약서에서 뽑는 게 없는 것도 같은 맥락입니다.

다른 하나가 좀 큽니다. 액션아이템 카드에 "근거 · 3페이지" 가 있는데,
지금 분석기 규격으로는 페이지를 알 수 없습니다.
analyze(text: str) 이라 텍스트 문자열만 받아서요.
목업이 요구하는 걸 지금 코드로는 못 만듭니다.
제가 규격을 바꾸는 안을 올려놨는데 (팀 메시지 바뀔 것 1번)

세현님 쪽에서 바뀔 게 네 개입니다. 팀 메시지 2·3·5·6번인데

문서에서 뽑은 금액을 집계·검증하는 건 합니다.
```

## ③ 최재정님께

```
재정님, OCR DB 설계안 꼼꼼해서 그대로 채택했습니다.
ocr_elements, document_pages, revision 체계, 비율 좌표, 논리 삭제,
version 낙관적 락 전부 변경 없이 넣었습니다.
processing_mode 에서 BATCH 빼고 batch_item_id 로 가자는 것도 그대로 반영했습니다.


제가 얹는 건 세 개입니다.

하나, 검수된 텍스트를 금액 계산의 입력으로 씁니다.
어느 revision 을 썼는지 기록해서, 검수 전후 금액 오류 건수를 비교할 수 있게
하려고 합니다. 재정님 검수 모드의 효과를 수치로 보여줄 수 있습니다.

둘, revision 사슬을 금액까지 연장합니다.
analyses.source_text_revision 두신 걸 amount_items, cost_estimates 까지
이었습니다. 금액은 revision 에 특히 민감해서요.
OCR 이 12,000,000 으로 읽은 걸 사람이 72,000,000 으로 고쳤는데
이미 계산된 금액이 옛 숫자면 안 되니까요.

셋, ocr_element_id 로 금액 역추적을 합니다.
금액 숫자를 누르면 원본 이미지의 그 박스가 하이라이트되는 건데,
재정님이 저장하는 좌표를 그대로 쓰는 거라 제가 새로 만들 게 없습니다.
설계안 9-1 에서 박스 id 유지와 논리 삭제를 강조하신 이유가
tasks.source_ocr_element_id 였는데, amount_items 도 같은 이유로 필요합니다.


그래서 재정님 검수 모드가 제 금액 파트의 전제입니다.
검수 없이는 금액 기능이 성립하지 않습니다.

반대로도 도움이 될 것 같은데, 검수 모드가 "왜 필요하냐" 에
금액이 가장 좋은 답이 됩니다. 숫자는 OCR 오인식에 제일 취약해서
1 을 7 로, 0 을 8 로 읽으면 전부 틀립니다. 자릿점 하나 놓치면 10배가 됩니다.
문장은 오탈자 한둘 있어도 요약이 대충 맞는데 금액은 아니라서요.
"있으면 좋은 기능" 이 아니라 "없으면 틀리는 기능" 이 됩니다.

목업에 계약_변경합의서_스캔.jpg 가 OCR 신뢰도 0.61 로 들어 있는데
이게 딱 그 사례여서 시연 시나리오 중심으로 잡았습니다.
스캔 계약서 올림 → 신뢰도 낮아 경고 → 검수로 금액 수정 →
금액 분석기가 증감액 대조 → 불일치 태스크 → 원문 역추적.
세 사람 파트가 한 흐름에서 다 나옵니다.


부탁드릴 게 하나 있습니다.
텍스트 조립할 때 각 조각의 문자 offset 을 남겨주시면 좋겠습니다.
(페이지번호, 시작offset, 끝offset) 이나 (ocr_element_id, 시작, 끝) 형태로요.
이게 없으면 분석기가 페이지를 몰라서 역추적이 안 됩니다.
reading_order 로 이어 붙일 때 자연히 나오는 값이라 큰 작업은 아닐 것 같은데,
맞는지 봐주시면 좋겠습니다.


3모드가 목업에 안 들어가 있어서 UI 변경안에 처리 모드 선택을 넣었습니다.
그리고 신뢰도 낮을 때 목업이 "확인 필요" 배지까지만 있고 다음 행동이 없어서,
"검수 모드로 열기 / 검수 없이 계속" 두 갈래를 그려 넣었습니다.
검수 없이 계속을 고른 것도 기록에 남으면 나중에 금액 틀렸을 때
원인을 짚을 수 있을 것 같습니다.


설계안 10절 미결 10개에 제 의견을 데이터구조_설계.md 13절에 적어놨습니다.
요약하면 —

  page_number 1부터 / 좌표 기준은 렌더링본 / polygon 은 컬럼만 준비
  검수 후 재수정 허용하고 IN_PROGRESS 로 되돌림 / 수정 이력은 P2
  ocr_revision 은 박스 1개만 고쳐도 항상 올림 (안 올리면 사슬이 깨져서요)
  텍스트 재조립은 동기·같은 트랜잭션 / group_id 먼저, ocr_groups 는 P2
  재OCR 은 사용자 확인 후 반영 / 오래된 분석은 자동 재실행 안 하고 사용자 재실행

ocr_engine, engine_version, preprocess_info 는 MVP 부터 저장하자는 것도
동의합니다. 나중에 어떤 조건에서 잘 됐는지 볼 수 있어서요.

검수 2단계(박스 이동·병합·재OCR·단락 편집)는 구현 20일이라 P2 로 뒀는데
이 부분 의견 주시면 좋겠습니다. 1단계(박스 표시·텍스트 수정·검수 완료)만으로도
금액 파트는 성립하니까 우선순위는 재정님이 정하시는 게 맞다고 봅니다.
```

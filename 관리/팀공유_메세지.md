# 팀 공유용 메시지 초안

메신저에 그대로 붙여 넣을 수 있게 쓴 것이다. **표를 쓰지 않았다** — 카카오톡 ·
Slack 에서 마크다운 표가 깨지기 때문이다.

구성 — **① 확정한 것 → ② 두 분 것 위에 얹는 것 → ③ 바뀌어야 하는 부분.**
일정은 전제로만 짧게 밝히고 기능으로 넘어간다.

세 덩어리다. 팀 채널에 ①을 올리고 ②③은 각자에게 따로 보낸다.

## ① 팀 채널 — 전체 공유

```
[본프로젝트 설계 정리 · 확인 부탁드립니다]

세현님 목업·기획안, 재정님 3모드 확장안·OCR DB 설계안 위에 제 금액 파트를
얹어서 문서로 정리했습니다. 두 분 설계는 그대로 살렸고, 분석기가 2개 이상이 될 때
안 맞는 지점만 조정했습니다.

github.com/bobohyeon/deliver  (브랜치 docs/산출물-정리-0805)

- 관리/기능명세서.md            10영역 108개 기능
- 산출물/기능명세서.xlsx        위 내용 엑셀 (자동필터 걸어놨습니다)
- 관리/데이터구조_설계.md        테이블 19개

■ 전제 — 구현은 20일입니다

테스트 기간을 반드시 남겨야 해서 이렇게 끊었습니다.

  설계·합의      8/10 ~ 8/14    5일
  구현           8/17 ~ 9/5     20일   (코드 프리즈 9/4 금)
  테스트·산출물   9/7  ~ 9/11    5일
  리허설·예비     9/12 ~ 9/13    2일

영업일 15일, 3인이면 45 인일입니다. P0+P1 이 72개라 다 못 합니다.
덜어내는 방식보다 묶는 방식으로 가면 꽤 들어갑니다.
액션아이템과 금액이 같은 골격(제안 카드 → 승인 → 태스크)을 쓰기 때문에
골격을 한 번 만들면 두 번째 분석기는 훨씬 쌉니다.

테스트·산출물 5일에는 문서를 새로 쓰지 않습니다.
기능명세서에 P0·P1 전부 완료 판정 기준을 붙여놨는데 그게 그대로
통합테스트 기대결과가 됩니다. 5일은 실행과 판정에만 씁니다.


■ 확정한 것 3개 — 이것 때문에 범위가 줄었습니다


[확정 1] 근거는 "왜 그렇게 판단했는지" 만 표시합니다. 페이지는 안 씁니다.

원래 목업 액션아이템 카드가 이랬습니다.

  근거 · 3페이지 "다음 주 금요일까지 김민수 책임이…"

여기서 "3페이지" 와 원문 하이라이트를 빼고, 대신 AI 가 왜 그렇게 판단했는지를
한 줄로 보여주는 방식으로 갑니다.

  근거 · 회의록에서 담당자와 기한이 함께 언급된 문장이라 액션으로 판단

이게 왜 중요한 결정인지 말씀드리면, 지금 분석기 규격이 이렇습니다.

  async def analyze(self, text: str) -> AnalyzeResult

텍스트 문자열 하나만 받습니다. 페이지 정보가 없습니다.
그래서 "3페이지" 를 표시하려면 분석기 규격을 바꿔야 했고,
재정님께 텍스트 조립할 때 문자 offset 을 남겨달라고 부탁드려야 했습니다.
세 사람이 인터페이스 합의를 하고 서로 기다려야 하는 작업이었습니다.

빼면 그게 전부 없어집니다.

  분석기 규격        안 고칩니다
  재정님께 부탁       없습니다 (offset 안 남겨도 됩니다)
  프론트 하이라이트   없습니다
  세 사람 대기        하나 줄어듭니다

그리고 분류 분석기가 이미 result_json 에 reason 을 담고 있어서
같은 패턴을 액션아이템·금액에 적용하면 됩니다. 새 구조가 아닙니다.

잃는 것도 있으니 말씀드립니다. 원문 대조로 근거를 검증할 수 없습니다.
reason 도 AI 가 쓴 글이라 그 자체가 틀릴 수 있습니다.
금액은 합계 대조(항목 합계 vs 문서 기재 합계)가 검증을 대신하지만,
액션아이템은 검증 수단이 없어서 승인율로만 관리합니다.


[확정 2] 문서 유형을 업로드할 때 정합니다. 기본값은 자동 판별입니다.

왜 이게 필요한지부터 말씀드리겠습니다.

분석기가 여러 개가 되면 문서마다 무엇을 돌릴지 골라야 합니다.
계약서에는 금액을 돌리고, 회의록에는 액션아이템을 돌리는 식입니다.
전부 다 돌리면 API 비용과 처리 시간이 낭비됩니다.

고르는 기준은 문서 유형입니다. 근데 여기서 막혔습니다.

  지금 문서 유형은 analyses.result_json['category'] 에 있습니다
       ↓
  그건 분류 분석기를 돌려야 나오는 값입니다
       ↓
  그런데 무엇을 돌릴지 고르는 시점은 분석 전입니다
       ↓
  순환입니다

그래서 유형을 업로드 시점에 정하는 방식으로 끊습니다. 두 경로입니다.

  업로드 화면에서 유형 선택
    ├─ 계약서 / 회의록 / 보고서... 를 사람이 고름
    │    → 분류 분석기를 건너뜁니다
    │    → 바로 어떤 분석기를 돌릴지 결정됩니다
    │
    └─ "자동 판별" (기본값)
         → 분류 분석기만 먼저 실행합니다
         → 결과를 documents.document_type 에 확정값으로 저장합니다
         → 그걸로 나머지 분석기를 결정합니다

어느 경로든 documents.document_type 에 확정값이 남습니다.
그 컬럼 하나만 보면 무엇을 돌릴지 정해집니다.
미니 프로젝트에서 만들어놓고 항상 general 이던 그 컬럼이 여기서 실제로 쓰입니다.


기본값을 "자동 판별" 로 두는 이유는 일괄 업로드입니다.

재정님 일괄 처리 모드에서 100건을 올리는데 각 파일마다 유형을 고를 수는 없습니다.
그래서 일괄은 이렇게 갑니다.

  1) 배치 단위로 유형을 한 번 지정
     같은 폴더에 있는 문서는 같은 유형인 경우가 많습니다.
     계약서 폴더를 통째로 올리면 "계약서" 한 번 고르고 끝냅니다.

  2) 섞여 있으면 "자동 판별"
     분류 분석기가 파일마다 판단합니다.

  3) 나중에 사람이 고침
     문서 상세에서 유형을 수정할 수 있게 합니다.
     유형이 틀리면 돌린 분석기도 틀리니까 고치면 재분석을 유도합니다.

사람이 유형을 고르면 분류 분석기 호출이 빠지는데, 이게 생각보다 큽니다.
미니 프로젝트 측정값으로 분류는 1건당 1.6초 · 토큰 2,880 이었습니다.
100건 일괄이면 160초와 토큰 28만 8천이 절약됩니다.


그리고 컬럼 하나를 더 두려고 합니다. document_type_source 입니다.

  USER            업로드할 때 사람이 골랐다
  AI              자동 판별로 분류 분석기가 정했다
  USER_CORRECTED  AI 판별을 사람이 나중에 고쳤다

USER_CORRECTED 비율이 곧 분류 오류율입니다.
기획안 성공지표에 "카테고리 분류 정확도 85%" 가 있는데,
원래는 별도 정답 데이터를 만들어서 재야 하는 항목이었습니다.
이 컬럼 하나로 실사용 데이터에서 그냥 나옵니다.
발표에서도 "실제 사용 중 사람이 고친 비율" 이 정답셋 정확도보다 셉니다.


[확정 3] 문서 유형을 7종으로 늘립니다. 계약변경을 추가합니다.

미니 프로젝트 6종에 하나를 더합니다.

  계약서 CONTRACT
  계약변경 CONTRACT_CHANGE   ← 추가
  회의록 MEETING_NOTES
  보고서 REPORT
  공지사항 NOTICE
  메뉴얼 MANUAL
  기타 ETC

계약변경을 왜 나누냐면, 금액 분석기가 뽑아야 하는 값이 다릅니다.

  계약서    → 계약금액, 지급 조건, 단가 항목
  계약변경  → 증감액, 변경 사유

같은 금액 분석기라도 프롬프트가 달라야 합니다.
세현님 목업에 용역계약서_최종.pdf 와 계약_변경합의서_스캔.jpg 가 둘 다 있어서
실제로 바로 마주칠 문제입니다.

프롬프트가 스스로 "원계약인가 변경인가" 를 판단하게 할 수도 있는데,
그러면 그게 또 하나의 분류 문제가 되고 틀렸을 때 사람이 고칠 방법이 없습니다.
유형으로 나눠두면 사람이 고칠 수 있습니다.


정리하면 이 세 가지 확정으로 화면 3곳과 DB 2컬럼이 바뀝니다.

  업로드 화면      유형 드롭다운 추가 (기본값 "자동 판별")
  일괄 업로드      배치 단위 유형 지정 1개
  문서 상세        유형 수정 가능하게
  documents        document_type 을 7종 enum 으로, 실제 값이 들어가게
  documents        document_type_source 신규


■ 두 분 것 위에 제가 얹는 것

새로 만드는 화면은 하나(단가 기준)뿐입니다. 나머지는 두 분이 만든 것 위에 얹습니다.

[세현님 목업 위에]

1) 문서 유형별 분석기 선택 규칙
   무엇: 문서 유형에 따라 어떤 분석기를 돌릴지 정하는 표입니다.
   이걸로: 세현님이 대시보드에 그려놓은 "문서 유형 분포" 가 실제로 쓰입니다.
         계약서 9건에서 뽑는 게 지금은 없는데 거기에 금액이 붙습니다.
         설정 화면에 이 표를 보여주면 "분석기가 갈아 끼울 수 있는 부품" 이라는
         말을 화면으로 증명할 수 있습니다.

2) 문서 상세 우측 패널에 "금액 항목" 섹션
   무엇: 액션아이템 카드와 똑같은 형식으로 금액 항목 카드를 붙입니다.
         제안 카드·승인/수정/거부·확신도·출처 링크 전부 그대로 씁니다.
   이걸로: 계약서를 열면 항목명·수량·단가·금액이 카드로 뜹니다.
         승인 전에는 어디에도 반영되지 않습니다.
         UI 패턴을 새로 만들지 않으니 프론트 작업이 거의 없습니다.

3) 합계 대조
   무엇: 뽑아낸 항목들을 Python 으로 더해서 문서에 적힌 합계와 맞춰봅니다.
   이걸로: 이게 금액 기능이 다른 분석기보다 센 지점입니다.
         액션아이템은 AI 가 뽑은 게 맞는지 알 방법이 없는데
         금액은 재계산해서 대조할 수 있습니다.
         항목 합계 72,000,000 인데 문서 기재가 79,200,000 이면
         차액 7,200,000 을 표시하고 "부가세 누락 가능" 을 띄웁니다.
         확정 1번에서 원문 대조를 뺐기 때문에 이게 유일한 검증 수단입니다.

4) 태스크 자동 제안
   무엇: 합계가 안 맞거나 단가가 미확정이면 태스크 제안을 만듭니다.
         (자동 등록은 안 합니다. 승인해야 등록됩니다)
   이걸로: 세현님 보드가 항상 채워집니다.
         검증만 하는 기능이면 문서가 깨끗할 때 태스크가 안 생겨서
         시연할 때 보드가 빕니다. 그런데 문서에 단가가 안 적혀 있는 경우는
         거의 항상 있어서 태스크·승인 UI 가 전부 동작하는 화면을 만들 수 있습니다.

5) 프로젝트 금액 현황
   무엇: 프로젝트 카드와 대시보드에 "미확정 금액" 지표를 넣습니다.
   이걸로: 프로젝트를 열기 전에 신뢰할 수 있는 금액인지 알 수 있습니다.
         승인 대기와 성격이 다릅니다. 승인 대기는 사람이 판단하면 끝인데
         미확정 금액은 단가 같은 문서 밖의 값을 채워야 끝납니다.

[재정님 파이프라인 위에]

6) 검수된 텍스트를 금액 계산의 입력으로
   무엇: 검수 완료된 텍스트로 금액을 뽑고 어느 revision 을 썼는지 기록합니다.
   이걸로: 재정님 검수 모드의 효과를 수치로 보여줄 수 있습니다.
         검수 전 금액 오류 몇 건 → 검수 후 몇 건, 이렇게요.
         검수 모드가 "있으면 좋은 기능" 이 아니라 "없으면 틀리는 기능" 이 됩니다.

7) revision 사슬을 금액까지 연장
   무엇: 재정님이 두신 analyses.source_text_revision 을 금액까지 잇습니다.
         ocr_elements 수정 → ocr_revision++ → extracted_texts
         → analyses → amount_items → cost_estimates
   이걸로: OCR 을 고치면 이미 계산된 금액이 자동으로 "오래됨" 표시가 됩니다.
         12,000,000 을 72,000,000 으로 고쳤는데 화면에 옛 금액이 남으면
         안 되니까요. 문장은 오탈자 한둘 있어도 요약이 대충 맞는데
         금액은 한 글자가 전부를 바꿉니다.

8) 단가 기준 데이터
   무엇: 단가표를 만들고 항목마다 출처와 기준일을 붙입니다.
   이걸로: 문서에 단가가 안 적힌 항목도 계산할 수 있습니다.
         AI 가 단가를 추측하면 그게 환각이라, 문서에 없으면 비워두고
         사람에게 묻습니다. 그게 이 기능의 안전장치입니다.

9) 일괄 업로드에 배치 유형 지정
   무엇: 일괄 업로드 화면에 유형 선택을 하나 넣습니다 (확정 2번).
   이걸로: 계약서 폴더를 통째로 올릴 때 분류 분석기를 100번 안 돌립니다.

제 파트의 원칙은 하나입니다.
"LLM 은 문서에 있는 것만 뽑고, 계산은 Python 이 한다."
문서에 없는 숫자를 AI 가 만들어내지 않게 하는 게 핵심입니다.


■ 바뀌어야 하는 부분 — 5개

1) 파이프라인 단계에서 분석기 이름을 빼야 합니다   [세현님·프론트]
```

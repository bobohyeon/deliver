## ① 팀 채널 — 전체 공유

```
[본프로젝트 설계 문서 정리 · 확인 부탁드립니다]

세현님 목업·기획안, 재정님 3모드 확장안·OCR DB 설계안, 그리고 제 금액 파트를
하나로 합쳐서 문서 4개 만들었습니다. 각자 만드신 걸 그대로 살렸고, 서로 안 맞는
지점만 조정했습니다.

github.com/bobohyeon/deliver  (브랜치 docs/산출물-정리-0805)

- 관리/팀컨셉_정리.md          컨셉 한 장
- 관리/기능명세서.md            10영역 107개 기능
- 관리/데이터구조_설계.md        테이블 19개
- 산출물/UI변경안.html          목업 대비 바뀌는 18곳 (브라우저로 열어주세요)

시간 없으시면 팀컨셉_정리.md 와 UI변경안.html 두 개만 봐주셔도 됩니다.


■ 먼저 말씀드릴 것 — 일정이 3주 초과입니다

기획안 로드맵 합계가 8주인데, 8/10부터 8주면 10월 4일입니다.
마감이 9/13, 발표가 9/14이니까 실제로 쓸 수 있는 건 5주입니다.
그리고 그 8주 안에 산출물 문서 작성 기간이 없습니다.

미니 프로젝트에서 산출물이 코드 프리즈 뒤로 몰려서 발표 준비가 빡빡했는데,
지금 계획대로면 그게 그대로 반복됩니다.

제 생각은 이렇습니다.

  설계·합의     8/10 ~ 8/14   범위·API 계약·DB 모델링·역할 분담
  1차 구현      8/17 ~ 8/28   P0 협업 기반 + P1 골격
  2차·통합      8/31 ~ 9/4    통합과 측정. 9/4 코드 프리즈
  산출물        9/7  ~ 9/10   테스트 결과서·화면정의서·WBS·발표자료
  리허설·예비   9/11 ~ 9/13

구현이 5주에서 3주로 줄어듭니다. 그래서 기능을 덜어내야 합니다.
지금 세어보니 P1이 42개인데 이건 3주에 불가능합니다.
무엇을 덜지 같이 정하면 좋겠습니다.


■ 컨셉은 이렇게 정리했습니다

"문서를 올리면 프로젝트가 자동으로 정리되는 협업 도구"

원칙 세 개만 지키면 된다고 봅니다.

  1. 문서가 원천이다 — 사람이 입력하지 않는다. 태스크도 금액도 문서에서 나온다
  2. AI는 제안하고 사람이 확정한다 — 자동 등록 금지
  3. 모든 결과는 원문으로 역추적된다 — 근거 없는 결과는 만들지 않는다

세 사람 파트가 한 흐름에서 만나는 예시를 하나 찾았습니다.
세현님 목업에 있는 계약_변경합의서_스캔.jpg (OCR 신뢰도 0.61) 이 딱 그 사례입니다.

  스캔 계약 변경합의서 업로드
    → OCR 신뢰도 낮아 경고            (재정님)
    → 검수 모드에서 금액 숫자 수정      (재정님)
    → 금액 분석기가 증감액 추출·대조    (제 파트)
    → 불일치 태스크가 보드에 뜸         (세현님)
    → 출처 누르면 원문 하이라이트        (세현님)

시연 시나리오를 이거 하나로 가면 세 파트가 전부 나옵니다.
따로따로 보여주는 것보다 훨씬 셉니다.

특히 금액은 검수 모드가 있어야 성립합니다.
문장은 오탈자 한둘 있어도 요약이 대충 맞는데, 금액은 1을 7로 잘못 읽으면
전부 틀립니다. 자릿점 하나 놓치면 10배가 됩니다.
반대로 검수 모드는 "왜 필요하냐"에 금액이 가장 좋은 답이 됩니다.
서로를 필요로 하는 관계라 이걸 발표에서 붙여서 말하면 좋겠습니다.


■ 바뀌어야 하는 부분 — 5개

각자 설계는 거의 그대로 두고, 분석기가 2개 이상이 되면 깨지는 것만 정리했습니다.

1) 처리 파이프라인 단계에서 분석기 이름을 빼야 합니다  [세현님·프론트]
   지금 목업이 "④ 액션 아이템 추출" 로 되어 있는데 이게 특정 분석기 이름입니다.
   금액 분석기 들어오면 6단계, 그다음엔 7단계가 됩니다.
   그때마다 화면·상태 enum·백엔드를 각자 고쳐야 합니다.
   → "분석 2/3" 처럼 분석기 개수 기반으로 바꾸면 됩니다.
   UI 변경 18곳 중에 구조를 바꾸는 건 이거 하나뿐입니다.

2) 문서 분류 결과를 라우팅 기준으로 올려야 합니다  [세현님·DB]
   문서 유형별로 어떤 분석기를 돌릴지 정하는 게 제 파트인데, 설계하다 막혔습니다.
   분류 결과는 분석을 돌려야 나오는데, 라우팅은 분석 전에 정해야 해서 순환입니다.
   → 분류만 라우팅 대상에서 빼고 무조건 먼저 실행하고,
     그 결과를 documents.document_type 에 확정값으로 넣는 방식을 제안합니다.
   미니 프로젝트에서 항상 general 이던 그 컬럼이 여기서 실제로 쓰입니다.

3) revision 전파를 금액까지 늘려야 합니다  [재정님 설계의 연장]
   재정님이 analyses.source_text_revision 두신 거 그대로 채택했고,
   금액까지 사슬을 늘렸습니다.
   OCR이 12,000,000 으로 읽은 걸 사람이 72,000,000 으로 고쳤는데
   이미 계산된 금액이 옛 숫자면 안 되니까요.
   ocr_elements 수정 → ocr_revision++ → extracted_texts → analyses
   → amount_items → cost_estimates 순서입니다.

4) tasks 의 출처가 3갈래가 됩니다  [세현님·DB]
   지금 source_analysis_id 하나인데, 금액 항목과 OCR 박스도 출처가 됩니다.
   → nullable FK 3개 + CHECK 제약을 제안합니다.
     source_type + source_id 방식은 FK를 못 걸어서 안 쓰는 게 좋다고 봅니다.

5) AI 채택률을 분석기별로 나눠야 합니다  [세현님·대시보드]
   목업에 "AI 제안 채택률 72%" 가 하나로 있는데 분석기가 늘면 의미가 섞입니다.
   액션아이템은 놓쳐도 사람이 기억하지만 금액은 놓치면 돈이 틀립니다.
   같은 지표로 묶기 어렵습니다.


■ 먼저 정할 것 4개

1. 일정 — 5주로 다시 짜고 P1에서 무엇을 덜지
2. 파이프라인 단계 일반화 (위 1번). 목업·프론트·enum·백엔드 4곳이 걸립니다
3. 분류 결과를 라우팅 기준으로 쓸지 (위 2번). DB 마이그레이션에 영향 있습니다
4. 단가 기준 데이터 범위 — 제 파트 최대 위험입니다.
   공공 단가 체계를 5주에 다루는 건 불가능해서, 팀이 만든 소규모 단가표로
   고정하고 화면에 "데모 범위" 라고 밝히는 방향을 생각하고 있습니다.
   이걸 안 정하면 발표에서 "그 숫자 근거가 뭐냐" 로 무너집니다.

내일(8/11) DB 모델링 하기로 되어 있으니, 그 전에 2번 3번만이라도
답 주시면 좋겠습니다. 나머지는 모여서 정하면 됩니다.

문서에 제 의견을 다 적어놨는데 어디까지나 제안이고,
아니라고 생각하시는 부분 말씀해 주시면 고치겠습니다.
```

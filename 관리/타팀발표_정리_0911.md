## 1조 — 통합 업무 플랫폼

**주제 축**: 회사 문서 관리 / 영수증 재무 관리 / 통합 업무 플랫폼
**목표**: 반복되는 작업을 하나의 흐름으로 통합해 줄이는 것

### 기능 구성

| 영역 | 내용 |
|---|---|
| 일정 | AI 캘린더 — 회의록·할 일 연계 |
| 재무 | 문서 결재 요청 → 이메일으로 전달 |
| 문서 | 사내 문서 + AI 채팅 |
| 개인화 | 지식바구니(북마크) — 마이페이지에서 확인 |
| 리포트 | 기업용 / 개발자용 분리 |
| 과금 | 구독 관리 / 결제 |

### 좋았던 점

- 처음부터 끝까지 **사이트 흐름의 완성도가 높다**
- **데이터를 직접 수집**했다
- 한국어 영수증을 중심으로 두고 영어 영수증으로 레이아웃을 보완했다 — 다양한 레이아웃 대응
- **하이브리드 검색 + 임베딩 캐시** — 임베딩 시간 단축
- **청크별로 테스트 결과**를 보여줬다

### 아쉬웠던 점

- 중간중간 캡처본이 빠진 곳이 많았다
- PPT 안의 검은 네모 박스 때문에 흐름이 끊겼다

### 발표 구성에 대해 남은 의문

발표를 보면서 우리 발표에 그대로 걸리는 질문들이다.

| 의문 | 지금 판단 |
|---|---|
| 프로젝트 개요를 길게 쓰는 게 좋은가 | 미결 |
| WBS·화면정의서·ERD 등 설계와 사이트 구성을 넣는 게 맞나 | 전에 안 넣어도 된다고 들었던 기억이 있다 — 확인 필요 |
| 단위·통합·회귀 테스트를 넣는 게 맞나 | **넣은 이유가 있었다 — 기능 검증용** |

### 제시된 수치 — 정의를 확인하기 전이다

- 임베딩 모델 기본값 98%?
- 기본 모델 테스트 결과 최소 96%?

> **두 숫자 모두 어느 지표인지 듣지 못했다.** 우리 숫자와 나란히 놓기 전에
> `accuracy@k`(= `Success@k` = `HitRate@k`, 첫 정답의 순위가 `k` 이하면 1)인지
> 표준 `recall@k`(상위 `k` ∩ 정답 / 정답 전체)인지 먼저 맞춘다. 같은 자료로
> 몇 배가 갈린다. 우리 도구는 앞의 것을 쓴다.

### Q&A

| 질문 | 답·평 |
|---|---|
| 성능이 낮은 이유가 무엇인가 | — |
| (심사 지적) 성능이 낮으면 실제 서비스가 힘들 수 있다 | **95% 이상은 나와야 한다** |
| 총평 | 결론적으로 나쁘지 않다 |

## 3조 — 의료 상담 챗봇

**주제 축**: AI 의료 상담 / 상담 이력 관리 / RAG 기반 정보 활용 / 관리자 AI 운영

### 흐름

증상 설명 → AI 답변 + 진료과 카테고리 분류 → 상담 내용 저장 / 관리자 AI 화면

### 기술 구성

| 구분 | 내용 |
|---|---|
| 모델 | `medgemma-4b`, `jina v4`, `medical bge-m3` |
| 데이터 | genMedGPT, 아산병원 건강정보, 질병관리청 OpenAPI |
| 인프라 | 메모에 "클라우드플레이어" 로 적혀 있다. Cloudflare 로 들렸으나 **확실하지 않다 — 확인 필요** |
| OCR | 관리자 페이지에서 RAG 자료 추출·등록에 사용 |
| 관리자 | LLM 응답 비교 페이지에서 **모델 선택 가능** (질문해서 확인했다) |

### 이 발표의 핵심 — 실패를 통해 얻은 결론

출발점은 **정답률만으로는 상담 안정성을 판단하기 어렵다**는 것이었다.

| 시도 | 결과 |
|---|---|
| MedGemma 4b 선택 | 정보 부족 인정 / 추가 정보 확인 / 응급 행동 우선 → **가장 높은 점수보다 의료 상담 서비스 목적에 맞는 행동을 선택** |
| 프롬프트에 규칙을 늘림 | 오히려 응급 안내가 늦어졌다 → **안전 규칙을 강화한다고 실제로 더 안전해지지는 않았다** |
| 프롬프트로 반복 억제 | 실패, 반복이 지속됐다 → **generation 설정 변경**으로 해결 |
| 응급 규칙 강화 | 모든 환자가 응급실로 가라는 답을 받았다 → red flag 를 우선하는 **v3.8 사용**. **무조건 최신 버전만 쓰지 않았다** |

버전별로 어떤 에러가 있었는지 설명해서 **해결 과정과 선택 이유의 근거**를 함께
제시했다. 이 방식이 발표에서 가장 설득력 있었다.

**결론 — 모든 문제를 프롬프트 하나로 해결하려 하지 말고, 문제에 맞는 계층에서
대응해야 한다.**

- 점수가 높다고 좋은 의료 상담이 아니다
- 프롬프트가 길다고 좋은 프롬프트가 아니다
- 최신 버전이 제일 좋은 것도 아니다
- RAG 를 연결했다고 품질이 보장되는 것도 아니다

### 아쉬웠던 점

- 시연 영상에서 재생 관련 문제가 발생했다
- 시연 영상을 편집하지 않아 길어졌다

### Q&A

| 질문 | 답 |
|---|---|
| 프롬프트 엔지니어링을 어떻게 했는가. 맥락·출력 결과 등 컨텍스트 엔지니어링을 많이 쓰는데 체계를 어떻게 잡았는지 | **컨텍스트를 점진적으로 변경**했다 |
| MedGemma(의료 특화 모델) 성능은 다른 모델과 비교해 어느 정도인가 | MedGemma 가 응답에 **더 근사한 정답**을 냈다. Llama 계열은 일본어로 답하는 경우가 있었고 환각 증상도 있었다 |
| 그럼 파라미터 튜닝은 어떻게 했는가 | **하지 않았다. 베이스 모델만** 썼다 |

## 우리 발표에 가져올 것

| 본 것 | 우리 쪽 적용 |
|---|---|
| 1조 — 청크별 테스트 결과 제시 | 조각 크기별 비교를 표로 남기면 설득력이 생긴다 |
| 1조 — 하이브리드 검색 + 임베딩 캐시 | 검색 정확도와 속도를 함께 다룰 때 참고한다 |
| 1조 Q&A — "95% 이상은 나와야 한다" | 목표 숫자를 말할 때 **어느 지표인지 먼저 밝히고** 말한다 |
| 3조 — 실패한 시도와 선택 근거를 함께 제시 | 결과만 두지 말고 "왜 이 선택인지" 를 발표에 넣는다 |
| 3조 — 문제에 맞는 계층에서 대응 | 프롬프트로 안 되는 것은 설정·파이프라인 층에서 잡는다 |
| 양 조 공통 — 캡처 누락 · 검은 박스 · 편집 안 된 시연 영상 | 우리 자료도 같은 항목으로 점검한다 |

### 확인이 필요한 채로 남은 것

- 1조가 말한 98% · 96% 가 어느 지표인지
- 3조의 인프라가 Cloudflare 인지
- 설계 산출물(WBS·화면정의서·ERD)과 테스트 산출물을 발표 PPT 에 넣는 것이 맞는지

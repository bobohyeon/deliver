# DocFlow 전체 데이터구조 설계

세 사람의 설계안을 하나로 맞춘 문서다.

| 출처 | 반영 |
|---|---|
| 미니 프로젝트 코드 | `documents` · `extracted_texts` · `analyses` 3테이블 |
| 착수기획서 6절 (박세현) | `users` · `projects` · `project_members` · `tasks` · `activity_logs` |
| **OCR-DB 설계안 (최재정)** | `document_pages` · `ocr_elements` + revision 체계 |
| 3모드 확장안 (최재정) | `batch_jobs` · `batch_items` |
| 기능명세서 `ANL-04`·`AMT` (김보현) | `analyzer_routes` · `amount_items` · `unit_prices` · `cost_estimates` |

기능 ID 는 `관리/기능명세서.md` 를 따른다.

## 0. 테이블을 나누는 기준 — 미니 프로젝트에서 세운 원칙을 그대로 쓴다

미니 프로젝트 발표에서 "3조는 테이블을 더 나눴는데 왜 그렇게 나눴나" 를
질문받았고, 이렇게 답했다.

> **저장할 결과의 모양이 얼마나 다른가로 갈린다.**
> 컬럼이 거의 같으면 **테이블 하나 + 구분 컬럼**, 모양이 크게 다르면 **JSONB**.

이 기준을 본프로젝트에도 일관되게 적용한다.

| 데이터 | 모양이 같은가 | 결론 |
|---|---|---|
| OCR 박스 | 엔진이 달라도 컬럼이 같다 (텍스트 · 좌표 · 신뢰도) | **테이블** `ocr_elements` |
| LLM 분석 결과 | 분석기마다 크게 다르다 (요약은 문장, 분류는 라벨, 액션아이템은 배열) | **JSONB** `analyses.result_json` |
| **금액 항목** | **항목마다 컬럼이 같다** (항목명 · 수량 · 단가 · 금액) | **테이블** `amount_items` |

**금액 항목을 테이블로 승격하는 이유가 하나 더 있다.** 태스크가 **개별 금액 항목을
참조**해야 한다 (`AMT-07` 불일치 태스크). JSONB 안의 배열 원소는 FK 대상이 될 수
없다. **행이어야 참조된다.**

아니라 **업로드 경로**다. `batch_item_id` 로 표현한다. OCR-DB 설계안의 지적을
그대로 받아들였다.

## 3. `document_type` 의 의미 변경과 순환 의존 문제

**여기서 설계 문제 하나를 발견했다. 착수 전에 정해야 한다.**

미니 프로젝트에서 `document_type` 은 사람이 붙이는 라벨이었고 **항상 `general`**
이었다. 실제 분류는 `analyses.result_json['category']` 에 있었다.

그런데 `ANL-04` 분석기 라우팅은 **문서 유형에 따라 실행할 분석기를 고른다.**
문제는 이렇다.

```text
분류 결과(category)는 분석을 돌려야 나온다
     ↓
그런데 라우팅은 분석 전에 결정해야 한다
     ↓
순환 의존
```

### 해법 — 분류를 라우팅보다 앞의 고정 단계로 둔다

```text
① 추출 ──▶ ② 분류 (무조건 실행) ──▶ ③ 라우팅 결정 ──▶ ④ 나머지 분석기 N개
                    │
                    └─▶ documents.document_type 에 확정값 기록
```

- **② 분류는 라우팅 대상이 아니다.** 모든 문서에 무조건 돌린다
- 결과를 `documents.document_type` 에 **확정값으로 승격**한다
- 사람이 덮어쓸 수 있게 한다 (분류가 틀렸을 때 라우팅도 틀리므로)

**즉 `document_type` 이 "항상 general 인 장식 컬럼" 에서 "라우팅을 결정하는 실제
값" 으로 격상된다.** 미니 프로젝트에서 만들어 두고 안 쓴 컬럼이 여기서 쓰인다.

| enum 값 | 미니 프로젝트 `category` 와 동일 |
|---|---|
| `CONTRACT` · `REPORT` · `MEETING_NOTES` · `NOTICE` · `MANUAL` · `ETC` | 계약서 · 보고서 · 회의록 · 공지사항 · 메뉴얼 · 기타 |

## 4. revision 전파 체계 — 세 파트가 DB 에서 만나는 지점

**이 문서에서 가장 중요한 절이다.** OCR-DB 설계안이 제안한 revision 개념을
금액까지 확장해야 한다.

### 왜 필요한가

금액은 revision 에 특히 민감하다.

> OCR 이 계약금액을 `12,000,000` 으로 읽었는데 실제로는 `72,000,000` 이었다.
> 사람이 검수 모드에서 고쳤다. **그런데 이미 뽑아둔 금액 항목과 계산된 추계액은
> 옛 숫자 그대로다.** 화면에는 틀린 금액이 남아 있다.

문장은 오탈자가 있어도 요약이 대충 맞다. **금액은 한 글자가 전부를 바꾼다.**

### 전파 사슬

```text
① ocr_elements.text 수정                        (재정)
        ↓
② documents.ocr_revision += 1                   (재정)
        ↓
③ extracted_texts.content 재조립
   extracted_texts.text_version = ocr_revision   (재정)
        ↓
④ analyses.source_text_revision < ocr_revision
   → 분석 결과 오래됨                            (보현)
        ↓
⑤ amount_items.source_text_revision < ocr_revision
   → 금액 항목 오래됨                            (보현)
        ↓
⑥ cost_estimates.is_stale = true
   → 추계 결과 무효                              (보현)
```

**①~③ 은 하나의 트랜잭션이어야 한다.** `ocr_elements.text` 만 바뀌고
`extracted_texts.content` 가 안 바뀌면 화면 · 검색 · 분석이 서로 다른 값을 본다.

**④~⑥ 은 트랜잭션에 넣지 않는다.** 비교로 판정한다.

```sql
-- 오래된 금액 항목 찾기
SELECT ai.* FROM amount_items ai
JOIN documents d ON d.id = ai.document_id
WHERE ai.source_text_revision < d.ocr_revision
```

**`is_stale` 컬럼을 따로 두지 않고 비교하는 이유** — 컬럼을 두면 갱신을 놓칠 수
있다. `ocr_revision` 하나만 올리면 하위 전체가 자동으로 오래된 것이 된다.
단, `cost_estimates` 는 계산 비용이 크므로 예외적으로 플래그를 둔다.

> **Spring 비교** — JPA 의 `@Version` 낙관적 락과 개념이 같지만 목적이 다르다.
> `@Version` 은 **동시 수정 충돌**을 막고(그건 `ocr_elements.version` 이 담당),
> `ocr_revision` 은 **파생 데이터의 신선도**를 판정한다. 둘을 같은 컬럼으로 쓰면
> 안 된다.

## 5. `ocr_elements` — OCR-DB 설계안 그대로

최재정님 설계안을 그대로 채택한다. 변경 없이 옮긴다.

| 컬럼 | 필수 | 설명 |
|---|:-:|---|
| `id` | O | **수정 후에도 유지되는 식별자** |
| `document_id` · `page_id` | O | |

| `text` | O | 현재 적용 값 |

| `source` | O | `OCR` / `TEXT_LAYER` / `MANUAL` / `RE_OCR` |
| `ocr_engine` · `engine_version` · `preprocess_info` | 권장 | MVP 부터 저장 권장 |
| `reading_order` | O | 텍스트 조립 순서 |
| `group_id` | | 단락 그룹 |
| `review_status` | O | `UNREVIEWED` / `REVIEWED` / `REJECTED` |
| `is_deleted` | O | **논리 삭제** |
| `created_by` · `updated_by` · `created_at` · `updated_at` | | |
| `version` | O | **동시 수정 충돌 방지** (`REV-16`) |
| `polygon_json` | 확장 | 기울어진 사각형 |

**`id` 유지와 논리 삭제가 왜 중요한지 근거가 하나 더 있다.** OCR-DB 설계안 9-1 이
`tasks.source_ocr_element_id` 연결이 끊어지는 문제를 지적했는데, **금액 항목도
같은 문제를 겪는다.** `amount_items.source_ocr_element_id` 로 금액 숫자의 원문
위치를 가리키기 때문이다 (`AMT-09` 역추적).

`document_pages` · `ocr_element_revisions` · `ocr_groups` 도 설계안 그대로 채택한다.
좌표 기준 이미지를 `document_pages.image_path` 로 고정하는 원칙도 그대로다.

## 7. `tasks` — 출처가 3갈래가 된다

**여기서 설계 결정이 필요하다.** 착수기획서는 `source_analysis_id` 하나를 뒀지만,
태스크의 출처가 세 종류가 된다.

| 출처 | 언제 | 기능 |
|---|---|---|
| `source_analysis_id` | 액션아이템 승인 | `TSK-03` |
| `source_amount_item_id` | 금액 불일치 · 전제 미확정 | `AMT-07` |
| `source_ocr_element_id` | 검수 중 확인 필요 표시 | `REV-05` 파생 |

### 채택안 — nullable FK 3개 + CHECK 제약

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | PK | |
| `project_id` | FK NOT NULL | |
| `title` · `description` | | |
| `assignee_id` | FK nullable | AI 가 못 찾으면 미지정 (`TSK-06`) |
| `due_date` | nullable | 기한 불명확 허용 |
| `status` | enum | `TODO` / `DOING` / `DONE` |
| `is_ai_generated` | bool | `TSK-05` 배지 |
| **`source_analysis_id`** | FK nullable | |
| **`source_amount_item_id`** | FK nullable | |
| **`source_ocr_element_id`** | FK nullable | |
| `created_by` · `created_at` · `updated_at` | | |

```sql
CHECK (
  (source_analysis_id IS NOT NULL)::int
+ (source_amount_item_id IS NOT NULL)::int
+ (source_ocr_element_id IS NOT NULL)::int
<= 1
)
```

### 왜 `source_type` + `source_id` 방식을 쓰지 않는가

| | nullable FK 3개 (채택) | `source_type` + `source_id` |
|---|---|---|
| FK 무결성 | **DB 가 보장한다** | 걸 수 없다. 애플리케이션 책임 |
| 삭제 연쇄 | `ON DELETE` 로 처리 | 직접 정리해야 한다 |
| JOIN | 명확 | 조건 분기 필요 |
| 출처가 늘어날 때 | 컬럼 추가 (마이그레이션) | 값 추가로 끝 |

**출처가 3개이므로 무결성을 택한다.** 5개를 넘어가면 다시 검토한다.

> **Spring 비교** — JPA 의 `@Any` 다형적 연관관계를 쓰는 대신 nullable 필드
> 여러 개를 두는 선택과 같다. `@Any` 는 FK 제약을 걸 수 없어 Hibernate 도
> 권장하지 않는다.

### 제안 거부 기록

`TSK-07` 거부를 남기지 않으면 채택률(`ANL-10`)을 계산할 수 없다. 거부는 태스크가
되지 않으므로 `tasks` 에 남길 수 없다.

**`analyses.result_json` 안의 각 제안에 `decision` 필드를 둔다** —
`PENDING` / `APPROVED` / `REJECTED` / `EDITED`. JSONB 이므로 스키마 변경이 없다.

## 8. `analyzer_routes` — 분석기 라우팅 (`ANL-04`)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | PK | |
| `document_type` | enum | 3절의 6종 |
| `analyzer_type` | enum | `SUMMARY` / `CATEGORY` / `ACTION_ITEM` / `AMOUNT` |
| `is_enabled` | bool | |
| `prompt_variant` | varchar nullable | 같은 분석기의 문서별 프롬프트 분기 |
| `execution_order` | int | |
| `project_id` | FK nullable | **NULL 이면 전역 기본값** |
| `updated_by` · `updated_at` | | |

**unique(`document_type`, `analyzer_type`, `project_id`)**

### `prompt_variant` 가 필요한 이유

목업 보드에 **"하도급 계약 조항 검토"** 카드가 있고 출처가 `용역계약서_최종.pdf`
7페이지다. 액션아이템 분석기가 계약서를 읽은 것인데, **회의록용 프롬프트로 계약서를
처리하면 안 된다.** 같은 `ACTION_ITEM` 분석기라도 문서 유형에 따라 프롬프트가 달라야
한다.

```text
MEETING_NOTES + ACTION_ITEM → prompt_variant = "meeting_v1"   담당자·기한 중심
CONTRACT      + ACTION_ITEM → prompt_variant = "contract_v1"  조항 검토 중심
```

### MVP 범위

`project_id` 는 컬럼만 만들고 **MVP 에서는 전역 기본값(NULL)만 쓴다.** 프로젝트별
커스터마이즈는 P2 이후다. 컬럼을 나중에 추가하면 마이그레이션이 늘어나므로
처음부터 둔다.

### 코드 상수가 아니라 테이블로 두는 이유

| | 테이블 (채택) | 코드 상수 |
|---|---|---|
| 운영 중 변경 | 가능 | 배포 필요 |
| 화면 표시 | 가능 — **"확장 가능" 주장의 증거** | 어렵다 |
| 프로젝트별 분기 | 가능 | 불가 |

**설정 화면에 이 표를 그대로 보여주면** 미니 프로젝트 발표에서 받은 Q1("분석기가
무슨 뜻이냐")의 답을 화면으로 대신할 수 있다.

## 11. N+1 방지 (`SYS-07`)

미니 프로젝트에서 목록 조회가 `2+2N` 이었다 (문서 9건에 쿼리 20개). **본프로젝트는
테이블이 19개로 늘어나 방치하면 훨씬 심해진다.**

| 화면 | 필요한 값 | 방법 |
|---|---|---|
| 프로젝트 목록 | 문서 수 · 열린 태스크 · 승인 대기 | **집계 서브쿼리 1회** |
| 문서 목록 | `category` · `summary_preview` | **`documents` 에 비정규화 2컬럼** |
| 태스크 보드 | 담당자 · 출처 문서명 | `selectinload` |
| 검수 화면 | 페이지별 박스 | 페이지 단위 조회 (전체 로드 금지) |

**문서 목록은 비정규화가 답이다.** 미니 프로젝트에서 확인했듯 `DocumentListItem` 이
필요한 값은 두 개뿐이다.

| 신규 컬럼 | 갱신 시점 |
|---|---|
| `documents.category_cache` | 분류 분석 완료 시 |
| `documents.summary_preview` | 요약 분석 완료 시 |

**트리거를 쓰지 않고 서비스 계층에서 함께 쓴다.** 트리거는 애플리케이션 로그에
남지 않아 디버깅이 어렵다.

## 12. 마이그레이션 순서 (`SYS-01`)

의존 관계 때문에 순서를 지켜야 한다.

```text
1. users
2. projects, project_members
3. documents 에 project_id · uploaded_by 추가
   → 기존 데이터는 마이그레이션용 기본 프로젝트에 배정
4. tasks, activity_logs
5. document_pages, ocr_elements
6. documents 에 processing_mode · review_status · ocr_revision 추가
7. extracted_texts 에 text_version · is_confirmed 추가
8. analyses 에 source_text_revision 추가
9. analyzer_routes  (+ 기본 라우팅 시드 데이터)
10. unit_prices, amount_items
11. cost_estimates, cost_estimate_lines
12. batch_jobs, batch_items
13. documents 에 비정규화 컬럼 2개 + 인덱스
14. ocr_element_revisions, ocr_groups  (확장 단계)
```

**3번이 위험하다.** `project_id` 가 NOT NULL 인데 기존 문서에는 값이 없다. 3단계로
나눈다 — nullable 로 추가 → 기본 프로젝트로 채움 → NOT NULL 로 변경.

## 13. 미결 사항

### OCR-DB 설계안 10절의 항목 (재정)

| | 안건 | 제 의견 |
|---|---|---|
| 1 | `page_number` 0 부터 · 1 부터 | **1 부터.** 화면 표시와 일치해 변환이 없다 |
| 2 | 좌표 기준 이미지 고정 | **렌더링본.** 전처리본은 프리셋에 따라 달라져 기준이 흔들린다 |
| 3 | `polygon_json` 저장 여부 | MVP 제외, 컬럼만 준비 |
| 4 | 검수 완료 후 재수정 허용 | **허용하고 `IN_PROGRESS` 로 되돌린다** |
| 5 | 수정 이력 MVP 부터 | **P2.** 단 `ocr_engine`·`engine_version`·`preprocess_info` 는 MVP 부터 |
| 6 | 박스 1개 수정이 `ocr_revision` 을 항상 올리는지 | **올린다.** 안 올리면 4절 사슬이 깨진다 |
| 7 | 텍스트 재조립 동기 · 비동기 | **동기 · 같은 트랜잭션** |
| 8 | `group_id` 만 먼저 둘지 | **`group_id` 먼저.** `ocr_groups` 는 P2 |
| 9 | 재OCR 자동 교체 여부 | **사용자 확인 후 반영** |
| 10 | 오래된 분석 자동 재실행 | **사용자 재실행 요구.** 자동은 API 비용이 튄다 |

### 이 문서에서 새로 생긴 안건 (보현)

| | 안건 | 왜 결정이 필요한가 |
|---|---|---|
| 11 | **`document_type` 을 라우팅 기준으로 격상** (3절) | 순환 의존 해소 방식. 분류를 고정 선행 단계로 둘지 |
| 12 | 분류가 틀렸을 때 **사람이 `document_type` 을 고칠 수 있게** 할지 | 틀리면 라우팅도 틀린다 |
| 13 | `tasks` 출처를 **nullable FK 3개**로 둘지 (7절) | 나중에 바꾸면 마이그레이션이 크다 |
| 14 | 제안 거부를 `result_json.decision` 에 둘지 별도 테이블로 둘지 (7절) | 채택률 지표의 원천 |
| 15 | `analyzer_routes` 를 **테이블**로 둘지 코드 상수로 둘지 (8절) | |
| 16 | 단가 마스터 범위 | **`AMT` 최대 위험.** 소규모 자체 데이터로 고정 권장 |
| 17 | `VIEWER` 에게 금액 노출 여부 (`AMT-11`) | 노출 안 하면 조회 쿼리에 조건이 붙는다 |

**11번이 가장 급하다.** 라우팅 구조 전체가 여기에 달려 있고, `documents` 컬럼
의미가 바뀌므로 마이그레이션에도 영향이 있다.

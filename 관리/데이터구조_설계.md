# DocFlow 데이터구조 — 설계 근거

**컬럼 목록은 이 문서에 없다.** `관리/DocFlow_DB.dbml` 이 스키마 정본이다.
두 곳에 컬럼을 적으면 반드시 어긋나므로 역할을 나눴다.

| 문서 | 담는 것 |
|---|---|
| `관리/DocFlow_DB.dbml` | **무엇을** — 테이블 · 컬럼 · 관계 · 인덱스 (사람이 읽는 정본) |
| **이 문서** | **왜** — 나눈 기준 · 결정 근거 · 미채택 대안 |
| `backend/migrations/versions/` | **실행본** — Alembic 리비전. 스키마를 실제로 만드는 것은 이쪽뿐이다 |
| `관리/기능명세서.md` | 기능 ID 와 완료 판정 기준 |

세 사람의 설계안을 하나로 맞춘 결과다.

| 출처 | 반영 |
|---|---|
| 미니 프로젝트 코드 | `documents` · `extracted_texts` · `analyses` |
| 착수기획서 6절 (박세현) | `users` · `projects` · `project_members` · `tasks` · `activity_logs` |
| **OCR-DB 설계안 (최재정)** | `document_pages` · `ocr_elements` + revision 체계 **(변경 없이 채택)** |
| 3모드 확장안 (최재정) | `batch_jobs` · `batch_items` |
| 기능명세서 `ANL`·`AMT`·`DLV` (김보현) | `amount_items` · `decisions` · `schedule_items` · `deliverables` |

## 0. 테이블을 나누는 기준 — 미니 프로젝트에서 세운 원칙

미니 프로젝트 발표에서 "3조는 테이블을 더 나눴는데 왜 그렇게 나눴나" 를 질문받았고
이렇게 답했다.

> **저장할 결과의 모양이 얼마나 다른가로 갈린다.**
> 컬럼이 거의 같으면 **테이블 하나 + 구분 컬럼**, 모양이 크게 다르면 **JSONB**.

본프로젝트에도 그대로 적용했다.

| 데이터 | 모양이 같은가 | 결론 |
|---|---|---|
| OCR 박스 | 엔진이 달라도 컬럼이 같다 | **테이블** `ocr_elements` |
| LLM 분석 결과 | 분석기마다 크게 다르다 | **JSONB** `analyses.result_json` |
| 금액 항목 | 항목마다 컬럼이 같다 | **테이블** `amount_items` |
| 결정사항 | 항목마다 컬럼이 같다 | **테이블** `decisions` |
| 일정 항목 | 항목마다 컬럼이 같다 | **테이블** `schedule_items` |
| 액션아이템 | 항목마다 컬럼이 같다 | **테이블** `action_items` (합의 대기) |

**금액 · 결정 · 일정을 테이블로 승격한 이유가 하나 더 있다.** 이것들이 **산출물의
재료**다(`DLV-04`~`DLV-07`). 프로젝트 단위로 기간 필터를 걸어 집계해야 하므로
JSONB 배열 안에 있으면 쿼리가 성립하지 않는다.

그리고 **태스크가 금액 항목을 참조**해야 한다(`AMT-07`). JSONB 안의 배열 원소는
FK 대상이 될 수 없다. **행이어야 참조된다.**

## 2. 기존 3테이블의 성격 변화

### `documents` — 스코프의 기준이 된다

`project_id` 가 NOT NULL 로 붙는다. **`PRJ-08` 스코프 강제의 기준**이고, 라우터가
아니라 **리포지토리 계층에서 조건을 강제**한다. 라우터에서만 검사하면 새 API 를
추가할 때 누락된다.

`status`(파이프라인)와 `review_status`(검수)를 **분리한다.** 추출은 끝났는데 검수는
진행 중인 상태를 표현해야 한다.

```
status = EXTRACTED  +  review_status = IN_PROGRESS
```

**`processing_mode` 에 `BATCH` 를 넣지 않는다.** 일괄은 개별 문서의 처리 방식이
아니라 **업로드 경로**다. `batch_item_id` 로 표현한다. OCR-DB 설계안의 지적을 그대로
받아들였다.

### `extracted_texts` — 원천에서 캐시로 내려온다

지금은 `content` 가 원천 데이터인데, 검수가 들어오면 **`ocr_elements` 가 원천이고
`content` 는 검색·분석용 스냅샷**이 된다. 이 전환이 `REV-17` 이다.

### `analyses` — 1:N 을 유지한다

재분석이 이전 결과를 덮지 않는다. 미니 프로젝트에서 `documents.summary` 컬럼을 두지
않은 이유가 그것이었고, 본프로젝트에서 모델을 비교할 원본 데이터가 된다.

`result_json` 안의 각 제안 원소에 `decision`(`PENDING`/`APPROVED`/`EDITED`/
`REJECTED`)을 넣는다. **거부를 기록하지 않으면 채택률(`ANL-10`)을 계산할 수 없다.**
거부한 제안은 태스크가 되지 않으므로 `tasks` 에 남길 수 없다.

## 3. `document_type` 의 격상 — 그리고 목적이 바뀐 이야기

미니 프로젝트에서 `document_type` 은 **항상 `general`** 인 장식 컬럼이었다. 실제
분류는 `analyses.result_json['category']` 에 있었다.

### 처음 계획 — 그리고 왜 폐기했나

원래는 **분석기를 고르는 기준**으로 쓰려 했다(`ANL-04` 분석기 선택 규칙). 계약서면
금액 분석기를 돌리고 회의록이면 안 돌리는 식이다. 그런데 순환이 생겼다.

```
분류 결과는 분석을 돌려야 나온다  →  그런데 분석기 선택은 분석 전이다  →  순환
```

이걸 "분류를 먼저 돌리는 고정 선행 단계" 로 풀려 했는데 **박세현님이 병렬 처리가
깨진다고 지적했다.** 맞는 지적이었다. 현재 코드는 `asyncio.gather` 로 요약·분류를
동시에 돌리는데(의도적으로 그렇게 만든 주석까지 있다), 분류를 앞으로 빼면
`gather` 가 두 단계로 쪼개지고 **요약이 분류를 기다릴 이유가 없는데 1.6초를 버린다.**

**그래서 선택 규칙을 폐기했다.** 근본 원인이 더 있었다 — **회의록·보고서에도 금액이
나온다.** 유형으로 금액 분석기를 껐다 켜면 오히려 놓친다.

### 현재 — 분석기는 넷 다 항상 돌린다

```python
await asyncio.gather(
    summary.analyze(content), category.analyze(content),
    extract.analyze(content), amount.analyze(content),
)
```

**`gather` 한 번, 순환 없음, 유형 몰라도 됨.** `document_type` 의 목적은 셋으로
줄었다.

| 쓰이는 곳 | |
|---|---|
| 목록 필터 · 대시보드 유형 분포 | 조회 |
| 프롬프트 힌트 | 계약서라고 알려주면 금액 분석기가 계약금액에 집중한다 |
| 산출물 분류 | 주간 보고서의 "회의록 3건 · 계약서 2건" |

### 7종으로 늘린 이유

`CONTRACT_CHANGE`(계약변경)를 더했다. **원계약은 계약금액을 뽑고 변경합의서는
증감액을 뽑으므로 프롬프트 힌트가 달라야 한다.** 목업에 `용역계약서_최종.pdf` 와
`계약_변경합의서_스캔.jpg` 가 둘 다 있어 실제로 마주칠 문제다.

프롬프트가 스스로 원계약인지 변경인지 판단하게 하면 **그게 또 하나의 분류 문제가
되고 틀렸을 때 사람이 고칠 방법이 없다.**

### `document_type_source` — 정답 데이터셋을 대신한다

| 값 | 뜻 |
|---|---|
| `USER` | 업로드할 때 사람이 골랐다 |
| `AI` | 자동 판별로 분류 분석기가 정했다 |
| `USER_CORRECTED` | AI 판별을 사람이 나중에 고쳤다 |

**`USER_CORRECTED` 비율이 곧 분류 오류율이다.** 기획안 성공지표 "카테고리 분류
정확도 85%" 를 별도 정답 데이터 없이 실사용 데이터로 잴 수 있다. 발표에서도
**"실제 사용 중 사람이 고친 비율" 이 정답셋 정확도보다 설득력이 있다.**

## 4. revision 전파 사슬 — 세 파트가 DB 에서 만나는 지점

OCR-DB 설계안이 제안한 revision 개념을 **금액 · 결정 · 일정까지 확장했다.**

### 왜 필요한가

> OCR 이 계약금액을 `12,000,000` 으로 읽었는데 실제로는 `72,000,000` 이었다.
> 사람이 검수로 고쳤다. **그런데 이미 뽑아둔 금액 항목은 옛 숫자 그대로다.**

문장은 오탈자가 있어도 요약이 대충 맞다. **금액은 한 글자가 전부를 바꾼다.**
자릿점 하나 놓치면 10배가 된다.

### 사슬

```
① ocr_elements.text 수정                          (재정)
② documents.ocr_revision += 1                     (재정)   ┐ 같은
③ extracted_texts.content 재조립 + text_version    (재정)   ┘ 트랜잭션
        ↓
④ analyses.source_text_revision       < ocr_revision → 오래됨  (보현)
⑤ amount_items.source_text_revision   < ocr_revision → 오래됨  (보현)
⑥ decisions / schedule_items          < ocr_revision → 오래됨  (보현)
```

**①~③ 은 하나의 트랜잭션이어야 한다.** `ocr_elements.text` 만 바뀌고
`extracted_texts.content` 가 안 바뀌면 화면 · 검색 · 분석이 서로 다른 값을 본다.

**④~⑥ 은 트랜잭션에 넣지 않고 비교로 판정한다.**

```sql
SELECT ai.* FROM amount_items ai
JOIN documents d ON d.id = ai.document_id
WHERE ai.source_text_revision < d.ocr_revision
```

**플래그 컬럼을 따로 두지 않는 이유** — 컬럼을 두면 갱신을 놓칠 수 있다.
`ocr_revision` 하나만 올리면 하위 전체가 자동으로 오래된 것이 된다.

> **Spring 비교** — `ocr_elements.version` 은 JPA `@Version` 낙관적 락이고
> **동시 수정 충돌**을 막는다. `documents.ocr_revision` 은 **파생 데이터의
> 신선도**를 판정한다. 목적이 다르므로 같은 컬럼으로 쓰면 안 된다.

## 5. `ocr_elements` — 설계안 그대로 채택

최재정님 설계안을 **변경 없이** 옮겼다. 핵심 결정만 다시 적는다.

| 결정 | 왜 |
|---|---|
| **비율 좌표(0~1)** | 화면 확대·축소와 무관하게 같은 위치에 박스를 그린다 |
| **`id` 유지** | 수정 시 삭제·재생성하면 참조가 끊어진다 |
| **논리 삭제** | 물리 삭제하면 이력과 참조가 사라진다 |
| **`version` 낙관적 락** | 두 사용자가 같은 박스를 고치면 나중 요청이 409 |
| **`original_text` / `text` 분리** | 최초 인식 품질 평가와 현재 값을 함께 남긴다 |
| **좌표 기준 이미지 고정** | `document_pages.image_path` 를 렌더링본으로 고정. 프런트가 보는 이미지와 다르면 박스가 어긋난다 |

`ocr_element_revisions` · `ocr_groups` 도 그대로 채택하되 **P2** 다. MVP 는
`ocr_elements.group_id` 만 쓴다.

## 6. `tasks` — 컬럼 두 개가 새로 필요하다

### `completed_at` — 없으면 주간 보고서를 만들 수 없다

착수기획서의 `tasks` 컬럼 목록에 **완료 시각이 없다.** `status=DONE` 은 알 수 있어도
**언제 완료됐는지** 모른다. `DLV-04` 주간 보고서의 "이번 주 완료 태스크" 를 뽑을 수
없다.

**목업이 이미 필요한 상태다.**

```
보드 완료 열   "킥오프 회의 진행 / 3월 7일 완료"
              "참석자 명단 정리 / 3월 8일 완료"
대시보드       "완료된 태스크 8건"
```

날짜를 화면에 보여주는데 담을 컬럼이 없다. `updated_at` 도 없어서 함께 넣는다.

### 출처가 2갈래 — nullable FK 2개 + CHECK

| 출처 | 언제 |
|---|---|
| `source_action_item_id` | 액션아이템 승인 (`TSK-03`) |
| `source_amount_item_id` | 금액 불일치 (`AMT-07`) |

원래 OCR 박스까지 3갈래였는데 **원문 위치 하이라이트가 범위에서 빠져** 2갈래로
줄었다. 검수 중 확인이 필요한 상태는 `ocr_elements.review_status` 로 이미 표현된다.

**`source_type` + `source_id` 방식을 쓰지 않는다.**

| | nullable FK 2개 (채택) | `source_type` + `source_id` |
|---|---|---|
| FK 무결성 | **DB 가 보장한다** | 걸 수 없다. 애플리케이션 책임 |
| 삭제 연쇄 | `ON DELETE` 로 처리 | 직접 정리해야 한다 |
| JOIN | 명확 | 조건 분기 필요 |
| 출처가 늘어날 때 | 컬럼 추가 (마이그레이션) | 값 추가로 끝 |

**출처가 2개뿐이므로 무결성을 택한다.** 5개를 넘어가면 다시 검토한다.

> **Spring 비교** — JPA `@Any` 다형적 연관관계를 쓰는 대신 nullable 필드 여러 개를
> 두는 선택과 같다. `@Any` 는 FK 제약을 걸 수 없어 Hibernate 도 권장하지 않는다.

## 7. 근거 표시 — 페이지·좌표를 버리고 `reason` 으로

`amount_items` · `decisions` · `schedule_items` 에 `reason`(텍스트)이 있고
`source_page` · `source_ocr_element_id` 는 **없다.**

### 왜 뺐나

분석기 규격이 `analyze(text: str)` 로 **텍스트 문자열만 받는다.** 페이지 정보가 없다.
그런데 목업 카드에 `근거 · 3페이지` 가 있었다.

페이지를 표시하려면 규격을 바꿔야 했고, 그러면 **분석기 규격(보현) → 텍스트 조립
offset(재정) → 하이라이트 UI(세현)** 세 사람이 인터페이스를 합의하고 서로 기다려야
했다. **구현 20일에 그 대기를 없앤 것이다.**

대신 **`reason`(왜 그렇게 판단했는지)** 을 표시한다. 분류 분석기가 이미
`result_json` 에 `reason` 을 담고 있어 **새 구조가 아니다.**

### 대가와 대응

**원문 대조로 근거를 검증할 수 없다.** `reason` 도 AI 가 쓴 글이라 그 자체가 틀릴 수
있다.

| | 검증 수단 |
|---|---|
| 금액 | **`AMT-03` 합계 대조** — 항목 합계 vs 문서 기재 합계 |
| 결정 · 일정 | 없다. 승인율로만 관리 |
| 일정 | 날짜는 형식이 있어 **원문 대조로 추출 정확도는 잴 수 있다** |

## 8. 금액은 집계다 — 추계가 아니다

**설계가 한 번 크게 바뀐 지점이라 기록해 둔다.**

| | 추계 (폐기) | 집계 (채택) |
|---|---|---|
| 하는 일 | 없는 금액을 **만든다** | 있는 금액을 **모은다** |
| 정답 | 없다 | 문서 안에 있다 |
| 필요한 것 | **단가 마스터** | 없다 |
| 위험 | "그 단가 근거가 뭐냐" | 없다 — 전부 문서에서 나왔다 |

`unit_prices` · `cost_estimates` · `cost_estimate_lines` 세 테이블이 여기서
사라졌고 **`AMT` 영역의 최대 위험도 함께 없어졌다.**

### 집계가 만드는 가치

```
용역계약서_최종.pdf        계약금액   72,000,000
계약_변경합의서_스캔.jpg    증액       +15,000,000
3월 2주차 주간보고.docx     집행액      60,000,000
                    ↓
현재 계약금액 87,000,000 · 집행 60,000,000 (69%) · 잔액 27,000,000

⚠ 변경합의서 기재 총액(85,000,000)과 계산값(87,000,000) 불일치
```

**문서 하나로는 알 수 없다.** 요약과 액션아이템은 문서 하나로 끝나지만 금액은 모아야
의미가 생긴다. 그래서 **"문서는 프로젝트 맥락 안에 있다" 는 컨셉을 증명하는 건
금액이다.**

---

## 9. `decisions` — 안건 테이블을 따로 만들지 않았다

`status` 로 세 상태를 표현한다.

| 값 | 뜻 | 쓰이는 곳 |
|---|---|---|
| `DECIDED` | 확정된 결정 | `DLV-05` 결정사항 대장 |
| `PENDING` | 결론이 안 났다 | **`DLV-06` 다음 회의 안건** |
| `REVERSED` | 뒤집혔다 | 대장에 이력으로 |

**미결 결정을 모으면 그게 회의 안건이다.** 테이블 하나가 절약된다.

`superseded_by` 가 **뒤집힌 결정을 추적**한다. 킥오프에서 "6개월" 로 정했다가 3월
회의에서 "8개월" 로 바뀌면, 앞 결정을 `REVERSED` 로 두고 이 컬럼이 뒤 결정을
가리킨다. **문서를 걸쳐야만 알 수 있는 것**이고 사람이 놓치기 쉬운 부분이다.

`decision_status` 와 `decision_state` 두 컬럼이 있는 것이 헷갈릴 수 있다.

| 컬럼 | 무엇의 상태인가 |
|---|---|
| `status` | **결정 자체**의 상태 (확정 / 미결 / 뒤집힘) |
| `decision_state` | **AI 제안**의 승인 여부 (승인 / 거부 / 대기) |

## 10. `deliverables` — 스냅샷이 갱신 판정을 한다

`source_counts_json` 에 생성 시점 개수를 남긴다.

```json
{"documents": 7, "tasks_done": 8, "decisions": 3, "amounts": 1}
```

현재 개수와 비교해 **"문서 2건이 나중에 추가됨 → 다시 만들기"** 를 띄운다. 없으면
매번 다시 세야 하고 판정이 부정확하다.

**주간 보고서의 LLM 호출은 1회뿐이다.** 재요약의 입력이 원문이 아니라 **저장된
요약**이다.

| 방식 | 문서 10건 기준 입력 토큰 |
|---|---:|
| 원문을 다시 보낸다 | 약 28,000 |
| **저장된 요약만 보낸다** | **약 1,500** |

`analyses.result_json['summary']` 에 이미 있는 값을 쓴다. 나머지 항목(태스크 · 결정 ·
일정 · 금액)은 전부 DB 쿼리와 코드 계산이라 **같은 기간을 다시 누르면 같은 표가
나온다.**

## 11. N+1 방지 (`SYS-07`)

미니 프로젝트에서 목록 조회가 `2+2N` 이었다(문서 9건에 쿼리 20개). **테이블이
18개로 늘어나 방치하면 훨씬 심해진다.**

| 화면 | 방법 |
|---|---|
| 프로젝트 목록 | 집계 서브쿼리 1회 |
| **문서 목록** | **`documents` 에 비정규화 2컬럼** |
| 태스크 보드 | `selectinload` |
| 검수 화면 | 페이지 단위 조회 (전체 로드 금지) |
| 산출물 미리보기 | 기간 조건 집계 쿼리 1회 |

**문서 목록은 비정규화가 답이다.** 미니 프로젝트에서 확인했듯 목록이 `analyses` 에서
필요한 값은 `category` · `summary_preview` **두 개뿐**이다.

**트리거를 쓰지 않고 서비스 계층에서 함께 쓴다.** 트리거는 애플리케이션 로그에 남지
않아 디버깅이 어렵다.

---

## 12. DBML 이 표현하지 못하는 것

**세 가지를 마이그레이션에 손으로 넣어야 한다.** SQL 은 `DocFlow_DB.dbml` 파일 하단
주석에 적어 두었다.

| | |
|---|---|
| `CHECK` 제약 | `tasks` 출처가 둘 중 최대 하나만 채워지게 |
| 부분 인덱스 | `is_deleted = false` · `decision = 'PENDING'` |
| `documents.project_id` NOT NULL | 기존 문서에 값이 없어 **3단계**로 전환 |

**마이그레이션 순서 14단계**도 같은 파일에 있다. `tasks` 가 `amount_items` 를,
`documents` 가 `batch_items` 를 참조하므로 순서가 걸린다.

## 13. 미결 사항

기능 단위 미결은 `관리/기능명세서.md` 17절에 있다. 여기는 **DB 에 한정**한다.

### 두 분께 필요한 것

| | 안건 | 담당 | 필수 |
|---|---|---|:-:|
| 1 | `tasks.completed_at` · `updated_at` 추가 | 세현 | **O** |
| 2 | `tasks.source_amount_item_id` + `CHECK` | 세현 | **O** |
| 3 | `documents.document_type` 7종 enum 실제 사용 | 세현 | **O** |
| 4 | `documents.document_type_source` | 세현 | 선택 |
| 5 | `projects.started_on` · `due_on` | 세현 | 선택 |
| 6 | `activity_logs.action_type` 값 목록 합의 | 전원 | O |

**최재정님 파트는 변경이 없다.** 설계안을 그대로 채택했고, 텍스트 조립 시 offset 을
남겨달라는 요청도 취소됐다.

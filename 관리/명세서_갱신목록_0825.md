## 재분석 중복 합산을 확인하는 방법 (패치 `45`)

패치 `45` 는 «문서마다 승인된 최신 분석만 본다» 를 쿼리에 넣은 것이다. 지금은 한
문서에 분석이 하나뿐이라 **눈에 보이는 변화가 없다.** 그래서 두 번째 분석을 손으로
넣어 확인한다.

**패치 전에 넣으면 두 배가 되고, 패치 후에는 그대로다.** 그 차이가 이 패치의 근거다.

**SQL 은 파일로 만들어 `psql -f` 로 넣는다.** psql 프롬프트에 여러 줄을 붙여넣다가
두 번 실패했다 — PowerShell 창에 그대로 붙여 SQL 이 파워셸 문법으로 해석됐다.
그리고 **값에 한글을 쓰지 않는다.** PowerShell 5.1 이 파일을 쓸 때 인코딩이 섞여
psql 이 첫 문장부터 깨진다. 확인용 데이터라 값이 무엇이든 상관없다.

```powershell
cd C:\dev\Tesqra\Tasqra

@'
WITH doc AS (
  SELECT id FROM documents WHERE project_id = 1 ORDER BY id LIMIT 1
), ana AS (
  INSERT INTO analyses (document_id, analyzer_type, result_json, provider, model_name, source_text_revision)
  SELECT id, 'AMOUNT_EXTRACT', '{"note":"dup-check"}'::jsonb, 'MANUAL', 'manual-test-2', 1
  FROM doc
  RETURNING id, document_id
)
INSERT INTO amount_items
  (document_id, analysis_id, item_name, category, quantity, unit, unit_price, amount,
   currency, source_quote, reason, decision, source_text_revision)
SELECT ana.document_id, ana.id, 'DUP-TEST', 'DIRECT_LABOR', 3.0, 'MM',
       8500000, 25500000, 'KRW', 'dup-check quote', 'dup-check', 'APPROVED', 1
FROM ana;
'@ | Set-Content -Path .\dup-check.sql -Encoding ascii

docker compose cp .\dup-check.sql db:/tmp/dup-check.sql
docker compose exec -T db psql -U postgres -d tasqra -f /tmp/dup-check.sql
```

|---|---|---|
| 패치 `45` 전 | **100,750,000** | 75,250,000 + 25,500,000. 두 분석의 항목이 다 더해진다 |
| 패치 `45` 후 | **25,500,000** | 문서 1 의 최신 분석만 본다 = `DUP-TEST` 한 건 |

패치 후 값이 크게 낮은 것은 **정상**이다. 시험 데이터 6건이 전부 문서 1 에 들어

### 정한 것

| | |
|---|---|
| 고칠 수 있는 것 | `quantity` `unit` `unit_price` `amount` `category` 다섯 |
| 고칠 수 없는 것 | `item_name` `source_quote` — 문서에서 읽은 **사실**이다. 이름을 바꾸면 원문과 대조할 수 없다 |
| 「안 보냈다」와 「`null`」을 구별한다 | 앞은 그대로 두라는 뜻, 뒤는 비우라는 뜻. 제경비처럼 수량이 원래 없는 항목에서 잘못 채운 값을 지울 수 있어야 한다 |
| 음수를 막는다 | 문서에 적힌 금액·단가는 음수가 아니다. 감액은 변경계약서 항목으로 온다 |
| 고친 뒤 여전히 어긋나도 막지 않는다 | 그것도 정보다 — 수량을 바로잡았는데 아직 맞지 않으면 다른 곳이 틀렸다는 뜻 |
| 응답이 목록의 한 줄과 같은 모양 | **다시 검산한 결과**가 함께 온다. 화면이 수량×단가를 다시 곱해 판단하지 않는다 |

**`amount`(문서에 적힌 금액)를 고치는 것은 막지 않지만 마지막 선택으로 표시한다.**
`models/amount.py` 는 *"수량x단가와 어긋나도 **코드가** 이 값을 고치지 않는다"* 고
적어 뒀다 — 사람이 고치는 것은 다르고, 그것이 `EDITED` 의 설계 의도다. 대신 화면에
「문서 자체의 오류가 감춰져서 합계 대조가 무의미해집니다」를 적었다.

### 확인하는 방법

문서 1 의 `불일치시험용` (수량 2 × 단가 100,000 = 200,000 인데 문서 금액 250,000).

| 무엇을 고치나 | 기대 |
|---|---|
| 수량을 `2.5` 로 | 2.5 × 100,000 = 250,000 → **「맞음」** 이 되고 어긋난 항목 필터에서 사라진다 |
| 단가를 `125000` 으로 | 2 × 125,000 = 250,000 → 같이 「맞음」 |
| 문서 금액을 `200000` 으로 | 「맞음」이 되지만 **합계가 50,000원 줄어든다** — 문서의 오류를 감춘 것 |
| 수량을 비우고 저장 | 검산 불가가 된다 (제경비처럼) |
| 아무것도 안 바꾸고 저장 | 화면이 «바뀐 값이 없습니다» 로 막는다. API 로 빈 본문을 보내면 `422` |

고친 뒤 **합계·원가구분별·문서 합계 대조가 함께 바뀌는지** 본다 — 그 셋을 다
다시 받게 해 뒀다.


## 수량 0 과 태스크 자동 기록 (패치 `49`)

명세 상태를 바꾸는 것은 없다. 패치 `47`·`48` 의 구멍 둘을 막는다.

### ① 수량이 `0` 일 때 문장이 읽히지 않았다 (사용자가 잡았다)

수량 `0`, 단가 `100,000`, 문서 금액 `200,000` 인 항목에서 —

```
지금:  문서 금액이 200,000원 많음      ← 계산값이 0원이라는 사실이 감춰진다
바꿈:  수량 × 단가가 0원입니다
```

`verify_line` 은 `quantity is None` 만 검산 불가로 본다. `0` 은 `None` 이 아니라
계산이 진행되고 `expected = 0` 이 된다. 계산은 맞지만 문장이 사실을 감췄다.

**`0` 을 「검산 불가」로 바꾸지 않았다.** 이 프로젝트가 계속 지켜온 «0 과 없음은
다르다» 를 깨기 때문이다 — `NULL` 은 "문서에 안 적혀 있다"(제경비), `0` 은 "문서에
0 이라고 적혀 있다" 다(`models/amount.py` 의 `quantity` 주석). 그리고 수량 0 에 금액
200,000 인 줄은 **실제로 앞뒤가 안 맞으므로** 잡아야 한다.

고치기 화면에 이 구별을 적었다 — 안 적으면 수량을 없애려고 `0` 을 넣고 계산값이
0원이 되는 것을 고장으로 읽는다(실제로 겪었다).

### ② 검산이 맞아도 보드에 태스크가 남는다

불일치로 태스크를 만든 뒤 금액을 고쳐 맞게 되면, 보드의 태스크가 **왜 아직 있는지
알 수 없다.**

| 안 하기로 한 것 | 왜 |
|---|---|
| **자동 삭제** | 담당자·마감일·활동 이력이 함께 사라진다. "자동 등록은 하지 않는다"(`AMT-004-3`)의 대칭 — 사람의 판단을 시스템이 덮어쓰는 것은 등록이든 삭제든 같다 |
| **자동 완료(`DONE`)** | `completed_at` 이 주간 보고서의 재료다(`DLV-002-1` 완료 판정: "`tasks.completed_at` 필수"). 시스템이 임의로 찍으면 **보고서에 "이 주에 이 일을 끝냈다" 는 거짓이 들어간다** |

**한 것: 설명 끝의 «자동 기록» 블록을 갈아끼운다.** 보드 카드가 `description` 을
그대로 렌더하므로(`BoardView.jsx` 의 `TaskCard`) 카드에서 바로 보인다. 활동 기록은
별도 다이얼로그 안이라 카드에서는 안 보인다.

```
(사람이 쓴 부분 · 손대지 않는다)

── 자동 기록 ──
검산이 맞았습니다. 수량 × 단가 250,000원 = 문서 금액 250,000원.
```

| 정한 것 | 왜 |
|---|---|
| 구분자 앞은 건드리지 않는다 | 사용자가 적어 둔 메모가 사라지면 안 된다 |
| 블록을 **통째로 교체**한다 | 여러 번 고쳐도 마지막 상태만 남는다. 이력은 `task_activity_logs` 가 담는다 |
| **시각을 적지 않는다** | 이 블록은 «현재 상태» 이고 이력이 아니다. 시각이 있으면 로그처럼 보여 "왜 한 줄만 있나" 가 된다 |
| 상태(`status`)는 안 바꾼다 | 위 표의 이유 |
| 기록 실패가 금액 수정을 되돌리지 않는다 | `enqueue_build_chunks` 주석의 판례 — "이미 성공해서 커밋된 작업을 되돌리면 안 된다". 예외를 삼키고 로그만 남긴다 |
| 색은 `--c-accent-strong` | `utils/theme.js` 가 사용자가 고른 색에서 파생하므로 어느 테마에서도 어울린다. **빨강은 안 쓴다** — 오류가 아니라 상태이고 빨강은 삭제·위험에 이미 쓰고 있다 |

⚠ **구분자 문자열이 두 곳에 있다.** `backend/app/services/task_service.py` 의
`AUTO_NOTE_MARKER` 와 `frontend/src/utils/taskNote.js` 의 같은 이름이다. 한 글자라도
다르면 보드가 블록을 못 찾아 색이 안 입고 본문에 섞여 나온다 — **에러가 없어
알아채기 어렵다.** 한쪽을 고치면 반드시 다른 쪽도 고친다. 파이썬과 자바스크립트라
상수를 공유할 수 없어서 양쪽 주석이 서로를 가리키게 해 뒀다.

### 태스크를 완료로 옮겨도 금액이 중복되지 않는다 (확인함)

사용자 질문이었다. 산출물이 둘을 **따로** 가져온다.

| 산출물 절 | 어디서 |
|---|---|
| 완료한 태스크 | `deliverable_repository.list_completed_tasks` → `tasks` |
| 금액 | `deliverable_repository.list_amount_items` → `amount_items` |

`tasks` 에 금액 컬럼이 없다. 태스크는 **건수·제목**으로, 금액은 **금액**으로 들어가니
같은 돈이 두 번 더해지지 않는다. **완료로 옮기든 삭제하든 금액에 영향이 없다.**

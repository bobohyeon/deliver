> **정답 데이터를 쉽게 만드는 방법** — 글자 정보가 있는 PDF(예: 주차장 표준약관)는
> PDF 안의 텍스트 층이 이미 정확한 정답이다. 같은 페이지를 이미지로 렌더링해 OCR 에 넣고
> 텍스트 층과 대조하면 사람이 옮겨 적지 않아도 실제 정확도가 나온다.
> 비교 시 공백은 정규화해서 제외한다 (텍스트 층도 자간이 뭉개져 있다).

### 목록 조회 N+1 쿼리 실측 — WBS 5.2.4

결정사항 17에서 **"선제 최적화하지 않고 측정한 뒤 개선한다"** 고 정한 항목이다.
발표에서 *"문제를 알고도 남겨두었다"* 가 아니라 *"측정해서 수치를 확보했다"* 로 말하려면 이 수치가 필요하다.

애플리케이션 코드를 건드리지 않고 **DB 쪽 로그**로 센다.

```powershell
# 1) 쿼리 로그 켜기
docker compose exec -T db psql -U postgres -c "ALTER SYSTEM SET log_statement='all'; SELECT pg_reload_conf();"

# 2) 로그 위치 표시를 남기고 목록 1회 조회
docker compose exec -T db psql -U postgres -c "SELECT 'MEASURE-START';"
curl.exe -s -o NUL "http://localhost:8000/api/documents?size=20"
docker compose exec -T db psql -U postgres -c "SELECT 'MEASURE-END';"

# 3) 두 표식 사이의 SELECT 개수 세기
docker compose logs db --tail 800 > "$env:TEMP\db.log"
$t = Get-Content "$env:TEMP\db.log"
$s = ($t | Select-String "MEASURE-START" | Select-Object -Last 1).LineNumber
$e = ($t | Select-String "MEASURE-END"   | Select-Object -Last 1).LineNumber
"구간 SELECT 수: " + (($t[$s..$e] | Select-String "statement: SELECT").Count)

# 4) 로그 되돌리기 (반드시)
docker compose exec -T db psql -U postgres -c "ALTER SYSTEM SET log_statement='none'; SELECT pg_reload_conf();"
```

**기대값** — 문서 20건이면 약 41개. 목록 1회 + 문서당 카테고리·요약 조회 2회.
수치가 나오면 `WBS 5.2.4` 진행률을 올리고, 발표 `05 자체 평가` 의 "조회 쿼리 최적화 미착수" 를
**"20건 조회에 41개 쿼리 — 수치 확보 후 본프로젝트 개선"** 으로 바꾸면 훨씬 단단해진다.

## 3. 준비하면 좋을 것

### 우선순위 높음

**① 발표 대본 (각자 자기 구간)**
슬라이드마다 **말할 문장 2~3개**만 적어 둔다. 통째로 외우면 한 번 막혔을 때 복구가 안 된다.
특히 숫자가 나오는 슬라이드(OCR 비교, 측정 사례, 테스트 결과)는 **숫자를 정확히** 말해야 한다.

**② 리허설 2회 · 시간 측정**
- 1회차 — 구간별 시간만 재고 초과 구간을 찾는다
- 2회차 — 전환 문장과 시연 동선까지 실제와 같게

**③ 시연 백업 영상**
AI 호출과 OCR 은 외부 상황에 좌우된다. **시연 전체를 미리 녹화**해두면 무슨 일이 생겨도 진행된다.
Windows 화면 녹화는 `Win + G` (Xbox Game Bar) 로 가능하다.

**④ 시연 환경 사전 점검** (발표 직전 5분)

```powershell
docker compose ps                                    # 3개 컨테이너 Up 확인
curl.exe -s -o NUL -w "health %{http_code}`n" http://localhost:8000/health
docker compose exec api python -c "from app.core.config import settings; print('키 길이:', len(settings.API_KEY), '/ FAKE:', settings.USE_FAKE_AI)"
```

- `FAKE: False` 여야 한다. **`True` 면 요약이 가짜 문장으로 나온다**
- 카테고리 5종이 목록에 보이는 상태로 사전 업로드해 둔다
- 짧은 공고문(HWPX) 1건을 실시간 업로드용으로 준비한다
- 브라우저 확대를 **110~125%** 로 올린다. 발표장 화면에서 표의 작은 글자가 안 보인다

### 예상 질문과 답변

| 질문 | 답변 요지 |
|---|---|
정확도 98.1% 는 어떻게 나온 값인가 | **엔진이 스스로 보고하는 confidence 평균이다.** 정답 데이터 기반 편집거리 측정 기능은 구현했으나 정답 파일을 확보하지 못해 실측은 본프로젝트로 넘겼다 |
왜 PaddleOCR 인가 | 세 엔진 동시 비교 결과. Tesseract 는 17배 빠르지만 정확도 64.4% 로 사용할 수 없었다 |
처리 시간 55초는 실용성이 있나 | 이미지 개수에 비례한다. 개선 시도 2건을 측정으로 기각했고, 비동기 처리와 진행률 표시를 본프로젝트 과제로 정리했다 |
상태가 `추출 완료` 인데 요약이 있는 이유 | 상태는 추출 파이프라인 단계를 나타내고, 분석은 여러 번 재실행할 수 있는 별도 이력이다. 화면에서는 카테고리 배지 유무로 분석 완료를 판단한다 |
인증은 왜 없나 | 지시서상 선택 항목이다. 구현 시 6~10시간과 기존 API 전체 재검증이 필요해 필수 산출물을 우선했고, 헤더 버튼과 라우트에 삽입 지점만 확보했다 |
테스트 44항목 중 미판정이 있는 이유 | 담당자와 사유를 문서에 남겼다. 그중 1건은 **테스트가 찾아낸 실제 결함**(비즈니스 오류가 서버 로그에 남지 않음)이라 결함으로 기록했다 |
요약 품질은 어떻게 보장하나 | 분류 근거를 함께 출력해 사람이 판단할 수 있게 했다. 자동 판정을 신뢰하는 구조가 아니다 |
업로드 진입점이 두 곳인 이유 | 결정사항 19에서 목록 버튼으로 통일했으나 08-05 UI 개편에서 헤더 메뉴가 다시 추가됐다. 기능 충돌은 없고 단일화는 본프로젝트에서 재검토한다 |

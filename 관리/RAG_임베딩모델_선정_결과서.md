## 0. 한 장 요약

| | |
|---|---|
| **결정** | `pgvector` 컬럼을 **`vector(1024)`** 로 한다 |
| **기본 모델** | **`dragonkue/BGE-m3-ko`** (1024차원 · **apache-2.0**) |
| **대안** | `nlpai-lab/KURE-v1`(mit) · `Snowflake/snowflake-arctic-embed-l-v2.0`(apache-2.0). 차원이 같아 **재임베딩 없이 교체 가능** |
| **탈락** | `e5` 3종(384·768·1024) · `nomic-embed-text-v2-moe`(768) · `Qwen3-Embedding-0.6B`(1024) |
| **핵심 근거** | 글자가 겹치지 않는 질의 **64개 중 41개.** 2·3위는 37개, 최하위는 18개 |
| **모델 확정** | **확정한다.** 8월 12일 판의 "보류" 를 해제한다. 질의를 73 → 133 으로 키워 판별했다 |
| **측정** | **5차까지 진행.** 모델 9개 · 질의 133개 · 청크 649개 (7.6절) |
| **라이선스** | **후보 9종 전부 확인 — apache-2.0 넷 · mit 다섯.** 걸러지는 것 없음 (13.8절) |
| **범위** | **임베딩 모델만 다룬다.** LLM 모델 비교는 별도 문서 (12절) |
| **왜 1024 인가** | **상위 4위가 모두 1024다**(41·37·37·35). 768 은 27·22, 384 는 19 |
| **확인된 것** | **차원이 높으면 좋다는 것은 성립하지 않는다.** 1024인 `e5-large` 가 9종 중 **최하위**다 (8.1절) |
| **철회한 것 둘** | **"768 이 384 보다 낮다"** · **"한국어 특화가 효과 있다"** — 표본을 키우니 성립하지 않았다 (8.1 · 8.2절) |
| **주의** | 채택 모델은 **Ollama 공식 라이브러리에 없다.** GGUF 등록 작업이 붙는다 (13.8절) |

**이 결정으로 pgvector 마이그레이션을 착수할 수 있다.**
차원을 몰라 미뤄뒀던 것이 이번 시험의 목적이었다.
**리비전 번호는 `0011` 이다 — 근거와 주의사항은 11.1절을 본다.**

## 2. 실행 환경 제약 — 이것이 선택 기준을 정했다

| 항목 | 내용 |
|---|---|
| 시험 장비 | 보현 PC. **GPU 없음. CPU 단독** |
| LLM 실행 장비 | 세현 GPU 장비 (별도) |
| 발표 방식 | **실시간 데모가 아니라 영상 촬영** |
| 문서 크기 상한 | `MAX_EXTRACTED_CHARS = 45,000자` |
| 성능 요구 | `PER-01` 10페이지 60초 |

**영상 촬영이라는 점이 판단을 바꿨다.**

| | 실시간 데모 | 영상 촬영 |
|---|---|---|
| 느린 구간 | 그대로 보인다 | 편집으로 잘라낸다 |
| 최종 실행 장비 | 발표장 PC | **세현 GPU 장비 가능** |
| CPU 속도 압박 | 크다 | 작다 |

그래서 **CPU가 느리다는 이유만으로 1024차원을 배제하지 않았다.**
개발·시험은 CPU에서 하고, 최종 촬영은 GPU 장비에서 하면 된다.
다만 384차원을 후보에 남겨 **CPU로 감당이 안 될 정도인지 실제로 재봤다.**

## 3. 모델 선택 시 고려 사항 8가지

| | 항목 | 왜 중요한가 | 이번에 확인한 방법 | 결과 |
|---|---|---|---|---|
| 1 | **벡터 차원** | `pgvector` 컬럼을 묶는다. 바꾸면 전체 재임베딩 | 384·768·1024 를 같은 평가셋으로 비교 | **1024 채택.** 상위 4위 독점 |
| 2 | **글자 안 겹치는 질의 성능** | 이게 임베딩을 쓰는 근거 자체 | `no_overlap` **64문항** `R@5` | 1위 41 · 최하위 18 |
| 3 | **글자 겹치는 질의만 보면 안 된다** | 키워드 검색으로도 되는 일이다 | `overlap`과 분리 집계 | **역전 발생 (8.3절)** |
| 4 | **접두어 규칙** | 안 지키면 한쪽이 억울하게 진다 | 모델이 선언한 값을 읽어 적용 | 적용 확인 (5.5절). **함정 하나 발견** |

## 4. 후보를 9종으로 늘린 근거

**3종 → 5종 → 9종으로 늘렸다.** 늘린 이유가 회차마다 다르다.

### 4.1 후보 9종 — 각 모델이 하나의 질문에 답한다

| | 모델 | 차원 | 질의 접두어 | 문서 접두어 | **이 모델로 답하는 질문** | 넣은 회차 |
|---|---|---|---|---|---|---|
| 1 | `BAAI/bge-m3` | 1024 | 없음 | 없음 | **기준선.** 한국어 특화가 이걸 못 이기면 특화의 의미가 없다 | 1차 |
| 2 | `nlpai-lab/KURE-v1` | 1024 | 없음 | 없음 | **한국어 특화가 효과 있나.** bge-m3 기반이라 같은 조건 비교 | 1차 |
| 3 | `dragonkue/multilingual-e5-small-ko-v2` | 384 | `query: ` | `passage: ` | **작은 모델로 충분한가.** CPU 현실성 | 1차 |
| 4 | `intfloat/multilingual-e5-base` | 768 | `query: ` | `passage: ` | 같은 계열에서 **차원만** 다르면 어떻게 되나 | 4차 |
| 5 | `intfloat/multilingual-e5-large` | 1024 | `query: ` | `passage: ` | 위와 같은 축의 상단 | 4차 |
| 6 | **`dragonkue/BGE-m3-ko`** | 1024 | 없음 | 없음 | **다른 한국어 튜닝은 다른가.** 같은 bge-m3 기반, 다른 제작자 | **5차** |
| 7 | `Snowflake/snowflake-arctic-embed-l-v2.0` | 1024 | `query: ` | **없음** | **다국어 최신 모델이 한국어 튜닝을 이기나** | **5차** |
| 8 | `nomic-ai/nomic-embed-text-v2-moe` | 768 | `search_query: ` | `search_document: ` | 768 · MoE 구조로 충분한가 | **5차** |
| 9 | `Qwen/Qwen3-Embedding-0.6B` | 1024 | `Instruct: …Query:` | 없음 | **디코더 계열이 인코더보다 나은가** | **5차** |

```
축 1  한국어 튜닝 효과        ->  bge-m3 대 KURE-v1 · BGE-m3-ko
축 2  다국어 최신 대 한국어    ->  arctic 대 KURE-v1 · BGE-m3-ko
축 3  같은 계열의 차원        ->  e5 384 · 768 · 1024
축 4  구조 (인코더 대 디코더)  ->  bge 계열 대 Qwen3
```

3번을 "자원 절약용"이 아니라 **진짜 후보**로 넣은 이유가 있다.
모델 카드가 "2배 큰 `e5-base`보다 한국어 벤치마크에서 낫다"고 밝히고 있다.
**5차에서 그 주장이 뒤집혔다** — 384(19) < 768(22) 이다(8.1절).

### 4.2 5차에서 후보를 늘린 이유

8월 12일 판은 **"1024차원 추가 모델은 지금 넣지 않는다"** 고 적었다.
근거는 "KURE 와 bge 차이가 1문항이라 같은 차원 모델을 더 넣으면 노이즈만
늘어난다" 였다. **그 판단을 뒤집었다.**

| | 그때 판단 | 5차에서 바꾼 이유 |
|---|---|---|
| 무엇 | 1024 모델을 더 넣지 않는다 | **넷을 더 넣었다** |
| 왜 | 표본 34문항에서 잡음만 늘어난다 | **표본을 64문항으로 키웠다.** 잡음이 줄었으니 후보를 늘릴 조건이 됐다 |
| 결과 | — | **넣은 넷 중 하나(`BGE-m3-ko`)가 1위가 됐다** |

**넣지 않았다면 1위 모델을 못 찾았을 것이다.** 다만 순서가 중요했다 —
**질의를 먼저 늘리고 후보를 늘렸다.** 반대로 했다면 잡음 속에서 9종을 비교하는
셈이었다.

세현이 요청한 두 모델(`BGE-m3-ko` · `Qwen3-Embedding`)이 6번과 9번이다.
**요청받은 모델을 재는 것이 이 회차의 계기였고, 그중 하나가 채택됐다.**

### 4.3 아직 보류한 후보

| 모델 | 차원 | 언제 넣나 |
|---|---|---|
| `nlpai-lab/KoE5` | 1024 | 한국어 튜닝을 더 볼 때. **접두어가 필요하다** (KURE README 주의사항) |
| `mykor/KURE-v1-gguf` | 1024 | 양자화본 품질을 볼 때. **채택 모델도 GGUF 로 배포하므로 같은 문제다** |
| CLOVA Studio 임베딩 | 확인 필요 | **유료.** 로컬로 좁힌 뒤 마지막 |
| `Qwen3-Embedding` 4B · 8B | 1024 | **CPU 로 무리다.** 0.6B 가 이미 2~2.5배 느리다 |

**CLOVA를 볼 때 확인할 것** — 임베딩 모델 목록에 `bge-m3`가 있는지 본다.
같은 가중치를 호스팅한다면 이번 로컬 결과가 그대로 적용되고,
비교가 "성능"이 아니라 **"직접 띄우기 대 API"** 로 단순해진다.

### 4.4 계획과 실제의 차이

당초 3단계로 나눴다.

| | 계획 | 실제 |
|---|---|---|
| 1라운드 | KURE 레포 발표 벤치마크로 후보 좁히기 | **실패.** 레포 접근이 403으로 막혔다. **나중에 MTEB-ko-retrieval 인용표로 대체했다** |
| 2라운드 | 우리 문서 5건 + 질의 15개로 도메인 확인 | **여기서 직접 측정.** 최종 문서 10건 · 질의 133개 |
| 3라운드 | 필요하면 확장 | **API 미착수.** 하네스는 붙여 뒀다 |

**1라운드를 건너뛰고 2라운드를 크게 한 셈이다. 결과적으로 이게 나았다.**
공개 벤치마크는 일반 한국어 검색을 재지만, 우리 도메인은 공공 SI 공고문과
계약 CSV다. 문장 구조와 어휘가 다르다.

**다만 공개 벤치마크를 나중에 인용표로 만든 것이 판단에 도움이 됐다.**
`관리/RAG_임베딩모델_공개벤치마크_인용표.md` 가 그것이고, 우리 실측 1·2·3·4위가
공개 순위 1·2·3·4위와 겹친다는 것을 확인했다. **표본이 작다는 약점을
남의 측정으로 보완한 것이다.**

당초 "질의 15개로 시작"으로 잡았으나 최종 133개가 됐다. 과했다고 보지 않는다.
**73개(안겹침 34)에서는 1위와 2위를 가릴 수 없었고, 133개(안겹침 64)에서
갈렸다.** 15개였다면 아무것도 판별하지 못했다.

### 5.2 청킹

```
python make_chunks.py --max-per-doc 300 --max 700

문서 10건 -> 청크 649개
총 210,078자 · 평균 305자 · 최장 697자
```

절 제목(`#`, `제3조`)에서 끊고, 표로 보이는 줄은 이어 붙인다.

**옵션이 8월 12일 판과 다르다.** 그때는 `--target 500 --max 1200` 이었다.

| 옵션 | 왜 바꿨나 |
|---|---|
| `--max 1200` → **`--max 700`** | 1200 짜리 청크는 512토큰 상한 모델에서 잘릴 수 있었다. 8.8절이 지적한 위험을 실제로 줄인 것이다 |
| **`--max-per-doc 300` 추가** | 문서 하나가 코퍼스를 지배하는 것을 막는다. 이것이 없어서 3,655청크 사고가 났다 |

#### 청킹 도구에서 고친 결함 셋

측정하면서 발견해 고쳤다.

| | 결함 | 무슨 일이 났나 | 고친 방식 |
|---|---|---|---|
| 1 | **상한을 넘는 덩어리를 쪼개지 않았다** | 표 하나가 2,000자·5,000자 청크가 되어 모델 입력에서 조용히 잘릴 수 있었다 | 상한 초과분을 다시 쪼갠다 |
| 2 | **문서 하나가 코퍼스를 지배했다** | CSV 20건을 넣었더니 청크가 545 → 3,655 로 늘고 **82%가 표의 행**이 됐다 | `--max-per-doc` 상한 + 지배 경고 |
| 3 | 중복 청크가 생겼다 | 같은 내용이 두 번 들어가 정답 청크가 갈렸다 | 중복 방지 |

#### PDF 추출에서 공백이 사라지는 결함 — 제품에도 있다

행안부 고시를 넣으면서 발견했다. **양쪽정렬(justified) PDF 를 PyMuPDF 로 뽑으면
어절 사이 공백이 사라진다.**

```
원문        제1조(목적) 이 지침은 「전자정부법」...
PyMuPDF     제1조(목적)이지침은「전자정부법」...
```

| 도구 | 공백 비율 |
|---|---|
| PyMuPDF | **9.7%** |
| pdfplumber (`x_tolerance=1.5`) | **19.9%** |

**PDF 안에 정보가 있는데 추출기가 잃는 것이다.** 양쪽정렬은 글자 위치를 좌표로
벌려 놓아서, PyMuPDF 가 간격이 기준보다 좁으면 공백을 넣지 않는다.

**이것은 시험 도구만의 문제가 아니다.** `도구/embed-test/convert_inputs.py` 의
주석에 **본구현(`app/extractors/pdf_extractor.py`)도 PyMuPDF 를 쓴다**고 적혀
있다. **관공서 고시·지침·계약서는 대부분 양쪽정렬이므로 DocFlow 에 올리면 같은
일이 생기고, 그 뒤 요약·분류·임베딩이 전부 공백 없는 텍스트를 받는다.**

`관리/산출물_변경대기_목록.md` `A-5` 에 제품 결함으로 등록했다.

**시험 도구에서는 문서를 지정해서만 pdfplumber 로 바꿨다.** 전부 바꾸면 이미
측정에 쓰고 있는 문서들의 텍스트가 달라져 **청크 번호가 밀리고 `gold_chunk_ids`
가 조용히 어긋난다.** `check_queries.py` 는 번호가 존재하는지만 보므로 이 사고를
잡지 못한다.

#### 쪽 넘김이 문장을 끊는 문제 — 아직 안 고쳤다

고시 조문에서 발견했다.

```
10쪽 끝 : ... 다만, 추정가격이 20억원 이상인 사업에 대해
11쪽 시작: 서는 제안요청 설명회를 실시하여야 한다.
```

**`대해` 와 `서는` 사이에 쪽 표시(`## 11쪽`)가 끼어들어 문장이 두 조각으로
갈라진다.** 질의 앵커를 잡을 때 이것 때문에 한 건이 실패했다.

**쪽 표시를 청크 본문에서 빼고 메타로 옮기는 것**을 검토해야 한다.
`RAG-01` 본구현은 `ocr_elements` 를 입력으로 쓰므로 쪽 경계 정보가 별도로
들어온다. 이 문제는 시험 도구에만 있는 것일 수 있다.

**본구현 청킹과 다르다는 점을 분명히 한다.** `RAG-01` 완료 판정 기준은
`ocr_elements` 의 `element_type` 으로 단락을 묶고 **토큰 수 기준**으로 자르는
것이다. 이 실험은 `corpus/*.md` 텍스트를 **글자 수 기준**으로 잘랐다.

| | 이 실험 | `RAG-01` 본구현 |
|---|---|---|
| 입력 | `corpus/*.md` (변환된 텍스트) | `ocr_elements` (DB 행) |
| 경계 | 마크다운 제목 · 절 제목 | `element_type` 단락 묶음 |
| 길이 기준 | **글자 수** (`--max 700`) | **토큰 수** |

**따라서 이 실험은 모델 비교용 근사 조건이다.** 차원과 모델 선택 결론은
청킹 방식에 크게 좌우되지 않으므로 유효하지만, **절대 점수(41/64)를 본구현
검색 품질 예측치로 쓰면 안 된다.** 본구현 청킹이 완성된 뒤 `RAG-10` 으로
다시 재야 한다. 표를 행 단위로 유지하는 규칙은 양쪽이 같다.

#### 청킹 입력은 재정 담당 OCR 산출물에서 받는다

기능명세서에 이미 그렇게 적혀 있다.

| ID | 선행 | 비고 |
|---|---|---|
| `RAG-01` | **`REV-17`** (텍스트 재조립) | **재정님 단락 분리를 입력으로 쓴다** |

**청킹을 별도로 만들지 않고 OCR 검수 파트의 출력을 받아 이어 붙인다.**
같은 문서를 두 번 구조화하지 않는다.

| | |
|---|---|
| 받는 것 | `ocr_elements` (`element_type` · 좌표 · `reading_order` · `is_excluded`) |
| 하는 것 | `element_type` 으로 단락 묶기 → 토큰 수로 자르기 → `document_chunks` 저장 |
| 의존 | **`RAG-01` 은 `REV-17` 완료에 블로킹된다** (재정 담당 · P1) |

#### 확인 필요 — `element_type` 의 값 집합이 정의되어 있지 않다

Tasqra 코드를 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| `ocr_elements.element_type` 컬럼 | **있다.** `String(20)` NOT NULL · 기본값 `"TEXT_LINE"` |
| 허용 값 CHECK 제약 | **없다** (0006 에는 좌표·version CHECK 만 있다) |
| `models/enums.py` 에 해당 Enum | **없다** |
| 응답 스키마 `OcrElementResponse` 노출 | **안 된다** (id · text · 좌표 · confidence · source · reading_order · version 만) |

**즉 `"TEXT_LINE"` 하나만 확인되고 나머지 값이 무엇인지 모른다.**
`RAG-01` 이 이 컬럼으로 단락을 묶는데, **어떤 값이 단락 경계인지 재정님과
합의해야 한다.** 값 집합이 없으면 청킹 규칙을 쓸 수 없다.

0007 docstring 에 "0006 은 `element_type` 컬럼으로 (단락 묶음) 같은 목적을
달성하고 있으므로" 라고 적혀 있어 **의도는 있으나 값이 아직 안 정해진 상태다.**

리비전 규칙(0001 부터)이 **ENUM 대신 `String` + CHECK** 이므로,
값이 정해지면 CHECK 제약을 추가하는 마이그레이션이 필요하다.
`element_type` 을 응답 스키마에도 노출해야 프런트가 단락을 표시할 수 있다.

`REV-17` 의 완료 판정이 "박스 수정 후 `extracted_texts.content` 가 같은
트랜잭션에서 갱신된다" 이므로, **그 트랜잭션이 끝난 시점의 텍스트가 청킹 입력이다.**

그리고 `RAG-10` 의 비고가 **"청킹 기준 변경의 판단 근거"** 다.
즉 본구현 청킹이 완성된 뒤 이 평가셋으로 다시 재는 것이 `RAG-10` 의 설계 목적이다.
**이번 결과서가 그 첫 회차 기록이 된다.**

**다만 리비전 `0011`(pgvector + `document_chunks`)은 지금 만들 수 있다.**
컬럼 차원만 알면 되고, 그것을 이 문서가 정했다. 청킹 로직과 스키마는 분리된다.

**머지된 `0008` 이 `ocr_elements.is_excluded` 를 추가한 것에 주의한다.**
제외 표시된 요소는 청킹에서 빼야 한다. 넣으면 검수로 지운 텍스트가 검색에
남는다 — `RAG-09` 가 막으려는 것과 같은 문제다.

**머지된 `0009` 는 `text_char_count` · `ocr_char_count` 를 나눠 저장한다.**
청크가 OCR 에서 왔는지 판단할 근거가 되어 스니펫에 표시할 수 있다 — 11.1절.

### 5.3 평가셋 설계 — 질의를 구하지 않고 문서에서 역으로 뽑았다

도메인 지식이 필요 없는 방법을 썼다.

```
1. 문서를 청크로 쪼갠다
2. 청크를 읽고 "이 청크가 답이 되는 질문" 을 쓴다
3. 정답은 자동으로 그 청크 번호가 된다
```

청크마다 두 종류를 만들었다.

| `kind` | 규칙 | 무엇을 재나 |
|---|---|---|
| `overlap` | 청크의 단어를 그대로 쓴다 | 기준선. 키워드 검색으로도 찾힌다 |
| **`no_overlap`** | **청크의 단어를 하나도 쓰지 않는다** | **의미 검색만 찾을 수 있다** |

`no_overlap`이 `RAG-04` 완료 판정 기준("글자가 하나도 겹치지 않는 질의")에
그대로 대응한다.

**중요 — `no_overlap`에서 키워드 검색의 상한은 정의상 0이다.**
2글자 이상 토큰이 정답 청크에 하나도 없도록 만들었고 이를 기계로 검증했다.
따라서 토큰·부분문자열 기반 검색(`regexp_replace` + `ILIKE`)은 원리상 찾을 수 없다.
**이건 측정 결과가 아니라 설계상 필연이므로, "키워드로는 0%"를 성과로 말하면 과장이다.**
성과는 임베딩이 그 0을 얼마나 넘는지다.

### 5.4 채점

| 지표 | 뜻 |
|---|---|
| `R@k` | 정답이 상위 k개 안에 들어온 질의 비율 |
| `MRR` | 정답의 순위 역수 평균. 몇 번째로 나오는지 |

`TOP_K = (1, 3, 5, 10)`. **판단 1순위는 `no_overlap`의 `R@5`.**

### 5.5 공정성 검증 — 접두어

접두어가 필수인 모델이 있다. 빼면 성능이 크게 떨어진다.
**틀리면 성능이 아니라 설정 실수를 재게 되므로 코드로 확인했다.**

```python
passages = [model_cfg["passage_prefix"] + c["text"] for c in chunks]   # run_eval.py
q_texts  = [model_cfg["query_prefix"]   + q["query"] for q in queries]
```

**5차에서는 짐작하지 않고 모델이 선언한 값을 읽었다.**
`config_sentence_transformers.json` 의 `prompts` 를 그대로 옮겼다.

| 모델 | `query_prefix` | `passage_prefix` |
|---|---|---|
| bge-m3 · KURE-v1 · **BGE-m3-ko** | (없음) | (없음) |
| **arctic-embed-l-v2.0** | `query: ` | **(없음)** |
| **nomic-embed-text-v2-moe** | `search_query: ` | `search_document: ` |
| Qwen3-Embedding-0.6B | `Instruct: …` + 줄바꿈 + `Query:` | (없음) |
| e5 3종 | `query: ` | `passage: ` |

**적용 확인. e5 의 패배는 설정 실수가 아니다.**

#### 함정 하나 — 같은 빈 문자열인데 뜻이 다르다

`nomic` 이 선언한 값은 이렇다.

```
"query":    "search_query: "
"document": ""                  <- 비어 있다
"passage":  "search_document: " <- 실제 문서 접두어는 여기
```

**`document` 키를 그대로 믿으면 `nomic` 문서에 접두어가 안 붙는다.**
`nomic` 은 접두어가 필수인 모델이라 점수가 크게 떨어진다.

**`arctic` 은 정반대다.** `arctic` 의 `"document": ""` 는 **진짜로 안 붙이는 것이
맞다**(`passage` 키가 아예 없다). 같은 빈 문자열인데 뜻이 반대다.

그래서 규칙을 이렇게 정했다.

> `passage` 가 있고 비어 있지 않으면 그것을 쓴다. 없으면 `document` 를 쓴다.
> 그것도 비어 있으면 접두어 없음.

**`Qwen3` 의 질의 접두어는 줄바꿈을 포함하고 `Query:` 뒤에 공백이 없다.**
임의로 공백을 넣으면 조건이 달라진다.

#### 5차에서 놓친 조건 — 정밀도

접두어와 최대 입력 길이는 맞췄는데 **정밀도를 안 봤다.**
`Qwen3` 만 `bfloat16` 으로 올라와 나머지 `float32` 와 조건이 달랐다.
경위는 7.6절에 있다.

| | 조건 | 5차 |
|---|---|---|
| 1 | 접두어 | 맞췄다 |
| 2 | 최대 입력 길이 | 맞췄다 |
| 3 | **정밀도(dtype)** | **놓쳤다** |

### 5.6 하네스 점검 — 바닥 확인

모델을 내려받기 전에 가짜 인코더(글자 빈도를 64차원에 넣는 것)로 채점 로직을
확인했다.

| 모델 | `no_overlap` R@5 | `overlap` R@5 |
|---|---|---|
| 가짜 인코더 (질의 78개 시점) | **0 / 39** | 15 / 39 |
| 가짜 인코더 (질의 73개 시점) | **0 / 34** | 7 / 39 |

`overlap`이 높고 `no_overlap`이 0인 방향이 나와야 정상이며 그대로 나왔다.
**`no_overlap` 0 은 아주 깨끗한 바닥이다.** 실제 모델이 여기서 올리는 만큼이
도입 근거다.

#### 5차(질의 133개)에서는 이 점검을 다시 돌리지 않았다

**`--self-test` 가 `results.csv` 를 가짜 결과로 덮어쓰기 때문이다.**
실제로 이 때문에 한 회차 결과를 잃었다 — 8모델 측정을 돌리기 전에 점검을
했더니 이전 회차 수치가 사라졌다.

**도구 결함으로 기록한다.** 가짜 결과가 진짜 파일을 지운다.
`results_selftest.csv` 로 분리해야 한다.

## 6. 평가셋 결함과 수정 경과

**이 절이 결과 신뢰도의 근거다.** 1차 결과에는 결함이 있었고, 진단으로 찾아 고쳤다.

### 6.1 검사 도구를 만든 이유

`run_eval.py`는 쓸 수 없는 행을 **예외 없이 건너뛴다.** 질의 40개를 넣고
32개만 채점돼도 알아채기 어렵다. 그래서 앞에 검증을 세웠다.

`check_queries.py`가 잡는 것:

| 잡아내는 것 | 위험 |
|---|---|
| `note`에 "예시"가 든 행 | **경고 없이 채점에서 빠진다** |
| 없는 청크 번호 · 정답 없음 | 같이 조용히 빠진다 |
| `no_overlap`인데 단어가 겹침 | **사람 눈으로는 반드시 새어나간다** |
| `overlap`인데 겹치는 말이 없음 | 기준선이 기준선 역할을 못 한다 |
| `kind` 오타 | `unknown`이 되어 어느 집계에도 안 들어간다 |
| 정답이 문서 한 곳에 몰림 | 그 문서 특성만 재게 된다 |

실제로 78문항 중 3건이 `no_overlap` 라벨 위반으로 걸렸다.
`하는` `있는` `사업` 이 정답 청크에 들어 있었다.

### 6.2 기각된 가설 두 개

`no_overlap` 39문항 중 13문항을 **세 모델이 모두 틀렸다.** 원인을 세 번 추정했다.

| 가설 | 결과 | 반박한 데이터 |
|---|---|---|
| 청크가 커서 벡터가 희석된다 | **기각** | 실패한 청크에 151자·99자가 있고, 같은 길이 CSV 행 청크는 성공했다 |
| 허브 청크가 상위를 점거한다 | **기각** | 전체 78질의로 세니 최다 10회. 기대값 3.07회의 3.3배 — 정상 분포 |
| **평가셋 결함이 지배한다** | **확인** | 청크 13 · 24 · 2가 실제 정답이었다 |

**두 번 앞서갔고 두 번 데이터에 교정받았다.**
`--target` 조정 실험을 먼저 했다면 헛수고였다.

### 6.3 확인된 결함 — 모델이 맞고 정답 표시가 틀렸다

| 청크 | 내용 | 오답 처리된 질의 |
|---|---|---|
| 13 (57자) | `공동이행방식만 가능하며, 공동수급체 구성원 모두가 입찰참가자격을 갖추어야 함` | `여러 곳이 팀을 짜서 들어올 수 있나` (정답 1) |
| 24 (483자) | `낙찰자 결정방법 — 기술능력배점 90점, 입찰가격배점 10점` | `점수를 어떻게 나눠 매기나` (정답 4) |
| 2 (465자) | `지역제한 업종제한 업종제한사항` | `장부 다루는 곳만 응찰할 수 있나` (정답 1) |

세 모델이 일관되게 이 청크들을 상위에 넣었다. **셋 다 정답이다.**

원인은 하나다. **같은 종류의 정보가 여러 문서에 흩어져 있다.**

```
평가 배점   청크 4  기초과학연구원 80% / 20%
            청크 24 중앙보훈병원  90점 / 10점      둘 다 정답이다

공동수급    청크 1  공동수급불허
            청크 13 공동이행방식만 가능              둘 다 답이 된다

예산·금액   60개 이상 청크                          특정 하나를 정답으로 둘 수 없다
```

**이번 시험에서 얻은 가장 중요한 평가셋 설계 원칙이다.**
문서 여러 건을 한 코퍼스에 넣으면 질의가 문서를 특정해야 하는데,
문서를 특정하면 문서명이 질의에 들어가 `overlap`이 되어버린다.
**해법은 정답을 넓게 두는 것이다.** `R@5`로 재니 둘 중 하나만 잡아도 성공이다.

### 6.4 수정 내역 — 78문항 → 73문항

| 조치 | 질의 | 이유 |
|---|---|---|
| **삭제** | `이 일에 잡힌 예산이 얼마인가` (4,5) | 예산 청크가 60개 이상. 측정 불가 |
| 삭제 | `배정된 예산 규모` (7) | 같은 이유 |
| 삭제 | `하나만 내면 되나` (31) | "하나"가 무엇인지 문장에 없다. **사람도 못 맞힌다** |
| 삭제 | `무엇을 해야 하는지 적힌 서류를 어디서 받나` (6) | "받나"가 다운로드인지 작성기준인지 모호 |
| 삭제 | `밖으로 새지 않게 다짐을 받아둘 수 있나` (33) | 코퍼스에 서약서·협약이 여럿 |
| **정답 확장** | `여러 곳이 팀을 짜서 들어올 수 있나` | 1 → 1,13 |
| 정답 확장 | `장부 다루는 곳만 응찰할 수 있나` | 1 → 1,2 |
| 정답 확장 | `점수를 어떻게 나눠 매기나` | 4 → 4,24 |
| 정답 확장 | `기술능력평가비율` | 4 → 4,24 |

```
1차  78문항  overlap 39 · no_overlap 39
2차  73문항  overlap 39 · no_overlap 34
5차 133문항  overlap 69 · no_overlap 64      <- 고시 조문 질의 60개 추가
```

**점수를 올리려는 조치가 아니다. 측정할 수 없는 문항을 빼고, 잘못 채점된
문항을 바로잡은 것이다.** 남기면 지표가 오염된다.
**1차 수치를 지우지 않고 함께 남긴다.** 결함을 찾아 고친 경과가 기록되어야
숫자를 신뢰할 수 있다.

### 6.5 5차 — 질의를 두 배로 늘렸다

**청크를 늘리는 것으로는 1위와 2위를 가릴 수 없다는 것을 4차에서 확인했다.**
4차에서 청크를 127 → 545 로 4.3배 늘렸는데 `KURE` 대 `bge-m3` 격차가 1문항
그대로였다. **방해물만 늘고 판별력은 안 늘었다.**

그래서 5차에서는 **질의를 늘렸다.**

| | 4차 | 5차 |
|---|---|---|
| 청크 | 127 | 649 |
| **안겹침 질의** | **34** | **64** |
| 정답 청크 | 32 | 62 |

#### 정답 청크 번호를 손으로 적지 않았다

질의 60개를 만들면서 **앵커 문구로 코드가 찾게 했다.**

```
("계약체결 후 10일 이내",                     <- 앵커
 "계약체결 후 10일 이내 착수계 제출",           <- overlap 질의
 "일을 시작하겠다는 서류를 언제까지 내나",       <- no_overlap 질의
 "제39조 착수계 10일",                        <- 사실 메모
 "착수계·계약체결·제출 안 씀")                 <- 피한 낱말
```

`make_queries_13.py` 가 `chunks.csv` 에서 앵커를 찾아 번호를 붙인다.
**앵커 비교는 공백을 모두 지운 뒤 하므로 줄바꿈이나 띄어쓰기 차이에 영향받지
않는다.** 앵커가 두 곳 이상에 걸리면 그 질의를 버린다.

**손으로 번호를 적으면 재청킹 때마다 어긋난다.** 앵커 방식은 청크가 다시 잘려도
다시 찾는다.

#### 부분 문자열까지 검사했다 — 9건이 걸렸다

`no_overlap` 라벨이 실제로 맞는지 도구로 전수 검사했다.
**낱말 단위가 아니라 부분 문자열까지 본다.**

| 질의에 쓴 말 | 걸린 이유 |
|---|---|
| `보안` | 정답 청크에 **`보안약점`** 이 있다 |
| `정한` | **`지정하여야`** 안에 들어 있다 |
| `항목을` `이상` | 정답 청크 본문에 그대로 있다 |
| `않은` `외부` | `검증되지 않은 외부 입력값` |
| `받은` `전에` `기존` `예산이` | 각각 정답 청크에 있다 |

**사람 눈으로는 못 잡는다.** 9건을 고쳐 `겹침 0` 을 만들었다.

#### 조 번호를 질의에 쓰지 않았다

**"제18조의 배점한도는?" 이라고 물으면 `제18조` 라는 글자가 그 청크에만 있어서
임베딩 실력이 아니라 글자 일치로 맞힌다.** 그래서 조 번호를 뺐다.

운영에서는 뒤집힌다. 사용자가 "제18조" 라고 물으면 낱말 일치로 찾는 것이 맞다.
**즉 조 번호·금액·날짜 같은 값은 벡터가 아니라 낱말 일치로 보내는 것이 낫고,
이는 8.6절 하이브리드 검색 결론과 같은 방향이다.**

#### 앵커 하나가 실패했다 — 쪽 넘김 때문

`이상인 사업에 대해서는 제안요청 설명회` 가 안 걸렸다. 원문이 쪽을 넘어간다.

```
10쪽 끝 : ... 추정가격이 20억원 이상인 사업에 대해
11쪽 시작: 서는 제안요청 설명회를 실시하여야 한다.
```

**앵커를 10쪽 안쪽으로 당겨 해결했다.** 5.2절에 청킹 쪽 문제로도 기록했다.

#### 기각한 가설 — 산술이 맞아떨어졌는데 전제가 틀렸다

원인을 찾을 때 `max_seq_length` 가 32,768 이라 배치를 그 길이로 채운다고 봤다.
**계산이 맞아떨어졌다** — 관측 CPU 시간을 32,768토큰 기준으로 나누면 현실적인
처리량이 나왔다. 400토큰 기준으로는 코어당 1 GFLOPS 라는 불가능한 값이었다.

**그런데 실제 패딩 모양을 찍어보니 `(8, 398)` 이었다.** 정상이다. 가설은 기각됐다.

> **계산이 맞는 것과 전제가 맞는 것은 다르다.**

이번 시험에서 같은 방식으로 두 번 틀렸다 — 토큰 잘림 때도, 패딩 때도
그럴듯한 근거를 먼저 만들고 확인을 나중에 했다.

### 재현성이 확인됐다

같은 코퍼스·질의로 두 번 돌렸더니 품질 수치가 **완전히 같았다.**

| 모델 | 8모델 실행 | 3모델 실행 |
|---|---|---|
| `KURE-v1` 안겹침 R@5 | 0.578 | **0.578** |
| `BGE-m3-ko` 안겹침 R@5 | 0.641 | **0.641** |

**품질은 결정적이고 비용은 아니다.** 모델 간 품질 격차를 실행 잡음으로 의심할
필요가 없다.

## 8. 결과가 말하는 것 — 주장과 근거

### 8.1 `pgvector` 컬럼은 `vector(1024)` — 확정

| 근거 | 수치 |
|---|---|
| **상위 4위가 모두 1024차원이다** | **41 · 37 · 37 · 35** |
| 768 최고 · 384 | **27** (`nomic`) · **19** (`e5-small-ko-v2`) |
| 1024 대 384 격차 | **41 대 19 — 22문항** |
| 저장 용량 손실 | 청크당 2.5KB. 649청크에 약 1.6MB, 문서 100건 규모(6,500청크)에 약 16MB. 무시 가능 |
| 교체 자유도 | 1024면 **다섯 모델**(`BGE-m3-ko`·`KURE-v1`·`arctic`·`bge-m3`·`Qwen3`)을 재임베딩 없이 바꿔 끼운다 |

**이 결정으로 pgvector 마이그레이션(리비전 `0011`)을 쓸 수 있다.**

#### 실측 — "차원이 높으면 성능이 높다" 는 성립하지 않는다

같은 `e5` 계열 세 점으로 확인했다. **계열을 고정하고 차원만 바꾼 비교다.**

| 차원 | 모델 | 계열 | `no_overlap` R@5 | R@10 |
|---|---|---|---|---|
| 384 | `e5-small-ko-v2` | e5 · **한국어 튜닝** | 19 / 64 | 28 |
| **768** | `e5-base` | e5 · 다국어 원본 | **22 / 64** | **29** |
| **1024** | **`e5-large`** | e5 · 다국어 원본 | **18 / 64** | **21** |

**차원을 768 에서 1024 로 올렸는데 점수가 내려갔다.**
`e5-large` 는 1024차원인데 **9종 중 최하위**이고 384차원 모델(19)보다도 낮다.

#### 8월 12일 판의 서술 하나를 철회한다

**"768 이 384 보다 낮다" 는 서술을 철회한다.** 표본을 키우니 뒤집혔다.

| | 4차 (질의 34개) | **5차 (질의 64개)** |
|---|---|---|
| 384 (`e5-small-ko-v2`) | **14** | 19 |
| 768 (`e5-base`) | 13 | **22** |
| R@10 · 384 대 768 | **24 대 18** (384 우세) | **28 대 29** (768 우세) |
| 그때 쓴 결론 | "한국어 튜닝이 차원 2배보다 크다" | **성립하지 않는다** |

**4차에서는 1문항 차이(14 대 13)를 근거로 결론을 썼다.** 그때도 "노이즈 범위"
라고 적었으면서 "차원 2배보다 크다" 는 서술을 함께 넣었다. **모순이었고,
표본을 키우니 반대 방향으로 3문항이 됐다.**

**교훈은 이것이다 — 1~3문항 차이로 결론을 쓰지 않는다.**
5차에서 판정선(6문항)을 미리 정한 이유가 여기 있다.

#### 그래도 차원 단조성은 여전히 깨져 있다

철회한 것은 "384 > 768" 이고, **"차원이 성능을 보장한다" 는 반박은 유지된다.**
깨지는 지점만 바뀌었다.

```
4차   384(14) > 768(13) < 1024(23)      깨진 곳: 384~768 구간
5차   384(19) < 768(22) > 1024(18)      깨진 곳: 768~1024 구간
```

**두 회차 모두 단조롭지 않다.** 그리고 5차의 이상값 `e5-large` 는 9종 전체
최하위라 4차의 1문항보다 훨씬 뚜렷하다.

#### `e5-large` 이상 현상 — 재현되지만 원인은 모른다

545청크에서도 그랬고 649청크에서도 그렇다. 상세 결과에 단서는 있다.
질의가 달라도 같은 청크 묶음이 반복해서 1위로 올라온다.

```
e5-large / 안겹침 / top5 = 374,300,273,144,186
e5-large / 안겹침 / top5 = 374,300,186,144,408
e5-large / 안겹침 / top5 = 300,374,273,186,144
```

**이것은 관찰이고 원인이 아니다.** 세운 가설 둘을 모두 기각했다.

| 가설 | 결과 |
|---|---|
| 청크가 512토큰을 넘어 조용히 잘렸다 | **기각.** 512토큰 초과 청크가 0개다 (8.8절) |
| 특정 청크가 허브처럼 모든 질의를 흡수한다 | **기각.** 다른 모델에서는 같은 현상이 안 나타난다 |

#### 세 요인이 섞여 있다

| 요인 | 효과 크기 | 근거 | 숫자 |
|---|---|---|---|
| **모델과 학습** | **가장 크다** | 같은 1024 안에서 갈린다 | 18 · 35 · 37 · 37 · 41 (**23문항**) |
| 차원 자체 | 있으나 단조롭지 않다 | 상위 4위가 1024지만 최하위도 1024다 | 768 은 27·22, 384 는 19 |
| 한국어 튜닝 | **모델에 따라 다르다** | `BGE-m3-ko` 는 원본 +6, `KURE-v1` 은 구별 불가 | 41 · 37 대 35 |

**차원은 상한만 정하고 실제 성능은 모델과 학습이 정한다.**

> 흔히 보는 "차원 표"(384 경량 · 768 표준 · 1024 고성능 · 3072 최대)는
> **같은 계열 안에서도 성립하지 않았다.**

#### 그래서 컬럼 차원을 1024 로 두는 근거가 둘이다

| 차원 | 실측 최고 | 지원 모델 |
|---|---|---|
| 384 | 19 / 64 | 로컬 소형 |
| 768 | **27 / 64** (`nomic`) | Gemini · `e5-base` · `nomic` |
| **1024** | **41 / 64** | **로컬 한국어 5종 · Voyage · OpenAI large · Gemini(임의)** |

**8월 12일 판은 "768 은 성능이 384 보다도 낮으니 볼 이유가 없다" 고 적었다.**
그 근거는 철회한다. **대신 다른 근거가 남는다** — 768 최고값(27)이 1024
상위권(41·37·37·35)에 크게 못 미치고, **Voyage 계열에 768 이 아예 없다.**

#### 768 을 재봐야 하는 이유 — Gemini 권장 차원이 768 이다

| 컬럼 차원 | 쓸 수 있는 것 | 잃는 것 |
|---|---|---|

| 1536 | Gemini(권장) · OpenAI small · OpenAI large(임의) | 로컬 전부 · Voyage |
| 3072 | Gemini(권장) · OpenAI large | 로컬 전부 · Voyage · 저장 3배 |

**정정 1번은 1024 의 근거를 약화시키지 않고 오히려 강화한다.**
전에는 "넷 중 셋을 살린다" 였는데 이제 **"넷 다 된다"** 다.
그리고 768 은 여전히 나쁘다 — **Voyage 계열에 768 이 아예 없기 때문이다.**

**앞서 "768 이 더 유연할 수 있다" 고 적었던 판단을 뒤집는다.**
Gemini 만 보고 판단하고 Voyage · OpenAI 의 지원 차원을 확인하지 않은 탓이었다.
**`vector(1024)` 를 유지한다.**

그럼에도 768 을 재는 일은 여전히 필요하다. 이유가 바뀌었다.

| | 전에 생각한 이유 | 실제 이유 |
|---|---|---|
| 왜 재나 | 컬럼 차원을 768 로 바꿀지 판단 | **차원과 모델 크기를 분리** (위 "주의" 항) |
| 결과가 바꾸는 것 | 컬럼 타입 | **"차원이 원인" 이라는 주장의 근거** |

측정 설계는 11.3절에 있다.

#### API 모델을 쓸 때 반드시 짚어야 할 것

**임베딩은 요약과 다르다. 문서의 100% 가 외부로 나간다.**

| | 요약 · 분류 (LLM) | 임베딩 |
|---|---|---|
| 외부로 보내는 것 | 필요할 때 그 문서만 | **모든 문서의 모든 조각** |
| 왜 | 사용자가 요청할 때 1회 | 검색하려면 전부 색인해야 한다 |

우리 도메인은 공공 SI 용역이고 고객 산출내역서 · 계약서를 다룬다.
나라장터 공고는 공개 정보지만 **고객 문서 전량을 외부 API 로 보내는 것은
계약상 문제가 될 수 있다.** 비기능 요구에 "타 프로젝트 데이터 접근 차단" 이
있는 것과 같은 성격의 관심사다.

**비용은 문제가 아니다.** 문서 20건 × 45,000자면 100만~135만 토큰이다.

| 제공자 | 문서 20건 | 문서 1,000건 |
|---|---|---|
| **Voyage `voyage-4` 계열** | **무료** — 계정당 첫 2억 토큰이 무료다 | **무료** (약 1,000만 토큰) |
| OpenAI `3-large` | 약 0.15달러 | 약 1.30달러 |
| Gemini | 약 0.2달러 | 약 2달러 |

**Voyage 무료 구간은 문서 약 2만 건까지 덮는다.** 우리 규모는 그 안이다.

**판단해야 할 것은 비용이 아니라 데이터가 나가도 되는지다.**
그리고 로컬에도 비용이 있다 — `torch` 와 모델 파일이 들어오는 배포 무게다
(13.8절). 이 결과서가 정할 사항이 아니므로 13절 안건으로 올린다.

### 8.2 기본 모델은 `BGE-m3-ko` — 확정

**8월 12일 판은 기본 모델을 `KURE-v1` 로 두고 "확정 보류" 라고 적었다.**
보류 근거는 "`no_overlap` 34문항에서 `bge-m3` 와 1문항 차이라 노이즈 범위" 였고,
해법으로 "평가셋을 키운 뒤에 다시 볼 일" 이라고 적었다. **그대로 했다.**

| | 8월 12일 판 | **5차** |
|---|---|---|
| 안겹침 질의 | 34 | **64** |
| 후보 | 5종 | **9종** |
| 기본 모델 | `KURE-v1` (보류) | **`BGE-m3-ko` (확정)** |

#### 5차 실측 — `BGE-m3-ko` 가 8개 지표 전부에서 1위다

| `no_overlap` 지표 | **BGE-m3-ko** | KURE-v1 | arctic | bge-m3 | 1위 격차 |
|---|---|---|---|---|---|
| R@1 | **25** | 22 | 21 | 20 | 3 |
| R@3 | **37** | 32 | 31 | 29 | 5 |
| **R@5** | **41** | 37 | 37 | 35 | **4** |
| R@10 | **48** | 47 | 43 | 44 | 1 |
| MRR | **0.503** | 0.457 | 0.438 | 0.415 | 0.046 |

`overlap` 과 전체에서도 1위다.

| 지표 | **BGE-m3-ko** | 2위 |
|---|---|---|
| `overlap` R@1 | **50** | arctic 48 |
| `overlap` MRR | **0.795** | arctic 0.772 |
| 전체 R@5 | **102** | arctic 97 |
| 전체 MRR | **0.655** | arctic 0.612 |

**8월 12일 판에서는 `KURE` 가 `overlap` R@1 에서 `bge-m3` 에 뒤졌다.**
지금은 1위 모델이 모든 칸에서 1위다. **지표 역전이 없다는 것이 이번 판정의
근거다.**

#### 근거의 한계를 먼저 적는다

**미리 정해둔 판정선을 넘지 못했다.** 안겹침 64문항에서 6문항 이상이면
실제 차이, 3문항 이하면 판별 불가로 정해두었다.

**`BGE-m3-ko` 는 `KURE-v1` 을 4문항 앞섰다. "참고" 구간이다.**

| 대비 | 엇갈림 | 양측 p | 판정 |
|---|---|---|---|
| 안겹침 64 | 6 (5 대 1) | **0.22** | 유의하지 않다 |
| 전체 133 | 9 (8 대 1) | **0.039** | **유의하다** |

**안겹침 64문항 중 6개만 엇갈렸고 58개는 `KURE-v1` 과 똑같이 움직였다.**
그런데도 1위로 적는 근거는 **8개 지표 전부에서 1위이고 전체 질의로는 유의하기
때문**이다. 한 지표만 튄 것이 아니라 한쪽으로만 쏠려 있다(8 대 1).

#### "한국어 특화가 효과 있다" 는 서술을 철회한다

8월 12일 판은 이렇게 적었다.

> KURE 가 다국어 원본을 4문항 앞섰다. **한국어 특화가 효과 있다는 것이
> 실측으로 확인됐다.**

**5차에서 성립하지 않았다.** 차원을 1024 로 고정하고 계열만 바꿔 다시 봤다.

| 모델 | 성격 | 안겹침 R@5 |
|---|---|---|
| **`BGE-m3-ko`** | bge-m3 **한국어 튜닝** | **41** |
| `KURE-v1` | bge-m3 **한국어 특화** | 37 |
| **`arctic-l-v2.0`** | **다국어** 최신 | **37** |
| `bge-m3` | **다국어** 원본 | 35 |
| `e5-large` | 다국어 원본 | 18 |

세 가지가 그 서술을 무너뜨린다.

| | 관찰 |
|---|---|
| 1 | **같은 원본에서 갈라진 한국어 튜닝 둘이 41 과 37 로 다르다** |
| 2 | **다국어 `arctic`(37)이 한국어 특화 `KURE-v1`(37)과 동점이다** |
| 3 | **`KURE-v1`(37)과 다국어 원본 `bge-m3`(35)는 구별되지 않는다**(p=0.77) |

| 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|
| `BGE-m3-ko` 의 한국어 튜닝은 원본을 **6문항** 앞섰다 | "한국어 특화 모델이면 다국어보다 낫다" |
| 튜닝이 효과를 낸 사례가 **있다** | 그 효과가 **한국어 특화라는 범주에서 온다** |

**결론 — 범주로 고르지 말고 개별 모델을 재야 한다.**
이름에 `ko` 가 붙었다고 나은 것이 아니고(384 한국어판이 8위다),
다국어라고 못한 것도 아니다(`arctic` 이 2위다).

**4차에서 이 서술을 쓴 것은 표본 하나(`e5-large`)에 기댄 판단이었다.**
`e5-large` 는 5차에서 9종 중 최하위로 드러났다. **가장 약한 모델 하나를 이겼다고
범주 전체의 우위를 주장한 셈이다.**

#### 대안 둘은 형식이 아니라 실제 대안이다

| 모델 | 안겹침 R@5 | 1위와의 관계 | 라이선스 | Ollama |
|---|---|---|---|---|
| `nlpai-lab/KURE-v1` | 37 | **통계적으로 구별 안 됨** | mit | 비공식 저장소 |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | 37 | **통계적으로 구별 안 됨** | apache-2.0 | **공식** |

**차원이 같아 DB 를 안 건드리고 바꿔 끼울 수 있다.**
교체 절차는 `관리/API_계약_RAG_검색_초안.md` 7-1절에 규정했다.

**`arctic` 이 특히 값을 한다.** 채택 모델은 Ollama 공식이 아니라 GGUF 등록이
필요한데(13.8절), `arctic` 은 `ollama pull` 한 줄로 끝난다.
**배포 경로가 문제가 되면 성능을 거의 잃지 않고 바꿀 수 있다.**

#### 지표를 하나만 보면 안 된다 — 4차의 관찰은 유지된다

4차에서 `e5-large` 가 `R@1` 1위이면서 `R@5` 최하위였다.
**5차에서도 같은 성질이 다른 모델에서 나타난다.**

```
overlap R@5   e5-small-ko-v2 (384)  64 / 69   1위
안겹침 R@5     e5-small-ko-v2 (384)  19 / 64   8위
```

우리는 `top-k` 를 5 이상으로 쓰기로 했으므로(8.9절) **안겹침 `R@5` 기준이 맞다.**
만약 1건만 보여주는 화면을 만든다면 판단이 달라질 수 있다.

### 8.3 e5-small 탈락 — 이유가 결론보다 중요하다

```
overlap    64 / 69   9종 중 1위
no_overlap 19 / 64   9종 중 8위
```

**작은 모델은 글자가 겹칠 때만 잘한다.** 그건 기존 `ILIKE` 검색이 이미 하는 일이다.
의미로 건너뛰는 능력이 약하다.

**만약 `overlap`만 재고 모델을 골랐다면 e5-small을 뽑았을 것이다.**
그리고 뜻으로 묻는 질의의 70%를 놓쳤을 것이다.
`overlap` 점수가 높은 것은 임베딩을 쓸 근거가 되지 않는다.

**같은 모델이 1위와 8위를 동시에 한다.** 이 한 줄이 이 시험의 핵심 발견이고,
`RAG-05` 하이브리드 검색의 근거다(8.6절).

#### 8월 12일 판의 재순위 논거를 철회한다

그때는 이렇게 적었다.

> `R@5` 에서 `R@10` 으로 가면서 **10문항이 더 잡힌다.** 즉 e5 는 정답을 찾기는
> 하는데 상위로 못 올린다. **재순위를 붙이면 384차원도 쓸 수 있다는 뜻이다.**
> (같은 구간에서 KURE는 27 → 29, bge는 26 → 28로 **2문항만** 늘어난다.)

**5차에서 그 대비가 사라졌다.**

| 모델 | 안겹침 R@5 | R@10 | 증가 |
|---|---|---|---|
| BGE-m3-ko | 41 | 48 | +7 |
| KURE-v1 | 37 | 47 | **+10** |
| bge-m3 | 35 | 44 | +9 |
| **e5-small-ko-v2** | 19 | 28 | **+9** |

**모두 7~10문항씩 늘어난다.** `e5-small` 의 도약이 특별한 것이 아니었다.
4차에서 `KURE` 가 2문항만 늘어난 것은 **34문항 표본에서 이미 27개를 잡아 천장에
가까웠기 때문**이다. 표본을 키우니 천장이 사라졌다.

**그리고 절대 격차가 재순위로 메울 수 있는 크기가 아니다.**
`e5-small` 의 R@10 은 **28** 이고 채택 모델의 R@5 는 **41** 이다.
**재순위는 이미 top-10 안에 든 것을 다시 세우는 것이므로 28 이 상한이다.**
41 을 넘을 수 없다.

**재순위 검토는 후속 과제로 남기되, "384 를 쓸 수 있다" 는 근거로는 쓰지 않는다.**
쓸 수 있는 근거는 CPU 속도(9~11배)와 메모리(430MB 대 2,203MB)뿐이고,
그것으로 22문항 차이를 상계할 수는 없다.

**`RAG-12`(유사 사업 단가 선례 검색)에 계약명 기준 필터가 필요하다는 근거다.**

### 8.5 `RAG-04` 후반 조건 — 이번 조건에서는 측정하지 않았다

`RAG-04` 완료 판정은 두 부분이다.

| 조건 | 상태 |
|---|---|
| 글자가 하나도 겹치지 않는 질의로 관련 문서가 나온다 | **충족** (27 / 34) |
| 다른 프로젝트 문서는 나오지 않는다 | **측정하지 않았다** |

**후반 조건은 벡터 유사도가 담당하지 않는다.** `documents.project_id` 가
NOT NULL 이고 **리포지토리 계층에서 스코프를 강제**하는 것이 설계다
(`PRJ-08` · `관리/데이터구조_설계.md` 2절). 라우터에서만 검사하면 새 API 를
추가할 때 누락되므로 리포지토리에 둔 것이다.

이번 실험은 문서 5건을 한 코퍼스에 넣고 **필터 없이** 검색했다.
프로젝트 경계가 없는 조건이므로 이 항목은 애초에 재현되지 않았다.
**"미충족" 이 아니라 "측정 불가" 다.**

다만 실험에서 관찰한 것은 별개로 유효하다. **같은 프로젝트 안에 문서가 여럿
있으면 문서 간 혼동이 생기고, 그것은 `project_id` 필터로 막히지 않는다.**

```
"이 일에 잡힌 예산이 얼마인가"   기초과학연구원 공고를 물었는데
                                한국지역난방공사 준공정보를 가져왔다 (107,108,123…)

"두 문서가 어긋나면 어느 쪽이 이기나"   공고문을 물었는데
                                       우리 팀 결정사항을 가져왔다 (45,41,59…)
```

**문서 격리는 벡터 유사도로 되지 않는다.** 문서 ID 또는 사업 단위 필터가
검색 조건에 들어가야 한다. `RAG-05`(하이브리드 검색, P2)와 함께 설계할 일이다.

### 8.6 숫자·코드번호 검색은 벡터가 약하다 — `RAG-05` 실측 근거

3차 상세에서 `overlap` 실패 사례가 드러났다. **글자가 그대로 겹치는데도
1024 두 모델이 10위 안에 못 넣은 질의들이다.**

| 질의 | 정답 | **BGE-m3-ko** | KURE-v1 | bge-m3 | e5-small |
|---|---|---|---|---|---|
| `사업금액 578600000원` | 7 | **실패** | **실패** | **실패** | 9위 |
| `공동수급불허 협상에의한계약` | 1 | **실패** | **실패** | **실패** | 4위 |
| `입찰공고번호 100354-24002` | 62 | **1위** | 3위 | 2위 | 4위 |
| `RHEL 라이선스 갱신 구매` | 96 | 2위 | 2위 | 2위 | 2위 |

`사업금액 578600000원` 에 대한 `BGE-m3-ko` 의 상위 결과가
`520,527,530,498,516` 이다. **전부 다른 문서의 금액 청크다.**
숫자를 물었는데 다른 숫자로 끌려간다.

**청크를 5배로 늘리자 더 나빠졌다.** 8월 12일 판(127청크)에서는 384 모델이
`사업금액` 을 4위로 잡았는데 지금은 9위이고, 1024 모델 셋은 여전히 못 잡는다.
**방해할 숫자가 늘어난 만큼 정확히 나빠진다.**

기능명세서 `RAG-05` 완료 판정이 이것을 예상하고 있었다.

| ID | 우선 | 완료 판정 기준 | 비고 |
|---|---|---|---|
| `RAG-05` | P2 | **고유명사 · 코드번호 검색에서 벡터 단독보다 정확하다** | **`VIS-06` FTS 와 결합** |

**이번 측정이 그 근거를 실측으로 채웠다.** 공고번호·계약번호·금액이 많은
도메인이라 `RAG-05` 를 P2 로 둔 판단이 맞다. 벡터 단독으로는 코드번호를
1위로 못 올린다.

**키워드 쪽은 새로 만들지 않는다.** 비고가 `VIS-06` FTS 와 결합하라고 지정한다.
`VIS-06`(통합 검색 · PostgreSQL FTS · P2 · 보현)이 이미 계획에 있으므로
별도 검색 엔진을 도입하지 않고 같은 DB 안에서 합친다.

| 구성 요소 | 무엇으로 | 근거 |
|---|---|---|
| 벡터 쪽 | pgvector + KURE-v1 (1024) | 이 문서 8.1 · 8.2절 |
| 키워드 쪽 | **PostgreSQL FTS** (`VIS-06`) | `RAG-05` 비고 |
| 스코프 | `project_id` 리포지토리 강제 | `PRJ-08` · 8.5절 |

그리고 **e5-small 이 이 구간에서 가장 강하다.** `overlap R@10 = 39 / 39` 다.
작은 모델이 어휘 매칭에 강하다는 뜻이며, 이는 8.3절의 `no_overlap` 최하위와
같은 성질의 다른 얼굴이다. **하이브리드 검색을 만들 때 키워드 쪽 후보로
e5 를 쓰는 구성도 검토할 값이 있다.**

### 8.7 큰 청크는 `overlap` 질의로도 못 찾는다 — `RAG-01` 근거

실패한 `overlap` 질의의 정답 청크 크기를 보면 원인이 보인다.

| 정답 청크 | 글자 | 무엇이 들어 있나 |
|---|---|---|
| 1 | 438 | 나라장터 화면 덤프. **필드 20여 개가 한 덩어리** |
| 4 | 533 | 입찰진행 주의 · 보증금 · 발표순서 · 평가기관 · 평가비율 · 가격 |
| 7 | 448 | 입찰 주의 · 공고명 · 사업내용 · 사업기간 · 계약방법 · 사업금액 |

**청크 1 을 정답으로 둔 `overlap` 질의 두 개가 모두 실패했다.**
`공동수급불허 협상에의한계약` 과 `회계법인 업종을 등록한 업체` 다.
글자가 그대로 있는데도 못 찾는다. 필드 20여 개를 벡터 하나가 대표하니
특정 필드의 신호가 묻힌다.

**`RAG-01` 이 `element_type` 단위로 단락을 묶는 이유가 여기서 확인된다.**
화면 덤프를 글자 수로 자르면 이런 덩어리가 생긴다.
`ocr_elements` 의 구조 정보를 쓰면 필드 단위로 끊을 수 있다.

### 8.8 긴 표는 조용히 잘릴 수 있다 — 아직 안 터진 위험

**이번 코퍼스에서는 발생하지 않았지만 본구현에서는 발생한다.**

조각 자르기 도구(`make_chunks.py`)에 규칙이 하나 있다.

```python
--max 1200   이 길이를 넘는 덩어리는 쪼개지 않고 그대로 둔다

if block_len >= hard_max:
    flush()
    chunks.append(block)      # 상한을 지키지 않고 통째로 넣는다
```

**표를 중간에서 자르면 항목과 금액이 분리되어 뜻이 사라지기 때문에 넣은 규칙이다.**
의도는 맞다. 그런데 부작용이 있다.

| 단계 | 무슨 일이 일어나나 |
|---|---|
| 1 | 산출내역서처럼 표가 긴 문서가 들어온다 |
| 2 | 표 하나가 2,000자, 5,000자짜리 조각이 된다 |
| 3 | 임베딩 모델에 그대로 들어간다 |
| 4 | **모델의 최대 입력 길이를 넘으면 뒷부분이 잘린다** |
| 5 | **경고가 없다.** 앞부분만으로 만든 벡터가 저장된다 |
| 6 | 표 뒷부분의 항목은 **검색으로 절대 찾을 수 없다** |

이번에는 최장 조각이 567자여서 안 터졌다. 상한 1200에 닿은 조각이 하나도 없었다.
**표가 짧은 코퍼스였을 뿐이다.**

#### 방지 방법 — 네 가지를 겹쳐 쓴다

| | 방법 | 효과 | 비용 |
|---|---|---|---|
| **1** | **표를 행 단위로 자르고 머리행을 각 조각에 복제한다** | **근본 해결.** 뜻이 보존되면서 길이도 제어된다 | 구현 필요 |
| **2** | 조각을 만든 뒤 **토크나이저로 토큰 수를 실측**하고 한계 초과분을 다시 자른다 | 잘림을 사전에 차단 | 토크나이저 호출 |
| 3 | `document_chunks` 에 `token_count` 를 저장하고 **한계 초과면 색인을 실패시킨다** | 조용히 넘어가지 않는다 | 컬럼 하나 |
| 4 | 모델의 `max_seq_length` 를 설정에서 읽어 상한을 **계산**한다 | 모델 교체 시 자동 대응 | 적재 시 1회 |

**1번이 핵심이다.** 그리고 이미 같은 발상이 코드에 있다.
원본 변환기(`convert_inputs.py`)의 CSV 처리가 행마다 `"열이름: 값"` 블록으로
푸는 방식이 그것이다.

```
## 1~1행
사업명: ○○기관 정보화 통합유지관리
계약방법: 제한경쟁
낙찰금액: 123,000,000
```

**표를 "자르지 않는다" 가 아니라 "행 단위로 자르고 머리행을 복제한다" 가 맞다.**
그러면 항목과 금액이 붙어 있으면서 조각 길이도 짧아진다.
유사 사업 단가 선례 검색(`RAG-12`)이 행 단위 검색이므로 목적에도 맞다.

문서를 조각으로 자르기(`RAG-01`) 완료 판정이 **"표는 행 단위로 유지된다"** 인데,
이것을 **"표는 행 단위로 자른다"** 로 읽는 것이 안전하다.
`ocr_elements` 에 표 구조 정보가 들어오면 행 경계를 알 수 있다.

**2번도 필요하다.** 1번을 해도 한 행이 매우 긴 표가 있을 수 있다.
`token_count` 를 세는 것은 어차피 토큰 수 기준으로 자르려면 해야 하는 일이다.

#### 5차에서 실측했다 — **잘림은 없었다**

8월 12일 판은 세 가지를 "확인하지 못한 것" 으로 남겼다. **셋 다 쟀다.**

**① 모델의 최대 입력 길이**

| 모델 | `max_seq_length` |
|---|---|
| `BGE-m3-ko` · `KURE-v1` · `bge-m3` · `arctic-l-v2.0` | **8192** |
| `e5` 3종 · `nomic-v2-moe` | **512** |
| `Qwen3-Embedding-0.6B` | **32768** |

**"512 로 내려가는 경우가 있다" 는 우려가 실제였다.** 네 모델이 512다.
`e5-large` 는 1024차원인데 입력 상한이 512다 — **차원과 입력 길이는 다른 값이다.**

**② 우리 청크의 실제 토큰 수**

| 항목 | 값 |
|---|---|
| 전체 청크 | 649개 |
| 가장 긴 청크 | 697자 |
| **512토큰 초과 청크** (XLM-R 계열) | **0개** |
| 정답 청크 | 62개 · **최대 306토큰** (상한 512의 60%) |
| 참고: Qwen3 토크나이저 최대 | 620토큰 |

**③ 잘림이 실제로 있었나 — 없었다**

**상한이 512인 네 모델도 이번 측정에서 잘림이 발생하지 않았다.**
`--max 700` 으로 청킹 상한을 낮춘 것이 결과적으로 안전선 안에 들어왔다.

**토크나이저가 다르면 토큰 수가 다르다.** 같은 청크가 XLM-R 로는 512 이하인데
`Qwen3` 로는 620토큰까지 나온다. **"몇 토큰인가" 는 모델마다 다른 값이므로
모델별로 세야 한다.**

#### 한 번 잘못 짚었다

**`e5-large` 점수가 크게 떨어진 것을 토큰 잘림으로 단정했는데 틀렸다.**
잘린 청크가 애초에 없었다. 원인은 아직 모른다(8.1절).

**글자 수로 토큰 수를 추정하면 안 된다.** "정답 청크 최대 533자면 512토큰 안에
들어갈 가능성이 높다" 고 적었는데, 그건 추정이었다. 실제로 재니 306토큰이었다.
맞는 방향이었지만 **근거가 추정이었으므로 결론으로 쓸 수 없었다.**

확인 명령은 이것이다.

```python
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("dragonkue/BGE-m3-ko")
print(m.max_seq_length)                              # 상한
print(len(m.tokenizer(가장_긴_청크)["input_ids"]))     # 실제 토큰 수
```

### 8.9 `top-k`는 5 이상이어야 한다

`no_overlap` `R@1` 이 최고 **25 / 64 (39%)** 다. **1위로 맞추는 것은 세 번에 한 번**
을 조금 넘는다. `R@5` 에서 **41개 (64%)** 로 오른다.

| 채택 모델 (`BGE-m3-ko`) 안겹침 | 값 | 비율 |
|---|---|---|
| R@1 | 25 / 64 | 39% |
| R@3 | 37 / 64 | 58% |
| **R@5** | **41 / 64** | **64%** |
| R@10 | 48 / 64 | 75% |

**본구현에서 `top-1` 만 쓰면 의미 검색의 40%를 버린다.**
`R@3` 에서 이미 58% 이므로 화면에 3~5개를 보여주는 설계가 맞다.

### 9.1 `PER-01` 60초 — Worker 는 아직 코드에 없다

`Tasqra/DEVELOPMENT_GUIDE.md` 4.2절이 요청 내부 동기 처리를 폐기하기로 했다.

```
업로드 요청 -> 문서·작업 생성 -> 큐 등록 -> 즉시 응답
                                        └-> Worker 처리
```

> 오래 걸리는 OCR, 문서 추출, LLM 분석, 일괄 처리는 Worker 에서 실행한다.

**그런데 이것은 지향점이고 코드에는 없다.** Tasqra `backend/` 를 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| 코드에서 `celery` · `redis` · `BackgroundTasks` 검색 | **0건** |
| `requirements.txt` | celery · redis **없음** |
| `docker-compose.yml` 서비스 | `db` · `api` · `frontend` **3개뿐** (redis · worker 없음) |
| `upload_router.py` | 파일을 읽고 **곧바로** `service.upload_and_extract(...)` 호출 후 응답 |
| 작업 상태 · 진행률 테이블 | `tasks` · `jobs` **없음** (0001~0007 전체 확인) |
| `DEVELOPMENT_GUIDE` 체크리스트 | `[ ] Celery·Redis Worker 구성` — **미완료 표시** |

`SYS-02`(Celery + Redis)가 **P0 인데 미착수**다. 담당은 재정이다.

**그래서 지금 임베딩을 Worker 로 돌릴 수 없다.** 두 갈래가 된다.

| 선택 | 내용 | 문제 |
|---|---|---|
| A | `SYS-02` 완료를 기다린다 | 재정 담당 P0 에 블로킹된다 |
| B | **기존 관례대로 동기로 만든다** | 업로드·분석이 이미 동기라 일관된다. 대신 응답이 늘어진다 |

**B 가 현재 코드와 일관된다.** 업로드와 분석이 모두 동기이므로 임베딩만
비동기로 만들면 구조가 어긋난다. `SYS-02` 가 들어오면 셋을 함께 옮기면 된다.

`PER-01` 의 60초는 **현재 코드 기준으로는 응답 지연 그 자체다.**
Worker 가 생긴 뒤에야 처리 완료 시간이 된다.

그럼에도 예산은 여전히 빡빡하다. CPU 에서 임베딩만 33초면 OCR 과 LLM 분석이
쓸 시간이 27초 남는다. 스캔 PDF 10페이지 OCR 이 그 안에 끝나지 않는다.
**GPU 실행이 사실상 전제다.**

| 항목 | 값 |
|---|---|
| 임베딩 (`BGE-m3-ko` · CPU · 약 61청크) | **35초** |
| 남는 예산 | **25초** |
| 미니 프로젝트 실측 OCR (PaddleOCR) | **15,541ms = 15.5초** (문서 1건 기준) |
| 미니 프로젝트 실측 요약 · 분류 | 3.2초 + 1.6초 |

미니 프로젝트 수치는 문서 1건 기준이고 10페이지 스캔 PDF 는 더 든다.
**임베딩을 GPU 로 옮기거나 Worker 병렬화가 필요하다.**

또한 **작업 멱등성**을 고려해야 한다(같은 4.2절). `RAG-09` 검수 확정 시
재임베딩이 두 번 돌아도 청크가 중복 저장되지 않아야 한다.

### 11.0 리비전 `0011` 보다 먼저 해야 할 것 — pgvector 가 설치되어 있지 않다

**DB 이미지에 pgvector 가 없다.** `CREATE EXTENSION vector` 를 넣어도 실패한다.

| 확인한 것 | 결과 |
|---|---|
| `docker-compose.yml` DB 이미지 | **`postgres:16-alpine`** — pgvector 미포함 |
| 마이그레이션에 `CREATE EXTENSION vector` | **없다** (`0001`~`0009` 전체 확인) |
| `requirements.txt` 에 `pgvector` 패키지 | **없다** |

세 가지가 선행되어야 `0011` 이 돌아간다.

| | 할 일 | 주의 |
|---|---|---|
| 1 | DB 이미지를 **`pgvector/pgvector:pg16`** 등으로 교체 | **`docker-compose.yml` 은 팀 공유 파일이다. 혼자 바꾸지 않는다** |
| 2 | `requirements.txt` 에 `pgvector` 추가 | SQLAlchemy 에서 `Vector` 타입을 쓰려면 필요하다 |
| 3 | `0011` 에서 `op.execute("CREATE EXTENSION IF NOT EXISTS vector")` | 확장 생성이 테이블보다 먼저다 |

**1번이 팀 합의 사항이다.** 작업 규칙에 "`.yml` 처럼 팀 전체가 공유하는 파일은
혼자 바꾸지 않는다" 가 있다. 이미지를 바꾸면 세 사람 모두 컨테이너를 다시
만들어야 하므로 미리 알려야 한다.

**이미지 교체와 리비전 추가가 같이 오면 다른 사람 환경이 두 번 깨진다.**
이미지 교체를 먼저 공지하고, 모두가 컨테이너를 다시 만든 뒤에 리비전을 올린다.

### 11.1 리비전 번호 — `versions/` 폴더로 확인한 값

**`관리/` 문서가 아니라 Tasqra 의 `backend/migrations/versions/` 가 정본이다.**

`origin/main` 의 실제 파일 목록이다. 체인은 선형이고 **head 는 `20260812_0009`** 다.

| 리비전 | 내용 | 상태 |
|---|---|---|
| `0001`~`0007` | `core` ~ `analysis_artifacts` | main 머지됨 |
| `0008` | `ocr_exclusion` (`ocr_elements.is_excluded`) | **재정 · main 머지됨** |
| **`0009`** | **`extracted_char_sources`** (`text_char_count` · `ocr_char_count`) | **재정 · main 머지됨 · head** |
| **`0010`** | `amount_items.unit_price` · `category` · `documents.document_type` CHECK 9종 | **보현 예정** |
| **`0011`** | **pgvector · `document_chunks` `vector(1024)`** | **이 문서로 착수 가능** |

`down_revision` 은 착수 순서에 따라 이렇게 정한다.

| 무엇을 먼저 만드나 | `down_revision` |
|---|---|
| CHECK(`0010`) 를 먼저 만들면 | **`20260812_0009`** |
| 이어서 pgvector(`0011`) 를 만들면 | `20260812_0010` |
| pgvector 를 먼저 만들면 (CHECK 를 뒤로) | **`20260812_0009`** 로 두고 pgvector 가 `0010` 이 된다 |

**`down_revision` 을 `20260811_0007` 이나 `20260812_0008` 로 두면 head 가 둘이
되어 `alembic upgrade head` 가 실패한다.** 컨테이너 기동 명령이 그것이라 앱이
아예 뜨지 않는다. 4회 충돌 때와 같은 실패 방식이다.

#### 재정님 `0009` 가 남긴 것 둘

**첫째, CHECK 제약 명명 선례가 생겼다.** 보현님 `0010` 이 CHECK 9종을 넣을
예정인데, 이미 팀에 쓰인 형태를 따르는 것이 맞다.

```python
op.create_check_constraint("ck_extracted_text_char_count",
                           "extracted_texts", "text_char_count >= 0")
```

**`ck_{테이블단수}_{컬럼}` 형태다.** `0010` 도 `ck_amount_item_unit_price` 처럼
맞춘다. 이름을 안 주면 Postgres 가 자동 생성해서 `downgrade` 에서 지울 수 없다.

**둘째, 청크의 출처를 구분할 근거가 생겼다.**

| 컬럼 | 뜻 |
|---|---|
| `extracted_texts.text_char_count` | 원본에 이미 글자로 박혀 있던 분량 |
| `extracted_texts.ocr_char_count` | OCR 로 읽어낸 분량 |

**검색 결과 스니펫(`RAG-08` 근거 표시)에 "이 근거는 OCR 결과다" 를 붙일 수
있다.** OCR 은 오독 가능성이 있으니 사용자가 원문을 확인할 판단 근거가 된다.
이번 시험 범위는 아니지만 `document_chunks` 설계에 반영할 값이 있다 — 13.7절.

### 11.3 768 차원 측정 — **완료** (결과는 7.5 · 8.1절)

**앞서 "모델을 더 추가하지 마라" 고 적었으나(8.2절) 그것과 다른 일이다.**

| | 8.2절에서 하지 말라고 한 것 | 여기서 하자는 것 |
|---|---|---|
| 무엇 | 같은 1024 차원 모델을 더 넣기 | **비어 있는 차원 점 하나를 찍기** |
| 왜 안 되나 / 되나 | 차이가 1문항이라 잡음만 늘어난다 | **384 와 1024 사이가 비어 있다** |
| 목적 | 모델 순위 | **컬럼 차원 결정** |

#### 두 개를 넣었다 — 하나로는 못 나눈다

`MODELS` 에 이미 추가해뒀다. **`e5` 원본 계열의 `base`(768)와 `large`(1024)** 다.

```python
{ "name": "intfloat/multilingual-e5-base",  "query_prefix": "query: ", … },   # 768
{ "name": "intfloat/multilingual-e5-large", "query_prefix": "query: ", … },   # 1024
```

**왜 `large`(1024)까지 넣나** — `base` 하나만 넣으면 비교 상대가 `KURE-v1` 인데,
그건 계열이 다르다(`bge` 기반 · 한국어 특화). 차원도 다르고 학습도 다르니
차이가 무엇 때문인지 또 모르게 된다.

같은 계열 안에서 두 점을 잡으면 변수가 하나만 남는다.

| 비교 | 무엇이 같나 | 무엇이 다르나 | 알 수 있는 것 |
|---|---|---|---|
| **`e5-base` 대 `e5-large`** | 계열 · 학습 · 접두어 | **차원(768 대 1024)과 크기** | **차원·크기를 키운 순수 효과** |
| **`e5-large` 대 `KURE-v1`** | **차원(둘 다 1024)** | 계열 · 한국어 특화 여부 | **한국어 특화 효과** |
| `e5-small-ko-v2` 대 `e5-base` | e5 계열 | 크기 · 한국어 튜닝 여부 | 참고 |

**두 번째 비교가 8.2절의 KURE 우위를 검증한다.** 지금은 `bge-m3` 와만 비교해
1문항 차이였는데, `e5-large`(같은 1024 · 다른 계열)와 비교하면 한국어 특화가
정말 효과가 있는지 다시 볼 수 있다.

접두어는 `e5` 계열이라 둘 다 `query: ` / `passage: ` 를 넣었다.
빼면 억울하게 진다(5.5절).

#### 실행

```powershell
cd C:\dev\embed-test
python run_eval.py                      # 5개 전부. 비교표가 한 번에 나온다
```

두 모델을 새로 내려받으므로 시간이 든다. 나눠 돌려도 된다.

```powershell

```

**`--only` 는 `MODELS` 에 등록된 것 중에서 이름으로 고르는 옵션이다.**
목록에 없는 이름을 주면 `--only 조건에 맞는 모델이 없다` 로 끝난다.

#### 판단 기준

| `e5-base`(768) 대 `e5-large`(1024) | 뜻 |
|---|---|
| 차이가 3문항 이하 | **차원을 키운 효과가 작다.** 성능은 계열·학습이 정한다 |
| 차이가 5문항 이상 | 차원·크기가 실제로 영향을 준다 |

| `e5-large`(1024) 대 `KURE-v1`(1024) | 뜻 |
|---|---|
| KURE 가 크게 앞선다 | **한국어 특화가 효과 있다.** 8.2절 결론이 강해진다 |
| 비슷하다 | 한국어 특화 효과가 작다. 다국어 원본으로도 충분하다 |
| `e5-large` 가 앞선다 | **KURE 를 기본값으로 둔 판단을 다시 봐야 한다** |

**컬럼 차원은 이 측정과 무관하게 1024 로 확정됐다**(8.1절 지원 차원 표).
이 측정은 **"차원이 원인" 이라는 주장을 검증하는 것**이지 컬럼을 바꾸려는 것이 아니다.

## 12. LLM 모델 비교와의 경계 — 판단은 세현, 재는 자는 보현

**이 문서는 임베딩 모델만 다룬다.** LLM 모델 선정 판단은 별도 문서로 분리한다.
**다만 측정 도구는 이 문서의 담당 영역이다.**

| | 담당 | 상태 |
|---|---|---|
| 임베딩 모델 선정 | 보현 | **이 문서** |
| LLM 모델 선정 판단 | 세현 | 진행 중 (HyperCLOVA X 2종 · 데이터 주입 전) |
| **`ANL-17` 평가셋 기반 정확도 측정 자동화** | **보현** | **이번 하네스가 원형** |

### 12.0 `ANL-17` — 이번 도구가 그 원형이다

기능명세서 8절이 `ANL-16`·`ANL-17` 담당을 보현으로 지정하고 있다.

> `ANL-17` 평가셋 기반 정확도 측정 자동화 — P1
> 정답 데이터와 대조해 정확도가 수치로 나온다.
> **모델·프롬프트를 바꿔도 같은 자로 잰다. 세현님 모델 비교에 직접 쓰인다**

이번에 만든 세 파일이 그 골격이다.

| 이번에 만든 것 | `ANL-17` 에서 하는 일 | 바뀌는 부분 |
|---|---|---|
| `queries.csv` (질의 · 정답 · 종류) | 평가셋 형식 | 정답이 청크 번호 → **기대 출력값** |
| `check_queries.py` | **채점 전 평가셋 검증** | 그대로 쓸 수 있는 발상 |
| `run_eval.py` | 채점과 지표 산출 | 지표가 `R@k` → 정확도 · 일치율 |

**`ANL-17` 이 P1 이고 `RAG-10` 이 P2 다.** 즉 **재는 자를 먼저 만든다.**
같은 자로 재지 않으면 모델을 바꿨을 때 좋아진 것인지 알 수 없다.

특히 `check_queries.py` 의 발상이 그대로 옮겨간다. **`run_eval.py` 가 못 쓰는
행을 조용히 건너뛴 것처럼, 정확도 측정도 잘못된 정답 데이터를 조용히 넘기면
숫자가 오염된다.** 이번에 78문항 중 5문항이 측정 불가였고 3문항이 라벨 위반이었다.
그것을 사람 눈으로는 못 찾았다.

**세현님 시험에 이 도구를 쓰려면 다음이 필요하다.**

| | 필요한 것 | 왜 |
|---|---|---|
| 1 | 정답 데이터 형식 합의 | 요약은 정답이 하나가 아니다. 무엇을 일치로 볼지 정해야 한다 |
| 2 | 분류는 그대로 쓸 수 있다 | 7종 중 하나이므로 정답이 명확하다 (`ANL-02`) |
| 3 | 요약은 지표를 따로 정해야 한다 | 사람 판정이 필요하다. 16절 비기능 요구가 `USER_CORRECTED` 비율을 쓰기로 했다 |

**요약 정확도를 재는 방식이 이미 정해져 있다는 점을 짚어둔다.**
기능명세서 16절이 "별도 정답 데이터를 만드는 대신 **사람이 AI 판별을 고친
비율**을 쓴다" 고 했다. 즉 분류는 `document_type_source=USER_CORRECTED` 비율로
잰다. 요약은 그 방식이 없으므로 세현님과 합의가 필요하다.

### 12.1 왜 분리하는가

선택 기준이 겹치지 않는다. 한 문서에 넣으면 "무엇을 왜 골랐나"가 흐려진다.

| | 임베딩 모델 | LLM |
|---|---|---|
| 핵심 지표 | `R@5` · `MRR` (기계 채점) | 출력 품질 (**사람 판정 필요**) |
| 결정에 묶이는 것 | **DB 컬럼 차원** | 프롬프트 · 토큰 예산 |
| 비용 구조 | 색인 1회 | **호출마다 과금** |
| 되돌리기 비용 | 재임베딩 반나절 | 설정 한 줄 |
| 평가셋 성격 | 질의와 정답 청크 | 입력 문서와 기대 출력 |

### 12.2 임베딩을 먼저 확정하는 것이 LLM 시험의 전제다

RAG 파이프라인에서 검색과 생성은 다른 단계다.

```
질의 -> [임베딩 검색] -> 청크 k개 -> [LLM 생성] -> 답변
         이 문서가 정한 것            세현 담당
```

**임베딩을 하나로 고정해두면 LLM 시험에서 들어가는 청크가 같아지므로
LLM 차이만 깨끗하게 측정된다.** 변수 통제다.

반대로 임베딩과 LLM을 같이 바꾸면 출력이 나빠졌을 때 검색이 잘못 가져온
것인지 생성이 잘못한 것인지 가릴 수 없다. **그래서 순서가 임베딩 먼저다.**

**그리고 임베딩은 검색 전용이 아니다.** 기능명세서 14절 도입부에 이렇게 적혀 있다.

> 임베딩은 금액 전용이 아니다. 요약·분류·검색이 같은 파이프라인을 쓴다.
> 특히 45,000자 문서를 요약할 때 무엇을 프롬프트에 넣을지 고르는 데 쓰인다.

`RAG-07`(프롬프트 컨텍스트 조립)이 토큰 예산 안에서 청크를 고르는데,
그 고르는 근거가 임베딩이다. **즉 임베딩 품질이 요약 품질의 상한을 정한다.**
LLM 이 아무리 좋아도 엉뚱한 청크가 들어가면 요약이 틀린다.

두 시험은 독립적으로 진행하되 **종속 관계는 한 방향이다.**

```
임베딩 품질  ->  RAG-07 이 고른 청크  ->  LLM 요약 품질
```

### 12.3 LLM 결과서에 담겨야 할 것

| | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | 모델명 · 버전 · **학습 여부와 학습 데이터** | 학습시킨 모델은 데이터가 변수다. 명시해야 재현된다 |
| 2 | 어느 작업에 썼나 (요약 · 분류 · 금액 추출) | 작업마다 기준이 다르다 |
| 3 | 평가 방법 (사람 판정 · 정답셋 · 지표) | 근거의 강도를 정한다 |
| 4 | 수치 (정확도 · 응답시간 · 토큰 · 비용) | 비교 표를 만든다 |
| 5 | 실패 사례 | 한계를 적는다 |
| 6 | 실행 환경 (**GPU 사양**) | `PER-01` 판단에 필요 (9절) |
| 7 | 선정 · 탈락 결론과 이유 | 결정 기록 |

**1번을 특히 주의한다.** 같은 모델을 서로 다른 데이터로 학습시켜 비교하면
모델 차이가 아니라 학습 데이터 차이를 재는 것이 된다. 두 조건 중 하나만
바꿔야 인과가 성립한다.

**6번은 이 문서 9절과 직결된다.** GPU 사양을 알면 `PER-01` 10페이지 60초가
가능한지 계산할 수 있다. 현재 CPU 기준으로는 임베딩만 33초다.

## 13. 팀 확인 필요 사항

GPU가 없다는 것은 임베딩만의 문제가 아니다.

| | 확인할 것 | 왜 |
|---|---|---|
| 1 | 세현 장비 GPU 사양 | 없으면 LLM도 CPU. `PER-01` 60초가 위험하다 |
| 2 | 모델을 각자 PC에서 돌리나, 공용 장비인가 | 각자면 영상 촬영을 누구 PC로 하나 |
| 3 | **임베딩을 어디서 돌리나** | 시험자 PC에 GPU가 없다. 최종 색인 장비를 정해야 한다 |
| 4 | `PER-01` 60초가 임베딩까지 포함하는가 | 9절 판단이 달라진다 |
| 5 | **HyperCLOVA X "학습" 이 파인튜닝인가** | 기능명세서 17절과 충돌 가능 (아래) |
| 6 | HyperCLOVA X 를 상용 API 로 쓰나 로컬로 띄우나 | 18절 25번 결정과 관계 |

**3번이 8.1절 결정의 전제다.** 공용 GPU 장비가 있으면 1024차원 운용에
문제가 없다. 없으면 색인 시간을 일정에 반영해야 한다.

### 13.1 파인튜닝 — 기능명세서와 어긋날 수 있다

기능명세서 **17절 "하지 않을 것"** 에 이렇게 적혀 있다.

| 안 함 | 이유 |
|---|---|
| **파인튜닝** | 20일에 자리가 없다. 프롬프트 + 구조화 출력으로 목표 달성 가능 |

그런데 LLM 시험이 "HyperCLOVA X 두 종을 학습시켜서 비교" 로 진행되고 있다.
**그 "학습" 이 파인튜닝이면 17절 결정과 충돌한다.**

| 무엇인가 | 17절과의 관계 |
|---|---|
| 파인튜닝 (가중치 갱신) | **충돌.** 17절을 고치거나 시험 범위를 조정해야 한다 |
| 프롬프트 · 예시 주입 (few-shot) | 충돌 없음. 17절이 권하는 방식이다 |
| RAG 로 문서를 넣어주는 것 | 충돌 없음. 그게 `RAG-07` 이다 |

**어느 쪽인지 확인해야 한다.** 파인튜닝이라면 일정(구현 20일)과 재현성 양쪽에
영향이 있다. 또한 기능명세서 18절 25번이 **"상용 API 유지 권장"** 으로
정리되어 있는데(1조가 Gemma 1B 에서 언어 쏠림을 겪은 사례), 로컬 학습 모델을
쓰는 방향이면 그 결정도 다시 봐야 한다.

**이 결과서가 판단할 사항은 아니다. 팀 안건으로 올린다.**

### 13.2 이 결과서 판단의 상한 — v0.3 기획안을 보지 못했다

`Tasqra/DEVELOPMENT_GUIDE.md` 1절이 기준의 우선순위를 정하고 있다.

```
DocFlow 통합 기획안 v0.3
  -> 개발 가이드
  -> API·DB 계약
  -> 구현 코드와 주석

규칙이 서로 충돌하면 위에 있는 기준을 따른다.
```

**최상위 기준인 v0.3 기획안 파일이 두 레포 어디에도 없다.**
`관리/` 문서 다섯 개가 v0.3 을 인용하고 있을 뿐이다.
따라서 이 결과서는 **2순위 이하 문서만 근거로 삼았다.** v0.3 에 다른 지시가
있으면 그쪽이 이긴다.

### 13.3 확인 필요 — 검색의 구현 계층

`DEVELOPMENT_GUIDE.md` 2절이 기능을 4계층으로 나누고 있다.

| 계층 | 내용 |
|---|---|
| 1 | 공통 기반 — 인증 · 프로젝트 스코프 · 비동기 큐 · OCR 요소 저장 |
| 2A | 액션아이템 추출과 태스크 자동화 |
| 2B | OCR 박스 검수와 확정 텍스트 |
| **4** | **확장 기능 — 대시보드 · 검색 · 일괄 처리 · 리포트 · 폴더 감시** |

> 현재 개발 범위가 어느 계층인지 먼저 확인하고, **다음 계층 기능을 섞어
> 구현하지 않는다.**

**검색이 4계층(확장)에 있는데 기능명세서는 `RAG-01`·`02`·`03`·`04`·`07`·`08`·
`09` 를 P1 로 둔다.** 두 기준이 어긋난다.

| 기준 | 검색의 위치 |
|---|---|
| `DEVELOPMENT_GUIDE` 2절 | 4계층 확장 기능 |
| `기능명세서` 14절 | **P1 — 차별화 핵심** |

우선순위 규칙상 `DEVELOPMENT_GUIDE` 가 기능명세서보다 위이므로
**문서만 보면 검색을 나중에 해야 한다.** 다만 기능명세서 14절이 도메인을
공공 SI 로 좁힌 뒤 근거가 바뀌었다고 명시하고 있어, **개발 가이드 쪽이 낡은
것일 가능성이 크다.**

**어느 쪽이 맞는지 확인해야 한다.** 이 결정이 `0011` 착수 시점을 정한다.

### 13.4 `VIS-07` 과 `RAG-04` 가 같은 기능을 두 번 정의한다

| ID | 기능 | 우선 | 담당 | 선행 |
|---|---|---|---|---|
| `VIS-07` | 시맨틱 검색 (pgvector) | **P3** | 보현 | `VIS-06` |
| `RAG-04` | 의미 검색 | **P1** | 보현 | `RAG-03` |

**같은 것이다.** 그런데 우선순위가 P3 과 P1 로 다르고, `VIS-07` 은 완료 판정
기준이 비어 있다.

`RAG` 영역이 신규로 추가되면서(기능명세서 14절 — "도메인을 공공 SI·용역으로
좁힌 뒤 정식 범위가 됐다") **`VIS-07` 이 정리되지 않고 남은 것으로 보인다.**
15절 폐기 목록에도 없다.

기능명세서 머리에 규칙이 있다.

> ID 는 확정 후 변경하지 않는다. 폐기된 기능도 번호를 재사용하지 않고 `폐기` 로 남긴다.

**따라서 `VIS-07` 을 지우지 않고 `폐기` 로 표시하거나, 성격을 바꿔야 한다.**
`VIS-06` 을 선행으로 두고 있으니 **"검색 화면에 시맨틱 결과를 얹는 UI"** 로
성격을 바꾸는 쪽이 자연스럽다. `RAG-04` 는 검색 자체이고 `VIS-07` 은 화면이다.
15절에 이미 "폐기하지 않고 성격만 바꾼 것" 표가 있으므로 거기에 한 줄 추가하면 된다.

### 13.5 API 계약서에 검색 엔드포인트가 없다

엔드포인트 50개를 확인했는데 `RAG` 영역에 대응하는 것이 하나뿐이다.

| 기능 | 우선 | 대응 엔드포인트 |
|---|---|---|
| `VIS-06` 통합 검색 | P2 | `GET /api/projects/{pid}/search` |
| **`RAG-04` 의미 검색** | **P1** | **없음** |
| **`RAG-08` 근거 스니펫 연결** | **P1** | **없음** |
| **`RAG-12` 유사 사업 단가 선례 검색** | P2 | **없음** |
| `RAG-01`·`02`·`03`·`07`·`09` | P1 | 내부 로직이라 불필요 (정상) |

**`RAG-04` 가 P1 인데 API 계약이 없다.** `RAG-08` 도 같다.
`0011` 을 만든 직후 구현할 대상인데 계약이 비어 있으면 프런트와 맞출 수 없다.

`VIS-06` 의 `search` 에 파라미터를 얹는 방식(`?mode=semantic`)과 별도 경로를
두는 방식(`/search/semantic`) 중 하나를 골라야 한다. `RAG-05` 가 둘을 결합하는
것이므로 **하나의 엔드포인트에 모드를 두는 쪽이 나중에 합치기 쉽다.**

**초안을 만들어 올릴 수 있다. 지시해주면 쓰겠다.**

#### 덧붙여 — 계약서에 중복 기재가 있다

`31`~`34` 번(`batch-jobs` 4건)이 **두 번 적혀 있다.** 번호도 31~34 로 같다.
복사 중 생긴 것으로 보이며 실제 엔드포인트는 50개가 아니라 46개다.

### 13.6 API 를 배제할 근거가 **약해졌다** — 8월 12일 판의 논거를 철회한다

8월 12일 판은 이 절 제목을 **"API 모델을 볼 필요가 줄었다"** 로 달고 이렇게
적었다.

> 한국어 특화가 효과 있다는 것이 확인됐다. 같은 1024 차원에서 한국어 특화
> `KURE-v1`(27)이 다국어 원본 `e5-large`(23)를 4문항 앞섰다.
> 후보 API 모델 셋은 **모두 다국어 모델**이다.
> **다국어 모델이 한국어 특화를 이기지 못한 사례를 우리가 직접 만들었으므로,
> 데이터를 외부로 보내면서까지 API 로 갈 근거가 약해졌다.**

**5차에서 이 논거가 무너졌다.**

| 모델 | 성격 | 안겹침 R@5 |
|---|---|---|
| `BGE-m3-ko` | 한국어 튜닝 | 41 |
| `KURE-v1` | **한국어 특화** | **37** |
| **`arctic-l-v2.0`** | **다국어 최신** | **37** |
| `bge-m3` | 다국어 원본 | 35 |

**다국어 최신 모델 `arctic` 이 한국어 특화 `KURE-v1` 과 동점이다.**
그리고 `KURE-v1`(37)과 다국어 원본 `bge-m3`(35)는 검정에서 구별되지 않는다(p=0.77).

**"다국어라서 불리하다" 는 논거를 더 쓸 수 없다.**

#### 왜 틀렸나 — 표본 하나에 기댔다

8월 12일 판의 근거는 **`e5-large` 하나**였다. 그 모델은 5차에서 **9종 중
최하위**로 드러났다.

> **가장 약한 모델 하나를 이겼다고 범주 전체의 우위를 주장한 셈이다.**

`arctic` 은 `e5-large` 와 같은 "다국어" 범주인데 37 대 18 이다.
**범주 안의 격차가 범주 간 격차보다 크다.**

#### 그래서 남은 API 쟁점은 하나다

| 쟁점 | 상태 |
|---|---|
| ~~한국어 성능이 떨어질 것이다~~ | **철회.** 다국어 `arctic` 이 2위다 |
| 비용 | **쟁점 아니다.** Voyage 는 첫 2억 토큰 무료 |
| 배포 무게 | **API 가 유리하다.** 로컬은 `torch` 나 GGUF 등록이 붙는다 |
| **문서가 외부로 나간다** | **이것만 남았다.** 성능과 무관한 판단이다 |

후보로 언급된 API 모델 셋은 여전히 **한국어 성능이 미확인**이다.

| 모델 | 한국어 특화 | 우리 실측과의 관계 |
|---|---|---|
| `voyage-4` 계열 | 아니다 (다국어) | **한국어 성능 미확인** |
| OpenAI `text-embedding-3-large` | 아니다 (다국어) | **한국어 성능 미확인** |
| `gemini-embedding-001` · `2` | 아니다 (다국어) | **한국어 성능 미확인** |

**미확인이라는 사실은 배제 근거가 아니다.** 재봐야 안다. 그리고 재기 전에
데이터 유출 허용 여부를 팀이 정해야 한다 — 그것이 성능보다 앞선 판단이다.

정리하면 이렇다.

| | 판단 |
|---|---|
| 지금 | **1라운드(로컬)로 확정하고 진행한다.** 한국어 특화가 앞선다는 실측이 있다 |
| 나중 | 시간이 남고 데이터 유출이 허용되면 2라운드로 API 하나를 재본다 |
| 순서 | `voyage-4` 가 1024 기본이라 **컬럼을 안 바꾸고 비교할 수 있다.** 첫 2억 토큰이 무료라 돈도 안 든다. 첫 후보로 적합하다 |
| 도구 | **하네스에 붙여 뒀다** — `run_eval.py --api-only`. 요청 형식은 `check_api_encoders.py` 로 키 없이 검사된다 |

#### 그래도 Gemini 를 볼 때 판단할 것 셋

세현이 제안한 후보다. 사양은 8.1절에 정리했다. **비용은 쟁점이 아니다**
(Voyage 는 첫 2억 토큰 무료 · Gemini 는 문서 20건에 0.2달러 수준).
판단해야 할 것은 다른 셋이다.

| | 안건 | 왜 팀이 정해야 하나 |
|---|---|---|
| 1 | **고객 문서 전량을 외부 API 로 보내도 되는가** | 임베딩은 요약과 달리 **모든 문서의 모든 조각**을 보낸다. 색인해야 검색되므로 100% 다 |
| 2 | **Preview 모델을 발표에 쓸 것인가** | `gemini-embedding-2` 는 Preview 다. 사양·가격·가용성이 바뀔 수 있다. GA 인 `gemini-embedding-001` 을 먼저 본다 |
| 3 | 권장 차원이 아닌 1024 를 쓸 것인가 | 3072 벡터를 잘라 쓰는 것이라 **직접 정규화해야 한다.** 권장 768 과 비교해 손실이 얼마인지 봐야 한다 |

**3번은 앞선 판에서 "1024 컬럼에는 안 들어간다" 고 적었던 것을 고친 것이다.**
들어간다. 8.1절의 정정을 본다. 따라서 **Gemini 때문에 컬럼을 768 로 낮출
이유는 없다.** 대신 잘린 벡터의 품질을 재봐야 한다는 문제로 바뀌었다.

#### 덧붙여 — 멀티모달이라는 점이 우리 파이프라인과 겹칠 수 있다

Gemini Embedding 2 는 **PDF·이미지를 직접 받는다.** 우리는 OCR 로 글자를 뽑아
텍스트를 임베딩하는 구조인데, 이 모델은 그 단계를 건너뛸 수 있다.

**다만 그러면 OCR 검수 기능(`REV-*` · 재정 담당)의 의미가 약해진다.**
우리 제품의 차별점 2B 가 "OCR 박스 검수와 확정 텍스트" 이고,
검수 확정 시 재임베딩(`RAG-09`)이 그 사슬의 끝이다.
**PDF 를 그대로 임베딩하면 사람이 고친 텍스트가 반영되지 않는다.**

그러므로 멀티모달 입력은 **쓰지 않고 텍스트 입력만 쓰는 것**이 제품 방향에 맞다.
이 점을 계약·설계에 못박아두지 않으면 나중에 편의상 PDF 를 직접 넣게 된다.

### 13.7 청크에 OCR 출처를 남길지 — 재정님 `0009` 가 준 선택지

머지된 `0009` 가 `extracted_texts` 에 두 컬럼을 넣었다.

| 컬럼 | 뜻 |
|---|---|
| `text_char_count` | 원본에 이미 글자로 박혀 있던 분량 |
| `ocr_char_count` | OCR 로 읽어낸 분량 |

**이 값이 있으면 검색 결과 스니펫에 "이 근거는 OCR 결과다" 를 붙일 수 있다.**
OCR 은 오독 가능성이 있으므로 사용자가 원문을 확인할 판단 근거가 된다.
`RAG-08`(근거 스니펫 표시)의 신뢰도를 높이는 값이다.

다만 **두 컬럼은 문서 단위 합계이고 청크 단위가 아니다.**
문서 하나에 원본 텍스트와 OCR 이 섞여 있으면 특정 청크가 어느 쪽에서 왔는지
이 값만으로는 알 수 없다.

| 방법 | 어떻게 | 정확도 | 비용 |
|---|---|---|---|
| A. 문서 단위 표시 | `ocr_char_count > 0` 이면 그 문서의 모든 청크에 표시 | **낮다.** 섞인 문서에서 원본 텍스트 청크도 OCR 로 표시된다 | 없음. 조회만 |
| B. 청크 단위 기록 | 청킹할 때 `document_chunks` 에 출처 컬럼을 둔다 | 정확하다 | 청킹 로직이 출처를 알아야 한다 |
| C. 표시하지 않는다 | 지금처럼 둔다 | — | 없음 |

**판단하지 않는다.** 이번 시험 범위는 임베딩 모델 선정이고, 이것은 청킹 구현
담당이 정할 사항이다. **다만 B 를 고르려면 `0011` 에 컬럼이 들어가야 하므로
그 전에 결정해야 한다.** 나중에 추가하면 마이그레이션이 한 번 더 필요하다.

`RAG-09`(검수 반영 재임베딩)와 성격이 같다 — **사람이 고친 결과가 검색에
제대로 반영되는지**의 문제다.

### 13.8 라이선스와 배포 무게 — 허깅페이스가 왜 나오나

#### 라이선스 — 후보 9종 전부 확인했다

**허브 모델 카드의 `license` 필드를 직접 읽었다.** 8월 12일 판은 GitHub 원본
저장소를 봤는데(허깅페이스 접속이 막혀서), **모델 카드와 저장소의 라이선스가
다를 수 있다**는 한계를 그때 스스로 적어 두었다. 그 한계를 해소했다.

```python
from huggingface_hub import HfApi
api = HfApi()
api.model_info("dragonkue/BGE-m3-ko").cardData.get("license")   # -> apache-2.0
```

| 모델 | 라이선스 | 상업적 사용 |
|---|---|---|
| **`dragonkue/BGE-m3-ko`** (채택) | **apache-2.0** | **가능** |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | apache-2.0 | 가능 |
| `nomic-ai/nomic-embed-text-v2-moe` | apache-2.0 | 가능 |
| `Qwen/Qwen3-Embedding-0.6B` | apache-2.0 | 가능 |
| `nlpai-lab/KURE-v1` | **mit** | 가능 |
| `BAAI/bge-m3` | **mit** | 가능 |
| `intfloat/multilingual-e5` (base · large) | mit | 가능 |
| `dragonkue/multilingual-e5-small-ko-v2` | mit | 가능 |

**라이선스로 걸러지는 후보는 없다.** 이 기준은 결과적으로 판별력이 없었다.
다만 확인하지 않고 넘어갔다면 채택 모델이 비상업 라이선스일 위험을 안고
제출했을 것이므로 확인 자체는 필요한 절차였다.

**확인이 필요했던 이유가 있다.** 같은 고려대 NLP&AI 연구실의 `KULLM3` 는
**CC-BY-NC**(비상업)다. 연구실이 같으니 `KURE` 도 그럴 수 있었다.
**아니었다 — `KURE` 는 MIT 다.**

#### 검토 때 나올 질문 하나

> 원본 `bge-m3` 가 MIT 인데 파생본 `BGE-m3-ko` 가 apache-2.0 인 것이 맞나?

**맞다.** MIT 는 재라이선싱을 막지 않는다. MIT 저작물을 수정해 더 엄격한(하지만
여전히 허용적인) Apache-2.0 으로 배포할 수 있고, 원본 MIT 고지만 유지하면 된다.

| | MIT | Apache-2.0 |
|---|---|---|
| 상업 이용·수정·재배포 | 가능 | 가능 |
| 의무 | 저작권 표시 | 저작권 표시 + **변경 사실 고지** + `NOTICE` 보존 |

**모델 가중치를 우리 저장소에 담지 않고 허브·Ollama 에서 받아 쓰므로 실무
부담은 출처·라이선스 표기뿐이다.**

#### 채택 모델은 Ollama 공식 라이브러리에 없다 — 배포 작업이 하나 붙는다

**`BGE-m3-ko` 는 허깅페이스 전용 모델이다.** Ollama 로 올리려면
**GGUF 파일을 내려받아 `Modelfile` 로 직접 등록**해야 한다.

| 후보 | Ollama 경로 | 배포 작업 |
|---|---|---|
| `bge-m3` · `arctic-l-v2.0` · `nomic-v2-moe` · `Qwen3` | **공식** | `ollama pull` 한 줄 |
| **`BGE-m3-ko`** (채택) | **공식 없음** | GGUF 내려받기 → `ollama create` → 태그 관리 |
| `KURE-v1` | 비공식 저장소 | `ollama pull daynice/kure-v1` |

**채택을 뒤집는 사유는 아니다.** 품질이 41 대 37 로 앞서고 한 번 등록해 두면
이후는 같다. 다만 **임베딩 생성·저장(`RAG-02`)에 "모델 등록" 작업이 하나
늘어난다.** 그것을 모르고 일정을 잡으면 막힌다.

**여기서 대안이 값을 한다.** 공식 경로가 꼭 필요하면 `arctic-embed-l-v2.0` 이
`ollama pull` 한 줄로 끝난다. 안겹침 37문항으로 채택 모델과 4문항 차이고
**통계적으로 구별되지 않는다**(8.2절). 차원이 같아 DB 도 안 건드린다.

**GGUF 는 양자화본이라 우리가 잰 fp32 점수와 다를 수 있다. 그건 안 쟀다**
(10절 9·10번).

**이것을 채택 결정 뒤에 알았다.** 배포 경로를 미리 확인하지 않은 것이
이번 시험의 절차 결함이다. 그래서 3절 고려사항에 **11. Ollama 지원** 을 추가했다.

#### 허깅페이스 얘기가 나오는 이유 — 코드로 확인했다

세현이 API 쪽을 선호하며 허깅페이스를 언급했다. **그 실체를 코드로 확인했다.**

| 확인 대상 | 결과 |
|---|---|
| 우리 시험 도구가 무엇을 쓰나 | `sentence-transformers`. **`SentenceTransformer("nlpai-lab/KURE-v1")` 의 그 문자열이 허깅페이스 저장소 경로다.** 모델 5개 전부 허깅페이스에서 받았다 |
| Tasqra 본코드에 허깅페이스가 있나 | **없다.** `transformers` · `sentence-transformers` · `torch` 가 `requirements.txt` 에 하나도 없다. AI 의존은 `openai` **한 줄뿐**이다 |
| 로컬 LLM 은 허깅페이스를 쓰나 | **아니다.** `app/ai/local_client.py` 는 **Ollama** 의 OpenAI 호환 엔드포인트를 부른다 |

**그러므로 "로컬 임베딩" 은 곧 "허깅페이스 의존을 새로 들이는 것" 이다.**
이것이 API 를 선호할 실질적 근거가 된다. **이 결과서가 그동안 빠뜨린 논점이다.**
"로컬은 0원" 이라고 적었지만 그것은 **호출 비용**만의 이야기였다.

#### 로컬을 택하면 새로 들어오는 것

| 항목 | 무엇이 | 왜 부담인가 |
|---|---|---|
| **패키지** | `sentence-transformers` → `torch` · `transformers` · `tokenizers` 등 | `torch` 는 파이썬 패키지 중 가장 무거운 축이다. 이미지가 커지고 빌드가 느려진다 |
| **모델 파일** | `BGE-m3-ko` 는 XLM-R large 계열 (**568M 파라미터 · 가중치 2,166MB**) | 이미지에 넣으면 이미지가 커지고, 런타임에 받으면 **허깅페이스가 죽으면 앱이 못 뜬다** |
| 메모리 | **실측 최고 2,203MB** | 컨테이너 메모리 상한을 올려야 한다 |
| 기동 시간 | **실측 적재 7.4초** (캐시가 있는 상태) | 캐시가 없으면 내려받는 시간이 더 붙는다 |
| **모델 등록** | Ollama 공식이 아니라 GGUF 등록이 필요하다 | 위에 적었다 |

**메모리 수치가 8월 12일 판(1,534MB)과 다르다.** 그 값은 틀렸다 —
현재 사용량을 모델 전후로 재서 뺀 값이라 가중치(2,166MB)보다 작게 나왔다.
**모델이 자기 가중치보다 적게 쓸 수는 없다.** 별도 도구로 최고 사용량을 재니
2,203MB 였다(7.6절).

**패키지 용량은 재지 않았다.** 추측하지 않는다.

#### 부담을 줄이는 방법 — 로컬로 가더라도

| 방법 | 내용 | 대가 |
|---|---|---|
| 모델을 이미지에 미리 넣는다 | 빌드 때 받아 굽는다. 런타임에 허깅페이스를 안 부른다 | 이미지가 커진다. 모델을 바꾸면 다시 빌드 |
| 볼륨에 캐시를 마운트한다 | `HF_HOME` 을 볼륨으로 두면 컨테이너를 다시 만들어도 유지된다 | 볼륨을 팀원마다 채워야 한다 |
| **임베딩만 별 컨테이너로 뺀다** | 본 API 는 가볍게 두고 임베딩 서버에 HTTP 로 부른다. **Ollama 를 쓰는 지금 구조와 같은 모양이다** | 컨테이너가 하나 늘고 관리 대상이 된다 |
| ONNX 로 바꿔 `torch` 를 뺀다 | `onnxruntime` 만 두면 `torch` 를 안 넣어도 된다 | 변환 작업이 붙고 정확도를 다시 확인해야 한다 |

**판단하지 않는다.** 배포는 이 시험의 범위가 아니고 팀 결정이다.
다만 **로컬이 0원이라는 말이 배포 무게까지 0이라는 뜻은 아니다.**

#### API 쪽 비용도 다시 봤다 — 우리 규모에서는 무료다

| | 확인한 사실 |
|---|---|
| Voyage | **`voyage-4` 계열은 계정당 첫 2억 토큰이 무료다** |
| 우리 규모 | 청크 649개 = 약 15만 토큰. **문서 약 1.3만 건까지 무료 구간 안이다** |
| OpenAI | 무료 구간 없음. 문서 1,000건에 약 $1.95 |

**비용은 어느 쪽에서도 쟁점이 아니다.** 그러므로 판단은 세 가지로 좁혀진다 —
**데이터 유출 · 검색 시 외부 의존 · 배포 무게.** 앞의 둘은 로컬이 유리하고
마지막 하나는 API 가 유리하다.

### 13.9 API 실측을 시도하다 나온 것 — 무료 등급의 함정 둘

2라운드를 실행해 보려고 키를 발급받아 돌렸다. **재보기 전에 알 수 없었던 것이
둘 나왔다.** 둘 다 문서만 읽고는 알 수 없는 종류다.

#### 함정 1 — Gemini 무료 등급은 우리 문서를 제품 개선에 쓸 수 있다

Google 공식 문서에 이렇게 적혀 있다.

> 결제 계정을 연결해 유료 등급으로 올리면 **프롬프트와 응답이 Google 제품
> 개선에 쓰이지 않도록** 보장할 수 있다
> — [Gemini API 결제 문서](https://ai.google.dev/gemini-api/docs/billing)

Google 개발자 포럼의 정리도 같다 — "제품 개선에 사용" 항목이
**무료 등급은 예 · 유료 등급은 아니오**다.

**즉 무료 키로 시험하는 것 자체가 데이터 유출이다.** 이것을 몰랐다면
"공짜니까 일단 재보자" 로 문서를 보냈을 것이다. 임베딩은 요약과 달리
문서 전량이 나가므로 피해 범위가 넓다.

**우리 코퍼스로 따지면 이렇다.**

| 문서 | 출처 | 무료 등급으로 보내도 되나 |
|---|---|---|
| 중앙보훈병원 입찰공고문 | 나라장터 **공개** | 괜찮다 |
| 지역난방공사 준공정보 | 공공데이터 **공개** | 괜찮다 |
| 지역난방공사 낙찰현황 | 공공데이터 **공개** | 괜찮다 |
| 기초과학연구원 공고 | 나라장터 **공개** | 괜찮다 |
| **미니플젝_결정사항** | **우리 팀 내부 문서** | **판단이 필요하다** |

5건 중 4건은 이미 공개된 문서라 문제가 없다. 하나가 걸린다.

**결론 — Gemini 는 무료 등급으로 재지 않는다.** 유료 등급으로 올린 뒤에
재거나, 내부 문서를 뺀 코퍼스로 재야 한다. 다만 코퍼스를 바꾸면 `gold_chunk_ids`
가 어긋나 로컬 실측과 비교할 수 없다. **그러므로 순서는 유료 등급이 먼저다.**

**본구현에서는 어느 쪽이든 무료 등급을 쓰면 안 된다.** 고객 문서가 들어온다.

#### 함정 2 — Voyage 무료 토큰 범위가 문서와 응답에서 다르다

문서에는 `voyage-4` 계열에 첫 2억 토큰이 무료라고 적혀 있다(8.1절 출처).
그런데 **429 응답 본문은 이렇게 답했다.**

```
the free tokens (200M tokens for Voyage series 3)
```

**series 3 이라고 한다.** `voyage-4` 가 무료 범위에 드는지 확인하지 못했다.
대시보드 billing 화면에 모델 이름이 나오지 않아 거기서도 확인이 안 됐다.

**지금은 문제가 되지 않는다.** 결제 수단을 등록하지 않으면 과금 자체가
불가능하다. **카드를 넣을 때만 확인이 필요하다.**

**만약 series 3 만 무료라면 `voyage-3.5` 로 재도 비교는 유효하다.**
차원이 1024 로 같고, 우리가 확인하려는 것은 "다국어 API 가 한국어 특화를
이기는가" 다. 세대 차이는 그다음 문제다.

#### 함정 3 — 카드를 등록하지 않으면 한도가 매우 낮다

Voyage 는 결제 수단이 없으면 **3 RPM · 10K TPM** 이다.

| | 우리 작업량 | 한도 |
|---|---|---|
| 요청 수 | 배치 64 로 4회 | **분당 3회** |
| 토큰 | 29,996자 ≈ 3~5만 토큰 | **분당 1만** |

**배치를 64로 잡아 둔 것이 이 한도를 전혀 고려하지 않았다.** 첫 시도가
429 로 실패했다.

카드 등록을 요구하지 않는 쪽으로 도구를 고쳤다. 주소를 영어로 채워야 하고,
**팀원이 각자 카드를 넣어야 재현할 수 있다면 그것은 도구가 아니다.**

| 붙인 것 | 내용 |
|---|---|
| `RateLimit` | 최근 60초의 요청·토큰을 들고 있다가 한도를 넘으면 창이 빌 때까지 잔다 |
| 토큰 추정 보정 | 한국어는 글자당 토큰이 토크나이저마다 다르다. 처음엔 1.6 으로 넉넉히 잡고 **응답의 실제 토큰 수로 고쳐 쓴다** |
| 배치 이중 상한 | 개수와 글자 수 둘로 자른다. 글자 상한은 TPM 의 절반이다 |
| 429 후퇴 시간 | 3 RPM 이면 창이 비는 데 20초다. 2·4·8초씩 물러나는 것은 의미가 없었다 |
| `--voyage-free` | `--rpm 3 --tpm 10000` 을 한 번에 준다 |

**이 대기가 검색 품질을 흐리지 않는다.** 임베딩은 텍스트마다 독립이라
배치 크기를 바꿔도 같은 청크는 같은 벡터가 나온다. 흐려지는 것은 속도
지표뿐이고, 그것은 애초에 로컬 CPU 시간과 같은 자로 비교할 수 없는 값이다.
`results.csv` 의 `wait_sec` 에 잔 시간을 따로 남겨 둔다.

**예외가 하나 있다.** `voyage-context-4` 처럼 같은 문서의 다른 청크를
참고해 벡터를 만드는 모델은 배치 구성이 결과를 바꾼다. 우리가 쓰는
`voyage-4` 는 아니다. 그 계열을 후보에 넣게 되면 이 판단을 다시 해야 한다.

#### 이 절이 말하는 것

**"API 를 재본다" 는 키만 발급받으면 되는 일이 아니었다.**
무료 등급의 데이터 이용 조항과 호출 한도가 먼저였다. 둘 다 성능과 무관한데
성능 측정을 막는다. **1라운드를 로컬로 확정하고 진행한 판단이 결과적으로
옳았다** — API 를 먼저 골랐다면 여기서 일정이 멈췄을 것이다.

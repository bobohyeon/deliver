## 1. 목적과 연결 기능

### 1.1 무엇을 정하려 했나

| 정할 것 | 왜 지금인가 |
|---|---|
| **벡터 차원** | `pgvector` 컬럼 타입에 박힌다. 나중에 바꾸면 **전체 재임베딩** |
| **기본 모델** | 위 차원 안에서 고른다 |
| **CPU 감당 여부** | 시험자 장비에 GPU가 없다 |

### 1.2 기능명세서 연결

| ID | 기능 | 우선순위 | 완료 판정 기준 | 이번 시험과의 관계 |
|---|---|---|---|---|
| `RAG-01` | 텍스트 정규화 · 청킹 | P1 | 토큰 수 기준으로 자른다. 표는 행 단위로 유지 | 청킹 조건이 검색 품질에 미치는 영향을 확인 |
| `RAG-02` | 임베딩 생성 · 저장 | P1 | **어느 모델·차원으로 만든 것인지 기록된다** | **차원과 모델을 이 문서로 확정** |
| `RAG-04` | 의미 검색 | P1 | **글자가 하나도 겹치지 않는 질의로 관련 문서가 나온다.** 다른 프로젝트 문서는 나오지 않는다 | 전반 조건을 측정. **후반 조건은 미충족 (8.5절)** |
| `RAG-10` | 검색 품질 측정 | P2 | 질의 목록에 대한 적중 여부가 수치로 나온다 | **이번 하네스가 곧 구현체** |

## 2. 실행 환경 제약 — 이것이 선택 기준을 정했다

| 항목 | 내용 |
|---|---|
| 시험 장비 | 보현 PC. **GPU 없음. CPU 단독** |
| LLM 실행 장비 | 세현 GPU 장비 (별도) |
| 발표 방식 | **실시간 데모가 아니라 영상 촬영** |
| 문서 크기 상한 | `MAX_EXTRACTED_CHARS = 45,000자` |
| 성능 요구 | `PER-01` 10페이지 60초 |

**영상 촬영이라는 점이 판단을 바꿨다.**

| | 실시간 데모 | 영상 촬영 |
|---|---|---|
| 느린 구간 | 그대로 보인다 | 편집으로 잘라낸다 |
| 최종 실행 장비 | 발표장 PC | **세현 GPU 장비 가능** |
| CPU 속도 압박 | 크다 | 작다 |

그래서 **CPU가 느리다는 이유만으로 1024차원을 배제하지 않았다.**
개발·시험은 CPU에서 하고, 최종 촬영은 GPU 장비에서 하면 된다.
다만 384차원을 후보에 남겨 **CPU로 감당이 안 될 정도인지 실제로 재봤다.**

## 3. 모델 선택 시 고려 사항 8가지

| | 항목 | 왜 중요한가 | 이번에 확인한 방법 | 결과 |
|---|---|---|---|---|
| 1 | **벡터 차원** | `pgvector` 컬럼을 묶는다. 바꾸면 전체 재임베딩 | 1024와 384를 같은 평가셋으로 비교 | **1024 채택** |
| 2 | **글자 안 겹치는 질의 성능** | 이게 임베딩을 쓰는 근거 자체 | `no_overlap` 39문항 `R@5` | 1024가 두 배 |
| 3 | **글자 겹치는 질의만 보면 안 된다** | 키워드 검색으로도 되는 일이다 | `overlap`과 분리 집계 | **역전 발생 (8.3절)** |
| 4 | **접두어 규칙** | 안 지키면 한쪽이 억울하게 진다 | 코드로 적용 여부 검증 | 적용 확인 (5.5절) |
| 5 | **CPU 색인 속도** | 색인은 한 번, 질의는 매번 1건 | 100청크당 초 측정 | 13배 차이 |
| 6 | **메모리** | 다른 모델과 동시 적재 가능성 | RSS 증가분 측정 | **측정 무효 (10절)** |
| 7 | **벡터 저장 용량** | 청크 수만큼 곱해진다 | 차원 × 4바이트 | 1024 = 4KB · 384 = 1.5KB |
| 8 | **로컬 대 API** | 비용과 반복 가능성 | 로컬 우선, API는 2라운드 | 미착수 |

**7번 저장 용량이 1024 채택의 유일한 손실이다.** 청크당 2.5KB 차이다.
문서 20건 × 190청크 = 3,800청크면 약 9MB 차이다. 무시할 수준이다.

## 4. 후보를 3종으로 추린 근거

### 4.1 선정한 3종 — 각 모델이 하나의 질문에 답한다

| | 모델 | 차원 | 접두어 | **이 모델로 답하는 질문** |
|---|---|---|---|---|
| 1 | `BAAI/bge-m3` | 1024 | 없음 | **기준선.** 한국어 특화가 이걸 못 이기면 특화의 의미가 없다 |
| 2 | `nlpai-lab/KURE-v1` | 1024 | 없음 | **한국어 특화가 효과 있나.** bge-m3 기반이라 같은 조건 비교 |
| 3 | `dragonkue/multilingual-e5-small-ko-v2` | 384 | `query: ` / `passage: ` | **작은 모델로 충분한가.** CPU 현실성 |

**축을 두 개로 좁혔다.** 한국어 특화 여부(1 대 2), 모델 크기(1·2 대 3).
CPU에서 다섯 개 이상을 돌리면 시간이 과하게 든다.

3번을 "자원 절약용"이 아니라 **진짜 후보**로 넣은 이유가 있다.
모델 카드가 "2배 큰 `e5-base`보다 한국어 벤치마크에서 낫다"고 밝히고 있다.
CPU 환경이면 이길 수도 있다고 보고 대등하게 시험했다.

### 4.2 보류한 후보와 이유

| 모델 | 차원 | 언제 넣나 |
|---|---|---|
| `dragonkue/BGE-m3-ko` | 1024 | 1라운드에서 `bge-m3`가 유망할 때 |
| `nlpai-lab/KoE5` | 1024 | KURE와 비교할 때 |
| `mykor/KURE-v1-gguf` | 1024 | **CPU 속도가 문제일 때.** 양자화판이라 성능 동일·속도만 다르다 |
| CLOVA Studio 임베딩 | 확인 필요 | **유료.** 로컬로 좁힌 뒤 마지막 |

**8.2절 결론에 따라 1024차원 추가 모델은 지금 넣지 않는다.**
KURE와 bge 차이가 질의 1개인 상태에서 같은 차원 모델을 더 넣으면 노이즈만 늘어난다.

**CLOVA를 볼 때 확인할 것** — 임베딩 모델 목록에 `bge-m3`가 있는지 본다.
같은 가중치를 호스팅한다면 이번 로컬 결과가 그대로 적용되고,
비교가 "성능"이 아니라 **"직접 띄우기 대 API"** 로 단순해진다.

### 4.3 계획과 실제의 차이

당초 3단계로 나눴다.

| | 계획 | 실제 |
|---|---|---|
| 1라운드 | KURE 레포 발표 벤치마크로 후보 좁히기 (우리가 만들 것 없음) | **실패.** 레포 접근이 403으로 막혔다 |
| 2라운드 | 우리 문서 5건 + 질의 15개로 도메인 확인 | **여기서 3모델 전부 직접 측정.** 질의 78문항 |
| 3라운드 | 필요하면 확장 | 미착수 |

**1라운드를 건너뛰고 2라운드를 크게 한 셈이다. 결과적으로 이게 나았다.**
공개 벤치마크는 일반 한국어 검색을 재지만, 우리 도메인은 공공 SI 공고문과
계약 CSV다. 문장 구조와 어휘가 다르다. 공개 수치로 걸러낸 뒤 우리 것으로
재확인하는 것보다, 처음부터 우리 도메인으로 재는 편이 근거가 직접적이다.

당초 "질의 15개로 시작"으로 잡았으나 78문항을 만들었다. 과했다고 보지 않는다.
`no_overlap` 34문항이면 모델 간 차이를 읽을 수 있고, 15개였다면 8.2절의
"차이가 노이즈"라는 판단조차 못 했을 것이다.

## 5. 시험 방법

### 5.1 코퍼스 — 문서 5건 · 29,996자 · 127청크

| 문서 | 글자 | 출처 성격 | 왜 넣었나 |
|---|---|---|---|
| 중앙보훈병원 유지관리 용역 입찰공고문 | 13,121 | 나라장터 공개 (PDF) | 실제 도메인 문서. 조항 나열형 |
| 미니플젝_결정사항 | 7,374 | 우리 팀 문서 (CSV) | **정답을 우리가 안다.** 서술형 |
| 한국지역난방공사 준공정보 | 4,722 | 공공데이터 (CSV) | `RAG-12` 단가 선례 자료 |
| 한국지역난방공사 낙찰현황 | 2,872 | 공공데이터 (CSV) | 같음 |
| 기초과학연구원 연구비 정산 용역 공고 | 2,042 | 나라장터 공개 (PDF) | 화면 인쇄본. 표 구조가 다르다 |

**우리 팀 문서를 반드시 섞었다.** 우리가 쓴 문서라 답이 어디 있는지 확실히
알 수 있어 정답 표시가 정확해진다.

문서 성격을 셋으로 갈라 넣은 것이 8.4절 발견으로 이어졌다.

### 5.2 청킹

```
python make_chunks.py          (기본값 --target 500 --max 1200)

문서 5건 -> 청크 127개
총 29,996자 · 평균 236자 · 최장 567자
```

절 제목(`#`, `제3조`)에서 끊고, 표로 보이는 줄은 이어 붙인다.

**본구현 청킹과 다르다는 점을 분명히 한다.** `RAG-01` 완료 판정 기준은
`ocr_elements` 의 `element_type` 으로 단락을 묶고 **토큰 수 기준**으로 자르는
것이다. 이 실험은 `corpus/*.md` 텍스트를 **글자 수 기준**으로 잘랐다.

| | 이 실험 | `RAG-01` 본구현 |
|---|---|---|
| 입력 | `corpus/*.md` (변환된 텍스트) | `ocr_elements` (DB 행) |
| 경계 | 마크다운 제목 · 절 제목 | `element_type` 단락 묶음 |
| 길이 기준 | **글자 수** (`--target 500`) | **토큰 수** |

**따라서 이 실험은 모델 비교용 근사 조건이다.** 차원과 모델 선택 결론은
청킹 방식에 크게 좌우되지 않으므로 유효하지만, **절대 점수(27/34)를 본구현
검색 품질 예측치로 쓰면 안 된다.** 본구현 청킹이 완성된 뒤 `RAG-10` 으로
다시 재야 한다. 표를 행 단위로 유지하는 규칙은 양쪽이 같다.

#### 청킹 입력은 재정 담당 OCR 산출물에서 받는다

기능명세서에 이미 그렇게 적혀 있다.

| ID | 선행 | 비고 |
|---|---|---|
| `RAG-01` | **`REV-17`** (텍스트 재조립) | **재정님 단락 분리를 입력으로 쓴다** |

**청킹을 별도로 만들지 않고 OCR 검수 파트의 출력을 받아 이어 붙인다.**
같은 문서를 두 번 구조화하지 않는다.

| | |
|---|---|
| 받는 것 | `ocr_elements` (`element_type` · 좌표 · `reading_order` · `is_excluded`) |
| 하는 것 | `element_type` 으로 단락 묶기 → 토큰 수로 자르기 → `document_chunks` 저장 |
| 의존 | **`RAG-01` 은 `REV-17` 완료에 블로킹된다** (재정 담당 · P1) |

#### 확인 필요 — `element_type` 의 값 집합이 정의되어 있지 않다

Tasqra 코드를 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| `ocr_elements.element_type` 컬럼 | **있다.** `String(20)` NOT NULL · 기본값 `"TEXT_LINE"` |
| 허용 값 CHECK 제약 | **없다** (0006 에는 좌표·version CHECK 만 있다) |
| `models/enums.py` 에 해당 Enum | **없다** |
| 응답 스키마 `OcrElementResponse` 노출 | **안 된다** (id · text · 좌표 · confidence · source · reading_order · version 만) |

**즉 `"TEXT_LINE"` 하나만 확인되고 나머지 값이 무엇인지 모른다.**
`RAG-01` 이 이 컬럼으로 단락을 묶는데, **어떤 값이 단락 경계인지 재정님과
합의해야 한다.** 값 집합이 없으면 청킹 규칙을 쓸 수 없다.

0007 docstring 에 "0006 은 `element_type` 컬럼으로 (단락 묶음) 같은 목적을
달성하고 있으므로" 라고 적혀 있어 **의도는 있으나 값이 아직 안 정해진 상태다.**

리비전 규칙(0001 부터)이 **ENUM 대신 `String` + CHECK** 이므로,
값이 정해지면 CHECK 제약을 추가하는 마이그레이션이 필요하다.
`element_type` 을 응답 스키마에도 노출해야 프런트가 단락을 표시할 수 있다.

`REV-17` 의 완료 판정이 "박스 수정 후 `extracted_texts.content` 가 같은
트랜잭션에서 갱신된다" 이므로, **그 트랜잭션이 끝난 시점의 텍스트가 청킹 입력이다.**

그리고 `RAG-10` 의 비고가 **"청킹 기준 변경의 판단 근거"** 다.
즉 본구현 청킹이 완성된 뒤 이 평가셋으로 다시 재는 것이 `RAG-10` 의 설계 목적이다.
**이번 결과서가 그 첫 회차 기록이 된다.**

**다만 리비전 `0010`(pgvector + `document_chunks`)은 지금 만들 수 있다.**
컬럼 차원만 알면 되고, 그것을 이 문서가 정했다. 청킹 로직과 스키마는 분리된다.

`document-detail` 브랜치의 `0008` 이 `ocr_elements.is_excluded` 를 추가한
것에 주의한다. **제외 표시된 요소는 청킹에서 빼야 한다.** 넣으면 검수로
지운 텍스트가 검색에 남는다 — `RAG-09` 가 막으려는 것과 같은 문제다.

### 5.3 평가셋 설계 — 질의를 구하지 않고 문서에서 역으로 뽑았다

도메인 지식이 필요 없는 방법을 썼다.

```
1. 문서를 청크로 쪼갠다
2. 청크를 읽고 "이 청크가 답이 되는 질문" 을 쓴다
3. 정답은 자동으로 그 청크 번호가 된다
```

청크마다 두 종류를 만들었다.

| `kind` | 규칙 | 무엇을 재나 |
|---|---|---|
| `overlap` | 청크의 단어를 그대로 쓴다 | 기준선. 키워드 검색으로도 찾힌다 |
| **`no_overlap`** | **청크의 단어를 하나도 쓰지 않는다** | **의미 검색만 찾을 수 있다** |

`no_overlap`이 `RAG-04` 완료 판정 기준("글자가 하나도 겹치지 않는 질의")에
그대로 대응한다.

**중요 — `no_overlap`에서 키워드 검색의 상한은 정의상 0이다.**
2글자 이상 토큰이 정답 청크에 하나도 없도록 만들었고 이를 기계로 검증했다.
따라서 토큰·부분문자열 기반 검색(`regexp_replace` + `ILIKE`)은 원리상 찾을 수 없다.
**이건 측정 결과가 아니라 설계상 필연이므로, "키워드로는 0%"를 성과로 말하면 과장이다.**
성과는 임베딩이 그 0을 얼마나 넘는지다.

### 5.4 채점

| 지표 | 뜻 |
|---|---|
| `R@k` | 정답이 상위 k개 안에 들어온 질의 비율 |
| `MRR` | 정답의 순위 역수 평균. 몇 번째로 나오는지 |

`TOP_K = (1, 3, 5, 10)`. **판단 1순위는 `no_overlap`의 `R@5`.**

### 5.5 공정성 검증 — 접두어

`e5` 계열은 접두어가 필수다. 빼면 성능이 크게 떨어진다.
**e5가 탈락했으므로 이 설정이 실제로 적용됐는지 코드로 확인했다.**

```python
passages = [model_cfg["passage_prefix"] + c["text"] for c in chunks]   # run_eval.py 170행
q_texts  = [model_cfg["query_prefix"]   + q["query"] for q in queries] # run_eval.py 179행
```

| 모델 | `query_prefix` | `passage_prefix` | 근거 |
|---|---|---|---|
| bge-m3 | (없음) | (없음) | 모델 카드 |
| KURE-v1 | (없음) | (없음) | bge-m3 기반 |
| e5-small-ko-v2 | `query: ` | `passage: ` | e5 계열 규칙 |

**적용 확인. e5의 패배는 설정 실수가 아니다.**

### 5.6 하네스 점검 — 바닥 확인

모델을 내려받기 전에 가짜 인코더(글자 빈도를 64차원에 넣는 것)로 채점 로직을
확인했다.

| 모델 | `no_overlap` R@5 | `overlap` R@5 |
|---|---|---|
| 가짜 인코더 | **0 / 39** | 15 / 39 |

## 6. 평가셋 결함과 수정 경과

**이 절이 결과 신뢰도의 근거다.** 1차 결과에는 결함이 있었고, 진단으로 찾아 고쳤다.

### 6.1 검사 도구를 만든 이유

`run_eval.py`는 쓸 수 없는 행을 **예외 없이 건너뛴다.** 질의 40개를 넣고
32개만 채점돼도 알아채기 어렵다. 그래서 앞에 검증을 세웠다.

`check_queries.py`가 잡는 것:

| 잡아내는 것 | 위험 |
|---|---|
| `note`에 "예시"가 든 행 | **경고 없이 채점에서 빠진다** |
| 없는 청크 번호 · 정답 없음 | 같이 조용히 빠진다 |
| `no_overlap`인데 단어가 겹침 | **사람 눈으로는 반드시 새어나간다** |
| `overlap`인데 겹치는 말이 없음 | 기준선이 기준선 역할을 못 한다 |
| `kind` 오타 | `unknown`이 되어 어느 집계에도 안 들어간다 |
| 정답이 문서 한 곳에 몰림 | 그 문서 특성만 재게 된다 |

실제로 78문항 중 3건이 `no_overlap` 라벨 위반으로 걸렸다.
`하는` `있는` `사업` 이 정답 청크에 들어 있었다.

### 6.2 기각된 가설 두 개

`no_overlap` 39문항 중 13문항을 **세 모델이 모두 틀렸다.** 원인을 세 번 추정했다.

| 가설 | 결과 | 반박한 데이터 |
|---|---|---|
| 청크가 커서 벡터가 희석된다 | **기각** | 실패한 청크에 151자·99자가 있고, 같은 길이 CSV 행 청크는 성공했다 |
| 허브 청크가 상위를 점거한다 | **기각** | 전체 78질의로 세니 최다 10회. 기대값 3.07회의 3.3배 — 정상 분포 |
| **평가셋 결함이 지배한다** | **확인** | 청크 13 · 24 · 2가 실제 정답이었다 |

**두 번 앞서갔고 두 번 데이터에 교정받았다.**
`--target` 조정 실험을 먼저 했다면 헛수고였다.

### 6.3 확인된 결함 — 모델이 맞고 정답 표시가 틀렸다

| 청크 | 내용 | 오답 처리된 질의 |
|---|---|---|
| 13 (57자) | `공동이행방식만 가능하며, 공동수급체 구성원 모두가 입찰참가자격을 갖추어야 함` | `여러 곳이 팀을 짜서 들어올 수 있나` (정답 1) |
| 24 (483자) | `낙찰자 결정방법 — 기술능력배점 90점, 입찰가격배점 10점` | `점수를 어떻게 나눠 매기나` (정답 4) |
| 2 (465자) | `지역제한 업종제한 업종제한사항` | `장부 다루는 곳만 응찰할 수 있나` (정답 1) |

세 모델이 일관되게 이 청크들을 상위에 넣었다. **셋 다 정답이다.**

원인은 하나다. **같은 종류의 정보가 여러 문서에 흩어져 있다.**


**이번 시험에서 얻은 가장 중요한 평가셋 설계 원칙이다.**
문서 여러 건을 한 코퍼스에 넣으면 질의가 문서를 특정해야 하는데,
문서를 특정하면 문서명이 질의에 들어가 `overlap`이 되어버린다.
**해법은 정답을 넓게 두는 것이다.** `R@5`로 재니 둘 중 하나만 잡아도 성공이다.

### 6.4 수정 내역 — 78문항 → 73문항

| 조치 | 질의 | 이유 |
|---|---|---|
| **삭제** | `이 일에 잡힌 예산이 얼마인가` (4,5) | 예산 청크가 60개 이상. 측정 불가 |
| 삭제 | `배정된 예산 규모` (7) | 같은 이유 |
| 삭제 | `하나만 내면 되나` (31) | "하나"가 무엇인지 문장에 없다. **사람도 못 맞힌다** |
| 삭제 | `무엇을 해야 하는지 적힌 서류를 어디서 받나` (6) | "받나"가 다운로드인지 작성기준인지 모호 |
| 삭제 | `밖으로 새지 않게 다짐을 받아둘 수 있나` (33) | 코퍼스에 서약서·협약이 여럿 |
| **정답 확장** | `여러 곳이 팀을 짜서 들어올 수 있나` | 1 → 1,13 |
| 정답 확장 | `장부 다루는 곳만 응찰할 수 있나` | 1 → 1,2 |
| 정답 확장 | `점수를 어떻게 나눠 매기나` | 4 → 4,24 |
| 정답 확장 | `기술능력평가비율` | 4 → 4,24 |

```
1차  78문항  overlap 39 · no_overlap 39
2차  73문항  overlap 39 · no_overlap 34
```

**점수를 올리려는 조치가 아니다. 측정할 수 없는 문항을 빼고, 잘못 채점된
문항을 바로잡은 것이다.** 남기면 지표가 오염된다.
**1차 수치를 지우지 않고 함께 남긴다.** 결함을 찾아 고친 경과가 기록되어야
숫자를 신뢰할 수 있다.

`R@1` 만 한 칸씩 움직였다. KURE 는 13 → 12, e5 는 9 → 10 이다.
그 한 질의의 순위가 KURE 에서 1위 → 2위, e5 에서 2위 → 1위로 바뀐 결과다.

**이 문항 자체가 `RAG-04` 의 좋은 예시 사례다.**
`기술능력배점 90점 · 입찰가격배점 10점` 을 `실력과 싼값` 으로 물었는데 찾았다.
발표에서 의미 검색을 보여줄 때 쓸 수 있다.

#### 속도는 1024 두 모델 사이에서 비교하지 않는다

| 100청크당 초 | 2차 | 3차 |
|---|---|---|
| bge-m3 | 42.28 | 43.47 |
| KURE-v1 | **35.86** | **45.91** |

**같은 모델·같은 127청크인데 KURE 가 10초 흔들렸다.** CPU 측정 노이즈다.
두 모델은 같은 계열이므로 속도가 비슷하다고 보는 것이 맞다.
**유의한 차이는 e5 와의 약 10배 격차뿐이다.**

메모리는 세 회차에서 일관됐다 (1,552 / 1,544 / 426MB).

## 8. 결과가 말하는 것 — 주장과 근거

### 8.1 `pgvector` 컬럼은 `vector(1024)` — 확정

| 근거 | 수치 |
|---|---|
| 1024차원 대 384차원, 글자 안 겹치는 질의 | **27 / 34 대 14 / 34. 두 배** |
| 이 격차는 표본 34개에서도 유의한가 | **13문항 차이.** 1문항 차이가 아니다 |
| 저장 용량 손실 | 청크당 2.5KB. 3,800청크에 약 9MB. 무시 가능 |
| 교체 자유도 | 1024면 `bge-m3` · `KURE-v1` · `BGE-m3-ko` · `KoE5` 를 재임베딩 없이 바꿔 끼운다 |

**이 결정으로 pgvector 마이그레이션(리비전 `0010`)을 쓸 수 있다.**

### 8.2 기본 모델은 KURE-v1, 확정은 보류

2차 실측에서 KURE가 **`no_overlap` 전 구간에서 앞섰다.**

| `no_overlap` 지표 | KURE-v1 | bge-m3 | 차이 |
|---|---|---|---|
| R@1 | 12 | 12 | **없음** |
| **R@3** | **22** | **19** | **3개** |
| R@5 | 27 | 26 | 1개 |
| R@10 | 29 | 28 | 1개 |
| MRR | 0.533 | 0.499 | 0.034 |

**R@3에서 3개 차이가 가장 큰 격차이고, MRR도 일관되게 KURE가 높다.**
`R@5`에서는 1개 차이지만 그보다 위 순위에서 벌어진다. 즉 **KURE는 정답을
더 위로 올린다.** 1차보다 근거가 강해졌다.

반대로 `overlap`에서는 bge가 앞선다.

| `overlap` 지표 | KURE-v1 | bge-m3 |
|---|---|---|
| R@1 | 25 | **26** |
| R@3 | 31 | **32** |

**KURE는 의미 검색에서, bge는 글자 겹침에서 조금 낫다.**
우리 목적이 `RAG-04` 의미 검색이므로 KURE를 기본으로 두는 것이 맞다.

그럼에도 확정은 보류한다.

| 보류 근거 | 내용 |
|---|---|
| 표본 | `no_overlap` 34문항. R@5 1개 차이는 노이즈 범위 |
| 1차 관찰 | 한 모델만 맞춘 3문항을 **세 모델이 각각 하나씩** 맞췄다 |
| 반례 | 탈락시킨 e5가 41번 문항을 1위로 맞췄고 1024 두 모델은 8~9위였다 |
| 되돌리기 비용 | **차원이 같아 재임베딩 없이 교체 가능하다** |

**그래서 같은 차원 모델을 더 추가하지 않는다.** `BGE-m3-ko`나 `KoE5`를 넣어도
같은 잡음만 본다. 평가셋을 키운 뒤에 다시 볼 일이다.
**지금 못 박을 이유가 없다.**

### 8.3 e5-small 탈락 — 이유가 결론보다 중요하다

```
overlap    38 / 39   세 모델 중 1위
no_overlap 12 / 39   세 모델 중 최하위
```

**작은 모델은 글자가 겹칠 때만 잘한다.** 그건 기존 `ILIKE` 검색이 이미 하는 일이다.
의미로 건너뛰는 능력이 약하다.

**만약 `overlap`만 재고 모델을 골랐다면 e5-small을 뽑았을 것이다.**
그리고 실제 사용자 질의에서 절반을 놓쳤을 것이다.
`overlap` 점수가 높은 것은 임베딩을 쓸 근거가 되지 않는다.

2차 실측에서 `overlap` R@10이 **39 / 39, 즉 100%** 였다.
글자가 겹치는 질의는 열 개 안에 반드시 들어온다.

**다만 `R@10`에서 흥미로운 도약이 나왔다.**

| e5-small `no_overlap` | 값 |
|---|---|
| R@1 | 10 / 34 (0.294) |
| R@5 | 14 / 34 (0.412) |
| **R@10** | **24 / 34 (0.706)** |

**R@5에서 R@10으로 가면서 10문항이 더 잡힌다.** 즉 e5는 정답을 찾기는
하는데 상위로 못 올린다. 순위 매김이 약한 것이다.
(같은 구간에서 KURE는 27 → 29, bge는 26 → 28로 2문항만 늘어난다.)

**이것은 재순위(`RAG-06`, P3)를 붙이면 384차원도 쓸 수 있다는 뜻이다.**
`top-10`을 뽑아 교차 인코더로 다시 세우면 14가 24에 가까워질 수 있다.
저장 용량과 CPU 속도 이점(13배)이 큰 만큼 검토할 값이 있다.
다만 재순위 모델이 추가로 필요하고 `RAG-06`은 P3이므로 이번 결정에는
반영하지 않는다. **11절 후속 과제로 남긴다.**

### 8.4 문서 성격이 검색 난이도를 지배한다

| 문서 성격 | 예 | 검색 결과 |
|---|---|---|
| **필드값 나열 (CSV 행)** | `계약명: 2024년 RHEL 라이선스 갱신 구매` | 고유명사 질의는 잘 찾는다 |
| **조항 나열 (공고문)** | `8. 낙찰자 결정방법 가. 평가방법…` | 실패가 몰렸다 |
| **서술형 (결정사항)** | `안건 / 결정 내용 / 결정 근거 / 대안` | **추상 질의를 끌어당긴다** |

세 모델이 다 틀린 13문항 중 **12문항이 공고문 PDF**였다.
반대로 다 맞춘 10문항은 대부분 CSV 행이었고, 질의에 `Microsoft` `RHEL`
`AutoCAD` `항온항습기` `업무용PC` 같은 **고유명사가 대응**됐다.

**행 단위 청크는 고유명사 질의에만 작동한다.** 청크 70은
`계약명: 전자계약시스템 개선사업 감리용역` 한 줄이 사실상 전부여서,
"감리"라는 단어를 모르면 도달할 방법이 없다. 문맥이 없다.
**`RAG-12`(유사 사업 단가 선례 검색)에 계약명 기준 필터가 필요하다는 근거다.**

### 8.5 `RAG-04` 후반 조건 — 이번 조건에서는 측정하지 않았다

`RAG-04` 완료 판정은 두 부분이다.

| 조건 | 상태 |
|---|---|
| 글자가 하나도 겹치지 않는 질의로 관련 문서가 나온다 | **충족** (27 / 34) |
| 다른 프로젝트 문서는 나오지 않는다 | **측정하지 않았다** |

**후반 조건은 벡터 유사도가 담당하지 않는다.** `documents.project_id` 가
NOT NULL 이고 **리포지토리 계층에서 스코프를 강제**하는 것이 설계다
(`PRJ-08` · `관리/데이터구조_설계.md` 2절). 라우터에서만 검사하면 새 API 를
추가할 때 누락되므로 리포지토리에 둔 것이다.

이번 실험은 문서 5건을 한 코퍼스에 넣고 **필터 없이** 검색했다.
프로젝트 경계가 없는 조건이므로 이 항목은 애초에 재현되지 않았다.
**"미충족" 이 아니라 "측정 불가" 다.**

다만 실험에서 관찰한 것은 별개로 유효하다. **같은 프로젝트 안에 문서가 여럿
있으면 문서 간 혼동이 생기고, 그것은 `project_id` 필터로 막히지 않는다.**

```
"이 일에 잡힌 예산이 얼마인가"   기초과학연구원 공고를 물었는데
                                한국지역난방공사 준공정보를 가져왔다 (107,108,123…)

"두 문서가 어긋나면 어느 쪽이 이기나"   공고문을 물었는데
                                       우리 팀 결정사항을 가져왔다 (45,41,59…)
```

**문서 격리는 벡터 유사도로 되지 않는다.** 문서 ID 또는 사업 단위 필터가
검색 조건에 들어가야 한다. `RAG-05`(하이브리드 검색, P2)와 함께 설계할 일이다.

### 8.6 숫자·코드번호 검색은 벡터가 약하다 — `RAG-05` 실측 근거

3차 상세에서 `overlap` 실패 사례가 드러났다. **글자가 그대로 겹치는데도
1024 두 모델이 10위 안에 못 넣은 질의들이다.**

| 질의 | 정답 | bge-m3 | KURE-v1 | e5-small |
|---|---|---|---|---|
| `사업금액 578600000원` | 7 | **실패** | **실패** | 4위 |
| `공동수급불허 협상에의한계약` | 1 | **실패** | **실패** | 2위 |
| `입찰공고번호 100354-24002` | 62 | 2위 | 3위 | 4위 |
| `RHEL 라이선스 갱신 구매` | 96 | 2위 | 2위 | 2위 |

`사업금액 578600000원` 의 상위 결과가 `123,119,113,106,127` 이다.
**전부 준공정보의 예산금액 청크다.** 숫자를 물었는데 다른 숫자로 끌려간다.

기능명세서 `RAG-05` 완료 판정이 이것을 예상하고 있었다.

| ID | 우선 | 완료 판정 기준 | 비고 |
|---|---|---|---|
| `RAG-05` | P2 | **고유명사 · 코드번호 검색에서 벡터 단독보다 정확하다** | **`VIS-06` FTS 와 결합** |

**이번 측정이 그 근거를 실측으로 채웠다.** 공고번호·계약번호·금액이 많은
도메인이라 `RAG-05` 를 P2 로 둔 판단이 맞다. 벡터 단독으로는 코드번호를
1위로 못 올린다.

**키워드 쪽은 새로 만들지 않는다.** 비고가 `VIS-06` FTS 와 결합하라고 지정한다.
`VIS-06`(통합 검색 · PostgreSQL FTS · P2 · 보현)이 이미 계획에 있으므로
별도 검색 엔진을 도입하지 않고 같은 DB 안에서 합친다.

| 구성 요소 | 무엇으로 | 근거 |
|---|---|---|
| 벡터 쪽 | pgvector + KURE-v1 (1024) | 이 문서 8.1 · 8.2절 |
| 키워드 쪽 | **PostgreSQL FTS** (`VIS-06`) | `RAG-05` 비고 |
| 스코프 | `project_id` 리포지토리 강제 | `PRJ-08` · 8.5절 |

그리고 **e5-small 이 이 구간에서 가장 강하다.** `overlap R@10 = 39 / 39` 다.
작은 모델이 어휘 매칭에 강하다는 뜻이며, 이는 8.3절의 `no_overlap` 최하위와
같은 성질의 다른 얼굴이다. **하이브리드 검색을 만들 때 키워드 쪽 후보로
e5 를 쓰는 구성도 검토할 값이 있다.**

### 8.7 큰 청크는 `overlap` 질의로도 못 찾는다 — `RAG-01` 근거

실패한 `overlap` 질의의 정답 청크 크기를 보면 원인이 보인다.

| 정답 청크 | 글자 | 무엇이 들어 있나 |
|---|---|---|
| 1 | 438 | 나라장터 화면 덤프. **필드 20여 개가 한 덩어리** |
| 4 | 533 | 입찰진행 주의 · 보증금 · 발표순서 · 평가기관 · 평가비율 · 가격 |
| 7 | 448 | 입찰 주의 · 공고명 · 사업내용 · 사업기간 · 계약방법 · 사업금액 |

**청크 1 을 정답으로 둔 `overlap` 질의 두 개가 모두 실패했다.**
`공동수급불허 협상에의한계약` 과 `회계법인 업종을 등록한 업체` 다.
글자가 그대로 있는데도 못 찾는다. 필드 20여 개를 벡터 하나가 대표하니
특정 필드의 신호가 묻힌다.

**`RAG-01` 이 `element_type` 단위로 단락을 묶는 이유가 여기서 확인된다.**
화면 덤프를 글자 수로 자르면 이런 덩어리가 생긴다.
`ocr_elements` 의 구조 정보를 쓰면 필드 단위로 끊을 수 있다.

### 8.8 `top-k`는 5 이상이어야 한다

`no_overlap` `R@1`이 최고 12 / 39다. **1위로 맞추는 것은 세 번에 한 번.**
`R@5`에서 24개로 두 배가 된다. **본구현에서 `top-1`만 쓰면 의미 검색의 절반을 버린다.**

## 9. 색인 규모 실측 환산

이번 실측 속도로 실제 규모를 환산했다.

```
평균 청크 크기      236자        (29,996자 ÷ 127청크, 실측)
문서 1건 상한       45,000자     (MAX_EXTRACTED_CHARS)
문서 1건 청크 수    약 190개
```

| 대상 | 청크 | KURE-v1 (CPU) | e5-small (CPU) |
|---|---|---|---|
| 문서 1건 (45,000자) | 190 | 79초 | 7초 |
| `PER-01` 기준 10페이지 (추정 18,750자) | 약 79 | **33초** | 3초 |
| 데모용 20건 | 3,800 | 26분 | 2.4분 |

**10페이지를 18,750자로 잡은 근거는 약하다.** 중앙보훈병원 공고문 13,121자가
PDF 7장에 걸쳐 있어 장당 1,875자로 환산한 값이다. 원문 인쇄 페이지 번호는
13까지 나오므로 **장과 페이지가 일치하지 않는다.** 실제 페이지당 글자 수는
문서 종류마다 다르므로 이 행은 자릿수 감각으로만 쓴다.

### 9.1 `PER-01` 60초 — Worker 는 아직 코드에 없다

`Tasqra/DEVELOPMENT_GUIDE.md` 4.2절이 요청 내부 동기 처리를 폐기하기로 했다.

```
업로드 요청 -> 문서·작업 생성 -> 큐 등록 -> 즉시 응답
                                        └-> Worker 처리
```

> 오래 걸리는 OCR, 문서 추출, LLM 분석, 일괄 처리는 Worker 에서 실행한다.

**그런데 이것은 지향점이고 코드에는 없다.** Tasqra `backend/` 를 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| 코드에서 `celery` · `redis` · `BackgroundTasks` 검색 | **0건** |
| `requirements.txt` | celery · redis **없음** |
| `docker-compose.yml` 서비스 | `db` · `api` · `frontend` **3개뿐** (redis · worker 없음) |
| `upload_router.py` | 파일을 읽고 **곧바로** `service.upload_and_extract(...)` 호출 후 응답 |
| 작업 상태 · 진행률 테이블 | `tasks` · `jobs` **없음** (0001~0007 전체 확인) |
| `DEVELOPMENT_GUIDE` 체크리스트 | `[ ] Celery·Redis Worker 구성` — **미완료 표시** |

`SYS-02`(Celery + Redis)가 **P0 인데 미착수**다. 담당은 재정이다.

**그래서 지금 임베딩을 Worker 로 돌릴 수 없다.** 두 갈래가 된다.

| 선택 | 내용 | 문제 |
|---|---|---|
| A | `SYS-02` 완료를 기다린다 | 재정 담당 P0 에 블로킹된다 |
| B | **기존 관례대로 동기로 만든다** | 업로드·분석이 이미 동기라 일관된다. 대신 응답이 늘어진다 |

**B 가 현재 코드와 일관된다.** 업로드와 분석이 모두 동기이므로 임베딩만
비동기로 만들면 구조가 어긋난다. `SYS-02` 가 들어오면 셋을 함께 옮기면 된다.

`PER-01` 의 60초는 **현재 코드 기준으로는 응답 지연 그 자체다.**
Worker 가 생긴 뒤에야 처리 완료 시간이 된다.

그럼에도 예산은 여전히 빡빡하다. CPU 에서 임베딩만 33초면 OCR 과 LLM 분석이
쓸 시간이 27초 남는다. 스캔 PDF 10페이지 OCR 이 그 안에 끝나지 않는다.
**GPU 실행이 사실상 전제다.**

| 항목 | 값 |
|---|---|
| 임베딩 (KURE-v1 · CPU · 79청크) | 33초 |
| 남는 예산 | 27초 |
| 미니 프로젝트 실측 OCR (PaddleOCR) | **15,541ms = 15.5초** (문서 1건 기준) |
| 미니 프로젝트 실측 요약 · 분류 | 3.2초 + 1.6초 |

미니 프로젝트 수치는 문서 1건 기준이고 10페이지 스캔 PDF 는 더 든다.
**임베딩을 GPU 로 옮기거나 Worker 병렬화가 필요하다.**

또한 **작업 멱등성**을 고려해야 한다(같은 4.2절). `RAG-09` 검수 확정 시
재임베딩이 두 번 돌아도 청크가 중복 저장되지 않아야 한다.

### 9.2 질의 쪽은 문제가 없다

질의 임베딩은 한 건씩이라 검색 응답에는 영향이 거의 없다.
무거운 것은 색인 한 번뿐이다. **다만 모델 교체나 차원 변경으로 전체 재색인이
필요한 상황은 CPU에서 반나절 작업이다. 차원을 지금 확정하는 것이 그래서 중요하다.**

### 11.0 리비전 `0010` 보다 먼저 해야 할 것 — pgvector 가 설치되어 있지 않다

**DB 이미지에 pgvector 가 없다.** `CREATE EXTENSION vector` 를 넣어도 실패한다.

| 확인한 것 | 결과 |
|---|---|
| `docker-compose.yml` DB 이미지 | **`postgres:16-alpine`** — pgvector 미포함 |
| 마이그레이션에 `CREATE EXTENSION vector` | **없다** (0001~0007 전체 확인) |
| `requirements.txt` 에 `pgvector` 패키지 | **없다** |

세 가지가 선행되어야 `0010` 이 돌아간다.

| | 할 일 | 주의 |
|---|---|---|
| 1 | DB 이미지를 **`pgvector/pgvector:pg16`** 등으로 교체 | **`docker-compose.yml` 은 팀 공유 파일이다. 혼자 바꾸지 않는다** |
| 2 | `requirements.txt` 에 `pgvector` 추가 | SQLAlchemy 에서 `Vector` 타입을 쓰려면 필요하다 |
| 3 | `0010` 에서 `op.execute("CREATE EXTENSION IF NOT EXISTS vector")` | 확장 생성이 테이블보다 먼저다 |

**1번이 팀 합의 사항이다.** 작업 규칙에 "`.yml` 처럼 팀 전체가 공유하는 파일은
혼자 바꾸지 않는다" 가 있다. 이미지를 바꾸면 세 사람 모두 컨테이너를 다시
만들어야 하므로 미리 알려야 한다.

`0008`(`ocr_exclusion`) 머지 시점과 겹치지 않게 잡는 것이 좋다.
**이미지 교체와 리비전 추가가 같이 오면 다른 사람 환경이 두 번 깨진다.**

### 11.1 리비전 번호 — `versions/` 폴더로 확인한 값

**`관리/` 문서가 아니라 Tasqra 의 `backend/migrations/versions/` 가 정본이다.
그리고 머지되지 않은 브랜치까지 봐야 한다.**

| 리비전 | 내용 | 상태 | 확인한 곳 |
|---|---|---|---|
| `0007` | `analysis_artifacts` | main 머지됨 | `origin/main` |
| **`0008`** | **`ocr_exclusion`** (`ocr_elements.is_excluded`) | **재정 담당 · 머지 전** | **`origin/document-detail`** |
| `0009` | `amount_items.unit_price` · `category` · `documents.document_type` CHECK 9종 | 보현 예정 | 문서상 `0008` — 한 칸 밀림 |
| **`0010`** | **pgvector · `document_chunks` `vector(1024)`** | **이 문서로 착수 가능** | 문서상 `0009` — 한 칸 밀림 |

`0008` 의 실제 내용은 다음과 같다.

```python
revision      = "20260812_0008"
down_revision = "20260811_0007"

op.add_column("ocr_elements",
              sa.Column("is_excluded", sa.Boolean(), nullable=False,
                        server_default=sa.false()))
```

**따라서 `down_revision` 을 `20260811_0007` 로 두면 head 가 둘이 되어
`alembic upgrade head` 가 실패한다.** 컨테이너 기동 명령이 그것이라 앱이 아예
뜨지 않는다. 4회 충돌 때와 같은 실패 방식이다.

| 착수 시점 | `down_revision` |
|---|---|
| 재정 `0008` 머지 후 · `0009` CHECK 를 먼저 만들면 | `20260812_0009` |
| 재정 `0008` 머지 후 · pgvector 를 먼저 만들면 | `20260812_0008` |
| 머지 전에 만들면 | **만들지 않는다.** head 가 갈라진다 |

### 11.2 갱신이 필요한 문서 4곳

`0008` 이 `ocr_exclusion` 에 점유되면서 아래가 한 칸씩 어긋났다.

| 문서 | 위치 | 적힌 값 | 실제 |
|---|---|---|---|
| `관리/산출물_변경대기_목록.md` | D절 제목 | 리비전 `0008` | `0009` |
| `관리/산출물_변경대기_목록.md` | B-3 | 리비전 `0009` | `0010` |
| `관리/기능명세서.md` | `RAG-03` | 리비전 `0009` | `0010` |
| `관리/DocFlow_DB.dbml` | 하단 마이그레이션 순서 | 예정 `0008` | `0009` |

**이 결과서 작성 중 같은 실수를 두 번 했다.**
처음에는 이전 논의의 번호를 그대로 옮겨 적었고, 다음에는 커밋된 `관리/` 문서만
보고 `versions/` 를 확인하지 않았다. 세 번째에 실제 파일을 열어 확인했다.

**교훈은 리포에 이미 적혀 있던 것과 같다** — 브랜치를 딸 때 다른 브랜치의
`versions/` 를 보지 않으면 git 이 충돌로 잡지 않는다. `관리/` 문서도 낡을 수 있으므로
번호는 항상 `versions/` 로 확인한다.

## 12. LLM 모델 비교와의 경계 — 판단은 세현, 재는 자는 보현

**이 문서는 임베딩 모델만 다룬다.** LLM 모델 선정 판단은 별도 문서로 분리한다.
**다만 측정 도구는 이 문서의 담당 영역이다.**

| | 담당 | 상태 |
|---|---|---|
| 임베딩 모델 선정 | 보현 | **이 문서** |
| LLM 모델 선정 판단 | 세현 | 진행 중 (HyperCLOVA X 2종 · 데이터 주입 전) |
| **`ANL-17` 평가셋 기반 정확도 측정 자동화** | **보현** | **이번 하네스가 원형** |

### 12.0 `ANL-17` — 이번 도구가 그 원형이다

기능명세서 8절이 `ANL-16`·`ANL-17` 담당을 보현으로 지정하고 있다.

> `ANL-17` 평가셋 기반 정확도 측정 자동화 — P1
> 정답 데이터와 대조해 정확도가 수치로 나온다.
> **모델·프롬프트를 바꿔도 같은 자로 잰다. 세현님 모델 비교에 직접 쓰인다**

이번에 만든 세 파일이 그 골격이다.

| 이번에 만든 것 | `ANL-17` 에서 하는 일 | 바뀌는 부분 |
|---|---|---|
| `queries.csv` (질의 · 정답 · 종류) | 평가셋 형식 | 정답이 청크 번호 → **기대 출력값** |
| `check_queries.py` | **채점 전 평가셋 검증** | 그대로 쓸 수 있는 발상 |
| `run_eval.py` | 채점과 지표 산출 | 지표가 `R@k` → 정확도 · 일치율 |

**`ANL-17` 이 P1 이고 `RAG-10` 이 P2 다.** 즉 **재는 자를 먼저 만든다.**
같은 자로 재지 않으면 모델을 바꿨을 때 좋아진 것인지 알 수 없다.

특히 `check_queries.py` 의 발상이 그대로 옮겨간다. **`run_eval.py` 가 못 쓰는
행을 조용히 건너뛴 것처럼, 정확도 측정도 잘못된 정답 데이터를 조용히 넘기면
숫자가 오염된다.** 이번에 78문항 중 5문항이 측정 불가였고 3문항이 라벨 위반이었다.
그것을 사람 눈으로는 못 찾았다.

**세현님 시험에 이 도구를 쓰려면 다음이 필요하다.**

| | 필요한 것 | 왜 |
|---|---|---|
| 1 | 정답 데이터 형식 합의 | 요약은 정답이 하나가 아니다. 무엇을 일치로 볼지 정해야 한다 |
| 2 | 분류는 그대로 쓸 수 있다 | 7종 중 하나이므로 정답이 명확하다 (`ANL-02`) |
| 3 | 요약은 지표를 따로 정해야 한다 | 사람 판정이 필요하다. 16절 비기능 요구가 `USER_CORRECTED` 비율을 쓰기로 했다 |

**요약 정확도를 재는 방식이 이미 정해져 있다는 점을 짚어둔다.**
기능명세서 16절이 "별도 정답 데이터를 만드는 대신 **사람이 AI 판별을 고친
비율**을 쓴다" 고 했다. 즉 분류는 `document_type_source=USER_CORRECTED` 비율로
잰다. 요약은 그 방식이 없으므로 세현님과 합의가 필요하다.

### 12.1 왜 분리하는가

선택 기준이 겹치지 않는다. 한 문서에 넣으면 "무엇을 왜 골랐나"가 흐려진다.

| | 임베딩 모델 | LLM |
|---|---|---|
| 핵심 지표 | `R@5` · `MRR` (기계 채점) | 출력 품질 (**사람 판정 필요**) |
| 결정에 묶이는 것 | **DB 컬럼 차원** | 프롬프트 · 토큰 예산 |
| 비용 구조 | 색인 1회 | **호출마다 과금** |
| 되돌리기 비용 | 재임베딩 반나절 | 설정 한 줄 |
| 평가셋 성격 | 질의와 정답 청크 | 입력 문서와 기대 출력 |

### 12.2 임베딩을 먼저 확정하는 것이 LLM 시험의 전제다

RAG 파이프라인에서 검색과 생성은 다른 단계다.

```
질의 -> [임베딩 검색] -> 청크 k개 -> [LLM 생성] -> 답변
         이 문서가 정한 것            세현 담당
```

**임베딩을 하나로 고정해두면 LLM 시험에서 들어가는 청크가 같아지므로
LLM 차이만 깨끗하게 측정된다.** 변수 통제다.

반대로 임베딩과 LLM을 같이 바꾸면 출력이 나빠졌을 때 검색이 잘못 가져온
것인지 생성이 잘못한 것인지 가릴 수 없다. **그래서 순서가 임베딩 먼저다.**

**그리고 임베딩은 검색 전용이 아니다.** 기능명세서 14절 도입부에 이렇게 적혀 있다.

> 임베딩은 금액 전용이 아니다. 요약·분류·검색이 같은 파이프라인을 쓴다.
> 특히 45,000자 문서를 요약할 때 무엇을 프롬프트에 넣을지 고르는 데 쓰인다.

`RAG-07`(프롬프트 컨텍스트 조립)이 토큰 예산 안에서 청크를 고르는데,
그 고르는 근거가 임베딩이다. **즉 임베딩 품질이 요약 품질의 상한을 정한다.**
LLM 이 아무리 좋아도 엉뚱한 청크가 들어가면 요약이 틀린다.

두 시험은 독립적으로 진행하되 **종속 관계는 한 방향이다.**

```
임베딩 품질  ->  RAG-07 이 고른 청크  ->  LLM 요약 품질
```

### 12.3 LLM 결과서에 담겨야 할 것

| | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | 모델명 · 버전 · **학습 여부와 학습 데이터** | 학습시킨 모델은 데이터가 변수다. 명시해야 재현된다 |
| 2 | 어느 작업에 썼나 (요약 · 분류 · 금액 추출) | 작업마다 기준이 다르다 |
| 3 | 평가 방법 (사람 판정 · 정답셋 · 지표) | 근거의 강도를 정한다 |
| 4 | 수치 (정확도 · 응답시간 · 토큰 · 비용) | 비교 표를 만든다 |
| 5 | 실패 사례 | 한계를 적는다 |
| 6 | 실행 환경 (**GPU 사양**) | `PER-01` 판단에 필요 (9절) |
| 7 | 선정 · 탈락 결론과 이유 | 결정 기록 |

**1번을 특히 주의한다.** 같은 모델을 서로 다른 데이터로 학습시켜 비교하면
모델 차이가 아니라 학습 데이터 차이를 재는 것이 된다. 두 조건 중 하나만
바꿔야 인과가 성립한다.

**6번은 이 문서 9절과 직결된다.** GPU 사양을 알면 `PER-01` 10페이지 60초가
가능한지 계산할 수 있다. 현재 CPU 기준으로는 임베딩만 33초다.

## 13. 팀 확인 필요 사항

GPU가 없다는 것은 임베딩만의 문제가 아니다.

| | 확인할 것 | 왜 |
|---|---|---|
| 1 | 세현 장비 GPU 사양 | 없으면 LLM도 CPU. `PER-01` 60초가 위험하다 |
| 2 | 모델을 각자 PC에서 돌리나, 공용 장비인가 | 각자면 영상 촬영을 누구 PC로 하나 |
| 3 | **임베딩을 어디서 돌리나** | 시험자 PC에 GPU가 없다. 최종 색인 장비를 정해야 한다 |
| 4 | `PER-01` 60초가 임베딩까지 포함하는가 | 9절 판단이 달라진다 |
| 5 | **HyperCLOVA X "학습" 이 파인튜닝인가** | 기능명세서 17절과 충돌 가능 (아래) |
| 6 | HyperCLOVA X 를 상용 API 로 쓰나 로컬로 띄우나 | 18절 25번 결정과 관계 |

**3번이 8.1절 결정의 전제다.** 공용 GPU 장비가 있으면 1024차원 운용에
문제가 없다. 없으면 색인 시간을 일정에 반영해야 한다.

### 13.1 파인튜닝 — 기능명세서와 어긋날 수 있다

기능명세서 **17절 "하지 않을 것"** 에 이렇게 적혀 있다.

| 안 함 | 이유 |
|---|---|
| **파인튜닝** | 20일에 자리가 없다. 프롬프트 + 구조화 출력으로 목표 달성 가능 |

그런데 LLM 시험이 "HyperCLOVA X 두 종을 학습시켜서 비교" 로 진행되고 있다.
**그 "학습" 이 파인튜닝이면 17절 결정과 충돌한다.**

| 무엇인가 | 17절과의 관계 |
|---|---|
| 파인튜닝 (가중치 갱신) | **충돌.** 17절을 고치거나 시험 범위를 조정해야 한다 |
| 프롬프트 · 예시 주입 (few-shot) | 충돌 없음. 17절이 권하는 방식이다 |
| RAG 로 문서를 넣어주는 것 | 충돌 없음. 그게 `RAG-07` 이다 |

**어느 쪽인지 확인해야 한다.** 파인튜닝이라면 일정(구현 20일)과 재현성 양쪽에
영향이 있다. 또한 기능명세서 18절 25번이 **"상용 API 유지 권장"** 으로
정리되어 있는데(1조가 Gemma 1B 에서 언어 쏠림을 겪은 사례), 로컬 학습 모델을
쓰는 방향이면 그 결정도 다시 봐야 한다.

**이 결과서가 판단할 사항은 아니다. 팀 안건으로 올린다.**

### 13.2 이 결과서 판단의 상한 — v0.3 기획안을 보지 못했다

`Tasqra/DEVELOPMENT_GUIDE.md` 1절이 기준의 우선순위를 정하고 있다.

```
DocFlow 통합 기획안 v0.3
  -> 개발 가이드
  -> API·DB 계약
  -> 구현 코드와 주석

규칙이 서로 충돌하면 위에 있는 기준을 따른다.
```

**최상위 기준인 v0.3 기획안 파일이 두 레포 어디에도 없다.**
`관리/` 문서 다섯 개가 v0.3 을 인용하고 있을 뿐이다.
따라서 이 결과서는 **2순위 이하 문서만 근거로 삼았다.** v0.3 에 다른 지시가
있으면 그쪽이 이긴다.

### 13.3 확인 필요 — 검색의 구현 계층

`DEVELOPMENT_GUIDE.md` 2절이 기능을 4계층으로 나누고 있다.

| 계층 | 내용 |
|---|---|
| 1 | 공통 기반 — 인증 · 프로젝트 스코프 · 비동기 큐 · OCR 요소 저장 |
| 2A | 액션아이템 추출과 태스크 자동화 |
| 2B | OCR 박스 검수와 확정 텍스트 |
| **4** | **확장 기능 — 대시보드 · 검색 · 일괄 처리 · 리포트 · 폴더 감시** |

> 현재 개발 범위가 어느 계층인지 먼저 확인하고, **다음 계층 기능을 섞어
> 구현하지 않는다.**

**검색이 4계층(확장)에 있는데 기능명세서는 `RAG-01`·`02`·`03`·`04`·`07`·`08`·
`09` 를 P1 로 둔다.** 두 기준이 어긋난다.

| 기준 | 검색의 위치 |
|---|---|
| `DEVELOPMENT_GUIDE` 2절 | 4계층 확장 기능 |
| `기능명세서` 14절 | **P1 — 차별화 핵심** |

우선순위 규칙상 `DEVELOPMENT_GUIDE` 가 기능명세서보다 위이므로
**문서만 보면 검색을 나중에 해야 한다.** 다만 기능명세서 14절이 도메인을
공공 SI 로 좁힌 뒤 근거가 바뀌었다고 명시하고 있어, **개발 가이드 쪽이 낡은
것일 가능성이 크다.**

**어느 쪽이 맞는지 확인해야 한다.** 이 결정이 `0010` 착수 시점을 정한다.

### 13.4 `VIS-07` 과 `RAG-04` 가 같은 기능을 두 번 정의한다

| ID | 기능 | 우선 | 담당 | 선행 |
|---|---|---|---|---|
| `VIS-07` | 시맨틱 검색 (pgvector) | **P3** | 보현 | `VIS-06` |
| `RAG-04` | 의미 검색 | **P1** | 보현 | `RAG-03` |

**같은 것이다.** 그런데 우선순위가 P3 과 P1 로 다르고, `VIS-07` 은 완료 판정
기준이 비어 있다.

`RAG` 영역이 신규로 추가되면서(기능명세서 14절 — "도메인을 공공 SI·용역으로
좁힌 뒤 정식 범위가 됐다") **`VIS-07` 이 정리되지 않고 남은 것으로 보인다.**
15절 폐기 목록에도 없다.

기능명세서 머리에 규칙이 있다.

> ID 는 확정 후 변경하지 않는다. 폐기된 기능도 번호를 재사용하지 않고 `폐기` 로 남긴다.

**따라서 `VIS-07` 을 지우지 않고 `폐기` 로 표시하거나, 성격을 바꿔야 한다.**
`VIS-06` 을 선행으로 두고 있으니 **"검색 화면에 시맨틱 결과를 얹는 UI"** 로
성격을 바꾸는 쪽이 자연스럽다. `RAG-04` 는 검색 자체이고 `VIS-07` 은 화면이다.
15절에 이미 "폐기하지 않고 성격만 바꾼 것" 표가 있으므로 거기에 한 줄 추가하면 된다.

### 13.5 API 계약서에 검색 엔드포인트가 없다

엔드포인트 50개를 확인했는데 `RAG` 영역에 대응하는 것이 하나뿐이다.

| 기능 | 우선 | 대응 엔드포인트 |
|---|---|---|
| `VIS-06` 통합 검색 | P2 | `GET /api/projects/{pid}/search` |
| **`RAG-04` 의미 검색** | **P1** | **없음** |
| **`RAG-08` 근거 스니펫 연결** | **P1** | **없음** |
| **`RAG-12` 유사 사업 단가 선례 검색** | P2 | **없음** |
| `RAG-01`·`02`·`03`·`07`·`09` | P1 | 내부 로직이라 불필요 (정상) |

**`RAG-04` 가 P1 인데 API 계약이 없다.** `RAG-08` 도 같다.
`0010` 을 만든 직후 구현할 대상인데 계약이 비어 있으면 프런트와 맞출 수 없다.

`VIS-06` 의 `search` 에 파라미터를 얹는 방식(`?mode=semantic`)과 별도 경로를
두는 방식(`/search/semantic`) 중 하나를 골라야 한다. `RAG-05` 가 둘을 결합하는
것이므로 **하나의 엔드포인트에 모드를 두는 쪽이 나중에 합치기 쉽다.**

**초안을 만들어 올릴 수 있다. 지시해주면 쓰겠다.**

#### 덧붙여 — 계약서에 중복 기재가 있다

`31`~`34` 번(`batch-jobs` 4건)이 **두 번 적혀 있다.** 번호도 31~34 로 같다.
복사 중 생긴 것으로 보이며 실제 엔드포인트는 50개가 아니라 46개다.

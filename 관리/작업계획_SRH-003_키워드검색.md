## 확인받을 것 — 셋

### ① 마이그레이션이 팀 공유 파일이다 ⚠ 가장 중요

키워드 검색은 **새 마이그레이션이 필요하다.** 지금 레포에 전문검색 기반이 하나도
없다(확인함) — `pg_trgm`·`unaccent`·`tsvector`·GIN/GiST 가 마이그레이션·모델·
서비스 어디에도 없다. `CREATE EXTENSION` 은 `0011` 의 `vector` **한 줄뿐**이다.

그래서 이런 영향이 있다.

| | 내용 |
|---|---|
| 현재 head | `20260819_0015_amount_item_fields` |
| 새로 붙일 것 | `20260820_0016_chunk_text_search` (`down_revision = "20260819_0015"`) |
| **다른 팀원 영향** | **각자 `alembic upgrade head` 를 돌려야 한다.** 안 돌리면 키워드 검색이 500 |
| **충돌 위험** | 재정님·세현님이 같은 시간에 `0016` 을 만들면 **head 가 갈라진다** |

> **먼저 팀에 알려야 한다.** "0016 을 내가 쓴다" 를 말해 두지 않으면 번호가 겹친다.
> 리비전 번호 충돌은 전에도 있었다(인수인계 8절 · `0001-fix-duplicate-revision-0007.patch`).

### ② 새 엔드포인트로 갈까, 기존 것을 확장할까

| | 방법 | 평가 |
|---|---|---|
| **A** | **`POST /api/search/keyword` 를 새로 만든다** | **추천.** `SRH-001` 이 이미 구현됨이라 기존 계약을 안 건드린다. 회귀 위험 0 |
| B | `POST /api/search` 에 `mode` 파라미터를 더한다 | 엔드포인트가 하나로 유지되지만, 구현된 기능의 요청 스키마를 고친다. 프론트도 같이 고쳐야 한다 |

`SRH-004` 하이브리드가 나중에 둘을 합치므로, **그때 `/api/search/hybrid` 를 하나 더
만드는 편이 세 방식을 나란히 비교하기 쉽다.** 셋을 같은 엔드포인트에 밀어넣으면
어느 방식의 점수인지 응답에서 구분해야 한다.

### ③ 점수를 어디에 담을까

`SearchResultItem.similarity` 는 **"코사인 유사도. 1.0 이 가장 가깝다"** 로
스키마 주석에 못박혀 있다. 키워드 점수를 그 필드에 담으면 뜻이 달라진다.

| | 방법 | 평가 |
|---|---|---|
| **A** | **`similarity` 를 그대로 쓰고 `match_kind` 를 더한다** | **추천.** `SRH-004` 가 두 결과를 한 순위로 합칠 때 같은 모양이어야 섞을 수 있다. 필드가 하나 늘 뿐이다 |
| B | 키워드 전용 응답 스키마를 새로 만든다 | 뜻은 정확하지만 하이브리드에서 두 모양을 합치는 코드를 또 써야 한다 |

## 어떻게 만들 것인가

### 매칭 방식 — `pg_trgm` + `ILIKE`

한국어는 PostgreSQL 에 **기본 전문검색 설정이 없다.** 그래서 선택이 갈린다.

| 방식 | 되는 것 | 안 되는 것 |
|---|---|---|
| `tsvector` (`simple` 설정) | 공백 단위 토큰 매칭 | **조사에 걸린다** — `계약금액은` 과 `계약금액` 이 다른 토큰이 된다 |
| **`pg_trgm` + `ILIKE`** | **부분 문자열 정확 매칭.** 조사·붙여쓰기에 안 걸린다 | 오타 교정은 `similarity()` 를 따로 써야 한다 |

**완료 판정이 방식을 정한다** — *"고유명사·숫자·문서번호처럼 **정확한 문자열**로
문서와 조각을 찾는다"*. 정확한 부분 문자열이 목적이므로 `ILIKE` 가 맞고,
`pg_trgm` 의 GIN 인덱스(`gin_trgm_ops`)가 그 `ILIKE` 를 가속한다.

> 명세 비고가 *"문서 목록의 `q` 필터(`ilike`)와는 다른 기능"* 이라고 한 것은
> **매칭 방식이 아니라 단위**를 말한 것이다. 문서 목록은 문서 단위로 찾고, 이건
> **조각 단위**로 찾아야 근거 인용(`SRH-002-2`)이 된다.

### 재사용할 것 — 새로 만들지 않는다

| 기존 것 | 왜 그대로 쓰나 |
|---|---|
| `SearchService._resolve_scope` | 권한·범위의 **유일한 진실**. 멤버 아닌 프로젝트를 404 로 막는다. 따로 구현하면 권한 구멍이 생긴다 |
| `ChunkRepository._scope_condition` | 하나면 `=`, 여럿이면 `IN`. `document_chunks` **자기 컬럼**으로 걸어야 한다(리비전 0014 전제) |
| `search_by_vector` 의 조인·반환 모양 | `(청크, 파일명, 프로젝트 id, 프로젝트 이름, 점수)`. N+1 방지 규약 |
| `SearchResultItem`·`SearchResponse` | 응답 계약. `MAX_SEARCH_LIMIT`(50)·`MAX_SCOPE_PROJECTS`(100) 상수도 |
| `BusinessError(ErrorCode.PROJECT_NOT_FOUND)` | 403 이 아니라 **404**. 남의 프로젝트 존재를 숨긴다 |

### 함정 — `embedding_model` 필터

키워드 검색에 임베딩 모델은 **의미가 없다.** 그런데 **빼면 안 된다.**

의미 검색은 `WHERE embedding_model = 현재 모델` 로 **우연히 중복을 피하고 있다.**
같은 문서를 두 모델로 청킹해 두면 같은 본문이 여러 행으로 있다. 키워드 검색에서
그 조건을 빼면 **같은 텍스트가 결과에 여러 번 나온다.**

→ **현재 모델로 필터를 유지한다.** `settings.EMBEDDING_MODEL` 이 아니라
임베딩 클라이언트의 `model_name` 을 쓴다(의미 검색과 같은 값이어야 한다).

### 테스트

**검색 테스트 파일이 지금 하나도 없다**(`test_search*.py` 없음, `conftest.py` 없음).
레포 관례는 **DB 를 띄우지 않는 두 방식**이다.

- `MagicMock` + `SimpleNamespace` 로 서비스만 조립 (`test_document_list_queries.py`)
- 순수 로직은 `sys.path` 를 끼워 단독 실행 (`test_chunking.py`)

스니펫 자르기와 범위 결정은 이 방식으로 DB 없이 검증할 수 있다.
**ILIKE 가 실제로 인덱스를 타는지는 DB 가 필요하다** — `explain_search()` 와 같은
방식으로 확인한다.

## 곁에서 발견한 것 — 확인 필요

**팀 레포 코드가 개인 레포에만 있는 파일을 가리킨다.**

| 위치 | 내용 |
|---|---|
| `backend/app/core/config.py:92` | *"embed_server.py 의 max_seq 를 함께 봐야 한다"* |
| `backend/app/services/chunking.py:77` | *"도구/embed_server.py 의 DEFAULT_MAX_SEQ"* |

`embed_server.py` 는 **`deliver/도구/` 에 있다.** 팀 레포에는 없다. 다른 팀원이
그 주석을 읽고 파일을 찾을 수 없다. 그리고 `SYS-002-4 임베딩 모델 서빙 경로 확정`
이 **미결**이라, 다른 팀원은 실제 모델로 검색을 돌릴 방법이 없다
(`USE_FAKE_EMBEDDING` 기본값이 `True` 라 가짜 벡터로는 돌아간다).

**이건 이번 작업 범위가 아니다.** 다만 키워드 검색은 임베딩이 필요 없으므로,
**다른 팀원이 처음으로 실제 검색을 돌려 볼 수 있는 기능**이 된다.

### 검색을 방식별 화면으로 나누지 않았다

`SearchView` 의 탭은 `aria-label='찾는 대상'` 으로 **무엇을 찾는가**(문서 내용 /
과거 단가 선례)로 갈린다. 여기에 "키워드" 를 넣으면 **어떻게 찾는가**라는 다른 축이
섞여, 사용자가 *"내가 지금 단가를 찾나 키워드를 찾나"* 를 판단해야 한다. 성립하지
않는 질문이다.

근거 셋 — 화면정의서 `HOME-09` 배너가 *"본문까지 통합 검색"* 이라고 쓴다 ·
`SRH-003` 의 구판 ID 가 `VIS-06 통합 검색` 이다 · `SRH-004` 가 명세에 있는 이유가
이것이다.

### 왜 점수를 더하지 않고 순위로 합쳤나 (RRF)

두 점수의 스케일이 다르다. **실측으로 확인했다** —
`word_similarity`: 정확일치 `1.0` · 조사붙음 `0.8` · 불일치 `0`.
코사인 `0.8`("방향이 비슷")과 트라이그램 `0.8`("조사가 붙음")은 다른 뜻이라
더하거나 크기를 비교하면 근거 없는 숫자가 나온다.

RRF 는 점수를 버리고 순위만 쓴다 — `Σ 1/(k+순위)` · `k=60`. **두 방식이 동의하는
결과가 자연히 위로 온다**: 한쪽 1등(`1/61`=0.0164) < 양쪽 3등·5등(`1/63+1/65`=0.0313).

### 한국어라서 `tsvector` 를 안 썼다

PostgreSQL 에 한국어 전문검색 설정이 없다. `simple` 설정은 공백으로만 토큰을
나눠서 `계약금액` 과 `계약금액은` 이 다른 토큰이 된다. 트라이그램은 글자 3개씩
겹쳐 보므로 조사에 걸리지 않는다. 완료 판정이 *"고유명사·숫자·문서번호처럼
**정확한 문자열**"* 이라 부분 문자열 매칭이 목적에 맞다.

## 잡은 실제 버그 다섯

| | 무엇 | 어떻게 찾았나 |
|---|---|---|
| 1 | **`유사도 N%` 가 키워드 결과에서 틀린 값** — `similarity` 의 뜻이 `match_kind` 에 따라 다르다 | 화면 작업 중 스키마 주석을 읽다가 |
| 2 | **`최고 N%` 가 RRF 순서에서 틀림** — *"첫 조각이 가장 가깝다"* 전제가 깨진다 | 같음 |
| 3 | **이모지·확장 한자에서 강조가 깨짐** — 파이썬 코드포인트 vs JS UTF-16 코드유닛 | **서버 offset 을 JS 로 잘라 보는 교차 검증** (`\ude42` 서로게이트 반쪽이 잘렸다) |
| 4 | **`ILIKE` 와일드카드 미이스케이프** — `%` 하나로 조건이 사라져 전체가 걸린다 | 코드를 쓰면서 |
| 5 | **한 청크 안의 중복 문장이 안 걸러짐** — 표의 같은 행이 반복되면 예산 낭비 | 테스트가 실패해서 |

3번은 재현까지 했다. 조달 문서에 이모지는 드물지만 **확장 한자(`𠀋`)는 인명·지명에
나올 수 있고 OCR 오인식도 있다.** 서버 offset 을 먼저 믿되 **그 자리에 검색어가
있는지 확인하고 어긋나면 직접 찾도록** 고쳤다(`usableOffset`).

### ORM 모델이 풀어 준 것

`decisions` 테이블은 리비전 0007 로 **DB 에 있었지만 ORM 모델이 없어서 코드가 다룰 수
없었다.** 그래서 대시보드가 결정사항을 세지 못하고 산출물도 못 만들었다.

풀린 P1 넷 — 생성 대상 미리보기 `DLV-001-2` · 결정사항 대장 `DLV-003-1` ·
다음 회의 안건 `DLV-003-2` · 생성 이력·다운로드 `DLV-003-3`.

**`완료 태스크` 는 여전히 못 센다** — `tasks` 테이블 자체가 없다(`TSK-001-1` 재정님).
대시보드 `open_tasks = null` 과 같은 이유다.

> **`status` 와 `decision` 을 섞지 않는다.** 둘 다 `PENDING` 값을 가져 헷갈린다.
> `status` 는 결정 자체의 상태(`DECIDED`/`PENDING`/`REVERSED`), `decision` 은 AI
> 제안의 승인 여부다. **다음 회의 안건이 모으는 것은 `status='PENDING'`** 이다.

### BM25 — 리랭커의 대체가 아니다

세현님이 물어온 것. **BM25 는 후보를 만드는 단계(①)의 점수 함수**이고 리랭커는
그 뒤(③)에서 다시 줄 세우는 단계라 하는 일이 다르다.

붙일 자리가 두 곳인데 값이 다르다.

| | 값 |
|---|---|
| 청크 키워드 검색 | **작다.** 한 덩어리로 찾는 경우가 많아 **IDF 가 순서를 바꾸지 않는다** |
| **검색 앞의 문서 선택 단계** | **크다.** 문서 전체를 대상으로 여러 단어 질의를 받으니 IDF·길이 정규화가 제 값을 한다. **모델이 필요 없어 메모리 문제도 없다** |

도입 비용 — PostgreSQL 에 BM25 가 내장되어 있지 않다(내장 `ts_rank` 는 IDF 가 없다).
`pg_search`(ParadeDB) 나 `pg_textsearch`(Tiger Data) 확장이 필요하고, 우리 이미지
`pgvector/pgvector:pg16` 에 없다. **이미지를 바꾸면 팀 전원이 로컬 데이터를 잃는다**
(`docker-compose.yml` 주석의 경고). 한국어 형태소 분석기 문제도 그대로 남는다.

# DocFlow 기능명세서

본프로젝트 전체 기능을 한 문서에 모은 것이다. 출처는 다섯 개다.

| 출처 | 반영한 것 |
|---|---|
| 목업 (박세현) | 화면에 실제로 그려진 요소 |
| `기획안_v0.1` · `착수기획서_v1.0` (박세현) | 우선순위 · 역할 · 로드맵 |
| `기능 확장 아이디어` 3모드 (최재정) | 일반 · 검수 · 일괄 처리 |
| `OCR-DB 설계안` (최재정) | 검수 기능이 요구하는 데이터 |
| 미니 프로젝트 코드 | 이미 구현된 것 |

WBS · 통합테스트 시나리오 · 화면정의서는 이 문서의 **기능 ID 를 그대로 인용**한다.
ID 는 확정 후 변경하지 않는다. 폐기된 기능도 번호를 재사용하지 않고 `폐기` 로 남긴다.

DB 스키마는 `관리/DocFlow_DB.dbml`, 설계 의도는 `관리/데이터구조_설계.md` 를 본다.

## 0. 읽는 방법

### 우선순위

| 표기 | 뜻 | 판단 기준 |
|---|---|---|
| **P0** | MVP 필수 | 없으면 "팀 도구" 가 성립하지 않는다 |
| **P1** | 차별화 핵심 | 이게 우리 제품의 주장이다. 발표 데모의 중심 |
| **P2** | 확장 | 시간이 남으면. 없어도 데모가 성립한다 |
| **P3** | 향후 | 발표에서 **"향후 개선사항"** 으로 배치한다 |

### 상태

`기존` 미니 프로젝트에서 구현 완료 · `확장` 기존 코드에 추가 · `신규` 새로 만든다

### 담당

`세현` 박세현 · `재정` 최재정 · `보현` 김보현 · `공통` 셋이 나눠 맡음

### 완료 판정 기준

**모든 P0 · P1 에 판정 기준을 붙였다.** 이 문장이 그대로 통합테스트 시나리오의
기대결과가 된다. 미니 프로젝트에서 산출물이 코드 프리즈 뒤로 몰린 원인이 판정
기준을 나중에 쓴 것이었다.

## 1. 제품이 무엇을 만드는가 — 흐름

```
문서 입력 → 추출·OCR 검수 → 분석(분석기 4개 병렬) → 조각 → 산출물
   세현        재정                  보현            보현     보현
 (그릇)      (입력 품질)                          (조각)   (출력물)
```

**태스크 보드는 중간 산물이고 출력물은 문서다.** 미니 프로젝트에서 우리가 손으로
만든 것(이슈 46건 · 결정사항 29건 · 주간 보고 · WBS)을 자동으로 만드는 것이
`DLV` 영역이다.

폐기 6건은 위 집계에 넣지 않는다. 14절에 따로 남긴다.

> 집계는 `도구/_build_feature_spec.py` 가 항목별 우선순위에서 직접 센 값이다.
> 손으로 센 값과 어긋나면 스크립트 출력을 정본으로 한다.

**P0+P1 이 80개, 구현은 20일이다.** 다 못 한다. 그래서 이 문서는 **덜어내기 목록이
아니라 묶기 목록**으로 쓴다. 같은 골격을 쓰는 기능을 함께 만들면 두 번째가 싸다.

| 묶음 | 기능 | 왜 함께 |
|---|---|---|
| **제안 골격** | `ANL-03` `ANL-14` `ANL-15` `AMT-01` `TSK-03`~`TSK-08` | 제안 카드 · 승인 · 태스크 등록 UI 를 공유한다. 분석기만 갈아 끼운다 |
| **산출물 골격** | `DLV-01`~`DLV-10` | 기간 필터 · 파일 생성 · 이력이 하나로 묶인다. 종류만 늘린다 |
| **검수 골격** | `REV-01`~`REV-07` `REV-16`~`REV-18` | 박스 표시와 텍스트 수정이 하나로 묶인다 |
| **스코프** | `AUTH-*` `PRJ-*` | 인증 없이 스코프가 성립하지 않는다 |

## 3. A. 계정·권한 `AUTH` — 담당 세현

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `AUTH-01` | 회원가입 | 신규 | P0 | 이메일 중복 시 409. 비밀번호는 해시로만 저장되고 응답에 포함되지 않는다 |
| `AUTH-02` | 로그인 | 신규 | P0 | 올바른 자격으로 access · refresh 토큰 발급. 틀리면 401 |
| `AUTH-03` | 내 정보 조회 | 신규 | P0 | 유효 토큰으로 본인 정보 반환. 만료 토큰은 401 |
| `AUTH-04` | 토큰 갱신 · 로그아웃 | 신규 | P0 | refresh 로 access 재발급. 로그아웃 후 해당 refresh 는 재사용 불가 |
| `AUTH-05` | 인증 의존성 `get_current_user` | 신규 | P0 | 토큰 없이 보호된 엔드포인트 호출 시 401. **모든 프로젝트 스코프 API 에 적용됨을 목록으로 확인** |
| `AUTH-06` | SSO | 신규 | P3 | — |

**`AUTH-05` 가 핵심이다.** 개별 라우터에서 검사하면 누락된다.

> **Spring 비교** — `get_current_user` 의존성은 Spring Security 의
> `SecurityFilterChain` + `@AuthenticationPrincipal` 에 해당한다. FastAPI 는
> 필터가 아니라 **의존성 주입으로** 같은 일을 한다.

## 5. C. 문서 입력·처리 `DOC` — 담당 재정 (`DOC-06`·`DOC-14` 세현)

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `DOC-01` | 파일 업로드 (드래그앤드롭 · 다중) | 확장 | P0 | PDF · DOCX · HWPX · JPG · PNG, 최대 20MB. 여러 파일 동시 선택 가능 |
| `DOC-02` | 파일 검증 | 기존 | P0 | 미지원 형식 415, 크기 초과 413. **에러코드가 서버 로그에 남는다** (`SYS-09`) |
| `DOC-03` | 형식별 추출기 자동 선택 | 기존 | P0 | 확장자별로 지정된 추출기가 선택된다 |
| `DOC-04` | OCR 실행 | 기존 | P0 | 스캔 PDF · 이미지에서 텍스트가 나온다 |
| `DOC-05` | 처리 모드 선택 (일반·검수·일괄) | 신규 | P1 | 업로드 시 모드가 저장되고 기본값은 일반. 검수 모드는 `review_status=PENDING` 으로 시작 |
| `DOC-06` | **비동기 큐 처리** | 신규 | P0 | 업로드가 **즉시 202 + document_id** 를 반환한다. 24페이지 스캔 PDF 에서 요청이 블로킹되지 않는다 |
| `DOC-07` | 처리 진행 상태 표시 | 확장 | P0 | 단계별 진행이 화면에 보이고 실패 단계에 오류 표시가 남는다 |
| `DOC-08` | 문서 목록 | 확장 | P0 | 프로젝트 스코프. 페이징. **쿼리 수가 문서 수에 비례하지 않는다** (`SYS-07`) |
| `DOC-09` | 문서 상세 | 확장 | P0 | 요약 · 추출 원문 · 메타(추출방식 · OCR엔진 · 페이지 · 글자수 · 평균신뢰도 · 처리시간) 표시 |
| `DOC-10` | 원본 다운로드 | 신규 | P0 | 업로드한 원본 파일이 그대로 내려온다 |
| `DOC-11` | 문서 삭제 | 기존 | P0 | 하위 데이터(추출텍스트 · 분석 · OCR요소 · 금액 · 결정 · 일정)가 함께 정리된다 |
| `DOC-12` | 재분석 | 신규 | P1 | 기존 분석을 지우지 않고 **새 행으로 쌓인다.** 이전 결과와 비교 가능 |
| `DOC-13` | 중복 파일 검사 (SHA-256) | 신규 | P2 | — |
| `DOC-14` | 파일 저장소 이전 (S3 · MinIO) | 신규 | P1 | 컨테이너 재기동 후에도 파일이 유지된다 |
| `DOC-15` | 문서 버전 관리 · 변경점 비교 | 신규 | P3 | — |
| `DOC-16` | 업로드 시 문서 유형 지정 | 신규 | P1 | 7종 중 고르거나 **자동 판별**(기본값). 일괄은 배치 단위로 한 번 지정한다 |

**`DOC-06` 이 본프로젝트 최우선이다.** 현재는 업로드 요청 스레드에서 OCR 을 직접
돌린다. 다중 사용자에서 바로 워커가 고갈된다.

### `DOC-16` 의 목적이 바뀌었다

원래는 **분석기를 고르는 기준**을 만들기 위한 기능이었다. 그 계획(`ANL-04`
분석기 선택 규칙)이 폐기됐으므로 목적이 셋으로 줄었다.

| 쓰이는 곳 | |
|---|---|
| 목록 필터 · 대시보드 유형 분포 | `documents.document_type` |
| **프롬프트 힌트** | 계약서라고 알려주면 금액 분석기가 계약금액에 집중한다 |
| 산출물 분류 | 주간 보고서에서 "회의록 3건 · 계약서 2건" |

**분석기를 껐다 켜지는 않는다.** 유형을 몰라도 분석은 전부 돌아간다.

## 6. D. OCR 검수 `REV` — 담당 재정

데이터 요구사항은 `OCR-DB 설계안` 을 **변경 없이 채택**했다.

### 1단계 — 표시와 기본 수정

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `REV-01` | 페이지 이미지 생성 · 저장 | 신규 | P1 | 페이지별 이미지와 **좌표 기준 크기**가 저장된다 |
| `REV-02` | OCR 박스 저장 | 신규 | P1 | 박스별 텍스트 · 좌표 · 신뢰도가 **0~1 비율 좌표**로 저장된다 |
| `REV-03` | 이미지 위 Bounding Box 표시 | 신규 | P1 | **화면 확대·축소와 무관하게 박스가 글자 위에 정확히 얹힌다** |
| `REV-04` | 신뢰도별 박스 구분 | 신규 | P1 | 높음 · 검토권장 · 낮음 · 선택 네 가지가 시각적으로 구분된다 |
| `REV-05` | 박스 선택 + 텍스트 수정 | 신규 | P1 | 수정 후 `original_text` 는 그대로 남고 `text` 만 바뀐다 |
| `REV-06` | 낮은 신뢰도만 모아보기 | 신규 | P1 | 임계치 미만 박스만 목록으로 순회할 수 있다 |
| `REV-07` | 검수 완료 처리 | 신규 | P1 | 완료 시 `is_confirmed=true`, 확정자 · 시각이 남고 **분석이 1회 실행된다** |
| `REV-16` | 동시 수정 충돌 방지 | 신규 | P1 | 같은 박스를 두 사용자가 수정하면 **나중 요청이 409** 를 받는다 |
| `REV-17` | 텍스트 재조립 | 신규 | P1 | 박스 수정 후 `extracted_texts.content` 가 **같은 트랜잭션에서** 갱신된다 |
| `REV-18` | 분석 결과 오래됨 표시 | 신규 | P1 | OCR 을 고친 뒤 화면에 **"분석을 다시 실행해 주세요"** 가 뜬다 |

### 2단계 — 영역과 구조 편집

| ID | 기능 | 상태 | 우선 | 비고 |
|---|---|---|---|---|
| `REV-08` | 박스 이동 · 크기 조정 | 신규 | P2 | 크기만 바꾸면 텍스트 유지 |
| `REV-09` | 박스 생성 · 삭제 | 신규 | P2 | 삭제는 **논리 삭제** |
| `REV-10` | 박스 병합 · 분리 | 신규 | P2 | |
| `REV-11` | 선택 영역 다시 OCR | 신규 | P2 | 사용자 확인 후 반영, `source=RE_OCR` |
| `REV-12` | 단락 지정 · 병합 · 분리 | 신규 | P2 | OCR 재실행 불필요 |
| `REV-13` | 읽기 순서 변경 | 신규 | P2 | **사용자 지정이 자동 결과를 덮지 않는다** |
| `REV-14` | 표 행 · 열 수동 보정 | 신규 | P3 | |
| `REV-15` | 수정 이력 · 되돌리기 | 신규 | P2 | `ocr_element_revisions` |

**`REV-13` 의 우선순위 규칙**을 코드에 못박는다.

```
사용자 지정 순서 > 사용자 지정 단락 > 자동 Recursive XY-Cut 결과
```

**`REV-03` 이 가장 자주 깨지는 지점이다.** 프론트가 보는 이미지와 OCR 좌표 기준
이미지가 다르면 박스가 어긋난다. `document_pages.image_path` 를 기준본으로 고정한다.

**금액 정확도가 검수에 달려 있다.** 숫자는 OCR 오인식에 가장 취약해서 `1` 을 `7` 로
읽으면 전부 틀린다. 문장은 오탈자가 있어도 요약이 대충 맞지만 금액은 아니다.

## 8. F. 분석 `ANL` — 담당 보현

### 분석기는 4개, `gather` 한 번

**문서 유형으로 분석기를 고르지 않는다. 항상 넷 다 돌린다.**

```python
analyzed = await asyncio.gather(
    summary.analyze(content),     # 요약        (기존 코드 그대로)
    category.analyze(content),    # 분류        (기존 코드 그대로)
    extract.analyze(content),     # 액션·결정·일정  (신규)
    amount.analyze(content),      # 금액        (신규)
)
```

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `ANL-01` | 요약 분석기 | 기존 | P0 | 요약문과 토큰 · 지연시간이 기록된다. **코드를 고치지 않는다** |
| `ANL-02` | 분류 분석기 | 확장 | P0 | 7종 중 하나로 분류하고 `reason` 을 함께 반환한다. **자동 판별인 문서에만 실행한다** |
| `ANL-03` | 항목 추출 분석기 | 신규 | P1 | 액션아이템 · 결정 · 일정을 **한 번의 호출로** 배열로 반환. 각 항목에 `reason` 과 확신도가 붙는다 |
| `ANL-04` | ~~분석기 선택 규칙~~ | **폐기** | — | **13절 참고** |

### 왜 4개인가 — 통합하지 않은 이유

| | 분석기 4개 (채택) | 통합 1개 |
|---|---|---|
| 입력 토큰 | 약 11,200 (본문 4회) | 약 2,850 (본문 1회) |
| 병렬 | `gather` 한 번, 완전 병렬 | 해당 없음 |
| 기존 코드 | **요약·분류 0줄 수정** | 흡수하며 회귀 위험 |
| 실패 단위 | 하나 실패해도 나머지 살아남는다 | 전부 실패 |
| 금액 정확도 | **프롬프트 집중 가능** | 주의가 분산된다 |
| 프롬프트 버전 | 분석기별로 따로 올린다 | 하나로 뭉친다 |

**토큰 2배를 감수하고 4개로 간다.** 개발은 `USE_FAKE_AI` 로 하고 실제 호출은
데모·측정 때만이므로 감당 가능하다. 그리고 **금액은 정확도가 중요해 프롬프트를
섞지 않는 게 맞다.**

**통합 방식은 측정해서 비교한다.** 미니 프로젝트에서 OCR 엔진 3종을 측정해 비교한
것과 같은 패턴이고, "왜 그렇게 했나" 에 수치로 답할 수 있다.

### 순환 의존이 없어졌다

문서 유형으로 분석기를 고르지 않으므로 **"분류는 분석 결과인데 선택은 분석 전"**
문제가 사라졌다. `ANL-02` 분류는 다른 분석기와 나란히 돌고, 결과를
`documents.document_type` 에 확정값으로 올린다.

> **Spring 비교** — `Analyzer` Protocol 은 `interface Analyzer { AnalyzeResult
> analyze(String text); }` 이고, `dependencies.get_analyzer_registry()` 는
> `@Configuration` 에서 `Map<String, Analyzer>` 빈을 만드는 것과 같다.
> `asyncio.gather` 는 `CompletableFuture.allOf(...)` 에 해당한다.

### 분석기를 하나 추가하는 비용

| 손대는 곳 | |
|---|---|
| `analyzers/xxx_analyzer.py` | 새 클래스 |
| `analyzers/prompts.py` | 프롬프트 |
| `dependencies.py` | registry **한 줄** |
| `models/enums.py` | `AnalyzerType` 값 |

**라우터 · 서비스 · 스키마는 안 고친다.** `analysis_router` 가 `analyzer_types` 를
그대로 넘기고 `analyses.analyzer_type` 이 `String(30)` 이라 DB 변경도 없다.

## 9. G. 금액 `AMT` — 담당 보현

**원칙 — 있는 금액을 모은다. 없는 금액을 만들지 않는다.**

`추계`(단가 × 수량으로 없는 금액을 산출)를 버리고 `집계`(문서에 적힌 금액을 모으기)로
좁혔다. 그래서 단가 마스터가 필요 없고, **"그 숫자 근거가 뭐냐" 에 전부 문서에서
나왔다고 답할 수 있다.**

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `AMT-01` | 금액 항목 추출 | 신규 | P1 | 항목명 · 수량 · 단위 · 금액 · **`reason`** 을 구조화 스키마로 반환. **문서에 없는 값은 비운다** |
| `AMT-02` | 금액 항목 승인 · 수정 UI | 신규 | P1 | 액션아이템과 **같은 제안 카드 형식**. 승인 전에는 어디에도 반영되지 않는다 |
| `AMT-03` | **합계 대조** | 신규 | P1 | 항목 합계와 문서에 적힌 합계가 다르면 **불일치 금액과 함께 표시**된다 |
| `AMT-04` | ~~단가 마스터 관리~~ | **폐기** | — | 13절 |
| `AMT-05` | ~~전제 입력 · 승인~~ | **폐기** | — | 13절 |
| `AMT-06` | **프로젝트 금액 집계** | 신규 | P1 | 여러 문서의 금액을 프로젝트 단위로 모은다. **같은 입력이면 항상 같은 결과**가 나온다 (단위테스트로 확인) |
| `AMT-07` | 불일치 태스크 제안 | 신규 | P1 | 불일치 시 태스크 제안 카드가 생긴다. **자동 등록은 하지 않는다** |

| `AMT-10` | ~~비용추계서 서식 출력~~ | **폐기** | — | 13절 |
| `AMT-11` | 금액 열람 권한 분리 | 신규 | P2 | 미결 — 14절 |

### `AMT-03` 과 `AMT-06` 이 이 영역의 가치다

**문서 하나로는 알 수 없는 것을 알려준다.**

```
용역계약서_최종.pdf        계약금액   72,000,000
계약_변경합의서_스캔.jpg    증액       +15,000,000
3월 2주차 주간보고.docx     집행액      60,000,000
                    ↓  자동 집계
현재 계약금액  87,000,000
집행액        60,000,000  (69%)
잔액          27,000,000

⚠ 변경합의서 기재 총액(85,000,000)과 계산값(87,000,000) 불일치 → 확인 태스크
```

**요약과 액션아이템은 문서 하나로 끝나지만 금액은 모아야 의미가 생긴다.** 그래서
"문서는 프로젝트 맥락 안에 있다" 는 컨셉을 증명하는 건 금액이다.

**그리고 검증 가능한 유일한 기능이다.** 요약 · 결정 · 일정은 AI 가 뽑은 게 맞는지
확인할 방법이 없지만 **금액은 재계산해서 대조**한다.

| `SYS-10` | 로컬 sLLM 옵션 | 신규 | P3 | |

**`SYS-01` 은 P0 착수 전에 끝내야 한다.** `SYS-09` 는 미니 프로젝트에서 프리즈
때문에 미룬 한 줄짜리 결함이므로 첫날 고친다.

## 13. K. 산출물 `DLV` — 담당 보현 **(신규 영역)**

**이 영역이 제품의 출력물이다.** 문서를 넣으면 문서가 나온다.

미니 프로젝트에서 **우리가 손으로 만든 것**을 자동으로 만드는 것이다.

| 우리가 손으로 만든 것 | 대응 기능 |
|---|---|
| 결정사항 대장 29건 | `DLV-05` |
| 주간 보고 | `DLV-04` |
| 회의 안건 정리 | `DLV-06` |
| 프로젝트 현황 보고 | `DLV-07` |

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `DLV-01` | **산출물 페이지** (사이드바 메뉴) | 신규 | P1 | 사이드바에 `산출물` 메뉴가 있고 개수 배지가 붙는다 |
| `DLV-02` | 기간 선택 | 신규 | P1 | `이번 주` · `지난 주` · `이번 달` · `직접 지정`. 기간이 필요 없는 종류는 선택이 흐려진다 |
| `DLV-03` | **생성 대상 미리보기** | 신규 | P1 | 선택한 기간에 잡히는 문서 · 완료 태스크 · 결정 · 기한 · 금액 건수가 **LLM 호출 전에** 보인다. **승인 대기 건수도 함께 보여준다** |
| `DLV-04` | **주간 보고서 생성** | 신규 | P1 | 개요 · 문서 목록 · 태스크 · 결정 · 기한 · 금액 변동이 한 파일로 나온다. **LLM 호출은 개요 한 단락에만 1회** |
| `DLV-05` | 결정사항 대장 생성 | 신규 | P1 | 결정 내용 · 결정일 · 출처 문서 · 상태(확정/미결/뒤집힘)가 표로 나온다 |
| `DLV-06` | 다음 회의 안건 생성 | 신규 | P1 | **`decisions.status=PENDING` 인 항목만** 모아 안건으로 만든다 |
| `DLV-07` | 프로젝트 현황 한 장 | 신규 | P2 | 일정 · 태스크 · 결정 · 금액 현재 상태를 한 페이지로 |
| `DLV-08` | 형식 선택 | 신규 | P1 | `XLSX` · `HTML` · `MD`. **기본값이 없다.** 고르지 않으면 생성 버튼이 비활성 |
| `DLV-09` | 생성 이력 · 다운로드 | 신규 | P1 | 만든 산출물이 목록으로 남고 다시 내려받을 수 있다 |
| `DLV-10` | 갱신 필요 판정 | 신규 | P1 | 생성 후 문서가 추가되면 **"문서 N건이 나중에 추가됨"** 과 `다시 만들기` 가 표시된다 |
| `DLV-11` | 인수인계 문서 생성 | 신규 | P3 | 프로젝트 종료 시 전체 누적 |

### `DLV-04` 의 LLM 호출이 1회뿐인 이유

**재요약의 입력이 원문이 아니라 저장된 요약이다.**

| 방식 | 문서 10건 기준 입력 토큰 |
|---|---:|
| 원문을 다시 보낸다 | **약 28,000** |
| **저장된 요약만 보낸다** | **약 1,500** |

`analyses.result_json['summary']` 에 이미 있는 값을 쓴다. **주간 보고서 한 장이
문서 반 건 분석보다 싸다.**

그리고 **개요 한 단락만 LLM 이 쓴다.**

```
주간 보고서
├─ 이번 주 개요        ← LLM 1회 (저장된 요약 N개를 재요약)
├─ 문서 목록           ← DB 쿼리
├─ 완료 / 신규 태스크   ← DB 쿼리 (tasks.completed_at 필요)
├─ 이번 주 결정사항     ← DB 쿼리
├─ 기한 임박 · 지난     ← DB 쿼리 + 날짜 계산
└─ 금액 변동           ← DB 쿼리 + 코드 합산
```

**나머지는 전부 결정론적이라 같은 기간을 다시 누르면 같은 표가 나온다.**

### `DLV-03` 미리보기가 세 가지를 해결한다

| | |
|---|---|
| 빈 보고서 방지 | 기간을 잘못 잡아 "문서 0건" 인 보고서를 만드는 걸 막는다 |
| 비용 절약 | **LLM 호출 전에** 무엇이 잡히는지 보인다. 미리보기는 DB 쿼리라 공짜 |
| 승인 유도 | `승인 대기 5건` 을 보여줘 "먼저 승인하고 만드시죠" 를 화면이 알려준다 |

### 파일 생성 도구가 이미 있다

미니 프로젝트에서 산출물을 만들려고 짠 스크립트를 그대로 쓴다.

| 도구 | 용도 |
|---|---|
| `도구/_md2html.py` | 마크다운 → 인쇄용 HTML |
| `도구/_build_wbs.py` · `도구/_build_feature_spec.py` | **`openpyxl` 없이 xlsx 생성** |

**엑셀 생성이 이미 검증됐다.** 이 문서의 xlsx 판이 그 도구로 만들어졌다.

### 시연은 우리 프로젝트로 한다

**DocFlow 에 우리 팀 문서를 넣는다.** 기획안 · 회의 메모 · 설계 문서를 올리면
결정사항 대장과 주간 보고서가 나온다.

> 우리가 이번 프로젝트에서 **손으로 만든 산출물을 이 도구가 자동으로 만듭니다.**

**손으로 만든 것과 자동 생성한 것을 나란히 놓을 수 있다.** 미니 프로젝트 심사에서
"주장에 기준·수치가 없다" 가 지적됐는데, 이 형태는 비교 대상이 있어 기준이 저절로
붙는다.

## 15. 비기능 요구사항

| 구분 | 요구 | 측정 방법 |
|---|---|---|
| 성능 | 10페이지 스캔 PDF 처리 완료 ≤ 60초 | 동일 파일 3회 평균 |
| 성능 | 목록 조회 쿼리 수가 문서 수와 무관 | 쿼리 로그 개수 (`SYS-07`) |
| 성능 | **주간 보고서 생성 ≤ 15초** | LLM 1회 + DB 쿼리 |
| 동시성 | 4~5인 동시 사용 시 정상 동작 | 동시 업로드 5건 |
| 정확도 | 액션아이템 승인율 ≥ 70% | `TSK-07` 거부 기록 기반 |
| 정확도 | 카테고리 분류 정확도 ≥ 85% | **`document_type_source=USER_CORRECTED` 비율** |
| 정확도 | **일정 추출 정확도** | Golden Dataset · 원문 대조 (날짜는 형식이 있다) |
| 정확도 | **금액 항목 추출 정확도** | Golden Dataset · 원문 대조 |
| 정확도 | **금액 집계 정확도 = 100%** | 단위테스트 (`AMT-06`) |
| 보안 | 타 프로젝트 데이터 접근 차단 | `PRJ-08` 침투 테스트 |
| 보안 | API 키는 서버에만 | 프론트 번들 검사 |
| 안정성 | 컨테이너 재기동 후 파일 유지 | `DOC-14` |

**분류 정확도 측정 방식이 바뀌었다.** 별도 정답 데이터를 만드는 대신 **사람이 AI
판별을 고친 비율**을 쓴다. 실사용 데이터라 발표에서도 정답셋보다 설득력이 있다.

**금액 지표를 두 줄로 나눈 것이 중요하다.** 추출은 원문이 정답이라 측정할 수 있고,
집계는 코드가 하니 100% 여야 한다. **"AI 가 금액을 얼마나 잘 맞추나" 는 정답이
없어서 측정할 수 없다.**

## 16. 하지 않을 것

| 안 함 | 이유 |

| 실시간 공동 편집 | Notion · Google Docs 대체가 아니다 |

**문서에서 추출한 금액의 집계와 검증은 한다.** 차이는 "입력을 누가 하는가" 다.

## 0. 이 문서가 무엇인가

기능 정의가 두 곳에 갈라져 있었다.

| | ID 체계 | 문제 |
|---|---|---|
| `산출물/기능명세서_v5_세분화.xlsx` | 3단 (`DSH-001` · `SRH-002-3`) | 표라서 **설계 근거를 담을 자리가 없다** |
| `관리/기능명세서.md` (구판) | 2단 (`VIS-01` · `RAG-04`) | 제품명이 `DocFlow` 로 남아 있고 **ID 가 낡았다** |

같은 기능이 다른 ID 로 존재해서 서로 다른 기능으로 읽힐 위험이 있었다. 실제로
대시보드가 구판에서는 `VIS-01`, v5 에서는 `DSH-001` 이다.

**v5 를 뼈대로 삼고 구판의 설계 근거를 그 위에 얹었다.** v5 가 최신 구현 확인분을
반영하고 담당·상태가 갈리는 단위로 세분화되어 있어서다.

### 영역이 재편됐다 — 단순한 이름 변경이 아니다

| 구판 | v5 | 무엇이 바뀌었나 |
|---|---|---|
| `VIS` 가시성 (9건) | **`DSH` 대시보드 + `SRH` 검색** | `VIS` 접두어가 없어졌다. 지표는 `DSH`, 검색은 `SRH` 로 갈렸다 |
| `RAG` 검색·근거 (12건) | **`RAG` 파이프라인 5 + `SRH` 검색 6 + `CHAT` 1** | 만드는 쪽(청킹·임베딩)과 쓰는 쪽(검색)을 나눴다 |
| 나머지 영역 | 접두어 유지 · 3단으로 세분화 | `AMT-01` → `AMT-001-1`·`AMT-001-2` 처럼 쪼개졌다 |

전수 대응은 **부록 A** 에 있다.

### v5 xlsx 는 8/18 기준이다 — 8/19 머지분을 반영했다

v5 는 *2026-08-18 구현 확인분* 이다. 그 뒤 8/19 에 PR 일곱 건(#29~#35)이 머지됐다.
표만 믿으면 **이미 만든 것을 안 만든 것으로 읽는다.** 아래 세 건을 이 문서에서 고쳤다.

| 기능 | v5 (8/18) | 이 문서 (8/19) | 근거 |
|---|---|---|---|
| `DSH-001` 프로젝트 핵심 현황 | 미구현 | **부분 구현** | PR #34. 지표는 서버 집계로 동작한다. 유형 분포·금액 승인 대기에서 이동이 안 돼 완료 판정을 일부 못 만족 |
| `SRH-002-3` 유사 사업 단가 선례 검색 | 미구현 | **부분 구현** | PR #32. API 는 되고 화면이 없어 "표시된다" 를 못 만족 |
| `AMT-001-1` 금액 항목 추출 | 미구현 | 미구현 (비고만 추가) | PR #31 로 저장 스키마만 준비됐다. 추출 로직은 없다 |

`DOC`·`REV`·`SYS` 영역도 8/19 에 PR #30·#33·#35 가 머지됐다. 재정님 영역이라
**상태를 내가 단정하지 않았다** — 확인 후 갱신할 항목이다.

### v5 가 담지 않은 것을 남겼다

v5 의 부제가 *"적용 페이지별 **사용자** 기능 중심"* 이다. 그래서 사용자에게 화면으로
보이지 않는 **기반·품질 항목이 빠져 있다** — `N+1 방지` · `FK 인덱스` ·
`request_id 로깅` · `Fake AI Client` 같은 것들이다.

이것들을 v5 로 갈아치우면서 잃으면 안 된다. **16절에 따로 보존했다.**

### 개별 ID 1:1 대응표를 전부 만들지는 않았다

이름으로 자동 대조해 봤더니 구판 153건 중 **확실한 대응 80 · 애매 28 · 미대응 45**
였다. 애매한 것에는 명백히 틀린 짝이 섞여 있었다 — `DOC-09 문서 상세` →
`DOC-006-1 문서 삭제`, `RAG-04 의미 검색` → `RAG-002-2 검색 품질 측정`(실제로는
`SRH-001`).

**틀린 대응표는 없는 것보다 나쁘다.** 그래서 부록 A 에는 **눈으로 확인한 것만**
넣었다. 실제로 커밋·PR·작업일지에서 인용되는 `RAG`·`VIS` 계열은 전수 확인했다.
나머지 구판 ID 는 부록 B 에 "어느 영역으로 갔는지" 까지만 적었다.

## 1. 읽는 방법

### 상태

| 값 | 뜻 |
|---|---|
| `구현됨` | 코드가 있고 완료 판정을 만족한다 |
| `부분 구현` | 일부만 동작한다. 무엇이 빠졌는지는 완료 판정과 비교해서 본다 |
| `미구현` | 코드가 없다 |
| `검토중` | 할지 말지 정하지 않았다 |
| `미결` | 하기로 했으나 방식이 정해지지 않았다 |

### 우선순위

| 값 | 뜻 |
|---|---|
| `P0` | 없으면 제품이 성립하지 않는다 |
| `P1` | 시연에 필요하다 |
| `P2` | 있으면 좋다 |
| `P3` | 이번 범위 밖 |

### 담당

v5 는 이름을 그대로 쓴다. 구판은 `세현`·`재정`·`보현` 처럼 줄여 썼다.

| v5 표기 | 구판 표기 | 맡은 영역 (주로) |
|---|---|---|
| 최재정 | `재정` | 계정·권한 · 프로젝트 · 문서 입력·처리 · OCR 검수 · 일괄 처리 |
| 김보현 | `보현` | 검색·근거 · 금액 · 가시성 · 산출물 |
| 박세현 | `세현` | 분석 · AI 추천 |

`최재정, 김보현` 처럼 둘이 적힌 항목은 화면과 서버를 나눠 맡은 것이다.

### 완료 판정 기준

**"만들었다" 가 아니라 "무엇을 확인하면 됐다고 하는가" 를 적는다.** 이것이 없으면
구현 여부를 사람마다 다르게 판단한다. 판정은 가능하면 실행해서 확인할 수 있는
형태로 쓴다.

### 설계 근거 (구판에서 옮김)

> 아래 글은 **구판 ID 기준**으로 쓴 기록이다. 그때의 판단을 그대로 남기는 것이
> 목적이라 ID 를 바꾸지 않았다. v5 ID 대응은 **부록 A · B** 를 본다.

**`AUTH-05` 가 핵심이다.** 개별 라우터에서 검사하면 누락된다.

> **Spring 비교** — `get_current_user` 의존성은 Spring Security 의
> `SecurityFilterChain` + `@AuthenticationPrincipal` 에 해당한다. FastAPI 는
> 필터가 아니라 **의존성 주입으로** 같은 일을 한다.

### 설계 근거 (구판에서 옮김)

> 아래 글은 **구판 ID 기준**으로 쓴 기록이다. 그때의 판단을 그대로 남기는 것이

### 분석기는 4개, `gather` 한 번

**문서 유형으로 분석기를 고르지 않는다. 항상 넷 다 돌린다.**

```python
analyzed = await asyncio.gather(
    summary.analyze(content),     # 요약        (기존 코드 그대로)
    category.analyze(content),    # 분류        (기존 코드 그대로)
    extract.analyze(content),     # 액션·결정·일정  (신규)
    amount.analyze(content),      # 금액        (신규)
)
```

### 왜 4개인가 — 통합하지 않은 이유

| | 분석기 4개 (채택) | 통합 1개 |
|---|---|---|
| 입력 토큰 | 약 11,200 (본문 4회) | 약 2,850 (본문 1회) |
| 병렬 | `gather` 한 번, 완전 병렬 | 해당 없음 |
| 기존 코드 | **요약·분류 0줄 수정** | 흡수하며 회귀 위험 |
| 실패 단위 | 하나 실패해도 나머지 살아남는다 | 전부 실패 |
| 금액 정확도 | **프롬프트 집중 가능** | 주의가 분산된다 |
| 프롬프트 버전 | 분석기별로 따로 올린다 | 하나로 뭉친다 |

**토큰 2배를 감수하고 4개로 간다.** 개발은 `USE_FAKE_AI` 로 하고 실제 호출은
데모·측정 때만이므로 감당 가능하다. 그리고 **금액은 정확도가 중요해 프롬프트를
섞지 않는 게 맞다.**

**통합 방식은 측정해서 비교한다.** 미니 프로젝트에서 OCR 엔진 3종을 측정해 비교한
것과 같은 패턴이고, "왜 그렇게 했나" 에 수치로 답할 수 있다.

### 순환 의존이 없어졌다

문서 유형으로 분석기를 고르지 않으므로 **"분류는 분석 결과인데 선택은 분석 전"**
문제가 사라졌다. `ANL-02` 분류는 다른 분석기와 나란히 돌고, 결과를
`documents.document_type` 에 확정값으로 올린다.

> **Spring 비교** — `Analyzer` Protocol 은 `interface Analyzer { AnalyzeResult
> analyze(String text); }` 이고, `dependencies.get_analyzer_registry()` 는
> `@Configuration` 에서 `Map<String, Analyzer>` 빈을 만드는 것과 같다.
> `asyncio.gather` 는 `CompletableFuture.allOf(...)` 에 해당한다.

### 분석기를 하나 추가하는 비용

| 손대는 곳 | |
|---|---|
| `analyzers/xxx_analyzer.py` | 새 클래스 |
| `analyzers/prompts.py` | 프롬프트 |
| `dependencies.py` | registry **한 줄** |
| `models/enums.py` | `AnalyzerType` 값 |

**라우터 · 서비스 · 스키마는 안 고친다.** `analysis_router` 가 `analyzer_types` 를
그대로 넘기고 `analyses.analyzer_type` 이 `String(30)` 이라 DB 변경도 없다.

### 설계 근거 (구판에서 옮김)

> 아래 글은 **구판 ID 기준**으로 쓴 기록이다. 그때의 판단을 그대로 남기는 것이
> 목적이라 ID 를 바꾸지 않았다. v5 ID 대응은 **부록 A · B** 를 본다.

**원칙 — 있는 금액을 모은다. 없는 금액을 만들지 않는다.**

`추계`(단가 × 수량으로 없는 금액을 산출)를 버리고 `집계`(문서에 적힌 금액을 모으기)로
좁혔다. 그래서 단가 마스터가 필요 없고, **"그 숫자 근거가 뭐냐" 에 전부 문서에서
나왔다고 답할 수 있다.**

### `AMT-03` 과 `AMT-06` 이 이 영역의 가치다

**문서 하나로는 알 수 없는 것을 알려준다.**

```
용역계약서_최종.pdf        계약금액   72,000,000
계약_변경합의서_스캔.jpg    증액       +15,000,000
3월 2주차 주간보고.docx     집행액      60,000,000
                    ↓  자동 집계
현재 계약금액  87,000,000
집행액        60,000,000  (69%)
잔액          27,000,000

⚠ 변경합의서 기재 총액(85,000,000)과 계산값(87,000,000) 불일치 → 확인 태스크
```

**요약과 액션아이템은 문서 하나로 끝나지만 금액은 모아야 의미가 생긴다.** 그래서
"문서는 프로젝트 맥락 안에 있다" 는 컨셉을 증명하는 건 금액이다.

**그리고 검증 가능한 유일한 기능이다.** 요약 · 결정 · 일정은 AI 가 뽑은 게 맞는지
확인할 방법이 없지만 **금액은 재계산해서 대조**한다.

### 설계 근거 (구판에서 옮김)

> 아래 글은 **구판 ID 기준**으로 쓴 기록이다. 그때의 판단을 그대로 남기는 것이
> 목적이라 ID 를 바꾸지 않았다. v5 ID 대응은 **부록 A · B** 를 본다.

**도메인을 공공 SI·용역으로 좁힌 뒤 정식 범위가 됐다.** 앞서 "기간 필터가 그
자리를 채우고 있다" 는 이유로 범위에서 뺐는데, **비용추계의 단가 근거를 과거
문서에서 찾아올 수 있다는 점**이 근거를 바꿨다. 환각이 아니라 선례 기반 추정이
된다.

**임베딩은 금액 전용이 아니다.** 요약·분류·검색이 같은 파이프라인을 쓴다.
특히 45,000자 문서를 요약할 때 무엇을 프롬프트에 넣을지 고르는 데 쓰인다.

**`RAG-09` 가 가장 놓치기 쉽다.** 검수 전파 사슬(`REV-17` → `REV-18` → `ANL-06`)의
끝이 임베딩이다. OCR 을 고쳤는데 벡터DB 가 옛 텍스트를 갖고 있으면 검색이 낡은
것을 찾아온다. **검수가 무의미해진다.**

**`RAG-11` 챗봇은 후순위로 합의했다.** 의미 검색(`RAG-04`)과 단가 선례
검색(`RAG-12`)을 먼저 만든다. 그 둘은 금액 영역의 근거 확보에 직접 쓰이고,
챗봇은 그 위에 얹는 화면이다.

## 16. 기반·품질 항목 — v5 에 없어 보존

v5 는 사용자 기능 중심이라 아래 항목들이 빠져 있다. 화면에 보이지 않지만
**빠지면 조용히 문제가 되는** 것들이라 여기 남긴다. 구판 ID 를 그대로 쓴다 —
v5 에 대응이 없어서 새 ID 를 임의로 만들면 명세에 없는 ID 가 생긴다.

| 구판 ID | 항목 | 왜 남기나 |
|---|---|---|
| `AUTH-05` | 인증 의존성 `get_current_user` | 개별 라우터에서 검사하면 **누락된다.** 모든 프로젝트 스코프 API 에 적용됨을 목록으로 확인해야 한다 |
| `PRJ-07` | 권한 3종 (OWNER · EDITOR · VIEWER) | 역할별 허용 동작 표가 문서로 있고 각 항목이 테스트로 확인돼야 한다 |
| `PRJ-08` | **프로젝트 스코프 강제** | 다른 프로젝트의 `document_id` 를 직접 넣어도 404 가 나와야 한다. 리포지토리 계층에서 막는다 |
| `SYS-07` | N+1 방지 | 목록 조회 쿼리 수가 문서 수와 무관해야 한다 (PR #33 으로 3곳 처리) |
| `SYS-08` | FK 인덱스 | 조인 성능 |
| `SYS-04` | `request_id` 로깅 | 장애 추적 |
| `SYS-05` | Fake AI Client | 개발 중 실수로 상용 API 가 호출되어 비용이 나가는 것을 막는다 |
| `DOC-13` | 중복 파일 검사 (SHA-256) | `content_hash` 로 같은 파일 재업로드를 걸러낸다 |
| `DOC-14` | 파일 저장소 이전 (S3 · MinIO) | 컨테이너 재기동 후 파일 유지 |
| `REV-01` | 페이지 이미지 생성·저장 | 검수 화면의 전제 |
| `REV-03` | 이미지 위 Bounding Box 표시 | 같음 |
| `BAT-05` | OCR Worker 수 제한 병렬 | 메모리 초과 방지 |
| `ANL-08` | 프롬프트 버전 관리 | 결과가 바뀐 원인을 추적하려면 필요하다 |

**이 목록은 "v5 에서 빠졌으니 안 한다" 가 아니다.** 대부분 이미 구현됐거나
구현 중이고, v5 의 표 형식에 들어갈 자리가 없었을 뿐이다. v6 를 만들 때
`SYS` 영역에 넣을지 판단해야 한다.

## 18. 비기능 요구사항

| 구분 | 요구 | 측정 방법 |
|---|---|---|
| 성능 | 10페이지 스캔 PDF 처리 완료 ≤ 60초 | 동일 파일 3회 평균 |
| 성능 | 목록 조회 쿼리 수가 문서 수와 무관 | 쿼리 로그 개수 (`SYS-07`) |
| 성능 | **주간 보고서 생성 ≤ 15초** | LLM 0회 + DB 쿼리·렌더링 |
| 동시성 | 4~5인 동시 사용 시 정상 동작 | 동시 업로드 5건 |
| 정확도 | 액션아이템 승인율 ≥ 70% | `TSK-07` 거부 기록 기반 |
| 정확도 | 카테고리 분류 정확도 ≥ 85% | **`document_type_source=USER_CORRECTED` 비율** |
| 정확도 | **일정 추출 정확도** | Golden Dataset · 원문 대조 (날짜는 형식이 있다) |
| 정확도 | **금액 항목 추출 정확도** | Golden Dataset · 원문 대조 |
| 정확도 | **금액 집계 정확도 = 100%** | 단위테스트 (`AMT-06`) |
| 보안 | 타 프로젝트 데이터 접근 차단 | `PRJ-08` 침투 테스트 |
| 보안 | API 키는 서버에만 | 프론트 번들 검사 |
| 안정성 | 컨테이너 재기동 후 파일 유지 | `DOC-14` |

**분류 정확도 측정 방식이 바뀌었다.** 별도 정답 데이터를 만드는 대신 **사람이 AI
판별을 고친 비율**을 쓴다. 실사용 데이터라 발표에서도 정답셋보다 설득력이 있다.

**금액 지표를 두 줄로 나눈 것이 중요하다.** 추출은 원문이 정답이라 측정할 수 있고,
집계는 코드가 하니 100% 여야 한다. **"AI 가 금액을 얼마나 잘 맞추나" 는 정답이
없어서 측정할 수 없다.**

## 19. 하지 않을 것

| 안 함 | 이유 |
|---|---|
| 실시간 공동 편집 | Notion · Google Docs 대체가 아니다 |
| 간트 차트 등 본격 PMS | 범위 밖 |
| **사람이 원가를 입력하는 비용 관리 모듈** | 컨셉과 반대다. **우리는 문서에서 뽑는다** |
| **금액 추계 · 예측** | 없는 값을 만드는 일이다. 단가 근거를 댈 수 없다 |
| 모바일 네이티브 앱 | 반응형 웹으로 대응 |
| **법안 등 법률문서 자동 생성** | 환각 위험 · 법적 책임 · 검증 부담 |
| 파인튜닝 | 20일에 자리가 없다. 프롬프트 + 구조화 출력으로 목표 달성 가능 |

**세 번째 항목의 경계를 분명히 한다.** 사람이 원가를 입력하는 관리 모듈은 안 하고,
**문서에서 추출한 금액의 집계와 검증은 한다.** 차이는 "입력을 누가 하는가" 다.

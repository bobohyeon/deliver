# DocFlow 기능명세서

본프로젝트 전체 기능을 한 문서에 모은 것이다. 출처는 네 개다.

| 출처 | 반영한 것 |
|---|---|
| 목업 5화면 (박세현) | 화면에 실제로 그려진 요소 |
| `기획안_v0.1` · `착수기획서_v1.0` (박세현) | 우선순위 · 역할 · 로드맵 |
| `기능 확장 아이디어` 3모드 (최재정) | 일반 · 검수 · 일괄 처리 |
| `OCR-DB 설계안` (최재정) | 검수 기능이 요구하는 데이터 |
| 미니 프로젝트 코드 | 이미 구현된 것 |

WBS · 통합테스트 시나리오 · 화면정의서는 이 문서의 **기능 ID 를 그대로 인용**한다.
ID 를 바꾸면 세 문서를 같이 고쳐야 하므로 ID 는 확정 후 변경하지 않는다.

---

## 0. 읽는 방법

### 우선순위

| 표기 | 뜻 | 판단 기준 |
|---|---|---|
| **P0** | MVP 필수 | 없으면 "팀 도구" 가 성립하지 않는다 |
| **P1** | 차별화 핵심 | 이게 우리 제품의 주장이다. 발표 데모의 중심 |
| **P2** | 확장 | 시간이 남으면. 없어도 데모가 성립한다 |
| **P3** | 향후 | 발표에서 **"향후 개선사항"** 으로 배치한다 |

### 상태

| 표기 | 뜻 |
|---|---|
| **기존** | 미니 프로젝트에서 구현 완료. 재사용 |
| **확장** | 기존 코드에 컬럼·조건을 추가 |
| **신규** | 새로 만든다 |

### 담당

`세현` 박세현 · `재정` 최재정 · `보현` 김보현 · `공통` 셋이 나눠 맡음

### 완료 판정 기준

**모든 P0 · P1 에 판정 기준을 붙였다.** 이 문장이 그대로 통합테스트 시나리오의
기대결과가 된다. 미니 프로젝트에서 산출물이 코드 프리즈 뒤로 몰린 원인이
판정 기준을 나중에 쓴 것이었다.

**P0 + P1 이 72개다. 구현 기간은 20일이다.** 다 못 한다.

> 위 집계는 `도구/_build_feature_spec.py` 가 항목별 우선순위에서 직접 센 값이다.
> 손으로 센 값과 어긋나면 스크립트 출력을 정본으로 한다.

그래서 이 문서는 **덜어내기 목록이 아니라 묶기 목록**으로 쓴다. 같은 골격을 쓰는
기능을 함께 만들면 두 번째가 훨씬 싸다. 12절에서 다룬다.

| 묶음 | 기능 | 왜 함께 |
|---|---|---|
| 제안 골격 | `ANL-03` `AMT-01` `TSK-03` `TSK-04` `TSK-05` `TSK-07` `TSK-08` | 제안 카드 · 승인 · 역추적 UI 를 공유한다. 분석기만 갈아 끼운다 |
| 검수 골격 | `REV-01`~`REV-07` `REV-16`~`REV-18` | 박스 표시와 텍스트 수정 하나로 묶인다 |
| 스코프 | `AUTH-*` `PRJ-*` | 인증 없이 스코프가 성립하지 않는다 |

## 2. A. 계정·권한 `AUTH` — 담당 세현

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `AUTH-01` | 회원가입 | 신규 | P0 | 이메일 중복 시 409, 비밀번호는 해시로만 저장되고 응답에 포함되지 않는다 |
| `AUTH-02` | 로그인 | 신규 | P0 | 올바른 자격으로 access · refresh 토큰 발급, 틀리면 401 |
| `AUTH-03` | 내 정보 조회 | 신규 | P0 | 유효 토큰으로 본인 정보 반환, 만료 토큰은 401 |
| `AUTH-04` | 토큰 갱신 · 로그아웃 | 신규 | P0 | refresh 로 access 재발급, 로그아웃 후 해당 refresh 는 재사용 불가 |
| `AUTH-05` | 인증 의존성 `get_current_user` | 신규 | P0 | 토큰 없이 보호된 엔드포인트 호출 시 401. **모든 프로젝트 스코프 API 에 적용됨을 목록으로 확인** |
| `AUTH-06` | SSO | 신규 | P3 | — |

**`AUTH-05` 가 핵심이다.** 개별 라우터에서 검사하면 누락된다. 기존
`dependencies.py` 패턴을 그대로 확장한다.

> **Spring 비교** — `get_current_user` 의존성은 Spring Security 의
> `SecurityFilterChain` + `@AuthenticationPrincipal` 에 해당한다. FastAPI 는
> 필터가 아니라 **의존성 주입으로** 같은 일을 한다.

## 4. C. 문서 입력·처리 `DOC` — 담당 재정 (`DOC-06`·`DOC-14` 세현)

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `DOC-01` | 파일 업로드 (드래그앤드롭 · 다중 선택) | 확장 | P0 | PDF · DOCX · HWPX · JPG · PNG, 최대 20MB. 여러 파일 동시 선택 가능 |
| `DOC-02` | 파일 검증 | 기존 | P0 | 미지원 형식 415, 크기 초과 413. **에러코드가 서버 로그에 남는다** (`SYS-09`) |
| `DOC-03` | 형식별 추출기 자동 선택 | 기존 | P0 | 확장자별로 지정된 추출기가 선택된다 |
| `DOC-04` | OCR 실행 | 기존 | P0 | 스캔 PDF · 이미지에서 텍스트가 나온다 |
| `DOC-05` | 처리 모드 선택 (일반 · 검수 · 일괄) | 신규 | P1 | 업로드 시 모드가 저장되고, 기본값은 일반. 검수 모드는 `review_status=PENDING` 으로 시작 |
| `DOC-06` | **비동기 큐 처리** | 신규 | P0 | 업로드가 **즉시 202 + document_id** 를 반환한다. 24페이지 스캔 PDF 업로드 시 요청이 블로킹되지 않는다 |
| `DOC-07` | 처리 진행 상태 표시 | 확장 | P0 | 단계별 진행이 화면에 보이고, 실패 단계에 오류 표시가 남는다 (`ANL-05` 와 함께) |
| `DOC-08` | 문서 목록 | 확장 | P0 | 프로젝트 스코프. 페이징. **쿼리 수가 문서 수에 비례하지 않는다** (`SYS-07`) |
| `DOC-09` | 문서 상세 | 확장 | P0 | 요약 · 추출 원문 · 메타(추출방식 · OCR엔진 · 페이지 · 글자수 · 평균신뢰도 · 처리시간) 표시 |
| `DOC-10` | 원본 다운로드 | 신규 | P0 | 업로드한 원본 파일이 그대로 내려온다 |
| `DOC-11` | 문서 삭제 | 기존 | P0 | 하위 데이터(추출텍스트 · 분석 · OCR요소)가 함께 정리된다 |
| `DOC-12` | 재분석 | 신규 | P1 | 기존 분석을 지우지 않고 **새 행으로 쌓인다.** 이전 결과와 비교 가능 |
| `DOC-13` | 중복 파일 검사 (SHA-256) | 신규 | P2 | — |
| `DOC-14` | 파일 저장소 이전 (S3 · MinIO) | 신규 | P1 | 컨테이너 재기동 후에도 파일이 유지된다 |
| `DOC-15` | 문서 버전 관리 · 변경점 비교 | 신규 | P3 | — |
| **`DOC-16`** | **업로드 시 문서 유형 지정 (기본값 자동 판별)** | 신규 | **P1** | 유형을 고르면 분류 분석기를 건너뛴다. **자동 판별을 고르면 분류 분석기가 먼저 실행되고 결과가 확정값으로 저장된다.** 일괄 업로드는 배치 단위로 한 번 지정한다 |

**`DOC-06` 이 본프로젝트 최우선이다.** 현재는 업로드 요청 스레드에서 OCR 을 직접
돌린다. 미니 프로젝트 측정으로 PaddleOCR 이 페이지당 15.5초였으므로 24페이지면
요청 하나가 6분을 잡는다. 다중 사용자에서 바로 워커가 고갈된다.

**`DOC-12` 재분석은 미니 프로젝트 설계 덕을 본다.** `analyses` 가 1:N 이라 재분석이
이전 결과를 덮지 않는다. 발표에서 "왜 테이블을 나눴나" 의 답이 된다.

## 5. D. OCR 검수 `REV` — 담당 재정

이 영역이 **최재정 파트의 핵심**이고, 데이터 요구사항은 `OCR-DB 설계안` 에 있다.

### 1단계 — 표시와 기본 수정

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `REV-01` | 페이지 이미지 생성 · 저장 | 신규 | P1 | 페이지별 이미지와 **좌표 기준 크기(width · height)** 가 저장된다 |
| `REV-02` | OCR 박스 저장 | 신규 | P1 | 박스별 텍스트 · 좌표 · 신뢰도가 **0~1 비율 좌표**로 저장된다 |
| `REV-03` | 이미지 위 Bounding Box 표시 | 신규 | P1 | **화면 확대·축소와 무관하게 박스가 글자 위에 정확히 얹힌다** |
| `REV-04` | 신뢰도별 박스 구분 | 신규 | P1 | 높음 · 검토권장 · 낮음 · 선택 네 가지가 시각적으로 구분된다 |
| `REV-05` | 박스 선택 + 텍스트 수정 | 신규 | P1 | 수정 후 `original_text` 는 그대로 남고 `text` 만 바뀐다 |
| `REV-06` | 낮은 신뢰도만 모아보기 | 신규 | P1 | 임계치 미만 박스만 목록으로 순회할 수 있다 |
| `REV-07` | 검수 완료 처리 | 신규 | P1 | 완료 시 `is_confirmed=true`, 확정자 · 시각이 남고 **분석이 1회 실행된다** |
| `REV-16` | 동시 수정 충돌 방지 | 신규 | P1 | 같은 박스를 두 사용자가 수정하면 **나중 요청이 409** 를 받는다 |
| `REV-17` | 텍스트 재조립 | 신규 | P1 | 박스 수정 후 `extracted_texts.content` 가 **같은 트랜잭션에서** 갱신된다 |
| `REV-18` | 분석 결과 오래됨 표시 | 신규 | P1 | OCR 을 고친 뒤 화면에 **"분석을 다시 실행해 주세요"** 가 뜬다 |

### 2단계 — 영역과 구조 편집

| ID | 기능 | 상태 | 우선 | 비고 |
|---|---|---|---|---|
| `REV-08` | 박스 이동 · 크기 조정 | 신규 | P2 | 크기만 바꾸면 텍스트는 유지 |
| `REV-09` | 박스 생성 · 삭제 | 신규 | P2 | 삭제는 **논리 삭제** |
| `REV-10` | 박스 병합 · 분리 | 신규 | P2 | |
| `REV-11` | 선택 영역 다시 OCR | 신규 | P2 | 사용자 확인 후 반영, `source=RE_OCR` |
| `REV-12` | 단락 지정 · 병합 · 분리 | 신규 | P2 | OCR 재실행 불필요 |
| `REV-13` | 읽기 순서 변경 | 신규 | P2 | **사용자 지정이 자동 결과를 덮지 않는다** |
| `REV-14` | 표 행 · 열 수동 보정 | 신규 | P3 | |
| `REV-15` | 수정 이력 · 되돌리기 | 신규 | P2 | `ocr_element_revisions` |

**`REV-13` 의 우선순위 규칙**을 코드에 못박아야 한다.

```
사용자 지정 순서 > 사용자 지정 단락 > 자동 Recursive XY-Cut 결과
```

**`REV-03` 이 가장 자주 깨지는 지점이다.** 프론트가 보는 이미지와 OCR 좌표 기준
이미지가 다르면 박스가 어긋난다. `document_pages.image_path` 의 이미지를 기준본으로
고정해야 한다.

### 폐기 — `ANL-13` `Analyzer` Protocol 확장

**근거 페이지 표시를 범위에서 빼기로 결정했으므로 폐기한다.**

대신 **`reason`(AI 판단 근거 서술)만 표시**한다. 텍스트 문자열만 받아도 만들 수
있으므로 **분석기 규격을 고치지 않는다.** 분류 분석기가 이미 `result_json` 에
`reason` 을 담고 있으니 같은 패턴을 액션아이템·금액에 적용한다.

| | |
|---|---|
| `Analyzer` Protocol | **안 고친다** |
| 검수 파트에 요청 | **없다.** 텍스트 조립 시 offset 을 남길 필요가 없다 |
| 프론트 하이라이트 로직 | **없다** |
| 세 사람의 인터페이스 대기 | **없어진다** |

**잃는 것도 있다.** 원문 대조로 근거를 검증할 수 없다. `reason` 도 AI 가 쓴 글이라
그 자체가 환각일 수 있다. 금액은 `AMT-03` **합계 대조**가 그 역할을 대신하지만,
액션아이템은 검증 수단이 없어 승인율(`TSK-07`)로만 관리한다.

<details>
<summary>폐기된 확장안 (기록용)</summary>

**당시 문제 — 규격이 텍스트 문자열 하나만 받는다.**

```python
class Analyzer(Protocol):
    async def analyze(self, text: str) -> AnalyzeResult: ...
```

그런데 목업의 액션아이템 카드에는 `근거 · 3페이지 "다음 주 금요일까지…"` 가 있고,
금액 항목도 `근거 · 7페이지` 가 필요하다 (`AMT-09`). **문자열만 받으면 페이지를
알 수 없다.** `ExtractResult.page_count` 는 있지만 `content` 는 페이지 구분이 없는
단일 문자열이다.

**컨셉 원칙 3번(모든 결과는 원문으로 역추적된다)이 여기에 걸려 있다.**

#### 채택안 — optional 인자 추가

```python
@dataclass(frozen=True)
class AnalyzeContext:
    page_spans: list[tuple[int, int, int]]   # (page_number, start_offset, end_offset)
    element_spans: list[tuple[int, int, int]] | None = None  # (ocr_element_id, s, e)

class Analyzer(Protocol):
    async def analyze(
        self, text: str, context: AnalyzeContext | None = None
    ) -> AnalyzeResult: ...
```

- **기존 `SummaryAnalyzer` · `CategoryAnalyzer` 는 고치지 않는다.** 인자가 optional
  이므로 무시하면 된다
- 분석기는 인용문의 문자 위치를 `page_spans` 와 비교해 페이지를 계산한다
- `element_spans` 가 있으면 `ocr_element_id` 까지 특정된다 → **좌표 하이라이트**

#### 왜 다른 방법을 쓰지 않는가

| 방법 | 문제 |
|---|---|
| 텍스트에 `[[page:7]]` 마커를 심는다 | 마커가 LLM 출력에 섞여 나온다. 토큰도 늘어난다 |
| 분석기가 `ocr_elements` 를 직접 조회 | 분석기가 DB 를 알게 된다. **계층 위반** |
| 분석기가 문서 전체를 받는다 | 분석기가 파일·프로젝트를 알게 된다. 갈아 끼울 수 없게 된다 |

**분석기는 텍스트와 위치만 알아야 한다.** 그 이상 알면 부품이 아니게 된다.

</details>

### `ANL-04` 분석기 선택 규칙 — 이 표가 산출물이다

**용어 주의** — 여기서 말하는 "선택 규칙" 은 FastAPI **라우터**와 아무 관계가 없다.
처음에 "라우팅" 이라고 불렀다가 라우터를 고쳐야 하는 것으로 오해를 샀으므로
이름을 바꿨다. **라우터·서비스는 안 고친다** (`analysis_router` 가
`analyzer_types` 를 그대로 넘기기만 한다).

문서 유형은 **7종**이다. 미니 프로젝트 6종에 `계약변경` 을 더했다.

| `document_type` | 요약 | 분류 | 액션아이템 | 금액 |
|---|:-:|:-:|:-:|:-:|
| 계약서 `CONTRACT` | O | 자동일 때만 | 조항 검토 | **O — 계약금액** |
| **계약변경 `CONTRACT_CHANGE`** | O | 자동일 때만 | 조항 검토 | **O — 증감액** |
| 회의록 `MEETING_NOTES` | O | 자동일 때만 | O | 비용 발생 요인만 |
| 보고서 `REPORT` | O | 자동일 때만 | O | 진행률 대비 |
| 공지사항 `NOTICE` | O | 자동일 때만 | — | — |
| 메뉴얼 `MANUAL` | O | 자동일 때만 | — | — |
| 기타 `ETC` | O | 자동일 때만 | — | — |

**`계약변경` 을 따로 둔 이유** — 원계약서는 **계약금액**을 뽑고 변경합의서는
**증감액**을 뽑는다. 같은 금액 분석기라도 프롬프트가 달라야 한다. 목업에
`용역계약서_최종.pdf` 와 `계약_변경합의서_스캔.jpg` 가 둘 다 있어 실제로 마주칠
문제다. 프롬프트가 스스로 원계약인지 변경인지 판단하게 하면 그게 또 하나의 분류
문제가 되고, 틀렸을 때 사람이 고칠 방법이 없다.

> **Spring 비교** — 미니 프로젝트의 `ExtractorRegistry` 가
> `Map<확장자, TextExtractor>` 로 추출기를 골랐다. `ANL-04` 는
> `Map<DocumentType, List<Analyzer>>` 로 분석기를 고르는 **같은 전략 패턴**이다.
> 이미 검증한 구조를 한 층 위에 다시 쓴다.

### 순환 의존을 어떻게 피하는가

분석기를 고르는 기준이 문서 유형인데, 문서 유형을 AI 분류로 정하면 **분류는 분석
결과인데 선택은 분석 전**이라 순환이 된다. **`DOC-16` 으로 끊는다.**

```
업로드 시 유형 선택
  ├─ 사람이 고름     → 분류 분석기 건너뜀 → 바로 선택 규칙 적용
  └─ 자동 판별(기본) → 분류 분석기만 먼저 실행 → 결과를 확정값으로 → 선택 규칙 적용
```

**`documents.document_type` 이 어느 경로든 확정값을 담는 컬럼이 된다.** 미니
프로젝트에서 항상 `general` 이던 장식 컬럼이 여기서 실제로 쓰인다.

**`ANL-04` 와 `ANL-05` 가 없으면 분석기를 늘릴 때마다 화면과 상태 enum 을 고쳐야
한다.** 목업 파이프라인이 `④ 액션 아이템 추출` 로 고정되어 있는 것이 그 증거다.

## 8. G. 금액·비용추계 `AMT` — 담당 보현

**원칙: LLM 은 추출만 하고 계산은 Python 이 한다.** 숫자에 환각이 들어갈 경로를
차단하기 위한 것이며, 이 원칙이 이 영역 전체를 지배한다.

| ID | 기능 | 상태 | 우선 | 완료 판정 기준 |
|---|---|---|---|---|
| `AMT-01` | 금액 항목 추출 | 신규 | P1 | 항목명 · 수량 · 단위 · 단가 · 금액 · **`reason`(왜 이 항목으로 봤는지)** 을 구조화 스키마로 반환. 스키마에 없는 필드는 나올 수 없다 |
| `AMT-02` | 금액 항목 승인 · 수정 UI | 신규 | P1 | 액션아이템과 **같은 제안 카드 형식**. 승인 전에는 어디에도 반영되지 않는다 |
| `AMT-03` | 검증 모드 — 문서 합계와 대조 | 신규 | P1 | 항목 합계와 문서에 적힌 합계가 다르면 **불일치 금액과 함께 표시**된다 |
| `AMT-04` | 단가 마스터 관리 | 신규 | P1 | 단가마다 **출처와 기준일**이 있고 화면에 표시된다. 사람이 수정 가능 |
| `AMT-05` | 전제 입력 · 승인 | 신규 | P1 | 계산에 필요한 전제가 비어 있으면 **계산을 실행하지 않고** 무엇이 빈지 알려준다 |
| `AMT-06` | 추계 계산 | 신규 | P1 | Python 이 계산한다. **같은 입력이면 항상 같은 결과**가 나온다 (단위테스트로 확인) |
| `AMT-07` | 불일치 · 미확정 태스크 제안 | 신규 | P1 | 불일치 또는 전제 미확정 시 태스크 제안 카드가 생긴다. **자동 등록은 하지 않는다** |
| `AMT-08` | 프로젝트 금액 현황 | 신규 | P2 | 계약금액 · 변경 증감 · 미확정 금액이 프로젝트 단위로 집계된다 |
| `AMT-09` | 금액 판단 근거 표시 | 신규 | P1 | 금액 항목마다 **`reason`** 이 보이고 **출처 문서로 이동**할 수 있다. 검증은 `AMT-03` 합계 대조가 담당한다 |
| `AMT-10` | 비용추계서 서식 출력 | 신규 | P3 | 확정된 항목을 서식에 배치. **생성이 아니라 배치** |
| `AMT-11` | 금액 열람 권한 분리 | 신규 | P2 | 미결 — 14절 |

### `AMT-01` 이 뽑는 것과 뽑지 않는 것

| 값 | 어디서 오나 | 누가 |
|---|---|---|
| 항목명 · 수량 · 단위 · 적용 기간 · 시행 시기 | **문서 안에 있다** | LLM 추출 |
| 단가 · 증가율 · 기타 전제 | **문서 밖에 있다** | 단가 마스터 또는 사람 |
| 곱셈 · 합계 · 연도 배분 | 어디에도 없다 | **Python** |

**LLM 이 문서에 없는 숫자를 만들어내지 않는다.** 이게 `AMT` 영역의 안전장치다.

### `AMT-06` 이 왜 검증 가능한가

계산이 Python 이므로 **정확도가 100% 여야 하고, 단위테스트로 증명된다.** AI 지표가
아니라 코드 품질 지표다. 반면 `AMT-01` 추출은 원문과 대조해 정확도를 잴 수 있다.
**"금액이 맞나" 가 아니라 "원문에서 제대로 뽑았나" 를 측정한다.**

## 12. 비기능 요구사항

| 구분 | 요구 | 측정 방법 |
|---|---|---|
| 성능 | 10페이지 스캔 PDF 처리 완료 ≤ 60초 | 동일 파일 3회 평균 |
| 성능 | 목록 조회 쿼리 수가 문서 수와 무관 | 쿼리 로그 개수 (`SYS-07`) |
| 동시성 | 4~5인 동시 사용 시 정상 동작 | 동시 업로드 5건 |
| 정확도 | 액션아이템 승인율 ≥ 70% | `TSK-07` 거부 기록 기반 |
| 정확도 | 카테고리 분류 정확도 ≥ 85% | Golden Dataset |
| 정확도 | **금액 항목 추출 정확도** | Golden Dataset · **원문 대조** |
| 정확도 | **금액 계산 정확도 = 100%** | 단위테스트 (`AMT-06`) |
| 보안 | 타 프로젝트 데이터 접근 차단 | `PRJ-08` 침투 테스트 |
| 보안 | API 키는 서버에만 | 프론트 번들 검사 |
| 안정성 | 컨테이너 재기동 후 파일 유지 | `DOC-14` |

**금액 지표를 두 줄로 나눈 것이 중요하다.** 추출은 원문이 정답이라 측정할 수 있고,
계산은 Python 이라 100% 여야 한다. **"AI 가 금액을 얼마나 잘 맞추나" 는 정답이
없어서 측정할 수 없다.**

## 14. 미결 사항 — 착수 전 합의 필요

### 우선순위

| | 안건 |
|---|---|
| 1 | **P0+P1 이 72개, 구현은 20일.** 덜어내기보다 **묶기**로 접근한다 (1절) |
| 2 | 액션아이템(`ANL-03`) 과 금액(`AMT-01`) 중 무엇을 먼저 만들지 |
| 3 | 검수 모드 2단계(`REV-08`~`REV-15`)를 P2 로 두는 것에 동의하는지 |
| 4 | **`DOC-16` 업로드 시 유형 지정.** `ANL-04` 선택 규칙의 전제이므로 먼저 붙어야 한다 |

**2번에 대한 의견** — 액션아이템으로 제안 카드 · 승인 · 역추적 · 태스크 생성
**골격**을 만들고, 금액을 **두 번째 분석기로 얹는** 순서를 권한다. 골격이
재사용되므로 두 번째가 훨씬 싸고, **"분석기를 갈아 끼울 수 있다" 는 주장을
공수 수치로 증명**할 수 있다.

**4번이 순서상 가장 앞이다.** `DOC-16` 이 없으면 `ANL-04` 선택 규칙이 기준값을
받을 수 없다. 업로드 화면 · `documents` 컬럼 · 일괄 배치 지정 세 곳이 걸리므로
**구현 첫 주에 유형 enum 과 저장 방식만 먼저 확정**하고, 나머지는 페이크 값으로
병렬 진행한다. 미니 프로젝트에서 페이크 구현체로 병렬 작업한 방식과 같다.

**참고 — 원래 여기 있던 `ANL-13`(분석기 규격 확장)은 폐기됐다.** 근거 페이지 표시를
범위에서 빼면서 인터페이스 변경이 필요 없어졌고, **세 사람이 서로 기다리는 지점이
하나 줄었다.**

### 설계

| | 안건 |
|---|---|
| 4 | 금액 항목을 `VIEWER` 에게 보여줄지 (`AMT-11`) |
| 5 | 단가 마스터 범위 — 소규모 자체 데이터로 고정할지 |
| 6 | `page_number` 를 0 부터 셀지 1 부터 셀지 |
| 7 | 좌표 기준 이미지를 원본 · 렌더링본 · 전처리본 중 무엇으로 고정할지 |
| 8 | 검수 완료 후 재수정을 허용할지 |
| 9 | 박스 수정 후 텍스트 재조립을 동기로 할지 비동기로 할지 |
| 10 | 분석 결과가 오래됐을 때 자동 재분석할지 사용자 재실행을 요구할지 |
| 11 | 배포 환경 — 클라우드 · 온프레미스 (OCR GPU 필요 여부와 직결) |
| 12 | AI 제공자 — OpenAI 유지 · 로컬 sLLM 병행 |

**5번이 `AMT` 영역 전체의 최대 위험이다.** 단가가 없으면 계산이 성립하지 않는다.
공공 단가 체계를 8주에 다루는 것은 불가능하므로 **소규모 자체 데이터로 고정하고
화면에 "데모 범위의 단가 기준" 을 명시**하는 방향을 권한다. 정하지 않으면 발표에서
"그 숫자 근거가 뭐냐" 로 무너진다.

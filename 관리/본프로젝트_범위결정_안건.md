# 본프로젝트 범위 결정 안건 (D1)

설계·합의 구간 첫날(8/10 월)에 정해야 할 것을 모은 문서다. 인수인계 문서에 남은
미결 항목 **"우선순위 9개 중 무엇을 할지 팀과 정하지 않았다"** 를 닫는 것이 목적이다.

미니 프로젝트의 `참고/D1_결정사항_체크리스트.md` 와 같은 역할이며, 여기서 결정한
내용은 WBS 의 **결정사항 시트**에 옮긴다.

---

## 0. 먼저 — 인수인계 문서를 정정한다

**우선순위 2번 "CER / WER 로 지표 전환" 은 전제가 틀렸다. CER 은 이미 구현되어 있다.**

`backend/app/services/ocr_ground_truth.py` 의 `compute_accuracy()` 를 확인한 결과다.

```
accuracy = max(0, 1 - CER) * 100
CER      = Levenshtein(정답, OCR결과) / len(정답)
```

양쪽 문자열을 `" ".join(text.split())` 로 공백 정규화한 뒤 문자 단위 편집거리를
정답 길이로 나눈다. 이것이 CER 의 정의(`(S+D+I)/N`) 그대로다. 커밋 `f25b58c`
**"compare ai 정확도 측정 방식 변경"**(8/5)에서 들어갔다. 인수인계 문서와
`타팀발표_정리.md` 표를 쓸 때 이 커밋을 반영하지 못했다.

`ground_truth_accuracy` 라는 **이름 때문에 자체 지표로 보였을 뿐, 값은 표준 CER 을
정확도로 뒤집어 표기한 것**이다.

그래서 2번의 남은 일은 "전환" 이 아니라 세 가지다.

| 남은 일 | 이유 |
|---|---|
| `cer` 값을 응답에 그대로 싣는다 | 지금은 `1-CER` 만 내보내 외부 논문·벤치마크와 바로 비교가 안 된다 |
| `wer` 를 추가한다 | 단어 단위는 없다. 문자 단위 편집거리를 공백 분리 토큰에 그대로 적용하면 된다 |
| 정규화 규칙을 문서에 밝힌다 | 공백을 제거하고 재기 때문에 공백 오류는 점수에 안 들어간다. 밝히지 않으면 수치를 부풀린 것으로 보인다 |

**공수가 크게 내려간다.** 2번은 독립 과제가 아니라 1번(저장)에 붙는 작은 일이 된다.

## 3. 9개 항목 재평가

인수인계 문서의 순위를 코드 확인 결과로 다시 매긴 것이다. 공수는 1인 기준 영업일이며
합의 시 조정한다.

| 순위 | 항목 | 코드 근거 (확인함) | 선행 | 공수 |
|---|---|---|---|---|
| 1 | OCR 결과를 테이블에 저장 | `models/document.py` 에 3테이블만 있다. `ocr_compare_router.py` 는 응답만 만들고 저장 호출이 없다 | — | 2 |
| 2 | `cer` · `wer` 노출 | `compute_accuracy()` 가 이미 CER 이다. WER 만 없다 | 1 | **0.5** |
| 3 | 텍스트 / 이미지 영역 시각화 | `LayoutElement` 에 `x` `y` `x2` `y2` `source`("text"/"ocr") 가 이미 있다. 밖으로 안 내보낼 뿐이다 | — | 2 |
| 4 | N+1 해소 | `document_repository.search()` 에 `selectinload` 가 없다. `DocumentListItem` 이 `analyses` 에서 쓰는 값은 `category` · `summary_preview` **2개뿐**이다 | — | 1.5 |
| 5 | 전처리 선택 + 비포 / 애프터 | `preprocessing.py` 에 `PRESET_NONE` `LIGHT` `SCAN` `FULL` 과 `PRESETS` dict, `preprocess_for_layout(preset)` 이 있다 | — | 3 |
| 6 | LLM 재시도 · 폴백 | `retry` · `fallback` 코드가 없다. `category_analyzer.FALLBACK_CATEGORY="기타"` 는 파싱 실패 시 기본 라벨이며 모델 폴백이 아니다 | — | 2 |
| 7 | 3종 병렬 후 자동 채택 | `OcrCompareService.compare()` 가 dict 리터럴에서 3종을 **순차** 호출한다. `easyocr` 만 별도 프로세스다 | 1 | 4 |
| 8 | 유저 / 개발자 화면 분리 | `CMP` 화면이 사용자 경로 `/ocr-compare` 에 있다 | 1, 3 | 3 |
| 9 | 벡터DB + RAG | 없다. PostgreSQL 선정 이유로만 언급했다 | 1 | 8+ |

### 순위가 바뀐 이유

- **2번이 9순위급 잔업으로 내려갔다.** CER 이 이미 있어서다 (0절).
- **시각화가 6위 → 3위로 올라갔다.** `LayoutElement` 에 `x2` `y2` 까지 있어 좌표를 새로
  구할 필요가 없다. 인수인계 문서가 "비용 대비 인상이 가장 크다" 고 본 판단이 코드로
  확인됐다.
- **N+1 이 4위 그대로다.** 다만 범위가 더 좁혀졌다. `DocumentListItem` 이 필요한 값이
  `category` · `summary_preview` 두 개라서, **`documents` 에 컬럼 2개만 붙이면** 된다.

### 함께 처리해야 할 부채 하나

`schemas/ocr_compare.py` 의 `OcrCompareResponse` 가 `paddle` · `tesseract` ·
`easyocr` 를 **고정 필드로 박아두었다.** 엔진을 하나 추가하면 API 응답 스펙이 바뀐다.

추출기는 `ExtractorRegistry` 로 확장에 열려 있는데 OCR 비교 응답만 닫혀 있다.
**1번이나 7번을 할 때 `engines: list[OcrEngineResult]` 로 함께 바꾼다.** 나중에 하면
프론트를 두 번 고쳐야 한다.

## 4. 스코프 3안 — 택일

| | A · 최소 | B · 권장 | C · 도전 |
|---|---|---|---|
| 포함 | 1 · 2 · 3 · 4 | A + 5 · 6 · 7 | B + 8 · 9 |
| 공수 합 | 6 인일 | 15 인일 | 26 인일 |
| 가용(31) 대비 | 19% | 48% | 84% |
| 새로 보여줄 것 | 정확도 추이 · 영역 시각화 | + 전처리 비포/애프터 · 자동 채택 | + RAG |
| 위험 | 낮다. 남는 시간에 무엇을 할지 다시 정해야 한다 | 중간. 7번 병렬화가 변수다 | 높다. 9번은 공수를 모른다 |

**B 를 권한다.** 이유는 세 가지다.

1. 가용의 절반만 쓴다. 미니 프로젝트에서 산출물이 프리즈 뒤로 몰린 원인이 여유를 안
   남긴 것이었다.
2. 발표에서 **비포 / 애프터와 자동 채택** 은 화면으로 바로 보인다. 심사에서 "듣는
   사람이 이해하게" 가 지적된 항목이었다.
3. 9번(RAG)은 공수를 모른다. **모르는 것을 일정에 넣지 않는다.** 남으면 그때 붙인다.

### 7번의 변수 — 병렬화 효과는 추정이다

미니 프로젝트 측정값으로 산술만 해 본 것이다.

| | 순차 | 병렬(이론) |
|---|---|---|
| PaddleOCR 15,541 + Tesseract 931 + EasyOCR 15,496 | 약 31,968ms | 가장 느린 항목 = 약 15,541ms |

**단순 산술로는 절반이지만 실제로는 다르다.** EasyOCR 은 별도 프로세스라 겹치기가
쉽지만, Paddle 과 Tesseract 는 같은 프로세스라 GIL 과 메모리 경합을 받는다. 두 엔진
모두 무거운 연산을 C++ 에서 하므로 GIL 을 놓을 가능성이 높지만 **확인하지 않았다.**

→ 8/17 첫날에 **스레드 2개로 재보고** 나서 7번 착수를 결정한다. 안 나오면 7번을
빼고 B 를 5·6번까지로 줄인다.

미니 프로젝트 담당을 이어받는 배치다. 각자 자기 파트의 코드를 이미 안다.

| 사람 | 미니 프로젝트 | 본프로젝트 안 | 근거 |
|---|---|---|---|
| 김보현 | 조회 화면, 데이터 모델, API 계약 | **1 · 4** + API 계약서 v2, DB 모델링 | 신규 테이블과 비정규화는 데이터 모델 담당 |

**테이블 설계는 김보현이, 저장 호출은 박세현이** 한다. 8/11 모델링 때 같이 정한다.

## 6. 결정 안건

회의에서 이 순서로 정한다. 결정과 함께 **미채택 대안과 그 이유**를 남긴다
(미니 프로젝트 결정사항 29건과 같은 형식).

| ID | 안건 | 선택지 |
|---|---|---|
| D-01 | 스코프 | A / **B** / C |
| D-02 | 9번(RAG) 처리 | 일정에서 빼고 "향후 개선사항" 으로 발표 / 넣는다 |
| D-03 | OCR 결과 테이블 이름과 키 | `ocr_runs` 단일 + `engine` 구분 컬럼 / 엔진별 분리 |
| D-04 | 비교 실행 단위 | 요청 1건 = 1행 / 요청 1건 = 엔진 3행 + 묶음 id |
| D-05 | `OcrCompareResponse` 구조 | `engines: list[...]` 로 변경 / 고정 필드 유지 |
| D-06 | 비정규화 컬럼 | `documents.category` · `summary_preview` 2개 / 별도 요약 테이블 |
| D-07 | 비정규화 값 갱신 시점 | 분석 완료 시 서비스가 함께 쓴다 / 트리거 |
| D-08 | WER 산정 단위 | 공백 분리 토큰 / 형태소 |
| D-09 | LLM 폴백 대상 | 같은 제공자의 하위 모델 / 다른 제공자 |
| D-10 | 재시도 횟수와 백오프 | 2회 · 지수 백오프 / 다른 값 |
| D-11 | 개발자 화면 분리 (8번) | B 에 미포함 · 시간 남으면 / 지금 넣는다 |
| D-12 | 자체 모델 사용 여부 | 상용 API 유지 / 자체 모델 병행 |
| D-13 | 배포 범위 | 로컬 도커 유지 / 클라우드 |
| D-14 | `ISS-046` 로그 누락 | 본프로젝트 착수 첫날 수정 / 유지 |

**D-12 는 1조 사례를 근거로 판단한다.** Gemma 1B 는 입력이 길어질수록 출력이 영어로
쏠렸다. 자체 모델을 쓰면 그 문제를 그대로 만나고, 재번역으로 막으면 지연이 두 배가
된다. 상용 API 유지를 권한다. 다만 `analyses` 에 `model_name` · `tokens_in` ·
`tokens_out` · `latency_ms` 를 이미 쌓고 있으므로 **비교 실험 자체는 언제든 가능하다.**

**D-14 는 지금 고친다.** `business_error_handler` 에 로그 호출이 없어 404 · 409 · 413
이 서버 로그에 남지 않는다. 프리즈 때문에 미뤘던 것이고 한 줄짜리다.

## 7. 발표를 염두에 둔 규칙

심사에서 두 팀 모두 지적된 것들이다. 구현 단계부터 지킨다.

- 기능을 만들 때 **기준과 수치를 함께 기록한다.** "빨라졌다" 가 아니라 "31,968ms →
  ?ms" 로 적는다. 1조가 지적받은 "기준 없음" 을 피하는 방법이다
- 용어는 **한 문장 정의를 먼저** 만든다. 미니 프로젝트에서 "추출기 · 분석기가 무슨
  뜻인가" 를 질문받았다
- 데이터 구조는 **나눈 기준(값의 수명)** 부터 말한다
- 안 한 것은 "미구현" 이 아니라 **"향후 개선사항"** 으로 배치한다
- 통합테스트 시나리오는 문서에는 촘촘하게, 발표에는 대표 사례 하나만

**메모리 열은 이 표에서 뺐다.** `run_eval.py` 값이 틀렸다는 증거가 있고(9절),
믿을 수 있는 값은 3종뿐이다. 9절 표를 본다.

## 2. 기준별로 무엇을 확인했나

### 기준 2 — 차원

`vector(1024)` 로 이미 정했다(비교분석표 1절). 여기서 볼 것은 **후보가 그
차원을 낼 수 있는지**다.

| 차원 | 후보 | 판단 |
|---|---|---|
| 1024 | KURE-v1 · bge-m3 · arctic · BGE-m3-ko · Qwen3 | 컬럼을 안 바꾸고 서로 바꿔 끼울 수 있다 |
| **768** | **nomic-embed-text-v2-moe** | **`vector(1024)` 에 그대로 못 넣는다** |

nomic 을 쓰려면 컬럼을 768 로 바꾸거나 벡터를 채워 넣어야 한다.
**이전 측정에서 768(e5-base)이 384(e5-small-ko-v2)보다도 낮았으므로**
nomic 이 이기지 못하면 볼 이유가 없다. 이기면 그때 컬럼을 다시 논의한다.

**그래서 채택 모델은 나중에 바꿀 수 있다.** 1024 후보 넷 사이에서는 컬럼을
안 건드리고 벡터만 다시 만들면 된다. 그것을 가능하게 하는 조건 세 개
— `embedding_model` 컬럼 · 검색 시 모델 필터 · 접두어의 설정 분리 —
는 `관리/API_계약_RAG_검색_초안.md` **7-1절**에 규정했다.

**Qwen3 재검토 조건** — 처음에 셋을 걸었고 **둘이 충족됐다. 남은 것은 품질뿐이다.**

| | 조건 | 상태 |
|---|---|---|
| 1 | no_overlap 64문항에서 채택 모델보다 **6문항 이상** 우위 | **미충족** — 오히려 **14문항 뒤진다** (27 대 41) |
| 2 | Ollama 지원 (없으면 백엔드에 `torch` 추가) | 충족 — 공식 지원 확인 (4절) |
| 3 | 색인 속도가 감당 가능한지 | 충족 — 649청크 약 13분 (기준 3·7) |

**두 조건이 풀리면서 상황이 바뀌었다.**

**2번** — `torch` 를 백엔드에 넣지 않아도 된다. 현재 AI 의존은 `openai` 한 줄뿐이고
그 상태를 유지할 수 있다. **가장 큰 전환 비용이 사라졌다.**

**3번** — 처음에 "GPU 배포 결정" 으로 적었는데 **틀린 조건이었다.** GPU 가 있어야
쓸 수 있다는 전제 자체가 정밀도를 맞추지 않은 측정에서 나왔다. 조건은
"GPU 가 있느냐" 가 아니라 **"배포 경로에서 감당되느냐"** 이고, CPU 에서 13분이면
감당된다.

**결론 — 채택하지 않는다. 다만 탈락 사유가 바뀌었다.**

| | 처음 | 최종 |
|---|---|---|
| 탈락 사유 | CPU 에서 측정 불가 (속도) | **검색 품질이 낮다** |
| 근거 | `bfloat16` 으로 잰 값 — **무효** | no_overlap 27 대 41 · 전체 85 대 102 |

**속도로 떨어진 것이 아니라 품질로 떨어졌다.** 조건 2·3 을 충족했는데도 1번에서
크게 못 미쳤다. 이쪽이 훨씬 단단한 근거다. 속도는 환경과 설정에 따라 달라지지만
같은 코퍼스·같은 질의·같은 정밀도에서 나온 품질 차이는 그렇지 않다.

### 기준 3·7 — 로컬 실행과 비용

**Qwen3-Embedding-0.6B 는 CPU 에서 쓸 수 있다.** 처음에는 쓸 수 없다고 적었고,
그것이 틀렸다. 경위를 남긴다.

#### 처음에 잰 값과 그 해석

| 항목 | 처음 관측 | 그때 쓴 해석 |
|---|---|---|
| 649청크 임베딩 | 배치 8개당 약 4분 · 전체 추정 5시간 40분 | "나머지보다 약 70배 느리다" |
| 판단 | — | "CPU 배포 전제로 제외" |

#### 실제 원인 — 정밀도가 달랐다

모델이 어떤 정밀도로 올라왔는지 확인하지 않은 것이 원인이었다.

| 모델 | dtype | 파라미터 | 가중치 |
|---|---|---|---|
| `Qwen3-Embedding-0.6B` | **`torch.bfloat16`** | 596M | 1,136MB |
| `dragonkue/BGE-m3-ko` | **`torch.float32`** | 568M | 2,166MB |

**두 모델의 크기가 거의 같다 — 596M 대 568M.** 계산량이 비슷한데 70배가 났다면
모델 특성이 아니다. **`bfloat16` 은 대부분의 CPU 에 하드웨어 가속이 없어
PyTorch 가 느린 대체 경로로 돈다.** Qwen3 계열은 설정에 `bfloat16` 이 들어 있어
그대로 올라왔고, 나머지 후보는 `float32` 로 올라왔다.

`float32` 로 맞춰 다시 재면 이렇다.

| | bfloat16 (처음) | **float32** | 배수 |
|---|---|---|---|
| 100청크당 | 약 3,000초 | **116.65초** | **약 26배** |
| 649청크 전체 | 추정 5시간 40분 | **757초 (12분 37초)** | — |
| 최고 메모리 | — | **4,793MB** | — |

**모델을 바꾸지도, 청크를 줄이지도 않았다.** `bfloat16` 을 `float32` 로 맞춘 것뿐이다.

#### 그래서 기록을 이렇게 고친다

| | 처음에 적은 것 | 실제 |
|---|---|---|
| 다른 후보 대비 | 70배 느리다 | **2~3배 느리다** |
| 649청크 색인 | 5시간 40분 | **약 13분** |
| 판정 | CPU 에서 쓸 수 없다 | **쓸 수 있다** |

**"측정 시간 초과로 제외" 라는 근거는 사라졌다.** 정밀도를 맞추지 않고 잰 값으로
모델을 탈락시킨 것이다. 최종 비교는 9절에서 같은 도구·같은 정밀도로 다시 잰다.

메모리 4,793MB 는 **상한으로 읽어야 한다.** `bfloat16` 으로 올린 뒤 `float32` 로
바꾸는 과정에서 두 벌이 잠시 함께 존재하기 때문이다. 처음부터 `float32` 로
올리면 더 낮아질 수 있다.

#### 여기서 배운 것 — "같은 조건" 은 세 가지다

모델을 나란히 재려면 세 가지를 맞춰야 한다. **이번에 둘은 맞췄고 하나를 놓쳤다.**

| | 조건 | 이번 시험 |
|---|---|---|
| 1 | **접두어** — 모델이 선언한 값을 그대로 쓴다 | 맞췄다 (3절). `nomic` 의 `document` 키가 빈 문자열인 함정도 걸러냈다 |
| 2 | **최대 입력 길이** — 잘림이 없는지 토큰 수로 확인한다 | 맞췄다 (기준 5) |
| 3 | **정밀도(dtype)** | **놓쳤다.** 한 모델만 `bfloat16` 이었다 |

**셋 중 하나만 어긋나도 성능 비교가 아니라 설정 비교가 된다.**
`도구/embed-test/check_model_cost.py` 는 `dtype` 을 출력에 항상 찍는다.

#### 남은 미확인 — 배포 경로

측정은 `sentence-transformers` + PyTorch 다. 배포는 **Ollama**(`app/ai/local_client.py`)
이고 내부가 llama.cpp 에 **양자화된 모델**이다. **다른 실행 경로다.**

| | 측정 경로 | 배포 경로 |
|---|---|---|
| 런타임 | PyTorch | llama.cpp (Ollama) |
| 정밀도 | float32 | 양자화 (Q4·Q8 등) |

**이 차이는 Qwen3 만의 문제가 아니라 후보 전부에 걸린다.** 우리는 `float32` 로
재고 양자화본으로 배포할 예정이며, 그 차이는 아직 재지 않았다(7절).

### 기준 5 — 최대토큰

**청크가 한도를 넘으면 뒤가 조용히 잘린다.** 오류가 안 나므로 점수만 떨어진다.

| 실측 최대토큰 | 후보 |
|---|---|
| **512** | nomic-embed-text-v2-moe · (이전 측정의 e5 계열 전부) |
| 8192 | KURE-v1 · bge-m3 · arctic · BGE-m3-ko |
| 32768 | Qwen3-0.6B |

글자 수로 추측하지 않고 **토크나이저로 직접 셌다.** 한국어는 토크나이저에 따라
글자당 토큰 수가 크게 달라지므로 글자 수는 근거가 못 된다.

| 항목 | 값 |
|---|---|
| 전체 청크 | 649개 |
| 가장 긴 청크 | 697자 |
| 정답 청크 | 62개 |
| **512토큰 초과 청크** (XLM-R 계열) | **0개** |
| **정답 청크 최대** | **306토큰** — 상한 512의 60% |
| 참고: Qwen3 토크나이저 최대 | 620토큰 |

**잘린 청크는 없다.** 상한이 512인 `e5` 3종과 `nomic` 도 이번 측정에서 잘림이
발생하지 않았다. **토큰 잘림은 이번 결과의 변수가 아니다.**

토크나이저가 다르면 토큰 수가 다르다. `e5`·`nomic` 은 XLM-R 계열이므로
`bge-m3` 토크나이저로 셌고, Qwen3 는 자기 토크나이저로 따로 셌다. 같은 청크가
XLM-R 로는 512 이하인데 Qwen3 로는 620토큰까지 나온다. **"몇 토큰인가" 는
모델마다 다른 값이다.**

> **한 번 잘못 짚었던 것** — `e5-large` 점수가 크게 떨어진 것을 토큰 잘림으로
> 단정했는데 **틀렸다.** 잘린 청크가 애초에 없었다. 원인은 아직 모른다(8절).

`nomic` 이 유독 낮게 나오면(실제로 5위였다) 이 항목을 먼저 의심하게 되지만,
**잘림이 없으므로 512토큰 상한은 nomic 의 낮은 점수를 설명하지 못한다.**

### 기준 6 — 무엇을 우선할 것인가

| 임베딩 종류 | 우리에게 필요한가 |
|---|---|
| 낱말 임베딩 | 아니다. 낱말 하나를 찾는 것이 아니다 |
| 문장 임베딩 | 부분적으로. 질의는 한 문장이다 |
| **문단·문서 임베딩** | **이것이다.** 청크(평균 305자)를 넣고 질의로 찾는다 |
| 멀티모달 임베딩 | 아니다. OCR 로 텍스트를 뽑은 뒤에 임베딩한다 |

**멀티모달을 쓰지 않는 이유가 따로 있다.** PDF 를 이미지째로 넣으면 **사람이
고친 OCR 텍스트가 반영되지 않는다.** 우리 설계는 OCR 결과를 사람이 검수한 뒤
그 텍스트를 임베딩한다. 이미지 입력은 그 검수를 무력화한다.

### 기준 8 — 라이선스

**후보 6종 전부 확인했다.** 허브 모델 카드의 `license` 필드를 직접 읽었다
(명령은 5절). AI 요약이나 블로그가 아니라 제작자가 적어 넣은 1차 값이다.

| 모델 | 라이선스 | 상업 이용 |
|---|---|---|
| **`dragonkue/BGE-m3-ko`** | **apache-2.0** | 가능 |
| `Snowflake/snowflake-arctic-embed-l-v2.0` | apache-2.0 | 가능 |
| `nomic-ai/nomic-embed-text-v2-moe` | apache-2.0 | 가능 |
| `nlpai-lab/KURE-v1` | **mit** | 가능 |
| `BAAI/bge-m3` | **mit** | 가능 |
| `Qwen/Qwen3-Embedding-0.6B` | apache-2.0 | 가능 |

`multilingual-e5`(base·large·small-ko-v2)는 MIT 다 (`gh api repos/microsoft/unilm`).

**라이선스로 걸러지는 후보는 없다.** 이 기준은 결과적으로 판별력이 없었다.
다만 확인하지 않고 넘어갔다면 채택 모델이 비상업 라이선스일 위험을 안고
제출했을 것이므로, 확인 자체는 필요한 절차였다.

### 검토 때 나올 질문 하나

> 원본 `bge-m3` 는 MIT 인데 파생본 `BGE-m3-ko` 가 apache-2.0 인 것이 맞나?

**맞다.** MIT 는 재라이선싱을 막지 않는다. MIT 저작물을 수정해 더 엄격한(하지만
여전히 허용적인) Apache-2.0 으로 배포할 수 있고, 원본 MIT 고지만 유지하면 된다.

| | MIT | Apache-2.0 |
|---|---|---|
| 상업 이용·수정·재배포 | 가능 | 가능 |
| 의무 | 저작권 표시 | 저작권 표시 + **변경 사실 고지** + `NOTICE` 보존 |

**모델 가중치를 우리 저장소에 담지 않고 허브·Ollama 에서 받아 쓰므로 실무
부담은 출처·라이선스 표기뿐이다.**

> 같은 연구실의 `KULLM3` 는 **CC-BY-NC**(비상업)다. 이름이 비슷하다고 같은
> 라이선스라고 볼 수 없다. `KURE` 는 MIT 다.

## 3. 접두어 규칙 — 틀리면 그 모델이 억울하게 진다

모델마다 질의와 문서에 붙이는 접두어가 다르다. **잘못 붙이면 성능이 아니라
설정 실수를 재게 된다.**

| 모델 | 질의 접두어 | 문서 접두어 |
|---|---|---|
| KURE-v1 | 없음 | 없음 |
| bge-m3 | 없음 | 없음 |
| BGE-m3-ko | 없음 | 없음 |
| **arctic-embed-l-v2.0** | `query: ` | **없음** |
| **nomic-embed-text-v2-moe** | `search_query: ` | `search_document: ` |
| Qwen3-Embedding-0.6B | `Instruct: ...` + 줄바꿈 + `Query:` | 없음 |
| (이전 측정) e5 계열 | `query: ` | `passage: ` |

### 여기서 걸린 함정

**nomic 이 선언한 값은 이렇다.**

```
"query":    "search_query: "
"document": ""                  <- 비어 있다
"passage":  "search_document: " <- 실제 문서 접두어는 여기
```

`document` 키를 그대로 믿으면 **nomic 문서에 접두어가 안 붙는다.** nomic 은
접두어가 필수인 모델이라 점수가 크게 떨어진다.

**arctic 은 정반대다.** arctic 의 `"document": ""` 는 **진짜로 안 붙이는 것이
맞다** (`passage` 키가 아예 없다). 같은 빈 문자열인데 뜻이 다르다.

그래서 규칙을 이렇게 정했다.

> `passage` 가 있고 비어 있지 않으면 그것을 쓴다. 없으면 `document` 를 쓴다.
> 그것도 비어 있으면 접두어 없음.

Qwen3 의 질의 접두어는 **줄바꿈을 포함하고 `Query:` 뒤에 공백이 없다.**
임의로 공백을 넣으면 조건이 달라진다.

## 4. Ollama 지원 — 배포 기준이지 측정 기준이 아니다

**측정은 Ollama 를 쓰지 않았다.** sentence-transformers 로 6종을 같은 조건에서
쟀다. 이유는 둘이다.

| 이유 | 내용 |
|---|---|
| 조건이 같아진다 | Ollama 는 모델을 양자화해서 배포한다. 원본과 양자화본의 점수가 다르다. 일부는 Ollama 에 없어 섞어 쓰면 비교가 깨진다 |
| 설치가 필요 없다 | 개발기에 Ollama 가 없었다. 수 GB 를 내려받아야 하고 그래도 조건이 달라진다 |

**Ollama 지원 여부는 "배포할 때 쓸 수 있나" 의 정보로만 표에 남긴다.**

| 모델 | Ollama |
|---|---|
| bge-m3 | 공식 |
| arctic-embed-l-v2.0 | 공식 (`snowflake-arctic-embed2`) |
| nomic-embed-text-v2-moe | 공식 |
| Qwen3-Embedding-0.6B | 공식 (`qwen3-embedding:0.6b` · 태그 0.6b·4b·8b) |
| KURE-v1 | 비공식 저장소 (`daynice/kure-v1`) |
| **BGE-m3-ko** (채택) | **공식 없음.** 허깅페이스 전용 — **GGUF 파일 + `Modelfile` 로 직접 등록** |

출처 — <https://ollama.com/library/qwen3-embedding>
사용자 이름이 붙지 않은 공식 라이브러리 경로다. *(라이선스 제약 준수를 위해 내용을 요약해 옮겼다)*

### 채택 모델의 배포 경로에 작업이 하나 붙는다

| 후보 | 배포 작업 |
|---|---|
| `bge-m3` · `arctic-l-v2.0` · `nomic-v2-moe` · `Qwen3` | `ollama pull` 한 줄 |
| **`BGE-m3-ko`** (채택) | GGUF 내려받기 → `ollama create` → 태그 관리 |
| `KURE-v1` | `ollama pull daynice/kure-v1` (비공식 저장소) |

**채택을 뒤집는 사유는 아니다.** 품질이 41 대 37 로 앞서고, 한 번 등록해 두면
이후는 같다. 다만 **임베딩 생성·저장(RAG-02) 에 "모델 등록" 작업이 하나 늘어난다.**
그것을 모르고 일정을 잡으면 막힌다.

**여기서 대안이 값을 한다.** 공식 경로가 꼭 필요하면 `arctic-embed-l-v2.0` 이
`ollama pull` 한 줄로 끝난다. 안겹침 37문항으로 채택 모델과 4문항 차이고
**통계적으로 구별되지 않는다**(8절). 차원이 같아 DB 도 안 건드린다.

**GGUF 변환본의 품질은 재지 않았다.** GGUF 는 양자화본이라 우리가 잰 fp32 점수와
다를 수 있다(7절).

**Tasqra 는 이미 Ollama 를 쓰고 있다** (`app/ai/local_client.py` 가 OpenAI 호환
엔드포인트를 부른다). 임베딩도 Ollama 로 올리면 `torch` 를 넣지 않아도 된다.
**KURE-v1 을 고르면 이 길이 비공식 저장소를 거친다는 점을 알고 골라야 한다.**

## 6. 한국어 RAG 실전 팁 — 우리 측정에서 나온 근거로만

일반론이 아니라 **이번 시험에서 실제로 확인한 것**만 적는다.

### 6-1. 하이브리드 검색이 필요하다 — 우리 데이터가 근거다

평가셋을 **글자가 겹치는 질의(`overlap`)** 와 **뜻으로만 찾아야 하는 질의
(`no_overlap`)** 로 나눠 쟀다. 결과가 갈렸다.

| 모델 | 차원 | overlap | no_overlap |
|---|---|---|---|
| e5-small-ko-v2 | 384 | **36 / 39 (92%)** | **10 / 34 (29%)** |
| KURE-v1 | 1024 | 30 / 39 | **18 / 34** |
| bge-m3 | 1024 | 28 / 39 | 17 / 34 |

*(545청크 기준. 오늘 649청크 재측정으로 갱신 예정)*

**384 모델이 글자겹침 질의에서는 1위이고 의미 질의에서는 최하위였다.**
질의 낱말이 청크에 그대로 있으면 작은 모델도 맞힌다. 반대로 큰 모델도 낱말이
안 겹치면 절반을 놓친다.

**그래서 벡터 검색 하나로는 부족하다.** 낱말 일치(BM25 등)와 벡터 검색을 함께
쓰고 점수를 합치는 편이 두 유형을 모두 잡는다. `RAG-12 유사문서 검색` 에
`mode=hybrid` 를 둔 근거가 이 표다.

### 6-2. 질의 전처리 — 숫자와 조 번호는 따로 다뤄야 한다

고시 조문으로 질의를 만들면서 확인한 것이다.

**조 번호를 질의에 쓰면 측정이 무의미해진다.** "제18조의 배점한도는?" 이라고
물으면 `제18조` 라는 글자가 그 청크에만 있어서 **임베딩 실력이 아니라 글자
일치로** 맞힌다. 그래서 질의를 전부 내용으로만 쓰게 고쳤다.

**운영에서는 뒤집힌다.** 사용자가 "제18조" 라고 물으면 그건 낱말 일치로 찾는
것이 맞다. **즉 조 번호·금액·날짜 같은 값은 벡터가 아니라 낱말 일치로
보내는 것이 낫다.** 질의 전처리에서 이런 토큰을 뽑아내는 것이 6-1의 하이브리드와
같은 결론으로 이어진다.

### 6-3. 청킹 — 이번에 실제로 깨진 것 네 가지

| 문제 | 무슨 일이 있었나 | 대응 |
|---|---|---|
| **문서 하나가 코퍼스를 지배한다** | 계약현황 CSV 20건을 넣었더니 청크가 545 → 3,655 로 늘고 **82% 가 표의 행**이 됐다. 측정 시간이 5개 모델에 122분으로 뛰었다 | 문서당 청크 상한(`--max-per-doc 300`) 과 지배 경고를 도구에 넣었다. CSV 는 코퍼스에서 빼고 분류 학습용으로 돌렸다 |
| **표를 잘못 자르면 머리행이 사라진다** | 표 중간에서 끊으면 아래 조각에 컬럼명이 없다. `계약금액` 이라는 말 없이 숫자만 남는다 | 표는 **행 단위로 자르고 머리행을 조각마다 복제**한다 |
| **양쪽정렬 PDF 는 공백이 사라진다** | 행안부 고시를 PyMuPDF 로 뽑으니 `제1조(목적)이지침은...` 처럼 어절이 붙었다. 공백 비율 9.7% | pdfplumber `x_tolerance=1.5` 로 뽑으니 19.9% 로 복구됐다. **문제 문서만 지정해서 바꿨다** — 전부 바꾸면 기존 청크 번호가 밀려 정답이 어긋난다 |
| **쪽 넘김이 문장을 끊는다** | `...20억원 이상인 사업에 대해` 에서 쪽이 바뀌고 `서는 제안요청 설명회를...` 이 다음 쪽이다. 그 사이에 쪽 표시가 끼어들어 문장이 두 조각으로 갈라졌다 | 아직 안 고쳤다. **쪽 표시를 청크 본문에서 빼고 메타로 옮기는 것**을 검토해야 한다 |

**공백 소실은 제품 결함이다.** `도구/embed-test/convert_inputs.py` 의 주석에
따르면 **본구현(`app/extractors/pdf_extractor.py`)도 PyMuPDF 를 쓴다.** 관공서
고시·지침·계약서는 대부분 양쪽정렬이므로, DocFlow 에 올리면 같은 일이 생긴다.
그 뒤 요약·분류·임베딩이 전부 공백 없는 텍스트를 받는다.
**`관리/산출물_변경대기_목록.md` 에 올려 팀에 알려야 한다.**

## 8. 판정 — 무엇이 갈렸고 무엇이 안 갈렸나

측정 **전에** 판정선을 정해 두었다. 결과를 보고 기준을 옮기지 않기 위해서다.

| 격차 (no_overlap 64문항) | 판정 |
|---|---|
| 6문항 이상 | 실제 차이로 본다 |
| 4~5문항 | 참고. 다른 기준과 함께 판단 |
| 3문항 이하 | 판별 불가 |

### 짝지은 검정 (McNemar)

개수만 세면 "같은 질의에서 누가 맞히고 누가 틀렸는지" 를 모른다.
`results_detail.csv` 의 질의별 적중으로 **엇갈린 질의만** 세어 검정했다.

| 대비 | A만 맞힘 | B만 맞힘 | 엇갈림 | 양측 p | 판정 |
|---|---|---|---|---|---|
| BGE-m3-ko 대 KURE-v1 · no_overlap 64 | 5 | 1 | 6 | **0.22** | **유의하지 않다** |
| BGE-m3-ko 대 KURE-v1 · 전체 133 | 8 | 1 | 9 | **0.039** | **유의하다** |
| KURE-v1 대 bge-m3 · no_overlap 64 | 7 | 5 | 12 | **0.77** | **구별 불가** |

**세 가지가 확정됐다.**

**1. BGE-m3-ko 가 1위다.** 8개 지표(R@1·R@3·R@5·R@10·MRR × overlap·no_overlap·전체)
전부에서 1위다. 한 지표만 튄 것이 아니다.

**2. 그 우위는 조건부로 유의하다.** 전체 133문항에서는 유의하고(p=0.039),
**뜻으로만 찾는 질의 64개만 보면 유의하지 않다(p=0.22).** 64문항 중 6개만
엇갈렸고 58개는 KURE 와 똑같이 움직였다. **미리 정한 6문항 판정선은 넘지 못했다
(4문항).**

**3. 2·3·4위는 서로 구별되지 않는다.** KURE-v1 · arctic · bge-m3 다.
특히 지난 회차에서 "KURE 18 대 bge-m3 17, 1문항 차라 판별 불가" 라고 했던 건이
**p=0.77 로 확인됐다.** 37 대 35 로 벌어져 보였지만 엇갈린 12문항이 7 대 5 로
거의 반반이다. **개수 차이는 우연이었다.** 그때 판단은 맞았지만 근거가 없었고,
이제 근거가 있다.

| | |
|---|---|
| 컬럼 | **`vector(1024)`** (유지) |
| **기본 모델** | **`dragonkue/BGE-m3-ko`** |
| 근거 | 실측 8지표 1위 · 공개 벤치마크 2위 · apache-2.0 · 1024차원 |
| 근거의 한계 | no_overlap 단독으로는 KURE 와 유의차 없음(p=0.22) |
| 대안 | `nlpai-lab/KURE-v1`(mit · 공개 1위) · `snowflake-arctic-embed-l-v2.0` |
| 제외 | `e5` 3종(384·768·1024 모두 하위) · `nomic`(768 · 5위) |
| 제외 | **`Qwen3-Embedding-0.6B`** — 속도가 아니라 **품질**로 떨어졌다 (9절) |

**대안 둘은 실측에서 1위와 구별되지 않으므로 진짜 대안이다.**
교체 절차는 `관리/API_계약_RAG_검색_초안.md` 7-1절에 있다.

### 확인된 부수 사실 셋

**차원이 높으면 좋다는 것은 성립하지 않는다.** 1024인 `e5-large` 가 **최하위(18)**
다. 384인 `e5-small-ko-v2`(19)보다 낮다. 545청크에서도 그랬고 649청크에서도
그렇다. **재현되지만 원인은 모른다.**

상세 결과에 단서가 있다. 질의가 달라도 같은 청크 묶음이 반복해서 1위로 올라온다.

```
e5-large / no_overlap / top5 = 374,300,273,144,186
e5-large / no_overlap / top5 = 374,300,186,144,408
e5-large / no_overlap / top5 = 300,374,273,186,144
```

**이것은 관찰이고 원인이 아니다.** 예전에 토큰 잘림으로 단정했다가 틀렸고
허브 청크 가설도 기각한 적이 있다. 이번에는 단정하지 않는다.

**같은 모델이 1위와 7위를 동시에 한다.** `e5-small-ko-v2`(384)가 글자겹침 질의
69문항 중 **64개(1위)** 인데, 의미 질의 64문항 중 **19개(7위)** 다.
6-1절 하이브리드 검색 근거가 여기서 다시 확인됐다.

**메모리 열은 쓸 수 없다.** 7절에 적었다.

## 9. Qwen3-Embedding 재시험 (진행 중)

**8절 확정은 이 시험 결과와 무관하게 유지한다.** 여기서 나온 값으로 확정을 바꿀
조건은 2절에 미리 적어 두었다. 결과를 보고 기준을 옮기지 않기 위해서다.

### 해결된 것

| 물음 | 답 |
|---|---|
| PyTorch 에서 왜 70배 느렸는가 | **`bfloat16` 으로 올라왔다.** CPU 에 하드웨어 가속이 없어 느린 대체 경로로 돌았다 |
| `max_seq_length` 32768 패딩이 원인인가 | **아니다.** 배치 8개 패딩 모양이 `(8, 398)` 로 정상이었다 |
| 우리 청크의 Qwen3 토큰 수 | 최대 **620토큰** · 평균 225. 상한을 **1024** 로 낮춰도 잘림이 없다 |
| `float32` 로 맞추면 얼마인가 | **100청크당 116.65초 · 649청크 757초(12분 37초)** |
| 색인 속도가 감당되는가 | **된다.** 13분이면 후보 자격이 있다 |

`max_seq_length` 패딩 가설은 산술적으로 맞아떨어져 보였다. 배치당 관측 CPU 시간을
32768토큰 기준으로 나누면 현실적인 처리량이 나왔기 때문이다. **그러나 패딩 모양을
찍어보니 398이었고 가설은 기각됐다.** 계산이 맞는 것과 전제가 맞는 것은 다르다.

### 남은 것

| 물음 | 상태 |
|---|---|
| Qwen3 의 검색 품질이 BGE-m3-ko 를 넘는가 | **넘지 못한다** (아래) |
| 같은 도구·같은 정밀도로 잰 비용 3종 비교 | **측정 중** (아래 표) |
| Ollama(llama.cpp · 양자화) 경로 속도 | 미확인. 후보 전부에 해당 |

### 품질 결과 — 3종 재측정 (`float32` · 649청크 · 질의 133개)

| 모델 | R@1 안겹침 | **R@5 안겹침** | MRR 안겹침 | R@5 겹침 | R@5 전체 |
|---|---|---|---|---|---|
| **`dragonkue/BGE-m3-ko`** | **25 / 64** | **41 / 64** | **0.503** | **61 / 69** | **102 / 133** |
| `nlpai-lab/KURE-v1` | 22 | 37 | 0.457 | 58 | 95 |
| `Qwen/Qwen3-Embedding-0.6B` | 15 | **27** | 0.320 | 58 | 85 |

**Qwen3 가 no_overlap 에서 14문항 뒤진다.** 재검토 조건은 "6문항 이상 **앞설** 때"
였으므로 반대 방향으로 크게 벗어났다. `nomic`(768차원, 27문항)과 같은 수준이다.

**관찰 — 겹침 질의만 보면 Qwen3 가 KURE 와 동점(58)이다.** 글자가 겹칠 때는
잘 찾고 뜻으로만 찾을 때 크게 떨어진다. 6-1절에서 384차원 모델이 보인 것과 같은
모양이다. **다만 왜 그런지는 모른다.** 기본 instruct 문장이 영어라는 점,
마지막 토큰으로 벡터를 만드는 방식 등이 짚이지만 **확인하지 않았다.**

### 재현성이 확인됐다

같은 코퍼스·같은 질의로 두 번 돌렸더니 **품질 수치가 완전히 같았다.**

| 모델 | 8모델 실행 | 3모델 실행 |
|---|---|---|
| `KURE-v1` no_overlap R@5 | 0.578 | **0.578** |
| `BGE-m3-ko` no_overlap R@5 | 0.641 | **0.641** |

**하네스가 결정적으로 동작한다.** 순위가 실행마다 흔들리지 않는다는 뜻이므로,
모델 간 격차를 실행 간 잡음으로 의심할 필요가 없다.

### 반대로 비용 수치는 흔들렸다

| 모델 | 8모델 실행 | 3모델 실행 | 차이 |
|---|---|---|---|
| `KURE-v1` 100청크당 | 56.11초 | **77.67초** | **+38%** |
| `BGE-m3-ko` 100청크당 | 57.36초 | 57.27초 | 거의 같음 |

**같은 모델·같은 코퍼스인데 38% 차이가 났다.** 다른 프로세스와 코어를 나눠 썼거나
발열로 속도가 내려간 것으로 보이지만 확인하지 않았다.
**`run_eval.py` 의 시간 값을 비용 근거로 쓰지 않는 이유가 여기 있다.**

### 메모리 값이 틀렸다는 증거

`run_eval.py` 는 `BGE-m3-ko` 의 메모리를 **1,494MB** 로 찍었다.
그런데 이 모델의 **가중치만 2,166MB** 다(기준 3·7).

> **모델이 자기 가중치보다 적은 메모리를 쓸 수는 없다.**

음수가 나온 것(-359MB)이 우연한 사고가 아니라 **측정 방식 자체가 틀렸다는 증거**다.
현재 사용량을 전후로 재서 빼면 앞 모델이 해제된 몫까지 상계되기 때문이다.

### 비용 재측정 — `check_model_cost.py`

`run_eval.py` 의 비용 값은 쓰지 않는다. 메모리에 음수를 뱉었고(7절), 시간도 같은
자라고 볼 근거가 없다. **모델 하나를 독립 프로세스에서 재는 도구를 따로 만들었다.**

**셋을 순차로 쟀다.** 두 프로세스를 동시에 돌리면 코어를 나눠 쓰게 되어 시간이
부풀어난다. 첫 시도에서 CPU 가 97% 까지 올라간 것이 그 상태였고, 그때 값은 버렸다.

| 모델 | dtype | 상한 | 적재(초) | **100청크당(초)** | 적재직후(MB) | **임베딩중 최고(MB)** |
|---|---|---|---|---|---|---|
| `dragonkue/BGE-m3-ko` | float32 | 8192 | 7.4 | **57.19** | 809 | **2,203** |
| `nlpai-lab/KURE-v1` | float32 | 8192 | 6.9 | **47.51** | 810 | **2,203** |
| `Qwen/Qwen3-Embedding-0.6B` | float32 (강제) | 1024 | 8.0 | **117.70** | 3,951 | **4,801** |

### 이 표가 도구를 검증한다

`BGE-m3-ko` 와 `KURE-v1` 은 **둘 다 `bge-m3` 기반으로 구조가 같다.**
그 둘의 메모리가 **809 대 810 · 2,203 대 2,203** 으로 일치했다.

> 구조가 같은 두 모델이 같은 값을 냈다. **도구가 모델을 재고 있다는 뜻이다.**
> `run_eval.py` 는 같은 모델에 -359MB 와 1,494MB 를 찍었다.

### "적재직후" 값은 그대로 읽으면 안 된다

`BGE-m3-ko` 는 적재직후 **809MB** 인데 **가중치만 2,166MB** 다. 모순처럼 보인다.

원인은 **safetensors 가 파일을 메모리에 매핑(mmap)** 하기 때문이다. 매핑만 해둔
페이지는 실제로 읽을 때까지 사용량에 잡히지 않는다. 임베딩이 시작되면 전 구간을
읽으므로 그때 **2,203MB** 로 올라간다. 가중치 2,166MB + 여유와 맞는다.

> **비용 근거로 쓸 값은 "임베딩중 최고" 다.** "적재직후" 는 아직 안 읽은 몫이
> 빠져 있다.

Spring 으로 바꿔 말하면, `@Lazy` 로 걸어둔 빈을 세면서 "메모리를 안 쓴다" 고
말하는 것과 같다. 실제로 호출되는 시점에 올라온다.

### Qwen3 의 메모리는 이 표에서 과대평가돼 있다

`3,951MB` 는 우리가 잰 방식 때문이다. `bfloat16`(1,136MB)으로 올린 뒤
`model.float()` 로 바꾸므로 **fp32 사본(약 2,270MB)과 원본이 함께 존재한다.**
1,136 + 2,270 ≈ 3,400MB 이고 여유를 더하면 3,951MB 와 맞는다.

**처음부터 fp32 로 올리면 다른 후보와 비슷한 수준일 가능성이 있다.**
그러므로 **Qwen3 의 메모리를 탈락 근거로 쓰지 않는다.** 깨끗한 값이 필요하면
`model_kwargs={"torch_dtype": "float32"}` 로 올려 다시 재야 한다. 아직 안 했다.

### 속도는 한 번씩만 재서 순위를 매길 수 없다

`KURE-v1` 의 100청크당 시간이 실행마다 크게 달랐다.

| 측정 | 값 |
|---|---|
| `run_eval.py` 8모델 실행 | 56.11초 |
| `run_eval.py` 3모델 실행 | 77.67초 |
| `check_model_cost.py` 단독 | **47.51초** |

같은 모델·같은 코퍼스인데 **47.5 ~ 77.7 초로 흩어진다.** 반면 `BGE-m3-ko` 는
57.36 · 57.27 · 57.19 로 거의 붙어 있다. 왜 한쪽만 흔들리는지 **모른다.**

**그래서 `KURE-v1` 이 `BGE-m3-ko` 보다 빠르다(47.5 대 57.2)고 말할 수 없다.**
두 모델은 구조가 같아 속도도 같아야 하고(메모리가 같게 나온 것이 그 증거다),
관측된 차이는 측정 편차로 보는 것이 타당하다. **순위를 매기려면 여러 번 재서
중앙값을 써야 한다. 이번에는 한 번씩만 쟀다.**

**확실하게 말할 수 있는 것은 하나다** — `Qwen3` 는 다른 둘보다
**약 2~2.5배 느리다**(117.7 대 47.5~57.2). 이 격차는 편차 범위를 넘는다.

측정 도구가 지키는 것 셋.

| | 무엇 | 왜 |
|---|---|---|
| 1 | 모델 하나만 올린다 | 앞 모델의 메모리 흔적이 섞이지 않는다 |
| 2 | 최고 사용량(peak)을 읽는다 | 증감을 빼지 않으므로 **음수가 원리적으로 나올 수 없다** |
| 3 | `dtype` 을 항상 출력한다 | 정밀도가 어긋난 비교를 다시 하지 않기 위해 |

### 하네스 변경

`도구/embed-test/run_eval.py` 에 모델별 설정 두 개를 넣었다.

| 키 | 무엇 |
|---|---|
| `force_fp32` | 적재 후 `model.float()`. `bfloat16` 으로 올라오는 모델을 맞춘다 |
| `max_seq_length` | 상한 덮어쓰기. **토큰 수로 잘림이 없음을 확인한 뒤에만 쓴다** |

Qwen3 항목은 주석을 풀고 `force_fp32: True` · `max_seq_length: 1024` 를 넣었다.

### 판정 — 8절 확정을 유지한다

| | |
|---|---|
| 기본 모델 | **`dragonkue/BGE-m3-ko`** (변경 없음) |
| Qwen3 | **채택하지 않는다** |
| 사유 | no_overlap 64문항에서 **27 대 41 로 14문항 뒤진다.** 재검토 조건 1번 미충족 |
| 부수 사유 | 색인 속도 **약 2~2.5배 느림** (117.7 대 47.5~57.2) |
| 근거로 쓰지 않은 것 | **메모리.** 4,801MB 는 우리 측정 방식이 부풀린 값이다 (9절) |

**미리 정한 조건으로 판정했고 기준을 옮기지 않았다.** 조건 2(Ollama)·3(속도)은
충족했으나 1(품질)에서 크게 못 미쳤다.

**이 재시험은 결론을 바꾸지 않았지만 근거를 바꿨다.** 처음의 탈락 사유
"CPU 에서 측정 불가" 는 정밀도를 맞추지 않은 측정이어서 무효였다. 그 상태로
제출했다면 **검토에서 반박당했을 근거**다. 지금은 같은 조건에서 나온 품질 차이가
사유이므로 반박할 지점이 없다.

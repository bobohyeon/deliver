# 임베딩 모델 비교 — `RAG-01`·`RAG-02`·`RAG-10`

**모델과 벡터 차원을 정하기 위한 실험 공간이다.** 여기서 나온 차원이
`pgvector` 컬럼(`vector(N)`)을 결정하므로, **이 결과 전에 마이그레이션을 쓰지
않는다.** 차원을 잘못 잡으면 컬럼 타입을 바꾸고 전체를 다시 임베딩해야 한다.

확정 후에는 `run_eval.py` 가 기능명세서 **`RAG-10` 검색 품질 측정**이 된다.
버리는 작업이 아니다.

| | |
|---|---|
| 두는 곳 | **`C:\dev\embed-test`** — Tasqra 레포 밖 |
| 왜 밖인가 | `torch`·`sentence-transformers` 가 무겁고 모델 파일이 GB 단위다 |
| 실행 환경 | CPU. GPU 없이 돌아간다 |

## 순서

### 1. 문서 넣기 — `corpus/`

`.txt` 또는 `.md` 파일을 넣는다. **5건이면 시작할 수 있다.**

| 출처 | 왜 |
|---|---|
| **우리 팀 미니 프로젝트 문서** | 회의록·결정사항·주간보고. **정답을 우리가 안다** |
| 나라장터 입찰공고 · 과업지시서 | 실제 도메인 문서 |
| 조달청 · 공공데이터포털 | 계약 · 산출내역 서식 |

**우리 팀 문서를 반드시 섞어라.** 우리가 쓴 문서라 "이 질문의 답이 어디
있는지" 를 확실히 알 수 있어 정답 표시가 정확해진다.

샘플 2건이 들어 있다. 형식 참고용이고 실제 문서로 바꿔도 된다.

### 2. 청크로 쪼개기

```powershell
python make_chunks.py
```

`chunks.csv` 가 생긴다. 목표 길이를 바꿀 수 있다.

```powershell
python make_chunks.py --target 500 --max 1200
```

| 옵션 | 뜻 |
|---|---|
| `--target` | 청크 목표 글자 수 (기본 500) |
| `--max` | 이 길이를 넘는 덩어리는 쪼개지 않는다. **표를 자르지 않기 위해서** |
| `--min` | 이보다 짧은 청크는 버린다 (제목만 있는 줄) |

**절 제목(`#`, `제3조`)에서 끊는다.** 그래야 정답을 문단 단위로 표시할 수 있다.
표로 보이는 줄은 이어 붙인다. 중간에서 끊으면 항목과 금액이 분리된다.

### 3. 질의 작성 준비

```powershell
python make_queries.py
```

두 파일이 생긴다.

| 파일 | 용도 |
|---|---|
| `chunks_worksheet.csv` | 청크 번호와 미리보기. **엑셀로 열어 보면서 질의를 쓴다** |
| `queries.csv` | 평가셋. 여기를 채운다 |

### 4. 질의 쓰기 — 여기가 핵심이다

**질의를 "구하는" 게 아니라 문서에서 역으로 뽑는다.** 답이 청크에 적혀
있으므로 도메인 지식이 거의 필요 없다.

`queries.csv` 를 이렇게 채운다.

| `query` | `gold_chunk_ids` | `kind` | `note` |
|---|---|---|---|
| 특급기술자 단가 | `1` | `overlap` | |
| 인건비를 얼마로 잡았나 | `1` | `no_overlap` | |
| 이관 대상 시스템 확정 | `7` | `overlap` | |
| 무엇을 옮기기로 했나 | `7` | `no_overlap` | |

정답이 여러 개면 `1,3` 처럼 쉼표로 적는다.

#### 두 종류를 꼭 나눠서 만든다

| `kind` | 규칙 | 무엇을 재나 |
|---|---|---|
| `overlap` | 청크의 단어를 그대로 쓴다 | 기준선. 기존 `ILIKE` 검색으로도 찾힌다 |
| **`no_overlap`** | **청크의 단어를 하나도 쓰지 않는다** | **의미 검색만 찾을 수 있다** |

**`no_overlap` 이 임베딩을 쓰는 근거다.** `RAG-04` 완료 판정 기준이 "글자가
하나도 겹치지 않는 질의로 찾아진다" 이므로, 여기서 이겨야 한다.
`overlap` 만 재면 지금 검색과 차이가 안 보인다.

#### 단어를 바꾸는 요령

| 청크의 표현 | 질의에서 |
|---|---|
| 특급기술자 · 인월 · 단가 | **인건비** · 사람 값 · 몇 명 |
| 제경비 110% | **간접비 비율** |
| 검사조서 · 준공 | **다 끝났는지 확인** |
| 과업변경합의서 | **일이 늘어난 것** |
| 대가지급청구서 | **돈 받는 절차** |

#### LLM 으로 초안 받기

```powershell
python make_queries.py --prompt 10
python make_queries.py --prompt 10 --start 10
```

출력을 복사해 아무 LLM 에 붙여넣으면 질의 초안이 나온다. **검수해서**
`queries.csv` 에 넣는다. 30개 만드는 데 30분 정도다.

**15개로 시작해도 방향은 보인다.** 완벽한 평가셋을 만들려다 시작이 늦어지는
게 더 큰 위험이다.

### 5. 하네스 점검 — 모델 내려받기 전에

```powershell
python run_eval.py --self-test
```

가짜 인코더로 채점 로직만 확인한다. 모델을 내려받지 않으므로 즉시 끝난다.

**`overlap` 이 `no_overlap` 보다 높게 나오면 정상이다.** 가짜 인코더는 글자
겹침만 보기 때문이다. 그 차이가 그대로 나타나면 하네스가 제대로 돈다.

여기서 `no_overlap` 질의 수가 0 이면 경고가 나온다. 그러면 4번으로 돌아간다.

### 6. 실제 비교

```powershell
python run_eval.py
```

처음에는 모델을 내려받는다. 3개 합쳐 몇 GB 다.

CPU 에서 반복할 때는 청크를 줄인다.

```powershell
python run_eval.py --limit-chunks 100 --batch-size 4
python run_eval.py --only KURE --only e5-small
```

| 옵션 | 뜻 |
|---|---|
| `--limit-chunks` | 앞에서 N개만 쓴다. 빠른 반복용 |
| `--batch-size` | 메모리가 부족하면 줄인다 (기본 8) |
| `--only` | 모델 이름 일부로 골라 실행 |

## 결과 읽는 법

두 파일이 나온다.

| 파일 | 내용 |
|---|---|
| `results.csv` | 모델별 요약 |
| `results_detail.csv` | **질의별 상세.** 틀린 질의를 여기서 확인한다 |

### 판단 순서

| | 볼 것 | 왜 |
|---|---|---|
| 1 | **`no_overlap` 의 `R@5`** | **의미 검색이 실제로 되는가.** 이게 1순위다 |
| 2 | `no_overlap` 의 `MRR` | 정답이 몇 번째로 나오나 |
| 3 | `100청크당 초` | CPU 로 감당되는가 |
| 4 | `메모리 MB` | 다른 모델과 같이 띄울 수 있는가 |
| 5 | `차원` | **`pgvector` 컬럼을 정한다** |

`overlap` 점수가 높은 건 당연하다. **거기서 이겨도 임베딩을 쓸 근거가 되지
않는다.** 키워드 검색으로도 되는 일이다.

### 틀린 질의를 반드시 열어본다

`results_detail.csv` 의 `top5` 를 보면 **모델이 무엇을 대신 찾았는지** 보인다.

| 원인 | 신호 | 대응 |
|---|---|---|
| 질의가 애매하다 | 모든 모델이 똑같이 틀린다 | 질의를 고친다 |
| 청크가 너무 크다 | 엉뚱한 절이 1위 | `--target` 을 줄인다 |
| 정답 표시가 틀렸다 | `top1` 이 사람 눈에는 맞아 보인다 | `gold_chunk_ids` 를 고친다 |
| 모델이 못한다 | 한 모델만 틀린다 | 그게 결론이다 |

**첫 실행에서는 대개 질의나 정답 표시가 문제다.** 모델을 의심하기 전에
상세를 먼저 본다.

## 비교 대상 모델

`run_eval.py` 의 `MODELS` 에 있다. **접두어 규칙이 공정성을 정한다.**

| 모델 | 차원 | 접두어 | 이 모델로 답하는 질문 |
|---|---:|---|---|
| `BAAI/bge-m3` | 1024 | 없음 | **기준선.** 한국어 특화가 이걸 못 이기면 의미 없다 |
| `nlpai-lab/KURE-v1` | 1024 | 없음 | **한국어 특화가 효과 있나** |
| `dragonkue/multilingual-e5-small-ko-v2` | 384 | `query: `/`passage: ` | **작은 모델로 충분한가.** CPU 현실성 |

**`e5` 계열은 접두어가 필수다.** 빼면 성능이 크게 떨어진다. 모델을 추가할
때는 반드시 모델 카드에서 접두어 규칙을 확인하고 `MODELS` 에 적는다.
**규칙을 섞으면 한쪽이 억울하게 진다.**

### 나중에 추가할 후보

| 모델 | 차원 | 언제 |
|---|---:|---|
| `dragonkue/BGE-m3-ko` | 1024 | 1라운드에서 `bge-m3` 가 유망할 때 |
| `nlpai-lab/KoE5` | 1024 | KURE 와 비교 |
| `mykor/KURE-v1-gguf` | 1024 | **CPU 속도가 문제일 때.** 양자화판 |
| CLOVA Studio 임베딩 | 확인 필요 | **유료.** 로컬로 좁힌 뒤 마지막에 |

**CLOVA 를 볼 때 `bge-m3` 를 호스팅하는지 확인한다.** 같은 가중치면 로컬
테스트 결과가 그대로 적용되고, 비교가 "성능" 이 아니라 "직접 띄우기 vs API"
로 단순해진다.

## 차원이 리비전을 묶는다

```
1024 로 정하면   bge-m3 · KURE-v1 · BGE-m3-ko · KoE5 를 자유롭게 바꿔 끼운다
 384 로 정하면   e5-small-ko-v2 계열만 쓸 수 있다
```

**차원이 다른 모델로 나중에 바꾸면 컬럼 타입을 바꾸고 전체를 다시 임베딩해야
한다.** 그래서 후보 대부분이 1024 인 점을 감안해 **1024 를 기본으로 보되,
CPU 속도가 감당 안 되면 384 를 택한다.**

우리는 실시간 데모가 아니라 **영상을 촬영해 발표**한다. 최종 실행을 GPU
장비에서 하면 CPU 속도 문제가 사라진다. 그 점도 판단에 넣는다.

## 알려진 제약

| | |
|---|---|
| `run_eval.py` 는 이 저장소에서 실행 검증하지 못했다 | 샌드박스에 `numpy`·`torch` 를 설치할 수 없다 |
| 검증한 것 | 청킹·워크시트 생성·CSV 처리·**채점 수식(Recall·MRR)을 손계산과 대조** |
| 첫 실행 시 | `--self-test` 로 하네스를 먼저 확인한다 |

`make_chunks.py` 는 실제로 돌려 확인했다. 처음에는 마크다운 제목을 경계로
보지 않아 문서 하나가 통째로 한 청크가 되는 문제가 있었고, 절 제목에서 끊도록
고쳤다.

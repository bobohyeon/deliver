# LLM 파인튜닝 데이터 규격 — 분류 · 갭분석 (2026-08-26)

세현님 LLM 학습용 데이터를 **일관된 형식**으로 만들기 위한 규격이다. 세현님이
검토·참고·사용 여부를 정한다(학습 주체는 세현님). 이 문서는 방법론이고 실제
원본 자료는 담지 않는다(deliver 는 public).

## 이 문서에 나오는 ID ↔ 작업명

| ID | 작업명 | 출력 |
|---|---|---|
| `ANL-001-2` | 문서 유형 분류 | `document_type`(8종 중 1) + `reason` |
| `REC-001` | 액션 태스크 추천 · 프로젝트 갭 분석 | 추천 배열(`title`·`description`·`reason`·`source`) |
| `ANL-002-1` | 액션 아이템 추출(선택) | 배열(`title`·`assignee_hint`·`due_date`·`confidence`·`reason`) |

## 왜 이 데이터인가 — 세현님 고민

> **모델이 `RFP` 와 `PROPOSAL` 을 잘 구분하지 못한다.**

둘은 겉모습(사업개요·과업범위·유사 목차)이 비슷하다. 그래서 데이터의 중심은
**둘을 가르는 신호를 모델이 배우게 하는 것**이다. 아래 §3 판별 루브릭이 핵심이고,
데이터에는 **헷갈리는 대조쌍(hard case)** 을 반드시 섞는다.

## 1. 도메인 · 라벨 (고정)

도메인은 **공공 SI·용역 사업**. 문서 유형은 **8종 고정**이며 이 밖의 값을 라벨로
쓰면 앱이 못 받는다(`documents.document_type` enum 은 `BILLING` 포함 9개지만,
분류 카테고리에서 `BILLING` 을 빼기로 해 학습 라벨은 8종이다 — 아래 표 주석 참고).

| 값 | 뜻 | 작성 주체 |
|---|---|---|
| `RFP` | 제안요청서 · 입찰공고 | **발주처** |
| `PROPOSAL` | 제안서 · 기술제안서 | **수행사(제안사)** |
| `COST_SHEET` | 산출내역서 · 견적서 · 원가계산서 | 수행사/발주처 |
| `CONTRACT` | 계약서 · 과업지시서 · 착수신고서 | 양자 |
| `CONTRACT_CHANGE` | 변경계약서 · 과업변경합의서 | 양자 |
| `REPORT` | 착수/주간/월간/완료보고서 · 검사조서 | 수행사 |
| `MEETING_NOTES` | 회의록 | 양자 |
| `ETC` | 위 어디에도 안 맞음 · **대가지급청구서·세금계산서(구 `BILLING`)** | — |

> **`BILLING` 은 뺀다(2026-08-26, 세현님 결정).** 분류 카테고리에서 제거하고
> 청구서·세금계산서류는 `ETC` 로 흡수한다. 그래서 라벨은 **8종**이다.

## 2. 출력 형식 (JSON) — 스키마가 곧 계약

파인튜닝 예시는 **messages JSONL** 한 줄이 한 예시다. `assistant` 내용은
**반드시 유효한 JSON 문자열**이고 아래 스키마를 지킨다(값을 지어내지 않음).

### 2-1. 문서 유형 분류 `ANL-001-2`
```json
{"messages":[
 {"role":"system","content":"문서를 8종 유형 중 하나로 분류하고 근거를 한 문장으로 쓴다. 유형: RFP,PROPOSAL,COST_SHEET,CONTRACT,CONTRACT_CHANGE,REPORT,MEETING_NOTES,ETC"},
 {"role":"user","content":"<문서 본문(발췌)>"},
 {"role":"assistant","content":"{\"document_type\":\"RFP\",\"reason\":\"...판별 신호를 인용한 한 문장...\"}"}
]}
```
- `document_type`: 8종 중 정확히 하나
- `reason`: **왜 그 유형인지** 한 문장. RFP/PROPOSAL 이면 §3 의 판별 신호를 반드시 인용

### 2-2. 갭 분석 · 태스크 추천 `REC-001`
```json
{"messages":[
 {"role":"system","content":"프로젝트 문서 흐름을 분석해 놓친 작업을 근거·출처와 함께 제안한다. 없는 사실을 지어내지 않는다."},
 {"role":"user","content":"[프로젝트 문서 목록/흐름 요약]\n- ...\n- ..."},
 {"role":"assistant","content":"[{\"title\":\"...\",\"description\":\"...\",\"reason\":\"...\",\"source\":[\"문서명(날짜)\"]}]"}
]}
```
- `source`: 근거가 된 문서를 반드시 명시. **문서에 없는 갭은 만들지 않는다**
- 놓친 작업이 없으면 빈 배열 `[]` 이 정답이다(억지 추천 금지 — 이런 음성 예시도 넣는다)

### 2-3. 액션 아이템 추출 `ANL-002-1` (넣기로 하면)
```json
{"role":"assistant","content":"[{\"title\":\"...\",\"assignee_hint\":\"홍길동\",\"due_date\":null,\"confidence\":0.82,\"reason\":\"...\"}]"}
```
- `due_date`: 기한 불명확이면 `null`(추정 금지) · `assignee_hint`: 문서에 적힌 이름만
- `confidence`: 0~1

## 3. RFP ↔ PROPOSAL 판별 루브릭 (이 데이터의 핵심)

**한 문장 규칙**: 문서가 **무언가를 요구·평가**하면 `RFP`, 무언가를
**하겠다고 약속·제안**하면 `PROPOSAL`. 목차가 아니라 **작성 주체와 방향**으로 정한다.

| | `RFP` (발주처가 씀) | `PROPOSAL` (수행사가 씀) |
|---|---|---|
| 방향 | 요구·요청·평가 | 약속·제안·이행 |
| 대표 표현 | "제출하여야 한다", "제안요청 사항", "평가 배점/방법", "입찰 참가자격", "유의사항" | "당사는 ~을 제안합니다", "~하겠습니다", "추진 전략", "투입 인력", "유사 수행실적" |
| 주체 표지 | 발주기관명·공고번호·입찰일정 | 제안사(회사)명·CI·"당사/폐사" |
| 목차 예 | 사업개요·과업범위·제안요청사항·평가방법·제출안내·계약조건 | 제안개요·사업이해·추진방안·사업관리·투입인력·실적·기대효과 |

### 헷갈리는 대조(hard case) — 반드시 데이터에 넣는다
1. **제안서가 RFP 요구사항을 그대로 인용(요구사항 대응표)** → RFP 처럼 보인다.
   판별: 그 요구에 **"대응/이행 방안"이 붙으면** `PROPOSAL`.
2. **RFP 의 "제안요청 사항"에 '제안' 단어가 잦다** → PROPOSAL 로 오인.
   판별: **요청하는 쪽**이면 `RFP`.
3. **둘 다 사업개요·과업범위가 유사** → 표지 말고 주체·방향으로.

`reason` 은 이 판별 신호를 **직접 인용**한다. 예: "'제출서류 및 평가 배점'을
발주처가 요구하는 형식이라 RFP" / "요구사항마다 '당사 이행방안'이 붙어 제안서".

## 4. 가공 원칙 — "너무 깨끗하지 않게"

세현님 요청: 처음부터 만든 **매끈한 데이터는 실제와 달라 쓸모가 준다.**
그래서 **실제로 찾은 자료를 가공**하고, 다음 노이즈를 **살린다**:
- 표가 텍스트로 풀리며 생긴 깨진 줄·정렬, OCR 오탈자, 관공서 상투구·머리말/꼬리말
- 발췌는 문서 앞부분만 자르지 말고 **판별 신호가 있는 구간**을 포함
- 단, 개인정보(주민번호·연락처·실명 등)와 비공개 식별정보는 **가린다/치환한다**

## 5. 구성 비율(제안, 세현님이 조정)

100개 기준 초안 — 분류 60 / 갭분석 30 / 액션아이템 10.
분류 60 중 **RFP·PROPOSAL 대조쌍에 절반 이상**을 배정하고, 나머지 7종도 최소
2~3개씩 커버. 갭분석엔 **빈 배열(추천 없음) 음성 예시**를 몇 개 포함.

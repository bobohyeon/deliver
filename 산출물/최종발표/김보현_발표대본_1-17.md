## 대본 사용 방법

- 일반 문장은 그대로 말해도 되는 발표 대본입니다.
- 대괄호 안의 문장은 말하지 않고 행동만 합니다.
- 숫자는 급하게 읽지 말고, 숫자가 뜻하는 바를 이어서 설명합니다.
- 시간이 부족하면 문서 끝의 `시간 조절표`에 적힌 부분을 줄입니다.

## 1번 — 프로젝트 소개

**예상 시간: 50초**

안녕하세요. 공공 SI·용역 프로젝트의 문서를 근거 있는 실행으로 연결하는 서비스, Tasqra를 발표할 김보현입니다.

저희가 다루는 타깃은 공공 SI를 중심으로 한 공공 용역 사업의 수행 문서입니다. 제안요청서와 계약서, 과업지시서, 착수·주간·완료 보고서처럼 사업의 시작부터 수행과 완료까지 이어지는 문서를 대상으로 합니다.

Tasqra는 이 문서를 읽고 검색 가능한 형태로 준비한 뒤, 인공지능이 제안한 정보를 사람이 확인하고 태스크와 대시보드, 산출물로 연결합니다.

오늘 발표에서는 먼저 왜 이 타깃을 선택했는지 말씀드리고, 시스템 구조와 검색 실험, 사람 검토와 업무 연결 순서로 설명드리겠습니다.

## 2번 — 타깃 선정과 실제 데이터 한계

**예상 시간: 1분 20초**

저희가 공공 SI·용역을 타깃으로 선정한 최초 이유는 데이터 접근성이었습니다.

나라장터 등에 공개된 문서가 많기 때문에, 학습과 검증에 필요한 데이터를 비교적 쉽게 확보할 수 있을 것으로 예상했습니다. 그래서 공공 SI를 중심으로 한 공공 용역 사업의 수행 문서를 프로젝트 대상으로 정했습니다.

하지만 프로젝트를 진행하면서 원문이 많다는 것과 학습·평가 데이터가 충분하다는 것은 다르다는 점을 확인했습니다. 공개된 원문 문서는 많았지만, 모델이 맞게 찾았는지 판단할 수 있는 정답 표시가 된 샘플은 부족했습니다. 결국 실제 문서를 직접 정리하고 평가 기준을 만들어야 했습니다.

[하단 문장을 가리키기]

타깃을 선정한 뒤에는 이 분야가 서비스 문제와도 맞는다는 점을 확인했습니다. 제안요청서부터 계약과 과업, 보고 문서까지 정보가 이어지고, 기한과 금액, 계약 이행 의무처럼 중요한 정보에는 원문 근거와 사람의 확인이 필요했습니다.

정리하면 데이터가 많을 것이라는 가설로 타깃을 정했고, 프로젝트를 진행하며 실제 문제의 적합성과 데이터의 한계를 함께 확인했습니다.

**예상 시간: 1분 10초**

첫째, 프로젝트에 문서를 업로드합니다.

둘째, PDF에 들어 있는 글자를 읽거나 스캔 문서에 OCR을 적용해 검색과 분석에 사용할 본문을 준비합니다.

넷째, 추출된 정보는 사람이 승인하거나 수정하고, 필요하지 않은 정보는 거절합니다.

다섯째, 승인된 정보만 태스크와 대시보드, 산출물로 연결합니다.

## 6번 — 서비스 전체 구조

**예상 시간: 1분 15초**

이제 이 흐름을 실제로 동작시키는 서비스 구조를 설명드리겠습니다.

왼쪽은 React로 만든 사용자 화면이고, 가운데는 FastAPI 서버입니다. 사용자의 일반적인 요청은 서버가 바로 처리합니다.

문서 추출이나 인공지능 분석처럼 시간이 오래 걸리는 작업은 오른쪽의 비동기 처리 경로로 보냅니다. Redis가 작업을 전달하고 Celery 작업 프로그램이 이를 처리합니다. 이 구조를 사용하면 오래 걸리는 작업 때문에 화면 요청 전체가 멈추는 것을 피할 수 있습니다.

아래에는 함께 사용하는 저장 공간이 있습니다. PostgreSQL에는 프로젝트와 문서, 업무 데이터와 의미 검색 정보를 저장하고, 문서 원본은 공유 파일 경로에 보관합니다. 내부 인공지능은 Ollama의 호환 요청 형식으로 연결했습니다.

핵심은 화면, 서버, 작업 프로그램이 같은 데이터와 문서 파일을 기준으로 움직인다는 점입니다.

## 7번 — 데이터 연결 관계

**예상 시간: 55초**

데이터 구조는 프로젝트와 문서를 중심으로 연결됩니다.

한 프로젝트에는 여러 구성원과 여러 문서가 있고, 각 문서에는 추출한 본문, OCR 검수 기록, 분석 결과와 검색용 문서 조각이 연결됩니다.

태스크와 검토 정보도 프로젝트에 연결됩니다. 검토 정보에는 결정사항, 일정, 계약 이행 후보, 금액처럼 사람이 확인해야 하는 항목이 포함됩니다.

문서 파일 자체를 데이터베이스 안에 큰 데이터로 넣지는 않았습니다. 공용 파일 경로에 저장하고, 데이터베이스에는 파일 위치와 문서 정보를 저장합니다.

이 구조를 통해 어떤 검색 결과와 분석 결과가 어느 프로젝트의 어느 문서에서 나왔는지 추적할 수 있습니다.

## 8번 — 작업별 상태 분리

**예상 시간: 1분**

문서를 처리할 때는 문서 읽기, OCR 검수, 인공지능 분석이 차례대로 일어납니다. 하지만 저희는 이 상태를 하나로 합치지 않고 각각 따로 관리했습니다.

문서 읽기는 대기, 읽는 중, 읽기 완료 상태를 가집니다. OCR 검수는 대기, 검수 중, 완료 상태를 따로 가집니다. 인공지능 분석도 대기, 분석 중, 완료 또는 일부 완료, 실패 상태를 별도로 저장합니다.

이렇게 분리한 이유는 한 단계의 실패가 이미 성공한 다른 단계까지 되돌리지 않게 하기 위해서입니다.

예를 들어 인공지능 분석이 실패하더라도 이미 끝난 문서 추출과 OCR 검수 결과는 유지합니다. 따라서 실패한 작업만 다시 처리할 수 있고, 현재 어느 단계에서 문제가 생겼는지도 명확하게 확인할 수 있습니다.

## 9번 — RAG 검색 준비 과정

**예상 시간: 1분 10초**

이제 제가 담당한 RAG 검색 흐름을 설명드리겠습니다.

먼저 OCR 검수가 끝난 확정 본문을 가져옵니다. 이 본문을 한 번에 검색하지 않고 문단 구조를 기준으로 읽기 좋은 크기로 나눕니다. 현재는 최대 480개 단위로 자르고, 앞 내용 48개를 겹쳐서 문맥이 경계에서 끊기는 것을 줄였습니다.

다음으로 각 문서 조각의 뜻을 BGE-m3-ko 모델을 이용해 검색용 숫자로 바꾸고 PostgreSQL의 pgvector에 저장합니다.

사용자가 질문하면 질문도 같은 방식으로 숫자로 바꿉니다. 그다음 사용자가 권한을 가진 프로젝트 안에서 뜻이 가까운 문서 조각을 찾습니다.

검색 결과에는 유사한 문장만 보여주는 것이 아니라 문서명, 페이지, 원문 위치를 함께 반환합니다.

주의할 점은 검색 모델을 바꾸면 숫자의 기준도 달라진다는 것입니다. 따라서 모델을 변경하면 기존 문서도 새 모델로 다시 색인해야 합니다.

## 10번 — 하이브리드 검색

**예상 시간: 1분 10초**

의미 검색만으로는 숫자와 코드처럼 정확히 일치해야 하는 표현을 놓칠 수 있습니다. 반대로 키워드 검색만 사용하면 표현이 달라졌지만 뜻은 같은 문장을 찾기 어렵습니다.

그래서 Tasqra는 두 검색을 함께 사용합니다.

왼쪽의 키워드 검색은 입력한 글자가 실제로 포함된 문장을 찾습니다. 숫자, 계약 조항, 문서 코드처럼 정확한 표현에 강합니다.

오른쪽의 의미 검색은 질문과 문장의 뜻을 비교합니다. 표현이 달라도 문맥이 비슷한 결과를 찾는 데 강합니다.

두 검색의 점수는 의미가 서로 달라서 직접 더하지 않았습니다. 대신 각 검색에서 앞에 나온 결과에 더 높은 점수를 주는 순위 합산 방식으로 최종 순서를 정했습니다. 현재는 두 검색에서 각각 상위 30개씩을 비교합니다.

사용자는 검색 방식을 따로 선택할 필요 없이 검색창 하나만 사용합니다.

## 11번 — 검색 규모 실험

**예상 시간: 1분 40초**

검색 기능에서 가장 중요하게 확인한 것은 문서 조각이 많아져도 정답을 앞에 보여줄 수 있는가였습니다.

이 그래프는 같은 BGE-m3-ko 모델과 같은 질문 214개를 사용하고, 검색 대상이 되는 문서 조각 수만 바꾼 결과입니다.

[왼쪽 첫 지점을 가리키기]

비교 대상이 30개일 때 첫 번째 결과의 정답률은 90.2퍼센트였습니다.

[오른쪽 마지막 지점을 가리키기]

하지만 전체 1,339개 문서 조각을 대상으로 검색했을 때는 36.9퍼센트까지 낮아졌습니다. 상위 5개 안에 정답이 있는 비율도 98.9퍼센트에서 74.3퍼센트로 낮아졌습니다.

여기서 첫 번째 결과의 정답률은 질문마다 첫 결과가 정답이면 성공으로 세는 비율입니다. 상위 5개는 정답이 다섯 개 안에 하나라도 있으면 성공으로 계산했습니다.

따라서 이 실험이 보여주는 것은 모델이 작은 범위에서는 잘 찾더라도 검색 대상이 커지면 정답을 첫 번째로 올리는 능력이 크게 떨어진다는 점입니다.

이 수치는 문서 수를 30개로 제한하자는 의미가 아닙니다. 검색 후보 범위를 바꾼 실험 결과이며, 저희의 다음 목표는 문서 수를 제한하지 않고도 첫 검색 결과의 정답률을 높이는 것입니다.

## 12번 — 검색 결과 재정렬

**예상 시간: 1분 30초**

검색 결과의 첫 순위를 개선하기 위해 박세현님이 리랭커를 학습했습니다.

리랭커는 처음 검색된 후보의 본문을 질문과 함께 다시 읽고, 정답 가능성이 높은 순서로 재배치하는 모델입니다.

실험 결과 첫 결과 정답률은 학습 전 34.11퍼센트에서 학습 후 49.07퍼센트로 올라갔습니다. 차이는 14.96퍼센트포인트입니다. 상위 5개 안에 정답이 있는 비율도 학습 후 80.84퍼센트까지 개선되었습니다.

다만 리랭커에는 명확한 한계가 있습니다. 처음 검색한 후보 안에서 순서만 바꿀 수 있기 때문에, 후보에 정답이 없으면 새로 찾아올 수 없습니다.

따라서 먼저 넓은 범위에서 정답 후보를 안정적으로 찾고, 그다음 리랭커로 첫 순위를 개선해야 합니다.

현재 리랭커는 그래픽 장치 사용을 권장하기 때문에 기본 설정에서는 꺼져 있습니다. 오류가 발생하면 검색 전체를 실패시키지 않고 기존 검색 순서를 사용하도록 했습니다. 측정된 한 번의 처리 시간은 0.192초였습니다.

## 13번 — 근거가 있는 질의응답

**예상 시간: 1분 15초**

검색 결과는 최종적으로 근거가 있는 질의응답에 사용됩니다.

먼저 사용자의 프로젝트 권한 범위 안에서 글자 검색과 의미 검색을 수행해 최대 24개의 후보를 찾습니다.

그다음 짧게 잘린 미리보기가 아니라 문서 조각의 원문을 다시 가져옵니다. 중복 문장을 제거하고, 최대 8개 문서 조각을 모델이 읽을 자료로 구성합니다.

인공지능은 답변과 함께 사용한 근거 번호를 반환합니다. 서버는 이 번호가 실제 검색 결과에 존재하는지, 사용 권한 범위 안인지, 중복되지는 않았는지 다시 확인한 뒤 문서명과 페이지, 원문 위치를 연결합니다.

근거가 없으면 인공지능을 호출하지 않고 근거를 찾지 못했다는 정해진 안내를 반환합니다.

다만 이 서버 검증이 답변 내용 자체가 사실인지 판단하는 것은 아닙니다. 서버가 보장하는 범위는 근거 번호가 유효한지와 사용 권한이 있는지까지입니다.

## 14번 — 정보 종류별 사람 검토

**예상 시간: 1분 5초**

지금까지 검색과 분석 과정을 설명드렸습니다. 이제 이 결과를 실제 업무에 반영하기 전에 어떤 검토를 거치는지 말씀드리겠습니다.

모든 인공지능 결과는 먼저 검토 대기 상태로 저장됩니다. 하지만 정보 종류마다 사람이 할 수 있는 작업과 승인 뒤의 반영 위치는 다릅니다.

결정사항과 일정은 승인, 수정 승인, 거절이 가능하고, 승인된 내용은 확정 목록과 보고서에 사용됩니다.

금액도 승인, 수정 승인, 거절 과정을 거치며, 모든 검토가 끝난 확정본이 대시보드와 질의응답, 산출물에 사용됩니다.

계약 이행 태스크 후보는 현재 승인과 거절을 지원합니다. 승인하면 실제 태스크가 만들어지고, 거절하면 후보에서 제외됩니다.

핵심은 모든 제안을 한곳에 똑같이 반영하는 것이 아니라, 정보 종류에 맞는 기능으로만 연결한다는 점입니다.

## 15번 — 계약 이행 후보에서 태스크까지

**예상 시간: 1분 10초**

계약 이행 태스크 후보의 범위를 조금 더 구체적으로 설명드리겠습니다.

이 기능은 모든 문서에서 인공지능이 해야 할 일을 자유롭게 만들어내는 기능이 아닙니다.

먼저 계약서와 변경계약서에서 규칙을 이용해 행동과 의무가 포함된 근거 구간을 찾습니다. 인공지능은 새 내용을 자유롭게 생성하는 대신, 미리 찾아둔 후보 안에서 필요한 항목을 선택합니다.

선택된 항목은 행위자와 기한, 근거 문장과 함께 검토 대기 상태로 저장됩니다. 사용자가 한 건씩 승인하면 그때 실제 태스크가 만들어지고, 거절하면 후보에서 제외됩니다.

현재 화면은 승인과 거절을 지원합니다. 수정 후 승인, 이미 승인한 항목의 취소, 분석 뒤 원문이 바뀌었는지 막는 기능은 다음 개선 항목입니다.

따라서 이 기능의 핵심은 자동 생성 자체가 아니라, 계약 문서의 근거가 있는 후보를 사람이 통제한 뒤 태스크로 연결하는 것입니다.

## 16번 — 금액 재분석과 확정본

**예상 시간: 1분 10초**

금액 정보는 재분석이 일어나도 대시보드 집계가 중간 상태로 흔들리지 않도록 확정본 방식으로 관리했습니다.

왼쪽은 현재 사용 중인 확정 결과입니다. 새로운 분석이 시작되더라도 대시보드와 질의응답, 산출물은 기존 확정본을 계속 사용합니다.

가운데에서 새 분석 결과를 검토합니다. 대기, 검토 중 단계를 거쳐 추출된 모든 항목의 검토가 끝나야 검토 완료가 됩니다.

[오른쪽 영역을 가리키기]

이 조건을 통과하면 대시보드와 근거 질의응답, 산출물이 새 확정본으로 동시에 전환됩니다.

예를 들어 열 건 중 아홉 건만 승인된 상태에서 일부 금액만 집계에 섞이지 않습니다. 열 건의 검토가 모두 끝날 때까지 기존 확정본을 유지하고, 완료되는 순간 기준을 한 번만 바꿉니다.

이를 통해 같은 시점의 대시보드와 산출물이 서로 다른 금액을 보여주는 문제를 방지했습니다.

## 17번 — 대시보드와 산출물

**예상 시간: 1분 10초**

사람이 승인한 정보는 최종적으로 대시보드와 산출물에서 사용됩니다.

[왼쪽 대시보드 영역을 가리키기]

왼쪽은 실제 제품 대시보드의 상단 구조를 축약한 화면입니다. 전체 문서와 처리 중인 문서, 추출 완료와 처리 실패, 열린 태스크를 한 번에 확인할 수 있습니다.

아래의 확인이 필요한 일에서는 처리 실패 문서, OCR 검수, 금액 승인 대기처럼 사람이 다음 행동을 해야 하는 항목을 모아서 보여줍니다. 액션 태스크 영역에서는 마감이 가까운 열린 태스크를 확인하고 전체 보드로 이동할 수 있습니다.

화면의 24건, 2건과 같은 숫자는 대시보드 배치를 보여주기 위한 예시 값입니다. 실제 실행에서는 프로젝트 데이터에 따라 집계됩니다.

[오른쪽 산출물 영역을 가리키기]

오른쪽에서는 승인된 같은 정보를 이용해 주간 보고서, 프로젝트 현황, 결정사항 대장, 회의 안건을 만듭니다. 출력 형식은 엑셀, 웹 문서, 마크다운, PDF를 지원합니다.

이렇게 검색과 분석에서 끝나는 것이 아니라, 사람이 확인한 정보가 실제 화면과 업무 문서까지 연결됩니다.

여기까지 문서를 검색하고 분석한 뒤, 사람이 승인한 정보가 실제 대시보드와 산출물로 이어지는 과정을 설명드렸습니다.

이제 박세현님이 최재정님이 구현한 OCR 처리 과정과, 본인이 담당한 인공지능 모델 적용 결과를 이어서 설명드리겠습니다.

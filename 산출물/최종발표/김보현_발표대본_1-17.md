# Tasqra 최종 발표 대본 — 김보현 1~21번

> 최신 슬라이드 순서 **1~21번** 기준입니다.
>
> 발표자: 김보현 / 예상 시간: 약 23~26분
>
> **22번 검색 결과 재정렬부터 박세현 발표입니다.** 22번 이후는 이 문서에서 다루지 않습니다.
>
> 21번 검색 모델 학습은 세현님이 만든 슬라이드이고 구현도 박세현입니다. 발표만 김보현이 합니다.

## 대본 사용 방법

- 일반 문장은 그대로 말해도 되는 대본이고, 대괄호는 행동 지시입니다.
- 숫자는 결과만 읽지 말고 평가 대상과 지표 뜻을 함께 말합니다.
- 구현 담당과 발표자를 구분합니다. 9번은 박세현·최재정, 10~11번 OCR은 최재정, 21번 검색 모델 학습은 박세현 구현이며 발표는 모두 김보현입니다.
- 임베딩 모델 선택 20번, 검색 모델 학습 21번, 재정렬 모델 22번은 평가 조건이 서로 다르므로 수치를 이어 붙여 전후 개선율처럼 말하지 않습니다.

## 전체 이야기

문제와 원칙 → 사용 흐름 → 팀 역할 → 그 흐름을 구현한 구조 → 공통 기반 → OCR → 검색 → 사람 검토와 업무 연결 → 임베딩 모델 선택 → 검색 모델 학습 → 재정렬 모델 인계 순서로 설명합니다.

## 1번 — 프로젝트 소개

**예상 시간: 50초**

안녕하세요. 공공 SI를 중심으로 한 공공 용역 프로젝트의 문서를 근거 있는 실행으로 연결하는 서비스, Tasqra를 발표할 김보현입니다.

Tasqra는 제안요청서, 계약서, 과업지시서와 각종 보고 문서를 읽고 검색 가능한 형태로 준비합니다. 인공지능이 문서에서 정보를 제안하면 사람이 확인하고, 승인된 정보만 태스크와 대시보드, 산출물로 연결합니다.

오늘은 왜 이 문제를 선택했는지부터 실제 서비스 흐름, 팀 역할과 시스템 구조, 검색 실험, 사람 검토와 업무 연결 순서로 설명드리겠습니다.

## 2번 — 공공 SI·용역 타깃 선정

**예상 시간: 1분 10초**

처음 공공 SI·용역을 선택한 이유는 공개 문서가 많아 학습과 검증 데이터를 확보하기 쉬울 것이라고 판단했기 때문입니다.

하지만 원문이 많다는 것과 정답이 표시된 학습·평가 자료가 충분하다는 것은 달랐습니다. 실제 문서는 많았지만 모델 결과가 맞는지 판단할 정답 샘플은 부족해 직접 평가 기준을 만들어야 했습니다.

진행하면서 이 분야가 서비스 문제에도 잘 맞는다는 점을 확인했습니다. 발주, 계약, 과업, 보고 문서의 정보가 서로 이어지고, 기한·금액·계약 이행 의무처럼 중요한 정보는 원문 근거와 사람 확인이 필요했습니다.

즉, 데이터 접근성이라는 가설로 시작해 실제 업무 문제와 데이터 한계를 함께 확인했습니다.

## 4번 — 전체 사용 흐름

**예상 시간: 1분 5초**

사용 흐름은 다섯 단계입니다. 문서를 업로드하고, PDF 글자와 OCR 결과를 검색 가능한 본문으로 정리합니다. 그다음 인공지능 분석과 검색 색인을 준비하고, 제안된 정보를 사람이 승인·수정·거절합니다. 마지막으로 승인된 정보만 태스크, 대시보드와 산출물에 반영합니다.

계약 이행 태스크도 바로 생성하지 않습니다. 계약 문서에서 행동과 의무 후보를 찾고 검토 대기로 저장한 뒤, 사람이 한 건씩 승인해야 실제 태스크가 됩니다.

이제 이 사용 흐름을 세 팀원이 어떻게 나눠 구현했는지 보겠습니다.

## 6번 — 시스템 아키텍처와 기술 선택

**예상 시간: 1분 35초**

저희는 하나의 요청을 FastAPI에서 바로 끝나는 요청과 오래 걸리는 작업, 두 경로로 나눴습니다.

[상단 사용자 화면에서 FastAPI까지 가리키기]

사용자 화면의 요청은 먼저 FastAPI로 들어옵니다. FastAPI가 요청을 검증하고 업무 처리를 시작한 뒤, 작업 시간에 따라 아래 두 경로로 나눕니다.

[왼쪽 ‘바로 끝나는 요청’을 가리키기]

바로 결과를 줄 수 있는 요청은 SQLAlchemy를 거쳐 PostgreSQL의 업무 데이터와 검색 벡터를 읽거나 저장합니다.

[오른쪽 ‘오래 걸리는 작업’을 위에서 아래로 가리키기]

OCR, 문서 나누기, AI 분석처럼 오래 걸리는 작업은 Redis 대기열에 등록합니다. Celery Worker가 대기 중인 작업을 이어서 처리하고, PostgreSQL과 문서 파일, AI 모델을 공유 자원으로 사용합니다.

[오른쪽 설계 이유를 가리키기]

이렇게 나누면 긴 작업 때문에 화면 요청이 멈추지 않고, Worker가 중단돼도 Redis에 작업이 남습니다. 재기동 뒤에도 같은 데이터와 문서 파일을 다시 조회할 수 있고, AI 모델도 호환 요청과 로컬 모델 경로를 통해 바꿔 연결할 수 있습니다.

정리하면 요청이 FastAPI에 들어오고, 작업 시간에 따라 분기된 뒤, 각 실행 경로에서 처리와 저장으로 이어지는 구조입니다.

이제 이 구조가 어떤 데이터를 중심으로 연결되는지 보겠습니다.

## 7번 — 핵심 데이터 구조

**예상 시간: 50초**

데이터는 프로젝트와 문서를 중심으로 연결됩니다. 프로젝트에는 구성원, 문서, 태스크와 검토 정보가 연결되고, 문서에는 추출 본문, OCR 기록, 분석 결과와 검색용 문서 조각이 연결됩니다.

문서 원본은 데이터베이스 BLOB이 아니라 API와 Worker가 함께 보는 파일 경로에 저장하고, 데이터베이스에는 파일 위치와 메타데이터를 보관합니다.

그래서 검색이나 분석 결과가 어느 프로젝트의 어떤 문서와 원문 위치에서 나왔는지 추적할 수 있습니다.

## 8번 — 상태를 나눈 이유

**예상 시간: 55초**

문서 추출, OCR 검수, AI 분석은 순서대로 이어지지만 상태는 하나로 합치지 않았습니다.

문서 추출은 대기·읽는 중·완료, OCR 검수는 대기·검수 중·완료, AI 분석은 대기·분석 중·완료·일부 완료·실패를 따로 저장합니다.

이렇게 하면 AI 분석이 실패해도 이미 끝난 문서 추출과 OCR 검수 결과는 유지됩니다. 어느 단계가 실패했는지 알 수 있고, 성공한 단계까지 처음부터 반복하지 않고 필요한 작업만 다시 실행할 수 있습니다.

## 9번 — 비동기 작업과 실패 처리

**구현 담당: 박세현·최재정 / 발표: 김보현**
**예상 시간: 1분 5초**

앞에서 상태를 분리했다면, 이 장은 오래 걸리는 작업을 실제로 어떻게 다시 처리하는지 보여줍니다.

OCR과 청킹 작업은 작업 확인을 늦게 확정해 Worker가 중단되면 대기열에 다시 넣고, 실패할수록 간격을 늘려 추가로 재시도합니다. 다음 단계가 실패해도 이미 성공한 OCR을 다시 돌리지 않습니다.

AI 분석은 같은 문서의 활성 작업이 중복되지 않게 하고, 시작 때의 원문 버전과 해시를 끝날 때 다시 확인합니다. 분석기를 차례로 실행해 요청 폭주를 막고, 일부만 성공하면 성공 결과는 보존하며, 제한 시간을 넘으면 중단합니다.

즉, 실패를 숨기는 것이 아니라 실패 범위를 작게 나눠 이어서 처리하도록 설계했습니다.

## 10번 — OCR 엔진 선택과 PDF 읽기

**구현 담당: 최재정 / 발표: 김보현**
**예상 시간: 1분 25초**

OCR은 본프로젝트에서 갑자기 정한 기술이 아니라 미니프로젝트에서 세 엔진을 직접 비교한 결과를 이어받았습니다.

[왼쪽 엔진 비교를 가리키기]

정답 텍스트와 OCR 결과의 문자 오류율을 이용해 정확도를 비교했습니다. 당시 저장된 기준선은 PaddleOCR 98.1퍼센트, EasyOCR 81.8퍼센트, Tesseract 64.4퍼센트였습니다. 처리 시간은 Tesseract가 약 0.9초로 가장 빨랐지만 정확도가 가장 낮았고, PaddleOCR과 EasyOCR은 각각 약 15.5초였습니다.

저희는 문서 내용을 검색과 분석에 다시 사용해야 했기 때문에 속도만으로 고르지 않고, 세 엔진 중 정답 정확도가 가장 높았던 PaddleOCR를 기본 OCR로 사용했습니다. 다만 이 수치는 미니프로젝트의 저장 기준선이지 모든 문서에서 같은 정확도를 보장한다는 뜻은 아닙니다.

[아래 흐름을 왼쪽부터 가리키기]

처리 시간을 줄이기 위해 모든 PDF를 무조건 OCR하지도 않습니다. PDF에 기존 글자가 있으면 먼저 보존하고, 텍스트층이 없는 이미지 영역만 OCR합니다. 글자가 전혀 없는 페이지는 두 배 크기로 렌더링해 전체 OCR하고, 결과 좌표는 원래 PDF 좌표로 되돌립니다. 마지막으로 단과 표 영역을 보존하면서 읽기 순서를 계산합니다.

즉, 미니프로젝트에서 엔진을 비교해 선택했고, 본프로젝트에서는 필요한 영역만 OCR해 수정 가능한 좌표와 읽기 순서를 남겼습니다.

## 11번 — OCR 수정과 검색 본문 동기화

**구현 담당: 최재정 / 발표: 김보현**
**예상 시간: 1분 5초**

사용자는 저장된 OCR 박스를 직접 수정하거나 선택한 영역만 다시 OCR할 수 있습니다. 이때 화면에 보이는 박스만 바꾸지 않습니다.

수정 범위를 확인하고 본문 구간을 교체한 뒤, 글자 수가 달라진 만큼 뒤 문장들의 원문 위치도 함께 옮깁니다. 문서 버전은 한 번만 증가시키고 검수 상태를 다시 확정합니다.

중간에 문제가 생기면 변경 전체를 취소합니다. 저장이 끝나면 문서 나누기와 의미 검색 자료도 다시 준비합니다.

그래서 화면에서 고친 글자와 검색에 쓰는 원문이 서로 달라지는 문제를 막습니다. 이렇게 확정된 본문이 다음 검색 단계의 입력이 됩니다.

## 12번 — 문서 분할과 임베딩 색인

**예상 시간: 1분 5초**

OCR 검수가 끝난 확정 본문을 문단 구조와 토큰 길이를 기준으로 나눕니다. 현재 최대 480토큰, 앞 문맥 48토큰을 겹쳐 경계에서 문맥이 끊기는 것을 줄였습니다.

각 문서 조각은 BGE-m3-ko로 1024차원 벡터로 바꿔 pgvector에 저장합니다. 질문도 같은 모델로 바꾼 뒤, 사용 권한이 있는 프로젝트 안에서 뜻이 가까운 조각을 찾습니다.

결과에는 문서명, 페이지와 원문 좌표를 함께 반환합니다. 임베딩 모델이 바뀌면 숫자의 기준도 달라지므로 기존 문서도 새 모델로 다시 색인해야 합니다.

## 13번 — 하이브리드 검색

**예상 시간: 1분 20초**

[왼쪽 키워드 검색을 가리키기]

키워드 검색은 계약번호, 금액, 날짜처럼 정확한 글자가 중요한 표현에 강합니다. 하지만 `휴가 규정`으로 검색했을 때 문서에 `연차 사용 기준`이라고만 적혀 있으면 같은 뜻이어도 놓칠 수 있습니다.

[오른쪽 의미 검색을 가리키기]

의미 검색은 표현이 달라도 뜻이 비슷한 문장을 찾습니다. 반대로 번호나 금액처럼 글자 자체가 정답인 표현은 정확한 값을 놓치거나 다른 문장을 앞세울 수 있습니다.

[가운데 순위 합산을 가리키기]

그래서 두 검색을 함께 사용했습니다. 다만 키워드 검색의 글자 유사도와 의미 검색의 벡터 거리는 단위와 분포가 달라 점수를 그대로 더하지 않았습니다.

[하단 세 카드를 왼쪽부터 가리키기]

먼저 키워드 검색과 의미 검색에서 각각 상위 30개 후보를 고릅니다. 그다음 점수 대신 각 검색 안에서의 순위를 사용하고, RRF가 두 순위를 합쳐 사용자에게 하나의 최종 결과 목록을 제공합니다.

같은 평가셋에서 단일 검색과 직접 비교한 실험은 아직 없기 때문에, 여기서는 성능 향상 수치가 아니라 서로 다른 누락 위험을 보완하는 검색 흐름을 설명드립니다.

## 14번 — 검색 규모 실험

**예상 시간: 1분 25초**

검색 대상이 커져도 정답을 앞에 보여줄 수 있는지 같은 모델과 질문 214개로 비교했습니다.

비교할 문서 조각이 30개일 때 첫 결과 정답률은 90.2퍼센트였지만, 전체 1,339개에서는 36.9퍼센트로 낮아졌습니다. 상위 5개 안에 정답이 하나라도 있는 질문의 비율도 98.9퍼센트에서 74.3퍼센트로 낮아졌습니다.

이 수치는 문서 수를 30개로 제한하자는 뜻이 아닙니다. 후보 범위가 커지면 첫 정답 순위가 무너진다는 실험이며, 문서 수 제한 없이 첫 결과 정답률을 높여야 한다는 과제를 보여줍니다.

## 15번 — 근거가 있는 질의응답

**예상 시간: 1분 5초**

검색 결과는 근거 질의응답으로 이어집니다. 권한 범위 안에서 최대 24개 후보를 찾고, 짧은 미리보기가 아니라 문서 조각 원문을 다시 읽습니다. 중복을 제거해 최대 8개 조각을 모델 입력으로 구성합니다.

모델이 답변과 사용한 근거 번호를 내놓으면, 서버는 번호가 실제 후보에 있는지, 권한 범위 안인지, 중복되지 않았는지 확인합니다. 확인이 끝나면 답변과 함께 문서명·페이지·원문 위치를 사용자에게 보여줍니다.

근거가 없으면 모델을 호출하지 않습니다. 다만 서버가 답변 의미 자체의 사실 여부까지 검증하는 것은 아니며, 근거 번호와 권한을 검증합니다.

## 16번 — 정보 종류별 사람 검토

## 17번 — 계약 이행 후보에서 태스크까지

사람은 태스크 후보를 한 건씩 확인합니다. 승인하면 실제 태스크가 생성되고, 거절하면 후보 목록에서 제외됩니다.

## 18번 — 금액 재분석과 확정본

[왼쪽 현재 사용 중인 확정본을 가리키기]

[가운데 새 분석 검토를 위에서 아래로 가리키기]

[굵은 화살표와 ‘동시 전환’을 가리키기]

모든 검토가 끝나는 순간에만 확정본을 한 번 교체합니다. 그러면 오른쪽의 대시보드, 근거 질의응답과 산출물이 모두 같은 새 확정본으로 동시에 바뀝니다.

따라서 열 건 중 아홉 건만 검토된 중간 결과가 집계에 섞이거나, 같은 시점의 화면과 산출물이 서로 다른 금액을 보여주는 문제를 막습니다.

## 20번 — 임베딩 모델 선택

**예상 시간: 1분 40초**

검색의 기본 임베딩 모델은 이름이 알려진 모델 하나를 바로 고르지 않고, 서로 다른 선택 축을 포함한 9개 후보를 같은 조건에서 비교했습니다.

후보에는 한국어 튜닝 모델과 최신 다국어 모델, bge와 e5 계열, 384·768·1024차원, 인코더와 디코더 계열이 포함됐습니다. 공개된 한국어 검색 성능을 참고하되, 로컬에서 실행 가능한지, 입력 길이와 계산 비용이 맞는지, 제품에서 사용할 수 있는 허용적 라이선스인지도 확인했습니다.

문서 10건, 청크 649개, 질문 133개를 사용했습니다. 이 가운데 질문과 정답의 글자가 겹치지 않는 64개에서 상위 5개 안에 정답이 하나라도 있으면 성공으로 계산했습니다.

BGE-m3-ko는 41개를 맞혀 64.1퍼센트였고, KURE-v1과 arctic-l-v2.0은 각각 37개였습니다. 전체 133개 질문에서도 102개, 76.7퍼센트로 1위였고 전체 비교의 통계값은 p=0.039였습니다.

다만 KURE와 안겹침 질문 차이는 네 문항이고 p=0.22라서 압도적인 우위라고 말할 수는 없습니다. 현재 자료에서 가장 일관되게 앞선 모델이라는 근거로 BGE-m3-ko를 선택했습니다.

여기서 Success@5는 상위 5개 안에 정답이 하나라도 있으면 성공으로 세는 내부 지표입니다. 공개 벤치마크의 표준 Recall@5와 정의가 달라 수치를 직접 비교하지 않습니다.

여기까지가 기본 임베딩 모델의 선택 근거입니다. 다음은 그 모델을 우리 문서에 맞게 학습시킨 결과입니다.

## 21번 — 검색 모델 학습 (하드 네거티브)

**구현 담당: 박세현 / 발표: 김보현**
**예상 시간: 1분 40초**

앞서 14번에서 검색 범위가 커질 때 첫 정답 순위가 무너지는 문제를 보여드렸습니다. 이 장은 그 문제를 모델 학습 쪽에서 개선한 결과입니다.

[왼쪽 위 두 막대를 가리키기]

먼저 확인한 것은 후보 개수가 같아도 난이도가 다르다는 점입니다. 비교할 후보를 똑같이 50개로 맞췄는데, 서로 다른 문서에서 고를 때는 첫 결과 정답률이 83.3퍼센트였고 같은 문서 안에서 고를 때는 57.0퍼센트였습니다. 하드 네거티브를 적용하기 전 모델 기준입니다.

즉 실제로 어려운 상대는 다른 문서가 아니라 같은 문서 안의 다른 문단이었습니다.

[왼쪽 아래 오답 구성을 가리키기]

그런데 기존 학습 방식은 한 묶음 안의 다른 샘플을 오답으로 사용합니다. 그 오답은 거의 다 다른 문서에서 오기 때문에, 모델이 실전에서 가장 헷갈리는 상대를 학습 중에는 본 적이 없었습니다.

그래서 오답을 같은 문서에서 직접 뽑았습니다. 뽑은 오답 1,200개 중 97.8퍼센트가 같은 문서에서 나온 문단입니다. 이때 정답 자신 400건, 바로 인접한 문단 746건, 같은 소제목 아래 120건, 본문이 60자 이상 겹치는 172건은 오답에서 제외했습니다. 사실상 정답인 문단을 오답으로 학습하면 안 되기 때문입니다.

[오른쪽 위 세 값을 왼쪽부터 가리키기]

결과는 전체 문서를 대상으로 질의 214개에서 측정했습니다. 첫 결과 정답률이 베이스 모델 16.8퍼센트, 오답을 따로 넣지 않은 파인튜닝 33.2퍼센트, 여기에 하드 네거티브를 더해 38.8퍼센트였습니다.

같은 문서 안과 밖의 성능 격차도 41.8퍼센트포인트에서 26.3, 20.5퍼센트포인트로 줄었습니다. 처음에 확인했던 난이도 차이 자체가 좁혀진 것입니다.

[오른쪽 아래 확인 항목을 가리키기]

의도한 곳이 올랐는지도 확인했습니다. 슬라이드 기준으로 첫 결과 정답률은 16.9퍼센트 개선됐고 상위 5개 포함률은 2.6퍼센트 개선됐습니다. 후보를 더 넓히는 장치가 아니라 1등을 바로 고르게 만드는 장치라는 설명과 개선 방향이 일치합니다.

첫 결과 정답률 90퍼센트를 유지할 수 있는 문서 범위도 9건에서 약 15건으로, 청크 기준 400개에서 700개로 넓어졌습니다. 대신 학습 쌍이 400개에서 1,200개로 늘어 학습 시간은 28분에서 2시간 26분이 됐습니다. 설정은 BGE-m3-ko에 LoRA를 적용한 36에포크이며, 48에포크는 성능이 꺾여 36으로 확정했습니다.

[하단 결론을 가리키기]

마지막으로 대조 실험도 했습니다. 효과를 만든 것은 오답을 같은 문서에서 뽑았다는 사실이었고, 가장 헷갈리는 것을 골랐기 때문은 아니었습니다.

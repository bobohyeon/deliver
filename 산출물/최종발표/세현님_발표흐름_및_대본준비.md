# Tasqra 최종 발표 흐름과 박세현 발표 준비

> 대상: 박세현
>
> 기준 자료: `Tasqra_최종발표_28장_v1.pptx`
>
> 전체 발표 시간: 약 31~38분 + 질의응답

## 1. 발표자와 구현 담당은 구분합니다

- **발표 순서**: 김보현 1~17번 → 박세현 18~27번 → 팀 전체 28번 질의응답
- **구현 담당 표기**: 각 슬라이드 아래의 `담당`을 따릅니다.
- 박세현이 발표하는 18~19번 OCR 슬라이드의 **구현 담당은 최재정**입니다. 발표자는 박세현이지만 구현자를 최재정으로 설명합니다.

## 2. 팀 역할 분담

| 팀원 | 대표 영역 | 주요 기능 |
|---|---|---|
| 김보현 | RAG 검색·정보 활용 | RAG 청킹·임베딩 색인, 하이브리드 검색·근거 QA, 금액 검토·대시보드·산출물 |
| 박세현 | LLM·임베딩 모델 | LLM 요약·분류 파인튜닝, 임베딩·리랭커 파인튜닝, 구조화 분석·AI 추천 |
| 최재정 | OCR·핵심 업무 흐름 | OCR 추출·본문 복원, OCR 검수·재OCR, 프로젝트·문서 처리·태스크 보드 |

## 3. 전체 발표 흐름

### 1~5번 — 타깃 · 서비스 소개 · 김보현

1. 공공 SI·용역 프로젝트를 위한 Tasqra 소개
2. 왜 공공 SI를 중심으로 한 공공 용역 사업의 수행 문서를 타깃으로 정했는지
   - 제안요청서부터 계약·과업지시·보고서까지 한 사업의 생애주기로 연결
   - 제출 기한·계약 이행 의무·금액은 원문 근거와 사람 확인이 필요
   - 공공 조달 특유의 문장·규정은 실제 도메인 문서로 검색 품질 검증 필요
3. 문서 근거를 찾고 사람이 확정한 뒤 업무로 연결하는 Tasqra의 목표
4. 팀 역할 분담
5. 문서 업로드부터 업무 반영까지의 전체 사용 흐름

### 6~8번 — 시스템 기반 구조 · 김보현

6. 서비스 전체 구성
7. 데이터 연결 관계
8. 문서 읽기·OCR 검수·AI 분석의 상태를 분리한 이유

### 9~13번 — RAG 검색과 근거 질의응답 · 김보현

9. 문서를 나누고 임베딩 색인을 만드는 과정
10. 키워드 검색과 의미 검색을 함께 쓰는 하이브리드 검색
11. 검색 범위가 커졌을 때 정확도가 낮아진 실제 실험
12. 리랭커가 기존 검색 후보의 순서를 개선한 결과
13. 답변과 함께 문서명·페이지·원문 위치를 제공하는 근거 QA

### 14~17번 — 사람 검토와 업무 반영 · 김보현

14. AI 결과를 바로 사용하지 않고 사람이 검토하는 구조
15. 계약 이행 태스크 후보 승인
16. 금액 재분석 중에도 기존 확정 결과를 유지하는 방식
17. 승인된 정보를 실제 대시보드와 산출물에 사용하는 과정

### 발표자 전환 · 김보현 → 박세현

김보현 마무리 문장:

> 여기까지 문서를 분석하고 사람이 승인한 정보가 실제 대시보드와 산출물로 이어지는 과정을 설명드렸습니다. 이제 박세현님이 문서를 안정적으로 읽는 과정과 AI 모델 적용 결과를 설명드리겠습니다.

박세현 시작 문장:

> 이어서 문서를 실제로 어떻게 읽고, 수정된 본문을 검색과 AI 분석까지 안정적으로 연결했는지 설명드리겠습니다.

## 4. 박세현 담당 발표: 18~27번

### 18번 — 페이지에 맞는 문서 읽기

**구현 담당: 최재정 / 발표: 박세현**

핵심 메시지:

> PDF에 글자가 이미 있으면 그대로 사용하고, 스캔 이미지는 OCR로 읽으며, 두 결과가 있으면 페이지 위치에 맞춰 합칩니다.

설명 순서:

1. PDF에 기존 글자가 있으면 보존
2. 스캔 페이지는 전체 OCR
3. 두 결과가 있으면 페이지 위치 순서로 결합
4. 사람이 고칠 수 있는 OCR 영역과 원문 위치를 함께 저장

다음 장 연결:

> 문서를 읽는 것만으로 끝나지 않고, 사용자가 OCR 결과를 수정했을 때 검색 본문도 함께 바뀌어야 합니다.

### 19번 — OCR 수정과 검색 본문 동기화

**구현 담당: 최재정 / 발표: 박세현**

핵심 메시지:

> 화면에서 OCR 글자를 수정하면 검색에 사용하는 본문과 문서 위치도 동시에 수정합니다.

설명 순서:

1. OCR 박스 수정
2. 수정 범위 검증
3. 본문 구간 교체
4. 뒤 문장 위치 조정
5. 문서 버전 증가
6. 검수 상태 재확정

강조할 점:

- 중간에 문제가 생기면 변경 전체를 취소
- 수정이 끝나면 문서 나누기와 의미 검색을 다시 준비
- 화면의 글자와 검색 원문이 달라지는 문제를 방지

다음 장 연결:

> 이런 문서 처리 작업은 시간이 오래 걸릴 수 있기 때문에, 실패해도 안전하게 다시 실행할 수 있어야 합니다.

### 20번 — 오래 걸리는 작업의 실패 처리

**구현 담당: 박세현·최재정 / 발표: 박세현**

핵심 메시지:

> OCR·문서 나누기·AI 분석이 실패해도 이미 성공한 작업까지 처음부터 반복하지 않습니다.

설명할 내용:

- 사라진 작업은 대기열에 다시 등록
- 실패한 작업은 간격을 두고 재시도
- 이미 성공한 OCR은 반복하지 않음
- AI 분석 전후로 원문이 변경됐는지 확인
- 일부 분석만 성공해도 성공한 결과는 보존
- 제한 시간을 넘긴 작업은 중단

다음 장 연결:

> 이 안정적인 처리 흐름 위에 업무별로 학습한 모델을 연결했고, 다음은 저장된 실제 평가 결과입니다.

### 21번 — 실제 모델 평가 결과

**구현 담당: 박세현 / 발표: 박세현**

숫자만 읽지 말고 **무엇을, 몇 건으로, 어떻게 평가했는지** 함께 설명합니다.

#### 문서 종류 분류

- 결과: **93.2%**
- 평가 대상: 실제 문서 **103건**
- 평가 방법: **5등분 교차검증**
- 오차: **±2.5%p**
- 적용 모델: `Tasqra-classification`

#### 문서 요약

- 결과: **65.4%**
- 평가 대상: 실제 문서 **26건**
- 오차: 약 **±8%p**
- 적용 모델: `Tasqra-summation`

주의해서 말할 부분:

> 분류 결과는 비교적 안정적이지만, 요약은 평가 문서가 26건이라 결과 변동 폭이 큽니다. 따라서 평가 문서를 늘려 다시 확인해야 합니다.

### 22번 — 박세현 최종 학습 자료

현재는 **박세현 작성 예정** 자리입니다. 최종 자료를 받으면 내용만 교체합니다.

권장 구성:

1. 왜 추가 학습이 필요했는지
2. 어떤 학습·평가 자료를 사용했는지
3. 학습 전후 결과가 어떻게 달라졌는지
4. 실제 적용 모델과 남은 한계

21번과 중복되지 않도록, 가능하면 22번에는 **LLM·임베딩·리랭커 학습 과정 또는 학습 전후 비교**를 넣습니다.

### 23번 — 정보 종류마다 다른 추출 방법

**구현 담당: 김보현·최재정·박세현 / 발표: 박세현**

핵심 메시지:

> 결정사항·일정·계약 이행 태스크 후보를 모두 같은 방법으로 찾지 않습니다.

- 결정사항: AI가 찾고 원문과 비교
- 일정: 프로그램이 날짜 후보를 먼저 찾고 AI는 날짜 역할만 구분
- 계약 이행 태스크 후보: 규칙으로 행동·의무 문장을 찾고 AI는 후보 안에서만 선택
- 각각 별도의 검토 목록에 대기 상태로 저장

반드시 제한해서 말할 부분:

> AI가 새로운 태스크를 자유롭게 만드는 것이 아닙니다. 계약·변경계약 문서에서 미리 찾아둔 행동·의무 후보 중 필요한 항목을 선택합니다.

### 24번 — 긴 문서의 실제 오류 해결

**구현 담당: 박세현 / 발표: 박세현**

핵심 메시지:

> 눈에 보이지 않는 특수문자 516개 때문에 인용문 확인이 실패했습니다.

슬라이드의 세로 흐름대로 설명합니다.

1. **문제 발견**
   - 특수문자 516개 발견
   - 사람 눈에는 같지만 프로그램은 다른 문장으로 판단
2. **원문 정리**
   - 특수문자를 같은 길이의 공백으로 변경
   - 글자 수와 원문 위치 유지
   - 탭과 줄바꿈은 문단 구조 때문에 보존
3. **확인 방식 보완**
   - 공백·특수문자 차이를 허용
   - 틀린 인용만 제거
   - 원문 시작·끝 위치 유지

결론 문장:

> 특수문자를 제거하면서도 글자 수를 유지해 기존 원문 위치를 다시 계산하지 않고 인용문 확인에 성공했습니다.

### 25번 — 제품 시연

예상 시간: **3~4분**

영상 흐름:

1. 문서 업로드
2. OCR 검수
3. 근거가 있는 질의응답
4. 계약 이행 태스크 후보 승인
5. 대시보드와 산출물 확인

시작 문장:

> 지금까지 설명한 기능들이 실제 제품에서 하나의 흐름으로 연결되는 모습을 영상으로 확인하겠습니다.

영상이 끝난 뒤:

> 문서 업로드부터 사람 검토와 실제 업무 반영까지 하나의 제품 흐름으로 연결되는 것을 확인했습니다.

### 26번 — 현재 한계와 다음 개선

다음 네 가지를 솔직하게 설명합니다.

1. 문서가 많아지면 첫 검색 결과 정확도가 낮아짐
2. 요약 평가는 문서 26건이라 오차가 큼
3. 계약 이행 후보 화면은 현재 승인·거절만 지원
4. 전체 자동 테스트와 운영 상태 확인 도구가 부족

가장 중요한 다음 목표:

> 문서 수를 제한하지 않고 첫 검색 결과 정답률 90%를 달성할 수 있는지 검증하는 것입니다.

### 27번 — 결론

발표 전체를 세 문장으로 정리합니다.

1. 문서에서 근거를 찾습니다.
2. AI가 제안한 정보를 사람이 확정합니다.
3. 승인된 정보를 실제 태스크·대시보드·산출물로 연결합니다.

마무리 문장:

> Tasqra는 단순히 문서를 저장하는 서비스가 아니라, 문서에서 판단 근거를 찾고 사람이 확정한 정보를 실제 업무로 연결하는 플랫폼입니다.

### 28번 — 질의응답

김보현·박세현·최재정이 함께 질문을 받습니다.

## 6. 대본 작성 시 주의할 표현

- 서비스 타깃은 **공공 SI를 중심으로 한 공공 용역 사업의 수행 문서**입니다. 공공기관의 모든 문서를 관리한다고 넓혀 말하지 않습니다.
- 김보현은 **RAG 청킹·임베딩 색인·하이브리드 검색**, 박세현은 **임베딩·리랭커 모델 파인튜닝**으로 구분합니다.
- 계약 이행 태스크는 모든 문서에서 자유 생성하는 기능이 아닙니다.
- 계약·변경계약 문서의 행동·의무 후보 중 AI가 선택하고, 사람이 승인해야 실제 태스크가 됩니다.
- 21번 평가 결과는 표본 수와 오차를 숫자와 함께 말합니다.
- 검색 실험 수치는 평가셋과 후보 범위가 다르면 직접적인 전후 개선율로 비교하지 않습니다.

# Tasqra 최종 발표 흐름과 박세현 발표 준비

> 대상: 박세현
>
> 기준 자료: 새 순서 1~21 SVG. 22번 이후는 박세현 수정 구간
>
> 전체 발표 시간: 22번 이후 최종 구성 확정 뒤 다시 계산

## 1. 발표자와 구현 담당은 구분합니다

- **발표 순서**: 김보현 1~21번 → 박세현 22번부터 (21번 검색 모델 학습은 세현님 슬라이드를 김보현이 발표)
- **구현 담당 표기**: 각 슬라이드 아래의 `담당`을 따릅니다.
- 김보현이 발표하는 10~11번 OCR 슬라이드의 **구현 담당은 최재정**입니다.

## 2. 팀 역할 분담

| 팀원 | 대표 영역 | 주요 기능 |
|---|---|---|
| 김보현 | RAG 검색·정보 활용 | RAG 청킹·임베딩 색인, 하이브리드 검색·근거 QA, 금액 검토·대시보드·산출물 |
| 박세현 | LLM·임베딩 모델 | LLM 요약·분류 파인튜닝, 임베딩·리랭커 파인튜닝, 긴 문서 분석 오류 개선 |
| 최재정 | OCR·핵심 업무 흐름 | OCR 추출·본문 복원, OCR 검수·재OCR, 프로젝트·문서 처리·태스크 보드 |

## 3. 전체 발표 흐름 — 새 1~21 순서

### 1~6번 — 문제에서 역할과 구현 구조까지 · 김보현

1. 공공 SI·용역 프로젝트를 위한 Tasqra 소개
2. 타깃 선정 과정과 정답 표본 부족이라는 실제 한계
3. AI가 제안하고 사람이 확정하는 원칙
4. 문서 업로드부터 승인 정보 반영까지의 전체 사용 흐름
5. 이 제품 흐름을 구현한 팀 역할 분담
6. 동기 요청과 비동기 작업으로 나눈 시스템 아키텍처·기술 선택

### 7~11번 — 공통 기반과 OCR · 김보현

7. 프로젝트·문서 중심 데이터 연결 관계
8. 문서 추출·OCR 검수·AI 분석 상태를 분리한 이유
9. 오래 걸리는 작업의 재시도와 부분 실패 처리
10. 미니프로젝트 3종 비교로 PaddleOCR를 선택하고, 텍스트층·이미지 영역·전체 페이지를 분기 처리 — 구현 최재정
11. 박스 수정·선택 재OCR과 검색 본문 동기화 — 구현 최재정

### 12~18번 — 검색과 근거에서 업무 연결까지 · 김보현

12. 문서 분할과 임베딩 색인
13. 키워드·의미 검색의 서로 다른 누락 사례와 점수 대신 RRF 순위를 합친 설계 근거
14. 문서명·페이지·원문 위치를 제공하는 근거 질의응답
15. 정보 종류별 사람 검토
16. 계약 이행 후보 승인 후 태스크 생성
17. 금액 재분석 중 기존 확정본 유지
18. 승인 정보를 대시보드·산출물로 연결

### 19~21번 — 검색 정확도 개선 한 덩어리 · 김보현

문제 제기부터 모델 학습까지 끊지 않고 이어서 말합니다. **검색 규모 실험이 14번에서 19번으로 내려왔습니다.**

19. 검색 범위가 커졌을 때 첫 정답 순위가 무너진 실험 — 문제 제기
20. 9개 후보 비교와 BGE-m3-ko 선택 근거 — 어떤 모델을 쓸지
21. 같은 문서에서 뽑은 오답으로 학습해 첫 결과 정답률을 올린 결과 — 구현 박세현, 발표 김보현

### 21번 — 검색 모델 학습 (하드 네거티브) · 발표만 김보현

**구현 담당: 박세현 / 발표: 김보현**

세현님이 만든 슬라이드이고 구현도 박세현이지만, **발표는 김보현이 합니다.**
같은 문서에서 뽑은 오답을 함께 학습시켜 첫 결과 정답률을 16.8 → 33.2 → 38.8퍼센트로
올린 내용이며, 김보현 대본에 21번으로 들어가 있습니다.

### 발표자 전환 · 김보현 → 박세현

**전환 지점이 21번 뒤로 바뀌었습니다.** 20번이 아닙니다.

김보현 마무리 문장:

> 여기까지 임베딩 모델을 우리 문서에 맞게 학습시킨 결과였습니다. 이제 박세현님이 검색 후보의 순서를 다시 정하는 재정렬 모델부터 이어서 설명하겠습니다.

박세현 시작 문장:

> 이어서 기본 검색이 찾은 후보를 다시 읽고, 정답을 더 앞에 배치하도록 학습한 재정렬 모델 결과를 설명드리겠습니다.

## 4. 박세현 담당 발표: 22번부터

### 22번 — 검색 결과 재정렬

**구현 담당: 박세현 / 발표: 박세현**

시작 문장:

> 이어서 기본 검색이 찾은 후보를 다시 읽고, 정답을 더 앞에 배치하도록 학습한 재정렬 모델 결과를 설명드리겠습니다.

핵심 메시지:

> 재정렬 모델은 이미 찾은 후보의 순서를 개선하지만, 후보에 없는 정답을 새로 찾지는 못합니다.

설명 순서:

1. 임베딩 단독 첫 결과 정답률: **33.18%**
2. 재정렬 학습 전: **34.11%**
3. 재정렬 학습 후: **49.07%**
4. 학습 전에서 후로 **14.96%p** 상승
5. 상위 5개 정답 포함률: **72.43% → 71.50% → 80.84%**
6. 한 번 처리 시간: **0.192초**

주의해서 말할 부분:

- 20번 임베딩 모델 선택, 21번 검색 모델 학습, 22번 재정렬 결과는 평가 조건이 서로 다르므로 직접적인 전후 개선율로 비교하지 않습니다.
- 재정렬은 벡터·키워드 후보와 RRF 결과를 다시 읽어 순서만 바꿉니다.
- 기본은 비활성이고 GPU 사용을 권장하며, 실패하면 원래 검색 순서를 사용합니다.

다음 장 연결 문장은 박세현님이 수정 중인 22번 최종 내용에 맞춰 연결합니다.

### 22번 — 박세현 최종 학습 자료

현재는 **박세현 작성 예정** 자리입니다. 최종 자료를 받으면 내용만 교체합니다.

권장 구성:

1. 왜 추가 학습이 필요했는지
2. 어떤 학습·평가 자료를 사용했는지
3. 학습 전후 결과가 어떻게 달라졌는지
4. 실제 적용 모델과 남은 한계

21번과 중복되지 않도록, 가능하면 22번에는 **LLM·임베딩·리랭커 학습 과정 또는 학습 전후 비교**를 넣습니다.

### 23번 — 정보 종류마다 다른 추출 방법

**구현 담당: 김보현·최재정·박세현 / 발표: 박세현**

핵심 메시지:

> 결정사항·일정·계약 이행 태스크 후보를 모두 같은 방법으로 찾지 않습니다.

- 결정사항: AI가 찾고 원문과 비교
- 일정: 프로그램이 날짜 후보를 먼저 찾고 AI는 날짜 역할만 구분
- 계약 이행 태스크 후보: 규칙으로 행동·의무 문장을 찾고 AI는 후보 안에서만 선택
- 각각 별도의 검토 목록에 대기 상태로 저장

반드시 제한해서 말할 부분:

> AI가 새로운 태스크를 자유롭게 만드는 것이 아닙니다. 계약·변경계약 문서에서 미리 찾아둔 행동·의무 후보 중 필요한 항목을 선택합니다.

### 24번 — 긴 문서의 실제 오류 해결

**구현 담당: 박세현 / 발표: 박세현**

핵심 메시지:

> 눈에 보이지 않는 특수문자 516개 때문에 인용문 확인이 실패했습니다.

슬라이드의 세로 흐름대로 설명합니다.

1. **문제 발견**
   - 특수문자 516개 발견
   - 사람 눈에는 같지만 프로그램은 다른 문장으로 판단
2. **원문 정리**
   - 특수문자를 같은 길이의 공백으로 변경
   - 글자 수와 원문 위치 유지
   - 탭과 줄바꿈은 문단 구조 때문에 보존
3. **확인 방식 보완**
   - 공백·특수문자 차이를 허용
   - 틀린 인용만 제거
   - 원문 시작·끝 위치 유지

결론 문장:

> 특수문자를 제거하면서도 글자 수를 유지해 기존 원문 위치를 다시 계산하지 않고 인용문 확인에 성공했습니다.

### 25번 — 제품 시연

예상 시간: **3~4분**

영상 흐름:

1. 문서 업로드
2. OCR 검수
3. 근거가 있는 질의응답
4. 계약 이행 태스크 후보 승인
5. 대시보드와 산출물 확인

시작 문장:

> 지금까지 설명한 기능들이 실제 제품에서 하나의 흐름으로 연결되는 모습을 영상으로 확인하겠습니다.

영상이 끝난 뒤:

> 문서 업로드부터 사람 검토와 실제 업무 반영까지 하나의 제품 흐름으로 연결되는 것을 확인했습니다.

### 26번 — 현재 한계와 다음 개선

다음 네 가지를 솔직하게 설명합니다.

1. 문서가 많아지면 첫 검색 결과 정확도가 낮아짐
2. 요약 평가는 문서 26건이라 오차가 큼
3. 계약 이행 후보 화면은 현재 승인·거절만 지원
4. 전체 자동 테스트와 운영 상태 확인 도구가 부족

가장 중요한 다음 목표:

> 문서 수를 제한하지 않고 첫 검색 결과 정답률 90%를 달성할 수 있는지 검증하는 것입니다.

### 27번 — 결론

발표 전체를 세 문장으로 정리합니다.

1. 문서에서 근거를 찾습니다.
2. AI가 제안한 정보를 사람이 확정합니다.
3. 승인된 정보를 실제 태스크·대시보드·산출물로 연결합니다.

마무리 문장:

> Tasqra는 단순히 문서를 저장하는 서비스가 아니라, 문서에서 판단 근거를 찾고 사람이 확정한 정보를 실제 업무로 연결하는 플랫폼입니다.

### 28번 — 질의응답

김보현·박세현·최재정이 함께 질문을 받습니다.

## 6. 대본 작성 시 주의할 표현

- 서비스 타깃은 **공공 SI를 중심으로 한 공공 용역 사업의 수행 문서**입니다. 공공기관의 모든 문서를 관리한다고 넓혀 말하지 않습니다.
- 박세현은 **LLM 요약·분류, 임베딩·리랭커 파인튜닝, 긴 문서 분석 오류 개선**을 담당했습니다. 프로젝트 진행 상황을 보고 다음 작업을 추천하는 AI 기능은 구현하지 않았으므로 박세현 담당 기능으로 말하지 않습니다.
- 계약 이행 태스크 후보는 제품에 구현된 별도 기능입니다. 이는 모든 문서에서 다음 작업을 자유롭게 추천하는 기능이 아니라, 계약·변경계약 문서에서 규칙으로 찾은 행동·의무 후보 중 필요한 항목을 선별하고 사람이 승인하는 제한된 흐름입니다.
- 김보현은 **RAG 청킹·임베딩 색인·하이브리드 검색**, 박세현은 **임베딩·리랭커 모델 파인튜닝**으로 구분합니다.
- 계약·변경계약 문서의 행동·의무 후보 중 AI가 선택하고, 사람이 승인해야 실제 태스크가 됩니다.
- 22번 재정렬 결과는 20번 임베딩 모델 선택·21번 검색 모델 학습과 평가 조건이 다르므로 직접적인 전후 개선율로 말하지 않습니다.
- 21번의 질의 214개가 14번 검색 규모 실험과 같은 평가셋인지 김보현과 맞춰야 합니다. 확인 전에는 두 장의 수치를 이어 붙이지 않습니다.
- 검색 실험 수치는 평가셋과 후보 범위가 다르면 직접적인 전후 개선율로 비교하지 않습니다.
